# BE API 연결 규칙 (mock → fetch)

> ⚠️ **초안(draft).** 퍼블리싱이 끝나고 BE 계약이 나오는 단계에서 쓴다. fetch 방식·인증·환경변수
> 같은 미확정 항목은 §7에 모아뒀고, 실제 BE가 정해지면 이 스킬을 확정본으로 갱신한다.

이 스킬의 핵심은 두 가지다: **(1) mock을 실제 fetch로 안전하게 갈아끼우기**, **(2) 그 과정에서
web·mobile 공통이 되는 것을 언제·무엇을 공용으로 뺄지 판단하기.** 배경은 [ADR 0011 공용 경계](../../docs/adr/0011-shared-code-boundary.md)와 [ADR 0005 승격 절차](../../docs/adr/0005-web-home-and-ui-promotion.md).

---

## 1. 전제 — 왜 이 단계가 특별한가

퍼블리싱 때는 각 앱 `_lib/mock.ts`가 화면에 데이터를 먹였다(타입은 `_lib/types.ts` = **BE 목표 shape**).
BE가 붙으면 그 mock을 실제 응답으로 교체한다. 이때 **도메인 데이터의 모양이 처음으로 굳으므로**,
"무엇을 공용으로 뺄지"를 판단하기 딱 좋은(그리고 처음으로 정당한) 시점이다 — [ADR 0011 게이트 C](../../docs/adr/0011-shared-code-boundary.md).

---

## 2. 순서 (엔드포인트 하나 = 작업 하나)

1. **티켓·엔드포인트 파악** — Jira에서 요구/완료조건, 응답 예시(shape·필드·페이지네이션)를 정리.
2. **응답 shape ↔ 도메인 타입 대조** — BE 응답을 기존 `types.ts`(`FeedPost`·`Comment` 등)와 맞춰본다.
   - 같으면 그대로. 다르면 **타입을 BE에 맞춰 조정**하고, **web·mobile 양쪽 `types.ts`를 같은 모양으로**
     동기화한다(현재는 수동 동기화 계약 — web `types.ts` 헤더 참고).
   - BE 필드명이 화면 관용과 다르면 **경계에서 변환**(예: `view_count → views`). 변환은 데이터 레이어에서.
3. **데이터 접근 레이어 작성** — fetch/변환을 `_lib`에 둔다(예: `_lib/api.ts` 또는 도메인별 `getPosts.ts`).
   화면 컴포넌트는 **소비 형태를 그대로 유지**하고 mock 대신 이 레이어의 결과를 받는다(§4).
4. **로딩/에러/빈 상태** — §5.
5. **공용화 판단** — §3. 이 PR에서 뺄지, 후보로만 기록할지 결정.
6. **검증** — 실제(또는 스텁) 응답으로 양쪽 앱 렌더 확인 + 클린 빌드(§6).
7. **커밋·PR** — 티켓 키 포함, `develop` 기준 브랜치, CI 통과. **병합은 사용자.**

---

## 3. ⭐ 공용화 판단 — 이 스킬의 핵심

BE를 붙이며 "web·mobile이 같은 걸 쓰네"가 보일 때, **바로 빼지 말고** 아래 규칙으로 나눈다.

### 3-1. 무엇을 어디로 (종류가 기준이다)

| 종류                                                                 | 어떻게                                                                                                                                                      | 왜                                                                                             |
| -------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------- |
| **데이터/타입** (응답 shape, `FeedPost`·`Comment`, 팀 레지스트리 등) | BE가 확정 + 양쪽이 같은 모양을 쓰면 → **공용으로 승격 검토**(`@plick/types` 또는 `@plick/core` 신설). 지금의 "수동 동기화"를 **단일 정의 + 양쪽 import**로. | BE가 모양을 정하므로 이때 굳는다. 굳은 계약은 한 곳에 두는 게 드리프트를 막는다.               |
| **화면 표현** (`ArticleBody`·리스트·시트 등 화면 컴포넌트)           | **앱별 유지.** BE가 붙어도 안 뺀다.                                                                                                                         | 스케일·인터랙션(hover vs active)·레이아웃이 web/mobile에서 다르다. 하나로 합치면 variant 폭발. |
| **순수 원자·유틸** (아이콘·썸네일·배지, `formatCount`)               | BE와 무관하게, **두 번째로 쓰이면 언제든** `@plick/ui`로.                                                                                                   | 도메인이 없어 굳을 걸 기다릴 필요가 없다.                                                      |

> 한 줄: **데이터는 공용, 표현은 앱별, 원자는 두 번째 쓰이면 공용.**

### 3-2. 승격 게이트 (ADR 0011) — 셋 다 통과해야 뺀다

- **A. 앱 역참조 금지(hard)** — 패키지가 `@/_lib/…`·라우트·`TEAMS`를 내부에서 조회하면 실격.
  못 끊으면 승격 불가, 끊으려면 **값을 prop로 주입**(예: `MediaThumb`은 `TeamCode`가 아니라 `colorVar`를 받음).
- **B. 동일성** — 두 앱에서 스케일·인터랙션·레이아웃이 **정말 같은가.** 갈리면 앱별.
- **C. 성숙도** — **두 번째 실사용처가 이미 있고** 모양이 굳었는가. BE로 shape가 확정된 지금이 이 관문이 서는 때.

### 3-3. 타이밍 — 첫 API는 앱별, 두 번째에서 공용

엔드포인트를 **하나씩** 붙이며, **첫 앱에선 그냥 앱별로** 붙인다. 두 번째 앱에서 **같은 shape를 또 쓰게 될 때**
"이건 공용" 하고 올린다. 첫 번째부터 "언젠가 공유하겠지"로 미리 빼지 않는다(조기 추상화 방지).

### 3-4. 확신 안 서면 앱별로 두고 "후보"로 기록

기본값(앱별·주입)은 **되돌리기 싸다.** 애매하면 승격하지 말고, ADR 0011 §7의 열린 후보 목록에
한 줄 남긴다. 근거가 필요하면 추측 말고 `/audit`(code-audit)으로 진짜 중복인지 확인 후 결정.

---

## 4. mock → fetch 교체가 쉬운 이유 (설계 유지)

퍼블리싱 때 화면은 **mock을 "데이터"로만 소비**하도록 짜여 있다(props로 받아 렌더). 그래서 교체는
**공급원만 바꾸는 일**이다.

- 서버 컴포넌트는 페이지/레이아웃에서 데이터 레이어를 `await`해 자식에 내려준다(현재 `getPost(id)`가
  하던 자리를 `await getPost(id)` fetch로).
- **mock.ts는 지우지 말고 판단** — BE 미완 화면의 fallback이나 개발용으로 남길 수 있다. 완전 대체되면 제거.
- 타입은 이미 BE 목표 shape라 대개 그대로. 필드 차이는 §2-2의 경계 변환으로 흡수.

---

## 5. 로딩·에러·빈 상태 (퍼블리싱엔 없던 것)

mock은 항상 성공·즉시였지만 fetch는 아니다. 화면마다 **세 상태**를 토큰으로 처리한다:

- **로딩**: Next `loading.tsx`(라우트) 또는 Suspense. 스켈레톤은 `bg-elevate`/`bg-media` 토큰으로.
- **에러**: `error.tsx` 또는 분기. 재시도 버튼은 기존 버튼 토큰 재사용.
- **빈 상태**: 홈 `NewsFeed`의 "아직 이 팀 소식이 없어요"(`text-text-4`) 같은 기존 패턴을 따른다.

하드코딩 색/문구 금지 — 색은 토큰, 문구는 화면 카피 규칙대로.

---

## 6. 검증

- **양쪽 앱 클린 빌드** — 공용(타입/패키지)을 건드렸으면 `pnpm --filter web build` + `pnpm --filter mobile build` 둘 다(회귀).
- **실제(또는 스텁) 응답으로 렌더** — 로컬 dev로 로딩→성공→에러→빈 상태를 실제로 밟아 확인(mock 즉시성에 속지 말 것).
- **타입** `pnpm check-types`, format:check·lint, CI 통과.

---

## 7. ⚠️ BE 확정 시 정할 것 (지금은 열린 항목)

이 초안이 **가정하지 않고 사용자에게 확인**해야 할 것들 — BE가 정해지면 이 스킬에 확정 기입:

- fetch 방식(순수 `fetch` + 서버 컴포넌트 / React Query 등 클라 캐시 도입 여부).
- API base URL·환경변수 이름, 프리뷰/프로덕션 분리.
- 인증(토큰 저장·주입) — **자격증명 처리는 사용자 몫**(직접 입력·저장 금지 규칙 준수).
- 페이지네이션·무한스크롤(릴스·피드) 계약, 재검증(revalidate) 전략.
- 데이터 레이어 파일 관례(`_lib/api.ts` 단일 vs 도메인별 파일), 공용 타입 패키지 신설 여부(`@plick/types`).

불명확하면 **추측하지 말고 사용자에게 확인한다.**
