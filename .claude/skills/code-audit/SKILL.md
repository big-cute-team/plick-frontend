# 코드 구조 감사 (code-audit)

코드베이스를 **빠짐없이 한 번씩** 훑어 구조적으로 고칠 부분을 리스트업한다.
수정이 목적이 아니라 **정확한 목록**이 목적 — 수정은 리포트 후 사용자 승인을 받아서만.

## 0. 판단 기준 먼저 로드

감사 기준은 이 저장소의 규칙 그 자체다. 감사 전 반드시 읽는다(이미 컨텍스트에 있으면 재독 불필요):

- `CLAUDE.md`의 **컨벤션** 섹션 (토큰, `_lib` 분리, 절대경로 import, 주석 스타일)
- `screen-publishing` 스킬 (토큰 목록, 컴포넌트 배치 규칙, 아이콘 규칙)
- `docs/adr/0002-mobile-home-layout.md` (레이아웃 패턴의 근거)

## 1. 전수 커버리지 — 샘플링 금지

이 감사의 가치는 "전부 봤다"는 보장에서 나온다. 눈에 띄는 파일만 골라 보면
중복은 절대 못 잡는다(중복은 정의상 서로 다른 곳에 흩어져 있다).

- 대상 목록 확정: `git ls-files 'apps/*' 'packages/*' | grep -E '\.(ts|tsx|css|mjs)$'`
  (인자로 범위 경로가 오면 그 하위만). `package.json`·설정 파일은 배치 판단에 필요할 때만 참조.
- **이 목록이 곧 체크리스트다.** 파일 수를 세고, 리포트에 "검사 n/n개"로 커버리지를 명시한다.
- **~40개 이하**면 직접 전부 읽는다. 그보다 크면 디렉토리 묶음별로 Explore 서브에이전트를
  **병렬**로 띄운다. 이때 각 에이전트에 (1) 이 스킬 파일 경로, (2) **정확한 파일 목록**,
  (3) 아래 요약 스키마를 준다. 막연히 "이 폴더를 봐라"라고 하면 빠뜨린다.
- 중복 탐지는 파일들을 **가로질러** 비교해야 하므로, 서브에이전트는 파일별 요약만 만들고
  교차 비교는 요약을 모아 메인 컨텍스트에서 한다.

서브에이전트 요약 스키마 (파일별):

```
경로 | 역할 한 줄 | export 목록 | 그리는 UI 요약(중복 대조용, 컴포넌트만)
| 체크리스트 위반 목록(항목·라인·근거) | 토큰이 아닌 색/px 클래스 목록
```

## 2. 체크리스트

### A. 중복 (같은 것이 두 군데 이상)

- 유사한 UI를 그리는 컴포넌트가 서로 다른 라우트 `_components/`에 따로 구현됨
  (예: 두 화면의 리스트 행·카드·필드가 사실상 같은 마크업)
- 같은 의미의 타입·인터페이스가 여러 `_lib/types.ts`(또는 인라인)에 중복 정의됨
- 같은 상수·참조 데이터(팀 목록 등)가 여러 `constants.ts`에 존재
- 같은 포맷/변환 로직이 여러 곳에 복사됨 (`app/_lib/format.ts`로 모을 것)
- TopBar류·필드류처럼 변형만 다른 컴포넌트 — 합칠 수 있으면 지적, 화면별 요구가 정말 다르면 통과

### B. 배치 (있어야 할 곳에 없음)

- 2개 이상 화면이 쓰는데 특정 라우트의 `_components/`·`_lib/`에 있음 → `app/_components/`·`app/_lib/`로
- 반대로 한 화면만 쓰는데 공용 폴더에 있음 → 해당 라우트로
- 컴포넌트 파일 안에 타입·상수·순수함수가 인라인으로 있음 → `_lib/` 분리
  (예외: 그 컴포넌트만 쓰는 사적·자명한 타입은 인라인 허용)
- `mock.ts`(가짜 데이터)와 `constants.ts`(유지될 참조 데이터)가 섞여 있음
- 파일 하나에 컴포넌트 여러 개 (작은 private 헬퍼는 예외)

### C. 컨벤션 위반

- 하드코딩 색(hex/rgb)·px 값 — 토큰 유틸이 있는 속성인데 임의 값 사용
- `px-screen` 사용 (Tailwind 예약어 충돌 — `px-edge`여야 함)
- `../` 부모 탐색 import (→ `@/…` 절대경로)
- 파일명 kebab-case·컴포넌트 PascalCase·훅 useXxx 위반
- 상호작용 없는데 `"use client"` (서버 컴포넌트가 기본)
- `//` 이중슬래시 블록 주석 (→ JSDoc `/** */`)

### D. 죽은 코드

- 어디서도 import되지 않는 export·컴포넌트 (`page.tsx`·`layout.tsx` 등 Next 엔트리는 제외)
- 어디서도 참조되지 않는 토큰(`theme.css`)·public 에셋

## 3. 거짓 양성 주의

- **아이콘은 피그마 노드 벡터가 스펙**이다. 비슷해 보여도 의도된 별개 형태일 수 있다 —
  path 데이터가 실제로 같을 때만 중복으로 보고.
- 같은 폴더 형제의 `./` 상대경로 import는 규칙상 **정상**이다.
- `packages/ui`의 Turborepo 보일러플레이트(button·card·code)는 알려진 상태 — 지적하되 🔵로.
- 확신이 없으면 심각도를 내려 🔵 제안으로 넣는다. 감사의 신뢰는 🔴가 전부 진짜일 때 생긴다.
- **권장 조치에서 "새 토큰 추가"를 제안하기 전에 `packages/tokens/theme.css`의 실제 값을 확인**한다.
  이미 있는 토큰(예: `--text-micro`=10px)을 우회한 하드코딩일 수 있다 — 그 경우 조치는 신설이 아니라 교체다.

## 4. 리포트 — 항상 이 템플릿

저장 위치: `docs/audits/YYYY-MM-DD-audit.md` (오늘 날짜는 `date +%F`로 확인, 같은 날 두 번째면 `-2`).

```markdown
# 코드 구조 감사 — YYYY-MM-DD

## 요약

범위: <경로> · 검사 n/n개 파일 · 🔴 x건 🟡 y건 🔵 z건

## 🔴 구조 문제 (중복·잘못된 배치 — 방치할수록 비싸짐)

| # | 항목 | 위치 | 근거 | 권장 조치 |

## 🟡 컨벤션 위반

| # | 항목 | 위치 | 근거 | 권장 조치 |

## 🔵 개선 제안 (판단 여지 있음)

| # | 항목 | 위치 | 근거 | 권장 조치 |

## 검사 커버리지

디렉토리별 검사 파일 수 (총 n개)
```

## 5. 후속 — 물어보고 고친다

1. 리포트를 저장하고, 채팅에 심각도별 핵심만 요약한다 (표 전체 복붙 금지 — 리포트 링크로).
2. `AskUserQuestion`(multiSelect)으로 **어떤 항목을 고칠지** 선택받는다.
3. 승인된 항목만 수정하고 `pnpm lint && pnpm check-types`로 검증 (레이아웃을 건드렸으면 클린 빌드까지).
4. 리포트·수정의 커밋/브랜치/PR은 CLAUDE.md Git 규칙대로 — 사용자가 지시할 때만.
