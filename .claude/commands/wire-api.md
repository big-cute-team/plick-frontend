너는 PLick의 퍼블리싱된 화면에 백엔드 API를 연결한다. 인자: `$ARGUMENTS`
(첫 번째 = Jira 티켓 키 `KAN-###`, 두 번째(선택) = 붙일 엔드포인트/화면 스코프)

**반드시 `api-integration` 스킬과 `docs/adr/0011-shared-code-boundary.md`를 먼저 읽고 그 규칙을 따른다.**
(승격을 실제로 할 땐 `docs/adr/0005-web-home-and-ui-promotion.md` 절차도.)

절차:

1. **티켓·엔드포인트 파악** — Jira에서 요구/완료조건, 응답 shape(필드·페이지네이션·에러)를 정리한다.
2. **타입 대조** — 응답 shape를 기존 `_lib/types.ts`(BE 목표 shape)와 맞추고, 다르면 타입을 조정하되
   **web·mobile 양쪽을 같은 모양으로 동기화**한다.
3. **브랜치** — `git switch -c feature/<티켓>-<짧은설명> develop`.
4. **데이터 레이어 교체** — fetch/변환을 `_lib`에 두고, 화면은 소비 형태를 유지한 채 mock 대신 그 결과를
   받게 한다. 로딩/에러/빈 상태를 토큰으로 처리한다(스킬 §4·§5).
5. **공용화 판단(핵심)** — 스킬 §3의 게이트 A/B/C로:
   **데이터/타입은 굳으면 공용, 화면 표현은 앱별, 순수 원자·유틸은 두 번째 쓰이면 공용.**
   첫 API는 앱별로, 두 번째에서 같은 shape면 그때 승격. 애매하면 앱별 유지 + 후보로 기록(조기 추상화 금지).
6. **검증** — 실제/스텁 응답으로 로딩→성공→에러→빈 상태를 밟고, 공용 건드렸으면 **양쪽 앱 클린 빌드**.
   check-types·lint·format:check·CI 통과.
7. **커밋·PR** — 티켓 키 포함, `pnpm format` 후 커밋, push, `gh pr create --base develop`. **병합은 사용자.**

원칙: 엔드포인트 하나 = 작업 하나로 작게. 미확정(fetch 방식·인증·env)은 **추측 말고 사용자에게 확인**(스킬 §7).
기본값은 앱별·주입이라 되돌리기 싸다 — **확신 설 때만 공용으로 뺀다.**
