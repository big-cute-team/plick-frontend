# 0032. 모바일 릴스 피드 API 연결 (KAN-276)

릴스 화면을 목데이터에서 실제 BE(`GET /api/v1/reels`)로 갈아끼운 세션이다. 바로 앞 세션에서 홈 소식
리스트를 같은 방식으로 붙였고(ADR 0030) 릴스 넘김을 Embla로 바꿔 뒀기 때문에(ADR 0031), 이번엔 그 둘을
합치는 일이 될 거라고 생각하고 시작했다. 실제로는 계약 확인에서 예상 못 한 게 하나 나왔고, 무한스크롤을
리스트가 아니라 캐러셀에 붙이면서 새로 배운 것도 있었다. 마지막엔 사용자한테 넘김이 툭 끊긴다는 지적을
받아 로딩 자리를 다시 설계했다.

## 릴스 API는 기사 API와 같은 쿼리였다

`be-verify` 서브에이전트에 계약 검증을 맡겼다. 스킬 규칙대로 티켓 설명도 스웨거 설명도 믿지 않고
실제로 때려 보게 했는데, 이번에 제일 큰 소득이 이거였다.

스웨거는 이 엔드포인트를 "릴스 전용 피드"라고 설명한다. 그 말만 보면 릴스용으로 고른 부분집합이 올 것
같다. 실제로는 `/api/v1/articles`와 완전히 같은 쿼리다. `teamId`만 null로 고정돼 있고, 같은 커서를 쓰고,
같은 정렬(`publishedAt DESC, articleSummaryId DESC`)로 같은 1616건을 준다. 응답 키 16개 중 15개가
문자 하나까지 같고, 다른 건 이미지 필드명 하나뿐이다. 기사 피드는 `mainImageUrl`, 릴스는 `reelsImageUrl`이다.

이건 "지금은 큐레이션이 없다"는 BE의 현재 상태이지 계약상 앞으로도 같을 거라는 보장은 아니다. 이 사실이
아래 타입 결정에 그대로 걸린다.

나머지는 기사 피드와 판박이였다. 전역 `security: [{bearerAuth: []}]`가 걸려 있어 문서상 보호 API로
보이지만 익명으로 200이 오고, 오히려 만료된 토큰을 실으면 401 `AUTH_EXPIRED_TOKEN`으로 피드 전체가
죽는다. 토큰을 실어도 응답이 바이트 단위로 같다(참여 집계가 아직 `NoopArticleEngagementProvider`라
좋아요·댓글·조회가 전부 0이고 `likedByMe`도 항상 false다). 그래서 여기서도 일부러 토큰을 싣지 않는다.
이 판단은 ADR 0030과 같고, 이유를 잊고 "보호 API 관용에 맞추자"며 헤더를 붙이는 일이 없도록 fetcher
파일 상단 주석에 남겨 뒀다.

null 표기는 스웨거에 하나도 없는데 실제로는 `rumorStage`, `reelsImageUrl`, `detailImageUrl`, `logoUrl`,
`sourceUrl`, `reporter` 객체 전체, `reporter.koName`, `reporter.tier`, `nextCursor`가 전부 null로 온다.

그리고 릴스 입장에서 제일 아픈 것: `reelsImageUrl`이 1616건 **전부** null이다. 릴스는 풀스크린 배경
이미지가 화면의 거의 전부인 화면인데 그 이미지가 하나도 없다. 즉 `MediaThumb`의 팀 컬러 그라데이션
placeholder가 지금은 예외 상황이 아니라 사실상 기본 화면이다.

## 단건 조회 API가 없어서 딥링크를 걷어냈다

바로 앞 세션(ADR 0031)에서 만든 `/reels/[postId]` 딥링크가 문제가 됐다. 홈 핫이슈 카드를 누르면 그
게시물부터 시작하는 릴스로 들어가는 라우트다. 목데이터일 땐 `getPost(postId)`로 배열에서 찾으면 됐다.

BE에는 `GET /api/v1/reels/{id}` 같은 단건 조회가 없다(404 `COMMON_NOT_FOUND`). 커서 피드만 있다. 그러면
딥링크로 들어온 id가 첫 페이지에 없을 때 그 릴을 가져올 방법이 없다. 50페이지 뒤에 있는 기사면 거기까지
커서를 타고 내려가야 한다는 뜻인데 그건 딥링크가 아니다.

게다가 이 딥링크의 유일한 진입점인 홈 핫이슈 캐러셀은 아직 목데이터다(BE에 인기·조회수·정렬 개념이 없어
무엇을 핫으로 볼지 근거가 없어서 ADR 0030에서 남겨 뒀다). 즉 `h1`, `h2` 같은 목 id를 BE 피드에 던지는
꼴이라 어느 쪽으로 처리하든 맞을 수가 없었다.

여기서 혼자 판단하지 않고 물어봤다. ADR 0030에서 무한스크롤 스코프를 내가 임의로 잘랐다가 지적받은 게
있어서, 기능이 줄어드는 방향의 결정은 확인하고 가기로 했다. 답은 명확했다. postId는 지금 URL에서 쓰지
않으니 라우트를 없애라는 것이었다.

그래서 `app/reels/[postId]/` 폴더를 통째로 지우고, 홈 핫이슈 카드의 링크를 `/reels/${post.id}`에서
`/reels`로 바꿨다. 딸려서 정리된 것도 있다. `ReelsFeed`의 `initialPostId` prop과 첫 렌더에 한 번만
인덱스를 정하던 `startIndex` 상태, 하이드레이션 전 첫 페인트용으로 컨테이너에 박아 두던 초기
`translate3d`, `useReelsCarousel(startIndex)`의 인자가 전부 필요 없어졌다. 딥링크 하나 때문에 있던
장치들이라 같이 걷어냈다. 나중에 BE에 단건 조회가 생기면 그때 다시 만드는 게 지금 반쯤 동작하는 걸
남겨 두는 것보다 낫다고 봤다.

## ArticleCard를 재사용할까 ReelCard를 만들까

응답이 기사 피드와 15/16 같으니 ADR 0030에서 만든 `ArticleCard`를 그대로 쓰면 매퍼까지 공유할 수 있다.
반대로 릴스가 나중에 진짜 큐레이션 피드로 갈라지면 그때 둘을 떼는 비용이 든다.

내 의견은 재사용 쪽이었다. 지금 두 응답이 같은 이유가 "같은 데이터를 서빙한다"라서 타입도 같은 게
사실에 가깝다고 봤다. 그런데 이 판단은 BE의 현재 구현 상태에 기대는 것이고, 스웨거는 이 엔드포인트를
별도 피드라고 선언하고 있다. 선언과 구현이 갈라져 있는 자리라 사용자에게 물었고, 답은 `ReelCard`를
따로 두는 쪽이었다.

그래서 `app/_types/reels.ts`에 `ReelCard`, `ReelFeedPage`, `InitialReelFeed`를 새로 만들었다. 이 파일은
원래 세부 시트의 개폐·드래그 상태(`ReelDetailMotion`, `TitleMotion`)만 담고 있었는데, 같은 릴스라는
주제이므로 파일을 쪼개지 않고 함께 뒀다(`_constants/reels.ts`가 캐러셀 옵션과 시트 기하를 함께 담고
있는 것과 같은 결이다).

`@plick/domain`의 `FeedPost`는 이번에도 건드리지 않았다. 퍼블리싱 때 추정으로 만든 타입이라 실계약과
어긋나는 게 한둘이 아닌데(팀이 단수, 단계가 필수, 기자가 필수, `timeLabel` 문자열, 본문·댓글·토론 존재),
이걸 고치면 아직 목데이터로 도는 web이 줄줄이 타입 에러가 난다. ADR 0030과 같은 판단이다.

타입을 따로 두기로 한 대신 진짜 중복은 최소화했다. BE 단계 값(`RUMOR`)을 도메인 `RumorStage`(`RUMOUR`)로
바꾸는 매핑 테이블은 두 fetcher가 같은 값을 쓰므로 `_constants/api.ts`로 옮겼다. 원래 `_services/articles.ts`
안에 있던 건데, 여기가 이미 `TEAM_IDS`·`TEAM_CODES` 같은 BE 계약 매핑이 사는 자리라 결이 맞다. 서비스끼리
서로를 import하게 만들지 않으면서 한 곳만 고치면 되는 상태가 됐다.

이 철자 문제는 매번 짚어 둘 만하다. BE와 DB는 미국식 `RUMOR`, 도메인 타입은 영국식 `RUMOUR`다. 한 글자
차이라 눈으로 잘 안 보이는데, `as RumorStage`로 캐스팅하면 타입 검사는 통과하고 `STAGE_META["RUMOR"]`가
`undefined`가 되어 배지 그리는 자리에서 런타임에 터진다. 테이블을 거치면 모르는 값이 null로 떨어져
배지가 안 그려질 뿐이다.

팀 컬러 폴백 상수(`NO_TEAM_COLOR_VAR`)도 마찬가지다. ADR 0030에서 `NewsItem.tsx` 안에 로컬 상수로 두고
있었는데 릴스에서도 같은 게 필요해졌다. 컴포넌트 파일에 상수를 두지 않는다는 컨벤션도 있고 해서
`_constants/app.ts`로 올리고 양쪽이 같은 걸 쓰게 했다.

## 공용 컴포넌트가 null을 못 받고 있었다

`@plick/ui`의 조각들이 퍼블리싱 시절 목데이터 모양(`tier: 1 | 2 | 3` 필수, 팀 필수)을 그대로 요구하고
있어서 실데이터를 그리려니 타입이 막혔다. 실측이 이렇다.

- `reporter.tier`: 1616건 중 903건이 null이다. 값이 있는 713건은 전부 `1`이고 2, 3은 아예 없다.
  티어가 기자가 아니라 기사(raw_article)별로 붙어서 같은 기자도 기사마다 null일 수 있다.
- `teams`: 빈 배열인 기사가 있다(1건). 팀 이름도 팀 컬러도 없다.

그래서 세 컴포넌트의 prop을 넓혔다. `ReporterTierBadge`는 `tier: number | null`을 받고 null이면 아무것도
그리지 않는다. 모르는 티어를 아무 숫자로 채우면 신뢰도를 잘못 표시하게 되니 안 그리는 쪽이 맞다.
`ReporterLine`도 같은 이유로 `tier`를 nullable로 바꿨다. `PostChips`는 `teamName`을 optional로 바꿔
없으면 팀 칩을 빼고 RUMOUR 칩만 그린다.

셋 다 **넓히는** 변경이라 web은 안 깨진다. `1 | 2 | 3`은 `number | null`에 그대로 들어가고 필수 prop은
optional prop을 만족한다. 그래도 공용 패키지를 건드렸으니 양쪽 앱을 다 빌드해 확인했다.

## 커서 무한스크롤을 캐러셀에 붙이기

데이터 쪽은 ADR 0030에서 만든 틀을 그대로 가져왔다. `useInfiniteQuery`에 `getNextPageParam: (last) =>
last.nextCursor ?? undefined`다. BE에 `hasNext`도 총 건수도 없어서 `nextCursor`가 null인지로만 끝을
판단하는데, RQ는 "다음 페이지 없음"을 undefined로 표현하므로 null을 그대로 돌려주면 안 된다. 그러면
RQ가 "커서가 null인 페이지가 더 있다"로 읽고 커서 없이 첫 페이지를 무한히 다시 받는다.

`be-verify`가 확인해 준 것 중에 이 판단을 뒷받침하는 게 있었다. 마지막 페이지가 26건/30으로 덜 찬 건
맞지만, 그 전 페이지들도 항상 꽉 차 있지는 않을 수 있으므로 `items.length < size`로 끝을 판정하면 안
된다. 끝을 지난 커서를 직접 만들어 던져도 404가 아니라 `{items: [], nextCursor: null}`이 온다.

`staleTime`과 `gcTime`을 같은 값(60초)으로 붙이는 것, 포커스 재요청을 끄는 것, 4xx 재시도를 끄는 것,
씨앗에 서버가 받은 시각을 달아 주는 것도 그대로 가져왔다. 이유가 전부 ADR 0030에 길게 적혀 있는데
상수와 함께 복사하면 둘이 갈라질 게 뻔해서 `_constants/feed.ts`를 만들어 `FEED_FRESH_MS`와
`FEED_MAX_RETRIES`를 옮기고 기사 피드 훅도 거기서 가져다 쓰게 했다.

다른 건 트리거였다. 홈 리스트는 목록 끝에 1px짜리 감시 요소를 두고 `IntersectionObserver`로 잡았는데,
릴스는 릴 한 장이 화면 전체라 감시 요소를 둘 자리가 없다. 대신 Embla가 지금 보고 있는 인덱스를 알려주니
그걸로 판단한다. 남은 장수가 `REELS_PREFETCH_AHEAD`(3) 이하가 되면 다음 페이지를 부른다.

여기서 걱정했던 게 슬라이드가 늘어나면 캐러셀이 어떻게 되느냐였다. Embla는 마운트 시점의 슬라이드를
재서 스냅 지점을 계산하는데, 페이지를 받아 10장이 더 붙으면 그 계산이 안 맞을 것 같았다. 수동으로
`reInit()`을 부르는 코드를 넣으려다가 `node_modules`의 embla 소스를 먼저 열어 봤다.

찾아보니 이미 하고 있었다. `SlidesHandler`가 컨테이너에 `MutationObserver`를 걸어 두고 자식이 바뀌면
`emblaApi.reInit()`을 부른다(`watchSlides` 옵션의 기본값이 true다). 그리고 `reInit`이 하는 일이 중요한데,
소스를 보면 이렇다.

```js
function reActivate(withOptions, withPlugins) {
  const startIndex = selectedScrollSnap();
  deActivate();
  activate(mergeOptions({ startIndex }, withOptions), withPlugins);
  eventHandler.emit("reInit");
}
```

지금 보고 있는 인덱스를 새 `startIndex`로 넘긴다. 그래서 슬라이드가 늘어나도 보던 자리가 유지된다.
직접 넣으려던 `reInit` 호출은 지웠고, 대신 이 동작에 기대고 있다는 걸 `useReelsCarousel` 주석에 적었다.

(이 판단은 뒤에서 뒤집힌다. 자리가 유지되는 건 맞지만 멈춰 있을 때만 그렇다. 아래 "그런데 여전히
끊겼다" 절에서 `deActivate()`가 무엇을 부수는지 마저 읽고 결국 자동 감지를 끄게 된다.)

## 로딩·에러·빈 상태

릴은 한 장이 화면 전체라 리스트처럼 문구를 아래에 덧붙일 자리가 없다. 그래서 릴이 놓일 자리를 통째로
차지하는 컴포넌트를 두 개 만들었다. `ReelSkeleton`은 첫 로딩용으로 실제 릴과 같은 하단 정보 블록 배치를
흉내 내고, `ReelStatus`는 에러와 빈 상태 문구(+재시도 버튼)를 가운데 놓는다. 색은 전부 토큰이다
(`bg-media`, `bg-elevate`, `text-text-4`).

서버 fetch 실패를 페이지 전체 에러로 만들지 않는 것도 홈과 같게 했다. `app/error.tsx`가 있어서 서버
컴포넌트에서 예외가 나면 페이지가 통째로 에러 화면이 되는데, 그러면 탭바까지 사라져 다른 화면으로 나갈
수도 없다. 페이지에서 try/catch로 흡수하고 씨앗 없이 클라에 넘기면 훅이 알아서 다시 받는다.

다음 페이지에서 400이 나면 커서를 버리고 첫 페이지부터 다시 받게 했다. 상한 커서와 잘못된 파라미터가
똑같은 `COMMON_INVALID_PARAM`으로 와서 구분할 방법이 없기 때문이다. 리스트에서는 이게 큰 손해가
아니었는데 릴스에서는 보던 자리를 잃는다는 대가가 더 크다. 그래도 같은 커서로 재시도해봐야 계속 400이라
다른 수가 없어서 그대로 갔다.

## 넘김이 툭 끊긴다는 지적

여기까지 만들고 나서 사용자한테 지적을 받았다. 마지막 게시물에서 아래로 내리면 툭 끊기면서 다음 페이지가
받아진다는 것이었고, 유튜브처럼 작은 스피너가 그 칸을 유지하는 방식으로 해달라는 요청이었다.

원인을 찾아보니 내가 만든 로딩 자리 자체였다. 처음엔 `isFetchingNextPage`일 때만 끝에 스켈레톤 슬라이드를
덧붙였다. 그러면 이런 일이 벌어진다.

```
받기 시작   → 슬라이드 한 장 추가 → MutationObserver → reInit
페이지 도착 → 스켈레톤 제거 + 10장 추가 → MutationObserver → reInit
```

DOM이 두 번 바뀌고 그때마다 캐러셀이 다시 초기화된다. 게다가 첫 번째는 사용자가 한창 넘기고 있는 중에
일어난다(남은 장수가 3일 때 받기 시작하니까). 넘기는 도중에 캐러셀이 재초기화되면 그게 툭 끊기는
느낌으로 나온다.

그래서 로딩 자리를 조건부로 넣었다 뺐다 하지 않고, **다음 페이지가 있는 동안 항상 한 장 붙여 두는**
방식으로 바꿨다. `ReelLoadingSlide`가 그거고, 릴 한 장을 통째로 덮는 스켈레톤 대신 가운데 작은 스피너만
돌린다. `isFetchingNextPage`가 바뀌어도 DOM이 안 변하니 재초기화가 페이지가 실제로 붙을 때 한 번만
일어나고, 그 한 번도 사용자보다 세 장 앞에서 벌어져 눈에 띄지 않는다.

덤으로 동작이 더 자연스러워졌다. 사용자가 스피너 칸까지 내려간 상태에서 페이지가 도착하면, 새 슬라이드가
스피너 앞에 끼어들면서 그 자리가 그대로 첫 번째 새 릴이 된다. 스피너가 있던 칸이 내용으로 채워지는
셈이라 유튜브에서 보던 그 동작이다.

미리 받는 시점은 원래부터 마지막 장이 아니라 세 장 남았을 때였는데(`REELS_PREFETCH_AHEAD = 3`),
지적받은 김에 다시 확인했다. 한 페이지가 10장이므로 인덱스 6에서 요청이 나가고, 사용자가 9번째 장에
닿기 전에 도착한다. 요청이 나가는 조건은 `남은 장수 <= 3 && 다음 페이지 있음 && 받는 중 아님 && 직전
실패 아님`이다. 받는 중에도 켜 두면 같은 페이지를 여러 번 요청한다.

### 그런데 여전히 끊겼다

여기까지 고치고 됐다고 생각했는데 아니었다. 다시 지적이 왔다. 넘어가려다가 fetch가 되면 멈췄다가, 원래
같으면 중단됐던 부드러운 움직임이 이어서 진행돼야 하는데 그냥 툭 하면서 다음 게시물이 바로 보인다는
것이었다. 스와이프 UX가 박살났다는 표현이었고 정확한 관찰이었다.

내 진단이 절반만 맞았던 거다. DOM 변경 횟수를 줄인 건 맞지만 진짜 문제는 횟수가 아니라 **재초기화가
무엇을 파괴하는가**였다. embla 소스의 `reInit`을 다시 따라가면 이렇다.

```js
function reActivate(withOptions, withPlugins) {
  const startIndex = selectedScrollSnap();
  deActivate();                     // ← 여기
  activate(mergeOptions({ startIndex }, withOptions), withPlugins);
}

function deActivate() {
  engine.dragHandler.destroy();
  ...
  engine.animation.destroy();       // ← 진행 중인 스냅 애니메이션이 죽는다
}
```

앞에서 나는 `reInit`이 지금 인덱스를 유지하니 안전하다고 적었는데, 그건 **멈춰 있을 때** 얘기였다.
넘기는 도중이면 `animation.destroy()`가 달리던 애니메이션을 그 자리에서 없애고, 새 엔진이 목적지
인덱스에서 시작한다. 그래서 중간 프레임이 통째로 사라지고 결과만 툭 나타난다. 사용자가 묘사한 "멈췄다가
바로 보이는" 게 정확히 이 동작이다.

프리페치를 세 장 앞에서 시작해도 소용이 없다. 요청이 나가는 시점이 아니라 **응답이 도착하는 시점**이
문제고, 그건 사용자가 한창 넘기는 중일 확률이 높다. 오히려 미리 받을수록 넘기는 중에 도착할 확률이 는다.

그래서 접근을 바꿨다. 슬라이드가 늘어난 걸 감추는 게 아니라, **다시 재는 시점을 미룬다.**

먼저 Embla의 자동 감지를 껐다(`watchSlides: false`). 기본값이면 컨테이너에 걸린 `MutationObserver`가
자식이 바뀌는 즉시 `reInit()`을 부르는데, 그 즉시가 하필 최악의 순간이다. 끄면 새 슬라이드가 DOM에는
들어와 있고 Embla만 아직 모르는 상태가 된다. 화면에는 아무 영향이 없다. 어차피 뷰포트 밖에 있고,
Embla는 컨테이너를 translate 할 뿐이라 자기가 모르는 자식이 뒤에 붙어 있어도 하던 일을 그대로 한다.

그리고 `useReelsCarousel`이 직접 잰다. 슬라이드 수가 바뀌었을 때 멈춰 있으면 바로 `reInit()`하고,
움직이는 중이면 플래그만 세워 뒀다가 멈춘 뒤에 부른다.

```ts
const stop = () => {
  moving.current = false;
  if (remeasure.current) {
    remeasure.current = false;
    embla.reInit(); // 멈춘 뒤라 파괴할 애니메이션이 없다
  }
};
```

움직이는 중인지를 무엇으로 볼지에서 한 번 더 걸렸다. 처음엔 `pointerDown`부터 움직이는 중으로 잡았는데,
그러면 제자리 탭에서 빠져나오지 못한다. 릴의 정보 블록을 탭해 세부 시트를 여는 게 이 화면의 핵심
인터랙션인데, 손가락이 움직이지 않으면 스냅 애니메이션도 없고 따라서 `settle`도 안 온다. 미뤄 둔
재측정이 영영 안 풀리는 상태가 된다.

그래서 위치가 실제로 바뀌었는지(`scroll`)로 판정하게 바꿨다. embla 소스에서 두 이벤트가 같은 렌더
루프에서 배타적으로 나온다.

```js
const hasSettledAndIdle = hasSettled && !dragHandler.pointerDown();
if (hasSettledAndIdle) eventHandler.emit("settle");
if (!hasSettled) eventHandler.emit("scroll");
```

움직이면 `scroll`이 계속 나오고, 멈추고 손가락까지 떼면 `settle`이 한 번 나온다. 제자리 탭은 둘 다
안 나오므로 애초에 움직이는 중으로 잡히지 않는다. 손가락을 대고 가만히 있는 동안에는 `settle`이
안 나오는데(`!pointerDown()` 조건), 이것도 맞는 동작이다. 손가락이 닿아 있는 동안 드래그 핸들러를
파괴하면 안 된다.

### 세 번째 지적: 마지막 릴에서 아래로 안 넘어간다

이것도 아직 아니었다. 다시 지적이 왔다. 스크롤하다가 중간에 데이터를 받아오는 것까지는 잘 되는데,
그 뒤 10번째 장에 도착해서 아무리 내려도 그 밑으로 안 내려가다가, 조금 시간이 지나거나 다른 곳에
포커스했다 오면 그때 또 된다는 것이었다.

증상만 봐도 원인이 좁혀진다. 10번째 장이 첫 페이지의 끝이고, 그 아래로 못 간다는 건 Embla가 아직
새 슬라이드를 세지 않았다는 뜻이다. 즉 미뤄 둔 재측정이 안 풀린 것이다. "다른 곳에 포커스했다 오면
된다"는 것도 맞아떨어진다. 그때 리사이즈가 잡히면 `watchResize`가 살아 있으니 그 경로로 `reInit`이
돌아 우연히 풀린다.

플래그 방식 자체가 문제였다. `settle` 핸들러 안에서 `embla.reInit()`을 부르는데, 그 `settle`은 Embla의
렌더 루프 한복판에서 나온다. 앞에 인용한 코드가 그대로 그 자리다.

```js
if (hasSettledAndIdle) animation.stop();
...
if (hasSettledAndIdle) eventHandler.emit("settle");   // ← 여기서 내 핸들러가 실행되고
if (!hasSettled) eventHandler.emit("scroll");          //   그 안에서 엔진을 파괴한다
```

`emit('settle')`이 부른 내 핸들러가 `reInit()`을 부르면, 지금 이 코드를 돌리고 있는 엔진을 그 자리에서
파괴하고 새 엔진을 만든다. 그러고 나서 제어가 돌아와 다음 줄부터는 이미 죽은 엔진의 클로저로 계속
실행된다. 재진입(reentrancy)이다. 내 `moving`, `remeasure` 플래그와 Embla의 실제 상태가 여기서 갈라지고,
한 번 갈라지면 다음 재측정이 영영 안 걸린다.

그래서 이번엔 상태를 내가 기억하지 않기로 했다. 움직이는 중인지 Embla에게 그때그때 물어보고,
이벤트 핸들러 안이 아니라 별도 프레임에서 잰다.

```ts
const remeasureWhenIdle = () => {
  const { dragHandler, scrollBody } = embla.internalEngine();
  if (dragHandler.pointerDown() || !scrollBody.settled()) {
    frame = requestAnimationFrame(remeasureWhenIdle);
    return;
  }
  embla.reInit();
};
```

조건 두 개는 Embla가 스스로 `hasSettledAndIdle`을 판정할 때 쓰는 것과 같은 값이다. `scrollBody.settled()`는
`|목표 위치 - 현재 위치| < 0.001`이라 기억이 아니라 지금 위치를 재는 순수 질의다. 그래서 어긋날 상태 자체가
없다. 멈춰 있으면 그 자리에서 한 번 재고 끝이고, 움직이는 중이면 다음 프레임에 다시 묻는다. 프레임마다
비교 두 번이라 비용도 없다시피 하고, 페이지가 붙은 뒤 잠깐만 돈다.

이벤트 핸들러가 아니라 `requestAnimationFrame` 콜백에서 부르는 것도 의도한 것이다. Embla의 렌더 루프와
같은 프레임에 실행되더라도 그 호출 스택 안이 아니라 옆에서 도는 콜백이라, 자기가 실행 중인 엔진을
파괴하는 상황이 안 생긴다.

`internalEngine()`은 Embla가 고급 사용자용으로 열어 둔 내부 API라 마이너 버전에서 바뀔 수 있다. 대신
쓸 공개 API가 없어서(멈췄는지 물어보는 공개 메서드가 없다) 그대로 쓰고 훅 주석에 이유를 남겼다.
버전을 올릴 때 이 자리를 확인해야 한다.

정리하면 이 문제는 세 번에 걸쳐 층이 벗겨졌다. 처음엔 DOM이 자주 바뀌는 게 문제인 줄 알았고(아니었다),
다음엔 애니메이션이 살아 있는 동안 파괴되는 게 문제였고(맞았다), 마지막엔 그걸 막으려고 둔 플래그가
라이브러리 렌더 루프와 재진입으로 어긋난 게 문제였다. 공통점은 라이브러리가 알아서 해 주는 부분이
"언제 무엇을 하는가"를 안 보고 기댄 것이다. `watchSlides`도, `settle` 이벤트도 편해 보여서 썼는데
둘 다 실행 시점이 중요한 자리였다.

## 아직 못 한 것

브라우저로 직접 밟아 보지 못했다. 이 세션에서 Chrome 확장이 계정 불일치로 연결되지 않았다
(`the OAuth token Claude Code is using belongs to a different claude.ai account`). 스킬은 화면 검증만은
위임하지 말고 직접 하라고 못박고 있는데 그걸 못 지켰다. HTTP 레벨까지만 확인했다.

이 대가가 그대로 나왔다. 넘김이 끊기는 문제도, 마지막 릴에서 안 넘어가는 문제도 내가 못 잡고 사용자가
세 번 지적해서야 잡혔다. 셋 다 실제로 손가락으로 넘겨 봤으면 첫 번째에 보였을 것들이다. 라이브러리
소스를 읽어 원인을 짚는 것과 화면을 밟아 증상을 보는 건 대체되지 않는다.

확인한 것: `/reels` 서버 렌더 HTML에 BE 실제 기사 제목이 박히는 것, 끝에 스피너 슬라이드가 함께 오는 것,
지운 `/reels/h1`이 404가 되는 것, `/be` 프록시로 첫 페이지와 `nextCursor`를 이어받은 두 번째 페이지가
각각 10건씩 오는 것, 깨진 커서와 `size=31`이 400으로 오는 것.

사람이 직접 밟아 봐야 하는 것: 실제 세로 스와이프로 넘길 때 3장 남는 시점에 요청이 나가는지, 넘김이
정말 안 끊기는지, 스피너 칸이 새 릴로 채워지는지, 세부 시트를 열었을 때 칩·제목이 시트 라인까지 따라
올라오는지, 팀 태그가 없는 기사에서 칩이 빠진 모양이 괜찮은지, 티어 없는 기자에서 배지 없이 이름만 나오는
모양이 괜찮은지, 그리고 BE를 껐을 때 에러 화면과 재시도 버튼이다.

계약과 DB는 `be-verify`가 다 봤다. 1616건을 커서로 완주해 중복·누락 0을 확인했고, 응답 건수가
`article_summaries where status='PUBLISHED' and published_at is not null`과 일치하는 것,
`summary`가 실은 `summary_detail`인 것, `hashtags`가 해시태그가 아니라 태그된 팀의 한글명인 것까지
DB로 대조했다. 읽기 전용이라 테스트 유저는 만들지 않았고 쓰기는 0건이다.

## 남아 있는 것

릴스 배경 이미지가 전량 null이라 지금 화면은 팀 컬러 그라데이션만 보인다. 이미지 파이프라인이 채워지면
`MediaThumb`을 `<img>`로 바꾸는 작업이 따로 필요하다.

댓글이 계약에 없다. 세부 시트의 댓글 목록은 빈 상태 문구만 보여주고 입력바는 여전히 미연결이다.
목데이터로 채워 두지 않은 건 규칙대로다(필요 없어진 목은 그 PR에서 지우고, 실제 값이 아직 미연동 API
몫이면 빈 값으로 시작한다). 댓글 API가 붙을 때 이 자리에 연결한다.

좋아요·저장도 마찬가지다. 좋아요 수와 `likedByMe`는 응답에 있지만 집계가 자리표시라 항상 0/false이고,
저장 여부는 계약에 아예 없어 액션 레일의 저장 아이콘은 늘 빈 상태다. 참여 API가 붙으면 낙관적 뮤테이션을
붙일 자리다(TanStack Query 도입 트리거 중 아직 안 쓴 하나가 이거다).

토론(투표) 블록도 응답에 없다. DB `debates` 테이블이 0건이고 `content_type`이 전부 `GENERAL`이라
릴스에서 토론형 릴은 계약상 아직 존재하지 않는다.

`_mocks/posts.ts`는 남는다. 릴스는 이제 안 쓰지만 홈 핫이슈 캐러셀과 기사 세부 페이지가 아직 쓴다.
마지막 소비자가 사라질 때 파일도 지운다.
