# 0195. 빨강 글자와 투표 캡션의 색 대비 보정 (KAN-627)

2026-10-11 prod 모바일 라이트하우스에서 `color-contrast`가 홈·팀 허브·기사·투표·인물·라이브 여섯 화면에서
떨어졌다. 걸린 자리는 두 묶음이었다. 핫이슈와 기사 카드의 순위 숫자 `[1]`, 라이브의 "VS", 날짜 띠의
"오늘"처럼 브랜드 빨강 `--plk-danger #e8342a`를 작은 글자에 쓴 자리가 흰 배경에서 4.24:1, 채운 면(`elevate`)
위에서 3.95:1이었고, 투표 카드의 "N명 참여" 캡션이 회색 글자 하한 `#767676`을 회색 카드 위에 올려 4.02:1이었다.
WCAG AA는 작은 글자에 4.5:1을 요구한다. 사용자의 조건은 하나였다. 기존 디자인에서 눈에 띄게 벗어나지 말 것.

## 빨강을 바꿀까, 글자용 빨강을 하나 더 둘까

가장 짧은 길은 `--plk-danger` 값 자체를 진하게 내리는 것이다. 그러면 63군데 클래스를 건드릴 필요가 없다.
그런데 이 토큰은 글자만 쓰는 게 아니다. LIVE 점, 배너의 세로 막대, 새 글 배지 배경, 좋아요 하트,
`danger-tint`로 파생되는 칩 배경과 테두리까지 전부 이 값을 읽는다. 대비 기준은 글자에만 걸리는데
면과 점까지 같이 어두워지면 시안과 맞춰 둔 브랜드 빨강이 화면 전체에서 미묘하게 틀어진다. 티켓도 같은
판단이었다. 브랜드 빨강은 두고 작은 글자용 변형을 둔다.

후보는 셋이었다. 흰 배경과 `elevate`, `chip`을 같이 계산했다.

| 값               | 흰색 | elevate `#f6f7f8` | chip `#f2f4f5` | 투표 카드 `#f1f1f2` |
| ---------------- | ---- | ----------------- | -------------- | ------------------- |
| `#e8342a` (현재) | 4.24 | 3.95              | 3.84           | 3.75                |
| `#dc2b21`        | 4.76 | 4.44              | 4.32           | 4.22                |
| `#d6281e`        | 5.02 | 4.68              | 4.55           | 4.45                |
| `#d0261c`        | 5.28 | 4.92              | 4.79           | 4.68                |

`#dc2b21`은 흰 배경만 넘고 `elevate` 위 VS·LIVE가 다시 걸린다. `#d0261c`는 여유가 있지만 원래 빨강과
나란히 놓으면 차이가 보이기 시작한다. `#d6281e`가 흰색·elevate·chip 셋을 모두 넘기면서 원래 값과
가장 가깝다. 투표 카드 위는 4.45로 아슬아슬하게 모자라는데, 투표 카드 위에 빨강 글자를 두는 자리가 없어서
그대로 뒀다. 이름은 `--plk-danger-strong`으로 했다. `--plk-text-strong`, `--plk-border-strong`과 같은
꼴이라 Tailwind 유틸이 `text-danger-strong`이 되고, 기존 `text-text-strong` 옆에서 읽힌다.

## 어디를 바꾸나

`text-danger`를 쓰는 자리는 두 앱과 `@plick/ui`를 합쳐 63군데였다. 글자인 것과 아이콘인 것을 갈라
글자만 바꿀까 했는데, 실제로 보니 거의 전부가 하트 아이콘 옆에 숫자가 붙는 식으로 글자를 같이 품고 있었다.
하트만 단독인 자리(좋아요 해제 버튼)도 한 단계 진한 빨강이 되는 게 문제가 아니라서, 규칙을 "글자색은
`text-danger-strong`, 면·점·테두리·틴트는 `danger`"로 단순하게 잡고 `text-danger` 전부를 바꿨다.
`bg-danger`·`border-danger`·`danger-tint`는 그대로다. 결과적으로 `--plk-danger`를 글자에 직접 쓰는
자리는 없어졌고, 둘의 차이는 나란히 놓고 봐야 보이는 정도다.

투표 캡션은 카드 배경을 밝히는 대신 글자를 `text-text-3 #5f6368`로 한 단계 올렸다. 카드 위에서 5.36이다.
배경을 밝히면 카드와 흰 바탕의 구분이 약해져 시안의 카드 느낌이 사라진다. 캡션 한 줄의 회색이 조금
진해지는 쪽이 훨씬 덜 보인다. 같은 카드의 남은 시간 표기는 `vote-closed-on #5c6673`이라 이미 5.16으로 넘는다.

theme.css의 "회색 글자 하한 #767676" 주석은 틀린 게 아니라 조건이 빠진 것이었다. 흰 배경 기준 4.54라는
뜻이지 아무 면 위에서나 안전하다는 뜻이 아니다. 주석에 그 단서를 달고, 회색 면 위에서는 `text-3`부터
쓰라고 적었다. `screen-publishing` 스킬의 토큰 요약도 같은 내용으로 고쳐 다음 화면부터 같은 실수를
반복하지 않게 했다.

## 검증

로컬 dev 서버(prod BE 읽기)에서 홈의 순위 숫자와 VS가 `rgb(214, 40, 30)`으로, 투표 카드 캡션이
`rgb(95, 99, 104)`로 계산되는 것을 DOM에서 확인했고, `text-danger` 클래스가 남은 자리는 0이다.

스크래치패드에 Lighthouse 12를 깔고 로컬 서버 상대로 여섯 화면에 `color-contrast` 감사만 돌렸다. 처음 결과는
투표·인물·라이브는 통과, 홈·팀 허브·기사는 실패 1건이었다. 빨강은 전부 사라졌고 남은 하나는 이번 티켓 뒤에
들어온 광고 자리 표시(KAN-652)였다. dev·로컬에서만 보이는 점선 상자의 "AD" 글자가 `text-text-4`를 `bg-elevate`
위에 올려 4.23이다. prod는 애드센스 iframe이 그 자리를 채우니 prod 측정에는 안 잡히겠지만, 이 티켓이 세운
"회색 면 위는 text-3부터" 규칙에 정확히 걸리는 자리라 두 앱의 `AdSlot` 플레이스홀더를 같이 올렸다.
다시 재니 여섯 화면 모두 `color-contrast` 통과다.

| 화면                     | 전(prod 10-11) | 후(로컬) |
| ------------------------ | -------------- | -------- |
| 홈 `/`                   | 실패           | 통과     |
| 팀 허브 `/teams/arsenal` | 실패           | 통과     |
| 기사 `/articles/7888`    | 실패           | 통과     |
| 투표 `/debates`          | 실패           | 통과     |
| 인물 `/figures/397`      | 실패           | 통과     |
| 라이브 `/live`           | 실패           | 통과     |

같은 세션에서 E2E 워크플로우가 develop 푸시 뒤 두 번 연속 떨어진 것도 봤다. 모바일 릴스의 "진입하면 첫 릴이
열리고 액션 레일이 있다"가 `main section:not([inert])`를 1개로 기대하는데 2개가 잡혔다. KAN-652의 전면광고
슬라이드 `ReelAdSlide`가 `<section>`인데 `ReelItem`과 달리 비활성일 때 `inert`를 달지 않아서다. DOM 창 밖
릴은 빈 `<section inert>`로 남는데 광고 슬라이드는 창 안팎 모두 `inert` 없이 서 있으니, 첫 릴에서도 8번째
칸의 광고 섹션이 활성 릴로 센다. 테스트의 문제가 아니라 앱의 문제다. 비활성 슬라이드는 포커스와 스크린리더가
닿으면 안 된다. 이 수정은 광고 티켓 몫이라 별도 브랜치(KAN-652)로 뺐다.
