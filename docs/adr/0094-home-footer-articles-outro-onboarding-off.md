# 0094. 홈 SEO 푸터, 기사 끝 문구, 리스트 톤 정리, 온보딩 내리기

날짜: 2026-08-12
관련: [0093 기사 페이지 신설과 홈 단순화](0093-articles-page-and-home-simplify.md),
[0084 홈 소개 문구](0090-home-intro-copy-follow-tab.md), KAN-386 후속

## 이번 세션에서 한 것

KAN-386으로 홈이 첫 페이지 고정이 되고 무한스크롤이 기사 페이지로 옮겨 간 뒤의
후속 작업 네 가지를 한 세션에 처리했다. 홈 푸터, 기사 리스트 끝 문구, 리스트
텍스트 톤 다운, 그리고 온보딩 흐름 내리기다.

## 1. 기사 리스트 끝에 "모은 페이지예요 + 마지막 페이지예요"

홈에는 KAN-384에서 넣은 크롤러블 소개 문구(HomeIntro)가 있는데 기사 페이지에는
그런 문구가 없었다. 기사 페이지는 무한스크롤이라 "여기가 끝"이라는 표시도 없어서,
마지막 페이지에 닿으면 리스트가 그냥 뚝 끊겼다.

`@plick/domain/brand`에 `articlesOutroCopy(teamFullName?)`를 추가했다. 팀 탭이면
"토트넘 핫스퍼의 이적 루머와 오피셜 소식을 모은 페이지예요", 전체 탭이면
"프리미어리그 팀별 ..."을 돌려준다. brand.ts에 둔 이유는 홈 소개 문구와 같다 —
검색 노출용 문구는 web과 mobile이 같은 값을 내야 해서 단일 출처로 모은다.
"기사의 마지막 페이지예요."라는 문장은 brand가 아니라 컴포넌트에 뒀다. 이건
SEO 문구가 아니라 리스트 상태(끝에 닿았다)를 알리는 UI 텍스트라서다.

ArticlesFeed에서 `!hasNextPage`일 때만 렌더한다. `hasNextPage`는 TanStack Query
무한 쿼리가 마지막 페이지 응답의 `nextCursor`가 null인지로 판정하는 값이고, 감시
요소(sentinel)가 관찰을 끄는 조건과 같은 값이라 새 상태를 만들 필요가 없었다.

검증에서 한 번 막혔다. 로컬 BE에 씨앗 기사가 수백 건이라 어느 팀 탭도 첫 페이지에
`nextCursor`가 있었고, 실제로 끝까지 내려서 문구를 보려면 수십 페이지를 당겨야
했다. 게다가 클로드 브라우저 패널이 숨겨져 있으면 IntersectionObserver가 얼어서
무한스크롤 자체가 안 돈다(이전 세션에서 이미 겪은 함정이다). 그래서 조건을 잠깐
`true`로 강제하고 감시를 꺼서 끝 상태를 스크린샷으로 확인한 뒤 되돌렸다. 되돌린
diff를 git으로 재확인했다.

## 2. 홈 SEO 푸터

홈이 무한스크롤일 때는 리스트가 끝나지 않아 푸터를 둘 자리가 없었다. 첫 페이지
고정이 되면서 바닥이 생겼고, 여기에 푸터(HomeFooter)를 새로 만들었다.

내용은 SEO 관점에서 골랐다.

- 팀별 링크 6개. 앵커 텍스트를 팀 허브의 title·h1과 같은 "○○ 이적 루머"로
  맞췄다. 링크를 받는 페이지의 주제와 앵커 텍스트가 일치할 때 검색엔진이 그
  페이지의 주제를 더 확신한다. 팀 허브가 홈 화면을 재사용하므로 허브끼리도
  서로 링크되는 효과가 있다.
- 서비스 링크: 기사, 릴스, FAQ, 이용약관, 개인정보처리방침. 색인 가치가 있는
  정적 페이지만 실었다. 로그인·마이는 noindex라 뺐다.
- 로고와 카피라이트.

상호작용이 없어 서버 컴포넌트다. 링크가 첫 HTML에 전부 실려야 크롤러가 읽는다.
색·간격·글자는 전부 토큰 유틸이고 링크는 text-3, 라벨·카피라이트는 text-4로
본문보다 어둡게 눌렀다.

## 3. 리스트 팀명·기자명 톤 다운

작업 중에 피드백이 하나 더 들어왔다. 홈·기사 리스트에서 팀 이름과 기자 이름이
너무 밝아 눈이 아프다는 것. 실제로 팀명이 `text-icon`(#c7d2e2), 기자명이
`text-text-2`(#c4cddb)로 제목(#eef2f8)과 밝기 차이가 거의 없어서, 리스트 전체가
같은 밝기로 빛나고 있었다.

둘 다 `text-text-3`(#93a0b4)로 한 단계 내렸다. 굵기(팀명 extrabold, 기자명
semibold)는 그대로 둬서 주변 메타 텍스트와의 구분은 무게로만 하고, 리스트에서
밝게 남는 글자는 기사 제목 하나가 되게 했다. 기자명은 감싸는 문단이 이미
text-text-3이라 색 클래스를 지우는 것으로 충분했다.

## 4. 온보딩 흐름 내리기

온보딩(닉네임 → 응원팀 2단계)을 당분간 쓰지 않기로 했다. 코드는 지우지 않고
남기되, 사용자가 접근할 수 없고 번들에도 들어가지 않아야 한다는 요구였다.

방법은 Next의 private folder 규약을 그대로 썼다. `app/onboarding`을
`app/_onboarding`으로 옮기면 언더스코어 폴더는 라우팅에서 제외되고, 어느 라우트도
import하지 않으므로 빌드 산출물에서도 빠진다. 빌드 후 라우트 목록에서
`/onboarding/*`이 사라진 것과 dev 서버에서 404가 나는 것을 둘 다 확인했다.
폴더 안 상호 참조(`@/onboarding/...`)만 `@/_onboarding/...`으로 일괄 치환했다.

진입점도 끊었다. 로그인 서버 액션(`_services/auth.ts`)이
`data.needsOnboarding ? ONBOARDING_ENTRY : "/"`로 분기하던 것을 항상 홈으로
보내게 바꿨다. `needsOnboarding`은 BE가 `nicknameChangedAt == null`로 계산해
계속 내려주는 필드라 응답 타입에는 남기고, 읽지 않는다는 주석만 달았다.
BE가 가입 시 닉네임을 자동 부여하므로(plick+숫자) 온보딩을 건너뛰어도 서비스
이용에는 지장이 없다.

`ONBOARDING_ENTRY` 상수는 남겼다. 잠들어 있는 온보딩 페이지끼리 참조하고
있어서다. 대신 주석에 지금은 라우팅되지 않는 주소이며, 되살릴 때 폴더를
되돌리고 로그인 분기를 복원하라고 적어 뒀다. robots.ts의 `/onboarding` 관련
주석도 현행에 맞게 고쳤다. `submitOnboarding` 서버 액션(`_services/users.ts`)은
그대로 뒀다 — 같은 파일의 프로필 수정·닉네임 확인 액션이 현역이라 파일을
쪼갤 이유가 없었다.

## 검증

- `pnpm --filter mobile build` 통과, 라우트 목록에 `/onboarding/*` 없음
- `pnpm lint`, `pnpm check-types`, `pnpm format:check` 통과
- dev 서버(:3001) 모바일 뷰포트 스크린샷으로 홈 푸터, 리스트 톤 다운, 기사 끝
  문구(강제 렌더로 확인 후 되돌림), `/onboarding/nickname` 404 확인

## 후속 피드백: 푸터 목적지, 웹 푸터, 더보기 정렬과 색

같은 세션에서 피드백 네 개를 이어 받았다.

푸터 팀 링크의 목적지를 바꿨다. 처음엔 홈 팀 허브(`/teams/[slug]`)로 이었는데,
홈 팀 허브는 상단 팀 탭이 이미 잇고 있으니 푸터는 팀별 기사
페이지(`/articles/teams/[slug]`)로 보내라는 피드백이었다. 듣고 보니 맞는 말이다 —
같은 페이지 안에서 두 요소가 같은 곳을 가리키는 것보다, 끝까지 읽을 목록이 있는
기사 쪽을 새로 이어 주는 게 내부 링크로도 더 값어치가 있다.

웹 홈에도 같은 내용의 푸터를 만들었다. 컴포넌트를 공용화하지는 않았다 —
모바일은 `px-edge`에 ScrollArea 안이고 웹은 전체 폭 border에 PageContainer라
레이아웃 뼈대가 완전히 달라서, ADR 0011 기준으로 프레젠테이션이 다른 조각이다.
내용(링크 목록)만 같고 각자 앱에 둔다. 웹 푸터는 당겨서 새로고침
transform(FeedPullRefresh) 바깥에 놓아 풀 제스처에 딸려 움직이지 않게 했다.

웹 홈의 "더보기" 링크 위치도 고쳤다. 섹션 헤더 행이
`flex justify-between`으로 컨테이너 전체 폭(1200px)을 쓰고 있어서, 더보기가
리스트가 아니라 사이드바 위 우측 끝에 붙어 있었다. 헤더 행을 아래
리스트/사이드바와 같은 그리드 템플릿(`lg:grid-cols-[minmax(0,1fr)_320px]`)으로
감싸 자식 하나만 두는 방법을 썼다 — 헤더 행이 리스트 열 폭과 항상 같이 움직여서
사이드바 폭을 바꿔도 어긋나지 않는다. 수치로 확인하니 더보기 우측(848px)과
리스트 우측(848px)이 픽셀 단위로 일치했다.

더보기 링크(헤더의 "더보기 >", 리스트 끝의 "기사 더보기 >" 블록 버튼) 글자색은
웹·모바일 모두 `text-accent`(초록)로 바꿨다. 회색이던 것이 리스트 안에서
행동 유도라는 게 안 드러난다는 피드백이었다.

검증은 양쪽 빌드와 lint·타입·포맷 통과, 웹은 데스크톱 뷰포트에서 정렬 수치와
전체 스크린샷(스크롤 상태 캡처가 얼어 세로 2400px 뷰포트로 한 화면에 담아
찍었다), 330px 가로 오버플로 0까지 확인했다.

## 후속: 검색 사이트명이 여전히 "PLick"으로 뜨는 문제

구글 검색 결과의 사이트명이 "플릭"이 아니라 "PLick"으로 나온다는 문의를 받았다.
실서비스 HTML을 curl로 직접 확인해 보니 코드는 이미 맞게 나가고 있었다 —
`og:site_name`도, Organization·WebSite JSON-LD의 name도 전부 "플릭"이고 PLick은
alternateName이다(KAN-384에서 맞춘 그대로).

단서는 문의에 첨부된 검색 결과 스크린샷에 있었다. 스니펫 설명문이 KAN-386에서
80자로 줄이기 전의 옛 description이었다. 즉 구글이 보여주는 건 예전 크롤 캐시고,
사이트명 변경 이후 재처리가 아직 안 된 상태다. 구글 사이트명은 스니펫과 별도
시스템이라 재크롤 뒤에도 갱신이 더 느리다. 해결은 코드가 아니라 콘솔이다 —
서치콘솔 홈 색인 재요청과 네이버 서치어드바이저 수집 요청은 소유 확인된 계정에서
직접 눌러야 해서 사용자 몫으로 넘겼다.

코드에서 할 수 있는 보조 신호 정리만 했다. "PLick" 단독 표기가 남아 있던 두
자리 — og:image alt(양쪽 앱 `opengraph-image.alt.txt`)와 Logo 컴포넌트
aria-label — 를 "플릭 PLick"으로 바꿨다. 검색엔진이 로고 대체텍스트를 눈에
보이는 브랜딩 신호로 읽기 때문에, 화면·메타·구조화 데이터의 브랜드 표기를
한글 우선으로 통일하는 몫이다.
