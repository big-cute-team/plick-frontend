# 0240. 모바일 웹 앱 다운로드 팝업과 예측 투표하기 버튼 축소 (KAN-711)

## 배경

KAN-711 티켓은 짧았다. 모바일 웹에 들어온 사람에게 플레이스토어나 앱스토어로 가는 팝업을 띄우되, 이미 앱으로 들어온
사람에게는 띄우지 말고, 우리 로고와 스토어 로고가 있는 "정석적인 앱 다운로드 팝업"에 "하루 동안 보지 않기"를 달아 달라는
것이었다. 티켓 작성자가 가장 걱정한 건 "앱 사용자를 가려낼 수 있는지"였는데, 코드를 뒤져 보니 그건 이미 풀려 있는 문제였다.

앱 셸(plick-AppShell, Expo + React Native WebView)은 웹뷰의 User-Agent 끝에 `PlickApp/1.2.0`을 붙인다. 웹 쪽은 KAN-610
인앱 브라우저 판별을 만들 때 `@plick/core/analytics`의 `resolveBrowserKind`에 이 값을 `plick_app`으로 넣어 두었고, 광고 모드
분기(`AdsProvider`)가 이미 그걸로 앱과 웹을 가르고 있었다. 그러니 이번에 새로 만들 건 팝업 UI와 "하루 동안" 저장 로직, 그리고
스토어 주소 정도였다.

## 시트냐 팝업이냐

처음에는 바텀 시트를 권했다. KAN-567 시안 규칙이 "팝업이 아니라 아래에서 올라오는 시트"였고, 저장소의 다이얼로그가 전부
`BottomSheet` 위에 얹혀 있어서였다. 구글이 모바일 첫 화면에서 본문을 덮는 앱 설치 인터스티셜을 감점한다는 것도 시트 쪽
근거로 들었다.

사용자가 "바텀시트 말고 팝업이 낫지 않나"라고 되물어서 다시 생각했다. 시안 규칙은 신고·차단·로그인 안내처럼 사용자가 뭔가
누른 뒤 뜨는 확인 UI를 두고 정한 것이고, 앱 설치 유도는 서비스가 먼저 거는 프로모션이라 범주가 다르다. 구글 페널티도
모양이 아니라 "검색에서 막 들어온 첫 화면에서 본문을 얼마나 가리느냐"가 기준이라 화면 절반을 덮는 시트와 가운데 중간
크기 팝업은 같은 취급이다. 그래서 가운데 팝업으로 갔고, 대신 크롤러 UA를 제외하고 카드 세로를 내용만큼만 차지하게 해서
본문이 위아래로 보이게 했다.

껍데기는 `PopupDialog`로 따로 만들었다. `BottomSheet`가 하는 세 가지, 즉 body로 포털을 뚫는 것(상단바의 `backdrop-blur`
같은 조상 filter가 `fixed`의 기준 상자를 바꿔 화면 전체를 못 덮는 문제), 딤을 누르면 닫히는 것, Escape로 닫히는 것을
그대로 가져오고 정렬만 가운데로 바꿨다. 카드 폭은 좌우 `px-edge`를 남기고 최대 20rem이다. 앱 셸이 480px로 중앙 정렬되는
넓은 화면에서도 가운데 카드라 어색하지 않다.

## 어느 스토어 버튼을 보일 것인가

티켓은 "플레이스토어, 앱스토어 구분된 로고로 각각 갈 수 있는 버튼"이라 썼지만, 아이폰 사용자에게 플레이스토어 버튼은 갈
데가 없다. OS에 맞는 스토어 버튼 하나만 보이기로 했다. 검증 중 사용자가 "왜 구글플레이만 있냐"고 물었는데, 브라우저
패널이 안드로이드(Pixel) UA를 흉내 내고 있어서였다. 설명하자 그 방식대로 가자고 했다.

OS 판별은 `resolveMobileOs`를 `@plick/core/analytics`에 더했다. 안드로이드는 UA의 `Android`, 아이폰은 `iPhone|iPad|iPod`
로 가른다. 아이패드 사파리는 iOS 13부터 UA가 `Macintosh`라 UA만으로는 맥과 구분이 안 되는데, `navigator.maxTouchPoints`가
맥은 0이고 아이패드는 5라 그걸로 가른다. 둘 다 아니면 null이고 팝업을 안 띄운다. 데스크톱 브라우저로 m 도메인에 들어온
사람에게는 스토어 버튼 대신 이미 PC 전환 배너가 뜬다. 단위 테스트(`tests/unit/mobile-os.test.mjs`)는 KAN-610 테스트의
UA 표본을 그대로 가져와 인스타 인앱, 사파리, 데스크톱, 아이패드 데스크톱 모드, 모바일 구글봇을 돈다.

## 안 띄우는 경우 다섯

판단은 마운트 뒤 `useEffect`에서 한 번 한다. 서버는 localStorage도 `navigator.userAgent`도 모르니 첫 렌더에는 안 그리고
이펙트에서 OS를 정한다. 기존 배너 둘(`SwitchToWebBanner`, `OpenInBrowserBanner`)과 같은 패턴이라 하이드레이션이 어긋나지
않는다.

1. 우리 앱 셸. `resolveBrowserKind(ua) === "plick_app"`.
2. 크롤러. `CRAWLER_UA_PATTERN`(KAN-607)이 걸리면 안 띄운다. 구글봇은 자바스크립트를 돌리니 이 제외가 없으면 렌더링
   결과에 팝업이 들어간다.
3. 폰이 아닌 기기. `resolveMobileOs`가 null.
4. "하루 동안 보지 않기" 뒤 24시간, 그리고 "닫기" 뒤 같은 탭 세션.
5. `/login`, `/signup`, `/oauth` 경로. 소셜 로그인 리다이렉트 위에 팝업이 서면 흐름이 꼬인다. 경로 제외는 렌더마다 보므로
   로그인에서 홈으로 돌아오면 그때 뜬다.

기존 배너의 닫기는 localStorage에 `"1"`만 적는 영구 닫기였다. 이번에는 값에 다시 띄울 수 있는 시각(epoch ms)을 적는다.
`Date.now() + 24h`를 저장하고, 읽을 때 지금보다 미래면 안 띄운다. "닫기"는 sessionStorage에 적는다. 페이지를 오갈 때마다
다시 뜨면 팝업이 아니라 방해라서, 탭을 닫기 전까지는 한 번만 보인다. 두 저장소 접근은 try/catch로 감쌌다. 사파리 사생활
보호 모드와 일부 인앱 웹뷰는 `localStorage`에서 던진다. 못 읽으면 안 닫은 것으로, 못 쓰면 조용히 넘긴다.

인스타 인앱 브라우저는 저장소를 잘 잊는다. KAN-610에서 쿠키를 날을 넘겨 안 들고 다녀 기기 식별자를 localStorage에
복제했던 전례가 있다. "하루 동안"도 localStorage 기준이라 인앱에서는 하루보다 자주 보일 수 있는데, 이건 받아들였다.

## E2E가 깨지는 문제

`tests/e2e`는 배포된 dev를 Playwright로 타는데 모바일 프로젝트가 갤럭시 UA를 쓴다. 팝업이 홈에 뜨면 딤이 클릭을
삼켜 모든 시나리오가 깨진다. 처음 생각은 E2E 봇 쿠키(`plick_e2e`)를 브라우저에서 읽어 제외하는 것이었는데, 그 쿠키는
HttpOnly다. 외부 호스트로 값이 새지 않게 도메인을 좁히고 서버만 읽게 한 KAN-573의 결정이라 바꿀 이유가 없었다.

대신 playwright.config의 `storageState`에 `origins`를 두고, 모바일 origin의 localStorage에 "하루 동안 보지 않기" 키를 먼
미래 값(2099년)으로 심었다. Playwright는 컨텍스트를 만들 때 이 값을 미리 넣어 두므로 팝업 코드가 보기에는 이미 닫은
사람이다. 키 이름은 `apps/mobile/app/_constants/app.ts`의 상수와 같아야 해서 양쪽 주석에 서로를 적어 두었다.

이 치환을 perl 한 줄로 하다가 파일을 망가뜨렸다. `s{...}{...}` 구분자 안에 `{`와 `}`가 든 패턴을 넣었더니 perl이 짝을
잘못 맞춰 치환문 자체가 파일에 섞여 들어갔다. 읽어서 그 블록을 통째로 다시 썼다. 중괄호가 든 코드를 치환할 때는
구분자를 바꾸거나 스크립트로 하는 게 맞다.

## 자산

앱 로고는 사용자가 채팅에 준 512 PNG였는데, `scripts/brand-assets/src/app-icon.png`(804px)와 같은 그림이었다.
원본이 더 크니 거기서 만들었다. `build.mjs`에 정사각 webp 두 단계(144·216)를 더하고 `@plick/ui`의 `Logo.tsx`에
`SquareLogo`를 뒀다. 72px 자리의 ×2와 ×3이라 두 단계이고 srcset으로 고른다. 모서리는 파일에서 깎지 않고 CSS
`rounded-hero`로 둥글린다. `public/`이 아니라 import인 이유는 KAN-624와 같다. import 자산은 해시 경로라 CDN이 1년
캐시한다. 빌드 스크립트를 다시 돌렸는데 기존 산출물은 바이트 단위로 같게 나와 새 파일 둘만 늘었다.

스토어 로고는 공식 배지 대신 단색 글리프를 골랐다. 애플 글리프는 KAN-395 소셜 로그인용 `AppleIcon`이 이미 있어서
그대로 썼다. 처음에 모르고 같은 이름으로 하나 더 넣었다가 `check-types`가 재선언 오류를 내서 알았다. 구글 플레이
삼각형은 simple-icons(CC0)의 경로를 가져와 `GooglePlayIcon`으로 넣었고 `AppleIcon`과 같은 꼴(px 크기, `currentColor` 면)로
맞췄다. 공식 네 색을 안 쓴 건 토큰 밖 색을 코드에 박지 않으려는 것이고, 초록 버튼 위 흰 글리프라 구분은 충분하다.

스토어 주소는 `@plick/domain/brand`에 뒀다. 앱 셸 저장소의 `eas.json`에 App Store Connect ID가, `app.config.ts`에 패키지명
`kr.co.plick.app`이 있다. 플레이스토어 주소에는 설치 리퍼러 `referrer=utm_source%3Dplick_mweb%26utm_medium%3Dpopup...`을
실었다. Play Console이 이 값을 설치 보고에 쓰므로 인스타 광고로 들어온 사람이 팝업을 거쳐 설치했는지 나중에 볼 수 있다.
앱스토어 캠페인 링크는 제공자 토큰(`pt`)이 있어야 `ct`가 집계되는데 아직 발급 전이라 주소만 뒀다.

## 검증에서 막힌 것 둘

같은 체크아웃에 다른 세션의 dev-mock 서버(3030, 3031)가 떠 있어 Next 16 잠금 때문에 새로 못 띄웠다. KAN-698 때처럼
그 서버에 그냥 접속하려 했는데 3031이 응답을 안 했고 사용자도 "무한로딩"이라고 했다. 로그를 보니 `○ Compiling / ...`에서
멈춰 있었다. 이틀 가까이 떠 있던 Turbopack dev 서버가 새 파일이 여럿 추가되자 재컴파일에서 굳은 것이다. 프로세스를
SIGKILL로 내리고(SIGTERM은 안 들었다) 같은 launch 항목으로 다시 띄우니 바로 돌았다.

iOS 시뮬레이터는 Safari에서 `127.0.0.1:3031`로 열었더니 팝업이 안 떴다. 메모에 적혀 있던 요령이었는데, 서버 로그에
"Blocked cross-origin request to Next.js dev resource from 127.0.0.1"이 찍혀 있었다. Next 16은 `allowedDevOrigins`에 없는
출처의 dev 리소스 요청을 막아서 하이드레이션이 안 되고 실검도 "불러오는 중"에 멈춰 있었다. `localhost:3031`로 다시
여니 App Store 버튼 팝업이 떴다. 127.0.0.1 요령은 `next start` 빌드 서버에서만 통한다(KAN-681 메모와 같다).

## 투표하기 버튼

사용자가 같은 PR에 넣어 달라고 한 건이 하나 더 있다. KAN-710에서 예측 3분할 바 바로 아래로 옮긴 `투표하기` 버튼이
웹·모바일 둘 다 너무 컸다. 처음엔 폭만 줄여 오른쪽에 붙였는데(`ml-auto w-fit px-5`), 이어서 "배경과 테두리 없는 글자
버튼"으로 해 달라고 해서 `text-accent` 글자 버튼으로 바꿨다. 같은 줄의 랭킹 링크와 같은 꼴이다. 탭 영역은 `-mr-2 px-2`로
글자보다 조금 넓게 두되 글자 오른쪽 끝이 바의 오른쪽 끝에 맞게 했다. mock 경기 900003(OPEN, 내 예측 없음)에서 모바일
3031과 웹 3030 둘 다 바 아래 오른쪽에 글자만 서는 걸 확인했다.

## 남은 것

- 앱스토어 캠페인 링크의 제공자 토큰. App Store Connect에서 발급받으면 `APP_STORE_URL`에 `pt`·`ct`를 단다.
- 이미 설치한 사람이 외부 브라우저로 들어오면 팝업이 뜬다. 스토어가 "열기"로 바뀌니 해는 없지만, 바로 앱을 여는 건
  앱 셸에 유니버설 링크·앱 링크가 생겨야 한다.
- 데스크톱 웹은 안 건드렸다. 스토어 팝업은 폰에서만 의미가 있고, 데스크톱이면 QR 코드가 정석이다.
- 노출 뒤 홈 이탈이 늘면 첫 페이지가 아니라 두 번째 페이지 이동 때 띄우는 선택지가 있다. `X-Plick-Path` 유입별 체류를
  배포 전후로 비교한다.
