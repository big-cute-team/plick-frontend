# 0104. 커서 400 "다시 시도"가 무한 400에 갇히는 경합 수정 (KAN-404)

## 티켓은 "확인만 하고 닫으면 됨"이었다

KAN-404는 원래 확인용 티켓에 가까웠다. BE가 피드·릴스 정렬 기준을 원문 발행 시각으로
바꾸면서(KAN-397) 커서 포맷이 v2로 바뀌었고, 배포 순간 무한스크롤 중이던 사용자가 옛 v1
커서로 다음 페이지를 요청하면 400 `COMMON_INVALID_PARAM`이 온다. 티켓 본문에도 "이미 커서
에러를 첫 페이지 재요청으로 처리하고 있으면 이 티켓은 확인만 하고 닫으면 됨"이라고 적혀
있었다.

그리고 코드를 보면 실제로 처리가 있었다. KAN-379 때 넣어둔 것들이다.

- 훅(`useArticleFeed`/`useReelsFeed`)의 `retry` 콜백이 4xx를 즉시 끊어서 무의미한 자동
  재시도를 막는다.
- 화면 컴포넌트의 `retryNextPage`가 400이면 `restartFeedQuery`를 불러 커서 체인을 버리고
  첫 페이지부터 다시 받는다. 기사·릴스, 모바일·웹 네 곳 모두 같은 형태다.

그래서 처음에는 "이미 돼 있으니 확인 코멘트만 남기고 닫자"고 결론 냈다. 그런데 사용자가
dev에서 직접 눌러 보니 아니었다. "다시 시도"를 무한히 눌러도 계속 400이 뜨고, 새로고침을
해야만 살아난다는 거였다. 코드 읽기로 내린 결론과 실기기 관찰이 정면으로 충돌했다.

## dev에서 재현하기: 죽은 커서를 어떻게 다시 만드나

문제는 재현 조건이었다. 배포 순간의 v1 커서는 이미 세상에 없다. dev BE는 이제 v2 커서만
발급하니까, 그냥 접속해서는 이 버그를 못 밟는다.

그래서 브라우저에서 `window.fetch`를 몽키패치해서 "옛 커서" 상황을 흉내 냈다. 패치 이후
클라이언트가 응답으로 새로 받은 `nextCursor`들만 "유효한 커서" 집합에 넣고, 그 집합에 없는
커서(= 서버 렌더 씨앗이 들고 있던, 패치 이전 세대의 커서)를 실은 요청은 커서 값을 깨진
문자열로 바꿔 보냈다. 서버 입장에서는 v1 커서가 온 것과 똑같다.

한 가지 더 걸림돌이 있었다. 이 세션의 브라우저 패널은 hidden 상태라
IntersectionObserver와 스크롤 입력이 얼어 있다(이전에 [ADR과 메모리에 적어둔
함정](0100-skeleton-flicker-removal.md)과 같은 계열). 무한스크롤 센티널을 실제로 노출시켜
다음 페이지를 당기게 만들 수가 없다. 대신 React fiber를 걸어 올라가
`QueryClientProvider`의 `client` prop을 찾아내는 방법을 썼다. DOM 요소의
`__reactFiber$...` 키에서 시작해 `memoizedProps.client`에 `getQueryCache`가 있는 fiber를
찾으면 그게 QueryClient다. 여기서 쿼리 상태를 직접 들여다보고,
`query.observers[0].fetchNextPage()`로 센티널이 하는 일을 그대로 흉내 낼 수 있었다.

이렇게 dev 기사 피드에서 400 에러 상태를 만들고 "다시 시도" 버튼을 `click()`으로 눌렀더니,
관찰 결과가 이상했다.

- 커서 없는 첫 페이지 재요청이 나가서 200으로 성공했다. `restartFeedQuery`는 분명히 돌았다.
- 그런데 그 직후 커서를 실은 요청이 하나 더 나갔고(내가 누른 게 아니다), 최종 쿼리 상태는
  다시 400 에러였다. 성공한 첫 페이지 응답은 캐시에 반영되지 못했다.

복구 요청이 성공하고도 버려진다. 여기서 경합을 의심하기 시작했다.

## 원인: 자동 다음 페이지 트리거가 복구 refetch를 죽인다

순서를 풀면 이렇다.

1. "다시 시도" → `retryNextPage`가 400을 확인하고 `restartFeedQuery`를 부른다.
   `restartFeedQuery`는 캐시를 첫 페이지 하나로 줄인 뒤(`setQueryData`)
   `refetchQueries`로 다시 받는다. 그런데 이때 남긴 첫 페이지는 옛날(배포 전) 응답이라
   `nextCursor`가 여전히 죽은 v1 커서다.
2. `setQueryData`가 캐시를 다시 쓰는 순간 쿼리의 에러 상태가 풀린다. 그러면
   `isFetchNextPageError`로 꺼져 있던 자동 다음 페이지 트리거가 되살아난다. 기사는
   센티널 IntersectionObserver(사용자는 이미 리스트 끝에 있으니 즉시 발화), 릴스는
   `remaining <= REELS_PREFETCH_AHEAD`일 때 도는 useEffect 프리페치다. 에러 슬라이드를
   보고 있다는 건 끝 슬라이드에 있다는 뜻이라 릴스는 조건이 거의 항상 참이다.
3. 트리거가 `fetchNextPage()`를 부른다. 커서는 `getNextPageParam`이 캐시의 마지막
   페이지에서 읽는데, 그게 1번에서 남긴 옛 첫 페이지다. 즉 죽은 v1 커서로 요청이 나간다.
4. 여기가 급소다. TanStack Query의 `fetchNextPage`는 기본값이 `cancelRefetch: true`라,
   진행 중인 fetch를 취소하고 자기가 시작한다. 1번에서 띄운 복구용 refetch가 여기서
   취소된다. 이펙트/옵저버 발화(수 ms)가 네트워크 왕복(수백 ms)보다 항상 빠르니 복구
   refetch는 사실상 매번 죽는다.
5. 죽은 커서 요청은 400 → 다시 에러 상태 → 트리거는 다시 꺼진다. 사용자가 또 누르면
   1번부터 반복. 무한 400이다.

새로고침이 살아나는 이유도 이걸로 설명된다. 하드 리로드는 서버 컴포넌트가 첫 페이지
씨앗을 새로 받아 심으니, 죽은 커서가 캐시에서 완전히 사라진다.

KAN-379에서 이 재시도 로직을 만들 때는 "restartFeedQuery가 refetch를 끝내면 새 커서가
온다"까지만 생각했지, refetch가 날아가 있는 동안 캐시에 남은 옛 페이지의 커서로 다른
트리거가 발화할 수 있다는 건 생각하지 못했다. 트리거 조건이 `!isFetchingNextPage`였던 게
구멍이다. 복구 refetch는 "다음 페이지 fetch"가 아니라서 이 조건을 통과한다.

## 수정: 트리거를 isFetching으로 막는다

수정 자체는 작다. 네 곳(모바일 `ArticlesFeed` 센티널, 모바일 `ReelsFeed` 프리페치 이펙트,
웹 `PostFeed` 센티널, 웹 `ReelsWorkspace` 프리페치 이펙트)의 트리거 조건에서
`!isFetchingNextPage`를 `!isFetching`으로 바꿨다. `isFetching`은 다음 페이지 fetch만이
아니라 모든 fetch(복구 refetch 포함)가 나가 있는 동안 참이라, 복구가 도는 동안 트리거가
아예 발화하지 못한다. refetch가 끝나면 캐시의 첫 페이지가 새 커서를 단 최신본으로 바뀌어
있으니, 그때 발화하는 fetchNextPage는 정상적으로 이어진다.

타이밍 구멍이 없는지도 따져봤다. `restartFeedQuery`는 `setQueryData`와 `refetchQueries`를
동기로 연달아 부르고, refetch는 호출 즉시 `fetchStatus`를 fetching으로 바꾼다. React
리렌더(와 이펙트 실행)는 그 뒤에 배치로 돌기 때문에, 컴포넌트가 "에러 풀림"을 보는 시점엔
이미 `isFetching`이 참이다. 트리거가 비집고 들어올 창이 없다.

대안으로 `fetchNextPage({ cancelRefetch: false })`도 검토했다. 이러면 fetch 진행 중의
fetchNextPage 호출이 무시돼 같은 효과가 난다. 다만 트리거 쪽 조건을 고치는 편이 "복구 중엔
다음 페이지를 당기지 않는다"는 의도가 코드에 그대로 드러나서 조건 수정을 택했다. 둘 다
넣는 것도 가능했지만, 조건이 막으면 cancelRefetch까지 갈 일이 없어 중복이라 뺐다.

참고로 UX 대안으로 "끊김 없는 이어붙이기"(queryFn 안에서 커서 400을 잡아 그 자리에서 커서
없이 첫 페이지를 받아 다음 페이지로 반환)도 논의했다. 릴스에서는 스와이프 흐름이 안 끊겨
매력적이지만, 기사 리스트에서는 방금 본 글이 아래에 또 이어붙는 중복 노출이 생긴다. 두
화면의 동작을 갈라놓기보다 지금의 "다시 시도" 버튼 방식을 유지하면서 버그만 고치기로 했다.

## 검증: 목 BE로 커서 세대 전환을 재현했다

로컬 BE가 없어서 검증용 목 BE를 만들었다(스크래치패드, :8080). 커서에 세대(epoch) 개념을
넣어 `E1-C1` 같은 커서를 발급하고, `POST /___cutover`로 세대를 올리면 이전 세대 커서는
전부 400 `COMMON_INVALID_PARAM`을 돌려준다. v1→v2 전환 배포를 그대로 흉내 낸 거다. 요청
로그도 쌓아서 나중에 순서를 검증할 수 있게 했다.

로컬 모바일 dev 서버를 이 목 BE에 붙였더니 재미있는 게 하나 걸렸다. 첫 로드에서 진짜
서비스 릴스("맨체스터 유나이티드…")가 나온 거다. 이전 dev 세션 때 Next 서버 데이터
캐시(`.next/cache`, 익명 GET revalidate 60초)에 남아 있던 응답이 씨앗으로 나온 거였다.
서버 캐시가 옛 커서를 씨앗에 실어 보낼 수 있다는, 이 버그의 트리거 조건 하나를 우연히
직접 목격한 셈이다.

A/B로 검증했다. 릴스에서 프리페치 이펙트가 자연 발화하는 조건(짧은 리스트 + 죽은 커서)을
만들고,

- 수정 전 코드: "다시 시도"를 3번 눌러도 전부 400 에러 상태 그대로. 목 BE 로그에는
  `cursor=None`(복구 요청) → `cursor=E1-C1`(죽은 커서) 쌍이 클릭마다 반복해서 찍혔다.
  복구 요청이 매번 나가고 매번 죽는 게 로그로 보인다. 사용자가 dev에서 본 증상 그대로다.
- 수정 후 코드: 같은 조건에서 한 번의 클릭으로 복구. 죽은 커서 요청 없이 커서 없는
  재요청만 나가 200을 받고, 새 세대 첫 페이지(10장)와 유효한 `nextCursor`로 정상 전환됐다.
  이어서 다음 페이지도 새 커서로 잘 물려 받았다.

기사 쪽은 센티널 IntersectionObserver가 hidden 패널에서 안 돌아 같은 방식의 로컬 A/B는
못 했지만, dev-m에서의 최초 재현이 기사 피드였고(위에서 본 "성공하고도 버려지는 복구
요청") 메커니즘과 수정이 릴스와 동일하다.

## 교훈

- "코드에 처리가 있다"와 "그 처리가 동작한다"는 다르다. 이번에도 코드 읽기로는 완벽해
  보였고, 실제로 눌러보니 죽어 있었다. 사용자의 "아닌 거 같은데?" 한 마디가 없었으면
  확인 코멘트만 남기고 닫을 뻔했다. 재현 절차가 가설보다 먼저라는 걸 또 확인했다.
- 에러 상태를 풀면서 비동기 복구를 시작하는 코드는, 에러 상태가 꺼두었던 자동 트리거가
  그 순간 되살아난다는 것까지 책임져야 한다. 상태 하나(에러)를 여러 소비자(재시도 버튼,
  프리페치 트리거)가 공유하면 한쪽의 복구가 다른 쪽의 오발을 부른다.
- TanStack Query `fetchNextPage`의 `cancelRefetch: true` 기본값은 "사용자가 다음 페이지를
  원하면 그게 우선"이라는 가정인데, 복구 refetch가 날아가 있는 상황에서는 이 가정이
  거꾸로 작동한다. 기본값의 가정이 내 상황과 맞는지 의심할 것.
- hidden 브라우저 패널에서 IntersectionObserver가 얼어 있어도, fiber 걸어 올라가기로
  QueryClient를 잡으면 `query.observers[0].fetchNextPage()`로 트리거를 흉내 내고 쿼리
  상태를 직접 검증할 수 있다. UI 입력이 막힌 환경에서 데이터 레이어를 검증하는 우회로로
  기억해 둘 만하다.
