# ADR 0025 — 모바일 내 프로필 조회 API 연결 (KAN-267)

- **날짜:** 2026-07-21
- **범위:** `apps/mobile` — `GET /api/v1/users/me`를 MY(`/me`)·프로필 수정(`/me/edit`)·온보딩 닉네임(1단계)에 연결. `CURRENT_USER` 목 제거.
- **관련:** [ADR 0024 온보딩 저장 API](0024-mobile-onboarding-api.md) · `api-integration` 스킬 · [ADR 0011 공용 경계](0011-shared-code-boundary.md)

## 무엇을 했나

온보딩 저장(KAN-264)에 이어 두 번째 보호 API를 붙였다. 이번엔 쓰기가 아니라 읽기 —
`GET /users/me`로 닉네임·이메일·마이팀을 받아, 지금까지 `CURRENT_USER` 목으로 채우던
MY 화면과 프로필 수정 화면을 실제 데이터로 바꿨다. 온보딩 1단계의 닉네임 초깃값도
이 API 몫이라(KAN-264에서 "그 API 티켓에서 채운다"고 미뤄둔 자리) 같이 채웠다.

## 스웨거 설명이 틀려 있었다

스킬이 "티켓을 믿지 말고 스웨거를 읽어라"라고 해서 읽었는데, 이번엔 스웨거 설명도 틀려
있었다. 설명엔 "온보딩 전이면 자동 닉네임(plick+숫자)을 반환한다"고 적혀 있지만, 테스트
유저를 만들어 실제로 때려 보니 `nickname: null`이 왔다. BE 코드를 열어 보니 자동 닉네임
생성 로직 자체가 아직 없다. 결국 진실은 스웨거 문서도 아니고 **실제 응답**이다 — 검증용
JWT를 직접 민팅해 온보딩 전/후 두 상태를 다 받아보고 나서야 shape를 확정했다.

그래서 FE는 `nickname`을 nullable로 받고, 온보딩 1단계는 null이면 빈 값으로 시작하게
했다. BE가 나중에 자동 닉네임을 구현하면 코드 수정 없이 그 값이 흘러 들어온다.
`email`도 카카오 가입 유저는 null이라(실제 DB에서 확인) 같이 nullable로 다뤘다.

## 경계 변환 — 배열을 단일 팀으로 접기

BE는 마이팀을 `teams: [{teamId, shortName, nameKo, logoUrl}]` 배열로 주지만 제품은
단일 팀이다(온보딩도 팀 하나만 보낸다). 화면마다 `teams[0]` 처리를 반복하기 싫어서
fetcher(`_lib/api/profile.ts`)의 경계 변환에서 `myTeam: TeamCode | null` 하나로 접었다.
다행히 `shortName`이 FE `TeamCode`("LIV" 등)와 같은 값이라 — KAN-264 때 문제가 됐던
teamId 숫자 매핑(`TEAM_IDS`)과 달리 — **재시드에 흔들리지 않는 문자열 코드로 역방향
매핑**이 된다. 빅6 밖의 코드가 오면 버린다(레지스트리에 없는 팀으로 화면이 깨지지 않게).

`handle`은 BE에 아예 없는 개념이라 프로필 카드의 둘째 줄엔 이메일을 넣었다. 도메인
`User` 타입(닉네임·핸들·이메일·팀)은 웹이 아직 목으로 쓰고 있어 건드리지 않고, 모바일
전용 `MyProfile` 타입을 `_lib/api/types.ts`에 새로 뒀다 — 첫 앱은 앱별, 웹이 같은
엔드포인트를 붙일 때 공용 승격을 판단한다(ADR 0011 게이트 C). 그때 `User`를 BE 계약
쪽으로 정리하는 것까지 같이 보면 될 것이다.

## fetcher를 서버 액션으로 만들지 않은 이유

KAN-264의 `submitOnboarding`은 `"use server"` 서버 액션이지만, 이번 `getMyProfile`은
아니다. 서버 액션은 "클라이언트에서 부를 수 있는 서버 함수"를 만드는 장치라 POST
엔드포인트가 하나 생기는 건데, 이건 **렌더 중에 읽기만 하는** 함수다. `cookies()`로
access 토큰을 읽어 Bearer로 싣고, 쿠키를 심지도 않는다. 그래서 `session.ts`처럼 그냥
서버 전용 모듈로 뒀다. 유저별 응답이라 `cache: "no-store"`도 박았다 — 서버 fetch의
Next 데이터 캐시는 **모든 유저가 공유**하는 캐시라, 내 프로필이 남의 렌더에 재사용되는
사고는 여기서 막아야 한다.

401 처리는 화면 성격대로 갈랐다. `/me`는 로그인 유도 카드가 이미 있으니 null을 돌려
그 분기를 태우고(무효 토큰 = 비로그인 취급), `/me/edit`과 온보딩은 세션 없이는 성립하지
않는 화면이라 `redirect("/login")`. 401 밖의 실패(BE 다운)는 fetcher가 그대로 던진다.

## 처음 생긴 로딩·에러 상태

목은 항상 즉시·성공이라 없던 상태가 fetch엔 있다. 로딩은 세 라우트에 `loading.tsx`
스켈레톤(`bg-elevate` 토큰, 실제 카드 자리 모양)을 뒀다 — Next가 서버 렌더가 끝날
때까지 이걸 먼저 스트리밍해 준다. 에러는 라우트별로 만들지 않고 앱 루트에 `error.tsx`
하나를 그물로 깔았다("문제가 생겼어요" + 다시 시도). `reset()`이 세그먼트를 다시
렌더하므로, BE를 죽였다 살리고 다시 시도를 누르면 프로필로 복구되는 것까지 확인했다.

## 검증

로컬 BE + 공유 DB에 일회용 테스트 유저 둘(온보딩 전/후)을 만들어 JWT를 민팅해 밟았다:
성공(팀 있음 "리버풀" 배지 / 팀 없음 "미설정"), 닉네임·이메일 null 표기, 비로그인
`/me`(유도 카드), 무효 토큰 401(유도 카드 폴백), 비로그인 온보딩 진입(`/login`
리다이렉트), BE 다운(에러 경계 → 복구). 테스트 유저는 삭제했다. check-types·lint·
format:check·mobile 클린 빌드 통과. 목이 사라진 `CURRENT_USER`는 mock.ts에서 지웠다
(웹 목은 웹 연동 티켓 몫).
