# 0190. 모바일 팀 프로필을 네 탭으로, 선수 프로필을 새로 (KAN-604)

## 무엇이 남아 있었나

2026-10 디자인 핸드오프에서 바뀐 화면은 팀 프로필과 선수 프로필 둘이다. 팀 프로필은 개요, 경기, 선수단,
기록 네 탭이 되고, 선수 프로필은 선수단에서 선수를 누르면 들어가는 새 화면으로 개요, 기록, 경기 세 탭이다.
KAN-604는 이걸 웹과 모바일 둘 다에 맞추는 티켓이었다.

작업을 시작하면서 먼저 어디까지 와 있는지 확인했다. 웹은 이미 끝나 있었다. 에픽 KAN-586 아래 KAN-599(웹 팀
프로필, [ADR 0187](0187-web-team-profile-redesign.md))와 KAN-600(웹 선수 프로필,
[ADR 0188](0188-web-player-profile.md))이 develop에 들어가 있었다. 남은 건 모바일이었다. 모바일 팀
프로필(`/teams/[slug]/profile`)은 KAN-574 때의 선수단, 팀 정보 두 탭 그대로였고, 선수단은 포지션별 칩
트랙이라 칩을 누르면 시즌 스탯 바텀 시트가 떴다. 선수 프로필 라우트는 아예 없었다.

BE도 확인했다. 팀 요약, 팀 경기, 팀 시즌 기록, 선수단 확장, 선수 프로필, 선수 경기, 선수 시즌별 기록 일곱
경로가 BE develop과 main에 모두 들어가 있었다. Jira의 BE 티켓들(KAN-588~595)은 "해야 할 일"로 남아 있었지만
상태만 안 옮긴 것이었다. prod에 경로가 실제로 올라가 있는지는 응답으로 가렸다. 없는 경로는 인증 필터에 걸려
`AUTH_REQUIRED`가 오는데, 새 경로들은 `MATCH_UPSTREAM_ERROR`(502)가 왔다. 라우트는 있고, 외부 축구 데이터
(API-Football)가 일시 중지라 값을 못 받는 상태라는 뜻이다. 순위표와 경기 목록까지 축구 데이터는 전부 502였다.
그래서 화면은 BE의 mock 프로필(8081)로 만들고, 502 상태는 prod BE에 붙여 그대로 확인하기로 했다.

## 데이터 계층은 그대로 쓰고 화면만 새로 짰다

웹 작업 때 데이터 계층을 이미 공용으로 만들어 둔 덕을 크게 봤다. 응답을 화면용 타입으로 바꾸는 fetcher는
`@plick/core/team-profile`, `@plick/core/player-profile`에 있고, 순위표에서 이 팀 앞뒤 5행을 자르는
`standingsWindow`, 선수단을 포지션별로 묶는 `groupSquadByPosition`, 팀 내 득점과 도움 순위를 고르는
`teamLeaders`, 90분당 수치를 만드는 `playerStatGroups`, 출전 형태를 세는 `usageCounts` 같은 계산은
`@plick/domain`에 단위 테스트까지 붙어 있었다. 모바일은 이걸 그대로 가져다 쓰고 화면만 새로 짰다. 같은
계산을 두 벌 두지 않으니, 예를 들어 "출전했는데 기록이 없는 골은 0, 출전 안 했으면 -" 같은 규칙이 두 앱에서
갈릴 일이 없다.

페이지가 하는 일도 웹과 같다. 팀은 요약, 경기, 시즌 기록, 선수단, 순위표, 팀 이슈 여섯 조회를
`Promise.allSettled`로 한 번에 받는다. 요약이 404면 not-found이고, 그 밖의 실패는 화면을 막지 않는다. 머리는
레지스트리 이름으로 그리고 숫자 상자는 "-"로 둔다. 관련 이슈는 우리 DB라 외부 장애와 무관하게 살아 있으니까
그것만이라도 보여 주는 게 맞다. 선수는 프로필, 경기, 시즌별 기록을 먼저 받고, 프로필에서 나온 소속팀으로
선수단(같은 팀 선수)을, 연결된 인물(`figureId`)로 관련 이슈를 이어서 받는다.

## 웹 레일을 모바일 어디로 옮기나

모양이 가장 많이 달라진 곳은 웹의 우측 레일이다. 웹은 본문 옆 300px 레일에 리그 순위 5팀, 구단 정보, 팀 내
순위, 부상자(팀), 시즌 출전과 같은 팀 선수(선수)를 둔다. 모바일은 레일 자리가 없어 탭 본문 안으로 내려야 했다.
어디로 내릴지는 시안이 정해 줬다. 팀은 리그 순위와 구단 정보가 개요 탭 아래로, 팀 내 순위와 부상자가 기록 탭
아래로 갔다. 선수는 시즌 출전과 같은 팀 선수가 개요 탭 아래로 갔고, 같은 팀 선수는 사진 76짜리 카드를 가로로
미는 줄이 됐다.

그래서 웹은 `TeamProfileView`가 `railTop`, `railBottom`을 받는데, 모바일은 그 자리가 없고 대신 개요 탭 노드에
순위와 구단 정보를 넣었다. 기록 탭은 대회 선택을 따라 클라에서 그리는 탭이라 팀 내 순위(선수단 기록으로
계산)와 부상자를 함께 넘겨 `TeamStatsPanel` 안에서 이어 그린다.

## 만들면서 고른 것들

탭 줄은 두 프로필이 같은 모양이라 `ProfileTabBar` 하나로 뺐다. 시안 수치대로 높이 44, 간격 22, 활성 900 +
2px 밑줄이고, 스크롤 본문 안에서 `sticky top-0`으로 붙는다. 밑줄을 `border-b-2` 대신 `inset 0 -2px 0` 그림자로
그린 건 시안 그대로다. 테두리로 그리면 탭 글자 상자 높이가 2px 늘어 탭 줄 밑선과 어긋난다. 본문 여백
(`px-edge`) 안에 놓이지만 바탕과 밑선은 화면 끝까지 가야 해서 `-mx-edge px-edge`로 넓혔다.

탭 상태는 웹처럼 URL에 올리지 않았다. 프로필을 열 때마다 개요로 시작해야 해서다. 팀에서 선수로, 선수에서 다른
팀으로 옮겨 갈 때 같은 컴포넌트가 재사용되며 이전 탭이 남지 않도록 `key`를 slug, playerId로 걸었다.

경기 행 날짜 칸이 좁아 선수 경기 행은 "10.3"처럼 점 표기를 쓴다. 웹의 "10월 3일"(`playedDateLabel`)에서
만드는 `dotDateLabel`을 도메인에 더했다. 행 아래 줄 "73', 1골, 슈팅 1, 패스 21"도 규칙이 있다. 골과 도움은
있을 때만 쓰고, 슈팅과 패스는 0이어도 쓰고, 결장은 "결장", 기록 조회에 실패한 경기(UNKNOWN)는 "-"다. 이것도
`matchStatLine`으로 도메인에 넣고 테스트를 붙였다.

시즌별 기록 표에서 한 번 고쳤다. 처음에는 좁은 폭이라 대회명을 행 `title`로만 남겼는데, 캡처해 보니 같은 시즌
줄이 리그와 컵으로 두 번 서면서 똑같이 "2026-27 토트넘"으로 보였다. 무엇이 다른 줄인지 알 수 없었다. 팀명
아래에 대회명을 작게 한 줄 더 붙였다.

대회 선택은 KAN-597이 디자인과 기본값을 정할 자리다. 웹은 `CompetitionPicker`라는 임시 텍스트 버튼 줄로 자리만
잡아 뒀는데, 모바일도 같은 이름의 같은 역할로 뒀다. 대회가 둘 이상일 때만 선수단 위, 기록 탭 첫 섹션 머리,
선수 숫자 상자 위에 선다.

로딩 자리도 붙였다. 프로필 조회는 전부 외부 축구 데이터를 타서 느릴 수 있는데, 엠블럼이나 선수단 행을 눌렀을
때 그 시간 동안 화면이 멈추면 [ADR 0189](0189-tab-streaming-loading.md)에서 고친 문제가 여기서 다시 생긴다.
두 프로필에 머리 실루엣만 그리는 `loading.tsx`를 뒀다.

## 지운 것

선수단 칩이 열던 `SeasonStatsSheet`와 그 시트만 쓰던 `usePlayerSeasonStats` 훅을 지웠다. 선수단 행이 이제
선수 프로필로 가므로 시트를 여는 곳이 없다. `@plick/core/live`의 `getPlayerSeasonStats`는 공용 패키지라 이번에는
남겼다. 지금은 쓰는 곳이 없다.

웹 선수 프로필 메타데이터에는 "모바일 선수 화면이 아직 없어 alternate를 선언하지 않는다"는 주석과 함께 빠져 있던
모바일 alternate를 이번에 더했다. 모바일 쪽은 canonical이 대응 데스크톱 URL을 가리키니 두 URL이 서로를 가리키는
구글 별도 모바일 URL 규칙이 이제 선수 프로필에서도 맞는다.

## 어떻게 확인했나

mock 프로필(8081)에 붙인 mobile dev 서버를 헤드리스 Chromium으로 열고 탭마다 캡처했다. 앱 셸이
`h-[100dvh]`로 높이를 못박고 안쪽 스크롤 영역만 스크롤하는 구조라 전체 페이지 캡처가 안쪽을 담지 못한다.
뷰포트 높이를 2400으로 길게 잡아 스크롤 영역이 다 펼쳐지게 해서 찍었다. 팀 네 탭, 선수 세 탭, 골키퍼 기록
탭(실점, 클린시트, 골키핑 묶음)을 피그마 모바일 프레임과 나란히 봤고 콘솔 에러는 없었다.

이동은 실제로 눌러 봤다. 맨유 팀 프로필에서 선수단 탭을 열고 선수 행을 누르면 `/players/5001`이 개요 탭으로
열린다. 소속팀 링크를 누르면 `/teams/tottenham/profile`이 개요 탭으로 열린다. 하위 바의 뒤로를 두 번 누르면
선수, 맨유 순서로 돌아온다. 프로필이 스택처럼 쌓였다가 하나씩 빠지는 셈이다.

없는 선수(`/players/abc`, mock이 404를 주는 `/players/999999`)와 없는 팀(`/teams/nope/profile`)은 안내
화면으로 간다. 다만 HTTP 상태는 404가 아니라 200이다. `loading.tsx`가 있으면 Next가 응답을 스트리밍으로
먼저 시작하고, 그 뒤에 `notFound()`가 불리면 이미 보낸 상태 코드를 바꿀 수 없어서다. 대신 Next가
`<meta name="robots" content="noindex">`를 넣어 색인은 막는다. 느린 데이터에서 화면이 멈추는 것보다 이쪽이
낫다고 봤다.

마지막으로 prod BE에 붙여 지금의 502 상태를 그대로 봤다. 팀 화면은 레지스트리 이름과 엠블럼으로 머리가 서고,
숫자 상자는 전부 "-", 관련 이슈는 실제 기사 다섯 건이 뜨고, 최근 경기와 선수단 자리에만 "경기 정보를 불러오지
못했어요"와 다시 시도가 섰다. 선수 화면은 이름을 대신할 데이터가 없어 다시 시도만 보인다.

## 아직 남은 것

실데이터 대조는 API-Football이 재개된 뒤에야 할 수 있다. 지금 화면의 숫자는 mock 값으로만 봤다.

선수 프로필 화면값은 분석에 집계되지 않는다. 화면 전환 이벤트(`screen_viewed`)의 화면값은 BE 허용 목록 열아홉
개만 받는데 거기에 선수 프로필이 없다. 웹 KAN-600 때부터 그렇다. `player_profile`을 허용 목록에 더하는 BE 작업이
먼저 있어야 `@plick/core/screens`에 경로를 올릴 수 있다. 팀 프로필 탭 전환은 기존 `team_profile` 값으로 계속
나간다.

웹은 경기 상세의 라인업, 득점자, 결장자와 기사 인물 태그(`apiPlayerId`가 있을 때)도 선수 프로필로 잇는다.
모바일은 이번에 선수단 행, 팀 내 순위, 부상자, 같은 팀 선수만 이었다. 경기 상세 라인업은 아직 경기 스탯 시트를
연다. 티켓 완료 조건 밖이라 따로 다룬다.
