# 0174. E2E가 한 번도 통과하지 못한 이유는 dev WAF였다 (KAN-573)

## 증상

[ADR 0169](0169-e2e-qa-automation.md)에서 배포된 dev를 바깥에서 타는 E2E를 만들었다. dev 배포가 끝나면 돌고,
매일 아침 9시에도 돈다. 그런데 GitHub Actions의 `E2E` 워크플로우 기록을 열어 보니 도입한 날부터
한 번도 초록불이 들어온 적이 없었다. 9월 21일부터 27일까지 열 번 넘게 돌았고 전부 빨간불이었다.

마지막 실행의 로그를 보면 실패가 이상하게 고르게 퍼져 있었다. 릴스, 기사, 투표 같은 시나리오만 깨진 게 아니라
"홈 첫 화면에 핫이슈와 탭바가 뜬다"처럼 가장 단순한 것까지 `element(s) not found`로 깨졌다.
모바일과 웹 두 프로젝트의 18개 시나리오가 재시도까지 전부 실패했다. 이렇게 전부 깨질 때는 테스트
하나하나를 볼 게 아니라 환경부터 의심해야 한다.

## 원인을 찾은 과정

단서는 테스트 앞 단계인 `Wait for targets`에 있었다. 이 단계는 Blue/Green 전환 직후 이전 인스턴스가 잠깐
응답하는 걸 피하려고 `/api/health`가 200을 줄 때까지 10초 간격으로 최대 12번 기다린다. 로그에 이렇게 찍혀 있었다.

```
https://dev-m.plick.co.kr/api/health -> 403, retry 1
...
https://dev-m.plick.co.kr/api/health -> 403, retry 9
```

403은 "서버가 요청을 이해했지만 거절한다"는 뜻이다. 앱이 떠 있지 않으면 502나 504가 나오고, 경로가 없으면 404가
나온다. 403은 누군가 의도를 갖고 막고 있다는 신호다. 같은 주소를 내 맥에서 curl로 찔러 보니 200이었다.
러너에서는 403이고 내 자리에서는 200이니, 요청 내용이 아니라 요청이 어디서 오느냐로 갈리는 것이다.

응답 헤더에 `via: ... cloudfront.net`이 있어 dev 앞에 CloudFront가 서 있다는 걸 알 수 있었다. CloudFront가
출발지로 요청을 거르는 방법은 두 가지다. 국가 단위로 막는 geo restriction, 그리고 AWS WAF를 붙이는 것이다.
`aws cloudfront list-distributions`로 보니 geo restriction은 전부 `none`이었고, dev 두 배포(`dev.plick.co.kr`,
`dev-m.plick.co.kr`)에만 WAF `plick-dev-lock`이 붙어 있었다. prod 쪽에는 WAF가 없다.

`plick-dev-lock`의 구성은 단순했다.

- 기본 동작(default action)이 Block이다. 어느 규칙에도 걸리지 않은 요청은 막힌다.
- 규칙은 `allow-team-ips` 하나다. IP 세트 `plick-team-ips`에 든 주소만 Allow한다.

dev를 외부에 노출하지 않으려고 팀 IP만 열어 둔 잠금이다. GitHub 호스티드 러너는 매번 다른 Azure 주소에서
뜨니 이 세트에 들어 있을 리가 없다. 러너가 연 브라우저는 앱이 아니라 WAF의 403 페이지를 받았고,
그 페이지에는 핫이슈도 탭바도 없으니 모든 로케이터가 "요소 없음"으로 끝난 것이다.

이게 일주일 동안 가려진 이유도 있었다. `Wait for targets`는 12번 다 실패해도 그냥 다음 단계로 넘어갔다.
재시도 루프가 `break`로 빠져나오기만 하고, 끝까지 200을 못 받았을 때 실패로 끝내는 줄이 없었다.
그래서 "접근 불가"가 "테스트 18개 실패"라는 모습으로 한 단계 뒤에서 드러났고, 실패 요약(`.e2e/failure.md`)도
각 시나리오의 로케이터 이야기만 했다. ADR 0169에서 로컬로 돌릴 때는 내 IP가 팀 세트에 있어 전부 통과했으니,
CI에서만 깨지는 이유를 한동안 테스트 쪽에서 찾게 되는 구조였다.

## 러너를 통과시키는 방법 고르기

선택지는 셋이었다.

첫째, 잡을 시작할 때 러너의 공인 IP를 알아내 `plick-team-ips`에 넣고, 끝날 때 뺀다. 이러려면 E2E 워크플로우에도
AWS 역할(OIDC)을 줘야 한다. 더 큰 문제는 청소다. 잡이 타임아웃이나 취소로 죽으면 `if: always()` 단계도
못 도는 경우가 있어 러너 IP가 세트에 남는다. 그리고 WAF IP 세트 갱신은 lock token을 쓰는 낙관적 잠금이라
배포와 E2E가 겹치면 경합이 난다. 움직이는 부품이 너무 많았다.

둘째, 팀 IP 대신 비밀값으로 통과시키는 WAF 규칙을 하나 더 둔다. 요청에 정해진 비밀 문자열이 있으면 Allow한다.
GitHub Secret에 그 값을 넣고 Playwright가 요청에 실으면 된다. 한 번 설정하면 끝이고 추가 비용도 없다.

셋째, self-hosted 러너를 팀 IP 안에 둔다. 러너 하나를 상시 관리해야 해서 이 규모에는 과했다.

둘째로 갔다. 남은 건 비밀값을 헤더에 실을지 쿠키에 실을지였다.

처음 떠오른 건 Playwright의 `extraHTTPHeaders`로 `x-e2e-bypass` 같은 헤더를 붙이는 것이다. 설정 한 줄이면 된다.
그런데 이 옵션은 페이지가 보내는 모든 요청에 헤더를 붙인다. 우리 화면은 트윗 이미지를 `pbs.twimg.com`에서,
폰트나 스크립트를 다른 호스트에서도 받는다. 그 요청에도 비밀값이 실려 외부 서버 로그에 남는다.
게다가 브라우저는 교차 출처(cross-origin) 요청에 표준이 아닌 헤더가 붙으면 본 요청 전에 `OPTIONS` 사전 요청
(CORS preflight)을 먼저 보낸다. 외부 호스트가 그 헤더를 허용한다고 답하지 않으면 본 요청이 막혀, 트윗 이미지가
안 뜨는 식으로 테스트가 엉뚱하게 흔들릴 수 있다.

쿠키는 이 문제가 없다. 쿠키는 브라우저가 도메인 속성을 보고 그 도메인으로 가는 요청에만 붙인다.
도메인을 `.plick.co.kr`로 주면 `dev-m.plick.co.kr`과 `dev.plick.co.kr`에는 실리고 `pbs.twimg.com`에는
실리지 않는다. 쿠키는 이미 모든 요청이 들고 다니는 `Cookie` 헤더에 들어가니 preflight도 생기지 않는다.
그래서 쿠키 이름을 `plick_e2e`로 정했다.

WAF 쪽 규칙은 콘솔에서 직접 만들었다. `plick-dev-lock`에 `allow-e2e-cookie` 규칙을 추가하고, 검사 대상을
`cookie` 헤더 하나로, 일치 방식을 "문자열 포함(Contains string)"으로, 찾을 문자열을 `plick_e2e=<토큰>`으로 두었다.
토큰은 `openssl rand -hex 32`로 만든 64자 값이다. 같은 값을 GitHub Secret `E2E_BYPASS_TOKEN`에 넣었다.
규칙 모양은 AWS CLI로 다시 확인했다. API는 SearchString을 base64로 돌려주는데 길이가 100이었다.
`plick_e2e=` 10바이트와 토큰 64바이트를 더한 74바이트를 base64로 인코딩하면 100자가 나오니 맞게 들어간 것이다.
비밀값 자체는 채팅이나 로그에 찍지 않았다.

## 코드에서 바꾼 것

Playwright 쪽은 `playwright.config.ts`의 `use.storageState`에 쿠키를 넣었다. `storageState`는 원래 로그인 상태를
파일로 저장했다가 새 브라우저 컨텍스트에 되살릴 때 쓰는 옵션인데, 파일 경로 대신 `{ cookies, origins }` 객체를
바로 줄 수도 있다. 모든 테스트는 새 컨텍스트에서 시작하니, 여기 넣은 쿠키는 첫 요청부터 실린다.
spec이나 fixture를 건드릴 필요가 없었다.

쿠키는 `E2E_TARGET`이 dev이고 `E2E_BYPASS_TOKEN`이 있을 때만 넣는다. 팀 IP에서 로컬로 돌릴 때는 토큰이 없어도
통과하니 아무것도 싣지 않고, prod는 WAF가 없으니 실을 이유가 없다. `httpOnly`와 `secure`도 켰다.
페이지의 스크립트가 읽을 일이 없고, https로만 보내면 된다.

워크플로우 쪽은 두 가지다.

- 잡 env에 `E2E_BYPASS_TOKEN: ${{ secrets.E2E_BYPASS_TOKEN }}`을 넣었다. GitHub는 로그에 시크릿 값이 나오면
  `***`로 가린다.
- `Wait for targets`를 엄격하게 바꿨다. health 요청에도 같은 쿠키를 싣고, 12번 안에 200을 못 받으면
  `::error::`로 마지막 상태 코드를 남기고 바로 실패한다. dev인데 시크릿이 비어 있으면 기다리기 전에 먼저 멈춘다.
  다음에 WAF 규칙이나 시크릿이 어긋나면 "테스트 18개 실패"가 아니라 "health가 403"으로 곧장 보이게 하려는 것이다.

## 문을 열자 드러난 진짜 테스트 실패 6개

차단을 풀고 나서 제 맥에서(팀 IP라 WAF를 통과한다) dev 상대로 전체를 돌렸다. 12개는 통과했고 6개가 깨졌다.
이번엔 환경이 아니라 테스트가 화면과 어긋난 것이다. 일주일 사이에 해축이모 리디자인([ADR 0171](0171-haechukimo-redesign.md))과
KAN-569 UI 수정([ADR 0172](0172-kan-569-ui-fixes.md))이 들어갔는데, WAF에 가려 E2E가 그 변화를 한 번도 보지 못했다.
`tests/e2e/tools/explore.mjs`로 실제 dev 화면의 접근성 트리를 떠서 하나씩 맞췄다.

- 모바일 기사 상세의 h1이 둘이 됐다. 헤더에 "맨유 이슈" 같은 h1이 생겨 `getByRole('heading', { level: 1 })`이
  두 요소에 걸렸다. Playwright 로케이터는 기본이 strict 모드라, 하나를 기대한 동작에서 둘 이상이 잡히면
  고르지 않고 실패한다. `main` 안의 h1으로 좁혔다. 팀 프로필 시나리오가 이미 같은 이유로 `main`을 쓰고 있었다.
- 기사 상세의 해시태그가 "#맨체스터 유나이티드"와 "#마이클 캐릭" 둘이 됐다. 원래 주석은 "인물 태그는 #이 없다"였는데
  이제 인물도 #을 단다. 이름으로는 구분이 안 돼 `href`가 `/teams/`로 시작하는 링크만 `and()`로 골랐다.
- 투표 목록은 dev에 진행 중인 투표가 하나도 없어 "진행 중인 투표가 없어요"만 떠 있었다. 데이터 사정이라
  언제든 다시 비어질 수 있다. 늘 카드가 있는 마감 탭을 보게 했다. 모바일은 `/debates?tab=closed` 링크로,
  웹은 `tablist`의 "마감" 탭을 눌러 간다.
- 웹 투표 목록은 옆에 "실시간 급상승" 목록도 `list`라 `main`의 `listitem` 첫 번째가 급상승 1위(`/stories/96`)였다.
  그래서 기사 대신 스토리로 가 URL 검사가 깨졌다. `region "투표"`를 품은 항목만 카드로 골랐다.
- 웹 홈 첫 기사 시나리오는 "h3를 품은 링크"를 찾았는데, 리디자인 뒤에는 표 행이 링크 안의 h3가 아니라 h3 안의 링크다.
  45초 타임아웃으로 끝났다. `h3 > link` 순서로 뒤집었다. 위 핫이슈 카드의 h3는 링크를 품지 않아 첫 매치가 표 첫 행이 된다.
- MY 탭의 계정 연동 링크 이름이 "계정을 연동…"에서 "계정 연동"으로 바뀌었다. 게스트도 이제 익명 계정이
  자동으로 붙어 닉네임이 보인다.

고친 뒤 전체가 18개 통과했다.

## 바꾸고 나서

전에는 E2E가 도입부터 매번 18개 전부 실패했고, 그 실패는 앱이나 테스트에 대해 아무 정보도 주지 못했다.
이제 러너가 쿠키로 WAF를 통과하고, 로컬(dev 대상) 기준 18개 전부 통과한다. WAF가 다시 막으면
`Wait for targets`가 첫 단계에서 403을 찍고 멈춘다.

돌아보면 교훈은 두 가지다. 대기 단계가 조용히 넘어가게 둔 탓에 환경 문제가 테스트 문제로 둔갑했다.
그리고 E2E를 로컬에서만 초록으로 확인하고 CI의 첫 실행을 끝까지 보지 않았다. 로컬과 CI는 네트워크 위치가 다르다는 걸
배포 대상 E2E에서는 먼저 확인해야 했다.

남은 것은 CI에서 실제로 초록이 나오는지다. 이 브랜치가 develop에 들어가 dev 배포가 끝나면 `E2E`가 돌고,
그 결과로 쿠키 통과가 최종 확인된다.
