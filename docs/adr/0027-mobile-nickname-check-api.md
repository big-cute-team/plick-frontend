# ADR 0027 — 모바일 닉네임 중복확인 GET 연결 (KAN-269)

- **날짜:** 2026-07-21
- **범위:** `apps/mobile` — `GET /api/v1/users/nickname-check`를 프로필 수정 화면(`/me/edit`)의 "중복확인" 버튼에 연결. 지금까지 클릭해도 아무 일 없던 껍데기 버튼이 실제로 닉네임 사용 가능 여부를 물어보게 됐다.
- **관련:** [ADR 0026 프로필 수정 PATCH](0026-mobile-users-me-patch-api.md) · [ADR 0025 내 프로필 조회](0025-mobile-users-me-api.md) · `api-integration` 스킬

## 무엇을 했나

KAN-268에서 프로필 수정 화면에 "닉네임 변경" 인풋 + 중복확인 버튼을 껍데기로만 그려뒀다. 그때 컴포넌트 주석에 "중복확인·저장은 BE 연동 티켓에서 채운다"고 적어둔 그 티켓이 이번이다. 입력값만 로컬로 들고 있던 버튼을 `GET /api/v1/users/nickname-check`에 이어, 누르면 초록 체크로 "사용할 수 있는 닉네임이에요" 또는 빨간 X로 "이미 사용 중이거나 쓸 수 없는 닉네임이에요"가 뜨게 했다.

여기서 딱 잘라둔 게 있다. 이 티켓은 **중복확인까지만**이다. 실제 닉네임 변경(값을 DB에 쓰는 `PATCH`)은 7일 제한 때문에 409를 다뤄야 하는 별개 몫이라 손대지 않았다 — 버튼을 눌러 확인은 되지만 아직 저장은 안 된다. 껍데기를 반만 채운 셈이고, 그게 티켓 경계다.

## 스웨거 — 이번엔 단순했다

응답이 `{ available: boolean }` 하나뿐이라 대조랄 게 없었다. 다만 스웨거 설명 한 줄이 중요했다: "익명 허용. 이미 사용 중이거나 금지어면 `available=false`." 두 가지다.

하나는 **익명 허용** — 이 엔드포인트는 토큰이 필요 없는 공개 API다. 지금까지 붙인 `/users/me`·onboarding·PATCH는 전부 보호 API라 access 쿠키를 Bearer로 실어 보냈는데, 이건 그럴 필요가 없다. 그래서 fetcher에서 Authorization 헤더를 아예 안 붙인다.

다른 하나는 **중복과 금지어를 응답이 구분하지 않는다**는 점. 둘 다 `available=false`로 온다. 그래서 화면 문구도 억지로 나누지 않고 "이미 사용 중이거나 쓸 수 없는 닉네임이에요" 하나로 묶었다. BE가 안 알려주는 걸 FE가 지어내지 않는 게 맞다.

로컬에 실제로 때려보니 문서대로였다. `김도완`(DB에 있는 닉네임)은 `available:false`, `freenick999`는 `available:true`. 값이 잘 갈린다.

## 읽기인데 왜 서버 액션인가

이게 이번에 제일 고민한 지점이다. 스킬 표는 "단발 읽기 = 서버 컴포넌트 fetch, 뮤테이션 = TanStack Query"로 가른다. 그런데 닉네임 중복확인은 **읽기지만 버튼 클릭으로 클라이언트가 부르는** 읽기라, 서버 컴포넌트 렌더 시점에 알 수 없다. 그렇다고 페이지네이션도 뮤테이션도 아니라 RQ 트리거도 안 선다. 표의 두 칸 어디에도 딱 안 맞는다.

선택지는 둘이었다. **(1) 클라에서 직접 fetch** — 그러면 브라우저가 `localhost:3001`에서 `localhost:8080`을 때리는 cross-origin이 처음 생기고, CORS를 없애려 `/be` 프록시 rewrite를 깔아야 한다(data-layer §1). 아직 클라 fetch가 하나도 없는 단계인데 이 한 버튼 때문에 그 인프라를 들이는 건 과하다. **(2) 서버 액션**(`"use server"`) — 클라 버튼은 Next 서버로 폼을 POST하고, 실제 BE GET은 서버에서 돈다. 서버→서버라 CORS가 없고, `apiFetch`의 서버 전용 base(절대 URL)를 그대로 쓴다. `submitOnboarding`·`updateMyTeams`가 이미 이 패턴이라 관용에도 맞는다.

(2)로 갔다. 읽기를 서버 액션에 태우는 게 살짝 어색하긴 하다 — 서버 액션은 내부적으로 POST고 순차 실행이라 원래 뮤테이션용이다. 하지만 사용자가 버튼을 눌러 한 번 확인하는 동작이라 순차·비캐시가 오히려 맞고, RQ 프로바이더도 프록시도 없이 기존 조각만으로 끝난다. 조기 추상화를 피한다는 스킬 원칙과 같은 방향이다. 클라 연속 fetch나 뮤테이션이 진짜 필요해지는 첫 엔드포인트에서 그때 프록시+RQ를 깔면 된다. 그래서 `checkNickname`도 `submitOnboarding`이 사는 `_lib/api/users.ts`에 나란히 뒀다(공개 API지만 유저 도메인이라 자리가 맞는다).

브라우저 네트워크 탭엔 `localhost:8080`으로 가는 GET이 안 보인다는 점만 검증 때 착각하지 않으면 된다 — 그건 서버에서 돌기 때문이다(ADR 0026에서 PATCH도 같은 이유로 안 보였다).

## 결과 상태를 입력이 바뀌면 지운다

작은 UX 디테일 하나. 중복확인을 눌러 "사용 가능"이 떴는데 사용자가 인풋을 더 고치면, 그 초록 체크는 이제 방금 값이 아니라 거짓말이 된다. 그래서 `onChange`에서 직전 결과를 `null`로 지운다 — 확인 결과는 "마지막으로 확인한 그 문자열"에만 붙어 있어야 한다. 버튼은 입력이 비었거나 확인 중이면 비활성(`disabled:opacity-40`)이고, 확인 중엔 텍스트가 "확인 중…"으로 바뀐다(`useTransition`).

"사용 가능" 초록 체크는 온보딩 닉네임 필드(`NicknameField`)가 이미 쓰던 `CheckIcon` + `text-accent` 표현을 그대로 맞췄고, "쓸 수 없음"은 `CloseIcon` + `text-danger`로 뒀다. 색·아이콘 다 토큰·공용 아이콘이라 하드코딩 없다.

## 공용화는 아직

web은 프로필 수정 화면 자체가 없어서 이 엔드포인트를 안 쓴다. 그러니 `checkNickname`은 mobile 앱 로컬에 둔다(스킬 §3 게이트 C — 두 번째 실사용처가 없다). 다만 같은 앱 안에 후보가 하나 있다: 온보딩 1단계 `NicknameField`도 지금은 "비어있지 않으면 사용 가능"이라는 목 동작이라, 나중에 실 중복확인으로 바꾸면 이 `checkNickname`을 재사용하게 된다. 그건 UX(버튼 클릭 vs 입력 중 라이브 표시)가 달라 이번 티켓 범위 밖이라 안 건드렸고, 후보로만 남긴다.

## 검증

BE `localhost:8080` 띄운 채 mobile dev(:3001)에서 실제로 밟았다. `/me/edit`는 로그인 게이트라, 공유 DB의 기존 유저(id 15, 온보딩 완료)에 대해 JWT를 민팅해 쿠키로 심고 들어갔다(테스트 유저를 새로 만들지 않았고, 이 엔드포인트는 읽기라 DB에 아무것도 안 썼다). 자유 닉네임 → 초록 체크, DB에 있는 `김도완` → 빨간 X, 콘솔 에러 없음까지 확인했다. 입력을 고치면 결과가 사라지는 것도 봤다. `check-types`·`lint` 통과.

## 후속 — 실제 닉네임 변경까지 (같은 세션)

"중복확인까지만"으로 잘라뒀던 경계를 같은 세션에서 마저 채우게 됐다. 요구는 둘: **저장이 실제로 닉네임을 바꾸고**, **입력이 비어 있으면 기존 닉네임을 자동으로 실어 보내라**. 거기에 BE가 `GET /users/me`에 `nicknameChangeableAt`(닉네임을 다시 바꿀 수 있는 시각, KST)을 새로 실어주기 시작해서 — **아직 못 바꾸는 시점이면 빨간 글씨로 안내하고 인풋을 잠그는 것**까지.

### "빈 값이면 기존 닉네임 재전송"이 안전한 이유

이게 이번의 핵심 확인이었다. 매 저장마다 닉네임을 보내면 7일 제한(409)에 걸리는 것 아닌가? BE 소스를 열어보니 `changeNickname`이 **지금과 같은 값이면 변경으로 치지 않고 그냥 리턴**한다 — 쿨다운 검사보다 먼저다. 즉 기존 닉네임을 되보내는 건 언제나 무해한 no-op이고, 7일 기산도 안 움직인다. curl로도 확인했다: 쿨다운에 걸린 유저가 같은 닉네임을 PATCH하면 200, 다른 닉네임이면 409. 그래서 폼은 `입력값.trim() || 기존닉네임`을 항상 싣는다. 이 확인이 없었으면 "빈 값이면 nickname 항목을 아예 빼는" 조건 분기를 짰을 텐데, BE가 멱등하게 받아주니 FE 분기가 하나 사라졌다.

### 구조 — 닉네임 상태를 폼으로 올렸다

지금까지 `NicknameEditField`는 페이지에 따로 서서 입력값을 저 혼자 들고 있었다(중복확인만 하니까). 저장이 닉네임을 실어야 하니 값이 "변경사항 저장" 버튼까지 닿아야 한다 → 상태를 `ProfileEditForm`으로 올리고 필드는 제어형으로 바꿨다. 온보딩의 `NicknameField`가 같은 이유로 제어형인 것과 같은 패턴이다. 서버 액션은 `updateMyTeams` → `updateMyProfile(nickname, teams)`로 이름을 바꾸고 body에 `nickname`을 추가했다. 에러는 온보딩 때처럼 BE 코드(쿨다운·중복·금지어)를 잡아 BE의 한국어 문구를 그대로 보여준다.

### 잠금 판정 — null 여부가 아니라 현재 시각과 비교

처음엔 `nicknameChangeableAt`이 null이면 가능, 값이 있으면 잠금으로 짰다. 그런데 피드백을 받고 보니 이 판정은 BE의 "지난 시각은 null로 돌려준다"는 구현 디테일에 기대는 데다, 그게 맞더라도 **조회 순간**의 답일 뿐이다 — 화면을 열어둔 채 시각이 지나면 FE는 계속 잠겨 있게 된다. 그래서 클라이언트에서 `Date.parse(changeableAt)`를 **현재 시각과 비교**해 잠금을 판정하도록 바꿨다. 덤으로 잠긴 동안 경계 시각까지 `setTimeout`을 하나 걸어, 그 순간 다시 렌더해 **리로드 없이 자동으로 풀리게** 했다(7일 잔여도 최대 6.05억 ms라 setTimeout 32비트 한계 안). 검증은 `nickname_changed_at`을 "7일 전 + 80초"로 심은 일회용 유저로 — 진입 시 잠김·빨간 안내가 뜨고, 경계가 지나자 같은 화면에서 안내가 사라지며 인풋이 풀리는 걸 눈으로 봤다.

7일 계산 자체는 여전히 서버 몫이고(FE는 받은 시각과 지금을 비교만), 잠기면 인풋·중복확인 버튼을 disabled + 흐리게 하고 `text-danger`로 "7월 28일 16:49까지는 닉네임을 바꿀 수 없어요"를 띄운다. 포맷은 `Intl.DateTimeFormat`에 타임존을 `Asia/Seoul`로 고정해 기기 시간대와 무관하게 KST로 보여준다(`me/edit/_lib/utils.ts`). 잠금 중에도 팀 저장은 돼야 하는데, 인풋이 잠겨 빈 값 → 기존 닉네임 재전송 → no-op이라 자연히 통과한다 — 위 확인 덕에 잠금·저장이 서로 안 얽힌다.

### UI 다듬기 — 닉네임 위치·카메라 배지·에러 팝업 (같은 세션 후속)

사용자 피드백으로 화면을 세 군데 고쳤다. 먼저 기존 닉네임을 정보 카드 행에서 빼서 **아바타 바로 밑에 조금 큰 글자**(`text-body-lg`)로 옮겼다 — 카드는 이메일 전용이 되어 이메일이 없으면(카카오 가입) 카드 자체가 사라진다. 다음으로 아바타의 **카메라 배지를 뺐다**. `AvatarField`는 `@plick/ui` 공용이라 web도 같이 바뀌는데, 배지는 애초에 업로드 기능 없이 "표시만"이던 장식이라 양쪽에서 함께 빼는 게 맞다고 봤다(업로드가 생기면 그때 다시 붙인다). 공용을 건드렸으니 web·mobile 클린 빌드로 회귀를 확인했다.

마지막으로 저장 거절(중복·7일 제한)을 **버튼 밑 빨간 글자 대신 중앙 팝업**으로 바꿨다. 마이페이지 로그아웃 확인 팝업(`LogoutButton`)이 이미 스크림(`--plk-scrim` color-mix) + 중앙 카드 관용을 깔아놔서 그대로 따라 `ErrorDialog`를 만들었다 — 제목 "저장할 수 없어요" 밑에 BE의 한국어 문구를 그대로 싣고 "확인"으로 닫는다. `role="alertdialog"`로 두고 스크림 탭으로도 닫히게 했다. 중복확인 버튼의 인라인 초록/빨강 표시는 "입력 중 피드백"이라 그대로 두고, 잠금 상태의 빨간 안내도 팝업이 아니라 상시 안내라 그대로다 — 팝업은 "저장을 눌렀는데 거절당한 순간"에만 쓴다.

검증에서 재미있던 건 7일 제한 팝업 재현이다. 잠금 상태에선 인풋이 막혀 있어 정상 경로로는 쿨다운 409를 만날 수 없다 — 이 팝업이 뜨는 건 **화면을 열어둔 사이 다른 데서 닉네임이 바뀐 경합**뿐이다. 그래서 일회용 유저로 화면을 열어두고, 뒤에서 curl로 닉네임을 바꿔 쿨다운을 건 다음, 열려 있던 화면에서 다른 닉네임으로 저장을 눌렀다 → 쿨다운 팝업이 정확히 떴다. 중복 팝업은 실존 닉네임으로 저장해 확인했다.

### 온보딩에도 같은 UX — 그리고 첫 앱 내 공용화 (같은 세션 후속)

프로필 수정에 만든 것들을 온보딩에도 똑같이 깔아달라는 요구가 왔다: 1단계에 중복확인 버튼, 제출("시작하기") 거절도 팝업으로, 덤으로 하단 버튼 위에 "다음에 할게요"(누르면 홈) 링크까지.

이 시점에 처음으로 **같은 앱 안에서 두 번째 사용처**가 생겼다. 위에서 "온보딩 `NicknameField`의 목 검증을 실 확인으로 바꿀 때 재사용하게 된다"고 후보로 적어둔 그 일이 실제가 된 것. 그래서 스킬 §3의 "두 번째 쓰임에서 공용" 규칙대로 세 조각을 앱 공용으로 올렸다 — 중복확인 상태 기계는 `_lib/useNicknameCheck.ts`(훅 파일 하나 = 훅 하나), 결과 한 줄(초록 체크/빨간 X/조회 실패)은 `_components/NicknameCheckNotice.tsx`, 그리고 `ErrorDialog`는 `me/edit/_components`에서 `app/_components`로 이동(2개 화면 공용 → app/\_components 규칙). 두 닉네임 필드는 이제 같은 훅·표시줄을 쓰고 시각(온보딩 accent 보더 vs 수정 화면 일반 보더)만 각자 가진다 — 표현은 화면별, 로직은 공용.

온보딩 1단계의 "비어있지 않으면 사용 가능"이던 목 표시는 이걸로 사라졌다. 재미있는 부작용: BE 자동 닉네임(plick+숫자)은 금지어 "plick"을 포함해서, 온보딩 초깃값을 그대로 중복확인하면 빨간 X가 뜬다 — BE가 "사용자가 plick 사칭 닉네임을 못 만들게" 일부러 막은 것이고, 자동 닉네임 자체는 시스템 생성이라 유효하다. 사용자가 그대로 제출하면 BE는 "자동 닉네임을 안 바꿨으면 검사 생략" 규칙이라 통과한다. 확인 버튼과 저장 검사의 기준이 이 한 지점에서 어긋나는 셈인데, FE가 지어낼 수 없는 서버 정책이라 그대로 뒀다.

"다음에 할게요"는 두 단계 공용이라 `onboarding/_components/SkipLink.tsx`로. 가입 때 BE가 자동 닉네임을 주니 온보딩을 건너뛰어도 깨진 상태가 아니고, 온보딩 진입은 로그인 직후 한 번뿐이라(미들웨어 강제 없음) 그냥 홈으로 보내면 끝이다.

검증은 온보딩이 필요한 일회용 유저로: 1단계에서 자동 닉네임 그대로 중복확인 → 빨간 X(금지어), 자유 닉네임 → 초록 체크, `김도완`으로 2단계 진행 후 시작하기 → 중앙 팝업("이미 사용 중인 닉네임입니다. 이전 단계에서 닉네임을 바꿔주세요."), "다음에 할게요" → 홈. 제출이 거절된 유저라 DB 변경 없이 삭제했다.

### 검증 — 이번엔 일회용 유저로

이번엔 실제 쓰기가 있어서 기존 유저를 못 쓴다(닉네임을 바꾸면 그 계정이 7일 잠긴다). 메모해둔 절차대로 일회용 테스트 유저를 insert하고 JWT를 민팅해 네 시나리오를 밟았다: ① 빈 입력 + 팀만 저장 → 성공, DB의 `nickname_changed_at`이 **여전히 null**(재전송이 no-op이라는 증거). ② 새 닉네임 저장 → 실제 변경, MY에 새 닉네임. ③ 재진입 → 인풋 잠김 + 빨간 안내(위 문구 그대로). ④ 잠긴 채 팀만 저장 → 409 없이 성공. 끝나고 테스트 유저는 팀 행까지 지웠다. `check-types`·`lint`·`format:check` 통과.
