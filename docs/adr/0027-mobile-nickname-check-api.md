# ADR 0027 — 모바일 닉네임 중복확인 GET 연결 (KAN-269)

- **날짜:** 2026-07-21
- **범위:** `apps/mobile` — `GET /api/v1/users/nickname-check`를 프로필 수정 화면(`/me/edit`)의 "중복확인" 버튼에 연결. 지금까지 클릭해도 아무 일 없던 껍데기 버튼이 실제로 닉네임 사용 가능 여부를 물어보게 됐다.
- **관련:** [ADR 0026 프로필 수정 PATCH](0026-mobile-users-me-patch-api.md) · [ADR 0025 내 프로필 조회](0025-mobile-users-me-api.md) · `api-integration` 스킬

## 무엇을 했나

KAN-268에서 프로필 수정 화면에 "닉네임 변경" 인풋 + 중복확인 버튼을 껍데기로만 그려뒀다. 그때 컴포넌트 주석에 "중복확인·저장은 BE 연동 티켓에서 채운다"고 적어둔 그 티켓이 이번이다. 입력값만 로컬로 들고 있던 버튼을 `GET /api/v1/users/nickname-check`에 이어, 누르면 초록 체크로 "사용할 수 있는 닉네임이에요" 또는 빨간 X로 "이미 사용 중이거나 쓸 수 없는 닉네임이에요"가 뜨게 했다.

여기서 딱 잘라둔 게 있다. 이 티켓은 **중복확인까지만**이다. 실제 닉네임 변경(값을 DB에 쓰는 `PATCH`)은 7일 제한 때문에 409를 다뤄야 하는 별개 몫이라 손대지 않았다 — 버튼을 눌러 확인은 되지만 아직 저장은 안 된다. 껍데기를 반만 채운 셈이고, 그게 티켓 경계다.

## 스웨거 — 이번엔 단순했다

응답이 `{ available: boolean }` 하나뿐이라 대조랄 게 없었다. 다만 스웨거 설명 한 줄이 중요했다: "익명 허용. 이미 사용 중이거나 금지어면 `available=false`." 두 가지다.

하나는 **익명 허용** — 이 엔드포인트는 토큰이 필요 없는 공개 API다. 지금까지 붙인 `/users/me`·onboarding·PATCH는 전부 보호 API라 access 쿠키를 Bearer로 실어 보냈는데, 이건 그럴 필요가 없다. 그래서 fetcher에서 Authorization 헤더를 아예 안 붙인다.

다른 하나는 **중복과 금지어를 응답이 구분하지 않는다**는 점. 둘 다 `available=false`로 온다. 그래서 화면 문구도 억지로 나누지 않고 "이미 사용 중이거나 쓸 수 없는 닉네임이에요" 하나로 묶었다. BE가 안 알려주는 걸 FE가 지어내지 않는 게 맞다.

로컬에 실제로 때려보니 문서대로였다. `김도완`(DB에 있는 닉네임)은 `available:false`, `freenick999`는 `available:true`. 값이 잘 갈린다.

## 읽기인데 왜 서버 액션인가

이게 이번에 제일 고민한 지점이다. 스킬 표는 "단발 읽기 = 서버 컴포넌트 fetch, 뮤테이션 = TanStack Query"로 가른다. 그런데 닉네임 중복확인은 **읽기지만 버튼 클릭으로 클라이언트가 부르는** 읽기라, 서버 컴포넌트 렌더 시점에 알 수 없다. 그렇다고 페이지네이션도 뮤테이션도 아니라 RQ 트리거도 안 선다. 표의 두 칸 어디에도 딱 안 맞는다.

선택지는 둘이었다. **(1) 클라에서 직접 fetch** — 그러면 브라우저가 `localhost:3001`에서 `localhost:8080`을 때리는 cross-origin이 처음 생기고, CORS를 없애려 `/be` 프록시 rewrite를 깔아야 한다(data-layer §1). 아직 클라 fetch가 하나도 없는 단계인데 이 한 버튼 때문에 그 인프라를 들이는 건 과하다. **(2) 서버 액션**(`"use server"`) — 클라 버튼은 Next 서버로 폼을 POST하고, 실제 BE GET은 서버에서 돈다. 서버→서버라 CORS가 없고, `apiFetch`의 서버 전용 base(절대 URL)를 그대로 쓴다. `submitOnboarding`·`updateMyTeams`가 이미 이 패턴이라 관용에도 맞는다.

(2)로 갔다. 읽기를 서버 액션에 태우는 게 살짝 어색하긴 하다 — 서버 액션은 내부적으로 POST고 순차 실행이라 원래 뮤테이션용이다. 하지만 사용자가 버튼을 눌러 한 번 확인하는 동작이라 순차·비캐시가 오히려 맞고, RQ 프로바이더도 프록시도 없이 기존 조각만으로 끝난다. 조기 추상화를 피한다는 스킬 원칙과 같은 방향이다. 클라 연속 fetch나 뮤테이션이 진짜 필요해지는 첫 엔드포인트에서 그때 프록시+RQ를 깔면 된다. 그래서 `checkNickname`도 `submitOnboarding`이 사는 `_lib/api/users.ts`에 나란히 뒀다(공개 API지만 유저 도메인이라 자리가 맞는다).

브라우저 네트워크 탭엔 `localhost:8080`으로 가는 GET이 안 보인다는 점만 검증 때 착각하지 않으면 된다 — 그건 서버에서 돌기 때문이다(ADR 0026에서 PATCH도 같은 이유로 안 보였다).

## 결과 상태를 입력이 바뀌면 지운다

작은 UX 디테일 하나. 중복확인을 눌러 "사용 가능"이 떴는데 사용자가 인풋을 더 고치면, 그 초록 체크는 이제 방금 값이 아니라 거짓말이 된다. 그래서 `onChange`에서 직전 결과를 `null`로 지운다 — 확인 결과는 "마지막으로 확인한 그 문자열"에만 붙어 있어야 한다. 버튼은 입력이 비었거나 확인 중이면 비활성(`disabled:opacity-40`)이고, 확인 중엔 텍스트가 "확인 중…"으로 바뀐다(`useTransition`).

"사용 가능" 초록 체크는 온보딩 닉네임 필드(`NicknameField`)가 이미 쓰던 `CheckIcon` + `text-accent` 표현을 그대로 맞췄고, "쓸 수 없음"은 `CloseIcon` + `text-danger`로 뒀다. 색·아이콘 다 토큰·공용 아이콘이라 하드코딩 없다.

## 공용화는 아직

web은 프로필 수정 화면 자체가 없어서 이 엔드포인트를 안 쓴다. 그러니 `checkNickname`은 mobile 앱 로컬에 둔다(스킬 §3 게이트 C — 두 번째 실사용처가 없다). 다만 같은 앱 안에 후보가 하나 있다: 온보딩 1단계 `NicknameField`도 지금은 "비어있지 않으면 사용 가능"이라는 목 동작이라, 나중에 실 중복확인으로 바꾸면 이 `checkNickname`을 재사용하게 된다. 그건 UX(버튼 클릭 vs 입력 중 라이브 표시)가 달라 이번 티켓 범위 밖이라 안 건드렸고, 후보로만 남긴다.

## 검증

BE `localhost:8080` 띄운 채 mobile dev(:3001)에서 실제로 밟았다. `/me/edit`는 로그인 게이트라, 공유 DB의 기존 유저(id 15, 온보딩 완료)에 대해 JWT를 민팅해 쿠키로 심고 들어갔다(테스트 유저를 새로 만들지 않았고, 이 엔드포인트는 읽기라 DB에 아무것도 안 썼다). 자유 닉네임 → 초록 체크, DB에 있는 `김도완` → 빨간 X, 콘솔 에러 없음까지 확인했다. 입력을 고치면 결과가 사라지는 것도 봤다. `check-types`·`lint` 통과.
