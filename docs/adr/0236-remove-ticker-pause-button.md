# 0236. 홈 실검·경기 띠의 멈춤 버튼을 뺐다 (KAN-707)

## 티켓

KAN-707은 한 줄짜리 요청이었다. 홈 상단 실검과 자동으로 넘어가는 상자들에 붙어 있는 멈춤·재생 버튼을 없애고,
그냥 항상 애니메이션이 돌게 해 달라는 것이다.

"자동으로 넘어가는 박스들"이 어디까지인지부터 확인했다. 홈에서 시간이 지나면 저절로 내용이 바뀌는 건 세 군데였다.
실검 띠(`HomeTrendTicker`), 오늘 경기·LIVE 띠(`HomeLiveTicker`), 그리고 VS 카드 안의 마감 카운트다운(`ParticipationStatus`).
앞의 둘은 `@plick/ui`의 `RotatingLine` 하나를 공유하고, 웹과 모바일이 같은 컴포넌트를 쓴다. 카운트다운은 1분마다
남은 시간을 다시 계산하는 시계라서 멈춤 버튼 같은 게 없고 이번 티켓과 무관했다. 결국 손댈 곳은 `RotatingLine` 한 파일이었다.

## 전에는 어땠나

`RotatingLine`은 KAN-703 홈 개편([ADR 0233](0233-vs-hub-and-prediction-fixes.md))에서 만든 공용 컴포넌트다. 실검은 4.5초,
경기는 5.5초 간격으로 한 항목씩 아래로 밀어 넘기고, 오른쪽 끝에 버튼 두 개를 뒀다. `N/M` 카운터를 누르면 다음 항목으로
넘어가고, 그 옆의 `멈춤`을 누르면 자동 전환이 서고 글자가 `재생`으로 바뀌었다. `aria-pressed`로 눌린 상태를 알렸다.

멈춤 버튼은 접근성 가이드(WCAG 2.2.2, 5초 넘게 저절로 움직이는 콘텐츠에는 멈출 수단을 둔다)를 따라 넣었던 것이다.
그런데 실제로 화면에 올려 보니 모바일 폭 좁은 띠에 `3/10 멈춤` 같은 글자 버튼이 붙어 있는 게 눈에 거슬렸고, 사용자 입장에서
그걸 눌러 실검을 세워 둘 이유가 거의 없다는 피드백이 왔다. 그래서 티켓이 생겼다.

## 어떻게 바꿨나

`paused` 상태와 그 토글 버튼을 지웠다. 효과(effect)의 의존성 배열에서도 `paused`를 빼서 자동 전환이 서는 조건은
세 가지만 남았다.

- 항목이 하나뿐이면 돌릴 게 없으니 타이머를 안 건다
- 화면 밖(IntersectionObserver)이거나 탭이 숨겨졌거나(`document.hidden`) 움직임 줄이기 설정(`prefers-reduced-motion`)이면 틱을 건너뛴다
- 마우스를 올려 두거나 안쪽 링크에 키보드 포커스가 있는 동안은 타이머 자체를 걷는다

세 번째는 남겨 두기로 했다. 티켓은 "항상 애니메이션"이라고 했지만, 호버 중에도 넘어가면 누르려던 링크가 손가락
밑에서 달아난다. 그건 멈춤 버튼처럼 눈에 보이는 제어가 아니라 손을 떼면 바로 다시 도는 잠깐의 정지라서 취지와
어긋나지 않는다고 봤다. 모바일에는 호버가 없으니 사실상 영향이 없고, 데스크톱 웹에서만 마우스를 올린 동안 선다.
움직임 줄이기 설정도 그대로 둔다. 그건 사용자가 OS에서 이미 내린 결정이고, 멈춤 버튼이 없어진 상태에서 자동 전환을
끌 유일한 길이라 접근성 측면의 최소 장치로 남긴다.

버튼이 하나로 줄어들자 둘을 감싸던 `div`가 필요 없어져 `N/M` 버튼이 바로 띠의 자식이 됐다. 글자 크기와 색 클래스
(`text-caption text-text-3`)는 감싸던 쪽에서 버튼으로 옮겼다. 접근성 라벨 `실검 다음 항목, 3/10`은 그대로다.
JSDoc은 "사용자가 직접 멈추는 버튼은 두지 않는다"고 고쳐 적어 다음에 누가 다시 넣으려 할 때 티켓을 찾아가게 했다.

## 검증

`pnpm check-types`, `@plick/ui` 린트, 단위 테스트 286개가 통과했다. E2E 시나리오에 멈춤 버튼을 집는 로케이터는 없었다
(`tests/e2e`를 `멈춤`·`자동 넘김`·`aria-pressed`로 뒤졌다).

화면 확인은 한 번 막혔다. 사용자가 띄워 둔 모바일 dev 서버(:3031)가 Next 16의 dev 잠금을 잡고 있어 새 dev 서버가
"Another next dev server is already running"으로 바로 죽었고, 그 서버에 붙은 BE에는 실검 API가 없어 띠 자리에
"순위를 불러오지 못했어요"만 떴다. 전에 쓴 길([리디자인 검증 환경](0171-haechukimo-redesign.md) 때와 같다)대로
`API_BASE_URL=https://plick.co.kr/be`로 production build를 돌리고 `next start`를 3061 포트에 올려 prod BE에서
실검을 읽어 확인했다.

375px 폭에서 띠 오른쪽에는 `5/6` 카운터 하나만 남았고 `멈춤` 글자는 없다. 접근성 트리에서 `자동 넘김`
라벨이 사라진 것과 `실검 다음 항목, N/6` 버튼이 남아 있는 것을 확인했다. 6초 기다렸더니 카운터가 `5/6`에서
`1/6`으로 넘어가 자동 전환은 그대로 돈다. 콘솔에는 게스트 상태의 401과 404만 있었고 이번 변경과는 무관하다.

## 남은 것

웹(데스크톱)은 같은 `RotatingLine`을 쓰니 코드상 함께 바뀌었지만 브라우저로는 모바일만 밟았다. 호버 중 정지를
남긴 판단은 피드백이 오면 뒤집을 수 있다. 그때는 `hovered`·`focused` 상태까지 걷어 내면 된다.

## 곁가지: 터져 있던 CI는 무엇이었나

PR을 올리기 전에 Actions에 빨간 게 여럿 보여 먼저 확인했다. 두 종류였다.

하나는 E2E였다. 07:53과 09:15 두 번 모두 모바일 기사 스펙 두 개(`목록 첫 기사를 열면 같은 제목의 상세가 뜬다`,
`상세의 팀 해시태그를 누르면 그 팀 프로필이 뜬다`)가 `getByRole('article').first()` 안의 h3 링크를 45초 동안 못 찾고
타임아웃이었다. KAN-703 홈 개편으로 투표 카드가 첫 `article`이 되면서 생긴 드리프트고, 이건 이미 develop에 머지된
[ADR 0235](0235-e2e-mobile-news-scope.md)(PR #355)가 뉴스 영역으로 범위를 좁혀 고쳤다. 다만 그 머지 뒤 E2E가 다시
돌지 않아 초록불을 못 봤는데, 이유는 아래 배포 실패로 `workflow_run` 게이트(`conclusion == success`)에 걸려 건너뛰었기
때문이다. 그래서 로컬에서 dev를 상대로 모바일 기사 스펙을 직접 돌렸고 6개 모두 통과했다. 이 PR에 테스트를 더 고칠 건 없었다.

다른 하나는 PR #355 머지 직후의 Deploy였다. CodeDeploy가 10분을 기다리다 `HEALTH_CONSTRAINTS`로 실패했다. 인스턴스별
이벤트를 보니 Green 두 대는 `ValidateService`와 `AllowTraffic`까지 전부 성공이고, Blue 두 대 중 한 대(`i-00c3…`)가
`BeforeBlockTraffic`에서 "CodeDeploy agent was not able to receive the lifecycle event"로 죽어 있었다. 코드 문제가 아니라
옛 세대 한 대의 에이전트가 응답을 안 한 것이다.

왜 응답을 안 했는지 SSM으로 들어가 봤다. `systemctl`에 `codedeploy-agent.service`가 아예 없었고 `/opt/codedeploy-agent`도
없었다. 건강한 짝 인스턴스에는 둘 다 있었다. `cloud-init-output.log` 끝을 보니 답이 있었다. user data가 `snap install
aws-cli --classic`에서 "error: unable to contact snap store"로 멈췄고, 스크립트가 `set -euxo pipefail`이라 그 뒤의
`pm2 startup`과 에이전트 설치가 통째로 빠진 채 cloud-init이 끝났다. 그 인스턴스는 08:59 배포(PR #354)의 Green으로 태어난
것인데, 당시 배포 기록에도 그 인스턴스는 `ApplicationStop` 실패로 찍혀 있었다. 그런데 배포 전체는 성공이었다. 배포 그룹의
설정이 `CodeDeployDefault.AllAtOnce`라 최소 정상 호스트가 0이어서 Green 절반이 죽어도 통과한 것이다. ASG 헬스체크도
EC2 기준이라 ASG는 그 인스턴스를 Healthy로 봤고, 대상 그룹에서만 두 포트 모두 unhealthy였다. 그러니 11:27 배포에서
그 인스턴스가 Blue가 되는 순간 터질 수밖에 없었다.

남은 상태는 이렇다. 실패한 배포의 Green ASG(`CodeDeploy_plick-frontend-dg-dev_d-EPEQYC7PL`) 두 대가 대상 그룹에서
healthy로 dev 트래픽을 받고 있다. 배포 그룹은 여전히 옛 ASG(`…_d-QS94LWXE9`)를 가리키고, 그 안에 고장 난 인스턴스와
트래픽이 빠진 멀쩡한 인스턴스가 남아 네 대가 돌고 있다. 이대로 다음 배포를 하면 옛 ASG가 다시 Blue라 같은 자리에서
또 실패한다. 복구 절차와 user data 재시도 루프는 [docs/deploy-v2.md](../deploy-v2.md) §6·§14와 함정 목록에 적었다.
인프라 조작은 되돌리기 어려워 이 세션에서는 문서까지만 하고 사용자 확인을 받기로 했다.

## 인프라 정리 실행

사용자 확인을 받고 dev를 정리했다. 먼저 배포 그룹의 ASG를 옛 `…_d-QS94LWXE9`에서 트래픽을 받고 있던 Green
`…_d-EPEQYC7PL`로 바꿨다(`aws deploy update-deployment-group --auto-scaling-groups`). CodeDeploy가 그 ASG에 자기
런치 훅을 새로 달았고, 실패한 배포가 남긴 옛 훅 하나가 같이 붙어 두 개가 됐다. 이어서 옛 ASG를 `--force-delete`로
지웠다. 고장 난 인스턴스와 트래픽이 빠져 있던 짝이 함께 종료됐고, 대상 그룹에는 Green 두 대만 healthy로 남았다.
서비스 중단은 없었다.

중복 훅 삭제와 Launch Template 새 버전(dev·prod에 snap 재시도 루프)은 자동 모드 권한 분류기가 공유 자원 수정으로
막았다. 우회하지 않고 사용자에게 명령을 넘겼다. 중복 훅은 어차피 다음 배포가 성공하면 그 ASG째 사라지는 거라
문제가 아니었다. CodeDeploy는 Green을 복사할 때 원본 ASG의 훅을 가져오지 않는다는 것도 확인했다(EPEQ ASG에는
복사 시점에 자기 훅 하나만 있었다).

마지막으로 실패했던 Deploy 워크플로를 `gh run rerun --failed`로 다시 돌렸다. 같은 커밋(72d58c9)이 새 Green으로
나가 인스턴스 4대 전부 성공했고(`d-9YT6039PL`), 배포 그룹은 그 ASG로 넘어갔으며 EPEQ는 CodeDeploy가 종료
대기에 넣었다. 뒤따라 돈 E2E는 18개 전부 통과했다. 모바일 기사 스펙 드리프트가 CI에서도 닫힌 것을 이걸로 봤다.

남은 건 Launch Template 두 벌에 재시도 user data를 default로 올리는 것 하나다. 이걸 안 하면 snap 스토어가 또
흔들리는 날 같은 일이 반복된다. 더 근본적으로는 배포 설정을 최소 정상 호스트 1로 올려 반쪽 Green을 성공으로
기록하지 않게 하는 것과, ASG 헬스체크를 ELB로 돌리는 것을 검토할 만하다.
