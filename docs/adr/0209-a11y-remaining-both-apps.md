# 0209. 두 앱 접근성 잔여 일괄 정리 (KAN-670)

2026-10-23에 KAN-667을 끝내고 prod를 Lighthouse 12.8.2로 다시 쟀을 때, 성능은 거의 정리됐는데 접근성 점수가
화면마다 86~94에 머물러 있었다. 남은 실패를 세어 보니 여섯 종류였고, 원래는 모바일(KAN-628), 웹(KAN-640),
웹 표 머리(KAN-639) 세 티켓에 흩어져 있었다. 그런데 들여다보면 좋아요 버튼 이름처럼 두 앱이 같은 규칙을
써야 하는 것들이라 앱별로 따로 고치면 또 어긋난다. 그래서 KAN-670 하나로 묶어 한 브랜치에서 고쳤다.
뷰포트 확대 금지(`meta-viewport`)는 별도 티켓으로 이미 develop에 들어가 있어서([ADR 0206](0206-viewport-zoom-unlock.md))
이번 범위가 아니었다.

## 1. 버튼 이름이 보이는 글자와 어긋났다 (label-content-name-mismatch)

먼저 이 감사가 무엇을 보는지부터 짚어야 했다. 버튼에는 "접근 가능한 이름(accessible name)"이 있다. 스크린리더가
읽고, 음성 제어(iOS 음성 제어, Dragon 같은 것)가 "○○ 눌러"라는 명령을 매칭할 때 쓰는 이름이다. 보통은 버튼 안
글자가 그대로 이름이 되지만, `aria-label`을 달면 그 값이 안의 글자를 통째로 덮어쓴다.

우리 좋아요 버튼은 하트 아이콘 옆에 `12` 같은 숫자만 보이고, `aria-label="좋아요"`(눌린 상태면 `"좋아요 취소"`)로
이름을 덮고 있었다. 숫자만 읽히면 무슨 버튼인지 모르니 단 라벨이었다. 문제는 화면을 보며 음성 제어를 쓰는
사람은 보이는 글자 "12"로 버튼을 부른다는 점이다. 이름이 "좋아요"라 "12"가 들어 있지 않으니 명령이 안 먹는다.
WCAG 2.5.3(Label in Name)이 요구하는 게 "보이는 글자가 이름 안에 포함될 것"이고, Lighthouse(axe)의 이 감사가
그걸 기계로 본다.

해결은 두 가지가 있었다. 숫자 `span`에 `aria-hidden`을 걸어 이름 계산에서 빼거나, 이름에 숫자를 넣거나.
앞쪽은 보이는 글자가 이름에서 빠지는 거라 오히려 Label in Name의 취지와 거꾸로 간다. 그래서 이름에 숫자를
넣었다. `aria-label={\`좋아요 ${formatCount(count)}\`}`다. `formatCount`를 그대로 써서 화면에 "1.2천"이 보이면
이름도 "좋아요 1.2천"이 되게 했다. 같은 포맷 함수를 쓰지 않으면 다시 어긋난다.

"좋아요 취소"는 이참에 버렸다. 버튼에 `aria-pressed`가 이미 있어서 스크린리더가 "좋아요 12, 토글 버튼, 눌림"처럼
상태를 따로 읽어 준다. 이름까지 "취소"로 바꾸면 "좋아요 취소, 눌림"이 돼 뜻이 꼬인다. 토글 버튼의 이름은
상태와 무관하게 고정하고 상태는 `aria-pressed`에 맡기는 게 ARIA의 정석이다.

걸린 자리는 생각보다 많았다.

- 기사 좋아요 버튼(두 앱 `ArticleLikeButton`)
- 댓글 좋아요 버튼(두 앱 `CommentThread`). 기사 화면 실패 2건 중 두 번째가 이거였다. 셀렉터가
  `div.border-border-soft > div.flex > button`이라 처음엔 기사 하단 바 버튼인 줄 알았는데, 댓글 행이었다.
- 릴스 액션 레일(두 앱 `ReelActionRail`). 좋아요와 댓글 버튼 아래 숫자 라벨이 있다. 레일의 `RailAction`이
  `ariaLabel`과 보이는 `label`을 둘 다 받으니, `aria-label={ariaLabel && \`${ariaLabel} ${label}\`}`로 한 곳에서
붙였다. 공유 버튼은 `ariaLabel`이 없어 보이는 "공유"가 그대로 이름이라 손댈 필요가 없었다.

웹 팀 프로필의 실패 2건은 결이 달랐다. 우측 레일 순위 카드(`StandingsWindowCard`)는 한 행 전체가 팀 프로필
링크이고, 행 안에 순위, 크레스트, 팀명, 경기 수, 득실, 승점이 다 보인다. 그런데 링크를 그리는 공용
`TeamProfileLink`가 `aria-label={\`${team.name} 팀 프로필\`}`을 달고 있어서 이름이 "리버풀 팀 프로필"로 덮였다.
보이는 "3 … 20" 같은 숫자가 이름에 없으니 실패다. 이 컴포넌트는 라이브 화면 여기저기서 쓰는데, 자식은 늘
크레스트와 팀명이라 `aria-label`이 없어도 이름이 내용에서 제대로 나온다. 그래서 두 앱 `TeamProfileLink`에서
`aria-label`을 지웠다. "팀 프로필"이라는 꼬리말은 잃지만 링크라는 사실은 역할(link)로 읽히고, 이름이 보이는
내용과 일치하는 쪽이 낫다고 봤다.

## 2. 크레스트 alt가 옆 팀명과 겹쳤다 (image-redundant-alt)

`@plick/ui/TeamCrest`는 `alt={team.name}`으로 그린다. 크레스트만 덩그러니 있는 자리라면 맞는 alt다. 그런데 대부분은
크레스트 바로 옆에 팀명 텍스트가 같이 있다. 그러면 링크 이름이 "리버풀 리버풀"이 되고 스크린리더가 두 번 읽는다.
axe는 이미지 alt가 같은 부모의 글자와 똑같으면 이걸 잡는다.

이미지가 옆 글자와 같은 정보만 담으면 장식으로 보고 `alt=""`를 주는 게 규칙이다. 빈 alt는 "이 이미지는 건너뛰어도
된다"는 신호다(alt 속성을 아예 빼면 스크린리더가 파일 이름을 읽어 버리니 빈 문자열이어야 한다).
`TeamCrest`에 `decorative` prop을 두고 true면 alt를 비우게 했다. 기본값은 false라 크레스트만 있는 자리(웹 목록 행의
크레스트 링크, 모바일 `NewsItem`, MY 화면의 응원팀 줄)는 그대로 팀명을 읽는다.

빅6 밖 팀까지 그리는 `LiveCrest`도 같은 prop을 받아 넘기게 했다. 빅6면 `TeamCrest`로 넘기고, 외부 CDN 로고면
`img`의 alt를 비우고, 로고가 없어서 회색 원에 약칭을 그리는 경우엔 `aria-label`을 빼고 `aria-hidden`을 건다.
모바일 팀 프로필의 실패 2건이 이 `LiveCrest`였다. 순위 창(`StandingsWindow`)에서 빅6 두 팀만 링크라 그 둘이 걸렸다.

`decorative`는 감사에 걸린 여섯 자리뿐 아니라 "크레스트 옆에 같은 팀명이 바로 있는" 자리 전부에 달았다.
홈 핫 카드, 기사 헤더와 웹 브레드크럼, 릴스 팀 줄, 인물 헤더, 팀 프로필 머리(h1 팀명 옆), 온보딩 팀 선택,
MY 편집의 팀 선택과 목록이다. 측정한 여섯 화면 밖이라도 같은 문제라 이번에 같이 정리했다.

## 3. 터치 타깃이 24px보다 작았다 (target-size)

WCAG 2.5.8은 누를 수 있는 대상이 24×24 CSS px 이상이거나, 그보다 작으면 주변 대상과 충분히 떨어져 있기를 요구한다.
홈 카드의 팀 링크는 11.5px 글자 한 줄이라 높이가 16px 남짓이었다.

높이를 그냥 `min-h-6`로 키우면 카드 줄 높이가 늘어 시안이 틀어진다. 그래서 패딩으로 박스를 키우고 같은 양의
음수 마진으로 레이아웃 자리를 되돌리는 방식을 썼다. 웹 `HotCard`는 `-my-1.5 py-1.5`라 박스는 위아래 13px씩
커지는데 flex 줄이 차지하는 높이는 그대로다. 모바일 `HotHeroCard`는 원래 `mb-1`이 있어서 `-mt-1 py-1`로 바꿨다.
위로 4.4px 당기고, 위아래 패딩 8.8px, 아래 마진 0이라 전과 같은 공간을 쓴다. 실측으로 링크 박스는 52×26px이었다.

웹은 한 번 더 막혔다. 고친 뒤 재니 홈 핫 카드 하나가 여전히 실패했고 설명이 "21.3px by 30.5px"였다. 높이는 넘었는데
"맨유"처럼 두 글자 팀명은 폭이 21px이었다. `min-w-6`을 더해 폭도 24px를 보장했다. 링크 오른쪽은 비어 있어서
남는 폭은 보이지 않는다.

릴스의 트윗 임베드는 남의 컴포넌트(react-tweet)라 다르게 풀었다. 실패 노드는 작성자 줄의 `authorMeta` 안
"· Follow" 링크였다. 우리 임베드는 KAN-297부터 `pointer-events: none`인 읽기 전용이라 이 링크는 애초에 누를 수
없다. 누를 수 없는 링크가 접근성 트리와 탭 순서에만 남아 작은 타깃으로 잡힌 것이다. 그래서 두 앱 `globals.css`에서
`[class*="tweet-header-module"][class$="__authorFollow"]`를 `display: none`으로 숨겼다. react-tweet의 CSS 모듈 클래스는
`tweet-header-module__q3x0NW__authorFollow`처럼 빌드마다 바뀌는 해시가 끼어 있어서, 아바타 축소 규칙(KAN-297)과
같은 방식으로 접두사 포함과 접미사 일치를 함께 쓴다.

## 4. 투표 카드 제목이 h1 다음 바로 h3였다 (heading-order)

투표 화면은 h1 "투표" 아래에 카드마다 `VoteCard`의 h3 질문이 온다. 헤딩은 스크린리더 사용자가 페이지를 훑는 목차라
레벨을 건너뛰면 "중간에 뭔가 빠졌나" 하게 된다. axe는 h1 다음 h3처럼 한 단계 넘게 내려가는 걸 잡는다.

`VoteCard`의 h3를 h2로 내리면 기사 세부처럼 이미 h2 절 아래에 카드가 놓이는 자리에서 거꾸로 레벨이 꼬인다.
그래서 카드는 그대로 두고, 투표 목록 위에 스크린리더 전용(`sr-only`) h2를 두 앱에 넣었다. 탭에 따라
"진행 중인 투표", "마감된 투표"를 읽는다. 문구는 두 앱 `_constants/debates.ts`의 `DEBATE_LIST_HEADING`이다.
시각 디자인에는 이미 탭이 그 역할을 하고 있어서 보이는 제목을 따로 두지 않았다.

## 5. 표 역할의 자식이 비어 있었다 (aria-required-children, aria-required-parent)

ARIA 역할에는 부모 자식 규칙이 있다. `role="table"` 아래에는 `row`가, `row` 아래에는 `cell`이나 `columnheader`,
`rowheader`가 있어야 한다. div에 역할을 붙여 표를 흉내 낼 때 줄까지만 붙이고 칸을 비우면 스크린리더는 표로 읽지
못한다. 칸 수를 세지 못하니 "3열 중 2열" 같은 안내도 없다.

모바일 팀 프로필의 `StandingsWindow`와 `TeamStatsPanel`이 이 상태였다. 행마다 칸에 역할을 채웠다. 머리 줄은
`columnheader`, 홈/원정 표의 첫 칸(구분 이름)은 `rowheader`, 나머지는 `cell`이다. 머리의 "#"은 `aria-label="순위"`,
홈/원정 표의 빈 첫 머리칸은 `aria-label="구분"`으로 읽을거리를 줬다.

`StandingsWindow`의 팀 칸은 링크라 한 가지 고민이 있었다. 링크에 `role="cell"`을 얹으면 역할이 하나뿐이라 링크
역할이 사라진다. 그래서 링크를 `role="cell"` span으로 한 겹 감쌌다. 이 span이 grid 칸이 되니 `minmax(0,1fr)` 열에서
말줄임이 계속 되도록 `min-w-0`을 줬다.

웹 홈의 `PostTableHead`는 반대 문제였다. 표 부모 없이 `role="row"`만 달린 고아 줄이었다(그래서 required-parent와
required-children이 둘 다 났다). 이 목록은 행 하나하나가 기사 링크라 구조상 표가 아니라 목록이다. 표 역할을
제대로 채우려면 행 링크까지 `row`로 바꿔야 하는데 그러면 링크 역할을 잃는다. 그래서 머리 줄에서 역할을 빼고
`aria-hidden`으로 보조기술에서 숨긴 시각 머리로 뒀다. 스크린리더는 각 행 링크를 기사 제목으로 읽으면 충분하다.

여기서 하나 더 보였다. 선수 화면(`PlayerStatGroups`, `PlayerSeasonsTable`, `PlayerMatchRows`)과 웹 팀 스쿼드
표(`TeamSquadTable`)도 같은 `role="table"` + 빈 칸 패턴이다. 이번 측정 여섯 화면 밖이라 손대지 않고 후속으로 남겼다.

## 6. 웹 팀 프로필 캡션 대비 (color-contrast)

숫자 띠(`TeamNumberBand`)의 보조 줄("10경기", "20득점 8실점")이 `text-text-4`(#767676)였다. #767676은 흰 바탕에서
4.54:1로 본문 하한(4.5:1)을 겨우 넘는 회색인데, 이 띠는 `bg-elevate`(#f6f7f8) 위라 4.23:1로 떨어졌다. 바탕이 조금만
어두워져도 무너지는 경계값이다. 티켓은 elevate 배경용 보조 토큰을 새로 두는 안도 적었지만, 쓰는 자리가 여기
하나라 그 칸만 `text-text-3`로 올렸다. 같은 띠의 라벨(dt)이 이미 `text-3`라 위계도 자연스럽다.

## 검증

로컬에서 두 앱을 prod BE를 읽는 dev 서버(`mobile-prodbe` :3001, `web-prodbe` :3000)로 띄우고, prod 측정과 같은
Lighthouse 12.8.2로 접근성 카테고리만 쟀다. 화면은 홈, FAQ, 기사(`/articles/9729`, 댓글 있는 기사), 릴스, 투표,
팀 프로필(`/teams/liverpool/profile`)이다. 웹은 `--preset=desktop`.

| --------- | -------------- | ---------- |
| 홈        | 89 → 100       | 86 → 100   |
| FAQ       | 92 → 100       | 100 → 100  |
| 기사      | 94 → 100       | 99 → 100   |
| 릴스      | 86 → 100       | 93 → 100   |
| 투표      | 92 → 100       | 98 → 100   |

"전"은 prod 3회 측정이고 "후"는 로컬 1회라 조건이 같지 않다. 모바일 점수에는 develop에 먼저 들어간 뷰포트 수정
(ADR 0206)도 섞여 있다. 접근성 감사는 DOM 구조를 보는 거라 네트워크 조건 차이로 흔들리지 않지만, prod 배포 뒤
같은 스크립트로 한 번 더 재서 확인할 생각이다.

릴스는 트윗이 실제로 렌더된 상태에서 쟀는지 따로 봤다. 웹 릴스에서 `authorFollow` 10개가 모두 `display: none`이고
레일 좋아요 버튼 이름이 "좋아요 7"로 읽혔다. 홈 핫 카드는 두 앱 스크린샷으로 줄 높이가 전과 같은 걸 확인했다.

티켓 완료 조건의 VoiceOver 실청취(홈 핫 카드, 기사 좋아요, 투표 헤딩)는 이 세션에서 하지 못했다.

E2E는 `getByRole("button", { name: "좋아요" })`로 좋아요를 찾는데, Playwright의 name 매칭은 기본이 부분 일치라
"좋아요 7"도 잡는다. 셀렉터를 바꿀 필요는 없었다.
