# 0100 - 스켈레톤 깜빡임 제거 (웹 릴 댓글, 웹·모바일 MY)

## 무엇을 했나

스켈레톤 UI 두 군데를 걷어냈다. 하나는 웹 릴 세부 패널의 댓글 로딩 스켈레톤이고,
다른 하나는 웹과 모바일 MY 페이지의 라우트 로딩 스켈레톤(`loading.tsx`)이다.
둘 다 "화면에 들어갈 때마다 스켈레톤이 깜빡인다"는 같은 증상에서 출발했는데,
파고들어 보니 원인 메커니즘은 서로 완전히 달랐다. 그 차이를 이해한 과정이 이 세션의
알맹이라 여기 자세히 남긴다.

## 릴 댓글 스켈레톤 - TanStack Query의 isPending

웹 릴스 화면에서 릴을 넘겨 세부 패널을 열 때마다 댓글 영역에 펄스 애니메이션
스켈레톤(아바타 원 + 텍스트 바 3줄)이 떴다가 사라졌다. 댓글 데이터는 금방 오는데
스켈레톤이 매번 번쩍이니 오히려 로딩을 더 의식하게 만들었다.

구조를 보면 `CommentList`는 기사 세부와 릴 세부 패널이 같이 쓰는 클라 컴포넌트다.
데이터는 `useComments` 훅(TanStack Query `useInfiniteQuery`)으로 받는데, 두 사용처의
로딩 경험이 갈린다.

- 기사 세부(`/articles/[postId]`)는 서버 컴포넌트가 첫 페이지를 미리 받아
  `initial`로 심어 준다. `initialData`가 있으면 쿼리가 처음부터 데이터를 들고
  시작하므로 `isPending`이 아예 true가 되지 않는다. 스켈레톤을 탈 일이 없다.
- 릴 세부 패널은 클라이언트에서 열리는 패널이라 씨앗 없이 마운트된다. 릴을 넘길
  때마다 `articleId`가 바뀌고, 쿼리키(`commentKeys.list(articleId)`)가 바뀌면
  캐시에 없는 새 쿼리가 시작되니 매번 `isPending` 구간을 지난다. 이 구간마다
  스켈레톤이 그려졌다.

그러니까 스켈레톤은 사실상 릴 패널 전용으로만 보이는 UI였고, 릴을 좌우로 휙휙
넘기는 사용 패턴에서는 넘길 때마다 번쩍이는 소음이었다. 고민 없이 `isPending`
분기를 `return null`로 바꿨다. 로딩 중엔 댓글 영역이 그냥 비어 있다가 도착하면
목록이 나타난다. 댓글 응답이 빨라서 빈 상태가 머무는 시간은 짧고, 스켈레톤이
있을 때보다 눈에 띄는 움직임이 훨씬 적다.

한 가지 조심한 건 분기 순서다. `isPending` 분기를 아예 지워버리면 로딩 중에
`comments.length === 0`이라 "아직 댓글이 없어요" 빈 상태 문구가 먼저 떠 버린다.
로딩과 빈 상태는 다른 상태이므로 분기는 남기고 그리는 내용만 null로 바꿨다.

## MY 페이지 스켈레톤 - loading.tsx와 동적 렌더링의 조합

MY 페이지는 증상은 같아 보여도 층이 완전히 다른 문제였다. 여기는 클라이언트
쿼리가 아니라 Next의 라우트 수준 로딩 UI(`loading.tsx`)가 깜빡이고 있었다.

사용자(나) 입장의 의문은 이거였다. "마이페이지는 내용이 자주 안 바뀐다. 응원팀
수정, 닉네임 변경, 로그아웃, 탈퇴 때만 최신화되면 되는데 왜 들어갈 때마다
스켈레톤이 뜨나?" 답은 이 페이지에 클라이언트 캐시라는 층이 아예 없어서다.
데이터가 바뀌었는지와 무관하게, 구조상 방문할 때마다 서버 왕복이 일어나게 돼
있었다. 왜 그런지 층층이 뜯어 보면:

1. `/me`의 `page.tsx`는 서버 컴포넌트고 `getMyProfile()`을 await한다. 이 fetcher는
   `cookies()`로 access 쿠키를 읽어 Bearer로 실어 보낸다. Next에서 `cookies()`를
   읽는 순간 그 라우트는 동적 렌더링이 된다. 요청마다 값이 다를 수 있는 입력을
   읽었으니 빌드 타임 정적 생성이나 서버 캐시 재사용이 불가능하다고 판단하는 거다.
2. fetch 자체도 `cache: "no-store"`다. 이건 의도된 거다. 유저별 응답이 공유 데이터
   캐시에 남으면 다른 유저 렌더에 샐 수 있다.
3. 남은 건 브라우저 쪽 라우터 캐시(클라이언트에 RSC 페이로드를 잠깐 보관하는 층)
   인데, Next 15는 동적 페이지의 라우터 캐시 보관 시간이 기본 0초다. 방금 봤던
   /me 결과를 재사용하지 않고 버린다.
4. 그래서 GNB에서 MY로 이동할 때마다 서버에 RSC 요청이 날아가고, 응답이 오기
   전까지 Next가 `loading.tsx`를 Suspense fallback으로 그린다. 이게 매번 보이던
   스켈레톤이다.

정리하면 `loading.tsx`는 "서버 렌더를 기다리는 동안 뭘 보여줄까"의 답인데, 동적
페이지 + 라우터 캐시 0초 조합에서는 "기다림"이 매 방문 발생하므로 스켈레톤도
매 방문 뜬다. 처음 만들 때는 빈 화면보다 낫다고 넣었던 건데(KAN-319), 실제로
써 보니 거의 항상 순간적으로 스쳐 지나가는 번쩍임이 됐다.

### 고른 해법과 버린 해법

세 가지를 놓고 골랐다.

1. `loading.tsx` 삭제. 로딩 경계가 없으면 Next는 새 페이지가 준비될 때까지 이전
   화면에 그대로 머물다가 완성된 화면으로 전환한다. 스켈레톤 깜빡임이 사라지는
   대신 이동이 살짝 굼떠 보일 수 있다.
2. `next.config`의 `experimental.staleTimes.dynamic`으로 라우터 캐시를 몇십 초
   살리기. /me 재방문이 즉시 뜨게 되지만 전 동적 라우트에 걸리는 전역 설정이라
   릴스 같은 다른 화면의 신선도에도 영향을 준다. 스켈레톤 하나 잡자고 만지기엔
   범위가 너무 넓다.
3. 프로필을 TanStack Query로 옮기고 팀 수정·닉네임 변경·로그아웃 뮤테이션에서만
   invalidate. "이벤트 있을 때만 최신화"라는 요구와 정확히 일치하지만, 서버
   컴포넌트 fetch를 클라 쿼리로 옮기는 재배관이라 손이 제일 많이 간다.

1번으로 갔다. 코드가 줄어드는 방향이고, MY 페이지 응답이 프로필 조회 하나라
서버 왕복이 짧아 이전 화면에 머무는 시간도 체감이 작다. 나중에 프로필 데이터를
다른 화면에서도 쓰게 되면 그때 3번(클라 쿼리 + invalidate)을 다시 꺼내면 된다.

적용 범위는 웹 `/me`와 모바일 `/me`다. `/me/edit`의 `loading.tsx`는 남겼다
(사용자 결정). 수정 화면은 진입 빈도가 낮아 깜빡임 체감이 덜하기도 하다.

`loading.tsx`는 어디서도 import하지 않는 파일 위치 규약이라 지우는 것만으로
끝난다. 웹·모바일 둘 다 타입 검사로 확인했다.

## 결과

- `apps/web/app/_components/CommentList.tsx`: `isPending` 분기가 스켈레톤 대신
  null을 돌려준다.
- `apps/web/app/me/loading.tsx`, `apps/mobile/app/me/loading.tsx` 삭제.
- `/me/edit`의 loading은 웹·모바일 모두 유지.

Jira 티켓은 따로 만들지 않고 진행했다(사용자 결정). 관련 맥락은 웹 댓글 이식
[0090대 KAN-329 작업]과 MY 페이지 API 연결(KAN-319, 모바일 KAN-267) ADR들에 있다.
