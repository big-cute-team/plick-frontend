# 0216. 게스트 발급 상한의 주체를 FE 인스턴스에서 방문자로 돌렸다 (KAN-680)

## 어디서 이어지나

[ADR 0215](0215-guest-route-proxy-regression-tests.md) 마지막 절에서 끝난 이야기다. 게스트 발급 라우트의
남용 방어를 따지다 BE 상한이 사람을 세는 게 아니라 FE 인스턴스를 센다는 걸 코드로 알아냈고, "증거가
없으니 재현부터"라며 KAN-680으로 넘겼다. 이번 세션은 그 티켓이고, 처음부터 블로그 글을 같이 쓰기로 했다.
문제 상황, 검증, 해결 방안 비교, 적용 순으로 글을 쌓고 콘솔 작업 사진은 사용자가 직접 찍어 넣는다.
초안은 `_workspace/2026-10-27-kan-680/blog-0*.md`에 있고 원본 수치는 같은 폴더 `evidence/`에 뒀다.

세션 초반은 설명이었다. 사용자가 "브라우저가 POST를 했는데 왜 IP를 모르냐", "다른 API는 왜 괜찮냐",
"서버 길과 브라우저 길은 왜 갈리냐", "라우트 핸들러가 뭐냐", "XFF는 우리가 만든 거냐"를 차례로 물었고,
그 답이 그대로 블로그 문제 상황 절의 뼈대가 됐다. 요점은 둘이다. HTTP 요청은 TCP 연결 위에서 가고
서버가 아는 상대는 자기와 연결한 쪽이라, FE 서버가 BE에 새 연결을 열면 BE가 보는 클라이언트는 FE다.
그리고 다른 API는 BE가 토큰으로 사람을 아니 IP가 없어도 되는데, 게스트 발급만 아직 토큰이 없어 IP가
유일한 손잡이라 거기서만 터진다.

## 공격 재현은 하지 않기로

티켓 0단계는 "dev에서 발급 주소를 분당 60회 넘게 두드리는 동안 다른 기기로 첫 방문해 503을 캡처"였다.
사용자가 이걸 빼자고 했다. 공격을 흉내 내는 스크립트는 자꾸 세이프가드에 걸리고, 구조가 그렇다는 건
로그와 테스트로 보여 주면 충분하다는 판단이었다. 돌이켜 보면 그게 더 나은 증거였다. 공격 재현은 "막을
수 있다"를 보여 주지만, 아래 관찰은 "이미 막히고 있었다"를 보여 줬다.

## 관찰 하나: 빨간 테스트

KAN-675의 테스트 도구는 전역 `fetch`를 가짜로 바꿔 라우트가 BE에 보내는 헤더를 기록한다. 거기에 되어야
하는 모양을 먼저 적었다. CloudFront를 거쳐 온 것처럼 `X-Forwarded-For` 체인과 `CloudFront-Viewer-Address`를
둘 다 넣은 요청을 라우트에 주고, BE 호출의 `X-Forwarded-For`가 방문자 IP 하나여야 한다는 단언이다.
두 앱 모두 `actual: null`로 떨어졌다. 체인을 잘못 넘기는 게 아니라 아예 안 넘긴다는 게 테스트로 고정됐다.
두 헤더를 다 넣은 건 1a와 1b 어느 쪽을 고르든 같은 테스트가 기준이 되게 하려던 것이다.

## 관찰 둘: dev에 한 번 방문하고 세 자리를 맞췄다

내장 브라우저로 dev 홈을 한 번 열었다. `POST /api/session/guest`가 200이었고 발급 시각은 14:28:35였다.
이 한 번의 방문을 세 자리에서 찾았다.

공용 ALB(`plick-alb-pub`) 액세스 로그의 클라이언트는 `15.158.3.142`, CloudFront 엣지였다. 내 공인 IP
`121.162.157.81`은 로그 어디에도 없다. 사설 ALB(`plick-alb-pri`) 로그의 같은 초 `/api/v1/auth/guest`
클라이언트는 `172.16.4.140`, dev FE 인스턴스 둘 중 하나였다. ALB 로그는 5분 단위로 S3에 떨어지니
백그라운드로 파일이 생기길 기다렸다가 받았다.

세 번째가 핵심이었다. BE가 센 키를 직접 보고 싶었는데 상한 키는 60초 뒤 사라진다. dev BE 인스턴스에
SSM으로 들어가 보니 `redis-cli`가 없고, Valkey는 ElastiCache에 TLS로 붙어 있었다. `apt install`은 dev
서버를 건드리는 일이라 피하고, 파이썬 표준 라이브러리로 RESP 프로토콜을 직접 보냈다. `ssl`로 소켓을
감싸고 `*3\r\n$4\r\nAUTH\r\n...` 모양의 배열을 보내면 된다. 비밀번호는 인스턴스 안의
`/etc/plick/plick.env`에서 스크립트가 읽게 하고 출력하지 않았다. 스크립트를 base64로 묶어
`aws ssm send-command`의 명령 한 줄로 보냈다. 발급 32초 뒤 결과는 이랬다.

```
KEYS ratelimit:* -> ['ratelimit:auth-guest:172.16.4.140']
ratelimit:auth-guest:172.16.4.140  value=1  ttl=27
```

내가 방문했는데 BE가 센 주체는 FE 서버다. 표로 놓으면 브라우저, 공용 ALB, 사설 ALB, Valkey 키 네 줄의
"본 주소"가 홉마다 바뀌고 마지막 둘이 같다.

181건은 10월 4일(83), 12일(24), 20일(74) 세 날에 몰려 있었다. 분 단위로 펼치니 상한의 모양이 그대로

같은 분의 공용 ALB 로그에서 무엇이 왔는지도 봤다. 처음 짠 집계 스크립트는 빈 결과를 냈는데, 동기화

같은 UA가 `/.env.development`와 `/actuator/env`를 찔렀다. 10월 12일은 윈도우 크롬 UA가 2분에 410건,
`/index.php`와 셸쇼크 페이로드 UA가 섞여 있었다. 스캐너다.

날짜가 전부 10월 23일 이전이라는 게 중요했다. KAN-665가 develop에는 10월 16일에 들어갔지만 main
릴리스는 10월 23일이라, 그때 prod는 아직 프록시가 쿠키 없는 페이지 요청마다 발급하던 구조였다. 쿠키
없는 스캐너가 페이지 150개를 훑으면 발급도 150번 나가고 인스턴스당 80건 남짓이니 바구니 60개는 40초쯤에
바닥난다. 그 뒤 다음 창까지 그 인스턴스로 떨어진 진짜 첫 방문자는 세션 없이 화면을 봤다. 직전 1분에
인스타그램 인앱 브라우저 요청이 19건 있었으니 사람이 들어오던 시간대였다. 누가 막혔는지는 로그로 특정할
수 없지만 막히는 구조였다는 건 특정됐다.

10월 23일 뒤로 prod 발급 호출은 하루 500에서 1,300건에서 25에서 56건으로 떨어졌다. JS를 돌리지 않는
스캐너가 발급을 못 일으키게 돼서다. 트리거는 사라졌지만 바구니의 주체가 FE라는 구조는 dev 관찰 그대로다.
이 바구니를 비운 게 발급 주소를 노린 공격이 아니라 평범한 스캐너였다는 점은 블로그 각도도 바꿨다.
"공격자 한 명이 막을 수 있다"보다 "상한이 사람별이었으면 스캐너가 자기 몫 60개 쓰고 막혔을 일을 공용이라
모두의 몫까지 비웠다"가 더 정확하다.

## 해결 방안 비교

다섯 갈래를 표로 놓고 봤다. 기준은 공격자를 막나, 진짜 방문자를 해치나, 그리고 틀어지면 어느 방향으로
틀어지나였다. 마지막 기준이 결정을 갈랐다.

받은 `X-Forwarded-For`를 그대로 넘기는 건 첫 값을 요청자가 지어낼 수 있어 상한 자체가 없어진다. 지금보다
나쁘다. FE 메모리 카운터는 인스턴스마다 따로 세고 재배포마다 비워지며, 키를 뭘로 셀지 정하는 순간 같은
질문으로 돌아온다. WAF rate rule은 CloudFront가 본 IP로 입구를 막지만 BE 바구니의 주체를 못 고친다.
서로 다른 IP 여섯이 분당 10회씩 보내면 바구니 60개는 그대로 빈다. 보조이고 보류했다. 조사하다 티켓에
적어 둔 "WAF 최소 단위 5분 창"이 옛 정보라는 것도 알았다. 지금은 창이 60·120·300·600초이고 하한은 10회다.

1b(체인 뒤에서 두 번째)는 코드만으로 되고 nginx `real_ip_recursive`나 Express `trust proxy: 2`와 같은
방식이라 낯설지 않다. 걸리는 건 "홉 수 2"가 코드에 박힌 가정이라는 점이다. 프록시가 하나 더 끼면 뒤에서
두 번째는 엣지 IP가 돼 "엣지당 공용"으로 조용히 바뀌고, CloudFront가 빠지면 요청자가 적은 값이 된다. 둘 다
에러가 없다. 테스트는 가짜 체인으로 초록이고 사고는 레디스 키 이름에만 남는다.

1a(`CloudFront-Viewer-Address`)는 체인이 아니라 값 하나이고 CloudFront가 직접 채운다. 오리진 요청 정책을
`AllViewer`에서 관리형 `AllViewerAndCloudFrontHeaders-2022-06`으로 바꿔야 오리진에 온다. 라우트는 헤더가
있으면 포트를 떼고 그 값 하나를 BE 호출의 `X-Forwarded-For`로 싣고, 없으면 안 싣는다. 이 "없으면 안
싣는다"가 결정의 이유다. 정책을 빠뜨린 배포가 있어도, 헤더 이름을 잘못 읽어도 결과는 오늘과 같은 공용
바구니이지 그보다 나쁜 상태가 아니다. 1b가 틀어지면 조작 가능한 값으로 갈 수 있는 것과 반대 방향이다.
둘을 "헤더가 있으면 1a, 없으면 1b"로 섞는 것도 버렸다. 어느 배포에서 어느 값이 쓰였는지 키만 봐서는 알 수
없고 1b의 조용한 실패가 폴백이라는 이름으로 다시 들어온다.

확인 못 한 게 둘 남았다. 헤더 값의 IPv6 형식은 AWS 문서에 예시가 없다(IPv4는 `198.51.100.10:46532`).
그리고 뷰어가 같은 이름의 헤더를 직접 보냈을 때 CloudFront가 덮어쓰는지도 명시가 없다. AWS re:Post는
"CloudFront가 직접 설정하는 헤더라 체인 조작 대상이 아니다"라고만 한다. 둘 다 정책을 바꾼 뒤 dev에 요청
하나를 보내 확인하기로 했다.

사용자가 "CloudFront가 쓰는 IP는 조작이 안 되냐"고 물었다. 조작되는 건 헤더에 적힌 문자열이고, CloudFront가
적는 건 TCP 연결의 소스 주소다. 패킷 소스 주소 자체는 위조할 수 있지만 TCP는 SYN-ACK가 그 주소로
돌아가야 연결이 맺어지니 남의 주소로는 연결이 안 된다. 다만 VPN이나 봇넷으로 여러 주소에서 오는 건
조작이 아니라 정말 다른 주소라 IP 상한이 애초에 못 막는 종류다. 이것도 블로그에 그대로 들어갔다.

## 코드

두 앱 `route.ts`가 한 글자도 다르지 않아 `@plick/core`에 `viewer-ip.ts`로 뺐다. `stripViewerPort`는
마지막 콜론 뒤를 포트로 보고 떼며 대괄호 IPv6도 받는다. 쉼표나 공백이 섞인 값은 버린다. BE가
`X-Forwarded-For`를 쉼표로 쪼개 첫 값을 보니 실어 보내는 값에 쉼표가 들어가면 그 자체가 체인 주입이다.
`viewerForwardedHeaders`는 `cloudfront-viewer-address`만 읽고 들어온 `X-Forwarded-For`는 아예 보지 않는다.
체인을 해석하지 않는다는 결정을 코드 모양으로 남긴 것이다. 라우트는 `issueGuest`에 분석 헤더와 이걸
펼쳐 넘기는 한 줄이 바뀌었다. BE 내부 ALB가 그 뒤에 FE IP를 덧붙여도 BE는 첫 값을 읽으니 BE 수정이
없다.

타입 검사에서 한 번 막혔다. `match()` 결과의 캡처 그룹이 `string | undefined`라 `?? null`을 붙였다.

테스트는 빨간 케이스가 초록이 됐고 세 가지를 더 고정했다. CloudFront 헤더 없이 체인만 오면 아무것도
싣지 않는 것, IPv6 두 형식, 그리고 헬퍼 단위 테스트로 빈 값·공백·쉼표·숫자 아닌 포트를 전부 버리는 것.
184개가 193개가 됐다.

단위 테스트는 가짜 `fetch`로 라우트를 직접 부르는 것이라 실제 Next 서버 경로에서도 봤다. 받은 헤더를
찍는 열다섯 줄짜리 가짜 BE를 8099에 띄우고, `launch.json`에 `API_BASE_URL`만 그쪽으로 돌린 임시 항목을
넣어 모바일 `next dev`를 올린 뒤 curl로 세 번 불렀다. CloudFront 헤더와 체인을 같이 보낸 요청은
`203.0.113.7` 하나, 체인만 보낸 요청은 없음, IPv6는 `2001:db8::1`. 체인의 첫 값 `1.2.3.4`는 어디에도
없었다. 덤으로 같은 로그에 두 길이 나란히 찍혔다. 서버 컴포넌트가 부른 `/api/v1/articles`는
`X-Forwarded-For`가 없고, 브라우저가 `/be`로 부른 `/api/v1/events`는 Next가 소켓 주소 `::1`을 채워
넘겼다. 임시 항목은 지우고 `launch.json`은 Prettier로 서식을 되돌렸다. 파이썬 `json.dump`로 고쳤더니
배열이 전부 줄바꿈돼 diff가 185줄로 불었던 걸 그렇게 수습했다.

## 헤드리스 리뷰가 잡은 것

push 전 `pr-review.sh`는 CRITICAL 0, WARN 1, INFO 4였다. WARN이 정확했다. `issueGuest`를 부르는 곳이
라우트만이 아니라 두 앱 `_services/auth.ts`의 로그아웃 서버 액션에도 있었다. 로그아웃하면 토큰을 지우고
곧바로 게스트를 다시 발급하는데, 그 호출에도 방문자 IP가 없었다. 라우트의 `request.headers`만 보고
서버 액션은 요청 객체가 없다고 넘겨 버린 건데, 서버 액션도 `next/headers`의 `headers()`로 들어온 요청
헤더를 읽을 수 있다. 같은 헬퍼를 `viewerForwardedHeaders(await headers())`로 꽂았다. 이 경로는
`cookies()`와 `headers()`가 요청 컨텍스트를 요구해 단위 테스트로 못 걸었다. INFO 중 하나는 헬퍼 머리
주석이 ADR 0215만 가리킨다는 것이라 0216과 호출처 둘을 적었다. IPv6에 대괄호가 없을 때 마지막 콜론으로
자르는 게 모호하다는 지적은 맞지만, CloudFront가 어느 형식을 쓰는지 문서에 없어 둘 다 받게 둔 채
dev에서 실제 값을 보고 좁히기로 했다.

## 남은 것

- 콘솔: 네 배포 기본 비헤이비어의 오리진 요청 정책을 `AllViewerAndCloudFrontHeaders-2022-06`으로. dev 둘
  먼저, prod 둘은 main 릴리스 뒤. S3 비헤이비어는 건드리지 않는다. 바꾼 뒤 홈 두 번째 응답의 `x-cache`가
  Hit인지 본다. 사용자가 하고 사진을 찍는다.
- dev 배포 뒤 관찰 둘을 그대로 반복한다. Valkey 키가 내 공인 IP로 바뀌는 것, 가짜
  `CloudFront-Viewer-Address`를 단 요청 하나로 덮어쓰기 여부, IPv6 형식.
- prod 반영 며칠 뒤 사설 ALB 로그의 429를 다시 센다.
- BE 티켓에 적을 함정: BE가 "뒤에서 n번째"로 바뀌면 브라우저 `/be` 길은 뒤에서 셋째(CloudFront, 공용 ALB,
  사설 ALB), 서버 길은 뒤에서 둘째(방문자, FE)라 홉 수 하나로 못 맞춘다. 그때 서버 길은 전용 헤더
  (`X-Plick-Viewer-Ip` 같은)로 넘기고 BE가 그걸 먼저 보게 하는 쪽이 맞다.
- `docs/deploy-v3-cdn.md` §6의 오리진 요청 정책 줄을 바꾼 정책과 이유로 갱신한다. 정책을 실제로 바꾼 뒤에.
