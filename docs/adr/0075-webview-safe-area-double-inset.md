# 0075. 앱셸 웹뷰에서 위아래로 생기는 이중 안전영역 여백 수정

## 증상

모바일 웹을 안드로이드 앱셸(웹뷰를 감싼 APK)에 연결해 갤럭시 폰에서 띄웠더니, 화면 위아래에 검은
공백이 생겼다. 위로는 상태바 아래에 한 뼘, 아래로는 하단 탭과 안드로이드 내비게이션 바 사이에 또 한
뼘. 앱 콘텐츠가 세로로 눌린 것처럼 보였다. 크롬 브라우저로 같은 페이지를 열면 멀쩡했다. 웹뷰에서만
났다.

## 원인 추적

스크린샷의 공백 높이를 재 봤다. 위 공백은 대략 40dp 안팎, 아래 공백은 50dp 안팎. 각각 안드로이드
상태바 높이와 제스처 내비게이션 바 높이에 거의 정확히 들어맞았다. 우연이라기엔 너무 맞아떨어져서,
시스템 바 높이만큼의 여백이 어디선가 "한 번 더" 얹히고 있다고 봤다.

코드에서 시스템 바 높이를 여백으로 쓰는 곳을 찾았다. `env(safe-area-inset-*)`를 직접 쓰는 데가
네 곳 있었다.

- `TopBarShell` - 상단바 `paddingTop: env(safe-area-inset-top)`
- `TabBar` - 하단 탭 `paddingBottom: env(safe-area-inset-bottom)`
- `BottomActionBar` - 온보딩·인증 CTA `paddingBottom: max(base, env(safe-area-inset-bottom) + 24px)`
- `ReelItem` - 릴 임베드 영역 `top: env(safe-area-inset-top)`

`env(safe-area-inset-*)`는 브라우저가 알려주는 "시스템 UI(노치, 상태바, 홈 인디케이터)에 가리는
영역"의 두께다. 뷰포트가 화면 끝까지 닿는(edge-to-edge) 환경에서, 콘텐츠가 노치나 홈 인디케이터에
깔리지 않게 이만큼 안쪽으로 밀어 넣으라는 뜻이다. 우리는 `viewport-fit=cover`를 선언해 두었기
때문에(노치·펀치홀 기기에서 화면을 끝까지 그리려는 의도) 이 값들이 살아난다.

문제는 앱셸 쪽 배치와의 조합이다. 스크린샷을 보면 상태바가 흰 배경으로 따로 그려져 있고 웹뷰는 그
아래에서 시작한다. 즉 네이티브 앱셸이 이미 웹뷰를 시스템 바 안쪽에 배치해서, 웹 입장에서는 가릴 것이
아무것도 없다. 그런데도 웹뷰(크로미움)가 safe-area 값을 0이 아니라 시스템 바 높이로 보고했다.
안드로이드 15부터 edge-to-edge가 강제되면서(targetSdk 35) 웹뷰가 화면 인셋을 CSS로 노출하는
동작이 생겼는데, 앱셸이 자체적으로 인셋을 처리해 웹뷰를 안쪽에 넣은 경우까지 값이 그대로 내려오는
케이스가 있다. 결과적으로 네이티브가 한 번 피하고, 웹이 그 위에 같은 높이를 패딩으로 한 번 더 얹어서
이중 여백이 됐다.

크롬 브라우저에서 멀쩡했던 이유도 설명이 된다. 일반 브라우저에서는 브라우저 크롬(주소창 등)이 시스템
바를 대신 감당하므로 safe-area 값이 0이다. 패딩이 0이라 아무 일도 없었던 것뿐이다.

## 해결 방법

처음엔 앱셸을 고치는 게 맞지 않나 생각했다. 앱셸이 웹뷰를 진짜 edge-to-edge로 깔고 인셋 처리를 웹에
전부 맡기면(웹은 이미 env()로 대응하고 있으니) 다크 배경이 상태바 뒤까지 이어지는 더 나은 모양이
된다. 하지만 지금은 웹 저장소에서 해결해야 했고, 어떤 앱셸에 실리든 웹이 알아서 버티는 쪽이 어차피
안전하다.

웹에서 풀려면 "지금 뷰포트가 정말 화면 끝까지 닿아 있는가"를 알아야 한다. CSS만으로는 알 수 없다.
env() 값은 두 경우 모두 0이 아니게 내려오기 때문이다. 대신 JS로 잴 수 있다. `screen.height`는 CSS
픽셀 기준 기기 화면 전체 높이고, `window.innerHeight`는 지금 뷰포트 높이다. 웹뷰가 edge-to-edge면
둘이 거의 같고(차이 0에 수렴), 시스템 바 안쪽에 배치돼 있으면 상태바+내비바 합(대략 90px 이상)만큼
차이가 난다. 문턱은 24px로 잡았다. 상태바 최소 높이가 24dp 언저리라, 그보다 작으면 오차로 보고
그보다 크면 "이미 안쪽"으로 판정한다.

구현은 세 조각이다.

먼저 `globals.css`에 변수를 만들었다.

```css
html {
  --safe-top: env(safe-area-inset-top);
  --safe-bottom: env(safe-area-inset-bottom);
}
html[data-inset-viewport] {
  --safe-top: 0px;
  --safe-bottom: 0px;
}
```

컴포넌트 네 곳은 `env()` 직접 참조를 전부 `var(--safe-top)`/`var(--safe-bottom)`으로 바꿨다.
기본값은 종전과 완전히 같고(env를 변수로 한 겹 감쌌을 뿐), `data-inset-viewport` 속성이 html에
달리는 순간만 0으로 접힌다.

판별은 `layout.tsx`의 `<head>` 인라인 스크립트가 한다.

```js
(function () {
  try {
    if (screen.height - window.innerHeight > 24)
      document.documentElement.setAttribute("data-inset-viewport", "");
  } catch (e) {}
})();
```

이 스크립트를 굳이 head의 동기 스크립트로 넣은 이유가 있다. 하이드레이션 후 useEffect에서 달면 첫
페인트는 이중 여백이 있는 채로 그려졌다가 잠깐 뒤 접힌다. 화면이 한 번 출렁이는 게 보인다. head의
동기 스크립트는 body 파싱 전, 즉 첫 페인트 전에 실행되므로 처음부터 접힌 채로 그려진다. 다크 테마
플래시를 막으려고 테마 스크립트를 head에 인라인으로 넣는 것과 같은 패턴이다.

일반 브라우저(크롬, 사파리)에서는 브라우저 크롬 때문에 차이가 24px를 넘어 속성이 달리지만, 그런
환경은 env()가 어차피 0이라 아무 변화가 없다. 반대로 진짜 edge-to-edge 환경(iOS 홈 화면 추가
스탠드얼론, edge-to-edge로 짠 웹뷰)은 차이가 0에 수렴해 속성이 안 달리고 env()가 그대로 산다.
잘못 접을 수 있는 경우는 "위만 피하고 아래는 edge-to-edge" 같은 반쪽 인셋 앱셸 정도인데, 세로 차이
하나로는 위아래를 구분할 수 없어 지금은 대칭으로만 판정한다. 그런 앱셸이 실제로 나타나면 그때 다시
본다.

## 하이드레이션 경고

붙이고 보니 콘솔에 hydration mismatch 경고가 떴다. React는 서버가 렌더한 HTML과 클라이언트 첫
렌더 결과를 대조하는데, 인라인 스크립트가 하이드레이션보다 먼저 html에 `data-inset-viewport`를
달아 버리니 서버 산출물에 없던 속성이 생겨 있어 어긋난다. `<html>`에 `suppressHydrationWarning`을
달아 해결했다. 이 플래그는 그 엘리먼트 하나의 속성 비교만 끄고 자식 트리에는 전파되지 않아서, 다른
곳의 진짜 mismatch를 가리지 않는다. next-themes 같은 테마 라이브러리가 쓰는 표준 수법이다.

## 검증

실기기 없이 데스크톱 브라우저 프리뷰로 로직을 검증했다.

- 뷰포트 차이가 24px를 넘는 조건에서 `data-inset-viewport`가 달리고, 0에 수렴하는 조건에서는 안
  달리는 것을 확인했다.
- 스타일 주입으로 `--safe-top: 40px`을 강제한 뒤, 속성이 있으면 상단바 패딩이 0으로 접히고 속성을
  떼면 40px로 살아나는 것을 확인했다. 변수 배관과 킬스위치가 둘 다 동작한다.
- `suppressHydrationWarning` 적용 후, 속성이 달리는 조건에서도 hydration 경고가 더 나오지 않는
  것을 확인했다.
- 홈·릴스 화면이 종전과 똑같이 렌더되는 것을 확인했다(브라우저에서는 env가 0이라 시각 변화가 없어야
  정상이다).

갤럭시 앱셸 실기기 확인은 사용자 몫으로 남았다. 판별이 기대대로면 위아래 공백이 사라져야 한다.

## 남은 한계

판별은 로드 시점 한 번만 한다. 회전이나 키보드로 뷰포트가 변해도 다시 재지 않는다. 키보드가 열릴 때
innerHeight가 줄어 edge-to-edge 환경을 인셋 환경으로 오판하는 걸 피하려고 일부러 리스너를 달지
않았다. 앱셸이 세로 고정이라 회전은 당장 문제가 아니다.

위아래를 따로 판정하지 못하는 것도 한계다. window.screenY 같은 값은 웹뷰 구현마다 신뢰할 수 없어
쓰지 않았다. 반쪽 인셋 앱셸을 만나면 그때 앱셸 쪽 정보(유저 에이전트나 JS 브리지)로 푸는 게 나을
것이다.

`screen-publishing` 스킬 §3.
