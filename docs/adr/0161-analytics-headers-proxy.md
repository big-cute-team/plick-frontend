# 0161. 프록시에서 기기 식별자와 유입 경로를 발급하고 분석 헤더 넷으로 전달

KAN-542. 2026-09-19.

## 무슨 일이었나

KPI가 DAU로 서면서 백엔드가 이벤트 계약을 v2로 올렸다(KAN-538). 모든 이벤트에 기기 식별자,
유입 경로, 앱 구분, 진입 화면이 붙고, 그 값은 프런트가 요청 헤더 넷(`X-Plick-Device`,
`X-Plick-Path`, `X-Plick-Client`, `X-Plick-Entry`)으로 실어 보내기로 했다. 게스트 계정은 세션마다
새로 생기니 계정 id로는 사람 수를 못 세고, 그래서 기기마다 익명 UUID를 하나 두자는 게 골자다.

티켓이 짚은 자리는 셋이었다. 게스트 발급(`proxy.ts`의 `startGuestSession`), 인증 헤더를 붙이는
자리(`authorized()`), 서버 측 fetch(`apiFetch`). 여기에 PC와 모바일을 오가는 전환 배너에서 식별자를
넘기는 규칙과, 비로그인 조회 기록에 원 클라이언트 IP가 `X-Forwarded-For`로 가는지 확인하는
항목이 붙어 있었다. 모바일 웹과 데스크톱 웹 둘 다다.

## 값은 어디서 정하고 헤더는 어디서 붙이나

메인 API는 브라우저가 직접 부르지 않는다. 두 길이 있다. 브라우저 fetch는 same-origin `/be/*`로
나가고 Next `rewrites`가 BE로 넘긴다(KAN-271). 서버 컴포넌트와 서버 액션은 `apiFetch`가 절대
URL로 BE를 직접 부른다. 어느 쪽이든 BE는 프런트 도메인의 쿠키를 못 본다. 그래서 쿠키에 보관한
값을 헤더로 옮겨 주는 자리가 필요하고, 그게 두 길 각각에 있어야 빠짐이 없다.

처음엔 서버 측 fetch 쪽이 막막했다. `apiFetch`를 부르는 자리가 두 앱 합쳐 서른 곳쯤이고, 그중
공용 fetcher(`@plick/core`의 `articles.ts`, `reels.ts` 등)는 `accessToken` 인자를 받아 호출부가
`Authorization`을 넘기는 구조다. 같은 식으로 분석 헤더도 인자로 넘기면 서른 곳을 다 고치고
공용 fetcher 시그니처까지 바꿔야 한다. 그리고 앞으로 fetcher를 하나 추가할 때마다 빠뜨릴 수 있다.

그래서 값을 정하는 자리를 프록시 하나로 못박고, 서버 측 fetch는 그 값을 "요청 헤더에서 읽어
옮기는" 방식으로 갔다. 흐름은 이렇다.

1. `proxy.ts`가 요청마다 쿠키와 URL에서 넷을 정한다(`resolveAnalytics`).
2. `NextResponse.next({ request: { headers } })`로 나가는 요청 헤더에 `X-Plick-*`를 찍는다(`forward`).
   `/be` fetch면 이 헤더가 rewrites를 타고 BE까지 그대로 간다. 페이지 요청이면 BE로 가는 게
   아니라 이번 렌더의 서버 컴포넌트가 `headers()`로 읽을 수 있는 요청 헤더가 된다.
3. 서버 측 `apiFetch`는 호출 직전에 헤더 제공자를 부른다. 각 앱의
   `_services/analytics-headers.ts`가 `headers()`에서 `X-Plick-*`만 골라 돌려주고, `apiFetch`가
   호출부가 안 넘긴 이름에만 채운다.

`NextResponse.next({ request: { headers } })`가 뭘 하는지 짚고 가면, 이건 응답 헤더가 아니라
다운스트림이 보게 될 요청 헤더를 바꾸는 것이다. Next는 이걸 내부 헤더(`x-middleware-request-*`,
`x-middleware-override-headers`)로 실어 보내 라우터가 요청을 다시 조립하게 한다. 그래서 프록시가
찍은 헤더를 rewrites 대상(BE)도 보고, 서버 컴포넌트의 `headers()`도 본다. 기존 코드가 `/be`
요청에 Bearer를 싣던 방법이 정확히 이것이라(KAN-308) 같은 자리에 넷을 더 얹었을 뿐이다.

헤더 제공자를 `apiFetch`에 어떻게 꽂느냐는 관측자(KAN-455)의 선례를 그대로 따랐다. `@plick/core`는
Next에 의존하지 않는 순수 패키지라 `headers()`를 직접 못 부른다. 그래서 `setApiFetchHeaderProvider`로
함수 하나를 받는 빈 슬롯만 두고, 각 앱 `instrumentation.ts`가 서버가 뜰 때 꽂는다. 슬롯은 모듈
변수가 아니라 `globalThis`에 `Symbol.for`로 둔다. Next가 instrumentation과 페이지, 서버 액션을 서로
다른 번들로 묶고 번들마다 `client.ts` 복사본이 따로 들어가서, 모듈 변수로 두면 instrumentation
번들에만 꽂히고 페이지 번들의 `apiFetch`는 빈 슬롯을 본다. 관측자 때 실제로 카운터가 0으로 남아
확인된 함정이다.

제공자가 던지면 빈 헤더로 통과시킨다. 분석 값 때문에 서비스 요청이 실패하면 안 된다는 건 BE
계약의 원칙이고 프런트도 같다. 다만 `headers()`가 정적 생성 중에 던지는 예외는 Next가 "이 라우트는
동적이다"를 알리는 제어 흐름이라 삼키면 안 된다. `unstable_rethrow`로 되던지고 나머지만 삼킨다.
실제로는 루트 레이아웃이 `cookies()`를 읽어 모든 페이지가 이미 동적이라 이 갈래에 닿을 일이
거의 없다. 빌드 로그에 찍히는 `Dynamic server usage: ... used cookies`는 이번 작업 전부터 있던
줄이다(릴스와 토론 페이지가 `getAccessToken`을 try 안에서 불러 잡아 찍는다).

## 넷을 어떻게 정하나

기기 식별자는 쿠키 `plick_did`. 없으면 `crypto.randomUUID()`로 만들어 400일짜리 쿠키로 심는다.
"1년 이상"이 요구사항이고 크롬이 `Max-Age`를 400일에서 자르니 그 상한을 그대로 썼다. 만드는 건
페이지 요청에서만 한다. `/be` fetch는 항상 페이지 뒤에 오므로 그때는 이미 쿠키가 있고, 없는
채로 fetch 여러 개가 동시에 오면 각자 다른 값을 만들어 마지막 Set-Cookie만 남는다. 크롤러에게는
안 만든다. 게스트를 안 주는 이유와 같다. 쿠키를 안 들고 다녀서 요청마다 새 기기가 되고 DB만 찬다.

이 쿠키는 HttpOnly가 아니다. 전환 배너가 링크에 값을 실어야 하는데 배너는 브라우저에서 도는 클라
컴포넌트다. 처음엔 서버 컴포넌트가 읽어 prop으로 내리려 했는데, 모바일 배너가 `AppShell` 안에
있고 `AppShell`은 클라 컴포넌트(`error.tsx`, `HomeScreen`)에서도 렌더된다. prop을 화면마다 꿰기엔
자리가 너무 많았다. 게스트 안내 표식(`guestNotice`)이 같은 이유로 HttpOnly를 뺐던 선례가 있어
따랐다. 담긴 값이 익명 난수 하나라 노출돼도 잃을 게 없고, 브라우저에서 고쳐 봐야 BE가 UUID
형식이 아니면 비운다.

유입 경로는 쿠키 `plick_path`. 페이지 요청의 `?path=`, 없으면 `utm_source`. 새 값이 오면 갱신,
없으면 유지, 쿠키도 없으면 `direct`. 허용 목록(`insta`, `facebook`, ...)은 프런트에 두지 않았다.
BE가 모르는 값을 `unknown`으로 접으니 프런트는 헤더에 실어도 안전한 문자(소문자·숫자·밑줄
32자)만 거르고, 광고를 새로 집행해 값이 늘 때 BE 목록만 고치면 되게 했다. 읽는 쪽이 프록시뿐이라
HttpOnly다.

앱 구분은 앱마다 상수다. 모바일 `_constants/analytics.ts`가 `mobile_web`, 웹이 `desktop_web`.
메인 API는 프런트 서버를 거쳐 오니 요청 도메인으로는 못 가르고 프록시가 고정값을 보낸다.

진입 화면은 절반만 했다. 페이지 요청은 그 경로, `/be` fetch는 Referer의 경로에서 `/`면 `home_feed`,
`/reels`면 `reels`, `/reels/{id}`면 `reels_deeplink`를 고른다. `hot`과 `share_link`는 경로만으로는
모른다. 핫이슈는 홈 안의 구획이고 공유 링크는 표식이 없다(ADR 0047, origin만 유지). Phase 33
계약이 원래 "화면을 옮길 때 클라이언트가 `X-Plick-Entry`를 바꾼다"였으니 그 둘은 클라이언트
이벤트 작업(KAN-543)이 요청마다 실어 주는 몫으로 두고, 프록시는 브라우저가 이미 실어 보낸
`X-Plick-Entry`가 있으면 덮지 않는다. 나머지 셋은 프록시가 주인이라 브라우저 값이 있어도 덮는다.

## 도메인을 넘을 때

쿠키는 도메인별이다. `m.plick.co.kr`에서 배너를 눌러 `plick.co.kr`로 가면 거기엔 `plick_did`가
없어 새 기기가 되고 한 사람이 둘로 세어진다. 규칙은 계약대로다. 보내는 배너가 `?did=`에 식별자를
싣고, 받는 쪽 프록시는 자기 쿠키가 없을 때만 채택한다. 있는 사람의 식별자를 남이 보낸 링크가
덮어쓰면 안 되니까. 쿼리 이름은 `@plick/domain/cross-site`에 상수로 뒀다. 보내는 앱과 받는 앱이
서로 다른 앱이라 이름이 갈리면 조용히 두 명이 된다. `crossSiteUrl`이 세 번째 인자로 식별자를 받아
붙인다.

로컬에서 이걸 검증하는 데 함정이 하나 있었다. 쿠키는 도메인만 보고 포트는 안 본다. 모바일을
`localhost:3013`, 웹을 `localhost:3003`에 띄우면 둘이 쿠키를 공유해서 넘김이 검증이 안 된다.
웹을 `127.0.0.1:3003`으로 열어 다른 호스트로 만들었다. 그 뒤 `?did=<모바일 값>`으로 들어가니
웹 요청이 그 식별자로 나갔고(`client=desktop_web`), 다시 다른 UUID를 `?did=`로 넣어도 채택되지
않았다.

`?did=`를 주소창에서 지우지는 않았다. 리다이렉트 한 번이 더 들고, 이 URL을 그대로 복사해 남에게
보내도 받는 쪽은 쿠키가 있으면 무시하니 실제 피해는 쿠키 없는 첫 방문자가 남의 기기가 되는
드문 경우뿐이다. 이건 남은 것에 적어 둔다.

## 게스트 발급과 재발급에도 싣는다

`guest_issued` 이벤트에 기기 식별자가 실리려면 게스트 발급 요청에도 헤더가 있어야 한다. 프록시는
요청 컨텍스트 밖이라(`headers()`를 못 쓴다) `apiFetch`의 헤더 제공자가 닿지 않는다. 그래서
`issueGuest`와 `refreshTokens`가 `headers` 인자를 받게 하고 프록시가 방금 정한 넷을 넘긴다.
재발급 dedupe(`refreshTokensShared`)는 첫 호출의 헤더만 BE로 가는데, 묶이는 형제 요청이 같은
브라우저의 버스트라 값도 같다.

기기 식별자가 게스트 발급 시점에만 만들어지면 안 된다는 것도 여기서 정리했다. 설계 문서는 "게스트
발급 자리에서 같이 심는다"고 했는데, 그렇게만 하면 이미 토큰을 가진 사람(배포 전에 들어온 게스트,
소셜 사용자)은 게스트가 만료돼 재발급될 때까지, 소셜이면 영영 식별자가 없다. 그래서 토큰 유무와
무관하게 페이지 요청에서 쿠키가 없으면 만든다. 프록시 갈래가 많아 갈래마다 심으면 빠뜨리니,
`proxy()`가 앞에서 넷을 정하고 갈래 함수(`route`)가 돌려준 응답에 뒤에서 쿠키를 얹는 구조로
바꿨다. 리다이렉트 응답에 심어도 브라우저가 저장하니 재시도 갈래에서도 새 기기가 안 생긴다.

## X-Forwarded-For는 그냥 통과한다

비로그인 조회 기록의 IP 한도(분당 120회)가 `X-Forwarded-For`의 첫 값을 쓴다. 브라우저 `/be`
요청이 Next rewrites를 거칠 때 이 헤더가 살아남는지가 질문이었다. Next의 외부 rewrite는
`http-proxy`로 요청 헤더를 그대로 넘기고 `x-forwarded-host`만 덧붙인다. 로컬에서 `curl`로
`X-Forwarded-For: 203.0.113.9, 10.0.0.1`을 실어 보내니 BE 앞 탭 프록시에 그 값 그대로 찍혔다.
브라우저 요청처럼 헤더가 아예 없으면 소켓 주소(`::1`)가 들어갔다. 배포에서는 ALB가 원 클라이언트
IP를 첫 값으로 넣고 Next가 손대지 않으니 BE가 첫 값을 읽으면 그게 클라이언트다. 서버 측 fetch는
프런트 서버 IP로 나가지만, 조회 기록은 브라우저에서만 부르는 호출이라 해당이 없다.

## 검증

로컬 BE를 8082에 띄우려다 공유 Supabase 스키마 검증에서 죽었다. `stories.figure_id`가 없다고
했고, 실제로 뒤져 보니 `match_fixtures` 테이블 통째와 `stories`의 두 컬럼이 빠져 있었다. `schema.sql`의
컬럼 목록과 `information_schema.columns`를 `comm`으로 대조해 빠진 걸 한 번에 찾고, 사용자 승인
뒤 그대로 적용했다.

헤더가 실제로 나가는지는 BE 앞에 헤더만 찍는 통과 프록시(8083→8082, 스크래치 20줄)를 두고
`API_BASE_URL`을 거기로 돌려 빌드했다. 브라우저 `/be`와 서버 측 fetch 양쪽이 같은 자리를 지나니
한 로그로 다 보인다. 확인한 것:

- 첫 방문 응답에 `plick_did`(HttpOnly 아님, 400일)와 `plick_path=direct`(HttpOnly)가 심긴다
- 게스트 발급, 재발급, `/users/me`, 피드, 핫이슈, 경기, 토론 목록 전부 넷이 실려 나갔고, BE 로그의
  `analytics event` 줄에 `device=<uuid> path=direct entry=home_feed client=mobile_web`으로 찍혔다.
  `guest_issued`에도 같은 식별자가 있다
- `?path=insta`로 들어가면 그 뒤 요청이 `path=insta`, 릴스로 옮겨도 유지된다
- 릴스에서 나가는 브라우저 조회 기록(`POST /articles/{id}/view`)에 식별자와 Bearer,
  Referer로 정한 `entry=reels`가 실렸다
- 구글봇 UA로 들어가면 Set-Cookie가 하나도 없고 요청엔 `path`와 `client`만 나간다
- 데스크톱 웹도 같은 값이 `client=desktop_web`으로 나간다. 도메인 넘김은 위에 썼다
- 1200px 뷰포트에서 모바일 배너 링크가 `http://localhost:3000/?did=<uuid>`였다
- `pnpm format:check`, `pnpm lint`, `pnpm check-types`, 두 앱 `next build` 통과

한 가지 눈에 띈 건 브라우저 패널이 처음 열릴 때 페이지 요청이 두 번 동시에 들어와 UUID가 둘
만들어지고 게스트도 둘 발급된 것이다. 둘 다 쿠키가 없는 상태에서 출발해 각자 만들고 마지막
Set-Cookie가 이긴다. 게스트가 둘 생기는 건 이번 작업 전부터 있던 경쟁이고(두 요청 모두
`startGuestSession`에 닿았다), 기기 식별자도 같은 경쟁에 같이 걸린다. 설계 문서가 "쿠키가 아직
