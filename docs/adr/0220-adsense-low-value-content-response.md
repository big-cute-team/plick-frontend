# 0220. 애드센스 "가치가 별로 없는 콘텐츠" 거절에 대응한다: 기사 noindex, 운영자 글, 문구 교체, 카카오 애드핏

2026-10-30. 티켓은 KAN-652([FE] 광고 추가)다. 새 티켓 생성 MCP가 분류기에 막혀 기존 광고 티켓에 붙였다.

## 어떤 알림이 왔나

애드센스 사이트 목록에서 plick.co.kr이 "주의 필요"가 됐고 상태 세부정보는 "가치가 별로 없는 콘텐츠"였다.
ads.txt는 "승인됨"이었다. 애드센스는 거절 사유를 이 한 줄 분류 말고는 어디에도 안 보여 준다. 사이트 행을
눌러도, 알림 메일도, 정책 센터도 같은 문구다. 정책 센터는 승인된 사이트에 광고 제한이 걸렸을 때만 항목이
생겨서 승인 전 사이트는 비어 있다. 그래서 사유를 받는 대신 구글이 봤을 것을 직접 재구성했다.

## 구글이 본 것을 재구성했다

크롤러 UA로 실서비스를 받아 보니 원인이 분명했다. 기사 한 건(`/articles/10839`)의 서버 렌더 본문이 이랬다.

```
첼시가 21세 코모 슈퍼스타를 1월 이적 시장에서 영입하려고 준비 중이다.
이 소식은 체스크 파브레가스의 팀이 맨유를 상대로 승리한 후 전해졌다.
# 맨체스터 유나이티드 # 첼시   출처 원문 보기
```

두 문장, 100자 남짓이다. 나머지는 내비게이션과 관련 기사 제목, 푸터뿐이고 모바일은 페이지 전체 텍스트가
775자였다. 사이트맵에는 이런 기사 페이지가 5,215개 URL 중 거의 전부였다. 구글 입장에서 이 구조는 애드센스
정책의 저가치 유형 세 가지에 동시에 걸린다. 타 매체 트윗을 가져와 원문 링크로 돌려보내는 복제·집계 콘텐츠,
사이트 설명 자체가 "AI가 한국어로 번역하고 요약"이라고 적힌 자동 생성 콘텐츠, 그리고 100자짜리 페이지가
수천 개인 얇은 페이지 대량 생산이다.

문제가 아닌 것도 가려 뒀다. ads.txt는 승인됐고 내용도 정상이었다. 개인정보처리방침과 이용약관, FAQ가 200으로
서빙됐다. SSR이라 크롤러가 본문을 읽을 수 있었다. 소개·문의 페이지가 없는 건(404) 가점 요소지 거절 사유는 아니다.

## 콘텐츠 파이프라인은 못 건드린다는 제약

기사 본문을 길게 만드는 건 BE 요약 파이프라인과 콘텐츠 정책의 문제라 이번에 할 수 없었다. 대신 "구글이
보는 페이지 집합"을 바꾸는 쪽으로 갔다. 구글은 사이트의 모든 페이지가 훌륭해야 한다고 보지 않고, 색인
대상 페이지 집합이 가치 있는지를 본다. 그래서 얇은 페이지를 색인에서 빼고, 남는 페이지에 운영자가 쓴 긴 글을
채우고, 자동 생성을 자백하는 문구를 고치고, 심사 축이 다른 카카오 애드핏을 두 번째 광고망으로 붙였다.
네 가지를 한 브랜치에 넣었다.

## 1. 기사와 릴 상세를 noindex로, 사이트맵은 정적 목록으로

기사 상세(`/articles/[postId]`)와 릴 딥링크(`/reels/[postId]`)의 `generateMetadata`에
`robots: { index: false, follow: true }`를 넣었다. 두 앱 네 페이지다. `follow: true`를 남긴 이유는 기사
페이지가 팀 허브와 인물 페이지로 가는 크롤 경로이기 때문이다. 색인만 막고 링크는 따라가게 둔다. 공유 카드(OG)와
JSON-LD는 그대로라 카카오톡이나 X에 공유했을 때 보이는 건 바뀌지 않는다.

사이트맵은 두 앱 모두 BE 기사 전건을 커서 페이징으로 걸어와 싣던 루프를 통째로 지웠다. 그 호출 때문에
`export const dynamic = "force-dynamic"`이었는데 이제 BE를 안 부르니 빌드 때 한 번 굳는 정적 파일이 됐다.
KAN-380에서 걱정하던 45,000 URL 상한과 인덱스 분할 문제도 같이 사라졌다. 사이트맵에 남는 건 홈, 릴스·라이브·
투표 진입점, 팀 허브 6개, 팀 프로필 6개, 그리고 새로 만든 소개·가이드와 FAQ·약관·개인정보처리방침이다.
30개 안팎이다.

여기서 하나 걸리는 게 있다. 기사 페이지로 들어오던 검색 유입이 있었다면 noindex가 반영되는 몇 주에 걸쳐
그만큼 줄어든다. Search Console에서 기사 URL 유입 비중을 보고 판단해야 하는데 이번 세션에서는 보지 않았다.
애드센스 통과가 우선이라는 결정이었고, 기사 본문이 길어지면 되돌리면 된다.

`llms.txt`도 맞췄다. 전에는 "전체 기사 목록은 사이트맵에 있다"고 적었는데 이제 없으니 기사는 noindex라고
적고, 대신 운영자가 쓴 글 섹션에 소개와 가이드를 실었다. `seo-text` 테스트가 `/sitemap.xml` 포함을
검사하고 있어서 반대로 포함되지 않음을 검사하도록 바꿨다.

## 2. 운영자가 쓴 글: 소개, 가이드 둘, 팀 소개 여섯

글은 전부 `@plick/domain`에 데이터로 두고 두 앱이 같은 본문을 그린다. FAQ가 `faq.ts`와 `FaqBody`로 그렇게 돼
있어서 같은 틀을 따랐다. 새로 만든 것은 이렇다.

- `prose.ts`: 절(`ProseSection`) 하나가 소제목과 문단 배열, 끝의 관련 링크다. `proseText`가 평문으로
  펴 준다. 글자 수 검사와 llms.txt가 쓴다.
- `about.ts`: 소개 페이지. 무엇을 하는 서비스인지, 소식을 모으는 방법, 콘텐츠 원칙, 화면 구성, 운영자와
  문의처. 문의 이메일은 FAQ와 같은 상수여야 해서 `CONTACT_EMAIL`로 뺐다.
- `guides.ts`: 가이드 두 편. "루머 단계와 기자 신뢰도 읽는 법"은 RUMOUR, IN PROGRESS, CONFIRMED,
  OFFICIAL 네 단계가 각각 무슨 뜻인지와 기자·매체별로 무게를 어떻게 다르게 읽는지를 쓴 글이다.
  "이적 시장 용어 사전"은 윈도우와 데드라인 데이, 히어 위 고, 바이아웃과 릴리스 클로즈, 애드온과 셀온, 임대
  옵션과 의무, 보스만과 사전 계약, 메디컬, PSR과 홈그로운을 풀었다. 둘 다 1,000자를 넘긴다. `updatedAt`을
  두고 화면 끝에 "YYYY-MM-DD 기준으로 운영자가 손본 글입니다"를 적는다. 자동으로 쌓이는 요약과 사람이 쓴
  글을 구분해 보이려는 장치다.
- `team-intro.ts`: 팀 허브 여섯 개에 들어가는 팀 소개. 절이 셋이다. 구단이 어떤 곳인지(창단, 홈구장, 우승
  기록처럼 바뀌지 않는 사실), 이적 시장에서 보이는 경향(협상이 긴 토트넘, 장기 계약 대량 영입의 첼시처럼
  몇 년 단위로 유지되는 패턴), 이 허브에서 볼 것(어느 기자의 보도를 기준점으로 삼을지). 감독 이름이나
  이번 시즌 성적처럼 금방 낡는 내용은 일부러 넣지 않았다.

화면 쪽은 `@plick/ui`에 `ProseBody` 하나를 만들었다. 절마다 h2(또는 h3)와 문단, 링크 목록을 그리고
`updatedAt`이 있으면 끝에 적는다. 팀 소개는 팀 허브의 "{팀} 알아보기" h2 아래 들어가니 소제목이 h3여야
해서 `headingLevel` prop을 받는다.

페이지는 두 앱에 `/about`과 `/guide/[slug]`를 만들었다. 가이드는 `generateStaticParams`로 빌드 때 두 편을
미리 그린다. 모르는 slug는 404다. 웹이 canonical이고 모바일은 웹 URL을 canonical로 선언하는 기존 규약
(KAN-346, KAN-623)을 그대로 따랐다.

팀 소개는 `HomeScreen`의 기사 목록 아래, 하단 배너 위에 `team !== "ALL"`일 때만 그린다. 홈에서 팀 탭을
바꾸면 `history.replaceState`라 서버 컴포넌트가 다시 렌더되지 않는다. 그래서 탭을 바꿔도 팀 소개는
새로고침 전까지 처음 연 팀의 것이 남는다. h1이 이미 같은 성질이라 같은 선택을 했다. 크롤러가 보는 건 URL
기준 서버 렌더라 색인에는 영향이 없다.

링크는 웹 푸터, 모바일 홈 SEO 푸터, 모바일 MY 문서 링크에 소개와 가이드 둘을 넣었다. FAQ에도 세 항목을 더해
단계 표시의 뜻, 본문이 짧은 이유, 광고 여부를 답하면서 가이드와 소개로 링크했다.

## 3. "AI가 번역·요약"을 뺐다

`BRAND_DESCRIPTION`은 "해축이모는 해외 축구 기자들이 X에 올리는 프리미어리그 이적 루머와 이슈를 AI가
한국어로 번역, 요약해 보여주는 서비스입니다"였다. 심사자가 첫 화면 meta description과 푸터에서 읽는 문장이
자동 생성 콘텐츠라는 자백이었다. "해축이모는 프리미어리그 빅6의 이적 루머와 이슈를 해외 기자 보도 기준으로
모아 한국어로 정리하고 팀별 흐름을 해설하는 서비스입니다"로 바꿨다. 74자라 네이버 80자 권장(KAN-386) 안이다.
`homeIntroCopy`도 보도한 기자와 원문을 밝히고 루머 단계를 표시한다는 쪽으로 고쳤다. 거짓말을 넣은 게 아니다.
실제로 기자명과 매체, 원문 링크, 단계가 모든 소식에 붙어 있고 이번에 해설 글이 생겼다.

이게 되돌아오지 않게 `prose-content` 테스트가 브랜드 문안에 "AI가"와 "번역"이 없는지 검사한다. 글자 수
(소개·가이드 1,000자, 팀 소개 500자), description 80자, 문의 이메일이 FAQ와 소개에서 같은 값인지, FAQ
링크가 실제로 있는 경로만 가리키는지도 같은 파일이 본다.

## 4. 카카오 애드핏을 두 번째 광고망으로

애드센스는 "검색 사용자에게 고유한 가치가 있는가"를 보고, 애드핏은 "정상 운영 중인 국내 매체인가, 불법·성인
아닌가"를 본다. 글 깊이로 떨어뜨리는 비중이 작아서 지금 구조로도 통과 가능성이 애드센스보다 높다. 다만
애드핏 매체 기준에도 타인 콘텐츠 무단 게재와 콘텐츠 부족 항목이 있어서 확답은 아니고, 그래서 1~3을 같이
배포한 뒤 신청하기로 했다.

광고 자리 체계는 KAN-652 때 만든 게 있다. 자리(`AdPlacement`)마다 `AdUnit`이 있고 `AdSlot`이 모드
(`live`·`placeholder`·`off`)에 따라 그린다. 여기에 새 광고망을 따로 짜지 않고 `AdUnit`에 `adfit`(애드핏
단위 ID, DAN-으로 시작) 필드를 더했다. `slot`과 `adfit`이 둘 다 비면 live에서 안 그리고, 둘 다 있으면
애드핏이 먼저다. 애드센스가 미승인이라 번호가 있어도 안 채워지기 때문이다.

애드핏 로더(`ba.min.js`)는 애드센스와 동작이 다르다. 애드센스는 head에 로더 하나를 두고 상자마다
`adsbygoogle.push({})`로 요청을 넣는다. 애드핏 로더는 실행되는 시점에 DOM에 있는 `.kakao_ad_area` 상자를
찾아 채우고 끝이다. 나중에 마운트된 상자를 채우는 공개 API가 없다. 그래서 `AdfitBox`가 상자를 그린 뒤
`useEffect`에서 그 옆에 새 `<script>` 요소를 끼워 넣고, 내릴 때 `window.adfit.destroy(unitId)`를 부르고
스크립트를 뗀다. `destroy`는 로더 버전에 따라 없을 수 있어 옵셔널 체이닝이다. 경로가 바뀌면 `key={pathname}`
으로 상자가 새로 마운트되니 스크립트도 다시 들어간다. 이게 리액트 쪽 애드핏 래퍼들이 쓰는 방식이고 SPA에서
검증된 패턴이다.

크기는 애드핏이 폭도 고정 px를 요구해서 폭을 채우던 가로 배너 자리에 쓸 기본 폭이 필요했다. 웹은 728, 모바일은
320을 `ADFIT_BANNER_WIDTH`로 두고 `@plick/core/ads`의 `adfitSize`가 자리 크기와 합친다. 높이가 없는 전면
릴스는 애드핏 규격이 없어 `null`이고 애드센스 전용으로 남는다. 웹 레일 소형 배너(높이 60)도 PC 규격에 없어
남긴다. 단위 ID는 매체 심사 뒤 나오니 지금은 전부 빈 문자열이고, 그래서 이 브랜치가 배포돼도 prod의 광고
동작은 바뀌지 않는다. ID를 채우는 커밋이 실제 노출 시점이다.

## 검증

`pnpm format`, `lint`, `check-types`, `test:unit`(202개, 새 테스트 7개 포함), `test:hooks`, `format:check`가
전부 통과했다. 빌드와 화면 확인은 아래에 이어 적는다.

빌드(`pnpm build`)는 통과했고 라우트 표에서 `/about`이 ○(정적), `/guide/[slug]`가 ●(빌드 때 두 편
미리 그림), `/sitemap.xml`이 ○으로 잡혔다. 전에 사이트맵은 ƒ(요청마다)였다.

빌드 산출물로 `next start`를 띄워 봤다. 로컬 BE가 없어 기사 페이지는 404라 기사 noindex는 확인이 안
됐고, 그래서 `API_BASE_URL`을 prod BE로 준 `mobile-prodbe-alt`(3061)로 다시 띄웠다(ADR 0171 때 쓴
방법). 거기서 `/articles/10839`가 `<meta name="robots" content="noindex, follow">`를 냈다. 소개와 가이드,
팀 허브는 로컬 빌드가 prod 사이트가 아니라 루트 레이아웃의 `noindex, nofollow`가 그대로 붙어 있는데,
이건 KAN-380부터 dev 빌드의 의도된 동작이라 배포에서는 안 붙는다. 릴 딥링크는 prod BE로도 메타데이터
fetch가 실패해 기본 title이 나왔다. 이 세션 전부터 그랬는지는 보지 않았고, 코드는 기사와 같은 자리에
같은 값이라 따로 확인하지 않았다.

사이트맵은 두 앱 모두 22개 URL이 됐다(전에는 5,215개). 홈 description이 새 문구로 바뀌었고 팀 허브
`/teams/chelsea`에 "첼시 알아보기" h2 아래 세 절이 서버 렌더로 실렸다. 홈(전체)에는 없다. llms.txt에
"운영자가 쓴 글" 절과 noindex 안내가 들어갔다. 소개·가이드 화면은 두 앱에서 스크린샷으로 봤다.

## 헤드리스 리뷰가 잡은 것

`./scripts/review/pr-review.sh develop`은 CRITICAL 0, WARN 4였다. 셋은 고쳤고 하나는 남겼다.

첫째, 소개 글이 자동 요약이라는 사실을 감춘다는 지적. 브랜드 한 줄에서 "AI가 번역·요약"을 뺀 건 맞지만
소개 페이지까지 그 사실을 안 적으면 심사 통과를 위해 방식을 숨기는 문구가 된다. 그리고 "기자 이름과 매체,
원문 링크가 없는 소식은 싣지 않습니다"는 사실이 아니었다. 도메인 타입을 보면 `reporter`가 null일 수 있고
대표 원문도 없을 수 있다. 소개 글의 "소식을 모으는 방법"에 자동 번역과 요약(AI 보조)을 거친다고 적고,
원칙은 "매체와 원문 링크를 붙이고 기자가 확인되면 이름도 밝힌다"로 지킬 수 있는 말로 바꿨다.
`prose-content` 테스트에 소개 글이 "자동 번역과 요약(AI 보조)"을 포함하는지 검사를 더했다. 브랜드
한 줄과 홈 소개문에 "AI가"와 "번역"이 없는지 보는 검사는 그대로다. 그 둘은 서비스 정의 문장이고 방식 설명은
소개 페이지 몫이라는 분담이다.

둘째, 탭 전환 뒤 팀 소개가 옛 팀으로 남는다는 지적. 처음엔 h1과 같은 성질이라 두고 ADR에만 적었는데,
리버풀 허브에서 첼시 탭을 보는데 리버풀 소개가 붙어 있는 건 사용자에게 틀린 화면이다. `HomeIntro`가 이미
푸는 방식이 있었다. 클라 컴포넌트에서 `usePathname()`을 `teamFilterFromPathname`에 넣어 URL이 정한 팀을
읽는 것이다. Next의 `usePathname`은 `history.replaceState`를 가로채 동기화하므로 탭 전환도 따라온다.
`TeamIntro`를 그렇게 바꾸고 prop을 없앴다. SSR 첫 HTML은 요청 경로의 팀이라 크롤러가 보는 건 같다. 팀 소개
여섯 편(약 10KB)이 클라 번들에 실리는 비용이 생겼는데 팀 허브 전용이라 받아들였다. 검증은 prod BE로 빌드한
`next start`(3061)에서 했다. `/teams/liverpool`을 열면 "리버풀 알아보기", 첼시 탭을 누르면 URL이
`/teams/chelsea`로 바뀌며 "첼시 알아보기"로 갈리고, 전체 탭이면 소개가 사라졌다. h1은 "리버풀 이적 루머"로
남았다(기존 동작).

여기서 환경 함정 하나. 처음 `mobile-prodbe-alt`로 띄웠을 때 탭을 누르자 "This page couldn't load"가 떴다.
서버 fetch는 런타임 `API_BASE_URL`(prod BE)을 읽지만 브라우저가 부르는 `/api/*` 프록시 rewrite는 빌드 때
`.env.local`의 8082로 굳어 있어서, 클라 내비게이션의 API 호출이 전부 ECONNREFUSED였다. 기록대로
`API_BASE_URL=https://plick.co.kr/be pnpm --filter mobile build`로 다시 빌드하니 됐다.

셋째, `AdSlot`의 광고망 선택 분기에 테스트가 없다는 지적. `adNetworkFor(unit)`를 `@plick/core/ads`로
빼서 애드핏 ID가 먼저, 다음 애드센스 번호, 둘 다 비면 null을 돌려주게 하고 테스트를 붙였다. `AdSlot`은
그 결과로 분기한다.

남긴 건 애드핏 로더를 마운트마다 다시 끼워 넣는 방식의 검증이다. 한 화면에 상자가 여럿이면 로더가 여러 번
돌고, dev Strict Mode에서는 effect가 두 번 돈다. 정리 함수가 스크립트를 떼고 `destroy`를 부르니 Strict
Mode 쪽은 괜찮을 것으로 보지만, 단위 ID가 전부 빈 문자열이라 지금은 코드가 실행되지 않고 ID를 채우는
커밋에서 처음 드러난다. 그때 dev에서 중복 노출을 보고 필요하면 가드를 둔다.
