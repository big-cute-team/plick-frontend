# 0208. 이미지를 끌면 따라다니는 반투명 복제본 걷어내기 (KAN-677)

## 티켓

KAN-677은 제목 한 줄짜리다. 앱 안 이미지를 누른 채 끌면 그 이미지가 투명해져서 손가락이나 커서를 따라다닌다는
것. 본문은 비어 있었다. `develop`(KAN-676 머지 직후)에서 `feature/KAN-677-image-drag-ghost`를 땄다.

시작 전에 범위 두 가지를 정했다. 모바일과 웹 둘 다 막는다. 대상은 이미지만이고 텍스트 링크를 끌어서 새 탭에
떨구는 데스크톱 동작은 남긴다. iOS에서 이미지를 길게 누르면 뜨는 미리보기와 저장 메뉴(callout)는 티켓 범위가
아니라 그대로 둔다.

## 그 반투명 복제본의 정체

브라우저의 기본 드래그 앤 드롭이다. HTML에서 `<img>`와 `href`가 있는 `<a>`는 따로 아무것도 하지 않아도 끌 수
있는 요소다. 마우스를 누른 채 몇 픽셀 움직이면 브라우저가 `dragstart` 이벤트를 쏘고, 끌리는 요소를 스냅숏으로
떠서 반투명하게 만든 "드래그 이미지"를 포인터 밑에 붙인다. 이미지를 다른 창이나 바탕화면에 떨구면 파일로
저장되는 그 기능이다. 우리 앱에서는 쓸 일이 없고 카드를 스와이프하거나 누르려다 살짝 밀리면 이게 떠서
이상해 보인다. 모바일 웹뷰에서도 같다. iOS 15 이후 WebKit은 아이폰에서도 길게 누른 뒤 끌면 드래그를 시작하고,
안드로이드 크로미움 웹뷰도 드래그 앤 드롭을 지원한다.

이 기본 동작을 끄는 방법은 셋이다. 요소에 `draggable="false"` 속성을 다는 것, `dragstart`에서
`preventDefault()`를 부르는 것, CSS `-webkit-user-drag: none`을 거는 것. 마지막은 이름에 접두어가 붙어 있지만
WebKit과 크로미움이 둘 다 아는 속성이다. Firefox만 모른다.

## 첫 시도: 전역 CSS 한 블록

이미지가 수십 군데에 흩어져 있어 하나하나 `draggable`을 다는 건 새 이미지가 생길 때마다 잊어버리기 좋다. 두
앱이 똑같이 import하는 `packages/tokens/theme.css` 리셋 구역에 규칙 하나를 넣었다.

```css
img,
a:has(img) {
  -webkit-user-drag: none;
}
```

`a:has(img)`까지 넣은 이유가 있다. 크로미움은 드래그를 시작할 요소를 정할 때 누른 지점의 요소부터 위로
올라가며 끌 수 있는 첫 조상을 찾는다. `img`만 막으면 그 위의 `<a>`가 걸려 링크 드래그가 시작되고, 링크
드래그 이미지에도 그 안의 사진이 찍혀 나온다. 결국 사진을 감싼 링크도 같이 막아야 한다. 텍스트만 든 링크는
`:has(img)`에 안 걸리니 그대로 끌린다.

이 규칙은 Tailwind의 `@layer` 밖에 있다. theme.css 주석이 경고하듯 레이어 밖 규칙은 유틸리티를 이긴다.
여기서는 `-webkit-user-drag`를 쓰는 유틸이 하나도 없으니 덮어쓸 상대가 없어 문제가 안 된다.

모바일 dev 서버를 prod BE에 붙여 띄우고 확인했다. 홈의 이미지 17장 계산값이 전부 `none`, 사진을 품은 링크도
`none`, 텍스트 링크는 `auto` 그대로였다. 여기까진 맞았다.

## 막힌 곳: 사진을 덮기만 하는 링크

계산값 말고 실제로 끌어 봐야 했다. 문서에 `dragstart` 리스너를 캡처 단계로 걸어 두고 브라우저 패널에서 핫이슈
카드 사진 위를 눌러 끌었다. 첫 시도는 좌표가 빗나가 상단 배너를 끌었다. 스크린숏 좌표계(800 폭)와 페이지 CSS
픽셀(1024 폭)이 달라서였고, 비율을 곱해 다시 잡았다.

두 번째에는 `dragstart`가 떴다. 대상이 `A`였다. 그 지점의 요소를 `elementFromPoint`로 꺼내 보니 사진이 아니라
비어 있는 `<a class="absolute inset-0">`였다. 핫이슈 카드(`HotHeroCard`)는 카드 전체를 링크로 만들되 그 안에
팀 프로필로 가는 링크가 또 있어서, 앵커 중첩을 피하려고 기사 링크를 카드 맨 끝에 형제로 깔고
`absolute inset-0`으로 카드 위를 덮는 구조다(흔히 stretched link라고 부른다). 사진은 그 링크 밑에 깔려 있을
뿐 링크의 자식이 아니다. 그래서 `a:has(img)`에 걸리지 않고, 누른 지점의 최상단 요소인 이 링크가 기본값대로
끌렸다.

같은 구조가 또 있는지 찾았다. `absolute inset-0`이나 `after:absolute after:inset-0`으로 덮는 링크는 네 곳이었다.
모바일 `HotHeroCard`와 웹 `HotCard`는 사진을 덮고, 모바일 `NewsItem`과 웹 `PostListItem`은 목록 행을 덮지만
행 안에 이미지가 없다. 이미지 드래그 문제는 앞의 둘뿐이다.

CSS로 일반화하는 길도 생각했다. 비어 있는 링크를 `a:empty`로 잡거나 "사진이 있는 카드 안의 링크"를
`:has()`로 엮는 식이다. 그런데 이건 마크업 모양에 기대는 추측이라 다음 사람이 링크 안에 스크린 리더용 텍스트
하나만 넣어도 조용히 풀린다. 두 곳뿐이니 해당 링크에 `draggable={false}`를 직접 달고 JSDoc에 이유를 남겼다.
`ArticleLink`는 `next/link`의 나머지 props를 그대로 넘기므로 `<a draggable="false">`로 렌더된다. 속성이라
Firefox에서도 먹는다는 덤이 있다.

## 확인

바꾼 뒤 같은 카드 사진을 다시 끌었을 때 `dragstart`는 한 번도 안 떴고 주소도 그대로였다. 화면 단위로도 훑었다.
페이지의 모든 `<img>`를 화면 가운데로 스크롤해 그 중심점에 있는 요소를 꺼내고, 그게 링크면 링크가, 이미지면
이미지가 끌 수 있는 상태인지 검사하는 스크립트를 돌렸다. 모바일 홈 17장, 기사 세부 6장, 릴스 7장, 웹 홈
17장 모두 끌리는 것이 없었다. 웹 홈 텍스트 링크는 여전히 `auto`에 `draggable`이 참이라 새 탭으로 끄는 동작은
살아 있다.

검사 중 하나 막힌 게 있었다. 처음 스크립트는 스크롤 뒤 `requestAnimationFrame`으로 한 프레임을 기다렸는데
45초 타임아웃이 났다. 브라우저 패널이 숨어 있으면 페이지가 백그라운드 탭 취급을 받아 rAF가 아예 돌지 않는다.
`setTimeout`으로 바꾸니 바로 끝났다.

## 남은 것

Firefox 데스크톱은 `-webkit-user-drag`를 모른다. 덮는 링크 두 곳은 `draggable` 속성이라 막히지만, 링크 밖에
있거나 링크가 품은 일반 이미지는 Firefox에서 여전히 끌린다. 모바일 앱 셸은 WebKit과 크로미움 웹뷰라 상관없고,
티켓이 앱 기준이라 이번엔 넘겼다. 필요해지면 루트 레이아웃 클라 컴포넌트에서 `dragstart`를 캡처해 대상이 이미지거나 이미지를 품은
링크일 때 `preventDefault()`를 부르면 브라우저 구분 없이 막힌다.
