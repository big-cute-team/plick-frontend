# 0049. web API 이식을 위한 도구 세팅 — /web-wire-api 커맨드와 web-wiring 참조 문서

## 배경

모바일(apps/mobile)은 UI/UX 수정과 API 연결이 전부 끝났다. 홈 피드, 핫이슈, 기사 상세, 댓글, 릴스,
인증, 프로필, 온보딩, 좋아요, 조회수까지 mock이 하나도 안 남았다. 이제 이걸 그대로 데스크톱 웹(apps/web)에도
붙일 차례다. 이번 세션은 그 작업 자체를 한 게 아니라, 그 작업을 반복할 때 쓸 커맨드와 스킬 문서를 만들었다.

모바일 때도 같은 구조를 썼다. `/wire-api` 커맨드가 절차를 잡고, `api-integration` 스킬이 규칙을 들고,
`be-verify` 서브에이전트가 로컬 BE에 직접 붙어 계약을 검증했다. 화면 퍼블리싱 쪽도 모바일 `/screen`과
웹 `/web-screen`으로 나뉘어 있다. 그러니 API 연결도 웹 전용 커맨드를 하나 더 만드는 게 자연스러웠다.

## 전수조사에서 알게 된 것

문서를 쓰기 전에 코드베이스를 전수조사했다. Explore 에이전트한테 모바일 데이터 레이어 인벤토리,
웹 현재 상태, 두 앱의 도메인 겹침, be-verify 도구, 관련 ADR 목록을 통째로 조사시켰다.
여기서 나온 사실들이 문서의 뼈대가 됐다.

가장 큰 발견은 이 단계의 성격이 모바일 때와 다르다는 것이다. 모바일을 붙일 때는 계약의 진실이
스웨거였고, 그 스웨거조차 실제와 달랐던 전례(ADR 0025, 0026) 때문에 be-verify가 매번 실제로 때려서
확인했다. 그런데 그 검증의 결과물이 지금 모바일 코드에 다 굳어 있다. `_services/` 각 fetcher의
BE 응답 타입과 경계 변환, `_types/`의 도메인 타입, `_constants/api.ts`의 매핑 테이블이 그것이다.
웹에 같은 엔드포인트를 붙일 때는 스웨거를 다시 뒤질 게 아니라 모바일 코드를 읽는 게 맞다.
계약의 출처가 바뀐 것이다. be-verify가 필요 없어진 건 아니고, 모바일이 안 붙인 새 엔드포인트나
BE가 바뀐 의심이 들 때, 뮤테이션 DB 반영을 다시 볼 때로 역할이 좁아졌다.

두 번째 발견은 웹이 ADR 0011 게이트 C의 "두 번째 실사용처"라는 점이다. 공용화 판단은 줄곧
"첫 앱에선 앱별로 붙이고, 두 번째 앱이 같은 shape를 쓸 때 승격을 판단한다"였고, 모바일 코드 주석들이
"web이 같은 API를 붙이면 그때 판단한다"고 예고까지 해 뒀다. 그 시점이 바로 지금이다. `apiFetch`와
`ApiError`, 계약 타입 다섯 파일, 팀 id 매핑 상수, 쿼리키 규약이 전부 승격 후보로 한꺼번에 올라온다.
심지어 `query-client.ts`는 웹에 동일한 복제본이 이미 있다. 그래서 웹 이식 커맨드는 승격 판단을
절차의 곁가지가 아니라 본편으로 다루게 썼다.

재미있는 역전도 하나 있었다. 웹은 전 화면 컴포넌트 13개가 `@plick/domain`의 `FeedPost`를 소비하는데,
모바일은 API를 붙이는 과정에서 이 타입을 이미 버렸다. 실제 계약이 다르게 생겼기 때문이다. 팀이 단일이
아니라 배열이고, `timeLabel` 같은 표시용 문자열 대신 ISO `publishedAt`이 오고, `stage`와 `reporter`가
nullable이다. 그래서 모바일은 `ArticleCard`, `HotArticle`, `ArticleDetail` 같은 실계약 타입으로 갈아탔다.
공용 패키지에 있는 타입이 오히려 낡은 쪽이고, 앱 로컬 타입이 진실인 상태다. 웹 이식은 화면을 하나
붙일 때마다 이 `FeedPost`를 실계약 타입으로 걷어내는 작업을 동반하고, 마지막 소비자가 사라지는 PR에서
`FeedPost`와 부속 타입을 domain에서 지우는 것까지가 끝이다.

그 밖에 웹에서 걸릴 함정들을 조사에서 미리 캤다.

- 프로필이 `User.myTeam` 단일에서 `MyProfile.myTeams` 다중으로 바뀐다. `me`, `me/edit`, `onboarding/team`
  세 화면이 단일 팀 전제로 짜여 있어서 화면 구성을 다시 정해야 한다.
- 웹 mock 중 `NOTIF_COUNT`(알림 뱃지)와 `TRENDING_POSTS`(실시간 인기)는 대응하는 BE 엔드포인트 자체가
  없다. 계약 공백이라 숨길지 hot으로 대체할지 판단이 필요하다.
- OAuth redirect_uri가 웹 dev 포트(3000) 기준이라 모바일(3001)과 다르다. 카카오와 구글 콘솔에 추가
  등록해야 하는데, ADR 0023이 정확히 이 redirect_uri 불일치로 로그인이 깨졌던 기록이다. 같은 데서
  두 번 넘어지지 않게 문서에 박아 뒀다.
- 미들웨어 파일 이름이 `middleware.ts`가 아니라 `proxy.ts`다. Next 16에서 개명됐고 export 이름도
  `proxy`다. 모바일이 이미 겪은 거라 웹에 새로 깔 때 헷갈리지 않게 적어 뒀다.
- 웹 레이어 폴더(`_apis/`, `_services/` 등)는 ADR 0029 때 `.gitkeep`만 넣어 이미 준비돼 있다.

## 무엇을 만들었나

새 스킬을 만들지, 기존 `api-integration` 스킬에 얹을지 고민했다. 규칙의 대부분(env, `apiFetch`,
fetcher 배치, RQ 도입 기준, 상태 처리)은 앱과 무관하게 동일해서 스킬을 쪼개면 같은 내용이 두 벌이 된다.
그래서 스킬은 하나로 두고 참조 문서를 하나 추가하는 쪽으로 갔다. 스킬에는 이미 `data-layer.md`와
`tanstack-query.md`라는 참조 파일 구조가 있어서 거기에 `web-wiring.md`를 나란히 놓았다.
달라진 것만 담았다. 계약 출처, 승격 후보 목록, 웹 신규 인프라, 화면 함정, 이식 순서.

커맨드는 `/web-wire-api`를 새로 만들었다. `/wire-api`를 인자 분기로 겸용시킬 수도 있었지만,
화면 쪽이 이미 `/screen`과 `/web-screen`으로 나뉜 관례가 있고, 절차 자체가 다르다.
모바일 커맨드는 "be-verify에 위임 → 타입 대조"로 시작하는데 웹 커맨드는 "모바일 코드 읽기 → 승격 판단"으로
시작한다. 섞으면 두 흐름 다 흐려진다.

서버 액션(`"use server"`) 파일은 승격 후보에서 뺐다. 쿠키 이름과 redirect 경로가 앱에 박혀 있기도 하고,
파일이 얇아서 앱별로 복제하는 비용이 싸다. 승격은 되돌리기 비싸고 복제는 싸다는 기존 원칙 그대로다.

이식 순서는 모바일 연결 순서를 그대로 따르지 않고 바꿨다. 모바일은 인증부터 붙였지만, 웹은 화면이
익명으로도 도는 읽기(홈 피드, 상세, 릴스)부터 붙이고 인증을 그 다음, 뮤테이션을 마지막에 뒀다.
읽기 엔드포인트들이 익명 허용이라 인증 없이도 화면이 완성되고, 첫 PR이 승격 판단의 대부분을
만나게 되어 공용화가 초반에 정리된다.

중간에 피드백을 하나 받았다. 처음엔 티켓이 없다길래 커맨드 인자를 엔드포인트만 받게 썼는데,
티켓도 넣을 수 있게 해 달라고 해서 선택 인자로 바꿨다. 티켓이 있으면 브랜치와 커밋에 Jira 키를 넣고,
없으면 `feature/web-<설명>` 브랜치에 키 없는 커밋으로 간다.

## 결과물

- `.claude/commands/web-wire-api.md` 신규. 웹 이식 절차 8단계와 원칙.
- `.claude/skills/api-integration/web-wiring.md` 신규. 웹 단계에서 달라지는 것 전부.
- `.claude/skills/api-integration/SKILL.md` 수정. 참조 목록에 web-wiring 추가, be-verify 위임 원칙에
  웹 예외 명시.
- `.claude/commands/wire-api.md` 수정. 웹 이식이면 `/web-wire-api`로 가라는 안내 한 줄.
- `CLAUDE.md` 더 읽을 것 수정. 두 커맨드와 web-wiring 문서 연결.

`be-verify` 서브에이전트는 손대지 않았다. 역할이 좁아진 건 부르는 쪽 조건의 문제지 에이전트 자체의
문제가 아니어서, 호출 조건은 커맨드와 web-wiring에 두고 에이전트 정의는 그대로 뒀다.

다음 세션부터 `/web-wire-api 홈 피드`처럼 부르면 된다. 첫 PR에서 rewrites와 env 인프라를 같이 깔고,
`apiFetch`와 계약 타입, 매핑 상수의 승격 판단부터 하게 될 것이다.
