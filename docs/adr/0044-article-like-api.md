# 0044 — 기사·릴스 좋아요 API 연결 (KAN-308)

- 상태: Accepted
- 날짜: 2026-07-27
- 범위: `apps/mobile`. 좋아요 등록·취소(`POST`·`DELETE /api/v1/articles/{articleId}/like`)를 릴스
  액션 레일과 기사 세부 버튼에 붙이고, 홈 목록에 좋아요 수를 표시한다. 읽기 요청에 토큰을 실어
  `likedByMe`가 실제 값으로 오게 하는 인증 배관과 `middleware.ts` → `proxy.ts` 이름 변경도 포함한다.

  [ADR 0011 공용 경계](0011-shared-code-boundary.md) · `api-integration` 스킬

## 티켓에 적힌 메서드가 틀렸다

티켓 제목은 `[FE] GET,DELETE /api/v1/articles/{articleId}/like`였다. 늘 하던 대로 `be-verify`
서브에이전트에 계약 확인을 맡겼는데, 첫 줄부터 티켓과 어긋났다. 실제로는 `POST`와 `DELETE`만 있고
`GET`은 핸들러가 아예 없다. 없는 걸 부르면 405도 아니고 500 `COMMON_INTERNAL_ERROR`가 온다.

좋아요 상태를 조회하는 API가 따로 없다는 뜻이라 처음엔 당황했는데, 기사 응답을 보니 이유가 있었다.
목록(`GET /api/v1/articles`), 상세(`GET /api/v1/articles/{id}`), 릴스(`GET /api/v1/reels`) 세 응답이
전부 `likeCount`와 `likedByMe`를 들고 있다. 초기 상태는 기사를 받을 때 같이 오고, 토글 결과는
POST·DELETE 응답이 알려주니 상태 조회 API가 있을 자리가 없다. 티켓 제목의 `GET`은 그 `likedByMe`를
읽는다는 뜻을 메서드로 잘못 옮겨 적은 것으로 보인다. 사용자에게 확인하니 POST·DELETE가 맞다고 했다.

응답은 두 메서드 모두 봉투를 벗기면 `{ "likeCount": 1 }` 하나다. 그리고 둘 다 멱등이다. 이미 누른
기사에 POST를 또 보내도, 안 누른 기사에 DELETE를 보내도 409가 아니라 200에 현재 카운트가 온다.
이건 낙관적 갱신을 짜는 데 꽤 큰 선물이었다. 중복 상태 분기를 안 만들어도 되고, 재시도가 카운트를
어긋나게 만들지도 않는다.

에러는 401 `AUTH_REQUIRED`(비로그인)와 404 `ARTICLE_NOT_FOUND`(없는 기사) 둘이다.

용어를 하나 풀어 두면, 멱등(idempotent)은 같은 요청을 몇 번 보내도 결과 상태가 같다는 뜻이다.
"좋아요를 1 증가시켜라"가 아니라 "좋아요를 켜진 상태로 만들어라"에 가깝다. 그래서 네트워크가
불안해 같은 요청이 두 번 나가도 카운트가 2씩 오르지 않는다.

## 서버 액션으로 감싼 이유

토글은 보호 API라 `Authorization: Bearer …`가 필요한데, access 토큰은 HttpOnly 쿠키에 있다.
HttpOnly는 브라우저 JS가 `document.cookie`로 읽을 수 없다는 뜻이라, 클라 컴포넌트는 스스로 헤더를
만들 수 없다. 그래서 댓글 작성(ADR 0042)에서 쓴 방식을 그대로 따랐다. `"use server"` 파일에
`likeArticle`·`unlikeArticle`을 두고, 그 안에서 `cookies()`로 토큰을 꺼내 BE를 부른다.

여기서 헷갈리기 쉬운 게 `"use server"`다. 이건 "서버에서 실행"이라는 일반적인 표시가 아니라 서버
액션 선언이다. 파일의 export가 전부 async 함수여야 하고, 클라가 그 함수를 import해 호출하면 Next가
그 자리에 POST 요청을 심어 준다. 함수 본문은 서버에서 돌고 반환값만 직렬화돼 돌아온다. 그래서
`_types/articles.ts`에 결과 타입을 따로 뺐다 — 같은 파일에 타입이나 상수를 두면 export 규칙에 걸린다.

실패는 던지지 않고 값으로 돌려준다. 서버 액션이 던진 에러는 프로덕션에서 메시지가 가려져
("An error occurred in the Server Components render") 클라가 BE 에러 code로 분기할 수 없기 때문이다.
`{ ok: false, status, code, message }`로 넘기고 클라 훅이 `ApiError`로 되살려 던진다. 이것도 댓글에서
한 번 겪고 정한 규약이라 그대로 재사용했다.

## 상태를 훅이 들지 않기로 한 것

처음엔 `useArticleLike`가 liked와 likeCount를 자기 state로 들게 짰다. 그런데 릴스에 붙이자마자
깨졌다. 릴을 몇 장 넘겼다가 돌아오면 하트가 도로 비어 있었다.

원인은 릴 카드의 원본이 컴포넌트가 아니라 TanStack Query의 무한 쿼리 캐시라는 데 있었다.
`ReelItem`은 캐시에서 내려온 `reel` prop을 그릴 뿐이라, 훅이 자기 state를 바꿔 봐야 다음 리렌더에
캐시 값이 다시 덮는다. 반대로 기사 세부는 캐시가 없고 서버가 준 props가 원본이라 state가 맞다.

그래서 훅에서 상태를 걷어내고 `onChange` 콜백으로 되돌려주는 모양으로 바꿨다.

```ts
useArticleLike({ articleId, state: { liked, likeCount }, onChange });
```

호출부가 자기 원본에 반영한다. 릴스는 `useReelLike`가 `setQueryData`로 캐시의 해당 아이템을 고치고,
기사 세부는 `ArticleLikeButton`이 `setState`를 그대로 넘긴다. 훅은 "언제 무엇으로 바꿔야 하는가"만
알고 "어디에 쓰는가"는 모른다.

낙관적 갱신(optimistic update)은 서버 응답을 기다리지 않고 화면부터 바꾸는 방식이다. 순서는 셋이다.

1. `onMutate` — 누른 즉시 하트를 채우고 카운트를 ±1 한다. 그리고 **되돌릴 값을 여기서 찍어 반환한다**.
2. `onSuccess` — BE가 계산한 `likeCount`로 덮는다. 그 사이 다른 사람이 누른 것까지 반영된다.
3. `onError` — 1에서 찍어 둔 값으로 되돌린다.

3번에서 한 번 틀렸다. 처음엔 `onError` 안에서 클로저에 잡힌 `state`를 그대로 되돌렸는데, 그때는 이미
`onMutate`가 낙관적 값으로 리렌더를 일으킨 뒤라 "낙관적 값으로 되돌리는" 꼴이었다. 실패해도 하트가
채워진 채 남는다. TanStack Query가 `onMutate`의 반환값을 `onError`의 세 번째 인자로 넘겨주는 게
정확히 이걸 위한 장치라, 문서대로 컨텍스트를 쓰는 걸로 고쳤다.

응답이 오기 전에는 다시 못 누르게 `isPending`으로 막았다. 멱등이라 서버 상태가 망가지진 않지만,
늦게 온 응답의 카운트가 화면을 덮으면 숫자가 튄다. 로컬에서는 왕복이 짧아 막힌 느낌이 없다.

## 눌러 보니 로그인 팝업이 릴 한 조각만 덮었다

비로그인 상태에서 하트를 누르면 댓글과 같은 `LoginPromptDialog`를 띄우기로 했는데, 릴스에서 띄우니
팝업이 화면 전체가 아니라 액션 레일 크기로 뜨는 이상한 그림이 나왔다.

이유는 CSS의 containing block 규칙이었다. `position: fixed`는 보통 뷰포트를 기준으로 자리를 잡지만,
조상 중에 `transform`이나 `filter`가 걸린 요소가 있으면 **그 요소가 기준 상자가 된다**. 액션 레일에는
`drop-shadow`(=`filter`)가 걸려 있어서 `inset-0`이 화면이 아니라 레일에 맞춰진 것이다. 릴 세부 시트도
`translateY`로 오르내리니 같은 함정이 있었다 — 거기서 쓰는 댓글 입력바의 로그인 팝업도 사실 같은
문제를 갖고 있었을 텐데 눈치채지 못하고 있었다.

`LoginPromptDialog`를 `createPortal(…, document.body)`로 바꿔 한 번에 해결했다. 포털은 리액트 트리
상으로는 제자리에 있으면서 실제 DOM 노드만 다른 곳에 붙이는 기능이다. body 밑으로 나가면 위의
조상들과 무관해지므로 어디서 부르든 화면 전체를 덮는다. 서버 렌더에는 `document`가 없으니 마운트
뒤에만 그리도록 가드를 뒀다.

문구도 상황에 맞게 받도록 `description` prop을 열었다. 좋아요에서 "댓글은 로그인한 사용자만 남길 수
있어요"가 뜨면 안 되니까.

## 읽기에 토큰을 실어야 했다 — 서버와 브라우저가 각자 다른 방식으로

여기가 이번 작업에서 제일 오래 걸린 부분이다.

기사·릴스 조회는 익명 허용 API라 지금까지 토큰을 일부러 싣지 않았다(ADR 0030). 그런데 `likedByMe`는
토큰이 있을 때만 그 유저 기준으로 계산되고, 없으면 무조건 false다. 그대로 두면 좋아요를 누르고
새로고침했을 때 카운트만 1이고 하트는 비어 있다. 그래서 읽기에도 토큰을 실어야 했다.

문제는 같은 fetcher를 서버와 브라우저가 함께 부른다는 것이다. 두 경로는 BE에 닿는 길 자체가 다르다.

- **서버 컴포넌트**: `API_BASE_URL`로 BE를 직접 부른다. `cookies()`를 읽을 수 있으니 호출부가 토큰을
  꺼내 `getArticle(id, accessToken)`처럼 넘기면 된다. `_services/session.ts`에 `getAccessToken()`을 뒀다.
- **브라우저**: same-origin 프록시 `/be/*`를 부른다(CORS를 없애려고 KAN-271에서 깐 rewrites다).
  쿠키는 same-origin이라 자동으로 실려 가지만 HttpOnly라 JS가 못 읽고, BE는 쿠키가 아니라 Bearer
  헤더만 본다. 그래서 클라 코드는 헤더를 만들 방법이 없다.

브라우저 쪽을 어떻게 할지 한참 고민했다. 릴스 다음 페이지를 서버 액션으로 감싸는 안도 생각했는데,
서버 액션은 POST RPC라 읽기에 쓰기엔 결이 안 맞고 직렬화돼 실행된다. 결국 `/be` 요청이 rewrites로
넘어가기 **전에** 지나가는 자리, 즉 미들웨어에서 헤더를 심는 쪽을 택했다. 쿠키를 읽을 수 있고,
`NextResponse.next({ request: { headers } })`로 바꾼 요청 헤더가 프록시 대상까지 그대로 간다.

동작할지 확신이 없어서 브라우저에서 직접 때려 봤다.

```js
fetch("/be/api/v1/articles/6633").then((r) => r.json());
// → { code: "OK", likeCount: 1, likedByMe: true }
```

토큰 없이는 절대 true가 나올 수 없는 값이라 이걸로 확인됐다.

만료 토큰을 실어 401로 화면이 죽는 걱정은 없다. 이 앱은 access 쿠키의 수명(15분)을 토큰 만료 신호로
쓰기 때문에(ADR 0021) 만료되면 쿠키 자체가 사라지고, 그러면 서버는 `undefined`를, 프록시는 헤더 없이
익명 요청을 보낸다. 공개 API라 익명이어도 200이 온다.

미들웨어에서 하나 고친 게 있다. refresh까지 실패하면 원래 무조건 `/login`으로 리다이렉트했는데,
`/be` 요청은 그러면 안 된다. 응답을 JSON으로 파싱하는 fetch에 로그인 페이지 HTML을 물리면 엉뚱한
파싱 에러로 죽는다. 프록시 요청은 쿠키만 지우고 익명으로 통과시키게 나눴다.

### 인증 응답은 캐시에 넣지 않는다

토큰을 싣기 시작하면서 하나 더 챙겨야 할 게 생겼다. Next의 데이터 캐시는 유저 구분 없이 URL 단위로
공유된다. 인증 응답이 거기 들어가면 한 사람의 `likedByMe`가 같은 주소를 부른 다른 사람에게 그대로
나갈 수 있다. 기본 캐시 동작에 기대지 않고 `apiFetch`에서 못박았다 — `Authorization` 헤더가 있으면
`cache: "no-store"`를 강제한다. 인증 호출 하나하나에서 기억해 붙이는 것보다 래퍼가 규칙으로 들고
있는 게 안전하다.

## 서버 번들이 안 갱신돼 한참 헤맸다

릴스에 좋아요 색을 입히고 나서 콘솔에 하이드레이션 불일치 경고가 떴다. 서버가 그린 하트 버튼은
`text-media-on`(안 누름)인데 클라가 그린 건 `text-accent`(누름)라는 것이었다.

처음엔 위에서 말한 데이터 캐시를 의심했다. 토큰 붙이기 전 익명 응답이 캐시에 남아 서버 렌더만 옛날
값을 쓰는 그림이 그럴듯했다. `cache: "no-store"`를 넣고 다시 봤는데 그대로였다.

curl로 서버 HTML을 직접 뜯어 보고 나서야 진짜 원인이 보였다. 그 버튼에는 `aria-label="좋아요 취소"`가
붙어 있었다. 그건 `liked`가 true일 때만 나오는 값이다. 즉 **데이터는 이미 맞게 오고 있었고**, 같은
버튼의 className만 옛날 값이었다. 데이터가 아니라 코드가 낡은 것이다.

dev 서버의 HMR이 클라 번들은 갱신했는데 서버 번들은 `active` prop을 추가하기 전 상태로 물고 있었다.
파일을 touch해도 안 풀려서 dev 서버를 재시작했더니 한 번에 정상이 됐다. 재시작 후 서버 HTML에서
30개 버튼 중 정확히 1개만 `text-accent`로 나왔다 — 좋아요를 누른 그 기사다.

교훈은 둘이다. 하나, 하이드레이션 불일치를 보면 데이터부터 의심하지 말고 **서버가 실제로 내려준
HTML을 직접 확인**할 것. 브라우저 devtools 말고 curl이 빨랐다. 둘, 원인을 오해한 채로 남긴 주석은
지운다. `cache: "no-store"`는 그 자체로 옳아서 남겼지만, "이 사건 때문에 넣었다"고 적어 둔 주석은
사실이 아니라 고쳤다.

## 홈 목록의 하트가 줄마다 다르게 뭉갰다

티켓 2번은 홈 기사 목록에 좋아요 수를 보여주는 것이었다(누르는 건 없음). 처음엔 이웃한 `조회 0`,
`댓글 3`과 같은 결로 `좋아요 1`이라고 글자로 넣었는데, 사용자가 하트 아이콘 + 숫자로 바꿔 달라고 했다.

바꾸고 나니 어떤 줄은 하트가 반 픽셀 내려앉은 것처럼 보인다는 피드백이 왔다. 브라우저를 확대하면
멀쩡하고 작을 때만 그랬다.

측정해 보니 레이아웃은 모든 줄이 완전히 같았다. svg 상자의 중심과 글자 상자의 중심이 소수점까지
일치했다. 다른 건 페이지 안에서의 절대 위치뿐이었다 — 478.22, 562.78, 647.34처럼 소수점 자리가
줄마다 달랐다. 캡션 글자에 맞춘다고 아이콘을 11px로 줄인 게 문제였다. `HeartMiniIcon`은 선(stroke)
아이콘이고 선 두께가 뷰박스 기준 0.5958이라, 11px로 그리면 실제 선이 0.92px다. 1px보다 얇은 선은
픽셀 격자에 딱 못 앉아서 줄의 소수점 위치에 따라 어떤 줄은 위 픽셀에, 어떤 줄은 아래 픽셀에 더 많이
번진다. 그게 "어떤 건 내려가 있다"로 보인 것이다.

아이콘 기본 크기(13px)로 되돌리니 선이 1.08px가 되어 모든 줄이 또렷해졌다. 기사 세부의 좋아요
알약이 멀쩡했던 것도 거기선 15px로 쓰고 있어서였다. 작은 선 아이콘은 설계 크기보다 줄이지 않는 게
낫다는 걸 배웠다.

내가 눌렀는지는 목록에서 칠하지 않는다. 목록 응답은 서버에서 익명으로 받아 `liked`가 늘 false라
칠하면 거짓말이 된다. 누르는 자리도 아니니 수만 보여준다.

## middleware.ts를 proxy.ts로

작업 중에 사용자가 dev 서버 경고를 물어봤다. Next 16에서 `middleware` 파일 규칙이 deprecated되고
`proxy`로 이름이 바뀌었다는 안내였다. 마침 그 파일을 고치고 있어서 같이 옮겼다.

바뀌는 건 파일명과 export 이름 둘뿐이다(`middleware` → `proxy`). `config`도, `NextRequest`/
`NextResponse`도 그대로다. 이름을 바꾼 이유는 Express의 미들웨어와 혼동돼 남용된다는 것이고,
"앱 앞에 놓인 네트워크 경계"라는 실제 역할에 맞춰 프록시로 부르기로 했다는 설명이다. 마침 이번에
그 파일이 하게 된 일이 정확히 프록시 요청에 헤더를 실어 주는 것이라 이름이 더 맞게 됐다.

한 가지 헤맨 건, 파일만 옮기고 export 이름을 안 바꾼 중간 상태에서 "Proxy is missing expected
function export name" 에러가 났던 것이다. 둘은 같이 바꿔야 한다.

## 공용화는 하지 않았다

릴스와 기사 세부가 같은 기능을 갖게 됐으니 버튼을 공용으로 뺄까 봤는데, ADR 0011 게이트 B(동일성)에서
막힌다. 릴스는 미디어 위에 세로로 선 28px 아이콘 + 숫자이고 기사 세부는 테두리 있는 알약 버튼이다.
누르는 동작만 같지 생김새는 공유할 게 없다. 그래서 **훅만 공유하고 버튼은 각자** 두었다.
`@plick/domain`이나 `@plick/ui`로 올린 건 없다. web은 아직 이 API를 안 쓰므로 게이트 C(성숙도)도 안 선다.

## 검증

계약과 DB는 `be-verify`가 밟았다. 일회용 유저를 만들어 등록 → 중복 등록 → 조회 → 취소 → 중복 취소 →
미인증 → 없는 기사까지 확인하고 `likes` 테이블 반영도 대조했다. 끝나고 그 유저의 행만 지웠다.

화면은 직접 밟았다.

- 비로그인으로 하트 → 로그인 팝업이 화면 전체를 덮는다(포털 확인).
- 민팅한 토큰을 쿠키로 심고 기사 세부에서 좋아요 → 즉시 채워지고 1, 새로고침해도 유지.
- 릴스에서 좋아요 → 강조색으로 채워지고 1 → 2, 다시 눌러 취소 → 1로 복귀. BE 재조회로 대조.
- 브라우저 fetch가 `/be`를 통해 인증되는지 직접 확인(위 fetch 스니펫).
- 서버 HTML에서 좋아요한 기사 하나만 강조 클래스로 나오는지 curl로 대조.

`pnpm check-types`, `lint`, `format:check`, 두 앱 빌드 모두 통과했다.

## 남은 것

- 홈 목록과 핫이슈 캐러셀의 읽기에는 토큰을 안 싣는다. 지금은 `liked`를 안 쓰니 문제가 없지만,
  목록에서도 내가 누른 걸 표시하게 되면 그때 토큰을 실어야 한다.
- 토글 실패 중 401이 아닌 것(없는 기사, 네트워크 순단)은 문구 없이 되돌리기만 한다. 채워졌던 하트가
  도로 비는 게 이미 신호이고, 좋아요 한 번에 모달을 세우는 건 과하다고 봤다. 원인은 콘솔에 남긴다.
  실사용에서 실패가 잦다면 그때 표시 방식을 다시 본다.
- `packages/ui`의 작은 선 아이콘들을 설계 크기보다 줄여 쓰는 자리가 또 있는지는 확인하지 않았다.
  같은 뭉개짐이 있을 수 있어 `/audit` 때 훑어볼 만하다.
