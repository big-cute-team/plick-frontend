## 받은 요청

세 줄짜리 수정 티켓이었다.

1. 핫이슈에 큰 테두리를 넣고, 사진 없는 핫이슈는 핫이슈 태그를 빼고 제목과 부제목만 남겨 높이를 줄인다.
2. 릴스는 지금 제목을 눌러야만 세부 패널이 열리는데, 화면 어디를 눌러도 열리게 한다. 공유 버튼 같은 건 제 기능을 유지하고, 배경을 누르면 닫히는 것과 끌어내려 닫는 것도 그대로 둔다.
3. 기사 옆에 `[숫자]`로 보여주는 걸 조회수 대신 댓글 수로 바꾼다. 0이면 아예 보여주지 않는다.

셋 다 웹과 모바일 양쪽이다. 이번 세션에서는 이 셋과 함께, 작업 방식 하나를 저장소 규칙으로 바꿨다. 클로드가 PR을 직접 올리지 않고 제목과 본문을 채팅에 써 주면 사용자가 직접 PR을 만드는 방식이다. 아래 마지막 절에 적었다.

## 1. 핫이슈 섹션 테두리와 텍스트 카드 축소

"핫이슈 자체에 큰 테두리"를 처음엔 잘못 읽었다. 같은 문장 뒤에 "노이미지 핫이슈엔"이 붙어 있으니 앞의 "핫이슈 자체"는 사진 있는 캐러셀 카드라고 보고, 카드마다 2px 흰색 계열(`media-chip-border`) 테두리를 둘렀다. 로컬을 켜서 보여 드리니 아니었다. 사진 카드와 사진 없는 카드를 통째로 담는, 핫이슈와 "지금 올라온 소식"을 가르는 연한 테두리 상자를 뜻한 것이었다. 카드 테두리는 걷고 섹션을 상자에 넣었다.

모바일은 `section`이 화면 여백(`px-edge`)을 맡고 그 안의 `div`가 `border-border rounded-card border py-3` 상자다. 상자 안 좌우 여백은 화면 여백 20px보다 좁은 `px-3`(12px)로 잡았다. 그러면서 안에 있던 `px-edge`가 전부 `px-3`으로 바뀌었다. 제목, 빈 상태·에러 문구, 캐러셀 래퍼, 텍스트 페이저의 칸(`li`)이다. 페이저는 홈 상자 안에서만 쓰는 컴포넌트라 상자에 맞춰 바꿨다. 캐러셀 트랙은 335px에서 309px(375 - 40 - 2 - 24)로 줄어 사진 카드 한 장이 162.5px에서 149.5px이 됐다. 카드 폭 계산식 `calc((100%-10px)/2)`는 트랙 기준이라 손댈 게 없었다.

웹은 `section` 자체에 `border-border rounded-card border p-5`를 줬다. 컨테이너가 1200px이라 상자 안 여백을 따로 줄일 이유가 없었고, 캐러셀의 `lg:[--hot-edge:0px]`와 3열 그리드는 상자 패딩 안에서 그대로 선다.

테두리 색은 처음에 `border-border`(슬레이트 12%)로 잡았다. 텍스트 카드와 사이드바 카드가 쓰는 본문 톤 선이라 "연한 테두리"에 맞는다고 봤는데, 로컬에서 본 피드백은 너무 연해서 조금만 더 진하게였다. 다음 단계 토큰 `border-border-strong`은 16%라 눈에 띄는 차이가 안 난다. 그래서 `text-4`(#5e6b80)에 40% 불투명도를 건 `border-text-4/40`으로 올렸다. 페이저의 비활성 점(`bg-text-4/40`)과 같은 회색이라 화면 안에서 이미 쓰이는 톤이고, 본문 카드 선보다는 확실히 보이면서 글자보다는 뒤로 물러난다. 두 앱 같은 값이다.

사진 없는 카드(`HotTextCard`)는 KAN-515에서 게시판 행처럼 줄였던 걸 한 번 더 걷었다. 머리 줄(깜빡이는 핫이슈 배지 + 단계 라벨)을 통째로 빼고 제목과 요약만 남겼다. 모바일은 패딩을 `p-3.5`에서 `px-3.5 py-3`으로, 줄 간격은 `gap-1.5`에서 `gap-1`로 내렸다. 실측으로 카드 높이가 72.75px이 됐다. 배지 줄 하나가 약 20px, 패딩과 간격 축소가 약 6px이니 30px 가까이 줄었다. 웹도 같은 줄을 빼고 `p-4`를 `px-4 py-3.5`로 내려 99px이 됐다. 요약은 웹이 두 줄, 모바일이 한 줄인 건 그대로다.

이걸로 `HotBadge`를 쓰는 곳이 없어졌다. KAN-515에서 두 앱이 같이 쓴다고 `@plick/ui`에 올렸던 건데 하루 만에 사용처가 0이 됐다. 죽은 코드를 남길 이유가 없어 지웠다. 섹션 제목의 불꽃 `HotFlame`은 그대로 쓴다.

## 2. 릴 화면 어디를 눌러도 시트 열기

릴 한 장은 `ReelItem`의 `<section>`이다. 그 안에 뒤 레이어로 사진이나 트윗 임베드가 깔리고, 그 위에 스크림, 정보 블록(팀 칩·제목·기자 줄), 우측 액션 레일(좋아요·댓글·공유)이 있다. 원래 시트를 여는 탭 타깃은 제목 버튼, 기자 줄 버튼, 댓글 아이콘 셋이었다. 정보 블록 컨테이너는 `pointer-events-none`이라 글자 밖을 누르면 아무 일도 없었다.

가장 단순한 길은 `<section>`에 `onClick`을 다는 것이다. 뒤 레이어의 사진, 빈 배경, 스크림, 정보 블록의 빈 자리 전부 이벤트가 섹션까지 버블링된다. 문제는 걸러야 할 게 셋이라는 점이다.

첫째, 제 기능이 있는 요소. 액션 레일의 버튼 셋, 제목·기자 줄 버튼, 트윗 임베드 안의 링크(react-tweet가 그리는 프로필·원문 링크). 이건 `event.target.closest("a, button, input, textarea")`로 걸렀다. 버튼은 이미 각자 시트를 열거나 팝업을 띄우니 섹션 핸들러가 한 번 더 열 이유가 없고, 임베드 링크는 브라우저 기본 동작대로 x.com으로 가야 한다.

둘째, 포털로 뜨는 팝업. 공유 팝업(`ShareDialog`)과 비로그인 팝업(`LoginPromptDialog`)은 `createPortal`로 `document.body`에 그린다. 레일에 걸린 `drop-shadow` 필터 때문에 릴 안에서 `fixed`를 쓰면 기준 상자가 레일이 돼서 그렇다(KAN-312 때 결정). DOM으로는 섹션 밖인데, React의 합성 이벤트는 DOM이 아니라 React 트리를 따라 버블링한다. 팝업이 `ReelItem`의 자식으로 렌더되니 팝업 배경을 눌러 닫는 클릭이 섹션 `onClick`까지 올라온다. 그러면 공유 팝업을 닫는 순간 시트가 열린다. `e.currentTarget.contains(e.target)`으로 DOM 포함 여부를 한 번 더 확인해 걸렀다. 포털 안의 요소는 섹션의 DOM 자손이 아니라 여기서 걸린다.

셋째, 세로 스와이프. 릴을 넘기려고 끌었다 떼면 브라우저는 `click`을 쏠 수 있다. Embla가 이걸 처리한다는 걸 소스에서 확인했다. Embla는 뷰포트 노드에 `click` 리스너를 캡처 단계로 걸어 두고, 포인터가 `dragThreshold`(우리 옵션에서 8px)를 넘겨 움직였으면 `preventClick` 플래그를 세운 뒤 그 click에 `stopPropagation()`과 `preventDefault()`를 건다. 캡처 단계 리스너는 대상 요소보다 먼저 불리니 React 루트의 버블 리스너까지 도달하지 않는다. 그래서 넘기다 손을 떼도 섹션 핸들러는 불리지 않는다. 8px 미만으로 움직인 탭은 click이 살아 시트를 연다. 탭과 스와이프의 경계가 곧 Embla의 드래그 판정 경계다.

시트가 떠 있는 동안은 시트 층(`z-20`, `inset-0`)이 섹션을 통째로 덮어 클릭이 섹션에 닿지 않는다. 그래도 `titleMotion`이 있으면 빠져나가는 보험을 한 줄 뒀다.

배경 탭으로 닫기는 사실 없던 기능이었다. 시트 컴포넌트의 바깥 div가 화면 전체를 덮지만 `onClick`이 없었다. 티켓은 "유지"라고 썼지만 실제로는 X 버튼, 그랩 존 드래그, 본문 최상단 드래그(KAN-358) 셋만 있었다. 릴 화면 전체가 탭 타깃이 된 지금 이 층이 탭을 받아 주지 않으면, 시트 위 빈 곳을 누른 사용자는 "왜 아무 일도 없지"가 된다. 바깥 div에 `onClick`을 달고 `e.target === e.currentTarget`일 때만 `requestClose()`를 부른다. 시트 본체 안의 클릭은 target이 본체 쪽 요소라 걸리지 않는다. `requestClose`는 `shown`을 false로 내리고, 시트가 아래로 내려가는 transition이 끝나면 `onTransitionEnd`가 언마운트한다. 기존 X 버튼과 같은 경로다.

끌어내려 닫기는 손대지 않았다. `useReelDetailMotion`의 그랩 존 포인터 핸들러와 본문 스크롤 영역의 네이티브 터치 핸들러가 그대로다.

제목·기자 줄 버튼은 남겼다. 섹션 `onClick`만으로는 키보드와 스크린리더가 시트를 열 길이 없어서다. 눈으로 보는 사람에겐 둘 다 같은 시트를 여는 중복 타깃이지만, 버튼은 `closest("button")`에 걸려 섹션 핸들러가 두 번 열지는 않는다.

웹 릴(`apps/web` `ReelItem`)도 같은 걸 했다. 9:16 카드 `div`에 `onClick`을 달고 같은 두 가드(`closest`, DOM 포함)를 걸었다. 웹 팝업도 포털이라 두 번째 가드가 똑같이 필요하다. 다른 점은 셋이다. 웹 뷰어는 Embla 드래그가 아니라 스크롤 스냅이라 스와이프 뒤 click 문제 자체가 없다. 데스크톱 세부 패널은 오른쪽에 인라인으로 서고 처음부터 열려 있어(KAN-483) 배경 탭 닫기가 성립할 배경이 없고, 좁은 폭에선 패널이 화면 전체를 덮는 오버레이라 역시 배경이 없다. Esc와 X 버튼이 닫기다. 카드에 `cursor-pointer`를 줘서 마우스로도 눌리는 면임을 알린다.

## 2-1. 넓은 화면에서 시트가 제목 아랫줄을 가리던 문제

로컬을 켜서 보던 중에 릴 시트가 열리면 제목 두 번째 줄이 시트 뒤로 잘리는 화면을 받았다. 이번 변경 탓인가 싶어 기하부터 재 봤다. 재현 조건은 1024px 이상 창이다. 그 폭에서는 셸 맨 위에 PC 전환 배너(KAN-379)가 45px로 서고, 릴 피드의 `main`은 그만큼 짧아진다. 제목 리프트 거리(`titleLiftDistance`)는 릴 섹션 사각형으로 잰다. 섹션 바닥에서 높이의 73%를 뺀 자리가 시트 상단이라고 계산한다. 그런데 시트는 `absolute inset-0`이라 가장 가까운 positioned 조상에 맞춰 크기가 잡히는데, 그게 `AppShell`(`relative`, 100dvh)이었다. 시트 높이가 셸 전체의 73%로 서니 실제 시트 상단은 계산값보다 배너 높이의 73%, 약 33px 위에 있었다. 제목 한 줄이 30px쯤이라 딱 아랫줄이 잘렸다.

배너가 시트보다 나중에 들어왔는데 시트의 기준 상자를 그대로 둔 게 원인이다. 폰에서는 배너가 없어 셸과 섹션 높이가 같아 드러나지 않았다. 이번 변경과는 무관하지만 같은 화면이라 여기서 고쳤다. `ReelsFeed`가 `main`과 시트를 `relative flex min-h-0 flex-1 flex-col` 래퍼로 감싼다. 래퍼가 `main`과 같은 높이의 기준 상자가 되니 시트 높이가 `main`의 73%가 되고 리프트 계산과 같은 자를 쓴다. 1100px 창에서 재 보니 시트 높이가 841.7px로 섹션 높이 1153px의 73%와 맞았다. 래퍼에 z-index는 없어 새 스태킹 컨텍스트가 생기지 않고, 시트(`z-20`)와 오버레이 탭바(`z-10`)의 순서도 그대로다.

같은 창에서 콘솔에 `403 /api/v1/articles/{id}/view`가 찍힌 건 코드 문제가 아니다. 검증용 프록시가 브라우저의 `Origin: http://localhost:3031` 헤더를 dev 백엔드에 그대로 넘겼고, dev의 CORS 허용 목록에 로컬 origin이 없어 조회 기록 POST를 거절한 것이다. 프록시에서 Origin을 떼니 401(토큰 없음)로 바뀌었다. 실배포에서는 같은 도메인의 `/be` rewrite라 나지 않는다.

## 2-2. 핫이슈 카드의 트윗 임베드가 양옆이 비던 문제

로컬을 보던 중 또 하나. 사진을 끝내 못 구해 원문 트윗을 임베드한 핫이슈 카드가 가로를 꽉 채우지 못하고 가운데에 작게 떠 있었다. 사진 카드가 한 줄 두 장으로 줄면서(KAN-515) 칸 폭이 150px 남짓이 됐는데, 임베드는 여전히 "박스에 맞춰 축소"하는 `fill` 레이아웃이었다. `useTweetFit`이 카드가 박스보다 크면 미디어를 숨기고 그래도 넘치면 `transform: scale`로 줄이는 방식이라, 긴 트윗은 세로를 맞추느라 가로가 절반으로 줄어 양옆이 비었다. 사용자 요청은 가로 우선이었다. 폭을 꽉 채우고 아래로 넘치는 만큼은 잘라도 된다.

릴이 이미 그렇게 하고 있었다. `layout="reel"`은 미디어를 살린 채 전폭 자연 높이로 세우고, 부모가 위에 붙여 넘치는 만큼 겹치거나 잘린다. 핫이슈 카드도 같은 레이아웃을 `absolute inset-0 overflow-hidden` 상자에 넣으니 원하는 모양이 됐다. 그러고 보니 `fill`을 쓰는 곳이 핫이슈 카드 하나였고, `flow`(기사 세부 자연 높이)는 쓰는 곳이 아예 없었다. 레이아웃 셋을 하나로 합쳐 `layout` 인자 자체를 없앴고, `useTweetFit` 훅과 `withoutMedia`, `TWEET_FLOW_MAX_HEIGHT_RATIO` 상수도 같이 지웠다. 웹 `TweetEmbed`가 원래 이 모양(릴 경로만 옮긴 축소판)이라 두 앱이 같아졌다.

그런데 폭을 재 보니 카드 150px에 임베드가 250px이었다. react-tweet 컨테이너 CSS에 `min-width: 250px`이 박혀 있다. 오른쪽 100px이 잘려 나가는 셈이라 `.hot-embed` 스코프를 하나 더 두고 `min-width: 0`으로 풀었다. 같은 스코프에서 패딩·아바타(24px)·글자(0.7rem)를 릴 축소값보다 한 단 더 줄였다. 그래도 150px 폭에서는 헤더의 X 로고와 "· Follow"가 작성자 이름을 두 글자만 남기고 먹었다. 둘 다 임베드가 `pointer-events: none`이라 눌리지도 않는 장식이라 숨겼고, 라이브러리가 로고 자리로 비워 두는 `.author`의 `max-width: calc(100% - 84px)`도 100%로 풀어 이름이 그 폭을 쓰게 했다. 카드 래퍼는 `reel-embed hot-embed` 둘을 달아 릴 배경색·헤더 축소는 물려받고 치수만 덮는다.

덤으로 하나 배웠다. 이 변경을 dev 서버가 반영하지 않았다. `globals.css` 변경은 HMR로 바로 탔는데 `HotHeroCard.tsx`에 클래스 하나 더한 건 파일을 touch해도, 브라우저를 강제 새로고침해도 서버 HTML에 안 나왔다. 같은 파일을 몇 분 전에 고쳤을 때는 바로 반영됐던 터라 Turbopack 서버 컴포넌트 캐시가 어긋난 것으로 보인다. dev 서버를 껐다 켜니 바로 나왔다. 화면이 코드와 다르게 보이면 curl로 서버 HTML부터 확인하고 재시작하는 게 빠르다.

## 3. 조회수 대신 댓글 수

`HotArticle` 타입에 `commentCount`가 이미 있었다. `GET /api/v1/articles/hot`이 `viewCount`·`likeCount`·`commentCount`를 같이 주고 `toHotArticle`이 셋 다 매핑한다. 화면만 `article.views`에서 `article.commentCount`로 바꾸고 0이면 `<span>` 자체를 그리지 않게 조건을 걸었다. 제목과 숫자는 flex 형제라(ADR 0155) 숫자가 빠져도 제목이 그 폭을 그냥 가져간다.

웹 텍스트 카드도 같다. 웹의 사진 캐러셀 카드(`HotCard`)는 조회수를 눈 아이콘과 함께 메타 줄에 따로 보여주는 자리라 그대로 뒀다.

## 4. 급상승 랭킹의 기사 수 제거

같은 세션에서 웹 홈 사이드바의 실시간 급상승 줄에 KAN-523 때 달았던 `기사 N`을 빼 달라는 요청을 받았다. `TrendingRow`에서 그 `<span>` 하나를 걷었다. 순위 카드에 순위 변동 말고 다른 숫자가 서면 읽는 사람이 헷갈리고, 사이드바 폭에서 제목이 그만큼 더 잘리던 자리다. `TrendItem.articleCount` 자체는 이슈 상세 헤더(`기사 N건`)와 메타 설명이 계속 쓰니 타입은 그대로다. 모바일에는 급상승 위젯이 없다(ADR 0156).

같이 받은 질문이 "순위 상승·하락은 반영돼 있는가"였다. 반영돼 있다. `toTrendDelta`가 BE `direction`·`rankDelta`를 읽어 `UP`이면 ▲와 오른 칸 수, `DOWN`이면 ▼와 내린 칸 수, `NEW`면 NEW 배지, `SAME`이면 가로줄을 그린다. 다만 확인 시점의 dev 데이터는 이슈 넷이 전부 `previousRank === rank`, `direction: SAME`, `rankDelta: 0`이라 화면엔 가로줄만 보였다. 회차가 바뀌어 순위가 움직여야 화살표가 선다. 코드가 아니라 데이터가 그렇다는 걸 dev API 응답으로 확인했다.

## 검증

로컬 BE는 떠 있지 않았고 공유 DB에는 기사 사진이 한 장도 없어(ADR 0155와 같은 사정) 캐러셀이 안 그려진다. 스크래치에 20줄짜리 node 프록시를 8081에 띄웠다. 모든 요청을 `https://dev.plick.co.kr/be`로 넘기되 `/api/v1/articles/hot` 응답의 `withImage`가 비어 있으면 `withoutImage` 앞 네 건을 복사해 채운다. 홈 서버 컴포넌트가 `withTweetPhotos`로 원문 사진을 채워 실제 사진 카드처럼 보인다. `mobile-dev-mock`(3031, `API_BASE_URL=8081`) dev 서버로 확인했다. 프록시는 커밋하지 않았다.

- 모바일 홈 375px: 핫이슈 상자 계산 스타일 `1px text-4/40`(oklab 알파 0.4), 사진 카드 테두리 0, 사진 카드 폭 149.5px. 텍스트 카드 세 장 모두 72.75px, 내용은 제목과 `[4]`·`[3]`, 요약 한 줄. 가로 오버플로 없음, 콘솔 에러 없음.
- 모바일 릴스: 트윗 임베드 위 빈 자리를 탭하면 시트가 열림(`role=dialog` 확인, transform 0). 시트 위 배경을 탭하면 닫힘. 공유 아이콘을 탭하면 공유 팝업만 뜨고 시트는 안 열림. 공유 팝업 배경을 탭하면 팝업만 닫히고 시트는 안 열림.
- 웹 홈 1440px(`web-dev-mock`, 3030): 핫이슈 `section` 테두리 1px 같은 색, 사진 캐러셀 네 장과 3열 텍스트 카드(99px, `[4]`·`[3]`)가 상자 안에 섬. 콘솔 에러 없음.
- 웹 릴스: X로 패널을 닫은 뒤(폭 0) 카드의 임베드 아래 빈 자리를 클릭하면 패널이 다시 열림(폭 472px).
- 웹 홈 사이드바 급상승: 줄에 순위·제목·변동 표시만 남고 `기사 N` 없음.
- 모바일 홈 핫이슈 임베드 카드: 임베드 폭 150px = 카드 폭(전에는 250px 최소 폭에 걸려 오른쪽이 잘렸다). 헤더에 아바타·이름·아이디만 남고 X 로고와 Follow는 `display: none`.
- 모바일 1100px 창(PC 배너 있음): 시트를 열면 시트 높이 841.7px = 섹션 1153px의 73%. 브라우저 패널이 숨겨져 전환이 얼어 있어 도킹된 제목은 기하로만 확인했고, 사용자가 로컬에서 안 잘리는 걸 확인했다.
- `pnpm check-types`, `pnpm lint`, `pnpm format:check`, `pnpm build` 통과.

댓글 0건인 핫이슈는 dev 데이터에 없어 `[0]`이 빠지는 분기는 눈으로 못 봤다. 조건 한 줄이라 코드로 갈음했다. 트윗 임베드 안 링크가 x.com으로 가는 것과 실제 손가락 스와이프 뒤 click 억제는 브라우저 패널에서 못 밟았다. 후자는 Embla 소스로 확인했고, 실기기 감은 사용자가 본다.

## 규칙 변경: PR은 채팅으로

이 세션부터 클로드가 PR을 올리지 않는다. 사용자가 직접 PR을 만들고 싶다고 해서다. 커밋과 push까지 하고, PR 제목과 본문(`pr-writing` 스킬의 5절 틀)을 채팅에 그대로 쓴다. CI는 PR이 없으니 로컬에서 `format:check`·`lint`·`check-types`·`build`를 돌려 대신한다.

CLAUDE.md의 Git·PR 절, `pr-writing` 스킬, `/screen`·`/web-screen`·`/wire-api`·`/web-wire-api` 커맨드, `api-integration` 스킬의 마지막 단계에서 `gh pr create`를 걷어냈다. 병합 금지는 그대로다.
