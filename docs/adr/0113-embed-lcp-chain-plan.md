# 0113. 임베드 LCP 체인 개선 계획 — 속성으로 안 되는 건 구조로 (2026-08-31)

[0111](0111-kan-421-lcp-font-selfhost.md)(KAN-421 폰트 셀프호스팅)의 후속 계획 세션이다.
폰트 작업으로 릴스 LCP를 14.75초에서 5.70초까지 내렸는데, 남은 5.7초의 병목이 무엇이고
어떻게 잡을지를 코드 확인과 함께 정리했다. 이번엔 코드를 한 줄도 안 고쳤다. 개선 순서를
먼저 문서로 박아두고 시작하기로 했다 — 0111에서 "단계를 쪼개고 단계마다 재야 수치가
귀속된다"는 걸 배웠기 때문이다.

## 남은 병목: LCP 이미지가 초기 HTML에 존재하지 않는다

0111 마지막 측정에서 LCP 요소는 여전히 트윗 임베드 이미지(`pbs.twimg.com`)였다. 발행된 릴
전건이 `reelsImageUrl` null이라 릴의 미디어는 전부 react-tweet 임베드로 온다. 그런데 이
임베드는 클라이언트 컴포넌트다. 브라우저 입장에서 LCP 이미지에 도달하는 체인이 이렇다.

1. HTML 도착. 이 시점 HTML엔 트윗 이미지가 없다 — 임베드 자리는 빈 영역이다.
2. JS 다운로드 → 하이드레이션 → `TweetEmbed`의 `useTweet`(swr)가 그제서야
   `/api/tweet/{id}`를 fetch한다.
3. 프록시 응답이 와야 비로소 이미지 URL을 알게 되고, 그때부터 `pbs.twimg.com` 요청이 시작된다.

여기서 처음에 헷갈렸던 걸 짚고 간다. "그럼 이미지에 `fetchPriority="high"` 붙이면 되는 거
아닌가" 싶었는데, 안 된다. `fetchPriority`는 브라우저의 프리로드 스캐너가 초기 HTML을 훑다가
그 `<img>` 태그를 발견했을 때 요청 우선순위를 올려주는 힌트다. 발견 자체가 하이드레이션 뒤에나
일어나는 이미지에는 힌트를 받아줄 태그가 HTML에 존재하지 않는다. Lighthouse가
"request is not discoverable in initial document"라고 찍은 게 정확히 이 얘기다. 0111에서
할 수 있었던 게 `pbs.twimg.com` preconnect(오리진 연결 미리 맺기)까지였던 이유도 같다 —
URL을 모르니 연결만 미리 해둘 수 있었다.

그래서 이번 챕터의 한 줄 요약은 이거다: 속성(attribute)으로 안 되는 건 구조로 푼다. 이미지
URL이 서버 렌더 시점에 존재하게 만들어서, 힌트를 받아줄 대상을 HTML에 만들어준다.

## 착수 전에 코드를 확인해서 리스크를 덜어냈다

계획만 세우기 전에 실제 코드를 열어봤고, 두 가지가 확인됐다.

- `apps/mobile/app/api/tweet/[id]/route.ts`가 이미 서버에서 `getTweet(id)`를 쓰고 있다.
  KAN-284 때 react-tweet 기본 엔드포인트의 공용 rate limit을 피하려고 만든 프록시인데,
  덕분에 "서버에서 트윗 데이터를 받는 경로"는 이미 검증된 상태다. 서버 렌더 임베드는
  이 호출을 라우트 핸들러에서 페이지 서버 컴포넌트로 옮기는 것에 가깝다.
- X Display Requirements 대응도 이미 서 있다. `TweetEmbed`의 `withoutMedia`(본문은 못
  건드리니 넘치면 미디어를 뺀다), 임베드 읽기 전용화(KAN-297) 규칙이 클라 렌더 기준으로
  다 구현돼 있다. 렌더 위치를 서버로 옮겨도 그리는 컴포넌트(`EmbeddedTweet`)와 규칙은
  같아서, 규정 리스크가 새로 생기지는 않는다.

처음엔 "X 임베드 표시 규정과 실패 fallback이 얽혀 있으니 티켓 하나 잡고 따로 돌자"고
겁먹었는데, 열어보니 절반은 이미 풀려 있었다. 겁의 근거를 코드로 확인하는 게 계획의
절반이었다.

## PR 1 설계 메모: 미리 알아둔 함정 두 개

서버 렌더 임베드의 뼈대는 이렇다. 릴스 페이지 서버 컴포넌트가 첫 릴의 트윗 id로
`getTweet(id)`를 호출해 트윗 JSON을 받고, 그걸로 초기 HTML에 임베드를 그려낸다. 이미지
URL을 서버가 아는 순간 `ReactDOM.preload(url, { as: "image", fetchPriority: "high" })`로
프리로드 링크까지 걸 수 있다. 체인에서 클라 fetch 한 번과 하이드레이션 대기가 빠진다.

다만 함정이 둘 있다.

- TTFB 역행 주의. 릴스 페이지는 `cookies()` 때문에 동적 렌더라 매 요청 서버를 탄다. 여기에
  신디케이션 API 왕복(수백 ms)을 그대로 얹으면 LCP 줄이려다 첫 바이트를 늦춘다. 프록시가
  성공 응답을 하루 캐시하듯(`max-age=86400`, 트윗 본문은 사실상 불변), 서버 호출도
  `unstable_cache` 같은 걸로 하루 캐시해서 왕복을 요청마다 내지 않게 한다.
- 첫 릴만 서버 데이터로 그리고 나머지는 지금처럼 클라 fetch로 둔다. 이때 첫 릴의 트윗
  JSON을 swr 캐시에 fallback으로 시딩해 줘야 하이드레이션 후 같은 트윗을 다시 fetch하는
  중복이 안 생긴다. 홈·기사에서 이미 쓰는 "서버 씨앗 + 클라 캐시 시딩" 패턴의 임베드판이다.

실패 fallback은 단순하게 간다. 서버 `getTweet`이 실패하면(원문 삭제, API 장애) 그 릴만
기존 클라 렌더 경로로 폴백한다. 지금도 클라 실패 시 안내 문구로 처리하는 로직이 있으니
서버 실패를 클라 경로에 위임하면 새 분기가 최소화된다.

## PR 1 실행 기록 — 구현은 계획대로, preload에서 한 번 당했다

계획을 세운 같은 날 바로 KAN-422로 실행했다. baseline은 develop `bc7665a`에서 새로 떴고
(`docs/perf/2026-08-31-kan-422-embed-lcp/before/`), 릴스 LCP 중앙값 5.41초로 0111의
after(5.70)와 노이즈 범위에서 같았다.

구현 자체는 확인해 둔 대로 순탄했다. `_services/tweet.ts`에 `getTweet`을
`unstable_cache`(하루)로 감싼 `getReelSeedTweet`을 만들고, 페이지가 첫 릴의 트윗
JSON을 받아 `ReelsFeed → ReelItem → TweetEmbed`로 내려보냈다. `TweetEmbed`는
`seedTweet`이 오면 `useTweet`에 id와 apiUrl을 둘 다 안 넘긴다 — react-tweet의
useTweet은 둘 다 없으면 swr 키가 null이라 요청 자체가 나가지 않는다. 이걸로
하이드레이션 후 중복 fetch가 원천 차단된다(초기 `/api/tweet` 10건 → 9건으로 실측 확인).
preload URL은 react-tweet 내부 `getMediaUrl(media, "small")` 규칙(`?format=…&name=small`)을
그대로 옮겨 만들었다 — 렌더와 URL이 다르면 이중 다운로드가 되니 버전 올릴 때
같은지 봐야 한다는 주석을 남겼다.

### ReactDOM.preload()가 캐시 히트 요청에서 증발했다

여기서 한 번 당했다. 처음엔 `ReactDOM.preload(url, { as: "image", fetchPriority: "high" })`
호출로 preload를 걸었고, 서버 기동 직후 curl로 `<link rel="preload" … fetchPriority="high">`가
head에 박힌 걸 확인하고 넘어갔다. 그런데 딥링크 페이지를 검증하다 보니 preload가 없었고,
다시 보니 탭 피드에서도 사라져 있었다. 서버를 재시작하고 요청을 순서대로 날려 보니 패턴이
잡혔다: 첫 요청(콜드)엔 나오고, 두 번째 요청부터(웜) 안 나온다. `unstable_cache`가 미스일
때만 preload가 살아남는 거다. 임베드 마크업 자체는 웜에서도 멀쩡히 SSR되는데 임퍼러티브
preload 호출의 결과만 증발한다 — Next의 Float(리소스 힌트 수집)와 Data Cache 히트 경로가
얽힌 동작으로 보이는데 내부 원인까지는 더 파지 않았다.

해결은 호출 대신 렌더였다. 페이지 JSX 트리에 `<link rel="preload" as="image" …>`를 직접
렌더하면 React 19가 요청마다 head로 호이스팅한다. 트리의 일부라 캐시 상태와 무관하게
결정적으로 나온다. 콜드·웜, 탭 피드·딥링크 전부에서 preconnect 바로 뒤에 박히는 걸
확인했다. "서버 기동 직후 첫 요청만 보고 검증 끝냈다"고 넘어갔으면 배포 후에야 알았을
문제다 — 캐시가 끼는 코드는 웜 요청을 꼭 다시 봐야 한다는 걸 이번에 몸으로 배웠다.

### 결과 — 구조는 다 잡혔고, 수치는 다음 PR의 몫이 드러났다

after 중앙값 (`after-server-embed/`, 같은 조건 5회):

| 지표                            | before | after        |
| ------------------------------- | ------ | ------------ |
| LCP                             | 5.41 s | 5.03 s (−7%) |
| lcp-discovery: 문서에서 발견    | ✗      | ✓            |
| lcp-discovery: 우선순위 힌트    | ✗      | ✓            |
| resource load delay (observed)  | 533 ms | 19 ms        |
| LCP 이미지 요청 시작 (observed) | 542 ms | 34 ms (High) |
| 초기 `/api/tweet` 요청          | 10건   | 9건          |
| TTFB                            | 4~6 ms | 6~12 ms      |

이 PR이 노린 것(발견 불가 해소, load delay 제거, 중복 fetch 차단)은 전부 잡혔다. 그런데
LCP는 0.4초만 움직였다. 이유가 재밌는데, load delay가 533→19ms로 사라진 자리를 load
