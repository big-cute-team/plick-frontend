# 0153. 라이브와 팀 화면을 주제별 탭으로 쪼개고, 핫이슈에서 임베드를 걷어냈다

KAN-484. 한 티켓에 여덟 줄짜리 요구가 뭉쳐 있었다. 라이브 어디서든 팀을 누르면
팀 화면으로 가게, 끝난 경기에 "킥오프 전"이 뜨는 걸 고치게, 경기와 팀 화면을
주제별 탭으로 쪼개게, 팀 프로필 선수 목록을 네모 칸으로 다시 짜게, 핫이슈
캐러셀에 트윗 임베드 대신 실제 사진만 보이게.

## 먼저 무엇이 이미 돼 있는지부터 봤다

티켓 첫 줄이 "이미 반영된건 넘어가셈"이었다. 티켓이 쌓여 있는 동안 몇 개는
다른 작업에서 이미 고쳐졌다는 뜻이다. 그래서 코드를 고치기 전에 여덟 항목을
하나씩 확인했다.

- "라이브 들어가면 디폴트로 리버풀에 초록 하이라이트": 순위표
  (`StandingsTable`·`StandingsRail`) 주석에 "껍데기 때 리버풀 행에 박아 둔
  마이팀 하이라이트는 걷어냈다"가 이미 적혀 있었다. dev(dev-m.plick.co.kr)에
  들어가 눈으로도 확인했고 하이라이트는 없었다.
- "웹도 라인업·스탯을 별개 탭으로": 웹 경기 상세는 KAN-462에서 이미
  요약·라인업·스탯 탭이었다. dev 웹에서 확인했다. 남은 건 뉴스 탭뿐이었다.

이 두 개를 걷어내니 실제로 할 일이 여섯 개로 줄었다. 확인 없이 다 손댔으면
멀쩡한 코드를 건드릴 뻔했다.

## 팀 최근 전적과 다음 경기는 뺐다

티켓에는 팀 프로필에 "최근 전적, 다음 경기, 뉴스"를 넣으라고 돼 있었다. 뉴스는
`GET /api/v1/articles?teamId=`로 바로 되는데 나머지 둘이 막혔다. BE 스웨거를
뒤져 보니 경기 API는 `GET /api/v1/matches?date=` 하나뿐이다. 날짜 하나만 받는다.
어떤 팀의 지난 다섯 경기를 알려면 날짜를 하나씩 거슬러 올라가며 스무 번쯤
불러야 하고, 그 중 그 팀 경기가 있는 날은 두세 번이다. 이건 FE에서 흉내 낼 게
아니라 BE에 `GET /teams/{id}/fixtures`가 있어야 하는 일이다.

사용자에게 물어보고 이 항목 전체를 후속으로 뺐다. 대신 팀 프로필은 "탭으로
나눠 컴팩트하게"로 방향을 잡았다.

## 1. 팀 클릭을 한 군데로 모았다

"라이브 관련 페이지 모든 곳에서 팀 클릭하면 팀 정보 페이지로"가 요구였다.
그때까지 팀이 링크였던 건 순위표 행 하나뿐이었고, 그마저도 옛 주소
(`/live/teams/{teamId}`)를 가리키고 있었다. 그 주소는 KAN-507에서 팀 프로필로
308 리다이렉트를 걸어 둔 자리다. 동작은 하지만 누를 때마다 서버 왕복이 한 번
더 생기고, Next의 prefetch도 리다이렉트 앞에서 멈춰 실제 도착지를 미리 받지
못한다. 도착지를 직접 가리키게 바꿨다. 리다이렉트 라우트는 지우지 않았다 —
이미 색인됐거나 공유된 주소가 404가 되면 안 된다.

팀이 그려지는 자리를 전부 찾아보니 여덟 군데였다. 경기 상세 헤더(모바일·웹),
순위표(모바일·웹), 프리뷰의 결장자 그룹·리그 순위·직전 경기 선발(모바일·웹).
처음엔 각 자리에 조건 분기를 하나씩 넣었는데, 세 번째쯤에서 같은 코드를 또
쓰고 있다는 게 보였다.

```tsx
if (team.code === null) return <div className={cls}>{content}</div>;
return (
  <Link href={teamProfilePath(team.code)} className={cls}>
    {content}
  </Link>
);
```

이 판정이 여덟 군데에 흩어지면 나중에 한 군데는 반드시 빠진다. `TeamProfileLink`
하나로 모았다.

```tsx
export function TeamProfileLink({ team, className, children }) {
  if (team.code === null) return <span className={className}>{children}</span>;
  return (
    <Link
      href={teamProfilePath(team.code)}
      aria-label={`${team.name} 팀 프로필`}
      className={className}
    >
      {children}
    </Link>
  );
}
```

`team.code`가 null인 팀은 빅6 밖이다. 라이브 데이터는 API-Football에서 오고
거기엔 코번트리든 브라이턴이든 다 있지만, PLick 팀 프로필은 빅6만 있다
(`TEAMS` 레지스트리). 그런 팀은 갈 곳이 없으니 링크가 아니라 그냥 글자로
남는다 — `<div>`가 아니라 `<span>`인 건 `<p>` 안에도 들어가야 해서다. 블록
요소를 문단 안에 넣으면 브라우저가 문단을 강제로 닫아 DOM이 어긋난다.

경기 목록 카드(`MatchCard`)에는 이걸 쓰지 않았다. 거기는 카드 전체가 경기
상세로 가는 `<Link>`인데, 그 안에 또 `<a>`를 넣으면 잘못된 HTML이라
하이드레이션이 깨진다. 목록에서 팀 줄을 누르면 지금처럼 그 경기로 간다.

선수 클릭은 이미 돼 있었다. 라인업 피치와 벤치, 선수단 목록은 누르면 스탯
시트가 열린다. 반면 타임라인과 득점 요약은 못 붙였다 — BE `MatchEvent`·
`MatchGoal`에 `playerName`만 있고 `playerId`가 없어서 어느 선수인지 특정할
방법이 없다. 이름으로 라인업을 뒤져 맞히는 건 동명이인과 표기 차이
("B. Davies" vs "Ben Davies")에서 바로 깨진다. BE가 id를 실어 줘야 하는
일이라 후속으로 남겼다.

## 2. 끝난 경기에 "킥오프 전"이 뜨던 자리

티켓에는 "경기 끝난 경기 들어갔는데, 킥오프 전 이라고 뜨는 문제"라고만 적혀
있었다. 재현부터 하려는데 로컬 BE가 경기 데이터를 못 준다 —
`MATCH_UPSTREAM_ERROR`, 즉 `FOOTBALL_API_KEY`가 없어서 API-Football을 못 부른다.
dev 환경에 들어가 끝난 경기를 열어 봤더니 헤더 칩은 "경기 종료 · FT"로 제대로
떴다.

그래서 코드에서 "킥오프"라는 글자가 나오는 자리를 전부 훑었다. 상태 칩
(`StatusChip`)은 `status === "SCHEDULED"`일 때만 "킥오프 전"을 쓰니 여기가
아니고, 진짜 범인은 탭 본문의 빈 자리 문구였다.

```tsx
{tab === "lineups" && (detail.lineups ? <LineupPitch … /> : (
  <EmptyBlock label="라인업은 킥오프 20~40분 전에 공개돼요" />
))}
```

라인업 탭은 `MATCH_TABS_BY_STATUS`상 LIVE와 FINISHED에만 뜬다. 즉 이 문구가
보이는 순간은 애초에 킥오프가 지난 뒤뿐이다. 끝난 경기인데 BE가 라인업을 안
실어 주면 "킥오프 20~40분 전에 공개돼요"가 뜬다. 종료된 경기를 열었는데 킥오프를
기다리라고 말하는 셈이다. 요약·스탯 문구도 같은 결로 "아직 없어요"였다.

상태로 갈랐다.

```ts
export function matchEmptyLabel(tab, status) {
  return MATCH_EMPTY_LABEL[tab][status === "LIVE" ? "pending" : "done"];
}
```

라이브 중이면 아직 들어올 수 있으니 "아직 없어요"가 맞고, 그 밖(종료·연기·취소)은
더 올 것이 없으니 "이 경기의 라인업 정보가 없어요"로 끝낸다.

이게 티켓이 말한 그 증상인지는 100%는 모르겠다. 사용자가 본 화면을 그대로
재현하지 못했으니까. 다만 "끝난 경기에서 킥오프를 말하는" 자리는 코드상 여기
하나였고, 이건 조건과 무관하게 틀린 문구라 고치는 게 맞다.

## 3. 경기 상세에 뉴스 탭을 붙였다

경기를 보다가 "이 팀 요즘 무슨 얘기가 도나"가 궁금해지면, 그때까지는 기사 탭으로
나가서 팀을 다시 고르고 돌아와야 했다. 경기 지면에 양 팀 기사를 합쳐 깔았다.

경기 전용 기사 API는 없다. 팀 필터 목록을 팀마다 받아 합쳤다 — 관련 기사
(`getRelatedArticles`)가 팀 하나로 이미 하고 있던 방식이다.

```ts
export async function getMatchNews(teams: TeamCode[]): Promise<ArticleCard[]> {
  if (teams.length === 0) return [];
  const pages = await Promise.all(
    teams.map((team) => getArticles({ team, size: MATCH_NEWS_COUNT })),
  );
  const byId = new Map<string, ArticleCard>();
  for (const item of pages.flatMap((page) => page.items)) {
    if (!byId.has(item.id)) byId.set(item.id, item);
  }
  return [...byId.values()]
    .sort((a, b) => Date.parse(b.publishedAt) - Date.parse(a.publishedAt))
    .slice(0, MATCH_NEWS_COUNT);
}
```

두 군데를 조심했다. 하나는 중복이다. "토트넘 맨유 이적설" 같은 기사는 양 팀에
다 태그돼 있어 두 목록에 다 온다. id로 한 번 접었다. 다른 하나는 정렬이다.
팀별로는 최신순이지만 두 목록을 이어 붙이면 순서가 섞인다. 합친 뒤 발행 시각으로
다시 정렬한다.

팀마다 8건을 받아 합친 뒤 다시 8건으로 자른다. 4건씩 받으면 한 팀 기사가 몰린
날 상대 팀 기사가 통째로 밀려난다.

`useMatchNews` 훅은 `enabled`로 막아 뒀다. 뉴스 탭을 열어야 요청이 나간다 —
요약만 보고 나가는 사람에게 기사 요청을 태우지 않는다. 무한 목록이 아니라 한
페이지 고정이고, 더 보는 건 기사 목록의 팀 탭으로 보낸다. 홈 소식 리스트를
첫 페이지 고정으로 되돌린 KAN-386과 같은 판단이다.

쿼리키는 팀 코드를 정렬해서 담는다.

```ts
matchNews: (teams: TeamCode[]) =>
  ["articles", "match-news", [...teams].sort().join("-")] as const,
```

같은 두 팀이 붙는 경기는 홈·어웨이가 뒤집혀도 같은 기사 목록이다. 정렬하지
않으면 `TOT-MUN`과 `MUN-TOT`가 다른 캐시가 돼 같은 걸 두 번 받는다.
`[...teams]`로 복사해서 정렬하는 것도 이유가 있다 — `Array.prototype.sort`는
원본을 제자리에서 바꾼다. 호출부가 넘긴 배열을 정렬해 버리면 화면의 팀 순서가
조용히 홈·어웨이에서 알파벳순으로 뒤집힌다.

뉴스 탭이 붙으면서 예정 경기도 탭이 둘(프리뷰·뉴스)이 됐다. 웹 경기 상세는
탭이 하나면 탭 줄을 안 그렸는데(`tabs.length > 1`), 이제 탭 줄이 없는 상태는
연기·취소뿐이고 그쪽은 아예 다른 지면으로 빠진다.

## 4. 팀 프로필을 탭으로 쪼개고 선수를 네모 칸으로 바꿨다

티켓 표현이 직설적이었다. "팀 정보 페이지 너무 짜침. 각 선수를 네모 칸으로,
선수 얼굴, 이런식으로. 그리고 지금처럼 중간에 공백이 엄청 생기는 구조가 아니라
포워드 한섹션, 그밑에 수비수 한섹션, 이런식으로… 지금처럼 그리드가 아니라."

dev 웹에서 리버풀 프로필을 열어 보니 무슨 말인지 바로 보였다. 포지션 그룹
자체가 2열 그리드에 들어가 있었다. 골키퍼는 4명, 수비수는 10명이다. 왼쪽 열의
골키퍼가 먼저 끝나면 그 아래가 통째로 빈 채로 다음 그룹이 오른쪽에서 시작한다.
화면 가운데에 세로로 긴 공백이 생긴다.

"지금처럼 그리드가 아니라"는 그리드를 쓰지 말라는 게 아니라, 그리드를 **그룹**에
걸지 말라는 뜻이었다. 그리드를 선수에 걸면 공백이 사라진다. 포지션 섹션은
가로를 다 쓰고 위에서 아래로 한 줄씩 내려가고, 그 안에서 선수 타일이 여러 열로
깔린다.

타일은 얼굴이 주인공이다. 전에는 36px(웹 48px) 원이 이름 옆에 붙은 행이라
누가 누구인지 알아보기 어려웠다. 사진을 72px로 키워 위에 놓고 이름과 등번호를
아래에 붙였다.

열 수는 모바일 3, 웹 3/4/6(sm/lg)이다. 모바일에서 3인 이유는 폭 계산이다.
320px 화면에서 `px-edge`(16×2)와 칸 사이(8×2)를 빼면 타일 하나가 90.7px,
타일 안쪽 패딩(8×2)을 또 빼면 74.7px이 남는다. 72px 사진이 딱 들어간다. 2열이면
타일이 커져 포지션 하나가 화면을 넘고, 4열이면 사진이 40px대로 줄어 결국 전과
같아진다.

그다음이 탭이다. KAN-507에서 "선수단"과 "기사에 나온 인물" 두 명단을 한 장에
합쳐 뒀는데, 섹션을 위아래로 쌓다 보니 선수단 33명을 다 지나야 인물 목록이
나왔다. 사용자가 "주제별로 탭 분리, 모바일처럼 웹을"이라고 못박아 줘서 경기
상세와 같은 탭 줄로 갈랐다.

탭 이름은 "선수단"과 "기사 속 인물"이다. 인물 쪽을 그냥 "인물"로 하면 선수단과
무슨 차이인지 안 읽힌다 — 둘 다 사람 목록인데 한쪽은 이번 시즌 등록 명단이고
다른 쪽은 기사에서 뽑아 쌓은 사전이다.

탭은 URL로 올리지 않고 컴포넌트 상태로 뒀다. 경기 상세 탭과 같은 판단이고
(ADR 0126 스토리 2), 팀 프로필의 색인 대상은 팀 자체지 탭이 아니다. 두 목록
다 서버에서 받아 넘기므로 첫 HTML에는 둘 다 들어 있다.

헤딩 레벨도 다시 손봤다. KAN-507에서 섹션 `h2` 밑으로 들어가느라 `h3`로 내렸던
포지션·구분 제목이, 탭 아래로 오면서 다시 페이지의 두 번째 층이 됐다. `h2`로
올렸다. 레벨을 건너뛰거나 거꾸로 두면 스크린리더가 목차를 못 만든다.

컴포넌트도 옮겼다. `SquadList`(모바일)와 `SquadGroups`(웹)는 `live/_components/`에
있었는데 KAN-507 이후로 부르는 곳이 팀 프로필 하나뿐이었다. 팀 프로필
`_components/SquadGrid.tsx`로 새로 쓰고 옛 파일은 지웠다. 한 화면 전용은 그
라우트에 co-locate한다는 규칙 그대로다.

기사 속 인물 목록은 행 구조를 그대로 뒀다. 여기는 감독·구단주가 섞여 있어
이름 옆에 구분 라벨이 붙고 섹션별 인원도 들쭉날쭉이라, 타일보다 행이 읽기 낫다.

## 5. 핫이슈 캐러셀에서 임베드를 걷어냈다

마지막 항목이 제일 재미있었다. "지금 핫이슈 캐러셀에 이미지 없으면 임베드
보여주는데, 임베딩 된거에서 실제 이미지만. 기자 이미지 아이콘 말고, 실제 큰
이미지만."

지금까지의 동작은 이랬다. 핫이슈 카드는 `imageUrl`이 있으면 사진을 꽉 채우고,
없으면 원문 X 게시물을 통째로 임베드했다(`TweetEmbed`). 임베드는 프로필
사진·아이디·본문·버튼을 다 들고 온다. 그래서 사진이 주인공이어야 할 캐러셀
칸에서 정작 사진은 작게 박히고 프로필 아이콘이 눈에 먼저 들어왔다.

왜 `imageUrl`이 비는지부터 짚어야 한다. KAN-480에서 BE가 핫이슈를 사진 유무로
두 그룹으로 갈라 주기 시작했는데, 나눈 기준은 원문 게시물에 사진이 있었는지
(`raw_articles.media_url`)이고 카드가 그리는 건 기사 대표 이미지
(`article_summaries.image_url`)다. 서로 다른 컬럼이라 "사진 있는" 그룹으로 온
기사도 `imageUrl`이 null일 수 있다. 티켓의 "이미지가 있는 게시물이라는건
확실한데, 백엔드에서 이미지 Url 이 없을 수 있으니까"가 정확히 이 얘기다.

그러면 원문 게시물에서 사진만 꺼내 오면 된다. 트윗 신디케이션 응답에는
`mediaDetails`가 있고 거기에 사진 원본 크기와 URL이 들어 있다.

```ts
const photos = (tweet.mediaDetails ?? []).filter((m) => m.type === "photo");
const biggest = photos.reduce((best, m) =>
  area(m.original_info) > area(best.original_info) ? m : best,
);
return withLargeVariant(biggest.media_url_https);
```

`type === "photo"`로 거르는 게 핵심이다. 영상과 GIF도 `mediaDetails`에 오는데
그 자리 URL은 재생 전 포스터 프레임이라 "게시물에 있는 사진"이 아니다. 프로필
사진은 `mediaDetails`에도 `photos`에도 없어서 따로 거를 게 없었다 — 임베드
컴포넌트가 `user` 필드에서 따로 가져다 그리던 것이었다.

`media_url_https`는 변형이 안 붙은 원본 경로라 `?name=large`를 붙여야 큰 판이
온다. 이미 쿼리가 붙어 있으면 건드리지 않는다.

캐시가 중요했다. `getTweet`은 매번 신디케이션 API로 나가는 fetch인데, 홈이
열릴 때마다 최대 5건을 물어보면 첫 바이트가 그만큼 늦어진다. 다행히 `getTweet`은
두 번째 인자로 `RequestInit`을 받아 그대로 fetch에 넘겨 준다. Next의 fetch
확장(`next.revalidate`)이 타입엔 없지만 런타임에는 그대로 먹으므로 캐스팅해서
하루를 재사용하게 했다. 트윗 본문은 사실상 불변이라 이미 `/api/tweet/[id]`
프록시도 같은 판단으로 `max-age=86400`을 쓰고 있었다.

```ts
tweet = await getTweet(id, {
  next: { revalidate: TWEET_REVALIDATE_SECONDS },
} as RequestInit);
```

어디에 둘지가 고민이었다. `TweetEmbed`와 `/api/tweet/[id]` 라우트는 web과
mobile에 한 벌씩 복제돼 있다. 라우트 핸들러는 각 앱에 있어야 하니 어쩔 수 없는
복제인데, 이건 순수 함수라 그런 제약이 없다. `@plick/core`에 넣고 `react-tweet`을
core 의존성에 더했다(ADR 0011 게이트 C — 두 번째 사용처가 생기면 승격). 두 앱
홈 서버 컴포넌트가 `getHotArticles()` 결과에 이걸 통과시킨다.

```ts
const heroes = hot ? await withTweetPhotos(hot.withImage) : [];
```

이미 `imageUrl`이 있는 카드는 신디케이션을 부르지 않는다. 못 채운 카드는
null 그대로라 배경색 위에 제목만 선다 — 임베드 폴백은 아예 지웠다. 딸려 있던
CSS(`.hero-embed`, `.hot-embed`)도 같이 지웠다. 쓰는 데가 없어진 선택자를 남겨
두면 다음 사람이 이게 살아 있는 규칙인 줄 안다.

## 확인하는 데서 제일 오래 걸렸다

로컬 BE 둘이 서로 다른 조각만 서빙했다.

- 8080·8082(최신 소스): 팀 프로필(`GET /teams/{id}`)과 기사·인물은 되는데
  경기·스쿼드는 `MATCH_UPSTREAM_ERROR`다. `FOOTBALL_API_KEY`가 없다.
- 8081(목): 경기·스쿼드·순위는 오는데 팀 프로필이 `COMMON_NOT_FOUND`다. 옛
  빌드라 그 엔드포인트가 없다.

팀 프로필 화면은 이 둘을 다 쓴다. 인물 사전 fetch가 먼저 실패하면 페이지가
통째로 not-found로 떨어져서 선수단 그리드를 볼 수가 없었다. 8081에 붙이면
프로필이 없어 404, 8082에 붙이면 선수단이 빈다.

그래서 두 BE를 한 origin으로 합치는 30줄짜리 프록시를 스크래치패드에 띄웠다.
`/matches`·`/standings`·`/teams/{id}/squad`·`/players`는 8081로, 나머지는
8082로 보낸다. 앱을 그 포트에 붙이니 한 화면에서 전부 확인됐다.

```js
const TO_8081 = [/^\/api\/v1\/matches/, /^\/api\/v1\/teams\/\d+\/squad/, …];
const port = TO_8081.some((re) => re.test(req.url)) ? 8081 : 8082;
```

dev 서버도 못 띄웠다. 다른 세션이 같은 디렉터리에서 `next dev`를 잡고 있었고
Next 16은 같은 디렉터리에 두 번째 dev 서버를 거부한다. 남의 프로세스를 죽이는
대신 프로덕션 빌드 + `next start`로 갔다. 결과적으로 `pnpm build`까지 같이
검증됐다.

핫이슈 사진만은 화면으로 못 봤다. 로컬 BE의 핫이슈 응답이 `withImage: []`라
채울 카드가 아예 없다. 대신 `largestTweetPhoto`가 쓰는 필드를 실제 트윗
세 건으로 확인했다 — `mediaDetails[].type`이 `photo`로 오고
`media_url_https`에 `?name=large`를 붙인 URL이 나온다.

```
2081672288076714166 | mediaDetails: photo | photos: 1
  | pick: https://pbs.twimg.com/media/HOOVf0nWQAAIiS2.jpg?name=large
```

화면으로 본 것과 함수로만 본 것을 섞어 두지 않으려고 여기 적어 둔다. 캐러셀에
실제로 사진이 깔리는 모습은 dev 배포 후에 확인해야 한다.
