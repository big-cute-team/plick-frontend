# 0085. 새로고침 깜빡임 잡기, 웹 당겨서 새로고침, 버전 전환 배너 (KAN-379)

한 세션에 네 가지를 했다. 응원팀 수정 진입점 추가, 탭 재탭 깜빡임 수정, 데스크톱 웹에 당겨서
새로고침 이식, 그리고 모바일↔데스크톱 버전 전환 추천 배너. 넷 중 둘째가 압도적으로 오래 걸렸고
배운 것도 거기서 다 나왔다. 순서대로 쓴다.

## 1. 응원팀 카드에도 수정 진입점

가장 쉬웠다. `/me`에는 프로필 카드와 응원팀 카드가 위아래로 있는데, "수정하기"가 프로필 카드에만
달려 있었다. 응원팀을 바꾸려면 프로필 카드를 눌러 `/me/edit`에 들어가야 한다는 걸 알아야만 했다.
카드에 팀이 그려져 있는데 거기엔 아무 버튼도 없으니, 누르면 바뀔 것 같은데 안 눌리는 상태였다.

다행히 닉네임과 팀은 이미 `/me/edit` 한 화면에서 같이 고치고 `PATCH /api/v1/users/me` 한 번으로
같이 저장된다(ADR 0026, 0027). 그래서 새 화면이나 새 API가 필요 없었고, 응원팀 카드 헤더 우측에
같은 `/me/edit`으로 가는 "수정하기" 링크만 달면 끝이었다. 모바일과 웹 양쪽에 같은 모양으로 넣었다
(두 `FavoriteTeamsCard`는 ADR 0011대로 승격하지 않고 같은 모양으로 동기화하는 복제다).

팀만 따로 바꾸는 별도 화면을 만들까도 생각했는데 접었다. 만들면 `updateMyProfile(현재닉네임, 팀들)`
꼴로 닉네임을 되보내야 하고(안 그러면 7일 쿨다운에 걸린다), 결국 같은 API를 부르는 화면이 하나 더
생길 뿐이다. 진입점만 늘리는 게 맞았다.

## 2. 탭을 다시 누르면 화면이 깜빡이는 문제

여기가 이 세션의 본체다.

### 처음 받은 증상

"홈에서 홈 버튼, 릴스에서 릴스 버튼을 다시 누르면 새로고침은 되는데, 그 뒤로 여러 번 누르면
내용물이 깜빡깜빡한다. 캐싱인지 전역 상태 관리인지 뭔가 이상하다."

재탭 새로고침은 KAN-314에서 넣은 기능이다(ADR 0048). 지금 있는 탭을 한 번 더 누르면 맨 위로
올라가면서 목록을 첫 페이지부터 다시 받는다. 앱에서 익숙한 손버릇이라 넣었는데, 그게 연타에
약했다.

### 첫 진단: 리셋이 씨앗을 다시 심는다

코드를 보니 재탭은 두 가지를 동시에 쐈다.

```ts
function retap(screen?: ScreenKey) {
  requestTop(screen);
  void (screen === "home" ? refreshHome() : refreshReels());
}
```

그리고 `useHomeRefresh`는 이랬다.

```ts
router.refresh();
await queryClient.resetQueries({ queryKey: articleKeys.feed(homeFilter) });
```

`resetQueries`는 이름 그대로 쿼리를 **초기 상태로 되돌린다**. 캐시 엔트리를 비운다는 뜻이다.
문제는 이 앱의 피드가 서버 컴포넌트가 받아 둔 첫 페이지를 씨앗(`initial`)으로 내려주고 클라
무한쿼리가 그걸 `initialData`로 물고 시작하는 구조라는 데 있다.

```ts
initialData: seed ? { pages: [seed.page], pageParams: [null] } : undefined,
```

`initialData`는 캐시가 비어 있을 때만 쓰인다. 평소엔 캐시가 차 있으니 무시된다. 그런데
`resetQueries`가 캐시를 비우는 순간 이 씨앗이 **다시 심긴다**. 그래서 화면이

[보던 목록] → [씨앗] → [새로 받은 목록]

으로 두 번 갈아 끼워진다. 이게 깜빡임이었다. 팀 탭에 있을 때는 더 심했다. 팀 탭 전환은
`history.replaceState`로 URL만 바꾸므로 서버 컴포넌트가 다시 돌지 않고, 그래서 `initialTeam`이
서버가 렌더한 값("ALL")에 머문다. `team !== initialTeam`이면 씨앗이 아예 없어서
`isPending`이 true가 되고 스켈레톤 4개가 뜬다. 리스트 → 스켈레톤 → 리스트다.

여기에 연타 방어가 하나도 없었다. 대조적으로 당겨서 새로고침에는 `busy` 플래그와 최소 스핀
시간(`PULL_MIN_SPIN_MS` 400ms)이 있다. 같은 `useHomeRefresh`를 부르는데 한쪽만 보호받고 있었다.
N번 누르면 RSC 요청 N개와 쿼리 리셋 N개가 겹쳐 각자 임의 순서로 도착하며 매번 트리를 갈아 끼운다.

### 첫 수정: 비우지 말고 줄여서 다시 받기

리셋을 쓴 이유 자체는 타당했다(ADR 0048에 근거가 있다). 무한쿼리를 `invalidateQueries`로
무효화하면 쌓인 페이지를 전부 다시 받는데, 커서 체인이라 앞 페이지가 와야 다음 커서를 알 수 있어
순차로 나간다. 20페이지를 넘긴 상태에서 당기면 요청 20개가 줄지어 나가고 그게 다 끝나야 스피너가
멈춘다. 리셋은 첫 페이지 하나만 받으니 그 문제가 없다.

그래서 "첫 페이지만 받는다"는 성질은 지키고 "캐시를 비운다"는 성질만 버리기로 했다.
`@plick/core/feed-refresh`에 이렇게 뒀다.

```ts
export async function restartFeedQuery(queryClient, queryKey) {
  const data = queryClient.getQueryData(queryKey);
  if (!data || data.pages.length === 0) {
    await queryClient.resetQueries({ queryKey });
    return;
  }
  queryClient.setQueryData(queryKey, {
    pages: data.pages.slice(0, 1),
    pageParams: data.pageParams.slice(0, 1),
  });
  await queryClient.refetchQueries({ queryKey, type: "active" });
}
```

쌓인 페이지를 첫 페이지 하나로 줄인 뒤 refetch한다. 캐시가 비는 순간이 없으니 `initialData`가
다시 심길 일이 없고, 새 응답이 올 때까지 보던 목록이 그대로 남는다. 화면은 한 번만 바뀐다.
페이지를 먼저 줄이기 때문에 refetch도 첫 페이지 하나만 나간다 — 리셋의 장점을 그대로 가져왔다.

연타 방어는 모듈 스코프 in-flight 프로미스로 넣었다.

```ts
let inFlight: Promise<void> | null = null;
// ...
if (inFlight) return inFlight;
```

훅 인스턴스가 탭바와 홈 스크롤 영역 두 곳에 생기기 때문에 `useRef`가 아니라 모듈 스코프에 뒀다.
도는 동안의 재호출은 새 요청을 만들지 않고 같은 프로미스를 돌려준다.

같은 패턴이 남아 있던 자리도 다 바꿨다. 커서가 상해서 400을 받았을 때 첫 페이지부터 다시 받는
`retryNextPage`가 모바일 홈·릴스, 웹 피드·릴스 네 군데에 있었는데 전부 `resetQueries`였다.

### 여기서 사용자 피드백이 붙었다

수정하고 나서 테스트 중인 사용자가 말했다. "로그아웃 시에는 연타해도 문제가 안 생기는데
로그인하고 나서는 문제가 생긴다."

로그인했을 때만 도는 경로를 뒤졌다. 루트 레이아웃이 `isLoggedIn()` 다음에 `getMyProfile()`을
부르니 `router.refresh()`가 더 느려진다는 것, 릴스는 서버에서 토큰을 실어 `likedByMe`를 받지만
기사 피드는 일부러 토큰을 안 싣는다는 것(만료 토큰을 실으면 401로 피드가 통째로 죽어서다) 등이
보였다. 그러다 프록시의 토큰 재발급에 눈이 갔다.

`ACCESS_TOKEN_MAX_AGE`가 15분이다. 이 앱은 BE 토큰에 만료 정보가 없어서 **access 쿠키의 수명을
만료 신호로 쓴다**. 15분이 지나면 브라우저가 쿠키를 버리고, 그 다음 요청은 access 없이 refresh만
달고 프록시에 닿는다. 그러면 프록시가 재발급을 부른다.

```ts
const tokens = await refreshTokens(refreshToken);
```

여기가 문제였다. 탭을 연타하면 RSC 새로고침 요청과 `/be` 피드 요청이 거의 동시에 나간다. access
쿠키가 막 사라진 순간이면 그것들이 **전부 같은 refresh 토큰을 들고 각자 재발급을 부른다**. BE
재발급은 회전 방식이라 한 번 쓴 refresh 토큰은 그 자리에서 무효가 된다. 먼저 닿은 하나만
성공하고 나머지는 401을 받는다. 그리고 프록시의 catch는 그걸 "세션이 끝났다"로 읽는다.

```ts
} catch {
  const response = isProxy ? NextResponse.next()
    : NextResponse.redirect(new URL("/login", request.url));
  response.cookies.delete(AUTH_COOKIES.access);
  response.cookies.delete(AUTH_COOKIES.refresh);
  return response;
}
```

멀쩡한 로그인 상태에서 쿠키가 지워지고 로그인으로 튕긴다. 로그인했을 때만, 그리고 15분에 한 번
찾아오는 그 순간에만 걸리니 간헐적이다.

재발급을 단일 비행으로 묶었다. `@plick/core/refresh`에 `refreshTokensShared`를 더해서, 같은
토큰에 대한 동시 호출은 하나로 합치고, 이미 끝난 회전은 30초간 기억해뒀다가 늦게 온 형제에게
같은 쌍을 돌려준다. 늦게 온 형제까지 챙겨야 하는 이유는 브라우저가 **요청을 시작한 시점의 쿠키**를
싣기 때문이다. 재발급이 끝나 `Set-Cookie`가 내려가도 그 직전에 출발한 요청들은 이미 소모된 옛
토큰을 달고 온다. 기억은 모듈 스코프라 한 서버 인스턴스 안에서만 유효한데, 문제의 버스트는
브라우저 하나가 같은 인스턴스로 보내는 동시 요청이라 이걸로 덮인다.

### 그런데 사용자가 말한 "다른 내용물"은 그게 아니었다

"다른 내용물이라는 게 로그인 리다이렉트가 아니라, 기사면 다른 기사 내용물인 거고 릴스면 다른
릴스 게시물이라는 거야."

내가 증상을 내 가설에 끼워 맞추고 있었다. 재발급 경쟁은 실재하는 버그였고 고친 건 잘한 일이지만,
사용자가 보고 있는 것과는 다른 문제였다. 다시 물어서 정확한 재현 절차를 받았다.

> 특정 기사를 들어가서 좋아요를 누르고 다시 홈에 가서 홈을 연타하면, 그 좋아요 수가
> 0,1,0,1,0,1 이런 식으로 깜빡인다. 내가 좋아요를 누르기 전 숫자가 잠시 보인다.
> 앱을 켰을 때 그 사이에 새 게시물이 올라왔으면, 그 게시물이 올라오기 전 목록이 잠시 보였다가
> 그런다.

이게 훨씬 정확했다. 그리고 이 설명을 듣고 나니 내가 이미 고친 것의 의미가 제대로 보였다.

"잠시 보이는 옛 값"의 정체는 **서버가 내려준 씨앗**이다. 홈이 마지막으로 서버 렌더된 시점의
목록이라, 좋아요를 누르기 전 숫자이고 새 게시물이 올라오기 전 목록이다. 그게 `resetQueries`로
캐시가 빌 때마다 다시 심겼다. 재탭할 때마다 [옛 씨앗] → [새 응답] 두 단계를 밟으니 숫자가
0,1,0,1로 흔들린다.

사용자가 이어서 정리해 줬다. "좋아요뿐만이 아니라 모든 요소들이 그렇겠지? 지금 기사 리스트 자체도
예전 목록이 잠시 되는 거 보면." 맞다. 좋아요 숫자는 그중 눈에 잘 띄는 한 필드일 뿐이고, 씨앗이
다시 심기면 목록 전체가 그 시점으로 되돌아간다. 그래서 첫 수정(`restartFeedQuery`)이 이 증상
전체를 덮는다 — 캐시를 비우지 않으면 씨앗이 다시 심길 자리 자체가 없다.

덤으로 하나 더 고쳤다. 기사 세부의 좋아요는 서버가 준 props를 원본으로 삼아 컴포넌트 state로
드는데(캐시가 없는 화면이라 그게 맞다), 그 기사는 홈·기사·릴스 피드 캐시에도 카드로 들어 있다.
세부에서 하트를 누르고 목록으로 돌아오면 목록은 누르기 전 숫자를 그대로 보여준다. 깜빡임과는
별개로 두 화면이 서로 다른 값을 말하는 상태였다. `syncLikeIntoFeeds`로 확정된 값을 캐시에 든
같은 id의 카드에도 함께 적게 했다. 팀 탭마다 캐시 엔트리가 따로 있어서 어디 들어 있는지 모르므로
도메인 상위 키(`articleKeys.all`, `reelKeys.all`)로 한 번에 훑는다.

### 릴스로 돌아오면 다른 릴이 0.1초 보이는 것

이건 또 다른 원인이었다. 사용자 말: "다른 화면에 갔다가 다시 릴스로 돌아오면 아까 보던 화면이
떠야 하는데, 순간적으로 다른 게시물이 0.1초 보이다가 다시 원래 보이던 게시물이 보인다."

`useReelsCarousel`을 보니 이랬다.

```ts
useEffect(() => {
  if (!embla || restored.current || slideCount === 0) return;
  restored.current = true;
  const target = Math.min(saved.current, slideCount - 1);
  if (target > 0) embla.scrollTo(target, true);
}, [embla, slideCount]);
```

Embla를 0번에서 만든 뒤 **이펙트에서** 저장된 인덱스로 건너뛴다. `useEffect`는 페인트 뒤에 돌기
때문에 그 사이 한 프레임 동안 첫 릴이 화면에 나온다. 그게 0.1초짜리 다른 게시물이다.

재미있는 건 바로 옆 `useScrollRestore`가 같은 함정을 이미 알고 있었다는 점이다. 그 파일 주석에
이렇게 적혀 있다. "되돌리기는 `useLayoutEffect`에서 한다. `useEffect`면 브라우저가 맨 위 상태를
한 번 그린 뒤에 뛰어서 화면이 번쩍인다." 스크롤은 챙겼는데 캐러셀만 빠져 있었다.

`useLayoutEffect`로 바꾸는 것도 방법이지만, Embla 자체가 자기 이펙트에서 초기화되므로 그것만으론
부족하다. 대신 Embla 옵션의 `startIndex`를 쓰기로 했다 — 아예 그 자리에서 만들면 중간 프레임이
생기지 않는다. 기존 주석은 "첫 렌더에는 데이터가 없어 0장이라 `startIndex`로는 못 잡는다"고
적고 있었는데, 탭에서 돌아오는 경우엔 쿼리 캐시에 릴이 남아 있어 첫 렌더에 이미 슬라이드가 있다.
그래서 대부분의 경우 `startIndex`가 먹는다. 서버 fetch가 실패해 첫 렌더가 0장인 경우만 기존
이펙트가 폴백으로 받게 남겨 뒀다.

옵션 객체는 `useRef`로 한 번 만들어 고정했다. 매 렌더 새 객체를 넘기면 embla-carousel-react가
옵션이 바뀐 걸로 보고 계속 다시 초기화한다.

기사 목록 쪽에도 같은 계열의 문제가 있어서 손봤다. `useScrollRestore`는 `useLayoutEffect`에서
`scrollTop`을 되돌리는데, 그 시점에 문서가 아직 짧으면 브라우저가 값을 끝까지만 깎는다. 그러면
첫 페인트가 엉뚱한 자리(목록 위쪽 다른 기사들)로 나가고 콘텐츠가 늘어난 뒤에야 제자리로 튄다.
원래 rAF 한 프레임만 재시도하던 걸 도달할 때까지 최대 30프레임(약 0.5초)으로 늘렸다. 사용자가
손을 대면(touchstart·wheel) 즉시 접어서 조작과 싸우지 않게 했다.

## 3. 웹에도 당겨서 새로고침

모바일에는 KAN-314에서 만든 당겨서 새로고침이 있는데(`usePullToRefresh`), 웹은 없었다. 웹도
좁은 화면에서 열면 모바일처럼 쓰게 되니 홈과 기사 목록에 같은 손버릇을 붙였다.

이식하면서 결정적으로 달랐던 게 하나 있다. 모바일은 `AppShell`이 `h-[100dvh] overflow-hidden`이고
실제로 스크롤되는 건 그 안의 `ScrollArea` 엘리먼트다. 웹은 문서(body) 자체가 스크롤한다. 그래서
리스너를 특정 엘리먼트가 아니라 window에 걸고, 맨 위 판정도 `el.scrollTop`이 아니라
`window.scrollY`로 바꿨다. 나머지 제스처 판정 3단계(맨 위였나 → 슬롭만큼 방향 재기 → 세로가
가로보다 큰가)와 감쇠 곡선, 상수 값은 그대로 가져왔다. 두 앱에서 같은 손맛이 나야 해서다.

`{ passive: false }`로 직접 리스너를 다는 이유도 같다. React가 JSX의 `onTouchMove`를 passive로
걸어서 거기서는 `preventDefault()`가 무시된다.

여기서 예상 못 한 함정을 하나 만났다. 콘텐츠를 밀어 내리려면 감싸는 div에 `transform`을 걸어야
하는데, **transform이 걸린 요소는 그 안의 `position: sticky`에 대해 컨테이닝 블록이 된다**.
웹에는 sticky가 두 군데 있다. `SiteHeader`(top-0)와 홈 사이드바(top-22). 처음에 화면 전체를
감쌌더니 헤더 고정이 풀렸다.

두 가지로 풀었다. 첫째, `SiteHeader`를 껍데기 밖에 두고 본문만 감쌌다. 둘째, transform 스타일을
제스처가 도는 동안만 단다 — `translateY(0)`도 컨테이닝 블록을 만들기 때문에 늘 달아 두면 사이드바
sticky가 깨진다. 손을 뗀 뒤 복귀 애니메이션 동안은 스타일이 남아야 해서(안 그러면 툭 끊긴다)
`settling` 상태로 그 구간을 붙잡았다가 전환 시간이 지나면 뗀다.

받아 주는 조건은 lg(1024px) 미만으로 뒀다. 데스크톱 터치스크린에서 당겨질 이유가 없고, 위의
사이드바 sticky 문제를 아예 만들지 않는다.

## 4. 버전 전환 추천 배너

`m.plick.co.kr`을 PC에서 열면 PC 버전을, `plick.co.kr`을 폰에서 열면 모바일 버전을 권하는 상단
배너다. 둘 다 X로 닫을 수 있고, 닫으면 localStorage에 남겨 다시 안 뜬다.

자동 리다이렉트는 하지 않기로 했다. 도메인을 강제로 바꾸면 사용자가 일부러 고른 주소를 뺏는
셈이고, 공유 링크가 `window.location.origin` 기준이라(ADR 0047) 리다이렉트가 링크 의미까지
바꿔 버린다. 권하기만 한다.

판별은 UA 스니핑이 아니라 뷰포트로 한다. 이 코드베이스의 반응형 판단이 전부 뷰포트 기준이고
(웹의 lg 분기, SEO alternate의 `MOBILE_ALTERNATE_MEDIA`), 틀려도 배너 하나라 대가가 없다.
웹 쪽은 아예 `MOBILE_ALTERNATE_MEDIA`를 그대로 재사용했다 — "이 조건이면 모바일 URL"이라고
크롤러에 이미 선언해 둔 기준이니 사람에게 권하는 기준도 같아야 맞다.

배너 링크는 지금 보던 화면으로 건너뛰게 했는데, 두 앱의 라우트가 완전히 같지는 않다. 기사
목록(`/articles`)은 데스크톱 전용이라 모바일엔 없다. 그래서 짝이 있는 경로(`/`, `/reels`,
`/teams/[slug]`, `/articles/[id]`)만 경로를 이어 붙이고 나머지는 상대 앱 홈으로 보내는
`crossSiteUrl`을 `@plick/domain/cross-site`에 뒀다. 두 앱이 같은 규칙을 써야 하고 한쪽만 고치면
조용히 어긋나는 종류라 도메인에 뒀다.

첫 렌더에는 아무것도 그리지 않고 마운트 뒤 조건이 맞을 때만 켠다. 서버에서는 창 크기도
localStorage도 알 수 없어서, 서버가 뭔가를 그리면 하이드레이션이 어긋난다.

배치는 앱마다 갈렸다. 모바일은 `AppShell` 안 맨 위에 `shrink-0`으로 뒀다 — 셸이 `h-[100dvh]`로
높이를 못박고 자식이 flex column이라 `shrink-0`이 없으면 눌린다. 웹은 화면마다 `SiteHeader`가
따로 있어서 전역 자리가 루트 레이아웃밖에 없다. 흐름에 얹었으므로 스크롤하면 배너는 올라가고
sticky 헤더가 상단에 붙는다.

## 이번에 남은 것

가장 크게 배운 건 두 번째 항목에서 증상을 내 가설에 맞춰 읽었다는 점이다. "로그인했을 때만
문제가 생긴다"는 말을 듣고 인증 배관을 뒤져서 재발급 경쟁을 찾아냈는데, 그건 진짜 버그이긴
했지만 사용자가 보고 있던 건 아니었다. "다른 내용물"을 로그인 화면으로 넘겨짚었고, 사용자가
"기사면 다른 기사, 릴스면 다른 릴스"라고 바로잡아 줘서야 방향이 맞았다. 정확한 재현 절차를
먼저 받았으면 훨씬 빨랐다. 증상 설명이 모호할 때는 가설을 세우기 전에 재현 절차부터 받아야 한다.

기술적으로 남는 교훈은 **`initialData`와 `resetQueries`를 같이 쓰면 안 된다**는 것이다. 서버가
씨앗을 내려주는 구조에서 캐시를 비우는 건 "새로 받는다"가 아니라 "서버 렌더 시점으로 되돌린다"에
가깝다. 그 시점이 얼마나 낡았는지는 아무도 모른다. 비우는 대신 줄여서 다시 받는 게 맞다.

그리고 transform이 sticky의 컨테이닝 블록을 만든다는 것. 알고는 있었지만 "당겨서 새로고침"을
이식하면서 그게 걸릴 거라고는 미리 생각하지 못했다. 조건부로 스타일을 다는 것으로 풀었는데,
복귀 애니메이션 구간을 따로 붙잡아야 해서 코드가 한 겹 더 생겼다.
