# 0109. KAN-418 토론(투표) 기능 — 모바일 + 웹 구현

## 무엇을 했나

KAN-418 티켓으로 토론 기능을 붙였다. 하단 탭바(웹은 GNB)에 토론 메뉴가 생기고, 투표형
게시물 리스트(`/debates`)가 열리고, 카드를 누르면 소속 기사로 간다. 투표 카드는 기사
상세와 릴 세부(모바일 시트·웹 패널) 양쪽에 들어가고, 릴스에는 "토론 중" 칩이 붙는다.
디자인 계약은 [ADR 0108](0108-vote-ui-figma-mockups.md)에서 확정해 둔 프로토타입 파일의
T1·T2·V3×3(모바일)과 W13~W15(데스크톱)다.

계획 단계에서 스웨거 문서만 믿지 않고 be-verify 서브에이전트로 로컬 BE를 실제로 두들겼는데,
이게 나중에 크게 돈이 됐다. 문서에 없는 사실이 둘 나왔기 때문이다.

## BE 계약 — 문서와 달랐던 두 가지

엔드포인트 자체는 단순하다. `GET /api/v1/debates`는 파라미터도 페이지네이션도 없는 배열이고,
`GET /api/v1/articles/{id}/debate`는 그 한 건(articleId 없이), `PUT /api/v1/debates/{id}/vote`는
`{optionType: "OPTION_A"|"OPTION_B"}`를 받아 최신 집계 셋(`voteCountA/B`, `myVote`)만 돌려준다.
재투표는 에러가 아니라 입장 변경이고 같은 값이면 멱등이다. `GET /api/v1/reels`에는 카드마다
`debate` 필드가 인라인으로 붙었다.

실측으로 안 것 첫째. 마감 판정의 실기준이 `closesAt` 시각이 아니라 기사
`content_type`(DEBATE=열림, FINISH=마감)이었다. `closesAt`은 표시용 힌트일 뿐, 리스트 필터도
투표 차단(409 `DEBATE_CLOSED`)도 content_type만 본다. 처음엔 `isDebateClosed(closesAt)` 헬퍼를
만들어 시각으로 판정했는데, BE 소스(`DebateService`)를 확인하고 전부 걷어냈다. 지금은
기사 상세 응답에 `contentType`을 추가로 매핑해 기사 화면만 마감을 판정하고, 리스트와 릴스는
BE가 애초에 열린 토론만 주므로(마감 기사는 리스트에서 빠지고 릴 카드의 debate도 null) 판정할
일 자체가 없다.

둘째. 릴스 응답에 `contentType`(GENERAL/DEBATE/FINISH)이 있고, debate 블록은 DEBATE 카드에만
실린다. 그래서 릴의 "토론 중" 칩은 `debate != null` 하나로 끝난다 — 마감 릴은 자연히 빠진다.

## 공용 레이어 — 처음부터 패키지로

이번엔 웹과 모바일을 같은 세션에 구현하기로 해서, ADR 0011 게이트를 거칠 것도 없이 데이터
레이어를 처음부터 패키지에 뒀다. `@plick/domain`에 `Debate`·`DebateListItem`·`VoteOption`·
`DebateVoteState` 타입과 `formatDebateTimeLeft`·`formatDebateCloseAt` 헬퍼, `@plick/core`에
`debates.ts`(fetcher + 경계 변환)·`debateKeys.ts`·`debate-sync.ts`(투표 집계를 토론 리스트·릴스
피드 캐시에 옮겨 적는 헬퍼, `like-sync.ts`와 같은 이유·같은 방식)를 만들었다.

투표 카드 본체(`VoteCard`)는 `@plick/ui`에 뒀다. 상태·뮤테이션을 소유하지 않는 제어형
컴포넌트로, 앱마다 `DebateVoteCard`라는 클라 경계가 감싸서 서버 액션(`voteDebate`)·낙관적
갱신 훅(`useDebateVote`)·로그인 게이트를 묶는다. 서버 액션과 훅을 앱별로 복제한 건 댓글과
같은 판단이다 — 쿠키 이름과 AuthProvider가 앱 로컬이다. 이 과정에서 `@plick/ui`가 처음으로
`@plick/domain`에 의존하게 됐다. 여태 ui 컴포넌트는 구조적 props(`{code, name}`)로 도메인을
피해 왔는데, VoteCard는 `Debate` 객체 자체가 본체라 구조적으로 풀면 호출부마다 메타 문자열
조립이 중복된다. 의존성 추가가 더 싸다고 봤다.

`useDebateVote`는 `useLikeToggle` 뼈대 그대로다. 상태는 호출부가 소유하고 훅은 `onChange`로
되돌려주되, 같은 토론이 토론 리스트·릴스 피드 캐시에도 살아 있어 갱신·확정·롤백마다
`debate-sync`로 캐시까지 함께 맞춘다. 낙관적 갱신은 누르는 즉시 내 표를 옮긴다 — 처음이면
고른 쪽 +1, 입장 변경이면 이전 쪽 -1에 새 쪽 +1. 응답이 오면 서버 집계로 덮어 그 사이 다른
사람 표까지 반영한다.

## 화면 — 기존 뼈대의 축소판

토론 리스트는 기사 목록의 축소판이다. 팀 필터도 무한스크롤도 없어서(BE에 파라미터가 없다)
`ArticlesFeed` 같은 200줄짜리가 아니라 `useQuery` + 서버 씨앗 + 재탭/당겨서 새로고침만 있는
얇은 `DebatesFeed`가 됐다. 탭 추가는 예상대로 연쇄였다 — `TABS` 상수에 한 줄 넣는 걸로 안
끝나고 `ScreenKey`에 "debate", `view-state`의 `topTicks` 초기값, `useDebatesRefresh` 훅,
`TabBar` retap 분기까지 다섯 군데를 같이 만졌다. 웹은 반대로 `NAV_LINKS` 한 줄이면 데스크톱
내브와 햄버거 메뉴에 다 반영됐다.

기사 상세는 `Promise.allSettled` 배치에 `getArticleDebate`를 한 줄 추가했다. 404
`DEBATE_NOT_FOUND`가 "투표형 게시물이 아니다"라는 정상 신호라 fetcher가 던지지 않고 null로
돌려주게 했고, 토론 조회만 실패해도 페이지는 뜬다(댓글 씨앗과 같은 판단). 티켓에서 사용자가
말한 그대로다 — 릴스는 피드가 토론을 인라인으로 주니 그대로 그리고, 기사는 API를 직접
불러야 한다.

시드가 없어 검증을 못 하는 상태라, be-verify에게 공유 DB에 일회용 debates 3행(진행 2 + 마감 1)을 심게 하고 테스트 유저로 투표→입장 변경→멱등 재투표→DB 대조까지 돌렸다. 브라우저 검증은
민팅한 토큰을 `document.cookie`로 심어서 했다 — HttpOnly가 아니어도 서버는 요청 쿠키 헤더만
본다(ADR 0044의 요령).

## 모프가 중간에 끊긴 이유 — button이 div로 바뀌고 있었다

ADR 0108에서 투표 전/후를 같은 상하 스택 지오메트리로 못박은 건 "같은 DOM에서 fill 폭·높이·
색만 트랜지션하면 그림 그대로 모프된다"는 계산이었다. 실제로 그렇게 짰는데, 사용자가 써 보니
"애니메이션이 중간에 커트된다", "늘어날 때는 아예 애니메이션이 없다"는 피드백이 왔다.

원인은 트랜지션 값이 아니라 React 재조정이었다. 처음 구현에서 "이미 내 선택인 트랙은 다시
못 누르게" 하려고 누를 수 있는 트랙만 `<button>`, 아닌 트랙은 `<div>`로 갈라 그렸다. 그런데
투표하는 순간 `isPending`이 서면서 두 트랙의 onVote가 undefined가 되고, React는 button과
div를 다른 타입으로 보고 DOM을 버리고 새로 만든다. 새로 마운트된 요소는 트랜지션의 출발점이
없으니 최종 상태로 즉시 뜬다 — 커트가 아니라 아예 재생성이었던 것. 요소 타입을 button으로
고정하고 재탭 차단을 `locked` 가드(클릭 핸들러에서 무시)로 바꾸니 모프가 끝까지 돌았다.
"조건에 따라 태그를 바꾸면 그 요소의 전환은 다 죽는다"를 몸으로 배웠다.

## 사용자 피드백으로 다듬은 것들

구현을 보면서 실시간으로 피드백이 왔고 그 자리에서 반영했다.

- "내 선택" 글자 제거 — `✓ 지른다`의 체크와 솔리드 필이면 충분하다는 판단. 뺐다.
- 트랜지션 500ms가 너무 빨랐다. 800ms로 늘렸다(fill 폭·색과 트랙 높이 동일).
- 각 선택지의 득표수가 보여야 한다 — 결과 상태에서 라벨 아래 "1,165표" 줄을 넣고, 두 줄이
  된 만큼 결과 트랙 높이를 한 단씩 키웠다.
- "오늘의 투표" 배지가 어색하다 — "진행 중"으로 바꾸고, 마감 카드는 같은 자리가 톤 죽은
  "마감" 배지가 되게 했다.
- 릴스의 토론 중 태그가 번쩍여야 한다 — 점만 깜빡이던 걸 칩 전체가 accent 글로우로
  번쩍이는 `debate-live` 키프레임(box-shadow + brightness)으로 바꿨다. 키프레임은 양쪽 앱
  globals.css에 복제다(`snap-x-carousel`과 같은 규약).
- 웹 릴스에도 투표가 보여야 한다 — 원래 데스크톱 릴 시안이 없어 뺐던 범위인데 요청으로
  넣었다. 이 시점에 `DebateLiveChip`이 두 앱 공용이 돼 `@plick/ui`로 승격했고, 웹
  `DebateVoteCard`도 기사·릴 두 화면 공용이 돼 `_components`로 올렸다. 웹 릴 패널은 릴을
  갈아타도 마운트가 유지되는 구조라 `key={reel.id}`로 카드 상태를 릴마다 새로 시작한다.

자잘한 버그도 하나 잡았다. 득표율을 `pctB = 100 - pctA`로 만들었더니 0표 마감 카드에서 B가
100%로 떴다. 0표는 양쪽 다 0%다.

## 검증 중에 헷갈렸던 것 — 사라진 토론 릴

웹 릴스에서 토론 릴이 안 보여서 한참 의심했다. BE를 직접 때리면 debate가 붙어 오는데
브라우저에선 첫 10장에 토론 릴이 아예 없었다. 정체는 둘의 조합이었다. localhost 쿠키는
포트를 가리지 않아서 :3001에서 심은 테스트 토큰이 :3000에도 실려 가고 있었고, 로그인 릴스
피드는 이미 본 릴을 BE가 걸러 준다. 테스트하면서 토론 릴들을 다 열어 봤으니 로그인 피드에서
그 릴들이 빠진 것. 릴 딥링크(`/reels/{id}`)로 앵커하니 정상적으로 칩과 투표 카드가 떴다.
"안 나온다 = 버그"로 달려들기 전에 누가 어떤 계정으로 보고 있는지부터 확인할 일이다.

## 남긴 것

- 시각 표기(`남은 시간`·`오늘 … 마감`)는 렌더 시각 파생이라 `suppressHydrationWarning`을
  달았다(릴 상대 시각과 같은 관용).
- 공유 DB에 검증 시드가 남아 있다 — debates 2·3·4(기사 8032·7806·7844, content_type도
  DEBATE/FINISH로 바꿔 둠), 테스트 유저 `KAN-418-test`(user 64). 정리 SQL은 이 세션 로그에
  있고, 이어지는 검증에 쓸 수 있어 일부러 안 지웠다.
- `handoff.md`의 옛 `FeedPost.debate` 추정 계약과 이번 실계약은 다르다 — 진영별 댓글은
  기획에서 빠졌고(ADR 0108), 결과 공개 게이트는 내 투표 또는 마감이다.
- 마감(FINISH) 릴은 BE가 debate를 null로 줘서 릴에서는 마감 결과를 볼 수 없다. 릴에서도
  보여주려면 `contentType`을 보고 기사 단건 debate를 따로 불러야 한다 — 필요해지면 후속.

## 이어서: 마감 릴에서도 결과 보이기

마감(FINISH) 릴은 릴에서 결과조차 못 본다는 TODO를 바로 이어서 처리했다. 기획 판단도 하나
확정됐다 — 마감된 토론은 투표한 적 없는 사람에게도 결과가 바로 보이고 상호작용만 불가하다.
"투표하면 결과가 열려요" 게이트는 열린 토론에만 의미가 있고, 마감이면 투표라는 대가 자체를
치를 수 없기 때문이다. 카드 게이트(`showResults = closed || myVote`)는 처음부터 그렇게 짜여
있어 화면 쪽 수정은 없었다.

릴 쪽은 BE 수정 없이 FE에서 풀었다. 릴 카드 응답에 이미 있던 `contentType`을 `ReelCard`에
매핑하고, 시트/패널이 열릴 때 FINISH 릴이면 `useArticleDebate` 훅으로 기사 단건 토론을
받아(`debateKeys.article`, `useArticleReporters`와 같은 패턴) 표시 전용 `VoteCard`를 마감
상태로 그린다. 열린 릴은 여전히 피드 인라인 데이터를 그대로 쓴다.
