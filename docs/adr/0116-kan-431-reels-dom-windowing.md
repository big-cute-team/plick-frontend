# 0116. 릴스 DOM 윈도우잉 — 4,291노드가 781이 되고, 가짜 누수를 쫓았다 (KAN-431)

2026-08-31. 덩어리 5(인터랙션)의 두 번째 레버. 성능 감사 #17이 지적한 "릴스 DOM 무제한
누적"을 잡았다. 릴 50장을 스크롤하면 DOM이 602 → 4,291노드로 릴당 92개씩 선형으로 늘고
상한이 없던 것을, 보고 있는 릴 ±3 밖의 내용을 비워 50장에서도 781노드로 평평하게 만들었다.
구현 자체는 순탄했는데, 검증 단계에서 "누수처럼 보이는 것"을 만나 힙 스냅샷으로 범인을
추적하는 샛길이 재밌었다. 결론부터 말하면 누수가 아니라 DevTools 자신이었다.

## before — 릴당 92노드, 상한 없음

KAN-430을 시작하며 떠 둔 before 시리즈(`_workspace/perf-raw/chunk5-before/dom-accumulation.json`)가
그대로 이 작업의 출발점이다. Embla API를 React fiber에서 꺼내 `scrollNext(true)`로 릴을
한 장씩 전진시키며 10장마다 쟀다.

| DOM 릴 수 | DOM 노드 | 마운트된 트윗 임베드 |
| --------- | -------- | -------------------- |
| 10        | 602      | 3                    |
| 30        | 2,404    | —                    |
| 50        | 4,291    | 43                   |

정확히 선형이다. 화면에 보이는 릴은 한 장인데 지나온 릴의 트윗 임베드 43개와 `<img>`
123장이 전부 마운트 상태로 남아 있었다. fetch 게이팅(KAN-429)이 요청 "시점"은 ±2 창으로
잘 늦춰 놨지만, 한 번 그려진 DOM은 영영 해제되지 않는 구조였다.

## 설계 — 빈 섹션 골격을 남기는 이유

무한스크롤 리스트의 윈도우잉이면 가상 스크롤 라이브러리를 붙이는 게 정석이지만, 릴스는
사정이 다르다. 스크롤러가 브라우저가 아니라 Embla 캐러셀이고(KAN-277에서 CSS scroll-snap
대신 채택), Embla는 슬라이드 "요소"들의 개수와 높이를 재서 스냅 지점을 계산한다. 슬라이드를
DOM에서 아예 빼 버리면 스냅 지도가 무너지고, KAN-276에서 공들여 만든 reInit 운동 상태
복원과도 얽힌다.

그래서 요소는 남기고 내용만 비웠다. `REELS_DOM_WINDOW`(3) 밖 릴은 `<section>` 골격만
렌더한다 — 클래스가 같아 높이(100dvh)가 보존되므로 Embla 입장에선 아무 일도 없다.
ReelItem 컴포넌트 자체는 마운트를 유지한다. 훅 규칙 위반 없이 조건부 반환만 하면 되고,
KAN-429의 fetch 래치(`embedFetchStarted`) 같은 상태가 살아남아서, 창에 다시 들어올 때
"이미 받아 본 릴"이라는 사실을 기억한다.

창 크기를 fetch 창(±2)보다 한 장 큰 ±3으로 잡았다. 창에 재진입한 릴은 내용을 다시
그려야 하는데, 그 재마운트가 화면에 걸리는 ±1에 닿기 전 두 장 밖에서 끝나 있게 하는
여유다.

디테일이 하나 있었다. 임베드 영역의 아래선을 재는 ResizeObserver 이펙트가 `titleMotion`만
의존성으로 갖고 있어서, 창 밖에서 태어난 릴(제목 요소가 없어 측정 불가)이 창에 들어와도
다시 재지 않았다. `inWindow`를 의존성에 추가해 창 진입 시 측정이 다시 돌게 했다 —
빠뜨렸으면 재진입 릴의 임베드가 제목 위까지 늘어지는 버그가 됐을 것이다.

부수 효과로 SSR도 가벼워졌다. 첫 렌더의 activeIndex가 0이라 서버 HTML부터 창 밖 6장이
빈 `<section></section>`으로 나간다. 첫 로드 DOM이 602 → 435노드가 된 이유다.
(view-state 스토어가 persist를 안 붙이는 덕에 서버와 클라 첫 렌더의 인덱스가 항상 같아
하이드레이션 불일치 걱정이 없었다 — 이건 설계가 아니라 운이 좋았던 쪽에 가깝다.)

## after — 평평해졌다

| DOM 릴 수    | before | after |
| ------------ | ------ | ----- |
| 10 (첫 로드) | 602    | 435   |
| 20           | 1,506  | 705   |
| 30           | 2,404  | 724   |
| 40           | 3,332  | 737   |
| 50           | 4,291  | 781   |

50장에서도 창 안 7장 + 빈 골격 43장 = 781노드. 마운트된 임베드는 43 → 6개. 되감기
검증도 깨끗했다 — 10장을 되감아도 재진입 릴의 내용이 즉시 복원되고 `/api/tweet` 재요청이
0건이다. react-tweet의 swr 캐시가 살아 있어서 언마운트했다 다시 그려도 네트워크가 안
나간다. 사용자 실기기 검증에서도 되감기 복원에 깜빡임이 없었고, 재진입 릴에서 시트
열기·드래그(KAN-430의 CSS 변수 경로)도 정상이었다.

## 샛길 — 우상향 그래프의 범인은 우리가 아니었다

장표용으로 Chrome 성능 모니터의 "DOM 노드" 그래프를 찍다가 이상한 걸 봤다. 문서 안
노드는 673개(콘솔 실측)인데 모니터는 6,798을 가리키며 계속 우상향했다. 윈도우잉이
만들었다 버리는 노드들이 detached 상태로 쌓이는 건 예상 범위인데, GC가 돌면 떨어져야
할 숫자가 힙 스냅샷(전체 GC 강제)을 떠도 5,608에서 꿈쩍하지 않았다. 진짜 누수라면
윈도우잉이 만든 신규 버그다.

스냅샷에서 `Detached` 필터로 인벤토리를 확인하니 `<div>` 1,159개, `<a>` 538, Text 864,
`<article>` 46(언마운트한 임베드 수와 일치) — 창 밖으로 나간 릴 내용 전부가 수거되지 않고
있었다. 아무 detached 노드나 골라 보관자(Retainers) 체인을 따라가 보니 끝이
`blink::InspectorDOMAgent → blink::InspectorCSSAgent → (GC roots)`였다.

DevTools였다. DevTools가 열려 있으면 DOM 에이전트가 DOM 변이를 추적하며 자기가 본
노드를 내부 맵에 붙잡고, 그 참조가 detached 노드의 GC를 막는다. 요소 탭을 안 열고
DevTools를 껐다 켜도 마찬가지였다 — DOM 도메인이 활성화되는 순간부터 추적이니, 성능
모니터를 보려고 DevTools를 여는 행위 자체가 관측을 오염시킨다. 실사용자 브라우저에는
DevTools가 없으므로 창 밖 노드는 정상 수거된다. 코드는 무죄, 계측이 유죄.

덕분에 "detached DOM이 늘어난다 = 누수"가 아니라는 걸 체득했다. detached는 GC 후에도
남아야 누수고, GC 후에도 남는다면 보관자 체인을 열어 소유자가 내 코드인지 계측 도구인지
먼저 봐야 한다. 이 챕터에서 KAN-427(폰트), KAN-430(will-change)에 이어 세 번째로
"그럴듯한 가설을 실측이 뒤집은" 사례가 됐다.

## 하지 않은 것

- TanStack `maxPages`: 감사에 "검토"로 적혀 있었는데 빼기로 했다. 쿼리 캐시의 페이지
  배열은 JSON이라 DOM 대비 무게가 미미하고, maxPages로 앞 페이지를 버리면 되감기에서
  커서 재조회가 필요해진다 — 커서 400 복구(KAN-404)와 얽히는 복잡도 대비 얻는 게 없다.
- web(데스크톱) 릴 패널: 구조가 달라(ReelViewer) 별도 티켓 몫이다.
