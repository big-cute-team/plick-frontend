# 0178. 공유 링크에 `?path=share`를 박아 확산 유입을 잡는다

KAN-578. 2026-09-28.

## 무슨 일이었나

유입 경로를 재는 배관은 KAN-542([ADR 0161](0161-analytics-headers-proxy.md))에서 깔았다. 두 앱의
`proxy.ts`가 페이지 요청마다 URL의 `?path=`(없으면 `utm_source`)를 읽어 `plick_path` 쿠키에 심고, 이후
메인 API로 가는 모든 요청에 `X-Plick-Path` 헤더로 싣는다. 파라미터가 없으면 쿠키 값을 그대로 쓰고,
쿠키도 없으면 `direct`다. 서버는 모르는 값을 `unknown`으로 접는다.

문제는 우리 서비스가 스스로 만드는 링크, 즉 공유 버튼이 복사해 주는 주소에는 아무 표식이 없었다는 점이다.
기사 공유 링크는 `https://m.plick.co.kr/articles/12` 그대로였다. 이 링크가 커뮤니티나 카톡방에 퍼져서
누가 타고 들어오면 URL에 `path`가 없으니 경로 판정이 검색으로 들어온 사람, 주소를 직접 친 사람과 같은
덩어리로 떨어진다. 커뮤니티형 서비스라 링크 확산이 주요 유입일 텐데, 그게 실제로 사람을 데려오는지 판단할
수 없는 상태였다.

## Referer로는 왜 안 되나

KAN-577([ADR 0177](0177-marketing-headers-proxy.md))에서 외부 유입 호스트(`referrer`)도 헤더로 보내기
시작했다. 처음엔 이걸로 확산 유입을 대충 가를 수 있지 않을까 생각했다. `Referer`는 브라우저가 링크를 따라
이동할 때 "어디서 왔는지"를 요청 헤더에 적어 주는 값이다.

그런데 이 값은 우리가 통제할 수 없다. 브라우저 기본 정책(`strict-origin-when-cross-origin`)은 다른
사이트로 넘어갈 때 경로를 빼고 도메인만 보낸다. 출발한 페이지가 `no-referrer`를 걸어 두면 아예 비어서 온다.
그리고 이번 일의 핵심인 카카오톡, 인스타그램 같은 인앱 브라우저는 링크를 새 웹뷰로 열면서 대체로
Referer를 싣지 않는다. 공유 링크가 가장 많이 퍼지는 자리에서 가장 안 잡히는 셈이다.

반대로 공유 버튼이 만드는 링크 문자열은 전부 우리 코드가 조립한다. 여기에 `?path=share`를 박아 두면
그 링크가 어디로 몇 번 복사돼 퍼지든 쿼리는 같이 따라다니고, 타고 들어온 첫 요청에서 프록시가 읽는다.
값 `share`는 BE 허용 목록(`insta`, `facebook`, `ad`, `ad_tv`, `share`, `direct`)에 이미 있어서 서버
쪽 작업은 없었다.

## 공유 주소가 만들어지는 자리

먼저 공유 대상이 몇 군데인지 셌다. 티켓은 기사, 릴스, 경기, 팀을 예로 들었는데 코드를 뒤져 보니
공유 기능은 두 앱 모두 기사와 릴 두 곳뿐이었다. 경기(라이브)와 팀 화면에는 공유 버튼이 없다.
그리고 두 곳 모두 같은 길을 탄다.

1. 호출부가 `articleSharePath(id)` 또는 `reelSharePath(id)`로 앱 내 경로를 만든다.
2. `ShareDialog`에 `path`로 넘긴다.
3. `ShareDialog`가 마운트된 뒤 `shareUrl(path)`로 `location.origin`을 붙여 절대 주소를 만들고, 그 문자열을
   화면에 보여 주면서 `useCopyLink`로 복사한다.

`shareUrl`이 유일한 병목이라 여기 한 곳만 고치면 복사되는 주소와 화면에 보이는 주소가 같이 바뀐다.
나중에 경기나 팀 공유가 생겨도 `ShareDialog`를 거치는 한 자동으로 따라온다. 두 앱 `_utils/share.ts`가
같은 구현을 복제하고 있어서 두 파일을 같이 고쳤다.

## 쿼리 합치기 규칙은 공용 패키지로

티켓 조건 중 두 개가 규칙이다. 기존 쿼리가 있으면 합쳐 붙이고, 이미 `?path=`가 있으면 중복되거나 덮어쓰지
않는다. 지금 넘어오는 경로에는 쿼리가 없어서 문자열 끝에 `?path=share`를 이어 붙여도 당장은 돈다. 하지만
그러면 `/articles/3?tab=comments`가 들어오는 날 `?`가 두 번 들어간 주소가 나온다.

그래서 `URL` 객체로 파싱해 `searchParams`로 다뤘다. `searchParams.set`은 기존 쿼리 뒤에 키를 더하고 해시
(`#c9`)는 제자리에 둔다. 유입 경로가 이미 있으면 손대지 않고 입력을 그대로 돌려준다(무엇을 "이미 있다"로
볼지는 처음에 잘못 정했다가 리뷰에서 고쳤다. 아래 절에 적었다). 덮어쓰지 않는 이유는
캠페인 링크(`?path=insta`)를 그대로 공유하는 경우를 생각해서다. 그 링크를 받은 사람은 원래 캠페인의 흐름
위에 있는 게 맞고, `share`로 바꿔 버리면 캠페인 성과가 공유로 샌다. `append`로 하나 더 붙이면 `path`가
두 개가 되는데, 프록시의 `readPathParam`은 `searchParams.get`이라 첫 값만 읽으니 결과는 같지만 URL이
지저분해지고 서버 로그에서 헷갈린다.

이 함수(`withSharePath`)와 값(`SHARE_PATH`)은 `@plick/core/analytics`에 뒀다. `plick_path`를 읽는
`readPathParam`과 `PATH_QUERY_PARAMS`가 이미 거기 있어서, 쓰는 쪽과 읽는 쪽 계약을 한 파일에서 볼 수 있다.
이 파일은 `import`가 하나도 없는 순수 모듈이라 클라 컴포넌트에서 가져와도 서버 전용 코드가 딸려 오지 않는다
(이미 PC/모바일 전환 배너가 클라에서 `DEVICE_ID_COOKIE`를 가져다 쓰고 있다). 또 앱 폴더가 아니라 패키지에
있어서 `tests/unit`의 `node --test`로 바로 돌릴 수 있다.

## 링크를 타고 들어오면 벌어지는 일

`?path=share`는 경로 쿠키만 바꾸는 게 아니다. KAN-577의 `resolveMarketing`은 URL에 유입 파라미터가
하나라도 있으면 "새 유입"으로 보고 마케팅 쿠키(`plick_mkt`)의 여섯 칸을 통째로 갈아엎는다. 판정에
`readPathParam`을 쓰니 `path=share`도 새 유입이다. 예를 들어 어제 광고(`fbclid`)로 들어왔던 사람이 오늘
친구가 보낸 공유 링크로 다시 오면, 광고 클릭 식별자가 지워지고 경로가 `share`로 바뀐다. 오늘의 방문을
광고 덕으로 세지 않는다는 뜻이라 의도에 맞다. 이 동작을 단위 테스트 하나로 고정해 뒀다.

## 검증

단위 테스트(`tests/unit/share-path.test.mjs`)는 여섯 경계를 본다. 붙인 값을 `readPathParam`이 `share`로
읽는지, 공유 진입이 지난 광고 값을 비우는지, 기존 쿼리와 해시가 보존되는지, 이미 있는 `path`를 덮거나
겹치지 않는지(두 번 적용해도 같은지), `utm_source`만 있는 링크를 지키는지, 빈 `path`나 형식 밖 `path`를
`share` 하나로 갈아 끼우는지다(뒤의 둘은 리뷰 뒤에 더했다).

실제 화면은 prod BE를 붙인 웹 dev 서버에서 봤다. 여기서 한 번 막혔다. 브라우저 패널에 전에 다른 BE로
받아 둔 로컬 토큰 쿠키가 남아 있어서 prod BE가 "유효하지 않은 토큰"으로 거절했고 기사 화면이 에러
경계로 떨어졌다. 패널의 쿠키를 지우는 대신 Playwright로 새 브라우저 컨텍스트를 열어 확인했다.
기사 공유 다이얼로그에 `http://localhost:3000/articles/5664?path=share`가 보였고 클립보드에도 같은 값이
들어갔다.

그다음 그 링크를 새 컨텍스트로 열었더니 `plick_path` 쿠키가 안 생겨서 잠깐 당황했다. 원인은 프록시의
크롤러 판정이었다. `CRAWLER_UA_PATTERN`에 `headlesschrome`이 들어 있어서, 헤드리스 브라우저는 검색
크롤러처럼 취급돼 쿠키를 심지 않는다. 크롤러가 쿠키를 받아 봐야 다음 요청에 안 들고 오니 의도된 동작이다.
UA를 카카오톡 인앱 브라우저 문자열로 바꾸자 `plick_path=share`가 심겼다. curl로도 웹과 모바일 각각
`Set-Cookie: plick_path=share`가 나오는 것, 기존 쿠키가 `insta`여도 공유 링크 진입이면 `share`로 갱신되는
것을 봤다.

마지막으로 헤더가 BE까지 실제로 가는지 봤다. 받은 헤더를 파일에 적기만 하는 파이썬 에코 서버를 8099에
띄우고 웹 dev 서버의 `API_BASE_URL`을 거기로 돌렸다. 공유 링크로 페이지를 열자 서버 컴포넌트가 부른
게스트 발급, 기사, 댓글, 토론 요청 네 개가 모두 `X-Plick-Path: share`를 달고 왔다. 쿠키만 들고 브라우저
쪽 `/be` 경로로 요청했을 때도 같았다. 서버 측 fetch와 브라우저 fetch 두 경로 모두 확인한 셈이다.

## 리뷰에서 걸린 것: "키가 있다"와 "경로가 있다"는 다르다

push 전 헤드리스 리뷰(`scripts/review/pr-review.sh`)가 WARN 두 개를 냈다. 하나는 실제 구멍이었다.
처음 구현은 `searchParams.has("path")`로 "이미 있으면 그대로"를 판정했다. 그런데 `?path=`처럼 값이 비었거나
`?path=a b`처럼 형식 밖이면 프록시의 `readPathParam`은 그걸 없는 것으로 보고 넘어간다. 키는 있는데 프록시
입장에선 경로가 없는 링크가 되는 것이다. 이러면 공유 표식도 안 붙고 경로도 안 잡혀서 결국 이 티켓이 막으려던
그 `unknown`/`direct`로 샌다.

같은 틈이 반대 방향에도 있었다. `?utm_source=naver`만 달린 광고 링크를 공유하면 `path` 키가 없으니
`share`를 붙이는데, 프록시는 `path`를 `utm_source`보다 먼저 읽으므로 원래 광고 유입이 `share`로 덮인다.
"덮어쓰지 않는다"는 조건을 문자 그대로는 지켰지만 뜻으로는 어긴 셈이다.

둘 다 판정 기준을 프록시와 맞추면 풀린다. `has("path")` 대신 `readPathParam(searchParams) !== null`을 본다.
프록시가 유효한 경로로 읽을 값이 있으면 그대로 두고, 없으면 `set("path", "share")`로 갈아 끼운다. `set`은
같은 이름의 키를 전부 지우고 하나만 남기니 빈 `path`가 남아 둘이 되는 일도 없다. 쓰는 쪽과 읽는 쪽이 같은
함수를 쓰니 앞으로 `PATH_QUERY_PARAMS`에 폴백 키가 늘어도 자동으로 따라간다. 이 두 경우를 테스트로 더했다.

다른 WARN은 `new URL`이 파싱에 실패하면 던진다는 지적이었다. 입력이 늘 `location.origin`과 앱 내 경로로
조립된 절대 주소라 실패할 길이 없어서 코드는 두고 JSDoc에 그 전제를 적었다. INFO로 나온 두 앱 `share.ts`
복제는 이번 변경과 무관한 기존 구조라 손대지 않았다. 공유한 본인이 자기 링크를 열어도 `share`로 잡힌다는
지적도 있었는데, 그 경우 그 사람은 이미 쿠키가 있는 기존 방문자라 방문자 수보다는 경로 쿠키 갱신 문제다.
작은 오차로 보고 넘겼다.

## 남은 것

지금은 "공유로 들어온 사람 수"까지만 보인다. 어느 기사가 퍼졌는지 보려면 링크에 대상 식별자를 같이 실어야
하는데, 기준선을 잡은 뒤 필요해지면 늘리기로 했다(티켓의 범위 밖 항목).

`resolveEntryPoint`의 주석은 `share_link` 진입을 "공유 링크는 표식이 없다"는 이유로 화면 경로만으로는
못 낸다고 적어 뒀다. 이제 표식이 생겼으니 `path=share` 첫 요청의 진입 화면을 `share_link`로 낼 수 있다.
진입 화면 값은 BE 이벤트 정의와 맞물려 있어 이번에는 건드리지 않았다.
