# 0081. CloudFront + S3로 정적 자산을 떼는 계획 세우기

이번 세션에도 코드는 안 짰다. 배포 v2([deploy-v2.md](../deploy-v2.md), ADR
[0067](0067-deploy-v2-plan.md)·[0068](0068-deploy-v2-groundwork.md))를 끝내고
운영하던 중에 인프라 쪽 피드백을 받았고, 그걸 우리 구성에 맞게 번역해서
계획 문서([deploy-v3-cdn.md](../deploy-v3-cdn.md))로 굳혔다. 티켓 없이 시작한
작업이라 브랜치는 `feature/deploy-v3-cdn`이다.

## 받은 피드백과, 우리가 이미 알고 있던 문제

피드백의 요지는 이랬다. 3티어에서 프론트는 두 버전이 동시에 떠 있는 순간이
있고, 사용자 브라우저에는 이전 버전 청크가 캐시돼 있다. 로드밸런서는 그 요청을
신규 인스턴스로 꽂는데 거기엔 다른 빌드의 파일이 있으니 불일치가 난다.
그러니 S3와 CloudFront를 써서 청크를 버전별로 들고 있어야 한다.

읽자마자 낯익었다. v2를 컷오버하던 첫 배포에서 정확히 이걸 밟았고,
[deploy-v2.md](../deploy-v2.md) §11에 "코드가 같아도 빌드가 다르면 Next 청크
해시가 달라서 HTML을 준 인스턴스와 정적 자산 요청이 떨어진 인스턴스가 어긋나면
`_next/static` 404가 난다"고 적어 뒀다. §14 맨 끝에는 "완전히 없애려면 정적
자산을 S3 + CloudFront로 분리해야 하고, 후속 과제로 둔다"고까지 써 놨다.
그때는 컷오버를 무사히 끝내는 게 우선이라 미뤘던 건데, 외부에서 같은 지적이
들어오니 미룰 이유가 없어졌다.

## 짚고 넘어간 것 — 버전 접미사는 필요 없다

피드백에는 이런 예시가 있었다.

```
_next/static/chunks/xxx-v1.js
_next/static/chunks/xxx-v2.js
```

"이런 식으로 버전을 가져야 한다"는 건데, 이 부분은 그대로 받아들이면 안 된다고
판단했다. 우리가 뭘 해서 버전을 붙이는 게 아니라 Next가 이미 붙이고 있다.
webpack/Turbopack이 청크를 뽑을 때 파일 내용의 해시를 이름에 넣어서
`chunks/main-app-a1b2c3.js` 같은 이름이 되고, 페이지 매니페스트류는
`static/<buildId>/...` 아래로 들어간다. 빌드가 다르면 파일명이 이미 다르다.
그래서 두 세대의 산출물을 같은 디렉터리에 나란히 부어도 서로 덮어쓰지 않는다.

그러면 왜 404가 나는가. 이름이 겹쳐서가 아니다. 그 파일을 가진 서버가
사라져서다. 지금은 청크가 EC2 인스턴스의 로컬 디스크에만 있고, Blue/Green은
인스턴스를 통째로 갈아치운다. Blue가 종료되는 순간 그 세대의 청크는 세상
어디에도 없다. 구세대 HTML을 들고 있는 브라우저가 그 파일을 부르면 신세대
인스턴스는 "그런 거 없는데"라고 답할 수밖에 없다.

정리하면 필요한 건 "버전이 붙은 파일명"이 아니라 "두 세대 이상을 동시에 들고
있는 창고"다. 그게 S3다. 결론은 피드백과 같지만 이유가 다르고, 이유가 다르면
설계도 달라진다. 파일명 규칙을 손대는 작업이 아니라 파일이 사는 곳을 옮기는
작업이다. `next.config`는 결국 한 줄도 안 건드리게 됐다.

그리고 이 관점으로 보니 문제 범위가 원래 생각보다 넓다는 것도 보였다.
피드백은 "블루/그린 겹침 구간"을 얘기했는데, 겹침이 끝나고 배포가 완전히 끝난
뒤에도 배포 전에 열어 둔 탭이 남아 있으면 똑같은 일이 난다. 그 탭이 소프트
내비게이션을 하면 자기가 아는 옛 청크를 새로 부르기 때문이다. 겹침 1~2분짜리
문제가 아니라 "사용자가 탭을 닫을 때까지"의 문제다. 계획서 §0에 이걸 따로
적었다.

## 판단 1. assetPrefix를 안 쓴다

CDN 분리라고 하면 보통 `assetPrefix`를 별도 CDN 도메인(`cdn.plick.co.kr` 같은)
으로 잡는 그림을 먼저 떠올린다. 처음엔 나도 그 그림이었다. 그런데 피드백에
같이 들어 있던 구조를 다시 보니, CloudFront를 서비스 도메인 그 자리에 세우고
CloudFront 안에서 경로로 오리진을 가르는 방식이었다. `/_next/static/*`이면
S3로, 나머지는 ALB로.

이러면 정적 자산도 브라우저 입장에서는 같은 오리진이다. `assetPrefix`가 필요
없다. 덤으로 CORS 설정, 폰트의 crossorigin 속성, 서드파티 쿠키 얘기가 전부
안 나온다. Next 코드는 지금 그대로 두고 인프라만 바뀐다.

이게 왜 되는지 한 번 더 확인했다. 사용자가 처음 접속하면 브라우저는 아직
어떤 청크가 필요한지 모른다. 그냥 `/`를 요청한다. CloudFront에서 이건
`/_next/static/*`에 안 걸리니 기본 비헤이비어로 가고, ALB를 거쳐 EC2가 HTML을
만들어 준다. 그 HTML 안에 `<script src="/_next/static/chunks/...">`가 들어 있고,
브라우저가 그걸 부르는 순간부터 CloudFront가 S3 쪽으로 보낸다. 처음엔 캐시가
없으니 S3까지 다녀오고 그 뒤로는 엣지에서 바로 나간다. 피드백에서 설명한
흐름 그대로다.

## 판단 2. CloudFront 배포를 2개로

여기서 한 번 막혔다. 처음엔 배포 하나에 alias 두 개(`plick.co.kr`,
`m.plick.co.kr`)를 붙이면 되겠다고 생각했는데, 그러면 S3 오리진을 어떻게
가르는지가 안 풀린다. web과 mobile은 둘 다 `/_next/static/...`이라는 똑같은
경로를 쓰는데, S3에서는 서로 다른 곳을 봐야 한다. 청크 파일명이 콘텐츠 해시라
충돌할 일은 거의 없지만, 앱이 다른데 같은 버킷 경로에 섞어 붓는 건 나중에
문제가 생겼을 때 원인을 못 찾는 구조다.

CloudFront 비헤이비어는 경로 패턴으로만 갈린다. Host 헤더로는 못 가른다.
이걸 확인하고 나서 선택지가 둘로 좁아졌다.

하나는 CloudFront Function을 붙여서 Host를 보고 URI 앞에 `/web`이나 `/mobile`을
붙이는 것. 배포를 하나로 유지할 수 있다. 다른 하나는 도메인마다 배포를 하나씩
두고 각 배포의 S3 오리진 경로를 다르게 주는 것.

후자로 갔다. 배포 하나를 아끼자고 엣지에서 도는 함수를 하나 얹는 교환이 안
맞는다고 봤다. 함수는 배포·롤백 경로가 하나 더 늘고, 잘못되면 전 요청이
영향을 받는데 디버깅은 CloudFront 로그로만 해야 한다. 반면 배포 2개는 도메인
2개, 대상 그룹 2개(`tg-front-web`·`tg-front-mobile`)라는 지금 구조와 그대로
대응된다. 콘솔에서 봤을 때 "이 배포가 저 도메인"이라고 바로 읽힌다.

## 판단 3. ALB 오리진을 origin.plick.co.kr로

이건 문서를 쓰다가 발견한 함정이다. CloudFront 오리진 도메인에 ALB의 기본 DNS
이름(`xxx.ap-northeast-2.elb.amazonaws.com`)을 그냥 넣으려다가, CloudFront가
오리진에 HTTPS로 붙을 때 오리진 인증서를 오리진 도메인 이름과 대조한다는 게
걸렸다. ALB에 붙어 있는 인증서는 `plick.co.kr`과 `*.plick.co.kr`짜리다.
`elb.amazonaws.com` 이름과는 안 맞으니 오리진 연결 자체가 실패한다.

CloudFront와 ALB 사이를 HTTP로 두는 방법도 있지만, ALB의 80 리스너가 지금
443으로 리다이렉트하도록 돼 있어서 그걸 건드려야 하고, 무엇보다 엣지에서
오리진까지 평문이 되는 게 마음에 안 들었다.

Route 53에 `origin.plick.co.kr` A 별칭을 ALB로 하나 더 만들고 그걸 오리진
도메인으로 주기로 했다. 와일드카드 인증서가 이 이름을 덮으니 HTTPS가 그대로
성립한다.

여기서 한 번 더 헷갈렸던 게 있다. 오리진 이름이 `origin.plick.co.kr`이면
ALB의 호스트 헤더 규칙(`plick.co.kr` → tg-front-web)이 깨지는 것 아닌가?
아니다. TLS 핸드셰이크의 SNI와 HTTP 요청의 Host 헤더는 다른 값이다. CloudFront는
SNI로 오리진 도메인(`origin.plick.co.kr`)을 쓰지만, 오리진 요청 정책을
`AllViewer`로 두면 Host 헤더에는 뷰어가 보낸 `plick.co.kr`이 그대로 실려 간다.
ALB 규칙은 Host를 보므로 계속 먹는다. 둘이 달라도 정상이고, 오히려 이게
성립해야 이 구조가 돌아간다.

## 판단 4. 두 비헤이비어의 정책이 서로 반대다

이 작업에서 제일 헷갈릴 지점이라고 보고 계획서에 크게 적었다.

기본 비헤이비어(ALB 오리진)는 오리진 요청 정책을 `AllViewer`로 둬야 한다.
Host가 넘어가야 ALB 규칙이 살고, 쿠키가 넘어가야 인증이 산다. 이걸 기본값으로
두면 ALB가 등록 안 된 호스트로 판단해 리스너 기본 작업인 404 고정 응답만
돌려준다. 전 화면이 404가 되는 시나리오다.

그런데 S3 비헤이비어에는 `AllViewer`를 붙이면 안 된다. 뷰어의 Host 헤더가
그대로 S3로 가면 SigV4 서명 검증에 실패해서 403이 난다. 이쪽은 오리진 요청
정책을 비워 둬야 한다.

같은 배포 안에서 비헤이비어 둘의 설정이 정반대여야 한다는 게 직관에 어긋난다.
"둘 다 AllViewer로 통일" 같은 실수를 하기 딱 좋아서, 예상 함정 목록(§15)에
403·404 증상과 원인을 짝지어 적어 뒀다.

캐시 정책도 반대다. 기본은 `CachingDisabled`, 정적은 `CachingOptimized`.
HTML을 캐시하면 두 가지가 터진다. 첫째로 HTML이 현재 세대의 청크 이름을 들고
있으니 옛 HTML이 캐시되면 지금 고치려는 문제가 그대로 재현된다. 둘째로,
그리고 이게 더 심각한데, 로그인 쿠키가 담긴 응답이 캐시돼 다른 사용자에게
나갈 수 있다. 함정 목록에서 이 항목만 우선순위 최상으로 표시했다.

## 비용 얘기를 다시 확인한 것

피드백에 "로드밸런서는 들어오는 것과 나가는 것 모두 비용이 청구되는데
CloudFront는 나가는 것만 청구된다"는 대목이 있었다. 대체로 맞는데, 우리 상황에
맞게 좀 더 정확히 정리해 뒀다.

ALB는 바이트 단위로 직접 청구하는 게 아니라 LCU라는 단위로 잰다. 신규 연결 수,
활성 연결 수, 처리한 바이트, 규칙 평가 횟수를 각각 계산해서 제일 큰 축을
기준으로 청구한다. 들어오는 트래픽과 나가는 트래픽이 다 이 계산에 들어간다.

CloudFront는 수신 요청에 데이터 요금이 없고 송출만 과금한다. 여기에 더해 AWS
오리진(ALB든 S3든)에서 CloudFront로 올라가는 데이터 전송이 무료라, 캐시 미스로
오리진에 다녀오는 구간도 공짜다. 그래서 바이트의 대부분인 JS·CSS가 CloudFront
캐시와 S3로 빠지면 ALB의 LCU가 통째로 줄어든다.

다만 기대치는 낮춰 잡았다. HTML, RSC 페이로드, `/be/*` 프록시는 여전히 매 요청
ALB를 탄다. 요청 수는 별로 안 줄고 바이트가 줄어드는 그림이다. "ALB 비용이
사라진다"가 아니라 "제일 무거운 축이 빠진다"가 맞는 표현이다.

WAF 얘기는 그대로 받아들였다. CloudFront 배포에 WebACL을 지정하는 건 클릭
몇 번이고 관리형 규칙 그룹도 바로 붙는다. 지금 WAF가 어디에도 없으니 이번에
같이 넣기로 했다. 단 처음부터 Block으로 켜면 서버 액션의 POST 본문이나 긴
쿠키가 오탐으로 막히는 일이 흔해서, Count 모드로 며칠 보고 전환하는 순서로
적었다.

## API 스펙이 바뀌는 경우 — CDN이 못 푸는 부분

피드백에 "프론트엔드 파일은 캐싱으로 우회할 수 있는데 API 스펙이 바뀌면 안 될
수 있다"는 대목이 있었고, 이게 제일 정확한 지적이라고 봤다.

정적 자산은 S3가 두 세대를 들고 있으면 끝이다. 그런데 구세대 FE 번들이 신세대
BE를 호출하는 건 별개 문제다. 그리고 이 작업을 하면 오히려 노출이 는다.
지금은 구세대 청크를 못 받아서 화면이 깨지고 사용자가 새로고침을 하게 되는데,
S3를 붙이면 구세대 번들이 멀쩡히 살아서 계속 돈다. 살아서 도는 채로 없어진
API 필드를 읽는다.

이건 인프라로 못 푼다고 결론 내고 세 갈래로 나눠 계획서 §14에 적었다.
BE의 하위호환 규약(expand/contract), 배포 순서 고정(BE 먼저), 그리고 Next의
`deploymentId`로 세대 불일치 시 하드 리로드를 유도하는 것. 앞의 둘은 BE와
합의가 필요해서 이번 작업 범위 밖으로 뺐고, `deploymentId`는 현재 Next
버전에서 실제 동작을 확인해야 해서 TODO로 남겼다. 확인 안 한 걸 계획서에
"이렇게 하면 된다"고 쓰지 않으려고 했다.

## 컷오버 순서에서 신경 쓴 것

v2 계획 때 제일 공들였던 게 컷오버 순서였는데(ADR 0067 판단 4), 이번에도
같은 걸 했다. 다만 성격이 다르다. v2는 "기존 EC2를 중지 상태로 남겨 두는
안전핀"이었고, 이번엔 "롤백선이 언제 닫히는가"다.

Route 53을 CloudFront로 돌린 직후에는 되돌리기가 쉽다. A 별칭 대상을 ALB로
바꾸면 끝이다. ALB가 아직 `0.0.0.0/0`으로 열려 있어서 그대로 받는다.

그런데 §9(ALB를 CloudFront 전용으로 잠그기)를 하는 순간 이 길이 막힌다.
보안그룹 소스를 CloudFront 접두사 목록으로 좁히고 리스너 규칙에 커스텀 헤더
검증을 걸면, ALB로 직접 오는 뷰어 트래픽에는 그 헤더가 없어서 전부 404가
된다. Route 53만 되돌리면 오히려 전면 장애다.

그래서 §9를 컷오버 직후가 아니라 며칠 관찰한 뒤로 미뤘다. 진행 순서 표(§16)의
"서비스 영향" 칸에 이 단계만 "없음 (롤백선 닫힘)"이라고 따로 표시했다.
그 대신 컷오버부터 §9까지는 `origin.plick.co.kr`로 CloudFront를 우회할 수 있는
구간이라 길게 끌지 않기로 했다. 며칠은 감수할 수 있는 노출이고, 그 사이에
문제가 생기면 즉시 되돌릴 수 있는 게 더 중요하다고 봤다.

## 리포 변경이 스텝 하나로 끝나는 것에 대해

계획을 다 세우고 보니 리포에서 바뀌는 게 `deploy.yml`의 업로드 스텝 하나뿐이다.

```yaml
aws s3 sync "apps/$APP/.next/static" "s3://$STATIC_BUCKET/$APP/_next/static" \
--cache-control "public,max-age=31536000,immutable"
```

`next.config`도, appspec도, 훅 스크립트도 안 바뀐다. 처음엔 이게 너무 적어서
뭘 놓친 건가 싶었는데, 다시 짚어 보니 맞다. v2에서 이미 standalone 산출물의
`.next/static`을 손으로 따로 다루고 있었고(standalone이 CDN 배포를 전제로 이걸
안 담기 때문에 `Assemble standalone` 스텝에서 복사해 넣고 있었다), 그 "따로
다루는 자리"에 S3 업로드를 한 줄 더하는 것뿐이다. 애초에 Next가 상정한
배포 형태로 돌아가는 셈이라 어색한 곳이 없다.

이 스텝에 걸린 함정은 세 개를 적어 뒀다. `--delete`를 붙이면 안 된다는 것
(붙이는 순간 이 작업 전체가 무의미해진다), `Cache-Control`을 직접 줘야 한다는
것(Next 서버는 붙여 주지만 S3는 안 붙인다), 무효화가 필요 없다는 것(파일명이
콘텐츠 해시라 같은 URL의 내용이 바뀌지 않는다).

`Assemble standalone`의 기존 복사는 당분간 남기기로 했다. CloudFront 비헤이비어가
잘못 걸렸을 때 EC2가 폴백으로 서빙해 주는 안전핀이다. 이중으로 들고 있는 게
낭비 같지만 전환 기간의 보험값으로는 싸다.

## 다음 세션에서 할 것

계획서 §16 표 순서대로 간다. 1~3번(S3 버킷, IAM, deploy.yml)이 리포와 콘솔
작업이고 서비스 영향이 없어서 여기부터 시작한다. 3번이 main에 들어가면 버킷에
산출물이 쌓이기 시작하므로, CloudFront를 세울 때 이미 읽을 게 있는 상태가 된다.
