# 0189. BE가 느려도 탭이 바로 반응하게 (KAN-602: loading.tsx, 섹션 Suspense, 레이아웃 분리)

## 무슨 일이 있었나

2026-10-06 오후, BE 서버 한 대(t4g.micro)가 모든 호출을 2초 넘게 처리하는 상태가 몇 시간 이어졌다. DB는
멀쩡했고(CPU 4%, 지연 1ms 미만) 프론트 서버도 멀쩡했다(ALB p50 0.01초, CPU 2~5%). 그런데 사용자 화면은
멀쩡하지 않았다. 홈에서 하단 탭바의 릴스를 누르면 4초 동안 홈 화면이 그대로 있다가 갑자기 릴스로 바뀌었고,
릴스에서 투표를 누르면 6.3초를 기다렸다. 눌린 건지 안 눌린 건지 알 수 없으니 다시 누르게 되고, 앱이 죽은
줄 안다.

DevTools 네트워크를 보면 상황이 분명했다. 탭을 누른 뒤 나가는 `debates?_rsc=...` 요청 하나가 6.32초
걸렸고, 그동안 받은 바이트가 0이었다. 브라우저는 받은 게 없으니 옛 화면을 들고 있을 수밖에 없다.

BE가 느린 건 BE 티켓에서 다룬다. 이 티켓의 질문은 이거였다. BE가 다시 느려져도 프론트가 멈추지 않으려면
무엇을 바꿔야 하나. 티켓은 세 단계로 나눴다. 1단계는 탭 라우트 다섯 개에 `loading.tsx`를 두는 것,
2단계는 페이지 맨 위의 `await`를 섹션으로 내려 섹션마다 Suspense를 거는 것, 3단계는 루트 레이아웃이
프로필 조회를 기다리지 않게 하고 게스트 발급에 상한을 두는 것이다. 처음에는 PR을 셋으로 나누려 했는데,
1단계를 끝낸 뒤 한 티켓을 한 번에 마무리하기로 하고 같은 브랜치에 이어서 했다. 이 ADR도 세 단계를 다 담는다.

## 왜 기사는 바로 넘어가는데 탭은 멈추나

같은 앱인데 기사 카드를 누르면 바로 뼈대 화면으로 넘어가고, 하단 탭을 누르면 멈췄다. 차이는 파일 하나였다.
`articles/[postId]/loading.tsx`가 있느냐 없느냐다. 이 파일이 있던 곳은 기사 상세와 프로필 편집뿐이고,
홈, 릴스, 투표, LIVE, MY 다섯 탭에는 하나도 없었다.

이게 왜 그렇게 큰 차이를 만드는지는 App Router의 내비게이션 흐름을 따라가 보면 보인다.

### 소프트 내비게이션과 RSC 페이로드

`<Link>`를 누르면 브라우저는 페이지를 새로 받지 않는다. 이걸 소프트 내비게이션이라고 부른다. 대신 Next
클라이언트 라우터가 서버에 `?_rsc=` 요청을 보내 새 화면의 RSC 페이로드를 받는다. RSC 페이로드는 서버
컴포넌트를 렌더한 결과를 직렬화한 데이터다. HTML이 아니라 React 트리를 다시 만들 수 있는 설명서 같은
것이고, 클라이언트 라우터는 그걸 받아서 지금 트리의 바뀐 부분만 갈아 끼운다.

서버 쪽에서 이 페이로드는 스트리밍된다. 서버 컴포넌트 하나가 `await`에서 멈춰 있으면, 그 컴포넌트를
감싼 가장 가까운 Suspense 경계까지만 먼저 내보내고, 경계 안쪽은 데이터가 준비되면 이어서 보낸다.
그런데 경계가 하나도 없으면 먼저 보낼 게 없다. 페이지 맨 위에서 `await getDebates()`를 하고 있으니
그 promise가 풀릴 때까지 페이로드의 첫 바이트도 나가지 않는다. 앞에서 본 "6.32초 동안 0바이트"가
정확히 이 상황이다.

### 클라이언트 라우터는 왜 옛 화면을 들고 있나

또 하나의 축은 React의 트랜지션이다. Next 클라이언트 라우터는 내비게이션을 `startTransition` 안에서
처리한다. 트랜지션 중에 새 트리가 아직 준비되지 않으면(suspend하면), React는 이미 보이고 있던 화면을
지우고 빈 화면을 띄우는 대신 옛 화면을 그대로 유지한다. 사용자 입장에서는 덜컹거리지 않게 하는 좋은
기본값이지만, 새 화면이 6초 뒤에 준비되면 6초 동안 아무 반응이 없는 것과 같다.

트랜지션 중에도 fallback이 보이는 경우가 하나 있다. 새로 마운트되는 Suspense 경계다. 이미 화면에 있던
경계는 트랜지션 중에 fallback으로 되돌아가지 않지만, 이번 내비게이션으로 처음 생기는 경계는 자기
fallback을 바로 보여 준다. `loading.tsx`가 바로 이 경계를 만든다.

### loading.tsx가 하는 일

라우트 폴더에 `loading.tsx`를 두면 Next가 그 폴더의 `page.tsx`(와 그 아래 하위 세그먼트)를
`<Suspense fallback={<Loading />}>`로 자동으로 감싼다. 그래서 흐름이 이렇게 바뀐다.

- 전: 탭 클릭 → 서버가 페이지의 BE 조회를 전부 기다림 → 페이로드 도착 → 화면 전환
- 후: 탭 클릭 → 뼈대(loading) 즉시 표시 → 서버가 BE 조회를 기다림 → 내용으로 교체

뼈대가 "즉시" 뜨는 이유는 두 겹이다. 첫째, `loading.tsx`는 데이터가 없는 정적 컴포넌트라 서버가
페이로드 맨 앞에 바로 실어 보낼 수 있다. 둘째, 동적 라우트를 프리페치할 때 Next는 가장 가까운
`loading.tsx` 경계까지만 미리 받아 둔다. 하단 탭바 링크는 화면에 늘 보이니 프리페치가 되어 있고,
그래서 클릭 순간 서버 왕복 없이 캐시에 있던 뼈대가 바로 그려진다. 루트에 있는 하단 탭바(`TabBar`)는
`usePathname()`으로 활성 탭을 판정하는데, 뼈대가 커밋되는 순간 경로도 새 주소로 바뀌므로 활성 표시도
같이 넘어간다. "눌렸는지 모르는" 상태가 사라지는 것이다.

`page.tsx`는 한 줄도 안 바뀐다. 이게 1단계를 먼저 하는 이유였다. 변경이 작고 효과는 탭 다섯 개 전부에
바로 온다.

## 만들면서 걸린 것들

### 하위 라우트까지 같은 뼈대로 덮이는 문제

처음 생각은 단순했다. `reels/loading.tsx`, `live/loading.tsx`, `me/loading.tsx`를 두면 끝이라고 봤다.
그런데 `loading.tsx`의 경계는 그 폴더의 페이지만이 아니라 아래 세그먼트 전부를 감싼다. `reels/` 아래에는
릴 상세 `/reels/[postId]`가 있고, `live/` 아래에는 경기 상세, 팀, 순위표, 채팅방이, `me/` 아래에는 계정,
차단 목록, 옛 활동 주소가 있다. 이대로 두면 LIVE 목록에서 경기 행을 눌렀을 때 경기 상세 대신 LIVE 목록
뼈대가 뜬다. 날짜 줄과 경기 행 실루엣이 잠깐 보였다가 전혀 다른 생김새의 경기 상세로 바뀌는 건 멈춤보다
나을 수는 있어도 틀린 화면이다.

그래서 라우트 그룹으로 페이지만 한 칸 내렸다. 라우트 그룹은 이름을 괄호로 감싼 폴더(`(feed)`)로, URL에는
나타나지 않고 파일 배치만 나눈다. `reels/page.tsx`를 `reels/(feed)/page.tsx`로 옮기고 `loading.tsx`를
그 옆에 두면, URL은 그대로 `/reels`인데 경계는 `(feed)` 안의 페이지만 감싼다. `/reels/[postId]`는
`(feed)` 밖이라 영향이 없다. LIVE는 `live/(list)/`, MY는 `me/(main)/`으로 같은 처리를 했다. 투표는 하위
라우트가 없어서 `debates/loading.tsx`를 그대로 뒀다.

홈은 원래 `(home)` 그룹 안에 있었고, 그 그룹 아래에 팀 허브 `/teams/[slug]`도 있다. 둘은 같은
`HomeScreen`을 팀만 바꿔 그리는 같은 화면이라 `(home)/loading.tsx` 하나가 둘을 다 덮는 게 오히려 맞다.
하단 탭바의 홈 링크가 마지막으로 보던 팀 URL(`/teams/arsenal` 같은)을 가리키는 경우가 있어서 이건 꼭
필요했다.

페이지 파일이 한 칸 내려가면서 `./_components/ReelsFeed` 같은 상대 import가 깨졌다. 앱 컨벤션
(`apps/CLAUDE.md`)대로 부모를 거쳐야 닿는 import는 `@/reels/_components/ReelsFeed`처럼 절대경로로 바꿨다.

### LIVE 날짜 이동마다 뼈대가 다시 뜨지 않을까

LIVE는 날짜를 `/live?date=2026-10-12` 쿼리로 들고, 날짜 줄을 누르거나 목록을 좌우로 끌면 `router.push`로
같은 라우트 안에서 쿼리만 바꾼다. 이때마다 페이지 전체가 뼈대로 바뀌면 오히려 퇴보다. 날짜 하나 넘길 때마다
상단 날짜 줄까지 깜빡이게 된다.

확인해 보니 그렇지 않다. Next의 layout-router는 세그먼트마다 `LoadingBoundary`를 렌더하는데, 그 경계의
key를 만들 때 쿼리 문자열을 뺀 세그먼트 이름을 쓴다(`createRouterCacheKey(segment, true)`). 쿼리만 바뀌면
경계 key가 같으니 같은 Suspense 경계가 유지되고, 이미 보이던 경계는 트랜지션 중에 fallback으로 돌아가지
않는다. 그래서 날짜 이동은 지금처럼 옛 목록을 들고 있다가 새 목록으로 바뀐다. 탭 전환처럼 다른 라우트에서
들어올 때만 경계가 새로 마운트되며 뼈대가 뜬다. 앞에서 설명한 트랜지션 규칙 그대로다.

### 뼈대를 어디서 가져오나

뼈대는 클라 피드가 씨앗 없이 들어와 직접 받을 때 이미 쓰고 있었다. 투표 카드 스켈레톤, 경기 행
스켈레톤, 소식 행 스켈레톤, 릴 스켈레톤이 각 피드 파일 안에 있다. 문제는 일부가 파일 안의 비공개 함수였다는
것이다. `DebatesFeed.tsx` 안의 `DebateCardSkeleton`, `LiveMatchesFeed.tsx` 안의 `MatchRowSkeleton`,
웹 `MyCommentsList.tsx` 안의 `RowSkeleton`이 그랬다.

`loading.tsx`에서 이걸 새로 그리면 같은 뼈대가 두 벌이 되고, 한쪽만 고치면 서버 로딩과 클라 로딩의 생김새가
갈라진다. 그래서 목록 단위로 뽑아 냈다. `DebateListSkeleton`, `MatchListSkeleton`은 개수까지 품은 목록
뼈대라 피드의 경계 fallback과 `loading.tsx`가 똑같이 `<DebateListSkeleton />` 한 줄을 쓴다. 웹의 내 댓글
줄은 다음 페이지 로딩에도 한 줄씩 쓰여서 행 단위(`MyCommentRowSkeleton`)로 뺐다.

홈은 핫이슈 상자와 소식 섹션의 뼈대를 `HotSectionSkeleton`, `NewsSectionSkeleton`으로 따로 만들었다.
지금은 `loading.tsx`에서만 쓰지만 2단계에서 섹션별 Suspense를 걸 때 그대로 각 섹션의 fallback이 된다.
소식 섹션 행 개수는 `NewsFeed`가 첫 페이지를 기다릴 때와 같은 `ARTICLES_PAGE_SIZE`(10)로 맞췄다.

웹 투표 화면의 탭 목록(`TABS`)은 `DebatesScreen.tsx` 안 상수였는데 뼈대도 같은 라벨을 써야 해서
`_constants/debates.ts`의 `DEBATE_TABS`로 옮겼다. 모바일은 이미 상수 파일에 있었다.

### 정적으로 굳는다는 것

`loading.tsx`는 빌드 때 정적으로 렌더된다. 요청마다 다시 그리지 않는다는 뜻이다. LIVE 뼈대에 진짜
날짜 줄(`DateStrip`)을 넣고 싶었는데, 날짜 줄은 "오늘"을 알아야 한다. 뼈대에서 `todayDateKeyKst()`를
부르면 빌드한 날짜가 박혀 다음 날부터 틀린 오늘을 보여 준다. 그래서 날짜 줄은 칸 모양 실루엣으로 대신했다.
같은 이유로 투표와 MY의 탭 줄도 어느 탭이 열릴지(`?tab=`) 모르니 밑줄 없이 라벨만 뒀다.

반대로 정적인 것은 실물을 그대로 쓴다. 상단바, 하단 탭바, 섹션 제목("핫이슈", "지금 올라온 소식"),
LIVE의 채팅방 배너, 웹 MY의 좌측 메뉴가 그렇다. 실물을 쓰면 내용이 도착해도 그 자리는 한 픽셀도 안
움직인다.

데이터가 필요한 부분은 뼈대에서 뺐다. 홈의 LIVE·VS 띠는 "없는 날"과 같게 비워 뒀고, 웹 우측 레일은
진짜 `SideRail` 대신 `TrendingRailSkeleton`만 세웠다. `SideRail`은 안에서 급상승 조회를 하는 서버
컴포넌트라 뼈대에 넣으면 정적 렌더 때 BE를 부르게 된다. 웹 기사 상세 로딩이 이미 같은 판단을 했다.

MY 뼈대는 로그인 여부를 아직 모른다. 로그인 안내, 게스트 연동 안내, 소셜 로그인 화면 세 갈래 중 가장 흔한
로그인 화면 모양(닉네임 줄, 활동 탭, 목록)으로 잡았다. 게스트로 들어가면 뼈대 다음에 연동 안내가 뜨면서
모양이 한 번 바뀐다. 3단계에서 프로필을 쿠키 기준으로 일찍 가를 수 있게 되면 다시 볼 대목이다.

## 어떻게 확인했나

BE를 실제로 느리게 만들어야 했다. dev BE는 이 IP를 CloudFront가 막고 있어서 prod BE의 익명 GET을 쓰되, 그 앞에 모든 요청을 3초 늦추는 작은 Node 프록시를 스크래치
폴더에 띄웠다. 그리고 `API_BASE_URL=http://localhost:8099`로 mobile, web dev 서버를 띄웠다. 프록시는 저장소에
넣지 않았다.

측정은 처음에 브라우저 패널에서 하려다 접었다. 패널이 숨겨진 상태라 `document.visibilityState`가
`hidden`이었고, 숨은 탭은 타이머와 `requestAnimationFrame`이 느려지거나 멈춘다. 20ms 간격으로 화면을 보던
측정 루프가 제대로 돌 리가 없었다. 그래서 `scripts/store-shots`에 있는 playwright-core로 헤드리스
Chromium을 띄워 측정했다. 하단 탭 링크를 클릭하고 `requestAnimationFrame`마다 DOM이 처음 바뀐 시각과
`animate-pulse` 뼈대가 사라진 시각을 쟀다.

여기서 한 번 헛다리를 짚었다. 첫 측정에서 개선 전인데도 투표 탭이 74ms 만에 바뀌었다. 프록시 로그를 보니
헤드리스 Chromium의 UA(`HeadlessChrome`)가 프록시(`proxy.ts`)의 크롤러 판정에 걸려 게스트 세션을 발급받지
않았고, 그래서 토큰 없는 익명 조회가 Next 데이터 캐시(60초)를 그대로 타고 있었다. 실제 사용자는 게스트든
소셜이든 토큰을 들고 있어 캐시를 못 탄다. 일반 iPhone Safari, macOS Chrome UA로 바꾸자 게스트가 발급됐고
그제야 사용자 상황이 재현됐다.

개선 전 수치는 같은 dev 서버에서 `loading.tsx` 다섯 개를 잠시 `.bak`으로 치워 두고 쟀다. 페이지 코드와
라우트 그룹은 그대로라 차이는 `loading.tsx` 유무뿐이다.

BE 지연 3초, 탭 클릭부터 화면이 처음 바뀔 때까지(ms):

| 탭   | 모바일 전 | 모바일 후 | 웹 전 | 웹 후 |
| ---- | --------- | --------- | ----- | ----- |
| 릴스 | 1230      | 86        | 1082  | 51    |
| 투표 | 3207      | 87        | 6429  | 53    |
| LIVE | 3459      | 79        | 3377  | 59    |
| MY   | 6299      | 78        | 3133  | 50    |
| 홈   | 3403      | 53        | 3359  | 63    |

개선 전 숫자는 그 탭의 서버 조회가 전부 끝난 시각과 같다. MY가 6초인 건 프로필과 활동 조회가 직렬로
3초씩 붙기 때문이고, 웹 투표가 6초인 건 목록 조회 뒤에 LIVE 띠의 경기 조회가 이어지기 때문이다. 개선
뒤에는 BE가 얼마나 느리든 탭 전환이 50~90ms 안에 뜬다. 이 값은 dev 서버 기준이라 프로덕션 빌드에서는
더 짧다.

내용이 채워지는 시각은 바뀌지 않는다. 바뀌면 안 되는 값이기도 하다. 이 단계는 BE를 덜 부르는 게 아니라
기다리는 동안 화면을 먼저 넘기는 것이다.

전환 400ms 뒤(뼈대)와 7초 뒤(내용)를 나란히 캡처해 다섯 탭 모두 뼈대와 실제 화면의 자리가 맞는지 봤다.
상단바, 탭바, 섹션 제목, 채팅방 배너처럼 실물을 쓴 부분은 그대로 있고, 뼈대 자리에 내용이 들어선다.

## 2단계: 가장 느린 섹션 하나가 화면 전체를 붙잡지 않게

1단계로 탭을 누르는 순간의 반응은 해결했다. 그런데 뼈대가 내용으로 바뀌는 건 여전히 페이지 단위로 한 번에
일어났다. 홈 서버 컴포넌트(`HomeScreen`)가 핫이슈, 소식 첫 페이지, 오늘 경기, 투표 리스트 네 조회를
`Promise.allSettled`로 다 기다린 뒤에야 JSX를 돌려줬기 때문이다. `allSettled`라 하나가 실패해도 나머지는
살지만, 하나가 느리면 나머지도 그만큼 기다린다. 그리고 BE가 느릴 때 가장 느린 건 늘 오늘 경기
(`/matches`, p90 5초 이상)였다. 홈 맨 위의 작은 LIVE 띠 하나 때문에 핫이슈와 소식 리스트까지 5초를
기다리는 셈이었다.

### Suspense 경계를 섹션마다 두면 무엇이 달라지나

앞에서 RSC 페이로드는 Suspense 경계 단위로 스트리밍된다고 했다. 페이지에 경계가 하나(`loading.tsx`가
만든 것)뿐이면 페이지 전체가 한 덩어리로 교체된다. 경계를 섹션마다 두면 서버는 껍데기를 먼저 보내고,
섹션은 각자 데이터가 준비되는 순서대로 따로 보낸다. 브라우저 쪽에서 React는 먼저 온 섹션부터 fallback을
실제 내용으로 바꾼다.

이걸 하려면 `await`가 경계 안쪽에 있어야 한다. 페이지 함수 맨 위에서 `await`하면 그 페이지 함수가 통째로
멈추니 경계를 아무리 둬도 소용이 없다. 그래서 조회를 섹션 컴포넌트 안으로 옮겼다. 홈은 셋으로 나눴다.

- `HomeBanners`: 오늘 경기와 투표 리스트를 받아 LIVE·VS 띠를 그린다. fallback은 `null`이다
- `HotSection`: 핫이슈와 트윗 사진 보충(`withTweetPhotos`)까지 받아 상자를 그린다. fallback은 1단계에서
  만든 `HotSectionSkeleton`
- `NewsSection`: 소식 첫 페이지를 받아 `NewsFeed`에 씨앗으로 넘긴다. fallback은 `NewsSectionSkeleton`

`HomeScreen`은 더 이상 async가 아니다. 상단바, 숨은 h1, 소개 문단, 푸터, 탭바는 데이터를 기다리지 않고
바로 나간다. 띠 둘(경기, 투표)을 한 경계에 묶은 건, 따로 두면 띠가 하나씩 들어오며 아래 내용이 두 번 밀리기
때문이다. 띠의 fallback을 `null`로 둔 건 "경기도 투표도 없는 날"과 같은 모양이라서다. 있는 날이면 도착할
때 위에 끼어든다. 레이아웃 시프트가 한 번 생기는 대가를 치르는 대신, 5초 걸리는 띠가 홈 전체를 붙잡지
않는다. 티켓에서도 이렇게 정했다.

에러 처리는 그대로 섹션 안에 남겼다. Suspense 경계 안에서 던진 에러는 가장 가까운 에러 경계(여기서는
루트 `error.tsx`)까지 올라가 페이지 전체를 에러 화면으로 바꾼다. 예전에는 `allSettled`가 섹션별 실패를
접어 "핫이슈를 불러오지 못했어요" 같은 문구만 그 자리에 뒀다. 그 동작을 지키려고 섹션마다 `try/catch`로
감싸 실패를 빈 배열이나 null로 접는다.

씨앗 패턴도 그대로다. 서버가 첫 페이지를 받아 `initial`로 내려 주고 클라 피드가 이어받는 구조
(`InitialArticleFeed`, `InitialReelFeed`)는 손대지 않았고, 그 씨앗을 만드는 `await`만 경계 안으로 들어갔다.
팀 허브의 CollectionPage 구조화 데이터는 첫 페이지 기사로 ItemList를 채우기 때문에 `NewsSection` 안으로
같이 옮겼다.

### 릴스, 투표, LIVE

릴스는 피드 하나라 단순했다. 페이지의 조회를 `ReelsFeedSection`으로 옮기고 fallback에 클라 피드가 쓰던
릴 뼈대를 그대로 뒀다. 첫 릴 임베드 이미지를 preload하는 `<link>`도 같이 옮겼는데, React가 트리 어디에서
렌더한 `<link rel="preload">`든 head로 올려 주므로 위치가 바뀌어도 동작은 같다. 웹은 클라 작업 영역이
씨앗 없이 받을 때 쓰는 바탕과 뼈대를 `ReelsWorkspaceSkeleton`으로 묶어 `loading.tsx`와 fallback이 같이
쓴다.

투표는 모바일이 탭 줄까지 클라 피드(`DebatesFeed`) 안에 있어서 fallback도 탭 줄 라벨과 카드 뼈대를 같이
그려야 했다. 1단계 `loading.tsx`에 있던 그 마크업을 `DebatesFeedSkeleton`으로 뽑아 둘이 같이 쓴다. 웹은
제목과 탭 링크가 서버 컴포넌트라 실물로 먼저 나가고 목록 자리만 `DebateListSkeleton`으로 기다린다.

LIVE는 티켓 범위에 없었지만 경기 조회가 가장 느린 화면이라 같이 했다. 경기 목록(`LiveMatchesSection`)과
순위표(`StandingsSection`)를 각자 경계로 나눠, 상단바, 채팅방 배너, 날짜 줄은 바로 나가고 둘은 따로 온다.
날짜 이동은 1단계에서 확인한 대로 트랜지션이라, 경계가 다시 뼈대로 돌아가지 않고 옛 목록을 들고 있다가 바뀐다.

### 웹 LIVE 띠

웹은 상단 바 바로 밑에 오늘 경기 띠(`LiveStrip`)가 있고, 홈, 투표, LIVE, 기사 상세, 스토리 페이지가 다
쓴다. 이 띠가 async 서버 컴포넌트라 경계 없이 놓이면 그 페이지들이 다 경기 조회를 기다린다. 측정에서 웹
투표가 6초 걸린 것도 목록 조회(3초) 뒤에 띠의 경기 조회가 이어졌기 때문이다.

페이지마다 Suspense를 두르는 대신 `LiveStrip` 자체를 경계를 품은 동기 컴포넌트로 바꿨다. 바깥
`LiveStrip`은 `<Suspense fallback={null}>`만 돌려주고, 실제 조회와 렌더는 안쪽 `LiveStripContent`가 한다.
쓰는 쪽 코드는 그대로라 다섯 페이지가 한 번에 풀렸다.

여기에는 예전 판단을 뒤집은 대목이 있다. 웹 홈은 원래 띠가 스스로 받게 두면 Suspense로 늦게 끼어들며
본문이 밀린다는 이유로, 페이지가 오늘 경기를 받아 `matches`로 넘겨 주고 있었다. 레이아웃 시프트를 피하려고
페이지 전체를 기다리게 한 것이다. 평소 BE가 수십 ms일 때는 맞는 판단이었다. 하지만 BE가 느린 날에는 그
대가가 홈 전체 5초 멈춤이었다. 띠는 데이터 캐시(20초)를 타서, 캐시가 살아 있으면 껍데기와 같은 응답 안에
붙어 와 첫 페인트 전에 자리를 잡는다. 시프트는 캐시가 식었고 BE가 느릴 때만 생긴다. 그 경우라면 밀리는 쪽이
멈추는 쪽보다 낫다고 봤다. `matches` prop은 이제 쓰는 곳이 없어 지웠다.

### 확인

경로마다 다르게 늦추도록 지연 프록시를 고쳤다. `/matches`는 6초, 게스트 발급은 0.5초, 나머지는 3초다.
Node 스크립트로 문서 요청 하나를 받으며 스트림에서 섹션별 마커(`snap-x-carousel`은 핫이슈 트랙,
`scroll-mx-4`는 소식의 팀 탭, `empty:hidden`은 띠 상자)가 처음 나타난 시각을 쟀다. 게스트 쿠키를 들고
모바일 홈을 새로고침한 값이다.

| 섹션                    | 2단계 전(ms) | 2단계 후(ms) |
| ----------------------- | ------------ | ------------ |
| 첫 바이트(상단바, 탭바) | 68           | 91           |
| 핫이슈                  | 6433         | 3196         |
| 소식 리스트             | 6433         | 3197         |
| LIVE·VS 띠              | 6432         | 6396         |

전에는 세 섹션이 6.4초에 한꺼번에 왔다. 후에는 핫이슈와 소식이 자기 조회 시간(3초)에 오고, 띠만 경기 조회
시간(6초)에 따로 온다. 첫 바이트가 둘 다 빠른 건 3단계를 먼저 반영한 레이아웃 위에서 쟀기 때문이다.

prod BE의 경기 API가 이 시간대에 502를 돌려줘서, 섹션 하나가 실패해도 나머지가 뜨는 것도 같이 확인됐다.
띠는 빈 날처럼 사라지고, LIVE 화면의 순위표 자리에는 "순위표를 불러오지 못했어요"만 섰다.

## 3단계: 앱 진입과 새로고침이 프로필 조회를 기다리지 않게

### 레이아웃은 왜 특별한가

1단계와 2단계는 소프트 내비게이션, 즉 탭 전환을 고쳤다. 앱 첫 진입, 새로고침, 외부 링크로 들어오기,
웹뷰 기동처럼 문서를 처음부터 받는 요청은 루트 레이아웃부터 다시 렌더한다. 그런데 루트 레이아웃이 이랬다.

```tsx
const loggedIn = await isLoggedIn(); // 쿠키만 본다
const profile = loggedIn ? await getMyProfile() : null; // BE /users/me
```

레이아웃은 트리의 뿌리다. `<html>`과 `<body>`부터 레이아웃이 그리고 `loading.tsx` 경계도 레이아웃
안쪽에 있으니, 레이아웃이 `await`에서 멈춰 있는 동안에는 응답의 첫 바이트도 못 나간다. BE가 느리면 앱
진입마다 `/users/me` 시간(측정 때 3초)만큼 흰 화면이었다.

이 프로필로 하는 일을 따져 보니 첫 화면에 필요한 건 하나도 없었다. 내 댓글에 수정·삭제 버튼을 달기 위한
userId, 웹 상단 바의 닉네임, 그리고 게스트 여부다. 로그인 여부 자체는 access 쿠키 유무(`isLoggedIn()`)로
이미 안다.

### 프로필을 Promise로 넘긴다

React 19는 서버 컴포넌트가 클라이언트 컴포넌트에 Promise를 prop으로 넘기는 걸 지원한다. 서버는 Promise를
기다리지 않고 "나중에 채워질 값"이라는 참조만 페이로드에 넣고, 풀리면 그 값을 별도 청크로 이어 보낸다.
클라이언트는 `use(promise)`로 그 값을 꺼내는데, 아직 안 왔으면 가장 가까운 Suspense 경계에서 멈춘다.

그래서 레이아웃은 이렇게 바뀌었다.

```tsx
const loggedIn = await isLoggedIn();
const guestExpiresAt = await getGuestExpiresAt();
const profile = loggedIn ? getProfileSeed() : Promise.resolve(null); // await 없음
```

`getProfileSeed()`는 `getMyProfile()`을 불러 `AuthProvider`에 필요한 세 값(게스트 여부, userId, 닉네임)만
추리고 실패는 null로 삼킨다. 이메일이나 응원팀까지 클라이언트로 보낼 이유가 없다.

티켓 초안은 소비처(내 댓글 판별, 로그인 유도 팝업)마다 `use(profilePromise)`로 직접 읽게 하자는 것이었다.
`useAuth()`를 쓰는 곳을 세어 보니 두 앱 합쳐 열 곳이 넘었고, 그 컴포넌트마다 Suspense 경계를 새로 둘러야
했다. 그보다 `AuthProvider` 안에서 한 번만 풀기로 했다. `AuthProvider`는 자식 옆에 아무것도 그리지 않는
`ProfileSeedReader`를 자기 Suspense 경계 안에 하나 둔다. 이 컴포넌트가 `use(profile)`로 값을 꺼내
`useEffect`에서 provider 상태로 올린다. 리더가 멈춰도 그 경계 안에서만 멈추니 형제인 화면 트리는 기다리지
않는다. `useAuth()`의 모양은 그대로라 소비처는 한 줄도 안 바뀌었다.

값이 오기 전에는 userId와 닉네임이 null이다. 내 댓글의 수정·삭제 버튼과 웹 상단 바의 닉네임이 프로필이
도착할 때 붙는다. 게스트 여부는 null로 두면 곤란하다. 게스트에게 소셜 사용자용 문구를 보여 주게 되기
때문이다. 다행히 게스트 마감 쿠키(`guestExpiresAt`)가 있다. 프록시가 게스트를 발급하거나 재발급할 때 심고,
로그인이나 계정 연동 때 지운다. 이 쿠키 유무로 잠정값을 정하고, 프로필이 오면 그 값으로 덮는다.

로그인이나 로그아웃은 서버 액션이 redirect하며 레이아웃을 다시 렌더하므로 새 Promise가 내려온다. 리더는
새 Promise로 다시 멈췄다가 풀리면 상태를 갈아 끼운다. 그 사이에는 직전 프로필을 들고 있어서
`router.refresh()` 때마다 닉네임이 깜빡이지 않는다.

같은 요청 안에서 MY 페이지도 `getMyProfile()`을 부르는데, 둘 다 같은 URL과 옵션의 GET fetch라 Next의
요청 메모이제이션으로 한 번만 나간다. 전에는 레이아웃이 먼저 다 받아 두고 페이지가 그 결과를 재사용했다면,
지금은 둘이 같은 진행 중 요청을 같이 기다린다.

### 게스트 발급에 상한을 둔다

쿠키가 하나도 없는 첫 진입은 레이아웃보다 앞에서 한 번 더 막힌다. 프록시(`proxy.ts`)가 게스트 계정을
발급하기 때문이다(`POST /auth/guest`). 프록시는 응답 쿠키를 심어야 해서 스트리밍 바깥에서 돌고, 발급이
끝나야 페이지 렌더가 시작된다. 측정 때 게스트 발급 3초에 프로필 3초가 직렬로 붙어 첫 바이트가 6.3초였다.

발급을 안 기다릴 수는 없지만 무한정 기다릴 이유도 없다. 원래 발급이 실패하면(BE 다운, 429) 삼키고 익명으로
통과시키는 갈래가 있었다. 게스트는 참여를 앞당기는 편의지 열람의 전제가 아니라서다. 여기에 시간 상한만
더했다. `@plick/core/guest`의 `issueGuest`가 `AbortSignal.timeout(1500)`을 실어 부르고, 1.5초를 넘기면
fetch가 `TimeoutError`로 끊겨 기존 실패 갈래로 떨어진다. 다음 내비게이션이 다시 발급을 시도한다. 두 앱
프록시가 같은 함수를 쓰니 한 곳만 고치면 됐다.

끊긴 요청을 BE가 끝까지 처리해 게스트가 하나 만들어졌다면 그 계정은 쓰이지 않고 14일 마감으로 정리된다.
BE가 1.5초를 넘길 만큼 느린 날에만 생기는 일이라 감수했다.

### 확인, 그리고 dev 서버가 옛 파일을 안 읽던 일

개선 전 값을 재려고 레이아웃, `AuthProvider`, `guest.ts` 세 파일만 `git checkout`으로 이전 커밋 상태로
되돌리고 같은 측정을 돌렸다. 그런데 결과가 개선 후와 똑같이 나왔다. 첫 바이트 70ms, 닉네임 3.1초.
처음에는 Next 16이 루트 레이아웃의 `await`를 기다리지 않고 껍데기를 먼저 보내는 건가 의심했다. 그런데
그러면 1단계 측정 때 첫 진입이 6.3초였던 게 설명되지 않는다.

추측을 그만두고 확인했다. 되돌린 레이아웃의 `<html>`에 `data-kan602="before"`라는 표식 속성을 넣고 다시
받아 보니 응답에 그 표식이 없었다. dev 서버 로그에는 "Compiled"가 찍히는데 실제 응답은 새 코드였다.
Turbopack dev 서버가 `git checkout`으로 바뀐 파일을 반영하지 않은 것이다. 1단계 때 `loading.tsx`를
`.bak`으로 바꾼 건 파일이 사라지는 변화라 잘 먹었던 것 같다. 결국 파일을 되돌린 상태로 dev 서버를 다시
띄우고서야 표식이 보였고 진짜 개선 전 값이 나왔다. 2단계 전 값도 같은 방식(표식 + 재기동)으로 쟀다.

모바일, 지연 프록시 기준 첫 바이트(ms):

| 상황                                  | 3단계 전  | 3단계 후 |
| ------------------------------------- | --------- | -------- |
| 게스트 쿠키로 새로고침                | 3113~3192 | 60~170   |
| 첫 진입(쿠키 없음, 게스트 발급 0.5초) | 3700      | 726      |
| 첫 진입(쿠키 없음, 게스트 발급 3초)   | 6294      | 1651     |

새로고침은 프로필 대기(3초)가 통째로 빠졌다. 첫 진입은 프로필 대기가 빠지고, 게스트 발급이 느리면 1.5초에서
끊긴다. 마지막 줄의 1.65초가 상한 1.5초에 응답 시작까지의 시간을 더한 값이다. 그 경우 게스트 없이 익명으로
들어가 캐시된 공개 조회를 타서, 핫이슈와 소식까지 첫 바이트와 같이 왔다.

회귀는 웹에서 헤드리스 Chromium으로 봤다. 첫 진입 뒤 상단 바는 0.8초, 새로고침 때는 0.13초에 뜨고,
닉네임은 프로필 조회(3초 지연)가 끝난 3.5초쯤 상단 바에 붙었다. 하이드레이션 에러는 없었다. 서버 렌더와
첫 클라이언트 렌더가 둘 다 프로필 없는 상태로 시작하고, 값은 하이드레이션 뒤 effect에서 들어오기 때문이다.
내 댓글 수정·삭제 버튼은 소셜 계정이 있어야 댓글을 쓸 수 있는데 prod BE에 쓰기가 막혀 있어 눈으로 확인하지
못했다. userId가 들어오는 길은 닉네임과 같아서 같은 시점에 붙을 것으로 본다.

## 아직 남은 것

내용이 채워지는 시간은 BE 속도 그대로다. 이 작업은 BE를 덜 부르는 게 아니라 기다리는 동안 화면을 먼저
넘기는 것이다. 그라파나에서 보면 ALB 응답 지연(첫 바이트 기준)은 내려가고 BE 호출 히스토그램은 그대로여야
정상이다. 배포 뒤 이 두 패널로 확인할 몫이다.

토큰을 실은 조회(`likedByMe`가 섞인 릴스, `myVote`가 섞인 투표)는 유저별 값이라 데이터 캐시를 못 탄다.
목록은 익명으로 캐시에서 받고 유저 상태만 따로 얹는 분리는 티켓에서도 별도로 뺐다.

MY는 섹션으로 나누지 않았다. 프로필을 먼저 알아야 로그인 안내, 게스트 연동 안내, 소셜 화면 중 무엇을 그릴지
정해지는 화면이라서다. 게스트가 MY에 들어가면 뼈대(로그인 모양) 다음에 연동 안내로 모양이 한 번 바뀌는 것도
그대로 남았다. 게스트 쿠키로 갈래를 먼저 정하는 방법이 있어 보이지만 이번 범위에서는 뺐다.

import 규칙은 [ADR 0029](0029-layered-architecture-restructure.md), 게스트 발급의 원래 설계는 KAN-514.
