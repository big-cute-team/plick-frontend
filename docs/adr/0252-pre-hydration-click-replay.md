# 0252. 하이드레이션 전에 누른 좋아요를 살리다가, 기사 상세가 하이드레이션되지 않고 있던 걸 찾았다

KAN-750. [ADR 0251](0251-optimistic-like-vote-race-on-open.md)에서 "열자마자 누른 좋아요가 안 먹는다"를 고치다가 원인이 하나 더 남았다. 버튼이 화면에 보인 뒤 React가 그 버튼에 붙기 전의 클릭은 그냥 버려진다. 이 글은 그걸 고친 기록인데, 절반은 고치려던 방법이 기사 상세에서만 안 먹는 이유를 파고든 이야기다.

## 무엇이 문제였나

서버가 보낸 HTML은 스크립트보다 먼저 그려진다. 하이드레이션은 그 HTML에 React가 이벤트 처리기를 붙이는 일이고, 스크립트를 받아 실행한 뒤에야 끝난다. 그 사이의 버튼은 보이기만 한다. `onClick`이 없으니 눌러도 아무 일도 안 일어나고, React는 붙기 전의 클릭을 기억했다가 나중에 처리해 주지 않는다.

0251에서 배포 dev에 재 둔 값이 있다. 캐시가 데워진 데스크톱에서는 틈이 20~110ms라 사람이 그 안에 누르기 어렵다. CPU를 4배 느리게 하고 느린 4G에 캐시를 비우면(중급 폰의 첫 방문에 가깝다) 버튼은 0.7초쯤 보이는데 눌리기 시작하는 건 2.4초쯤이다. 1.7초 동안 눌러도 반응이 없다.

## 폼 제출은 React가 기억해 준다

클릭은 안 되지만 폼 제출은 된다. React 19는 `<form action={함수}>`를 서버에서 그릴 때 두 가지를 한다. `action` 속성에 `javascript:throw new Error('React form unexpectedly submitted.')`라는 표식을 적고, 작은 인라인 스크립트를 HTML에 같이 내보낸다. 그 스크립트는 문서에 `submit` 리스너를 걸어, 표식이 붙은 폼이 제출되면 기본 동작을 막고 `document.$$reactFormReplay` 배열에 폼과 제출 버튼, 폼 데이터를 쌓아 둔다. 인라인이라 번들을 기다리지 않고 HTML을 읽는 순간 돈다. 나중에 React가 하이드레이션을 마치면 이 배열을 훑어 폼의 `action` 함수를 부른다.

그래서 버튼을 폼으로 감쌌다(`packages/ui/src/EarlyClickButton.tsx`).

```tsx
<form action={onPress} className="contents">
  <button
    {...rest}
    type="submit"
    onClick={(event) => {
      event.preventDefault();
      onPress();
    }}
  >
    {children}
  </button>
</form>
```

붙기 전에 누르면 submit 버튼이라 폼이 제출되고, 인라인 스크립트가 모아 뒀다가 붙은 뒤에 `onPress`로 온다. 붙은 뒤의 클릭은 `onClick`에서 제출을 막고 `onPress`를 바로 부른다. 평소 길을 폼으로 보내지 않은 이유가 있다. 폼 `action`은 트랜지션 안에서 돈다. 트랜지션은 "급하지 않은 갱신"이라는 표시라 그 안의 `setState`는 다른 일에 밀릴 수 있는데, 좋아요는 누른 즉시 하트가 차야 한다. 일찍 누른 클릭은 어차피 늦게 처리되는 것이니 트랜지션이어도 상관없다.

폼은 `display: contents`라 배치에 끼어들지 않는다. 부모들이 전부 `flex`에 `gap`이라 자식이 하나 더 감싸여도 달라지지 않는 걸 확인했고, 배포 dev와 로컬에서 버튼과 이웃 버튼의 위치와 크기를 재서 숫자가 같은 것까지 봤다.

붙인 곳은 기사 상세의 좋아요, 릴스 레일의 좋아요, 페이지 안 투표 카드의 선택지다. 투표 카드는 `VoteCard`에 `earlyClick` 옵션으로 넣었다. 의견 창 안의 투표 카드는 이미 댓글 폼 안에 들어 있어서 켜지 않았다. 폼 안에 폼을 두면 브라우저가 안쪽 폼 태그를 버리고, 그러면 서버 HTML과 React가 기대하는 구조가 달라진다.

## 릴스는 되는데 기사 상세는 안 됐다

프로덕션 빌드를 띄우고 느린 폰 조건에서 하이드레이션 전에 클릭을 보냈다. 릴스는 다섯 번 중 네 번 하트가 찼다. 기사 상세는 다섯 번 모두 안 찼다.

단계별로 찍어 봤다. 클릭은 폼 제출이 됐고 `$$reactFormReplay`에도 쌓였다. 그런데 하이드레이션이 끝난 뒤에도 배열이 그대로였고 서버 액션도 안 나갔다. React가 다시 처리하지 않은 것이다.

React 소스를 읽었다. 다시 처리할 때 모아 둔 폼 노드에 React가 붙었는지(`form[internalPropsKey]`)를 본다. 붙어 있지 않으면 건너뛴다. 그래서 모아 둔 폼 노드를 확인했더니 문서에서 떨어져 있었다(`isConnected: false`). 내가 누른 그 버튼이 하이드레이션 뒤에는 화면에 없고, 같은 자리에 새 버튼이 있었다.

버튼 노드에 번호를 매겨 로드 중에 10ms마다 찍어 보니 이렇게 나왔다.

```
267 node1 react=false   서버 HTML의 버튼
296 node1 react=false   (숨겨져 있던 구간이 제자리로 들어옴)
672 node2 react=true    다른 노드. React가 새로 만든 버튼
```

하이드레이션이라면 `node1`에 React가 붙어야 한다. 그런데 `node1`은 버려지고 `node2`가 새로 생겼다. 그리고 이건 내 수정과 무관했다. 배포 dev(수정 전 코드)에 같은 걸 돌려도 똑같았다. 기사 상세는 원래부터 서버가 그린 화면을 이어받지 않고 통째로 새로 그리고 있었다.

## 누가 서버 HTML을 버렸나

가설을 세 번 틀렸다.

처음에는 하이드레이션 불일치를 의심했다. 서버 HTML과 브라우저가 그린 결과가 다르면 React는 그 구간을 버리고 새로 그린다. ISR로 미리 구워 둔 HTML이라 시각에서 파생된 글자("3분 전")가 어긋날 수 있다고 봤다. 그런데 방금 처음 요청해 막 구워진 기사도 똑같이 버려졌고, 개발 모드에서 브라우저 시계를 세 시간 앞당겨도 불일치 경고가 없었다.

다음으로 Next 라우터가 페이지를 다시 받아 갈아 끼우는지 봤다. 그 주소로 가는 RSC 요청은 없었다.

오류 보고도 없었다. `window.reportError`와 콘솔, `error` 이벤트를 전부 걸어 놓고 봤는데 조용했다.

결국 DOM에서 노드를 떼는 호출(`removeChild`)을 가로채 스택을 찍었다. 프로덕션 번들은 함수 이름이 뭉개져 있어 `next build --no-mangling`으로 다시 빌드했다.

```
at clearHydrationBoundary
at commitDeletionEffectsOnFiber
at recursivelyTraverseMutationEffects
```

`clearHydrationBoundary`는 React가 아직 하이드레이션하지 않은 Suspense 경계의 서버 HTML을 지우는 함수다. 오류가 아니라 React가 스스로 그 경계를 "하이드레이션하지 않고 클라에서 그리기"로 돌린 것이다.

React가 그러는 조건이 있다. Suspense 경계는 루트와 따로 하이드레이션된다. 루트가 먼저 붙고, 경계 안쪽은 조금 뒤에 붙는다. 그 사이에 경계 바깥에서 급한 갱신(트랜지션이 아닌 `setState`)이 일어나 컨텍스트 값이 바뀌면 React는 곤란해진다. 경계 안에 그 컨텍스트를 읽는 컴포넌트가 있을 수 있는데, 아직 붙지 않아서 누가 읽는지 모른다. React는 먼저 그 경계를 서둘러 하이드레이션해 보고, 그게 바로 끝나지 않으면 서버 HTML을 버리고 새 컨텍스트 값으로 처음부터 그린다. React 18에서는 이때 "This Suspense boundary received an update before it finished hydrating"이라는 복구 가능 오류를 남겼는데 19에서는 아무 말 없이 한다. 그래서 어디에도 안 찍혔다.

우리 앱에는 그 조건이 정확히 갖춰져 있었다.

- 경계: `articles/[postId]/loading.tsx`. Next는 `loading.tsx`가 있으면 페이지를 Suspense로 감싼다. 기사 상세의 화면 전체가 경계 하나 안에 있다
- 급한 갱신: 루트 레이아웃의 `AuthProvider`와 `AdsProvider`. 둘 다 서버와 같은 값("세션 모름", 광고 "off")으로 그린 뒤 `useLayoutEffect`에서 쿠키와 UA를 읽어 `setState`로 올린다. 서버가 쿠키를 읽지 않게 하려고(KAN-632, 익명 ISR) 고른 구조다. 레이아웃 이펙트 안의 `setState`는 동기 갱신이고, 루트가 붙자마자 돈다. 페이지 경계는 그때 아직 붙기 전이다

릴스(`reels/[postId]`)는 `loading.tsx`가 없어 페이지가 루트와 한 번에 붙는다. 그래서 릴스만 멀쩡했다. 홈은 `loading.tsx`가 있는데도 이어받았다. 서둘러 하이드레이션하는 시도가 그 자리에서 끝나면 버리지 않기 때문이고, 기사 상세는 그 시도가 끝나지 못하는 무언가가 안에 있다. 그게 정확히 어느 컴포넌트인지는 끝까지 좁히지 않았다. 원인 쪽(급한 갱신)을 고치면 어느 경계든 같이 풀리기 때문이다.

개발 모드에서는 재현되지 않는다. 같은 코드인데 `node1`에 그대로 붙는다. 그래서 지금까지 아무도 못 봤을 것이다.

## 트랜지션으로 바꿨다

React 문서가 이 상황에 권하는 방법이 원래 갱신을 `startTransition`으로 감싸는 것이다. 트랜지션 갱신이 붙기 전 경계에 닿으면 React는 경계를 먼저 하이드레이션하고 나서 갱신을 반영한다. 급하지 않으니 기다릴 수 있다.

`AuthProvider`는 하이드레이션 직후의 첫 반영만 트랜지션으로 냈다.

```ts
if (firstRead.current) {
  firstRead.current = false;
  startTransition(apply);
} else {
  apply();
}
```

같은 레이아웃 이펙트가 화면을 옮길 때도 돈다. 로그인이나 로그아웃 뒤 리다이렉트로 화면이 바뀌면 쿠키를 다시 읽는데, 그때 트랜지션이면 옛 세션으로 그린 화면이 몇 프레임 보일 수 있다. 그건 지금처럼 바로 반영한다.

첫 반영이 늦어지는 건 손해가 아니다. 원래 주석은 "레이아웃 이펙트라 사용자는 모름 상태를 한 프레임도 보지 않는다"고 적고 있었는데, 서버 HTML이 이미 "모름" 상태로 그려져 하이드레이션 전 내내 보이고 있다. 새로 보이는 화면이 생기는 게 아니라 같은 화면이 조금 더 가는 것이다. 주석도 그렇게 고쳤다. `AdsProvider`는 마운트 때 한 번만 올리므로 통째로 트랜지션이다.

트랜지션으로 바꾸고 다시 빌드하니 `node1`에 React가 붙었다.

```
290 node1 react=false
612 node1 react=true
```

## 전후

프로덕션 빌드(`next start`, dev BE)에서 CPU 4배, 느린 4G, 콜드 캐시로 쟀다. 수정 전은 배포 dev다. 버튼이 보이자마자 클릭을 보내고 하이드레이션이 끝난 뒤 하트가 찼는지 본다.

| 화면        | 수정 전 | 수정 후 |
| ----------- | ------- | ------- |
| 모바일 기사 | 0 / 3   | 6 / 6   |
| 모바일 릴스 | 0 / 3   | 6 / 6   |
| 웹 기사     | 0 / 3   | 5 / 5   |
| 웹 릴스     | 0 / 3   | 5 / 5   |

틈 자체는 그대로다(1.6~1.9초). 스크립트를 받아 실행하는 시간은 줄이지 않았다. 그 사이에 누른 클릭이 이제는 붙은 뒤에 처리된다.

기사 상세가 서버 HTML을 이어받는지도 전후로 봤다. 수정 전에는 모바일과 웹 모두 버튼 노드가 교체됐고, 수정 후에는 같은 노드에 React가 붙었다.

0251에서 고친 것들도 새 빌드에서 다시 돌렸다. 기사 좋아요(재방문자, 첫 방문자 둘), 릴스 좋아요, 댓글 좋아요, 토론 투표, 릴스 좋아요 수까지 모바일과 웹에서 전부 통과했다. 세션을 올리는 시점을 건드렸으니 그쪽이 깨지지 않았는지가 제일 걱정이었다.

E2E에 회귀 spec을 넷 넣었다(두 앱의 기사와 릴스). 앱 스크립트를 붙잡아 두면(`holdAppScripts`) 화면은 서버 HTML만 그려진 상태로 멈춘다. 거기서 좋아요를 누르고, 버튼에 React가 아직 안 붙었는지 확인하고, 스크립트를 풀어 준 뒤 하트가 차는지 본다. 서버 액션은 앞의 spec들처럼 붙잡아 dev에 남기지 않는다. 로컬에서 세 번씩 통과했고 전체 31개가 프로덕션 빌드와 개발 모드 양쪽에서 통과했다. 같은 넷을 배포 dev에 돌리면 모두 실패한다.

## 확인하지 못한 것, 남긴 것

투표 선택지의 일찍 누르기는 브라우저로 못 봤다. dev에 열린 토론이 없어 서버 HTML에 선택지 버튼이 아예 없다(마감된 카드는 버튼이 아니라 결과 막대다). 좋아요와 같은 컴포넌트를 쓰고, 붙은 뒤의 투표가 그대로 되는 것만 0251의 꾸민 시나리오로 확인했다.

일찍 누르면 하트는 하이드레이션이 끝난 뒤에 찬다. 누른 순간에는 아무 표시가 없다. 그래서 반응이 없다고 한 번 더 누를 수 있는데, 두 번 모였다가 처리돼도 꺼지지는 않는다. 둘 다 같은 렌더의 "지금 안 눌림"을 보고 켜는 요청을 보내고, 좋아요 API가 멱등이다. 누른 순간에 뭔가 보여 주려면 `<head>`에 직접 짠 스크립트가 필요한데 그건 하지 않았다.

댓글 좋아요, 댓글과 공유 버튼, 예측 화면은 손대지 않았다. 댓글은 브라우저가 받아 그리는 목록이라 서버 HTML에 버튼이 없고, 나머지는 다시 누르면 되는 동작이다.

기사 상세에서 서둘러 하이드레이션하는 시도가 왜 끝나지 못하는지는 찾지 않았다. 같은 구조(`loading.tsx` 아래 페이지)인 다른 화면이 조건에 따라 같은 일을 겪었을 수 있는데, 홈만 확인했다. 루트 제공자가 급한 갱신을 내지 않게 됐으니 지금은 어느 경계든 같은 이유로 버려지지는 않는다.

이 수정은 KAN-748 브랜치 위에 쌓았다. 그쪽이 아직 `develop`에 없고, 여기 E2E가 그쪽 픽스처를 쓴다.

## 배운 것

하이드레이션 문제를 볼 때 "React가 붙었는가"만 재면 놓친다. 0251에서 틈을 잴 때 `__reactProps`가 생기는 시각만 봤고, 같은 노드에 붙었는지 새 노드가 생겼는지는 안 봤다. 노드가 교체되고 있다는 건 모아 둔 클릭이 사라지는 걸 보고서야 알았다.

조용한 실패는 로그가 아니라 부작용으로 잡는다. React 19는 경계를 클라 렌더로 돌릴 때 아무것도 남기지 않는다. `removeChild`를 가로채 스택을 본 게 결정적이었고, 이름이 남는 빌드(`--no-mangling`)가 없었으면 그 스택도 못 읽었다.

개발 모드에서 멀쩡하다는 건 하이드레이션에 관해서는 아무것도 보장하지 않는다.
