# 0215. 게스트 발급 라우트와 세션 프록시에 회귀 테스트를 붙였다 (KAN-675)

## 왜 이 테스트가 필요했나

[ADR 0201](0201-guest-issue-off-page-response.md)(모바일 KAN-665)과
[ADR 0204](0204-web-render-cache-port.md)(웹 KAN-667)에서 게스트 발급을 페이지 응답에서 떼어 냈다.
전에는 프록시가 쿠키 없는 페이지 요청마다 BE에서 게스트 토큰을 받아 그 페이지 응답에 `Set-Cookie`로
심었다. 페이지가 정적·ISR이 되면서 그 응답은 `s-maxage`, 그러니까 "CDN이 저장해 다른 사람에게 줘도
된다"는 헤더를 달고 나가게 됐는데, 거기 토큰이 실려 있으면 CloudFront가 한 사람의 토큰을 저장해 다음
사람에게 그대로 내준다. 그래서 발급은 브라우저가 화면을 띄운 뒤 부르는 `POST /api/session/guest`
라우트로 옮겼고, 프록시에는 "쿠키를 심거나 지운 응답은 무조건 `Cache-Control: private, no-store`로
덮는다"는 안전핀을 달았다. `private`은 공유 캐시(CDN)가 저장하지 말라는 뜻이고, `no-store`는 브라우저
캐시를 포함해 어디에도 남기지 말라는 뜻이다.

이 두 자리는 깨져도 화면에서는 아무 티가 안 난다. 안전핀이 빠져도 내 브라우저에서는 페이지가 멀쩡히
뜨고, 사고는 CDN 저장소 안에서 남의 브라우저로 번진다. KAN-667 헤드리스 리뷰가 "이 분기들에 테스트가
없다"를 WARN으로 남긴 이유가 그거다. 사람 눈에 보이기 전에 테스트가 먼저 잡아야 하는 종류다.

티켓은 테스트 말고도 두 가지를 판단하라고 했다. 발급 POST의 남용 방어가 출처·UA 검사뿐인데 그걸로
충분한가, 그리고 발급이 실패한 뒤 재시도를 다음 상호작용에 맡기는 지금 방식이 맞는가.

## 앱 파일을 그대로 테스트에 올리기까지

`pnpm test:unit`은 Node 22의 내장 테스트 러너(`node --test`)로 `packages/*`의 TS 소스를 빌드 없이
직접 부르는 구조다. 지금까지는 `@plick/core`·`@plick/domain` 같은 순수 함수만 테스트했고, 앱 파일
(`apps/*/proxy.ts`, `apps/*/app/api/...`)을 부른 테스트는 없었다.

처음 떠올린 길은 티켓에 적힌 대로였다. `resolveAnalytics`·`forward` 같은 프록시 내부 함수를
`@plick/core`로 떼어 내고 의존성(`issueGuest` 등)을 인자로 받게 바꾼 뒤 그걸 테스트하는 것. 그런데 두
앱의 `route.ts`와 `proxy.ts`를 diff로 맞대 보니 코드는 한 글자도 다르지 않고 주석의 티켓 번호만
달랐다. 이 상태에서 로직을 패키지로 옮기면 테스트를 위해 프로덕션 구조를 크게 흔드는 셈이고, 정작
지켜야 할 건 "앱에 실제로 배포되는 그 파일"이다. 그래서 반대로 갔다. 프로덕션 코드는 건드리지 않고,
테스트가 두 앱의 실제 파일을 그대로 import하게 만들었다. 같은 케이스를 앱 목록을 돌며 양쪽 파일에
건다. 완료 조건의 "두 앱이 같은 테스트를 공유"가 이걸로 채워진다.

막상 import하자 세 번 막혔다.

첫째, `@/` 절대경로. 앱 파일은 `@/_constants/api`처럼 앱 tsconfig의 alias(`@/* → ./app/*`)로 서로를
부르는데, Node는 tsconfig를 모른다. `tests/unit/register.mjs`는 원래 "상대 경로 import가 실패하면
`.ts`를 붙여 한 번 더 찾는" 해석 훅(resolve hook, 모듈 이름을 실제 파일 경로로 바꾸는 단계에 끼어드는
함수)만 걸고 있었다. 여기에 "`@/`로 시작하면 부르는 파일의 URL에서 `/apps/<앱>/`을 찾아
`apps/<앱>/app/` 아래로 풀어 준다"를 더했다. 부르는 쪽이 어느 앱 아래 있는지로 앱을 정하니 모바일
파일의 `@/`는 모바일로, 웹 파일의 `@/`는 웹으로 간다.

둘째, `next/server`. `Cannot find module .../node_modules/next/server`가 떴다. `next` 패키지는
`package.json`에 `exports` 맵이 없고 루트에 `server.js` 파일만 둔다. CommonJS 해석기는 확장자를 알아서
붙여 주지만 ESM 해석기는 확장자 추측을 하지 않는다. 그래서 `next/`로 시작하는 이름이 실패하면 `.js`를
붙여 다시 찾게 했다. 테스트 쪽에서 `NextRequest`를 만들 때도 같은 문제가 있었는데, pnpm은 `next`를 앱
폴더 아래에만 링크하고 저장소 루트에는 두지 않아서 루트의 `tests/unit/`에서는 `next`가 아예 해석되지
않는다. 공용 도구(`tests/unit/support/next-app.mjs`)의 `loadApp(name)`이 앱 폴더의
`node_modules/next/server.js`를 직접 가리키게 해서 풀었다.

셋째, `TypeScript parameter property is not supported in strip-only mode`. 프록시가 부르는
`@plick/core/client`의 `ApiError`가 `constructor(public status: number, ...)`처럼 생성자 매개변수
프로퍼티를 쓴다. 이건 타입 표기가 아니라 "필드 선언과 대입"을 만들어 내는 문법이라, 타입만 지우는
`--experimental-strip-types` 모드는 처리하지 못하고 문법 오류로 멈춘다. `ApiError`를 풀어 쓰는 방법도
있었지만 테스트 도구 사정으로 프로덕션 코드를 고치는 건 내키지 않았다. `test:unit` 플래그를
`--experimental-transform-types`로 바꿨다. 이 모드는 타입을 지우는 데서 그치지 않고 enum이나 매개변수
프로퍼티처럼 런타임 코드가 필요한 문법을 JS로 변환한다. 기존 테스트 144개도 이 플래그에서 그대로
통과했다.

BE는 모듈을 갈아끼우지 않고 전역 `fetch`만 가짜로 바꿨다. 라우트의 `issueGuest`도, 프록시의
`refreshTokensShared`도 결국 `apiFetch` 안의 `fetch(\`${API_BASE_URL}${path}\`)`한 줄을 지나기 때문이다.
가짜`fetch`는 호출 기록(경로, 헤더)을 남기고, 케이스마다 BE 성공 봉투나 에러 봉투를 돌려준다. Node의
모듈 목(mock.module)은 아직 실험 플래그가 하나 더 필요하고 import 순서에 민감해서 피했다.
재발급 쪽은 하나 조심할 게 있었다. `refreshTokensShared`는 같은 refresh 토큰의 재발급을 30초 동안
기억해 두고 형제 요청에 같은 결과를 돌려준다(KAN-379). 모듈 스코프 메모리라 테스트 케이스 사이에도
살아 있어서, 케이스마다 refresh 토큰 값을 새로 만들어 서로 섞이지 않게 했다.

## 무엇을 확인하나

프록시 응답은 Next가 내부 헤더로 표현한다는 점을 이용했다. `NextResponse.next()`는
`x-middleware-next: 1`을, `NextResponse.rewrite(url)`은 `x-middleware-rewrite: <url>`을 달고, 다운스트림
요청 헤더를 바꾸면 `x-middleware-request-<이름>`으로 실린다. 그래서 "Bearer를 실었나", "BE로 직접
rewrite했나", "이번 렌더의 헤더에 유입 경로가 실렸나"를 응답 헤더만 보고 판정할 수 있다.

게스트 라우트(앱마다 9개):

- 크롤러 UA는 403이고 BE를 부르지 않는다.
- `Sec-Fetch-Site: cross-site`는 403. 그 헤더가 없는 옛 브라우저면 `Origin` 호스트를 `Host`와 맞추는데,
  다른 출처와 `Origin` 없음은 403, 같은 출처는 통과.
- 세션이 이미 있으면 `issued: false`이고 BE를 부르지 않는다. 표식 쿠키(`sessionKind`)가 없는 옛 세션이면
  마감 쿠키 유무로 `guest`·`user`를 정해 표식 하나만 심는다.
- 발급 성공이면 쿠키가 정확히 다섯 개(access, refresh, 마감, 세션 종류, 첫 진입 안내)이고 `no-store`다.
  토큰 둘은 HttpOnly, 브라우저가 읽는 셋은 HttpOnly가 아니어야 한다.
- 발급 호출에 쿠키에서 읽은 분석 헤더(유입 경로, 기기, 앱 구분)가 실린다.
- 자연 발급은 로그아웃 출신 표식과 재발급 재시도 가드를 지운다.
- BE 429·500·네트워크 오류는 모두 503이고 `Set-Cookie`가 하나도 없다.

세션 프록시(앱마다 11개):

- 토큰 없는 페이지 요청은, 주소에 `?path=insta&utm_campaign=...&fbclid=...`와 인스타 Referer가 붙어
  있어도 `Set-Cookie`가 없고 `Cache-Control`을 건드리지 않는다. 대신 이번 렌더의 요청 헤더에는
  `X-Plick-Path: insta`가 실린다. 광고 랜딩 화면이 CDN을 타야 한다는 KAN-665의 약속이 이 케이스다.
- access가 살아 있는 `/be` 요청은 Bearer만 싣고 쿠키가 없다.
- 게스트 재발급은 회전된 쌍과 마감·종류 표식을 심고 `no-store`. 소셜 재발급은 마감 표식을 지우고 종류를
  `user`로 바꾸며, 쿠키를 심는 `/be` 응답이라 config rewrites가 아니라 BE 주소로 직접 rewrite한다
  (외부 rewrite는 Next가 미들웨어 응답 헤더를 버리는 문제, ADR 0201).
- 랜딩 쿠키를 든 `/be` 요청은 유입·마케팅 쿠키를 심고 랜딩 쿠키를 지운다. 크롤러는 심지 않는다.
- 크롤러의 분석 쓰기는 204로 끊는다.
- 재발급 401의 첫 번째는 같은 주소로 307 재시도, 게스트의 두 번째 401(마감)은 세션 쿠키 여섯 개를 전부
  지우고 익명으로 통과, 소셜의 두 번째 401은 `/login`으로. 쿠키를 건드린 세 갈래 모두 `no-store`다.
- 재발급 5xx는 쿠키를 지우지 않고 익명으로 통과하고, 쿠키가 없으니 `Cache-Control`도 없다.

## 테스트가 정말 잡는지 소스를 깨서 확인했다

처음 돌렸을 때 40개가 한 번에 다 통과했다. 너무 순조로우면 "아무것도 안 보는 테스트"일 수 있어서,
지키려는 줄을 일부러 하나씩 깨고 다시 돌렸다(확인 뒤 `git checkout`으로 원복).

| 깬 것                                                | 실패한 케이스 |
| ---------------------------------------------------- | ------------- |
| 모바일 프록시 안전핀(`Cache-Control` 덮기) 제거      | 6             |
| 웹 프록시가 페이지 응답에도 유입 쿠키를 심게 함      | 1             |
| 모바일 라우트 `no-store`를 `public, s-maxage=60`으로 | 4             |
| 웹 라우트 출처 검사 제거                             | 2             |
| 모바일 프록시 마감 처리에서 `sessionKind` 삭제를 뺌  | 1             |

다섯 번 모두 해당 앱의 해당 케이스가 빨갛게 됐다. 특히 첫 줄은 이번 티켓이 존재하는 이유 그 자체라,
안전핀이 빠지면 재발급·재시도·마감·랜딩 소모 갈래가 전부 동시에 실패하는 걸 본 게 수확이었다.

## 남용 방어: BE 상한이 사실은 사람별이 아니었다

"같은 IP 분당 60회 BE 상한(429)에 기대면 충분한가"를 보려고 BE 저장소의 `RateLimitAspect`를 열었다.
게스트 발급(`auth-guest`)은 `Scope.IP`로 세고, IP는 `X-Forwarded-For`의 첫 값을, 없으면 소켓 주소를
쓴다. ALB 뒤라 그렇게 짰다는 주석이 붙어 있었다.

문제는 누가 BE를 부르느냐다. 브라우저의 `/be` fetch는 Next rewrites가 요청 헤더째 BE로 넘기고,
Next는 들어온 `X-Forwarded-For`가 있으면 손대지 않는다(`base-server.js`의 `??=`). 그래서 CloudFront가
적어 준 방문자 IP가 체인에 남은 채 BE에 닿는다. 그런데 게스트 발급은 FE 서버의 라우트
핸들러가 `apiFetch`로 직접 BE 내부 ALB(`API_BASE_URL=http://<BE 내부 ALB>`)를 부른다. 이 호출에는
`X-Forwarded-For`가 없고, 내부 ALB는 연결해 온 쪽, 즉 FE 인스턴스의 사설 IP를 적어 넘긴다. BE가 세는
IP는 방문자가 아니라 FE 인스턴스다. 지금 상한은 사람마다 분당 60회가 아니라 "인스턴스당 분당 60회를
모든 방문자가 나눠 쓰는" 공용 상한이다. 프록시가 발급하던 KAN-514 때부터 같은 구조였다.

이게 꼭 나쁘기만 한 건 아니다. 누가 발급 주소를 두드려도 인스턴스당 분당 60개 넘게는 게스트 행이
안 생긴다. 반대로 광고 유입이 몰려 한 인스턴스에 분당 60명 넘게 처음 들어오면 그 너머는 진짜
방문자인데도 429를 받고, 라우트는 503으로 답한다. 이 판단은 코드를 읽어 내린 것이고, prod에서 429를
실제로 관측하지는 않았다.

가장 쉬워 보이는 수정은 라우트가 받은 `X-Forwarded-For`를 그대로 BE 호출에 실어 주는 것이다. 그런데
CloudFront는 방문자가 보낸 `X-Forwarded-For`를 지우지 않고 뒤에 자기가 본 IP를 덧붙인다. 첫 값은
방문자가 마음대로 지어낼 수 있다는 뜻이고, 그 값을 BE에 넘기면 요청마다 가짜 IP를 바꿔 끼우는 것만으로
상한이 사라진다. 지금의 "공용 상한이라도 있는" 상태보다 나빠진다. 믿을 수 있는 방문자 IP는 CloudFront가
붙이는 값(`CloudFront-Viewer-Address` 헤더나 체인 끝에서 정해진 위치)인데, 그걸 쓰려면 오리진 요청
정책과 ALB 앞단 구성을 확인해야 해서 이 티켓에서 손대지 않고 후속으로 넘겼다.

FE에 간단한 상한을 두는 안도 버렸다. 인스턴스 메모리에 카운터를 두면 ASG로 인스턴스가 여럿이라
인스턴스마다 따로 세고, 무엇을 키로 셀지도 결국 같은 "믿을 수 있는 IP" 문제로 돌아온다. 정리하면
FE에는 지금의 UA·출처 거름만 두고, 상한은 BE에 맡기되 BE가 방문자 IP를 보게 만드는 일을 따로 한다.
이 내용은 두 앱 `route.ts`의 JSDoc에 적었다.

## 재시도: 다음 상호작용에 맡긴다

`AuthProvider`는 발급이 실패하면 `issueFailed`를 세우고, 그 화면에서는 한가할 때의 자동 발급을 다시
부르지 않는다. 화면을 옮기면 표식이 풀려 다시 시도한다. 좋아요·투표·댓글은 누르는 순간
`ensureSession`이 이 표식과 상관없이 발급을 다시 부른다.

일정 시간 뒤 한 번 더 부르는 안을 따져 봤지만 그대로 두기로 했다. 발급이 실패하는 경우는 BE 다운, 상한
초과(429), 1.5초 타임아웃이고 셋 다 BE가 버거운 때다. 그때 모든 브라우저가 30초 뒤에 일제히 다시
부르면 회복을 늦추기만 한다. 세션이 없어도 읽기는 그대로 되고, 세션이 꼭 필요한 순간(좋아요 등)에는
사용자의 탭이 곧 재시도다. 위에서 본 BE 상한은 60초 고정 창이라 사람이 다음 행동을 할 즈음이면 대개 풀려
있다. 손해를 보는 건 채팅과 내 정보처럼 세션이 있어야 그리는 화면인데, 실패하면 로그인 안내로 떨어진다.
이 판단을 두 앱 `AuthProvider`의 `issueFailed` 주석에 남겼다.

## 바뀐 파일

- `tests/unit/guest-route.test.mjs`, `tests/unit/session-proxy.test.mjs`: 두 앱 공용 케이스. `test:unit`이
  144개에서 184개가 됐다.
- `tests/unit/support/next-app.mjs`: 앱 로더, 가짜 `fetch`, `Set-Cookie` 파서.
- `tests/unit/register.mjs`: `@/` alias, `next/*` 확장자 보정.
- `package.json`: `test:unit`을 `--experimental-transform-types`로.
- 두 앱 `route.ts`와 `AuthProvider.tsx`: 남용 방어와 재시도 판단 주석. 코드 동작은 그대로다.

## 헤드리스 리뷰에서 고친 것

push 전 `pr-review.sh`가 CRITICAL 없이 WARN 셋을 남겼다. 하나는 정확한 지적이었다. "BE를 부르면 안
된다"를 가짜 `fetch` 안의 `assert.fail`로만 걸어 뒀는데, 프록시는 재발급 호출을 `try/catch`로 감싸 실패를
익명 통과로 바꾼다. 프록시가 실수로 BE를 불러도 `assert.fail`이 던진 예외를 프록시가 삼키면 테스트는
초록으로 남는다. 해당 다섯 케이스 끝에 `stub.calls.length === 0`을 직접 확인하게 했다. 테스트의 마감
시각 상수는 지금은 문자열로만 오가지만 언젠가 프록시가 해석하게 되면 그 날짜가 지나는 순간 깨지는 시한폭탄이라
2099년으로 옮겼다. `--experimental-transform-types`가 Node 22.7부터라는 지적은 CI의 setup-node가 `.nvmrc`의
`22`를 최신 22.x로 받고 로컬도 22.19라 그대로 뒀다. 라우트 주석에는 BE·인프라를 읽고 내린 판단이고 prod
관측은 아니라는 근거 시점을 달았다.

## 후속: 상한 문제는 생각보다 크다 (KAN-680)

PR을 올린 뒤 이 상한 문제를 다시 따져 봤다. 처음엔 "유입이 몰릴 때 진짜 방문자가 막힌다"는 각도로만
봤고, 유저가 아직 많지 않으니 급하지 않다고 적었다. 그런데 각도를 바꾸면 유저 수와 상관이 없다.

라우트의 거름은 UA 검사와 `Sec-Fetch-Site`·`Origin` 검사뿐이다. 둘 다 브라우저가 붙이는 요청 헤더를 보는
방식이라 스크립트가 같은 헤더를 흉내 내면 그대로 통과한다. 그러면 한 사람이 초당 한두 번만 발급 주소를
두드려도 FE 인스턴스당 공용 한도 60회가 1분 내내 바닥나 있고, 그동안 처음 들어오는 모든 사람의 게스트
발급이 503으로 떨어진다. 글 읽기는 되고 좋아요를 누르면 다시 시도하니 화면이 죽지는 않지만, 신규 유입
전체의 세션을 적은 비용으로 막을 수 있는 구조다. 트래픽이 적어서 안 터진 게 아니라 아직 아무도 두드리지
않아서 안 터진 것이다. 이것도 코드로 따진 결론이고 dev에서 재현해 보지는 않았다.

해결 방향은 후속 티켓 KAN-680에 자세히 적었다. 요지는 둘이다.

- 방문자 IP를 BE까지 믿을 수 있게 전달한다. ALB는 이미 `X-Origin-Verify` 헤더와 CloudFront 프리픽스
  리스트로 CloudFront 요청만 받으므로([deploy-v2](../deploy-v2.md), [ADR 0084](0084-prod-vpc-frontend-stack.md)),
  CloudFront가 붙인 값은 믿어도 된다. 오리진 요청 정책을 `CloudFront-Viewer-Address`가 포함된 것으로
  바꾸거나(1a), 지금 `X-Forwarded-For` 체인에서 뒤에서 두 번째 값(CloudFront가 본 뷰어 IP)을 쓴다(1b).
  라우트는 그 값을 BE 호출의 `X-Forwarded-For`로 실어 보내면 BE 수정 없이 방문자별로 센다.
- 보조로 CloudFront WAF에 발급 경로 rate-based rule을 둘 수 있다. 공격자가 FE에 닿기 전에 걸러진다.

따지다 보니 같은 뿌리의 구멍이 하나 더 보였다. 브라우저 `/be/*` fetch는 Next rewrites가 요청 헤더째 BE로
넘기므로 BE에 닿는 `X-Forwarded-For`의 첫 값은 뷰어가 지어낸 값일 수 있다. BE가 첫 값을 믿는 한
`ANONYMOUS_IP` 스코프의 조회 상한도 우회된다. 이건 BE가 "첫 값"이 아니라 "믿을 수 있는 홉 수만큼 뒤에서
센 값"을 보게 바꿔야 끝나는 문제라 BE 티켓 몫으로 넘긴다. 확인은 KAN-680에서 한다.

포트폴리오 재료로는 이 흐름이 쓸 만하다고 판단했다. 요청이 CloudFront, ALB, FE, BE를 지나는 동안 IP의
신뢰가 어느 홉에서 깨지는지 추적한 것, "XFF를 넘기면 되잖아"가 왜 지금보다 나쁜지 짚은 것, 그리고 화면에
안 보이는 사고를 테스트로 막고 테스트가 진짜 잡는지 코드를 깨서 증명한 것이 한 묶음이다. 다만 지금은 판단만
있고 증거가 없어서, KAN-680에서 고치기 전에 dev에서 재현해 "전" 수치를 캡처하고 고친 뒤 같은 재현으로
"후"를 남기기로 했다.
