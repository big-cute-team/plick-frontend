# 0110. 포트폴리오를 위한 성능 전수 감사

## 왜 시작했나

포트폴리오에 "성능을 어떤 수치에서 어떤 수치로 개선했다"는 이야기를 쓰고 싶었다. 그런데 막상
무엇을 개선할 수 있는지부터 몰랐다. 감으로 "이미지 최적화 하면 되겠지" 정도로 시작했다가는
수치가 안 움직이는 걸 골라 며칠을 날릴 수도 있겠다 싶어서, 먼저 코드베이스 전체를 성능 관점으로
전수조사하고 개선 후보를 심각도별로 리스트업하기로 했다.

## 어떻게 조사했나

한 번에 다 보기엔 범위가 넓어서 세 축으로 갈라 병렬로 조사했다.

- 이미지·폰트·미디어: img 태그와 next/image, LCP 후보의 로딩 우선순위, 폰트 로딩 경로,
  CDN 캐시 헤더
- 데이터 페칭: 서버 컴포넌트의 직렬 await 워터폴, fetch 캐싱 정책, Suspense와 스트리밍,
  TanStack Query 설정, 미들웨어, 라우트 정적화 여부
- 번들·클라이언트 렌더링: use client 배치, 의존성 무게, 코드 스플리팅, 릴스 피드의 DOM 누적,
  리렌더 패턴, 제스처 핸들러

여기에 더해 기준선이 될 실제 수치를 하나라도 확보하려고 로컬에서 프로덕션 빌드를 돌려
청크 크기를 직접 쟀다. Next 16 Turbopack의 빌드 출력에는 예전처럼 라우트별 First Load JS가
안 찍혀서, `build-manifest.json`의 rootMainFiles를 읽어 gzip으로 압축해 합산하는 스크립트를
즉석에서 짰다. 공유 First Load JS gzip 128KB, 전체 클라이언트 청크 gzip 353KB가 나왔다.
대형 청크 세 개를 열어 보니 전부 프레임워크(Next·React) 코드였고 앱 코드 자체는 가벼웠다.

## 무엇이 나왔나

솔직히 조사 전에는 "고칠 게 많이 나오겠지" 했는데, 기초 체력은 예상보다 훨씬 좋았다.
passive 리스너, zustand 셀렉터 구독, 서버 씨앗과 `initialDataUpdatedAt`, 인증/익명 분기 캐싱,
배럴 금지까지 그동안 세워 온 컨벤션이 실제로 지켜지고 있었다. "엉망을 고쳤다"는 서사는
못 쓴다는 뜻이라 아쉽기도 했지만, 대신 굵직한 덩어리 여섯 개가 나왔다. 전체 목록은
[감사 리포트](../audits/2026-08-31-performance-audit.md)에 있고, 여기엔 발견 과정에서
인상 깊었던 것만 적는다.

가장 의외였던 건 라우트 정적화였다. 빌드 출력을 보니 22개 라우트가 전부 동적(ƒ)이었다.
`/faq`나 `/terms`처럼 데이터가 하나도 없는 페이지까지 매 요청 렌더되고 있었는데, 원인은
루트 레이아웃 한 줄이었다. 레이아웃에서 `isLoggedIn()`이 `cookies()`를 읽는 순간 Next는
그 아래 모든 라우트를 동적 렌더로 강등시킨다. 쿠키는 요청마다 다르니 당연한 동작인데,
"로그인 여부를 서버에서 한 번 읽어 시드한다"는 편의가 앱 전체의 정적화 가능성을 통째로
막고 있을 줄은 몰랐다. 게다가 로그인 유저는 `getMyProfile()`의 BE 왕복(no-store)이 끝나야
어떤 페이지든 첫 바이트가 나간다. 레이아웃은 Suspense 스트리밍 경계 밖이라 이 대기를
피할 수도 없다.

폰트도 부끄러운 발견이었다. Pretendard를 jsdelivr CDN의 CSS link로 걸어 뒀는데, 알고 보니
dynamic-subset이 아니라 한글 전 글리프가 든 통짜 variable이었고, preconnect도 없어서
첫 페인트 앞에 외부 도메인 DNS부터 woff2까지 직렬로 붙어 있었다. GA는 afterInteractive로
미루면서 LCP를 지키려 애썼는데 정작 제일 비싼 렌더 블로킹은 폰트가 내고 있었다.

릴스 쪽은 두 가지가 겹쳤다. 첫 슬라이드 배경 이미지, 그러니까 LCP 요소 그 자체가
`loading="lazy"`였다. 목록 아이템에 lazy를 붙이는 습관이 첫 화면에도 그대로 적용된 결과다.
그리고 상세 시트를 드래그하면 매 프레임 릴 전체가 리렌더된다는 것도 찾았다. 드래그 위치
`dragY`를 React state로 들고 있고 그 소유자가 `ReelsFeed`라, 손가락이 움직일 때마다
memo 없는 릴 N개가 전부 재조정된다. 재밌는 건 같은 리포의 `useTeamSwipePager`는 정확히
이 문제를 피하려고 ref에 `style.transform`을 직접 쓰는 패턴을 이미 쓰고 있었다는 점이다.
한쪽 훅에서 배운 교훈이 다른 훅으로 전파되지 않았다.

중복 페치도 하나 웃겼다. 릴스 딥링크의 `generateMetadata`가 트래픽을 아끼려고 `size=1`로
부르는데, 페이지 본문은 기본 `size=10`으로 부른다. size가 쿼리스트링에 들어가니 URL이
달라져서 Next의 fetch 메모이제이션이 안 먹고, 결국 같은 릴을 두 번 받는다. 아끼려던
최적화가 오히려 중복을 만든 셈이다.

## 어디에 남겼나

발견 24건을 [docs/audits/2026-08-31-performance-audit.md](../audits/2026-08-31-performance-audit.md)에
심각도별로 정리했다. 개선 전후 비교가 포트폴리오의 생명이라, 코드를 건드리기 전에 떠 둬야 할
측정 항목(라이트하우스, TTFB, 프레임 시간, DOM 노드 수 등)과 도구를 측정 계획 표로 같이
박아 뒀다. dev 서버에서 재면 수치가 왜곡되니 반드시 프로덕션 빌드에서 잰다는 것도.

## 남은 것

- 실측 캡처가 아직 없다. 개선 착수 전에 리포트의 측정 계획대로 before를 먼저 뜬다.
- 포트폴리오 서사는 셋 중에서 고른다: LCP 개선기(폰트+fetchPriority), 전 라우트 동적 →
  정적/ISR 전환기, 릴스 인터랙션 최적화기(리렌더 제거+윈도우잉).
- 포트폴리오 본문은 피그마에서 쓴다. 개선 작업과 장표 작업이 번갈아 진행될 예정이다.
