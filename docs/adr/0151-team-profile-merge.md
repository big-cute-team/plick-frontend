# 0151. 한 팀을 보는 화면이 두 장이었다 — 팀 프로필로 합쳤다

KAN-507. 라이브 순위표에서 팀을 누르면 나오는 선수단 화면과, 기사 쪽에서 팀을
누르면 나오는 팀 프로필을 한 장으로 합쳤다. 웹에는 팀 프로필이 아예 없어서 그건
새로 만들었다.

## 같은 팀인데 들어온 문에 따라 다른 화면이 떴다

라이브 스코어를 쓰다가 알아챘다. 순위표에서 토트넘을 누르면
`/live/teams/6`으로 가는데, 거기는 API-Football에서 받은 이번 시즌 등록 명단이
포지션별로 깔리고 선수를 누르면 시즌 스탯 시트가 열린다. 그런데 기사 카드의
토트넘 로고를 누르면 `/teams/tottenham/profile`로 가고, 거기는 PLick 인물
사전의 소속 인물 목록이 뜬다. 감독·구단주까지 들어 있고 누르면 그 인물의 관련
기사로 간다.

둘 다 "토트넘 팀 화면"인데 내용이 전혀 다르다. 게다가 서로 링크도 안 돼 있어서,
한쪽을 보고 있으면 다른 쪽이 있다는 걸 알 방법이 없었다. 웹은 더 심해서 라이브
쪽만 있고 인물 사전 명단은 볼 데가 없었다.

## 두 명단을 지우지 않고 한 장에 세웠다

처음엔 하나를 버리는 것도 생각했는데, 둘은 진짜로 다른 데이터다.

- **선수단**: API-Football의 이번 시즌 등록 명단이다. 33명쯤 되고 사진과 등번호,
  포지션이 있고 시즌 스탯을 볼 수 있다. 실제 스쿼드다.
- **기사에 나온 인물**: PLick이 기사에서 뽑아 쌓은 인물 사전이다. 이적 루머에
  이름이 나온 사람들이라 이적한 선수, 감독, 구단주가 섞여 있고, 대신 그 인물의
  관련 기사로 갈 수 있다.

겹치지도 않는다(토트넘은 라이브 33명, 인물 사전 38명인데 표기 체계부터 다르다 —
라이브는 "B. Davies", 인물 사전은 "벤 데이비스"다). 그래서 섹션을 갈라 둘 다
남겼다. 제목만으로 무슨 목록인지 알게 "선수단"과 "기사에 나온 인물"로 붙였다.

작은 걸림돌이 하나 있었다. 인물 사전 섹션 구분(`FIGURE_SECTIONS`)이
감독·코칭스태프 / **선수단** / 구단주·관계자인데, 바로 위에 라이브 "선수단"
섹션이 생기면 같은 이름이 두 번 나온다. 인물 사전 쪽을 "선수"로 좁혔다.

헤딩 레벨도 손봤다. 라이브 선수단 목록(`SquadList`·`SquadGroups`)과 인물
목록(`TeamFiguresList`)은 원래 자기가 페이지의 두 번째 층이라 포지션·구분
제목이 `h2`였다. 이제 위에 섹션 `h2`가 생겨서 `h3`로 내렸다. 레벨을 건너뛰면
스크린리더가 목차를 못 만든다.

## 옛 URL은 지우지 않고 308로 보냈다

`/live/teams/[teamId]`를 지울 수도 있었지만 리다이렉트로 남겼다. 이유가 둘이다.

하나는 링크를 한 번에 다 고치지 않아도 된다는 것. 순위표(`StandingsTable`·
`StandingsRail`)와 경기 화면 여러 곳이 이 주소로 걸려 있는데, 리다이렉트를 두면
그 링크들이 그대로 새 화면에 도착한다.

다른 하나는 색인과 공유다. 이 주소는 이미 사이트맵과 검색에 올라가 있고 누가
공유했을 수도 있다. 지워 버리면 404가 된다.

`redirect()`가 아니라 `permanentRedirect()`를 썼다. 둘의 차이는 HTTP 상태
코드다. `redirect()`는 307(Temporary Redirect)이라 "이번만 저리로 가라"는
뜻이고, 크롤러는 색인을 원래 주소에 그대로 둔다. `permanentRedirect()`는
308(Permanent Redirect)이라 "앞으로 이 주소는 저기다"라는 뜻이고, 검색엔진이
색인을 새 URL로 옮기고 브라우저도 다음부터 새 주소로 바로 간다. 화면을 옮긴
경우엔 308이 맞다.

둘 다 함수를 부르면 서버에서 예외를 던지는 방식이라 그 아래 코드는 실행되지
않는다. 그래서 `return`을 쓸 필요가 없고, 타입상으로도 `never`를 돌려준다.

빅6 밖 id는 옮길 곳이 없어 그대로 `notFound()`다.

확인은 curl로 했다.

```
GET /live/teams/6   → 308  Location: /teams/tottenham/profile
GET /live/teams/99  → 404
GET /live/teams/abc → 404
```

## 웹 팀 프로필을 새로 만들었다

모바일 화면을 데스크톱 폭(`max-w-page`)으로 옮겼다. 데이터 레이어는 이미
공용이라(`getTeamProfile`·`getTeamSquad`) 화면 조각만 새로 썼다.

모바일과 다른 건 셋이다. 선수단과 인물 목록을 넓은 폭에 맞춰 2열 그리드로
깔았고(라이브 스쿼드 화면이 쓰던 격자 그대로), 행에 hover·focus 상태를 얹었고,
"팀 관련 기사 보기" 버튼이 화면 폭을 다 먹지 않고 내용 폭(`w-fit`)만 차지한다.

`generateMetadata`에 canonical과 모바일 alternate를 걸었다. 별도 모바일 URL
패턴의 규약이라 이 URL이 정본이고 `m.plick.co.kr`의 같은 경로를 대응으로
선언한다.

## 실패를 다르게 다뤘다

두 호출을 `Promise.allSettled`로 병렬로 받는데, 실패했을 때 대응이 다르다.

인물 사전(`getTeamProfile`)이 404면 `notFound()`다. 레지스트리에 있는 slug인데
BE가 모르는 팀이라면 마스터가 어긋난 것이고, 그때는 보여 줄 게 없다.

선수단(`getTeamSquad`)만 실패하면 페이지를 죽이지 않고 그 섹션 자리에만 실패
문구를 남긴다. 라이브 API는 외부(API-Football) 의존이라 인물 사전보다 덜 미덥다.
실제로 로컬 BE는 `FOOTBALL_API_KEY`가 없어서 이 호출이 늘 `MATCH_UPSTREAM_ERROR`로
떨어지는데, 그 상태에서도 인물 목록은 멀쩡히 보여야 한다. 이건 우연한 시나리오가
아니라 로컬 개발의 기본 상태다.

## 검증하며 만난 것

로컬 BE에 라이브 데이터가 없어서(위의 `FOOTBALL_API_KEY`) 스쿼드가 붙은 화면을
볼 수가 없었다. dev BE에는 있는데 dev API 주소는 시크릿이라 손에 없다. 웹 앱의
`/be` 프록시를 통하면 `https://dev.plick.co.kr/be/api/v1/...`로 읽힌다는 걸
KAN-501에서 알아 둔 게 여기서 또 쓸모가 있었다. 스크래치에 그 주소로 넘기는 작은
프록시를 띄우고 `API_BASE_URL`을 거기로 돌려 확인했다.

포트 3000·3001에 dev 서버가 이미 떠 있어서 `next dev`를 하나 더 못 띄운다(Next가
같은 디렉터리에서 둘을 허용하지 않는다). 빌드 산출물을 `next start`로 다른
포트에 올려 확인했다.

결과는 이렇다.

- 헤딩이 `h1 토트넘 핫스퍼` → `h2 선수단` → `h3 골키퍼/수비수/미드필더/공격수`
  → `h2 기사에 나온 인물` → `h3 감독·코칭스태프 / 선수`로 층이 맞는다
- 선수단 33명, 인물 사전 38명이 각자 섹션에 들어간다
- 인물 행 링크가 `/figures/400` 식으로 나간다
- 모바일 375px 가로 오버플로 0

## 남은 것

- **라이브 선수를 누르면 여전히 시즌 스탯 시트다.** 인물 프로필로 보내려면
  API-Football player id와 PLick `figureId`를 이어 줄 매핑이 필요한데 지금
  없다. 이름으로 맞춰 보는 건 표기 체계가 달라("B. Davies" vs "벤 데이비스")
  틀릴 위험이 크고, 인물 목록 조회 API도 없다. BE에 `figures` 테이블로 player
  id 컬럼을 넣어 달라고 요청하는 게 맞는 길이다
- **순위표·경기 화면의 링크는 여전히 `/live/teams/`를 가리킨다.** 308이 받아
  주니 동작은 맞지만 한 번 더 도는 건 사실이다. 나중에 한 번에 정리한다
- **모바일 팀 프로필에 `h1`이 둘이다.** `ProfileTopBar`의 제목과 화면 머리가
  겹친다. 이번 변경 전부터 있던 것이라 손대지 않았다
- **사이트맵.** 웹 팀 프로필을 넣지 않았다
