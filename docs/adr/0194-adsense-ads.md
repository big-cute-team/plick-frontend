# 0194. 애드센스 광고 자리와 릴스 전면광고 (KAN-652)

이번 세션은 광고다. 티켓은 스크린샷 두 장(웹 홈, 웹 기사 상세)에 광고가 박힌 모습과 짧은 메모 세 줄이
전부였다. 푸터에 카피라이트를 넣을 것, 모바일은 PC를 참고해 최소화할 것, 릴스는 8장마다 전면광고가
나올 것. 저장소에는 광고와 관련된 코드가 한 줄도 없었고 사용자도 광고 네트워크를 한 번도 설정해 본 적이
없다고 했다. 그래서 이 글은 코드 이전에 "무엇을 골랐고 왜 그랬나"부터 적는다.

## 네트워크를 고르기

스크린샷의 광고 모양이 힌트였다. STENA와 덴프스몰 같은 네이티브 카드, 대성패스 300×250 사각형, 좌측
160×600 세로 배너, 광고 구석의 ⓘ✕ 마크. 전부 구글 애드센스가 내는 포맷이다. 그래서 애드센스로 가되
슬롯 컴포넌트 안쪽만 바꾸면 카카오 애드핏이나 직판 배너도 끼울 수 있게 자리와 네트워크를 분리하기로
했다.

애드센스를 쓰려면 코드 밖 절차가 있다. 계정을 만들고 사이트를 등록하면 게시자 ID(`ca-pub-…`)가 나오고,
그 ID가 박힌 스크립트가 `<head>`에 있거나 도메인 루트에 `ads.txt`가 있으면 사이트 소유가 확인된다.
그 다음 구글이 사이트를 심사하는데 며칠에서 몇 주 걸린다. 승인이 나야 대시보드에서 광고 단위를 만들
수 있고, 단위마다 번호(`data-ad-slot`)가 나온다. 이번 세션은 사용자가 가입해서 게시자 ID
`pub-1989769587706531`을 알려준 시점까지다. 단위 번호는 아직 없다. 그래서 코드는 "번호가 비어 있어도
깨지지 않고, 번호만 채우면 켜지는" 모양이어야 했다.

## 앱 셸 문제

여기서 한 번 돌아갔다. 해축이모는 모바일 웹을 그대로 띄우는 RN WebView 앱(plick-AppShell)이 있다.
웹에 광고를 넣으면 앱에서도 똑같이 보인다. 기술적으로는 아무 문제가 없는데 구글 규정이 문제였다.
애드센스 정책은 앱 안 광고를 모바일 광고 SDK(AdMob)를 쓸 때만 허용한다. WebView에서 애드센스가
노출되면 계정 정지 사유가 되고 그러면 웹 수익까지 막힌다.

사용자가 티스토리 글 하나를 가져왔다. 구글 모바일 광고 SDK에 `MobileAds.registerWebView()`라는
API가 있어서 앱이 자기 WebView를 SDK에 등록하면 그 안의 애드센스 광고가 규정상 허용되는 광고가 된다는
내용이었다. 구글 공식 문서(WebView API for Ads)에도 같은 내용이 있어 지금도 유효한 길이다. 다만 우리
앱은 Expo + React Native라 글의 안드로이드 네이티브 코드를 그대로 못 쓰고, 많이 쓰는
`react-native-google-mobile-ads`에도 이 기능이 없다(기능 요청 #855가 미구현으로 닫혔다). 안드로이드와
iOS용 짧은 네이티브 모듈을 직접 써야 해서 AppShell 쪽 별도 작업이 된다.

그래서 셋 중 첫째를 골랐다. 앱에서는 광고 자리를 아예 그리지 않는다. 둘째(WebView 등록)는 AppShell
티켓으로 넘기고, 그게 끝나면 프론트의 스위치만 끄면 된다. 셋째(앱에 AdMob을 따로)는 가장 크다.

앱인지는 이미 알고 있었다. 프록시(`proxy.ts`)가 UA 끝의 `PlickApp/x.y` 표식을 보고 `X-Plick-Browser:
plick_app` 헤더를 찍는다(KAN-610). 이 헤더는 BE로 가는 게 아니라 이번 렌더의 서버 컴포넌트가
`headers()`로 읽으라고 페이지 요청에 얹어 둔 값이다. 레이아웃이 그걸 읽어 광고 모드를 정하면 된다.

## 세 가지 모드

광고 모드를 `live`, `placeholder`, `off` 셋으로 뒀다. `@plick/core/ads`의 `AdsMode`다.

- `live`: 실제 애드센스 `<ins>`를 두고 로더에 push한다. prod 빌드만이다.
- `placeholder`: 같은 크기의 점선 상자에 AD만 쓴다. dev와 로컬이 여기다. 애드센스는 미승인 도메인
  (dev.plick.co.kr)에 실광고를 걸면 정책 위반이라 dev는 절대 live가 아니다. 대신 레이아웃과 E2E를 볼 수
  있다.
- `off`: 자리 자체를 안 그린다. 앱 셸이다.

기본 모드는 빌드가 정한다. `IS_PRODUCTION_SITE`(SITE_URL이 prod 도메인인지)가 true면 live, 아니면
placeholder다. GA_ID처럼 env를 하나 더 두지 않은 이유는 애드센스 게시자 ID가 공개 값이라 감출 게
없고, prod 여부는 이미 빌드 시점에 굳는 값이어서다. 로컬에서 끄고 싶을 때를 위해
`NEXT_PUBLIC_ADS_MODE`로 덮을 수는 있다.

요청별 모드는 레이아웃이 정한다. `resolveAdsMode(ADS_BASE_MODE, headers().get("X-Plick-Browser"))`가
앱 셸이면 off로 접는다. 레이아웃은 이미 `cookies()`를 읽어 동적이라 `headers()`를 더 읽어도 정적
페이지가 동적으로 바뀌는 비용은 없다. 정해진 모드는 `AdsProvider` 컨텍스트로 내려가고 `AdSlot`이
`useAdsMode()`로 읽는다. 클라에서 `navigator.userAgent`를 다시 보지 않고 서버가 정한 값을 쓰는 이유는
자리를 미리 잡는 wrapper가 서버 HTML부터 맞아야 하이드레이션 뒤 밀림이 없어서다.

로더 스크립트는 레이아웃에서 live일 때만 `next/script`로 `afterInteractive`에 싣는다. GA와 같은
판단이다. 광고 때문에 LCP를 깎으면 본말전도다.

## AdSlot과 애드센스 함정

`AdSlot`은 자리 이름(`placement`)을 받아 각 앱 `_constants/ads.ts`의 `AD_UNITS`에서 단위 번호와
크기를 찾는다. wrapper는 `min-height`로 자리를 미리 잡는다. 광고가 늦게 오거나 안 와도 본문이 밀리지
않는 게(CLS) 광고 작업에서 UX를 지키는 핵심이다. 얼마 전 라이트하우스 작업(KAN-624~643)으로 올린
점수를 광고가 되돌리면 안 된다.

크기는 px다. 앱 코드는 px 금지에 rem 배율(KAN-574)인데, 애드센스 고정 크기 단위(300×250, 160×600)는
실제 픽셀 규격이라 rem 배율을 태우면 규격에서 벗어나 채워지지 않는다. 광고 상자와 그 자리를 잡는
wrapper만 px이고 주변 여백은 토큰이다. 가로 배너는 폭을 컬럼에 맞추고 높이만 90(웹)·100(모바일)으로
고정했다. 애드센스가 문서화한 "높이 고정 반응형" 변형이다(`width:100%; height:90px`,
`data-ad-format` 없음).

애드센스에는 알려진 함정이 둘 있어 `AdSlot` 안에서 막았다.

하나, 숨겨진 상자를 push하면 "No slot size for availableWidth=0"으로 실패하고 그 상자는 다시 살아나지
않는다. 우측 레일(`SideRail`)은 `hidden lg:flex`라 좁은 창에서 숨겨지고, 좌측 세로 배너는 넓은 창에서만
보인다. 그래서 `media` prop으로 같은 조건을 넘기고 `useMediaQuery`가 true일 때만 `<ins>`를 마운트한다.
`useMediaQuery`는 `useSyncExternalStore`로 서버 스냅샷을 `null`로 둬서 서버 HTML에는 상자가 없고
클라에서 창 폭을 안 뒤에 붙는다.

둘, 같은 상자를 두 번 push하면 "All ins elements already have ads"로 실패한다. 홈과 팀 허브는 같은
`HomeScreen` 트리를 써서 클라 라우팅으로 오가면 슬롯이 그대로 살아남는다. `usePathname()`을 key로
걸어 경로가 바뀌면 상자를 새로 마운트한다.

live인데 단위 번호가 비어 있으면 `AdSlot`은 null을 돌려준다. 승인 전 prod에 빈 회색 칸을 남기지
않으려는 것이다. 즉 지금 prod에 배포되면 로더 스크립트(소유 확인)와 ads.txt, 푸터 카피라이트만 보이고
광고 자리는 하나도 안 보인다.

## 자리

웹은 홈과 기사 상세가 둘 다 `PageContainer` 2열 그리드 + `SideRail`이라 같은 자리를 쓴다.

| 자리         | 규격             | 위치                                                    |
| ------------ | ---------------- | ------------------------------------------------------- |
| skyscraper   | 160×600 fixed    | 컨테이너 바깥 왼쪽 여백. 1800px 이상 창에서만           |
| feedBanner   | 폭 100%, 높이 90 | 홈 핫이슈와 새 이슈 사이                                |
| railBanner   | 폭 100%, 높이 60 | 우측 레일 급상승 아래, 채팅 위                          |
| railRect     | 300×250          | 우측 레일 맨 아래                                       |
| bottomBanner | 폭 100%, 높이 90 | 홈은 이슈 더 보기 아래, 기사는 댓글 아래. 둘 다 푸터 위 |

`SideRail`에 넣었으니 투표와 스토리 페이지도 레일 광고가 자동으로 따라온다. 인물·선수·팀 프로필과
LIVE 목록은 레일이 따로라 이번엔 안 넣었다.

좌측 세로 배너의 문턱은 계산해 봤다. 페이지 폭 `80rem`에 html 110% 배율을 곱하면 1408px이고, 양쪽에
광고 160px과 거터 31px이 더 남아야 하니 약 1790px이다. 미디어 쿼리의 rem은 html 폰트 크기가 아니라
브라우저 기본 16px 기준이라 `min-[112.5rem]`(1800px)로 적었다. 솔직히 이 폭을 넘는 화면은 흔치 않다.
그보다 좁은 노트북에서도 보이게 하려면 본문을 좁혀야 해서 안 했다. 자리는 `fixed`로 두고 `left`를
`calc((100vw - 80rem)/2 - 10rem - gutter)`로 계산해 컨테이너 왼쪽 가장자리에서 광고 폭만큼 더 왼쪽에
붙였다. 헤드리스 측정에서 컨테이너가 x=246일 때 광고가 x=39에 섰다.

모바일은 티켓대로 최소화했다. 홈 둘(핫이슈와 새 이슈 사이 높이 100, 기사 더 보기 아래 높이 100), 기사
하나(본문 끝 표식 `ReadEndSentinel` 뒤, 함께 보면 좋은 기사 위에 300×250). 하단 앵커 광고는 탭바와
겹쳐 쓰지 않았다. 기사 광고를 본문 끝 표식 뒤에 둔 건 읽기 종료 판정(KAN-543)에 광고가 끼지 않게
하려는 것이다.

## 릴스 전면광고

양 앱 다 릴 배열을 그대로 슬라이드로 그리고 있었다. 웹은 `ReelViewer`가 `reels.map`으로 스냅 섹션을
만들고 `useActiveReel`의 IntersectionObserver가 `data-reel-index`를 읽어 활성 인덱스를 정한다. 모바일은
`ReelsFeed`가 Embla 캐러셀에 `reels.map`으로 `ReelItem`을 깔고 `useReelsCarousel`이 활성 인덱스를 준다.
여기에 광고 슬라이드를 끼우면 "슬라이드 순번"과 "릴 순번"이 갈라진다. 활성 릴, 주소 동기화, 조회
기록의 `rank`, 프리페치의 남은 장수가 전부 인덱스를 쓰고 있어서 하나라도 놓치면 엉뚱한 릴을 기록하거나
프리페치가 한 장 늦는다.

그래서 `@plick/core/ads`에 순수 함수 둘을 뒀다. `interleaveReelAds(reels, 8)`은 릴 배열을
`{kind:"reel", reel, reelIndex} | {kind:"ad", id}` 배열로 바꾼다. 광고는 릴과 릴 사이에만 들어간다.
정확히 8장이면 끝에 광고가 붙지 않고, 다음 페이지가 붙어 9장째가 생길 때 그 앞에 들어간다. `reelIndexAt(slides, i)`는
슬라이드 순번이 가리키는 릴 순번이다. 광고 슬라이드면 바로 앞 릴의 순번이다. "지금까지 몇 번째 릴까지
봤나"라 프리페치와 조회 기록이 이 값을 쓴다. 둘 다 `tests/unit/ads.test.mjs`에 테스트를 붙였다.

컴포넌트 쪽은 인덱스를 전부 슬라이드 순번으로 통일하고 릴 순번이 필요한 자리만 환산했다. 웹은
`activeSlide = slides[activeIndex]`, `activeReel`은 릴 슬라이드일 때만, `remaining`과 `useArticleView`의
rank는 `reelIndexAt`. 모바일은 캐러셀 슬라이드 수를 `slides.length + trailing`으로 늘리고 `ReelItem`의
`rank`에 `slide.reelIndex`를, `active`·`nearActive`·`inWindow`에는 슬라이드 거리를 그대로 썼다.
광고 슬라이드가 활성이면 `useReelUrlSync`에 undefined를 넘겨 주소가 직전 릴에 머문다. 조회 기록도
나가지 않는다. 모바일의 보던-릴 복귀 순번(`useViewState.reelsIndex`)은 슬라이드 순번 그대로 둔다. 모드가
세션 안에서 바뀌지 않으니 같은 자리로 돌아온다.

광고 슬라이드(`ReelAdSlide`)는 모달이 아니다. 릴과 같은 크기의 칸에 광고 상자를 채우고 위에 "광고",
아래에 넘기는 안내만 뒀다. 웹은 9:16 카드, 모바일은 화면을 채운다. 스와이프나 스크롤로 지나가는 한
칸이라 전면광고 중 UX 손상이 가장 적다. 모바일은 `REELS_DOM_WINDOW`(KAN-431) 창 밖이면 `enabled`를
꺼서 자리만 잡고 상자는 두지 않는다. 창 밖에서 push하면 보이지 않는 채로 채워져 노출로 안 센다.

웹 헤드리스 측정에서 릴 11장 중 9번째가 광고(`rrrrrrrrArr`)로 섰고, 프리페치가 붙은 뒤 두 번째 광고가
8장 뒤에 또 섰다. 모바일도 `rrrrrrrrArrr`이었다.

## 검증에서 막힌 것

브라우저 패널로 홈은 잘 쟀는데 기사 상세와 릴스로 넘어가자 모든 광고 자리의 rect가 0으로 나왔다.
`document.querySelector('h1')`까지 0이었다. 파고 보니 `article`과 `footer`가 `<div hidden id="S:1">`
안에 있었다. React 19 스트리밍에서 Suspense 내용은 숨긴 div로 먼저 내려오고 인라인 `$RC` 스크립트가
제자리로 옮기는데, 19.2부터 이 reveal이 `$RB`·`$RV`로 묶여 rAF 타이밍에 돈다. 패널이 hidden이면
rAF가 얼어 reveal이 영영 안 돌고, 화면에 보이던 것은 로딩 스켈레톤(`loading.tsx`의 `aside`만 277px로
멀쩡히 재진 이유)이었다. 스크린샷은 옛 프레임이었다. 메모리에 적어 둔 "패널 hidden이면 헤드리스
캡처"가 그대로 맞았다.

그래서 Playwright 헤드리스 스크립트로 바꿨다(`tests/e2e`의 Playwright를 `createRequire`로 끌어 쓰는
스크래치 스크립트). 웹 1900×1000과 모바일 360×780에서 홈·기사·릴스를 열어 슬롯 rect와 스크린샷을 남겼다.
웹 홈 다섯 자리, 기사 네 자리, 모바일 홈 둘·기사 하나·릴스 광고 슬라이드가 전부 의도한 위치와 크기였고
hidden 세그먼트는 없었다.

콘솔에 `[views] 조회 기록 실패: Unexpected end of JSON input`이 찍혔다. prod BE를 로컬에서 붙인 환경
(`web-prodbe`)의 조회 기록 POST 응답이 비어 있어서다. 이번에 건드리지 않은 `recordArticleView` 경로고
dev BE가 403이라 prod BE로 읽기 검증을 하는 환경의 한계다(ADR 0171 검증 환경 메모와 같다).

## 카피라이트와 개인정보처리방침

카피라이트 문구는 `@plick/domain/brand`의 `copyrightNotice(year)` 한 곳이다. 웹 `SiteFooter`는 없던
줄을 추가했고 모바일 `HomeFooter`는 `© 2026 해축이모`를 같은 문구로 바꿨다. 티켓 문구는 2026 고정인데
연도는 렌더 시점으로 뒀다. 내년에 또 고치는 티켓을 만들 이유가 없다.

애드센스는 제3자 광고 쿠키를 개인정보처리방침에 적을 것을 요구한다. 기존 10항은 "맞춤형 광고 목적의
쿠키는 사용하지 않습니다"였다. 그 줄을 광고 쿠키 설명으로 바꾸고 거부 방법에 구글 광고 설정
(adssettings.google.com)을 더했다. 7항 위탁과 8항 국외 이전의 Google LLC 항목에 광고 게재를 붙였다.
14항의 시행일은 손대지 않았다. 광고가 실제로 켜지는 날(승인 뒤 단위 번호를 넣어 배포하는 날)에 맞춰
적어야 해서 TODO로 남긴다.

## 남은 것

- 애드센스 심사. 이 PR이 prod에 나가면 사용자가 대시보드에서 "사이트 확인"을 누른다. 로더 스크립트와
  `/ads.txt`가 소유 확인이다.
- 승인 뒤 광고 단위 번호를 양 앱 `_constants/ads.ts`의 `AD_UNITS`에 채운다. 웹 6개, 모바일 4개.
  대시보드의 자동 광고는 꺼야 한다. 켜 두면 앵커와 전면이 마음대로 끼어든다.
- 개인정보처리방침 14항 시행일을 광고가 켜지는 배포일로 적는다.
- 앱 셸에서 광고를 켜려면 AppShell에 `registerWebView` 네이티브 모듈을 넣고 `resolveAdsMode`의
  `plick_app` 분기를 푼다. 옛 앱 버전이 남으니 UA의 버전으로 문턱을 두는 편이 안전하다.
- 다른 페이지(프로필·선수·LIVE 레일) 확장은 노출 지표를 본 뒤 별도 PR이다.
- E2E 릴스 spec이 슬라이드 수를 세지는 않아 그대로 돈다. dev는 placeholder라 점선 상자가 보인다.

## 덧. 소유 확인이 코드 스니펫으로는 안 됐다

배포 뒤 사용자가 애드센스에서 "애드센스 코드 스니펫"으로 사이트 확인을 눌렀더니 "사이트를 확인할 수
없습니다"가 떴다. prod HTML을 curl로 뜯어 보니 로더는 `<link rel="preload" as="script">`와 RSC 페이로드
안의 문자열로만 있었다. `next/script`의 `afterInteractive`는 서버 HTML에 실제 `<script src>` 태그를 쓰지
않고 하이드레이션 뒤 브라우저가 태그를 만든다. 애드센스 크롤러(Mediapartners-Google)는 JS를 돌리지 않고
head의 태그를 찾으니 "코드 없음"이었다. ads.txt 방식으로 바꿔 누르니 바로 통과했고 검토 요청까지 됐다.

소유 확인은 끝났지만 심사 중에도 크롤러가 페이지에서 광고 코드를 찾는다고 해서 태그를 진짜로 바꿨다.
`next/script`를 버리고 구글이 주는 스니펫 그대로 `<script async src crossOrigin="anonymous">`를 head에 둔다.
async라 파싱과 첫 페인트를 막지 않는 건 같다. 잃는 건 Next가 넣어 주던 preload 링크 하나다. 로컬에서
`NEXT_PUBLIC_ADS_MODE=live`로 띄워(launch.json `web-ads-live`·`mobile-ads-live`) Mediapartners-Google UA로
curl하니 두 앱 다 head에 태그가 있고, `PlickApp/` UA로는 태그도 자리도 없었다.
