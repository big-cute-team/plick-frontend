# ADR 0020 — 모바일 로그아웃 API 연결 + MY 로그인 분기 (KAN-255)

- **상태:** Accepted
- **날짜:** 2026-07-20
- **관련:** [ADR 0019 로그인 API](0019-mobile-auth-login-api.md) · [ADR 0017 API 연결 전략](0017-api-integration-strategy.md) · [ADR 0011 공용 경계](0011-shared-code-boundary.md) · `api-integration` 스킬

로그인 다음 이야기다. `/api/v1/auth/logout` 하나를 붙이는 티켓인데, 스웨거를 열어 보니 엔드포인트 자체는 허무할 만큼 간단했다 — body도 파라미터도 없고, `mock-auth` 태그에 설명은 "정적 mock — 항상 성공", 응답은 `{ code:"OK", data:null }` 봉투뿐. curl로 한 번 때려 보고 끝. 진짜 일은 엔드포인트가 아니라 티켓이 곁들여 달아 놓은 UX였다. 로그아웃 버튼에 확인 팝업을 달고, 마이페이지가 로그인 여부에 따라 갈리게 하는 것.

## 로그아웃도 로그인과 대칭으로 서버 액션

로그인을 서버 액션 + HttpOnly 쿠키로 했으니 로그아웃도 같은 결로 갔다. 토큰이 HttpOnly 쿠키라 애초에 브라우저 JS로는 못 지운다 — 심는 것도 서버였으니 지우는 것도 서버여야 대칭이 맞다. 그래서 `logout` 서버 액션 하나가 BE에 로그아웃을 알리고, `accessToken`·`refreshToken` 쿠키를 지우고, `/login`으로 redirect한다.

한 가지 정한 건 BE 호출을 best-effort로 둔 것이다. `apiFetch`를 `try/catch`로 감싸고 실패해도 그냥 넘어가 쿠키를 지운다. 로그아웃이 로그인과 다른 점이 여기다 — 로그인은 실패하면 안 들여보내는 게 맞지만, 로그아웃은 BE가 죽었다고 사용자를 로그인 상태에 가둬 두면 안 된다. 지금 mock은 어차피 항상 성공하지만, 진짜 로그아웃(리프레시 토큰 무효화)이 붙어 그게 실패하더라도 로컬 세션은 반드시 끊기게 해 뒀다.

### 서버 코드가 브라우저 쿠키를 어떻게 읽고 지우나

여기서 한 번 멈칫할 수 있다. 서버 액션은 서버에서 도는데, 어떻게 브라우저의 쿠키를 읽고(`await cookies()`) 지우나(`jar.delete()`)? 답은 **서버는 브라우저를 들여다보는 게 아니라, 요청/응답 헤더로만 주고받는다**는 것이다. 쿠키는 HTTP 왕복 편지에 실려 다닌다.

- **브라우저 → 서버**: 같은 origin으로 요청할 때마다 브라우저가 **자동으로** `Cookie:` 요청 헤더에 쿠키를 담아 보낸다. `await cookies()`는 브라우저 어딘가를 뒤지는 게 아니라 **"지금 처리 중인 그 요청"의 `Cookie` 헤더를 파싱**해 돌려준다(request-scoped라 `await`이고, 요청 컨텍스트 밖에선 못 쓴다). 서버 컴포넌트 렌더는 그 페이지를 부른 GET 요청의 쿠키를, 서버 액션은 클릭이 보낸 POST 요청의 쿠키를 읽는다. HttpOnly라도 이 자동 전송은 그대로다 — HttpOnly는 JS의 `document.cookie` 접근만 막지 브라우저가 서버로 보내는 건 안 막는다.
- **서버 → 브라우저**: `jar.set()`/`jar.delete()`도 브라우저를 직접 건드리는 게 아니라 **응답에 `Set-Cookie` 헤더를 예약**하는 것뿐이다. 삭제는 "만료된 쿠키"를 `Set-Cookie: …; Max-Age=0`으로 보내 브라우저더러 지우라고 시키는 것 — 실제 삭제는 브라우저가 응답을 받아야 일어난다.

로그아웃 전체를 이 렌즈로 보면: (1) 클릭 → 브라우저가 `POST /me`에 쿠키 자동 첨부 → (2) 서버 액션이 `cookies()`로 읽고 `jar.delete()`로 만료 `Set-Cookie`를 응답에 예약하고 `/login`으로 redirect → (3) 응답 도착 → 브라우저가 쿠키 삭제 → (4) 다음 요청엔 그 쿠키가 안 실려 `isLoggedIn()`이 `false`. 즉 서버는 "들어온 요청 헤더를 읽고 / 나가는 응답 헤더로 지시"할 뿐, 저장·삭제의 실행은 늘 브라우저 몫이다.

## 로그인 여부는 쿠키가 있냐 없냐로만 갈랐다

마이페이지가 로그인/로그아웃으로 갈려야 하는데, 여기서 잠깐 멈춰서 스웨거를 다시 봤다. `/api/v1/users/me`가 있긴 하다 — 진짜 프로필을 주는 엔드포인트. 하지만 그건 별도 엔드포인트고, 스킬 원칙이 "엔드포인트 하나 = 작업 하나"라 이 티켓에서 붙일 게 아니다. 이 티켓에 필요한 건 "로그인했나 안 했나" 신호 하나뿐이지, 프로필 데이터가 아니다.

그래서 `accessToken` 쿠키의 존재 여부만으로 갈랐다. `isLoggedIn()`은 서버 렌더 중에 쿠키를 읽어 boolean만 돌려준다. BE를 때리지 않는다. 토큰이 진짜 유효한지 검증하는 건 나중에 보호 API가 붙을 때 그 호출이 겸하면 되고, 지금 화면 분기엔 존재 여부로 충분하다. 프로필에 보이는 이름·핸들·응원팀은 여전히 mock `CURRENT_USER`다 — 그 자리는 `/users/me` 티켓에서 진짜 데이터로 갈아끼운다.

여기서 작은 결정 하나. `isLoggedIn()`을 로그인·로그아웃이 든 `auth.ts`에 같이 두고 싶었는데, 그 파일은 맨 위에 `"use server"`가 붙어 있어서 그럴 수가 없었다. 이걸 제대로 이해하려면 헷갈리기 쉬운 두 개념을 갈라야 한다 — **"서버에서 실행되는 함수"** 와 **"서버 액션"** 은 다르다.

App Router는 **모든 게 기본이 서버 컴포넌트**다. 아무 지시어도 안 붙이면 서버에서 실행되고 브라우저로 JS가 안 내려간다. 클라로 빼려면 그때 `"use client"`를 붙인다. 그러니 `isLoggedIn()`은 `"use server"`가 없어도 **서버에서 실행되는 함수 맞다** — `me/page.tsx`(서버 컴포넌트)가 렌더 중에 import해 부르니 서버에서 돈다.

함정은 `"use server"`의 뜻이다. 이건 "서버에서 실행해라"가 **아니다**(안 붙여도 서버 컴포넌트 파일 함수는 어차피 서버에서 돈다). `"use server"`는 **"이 export들은 서버 액션"** 이라는 표시다. 서버 액션이 되면 Next가 그 함수에 고유 ID를 붙이고 **네트워크 엔드포인트(RPC)를 하나 만들어**, `"use client"` 컴포넌트가 그 함수를 호출할 수 있게 해 준다(클릭 → 브라우저가 인자를 POST → 서버에서 실행 → 결과 반환). 즉 `"use server"`는 실행 위치가 아니라 **"클라가 네트워크로 부를 수 있는 함수"** 라는 경계 표시다.

그래서 `logout`·`login`은 `"use server"`가 맞다 — 클라 컴포넌트(버튼)가 클릭 때 호출해야 하니까. 반면 `isLoggedIn`은 클라가 부르는 게 아니라 서버 컴포넌트가 렌더 중 읽는 순수 조회다. 이걸 `"use server"` 파일에 넣으면 **아무도 안 부르는데 서버 액션 엔드포인트가 하나 생겨** 클라에 노출된다. 그래서 `"use server"` 없는 `session.ts`로 따로 뺐다 — 서버에서 도는 일반 함수로 충분하다. (덤으로, `"use server"` 파일은 export를 전부 async 함수로만 해야 한다는 제약도 있다. ADR 0019에서 상수·타입을 `api/constants.ts`·`api/types.ts`로 밀어냈던 그 규칙이다.) 참고로 `isLoggedIn`을 억지로 `"use client"` 컴포넌트에서 부르려 하면 에러가 난다 — 안에서 `next/headers`의 `cookies()`(서버 전용)를 쓰기 때문이다.

## 확인 팝업은 상호작용 조각만 클라로

마이페이지는 서버 컴포넌트다. 그런데 로그아웃 버튼은 눌렀을 때 팝업을 띄우고, 확인을 받고, 액션을 부르는 상호작용이 필요하다. 로그인 때 버튼 묶음만 `SocialLoginActions`로 떼어냈던 것처럼, 여기서도 `LogoutButton` 하나만 `"use client"`로 떼어내고 나머지 페이지는 서버 렌더로 뒀다.

이 컴포넌트가 하는 일은 로그인 액션 쪽과 판박이다. 버튼을 누르면 팝업을 열고(오탭으로 로그아웃되는 걸 막는 게 티켓의 요구였다), 확인 버튼을 누르면 `useTransition`으로 `logout()`을 부르면서 `isPending` 동안 팝업의 두 버튼을 잠가 연타를 막는다. 성공하면 액션이 서버에서 `/login`으로 redirect하니 클라에선 팝업을 닫을 일조차 없다 — 화면째 넘어간다.

팝업 디자인은 피그마가 없어서 토큰으로 직접 짰다. 가운데 뜨는 모달로 하고(티켓의 "뽈롱 튀어나오게"는 바텀시트보단 센터 팝업이 맞다고 봤다), 뒤는 스크림으로 덮었다. 스크림 색은 하드코딩하지 않고 앱이 이미 쓰는 `color-mix(in srgb, var(--plk-scrim) N%, transparent)` 패턴을 그대로 썼다 — 릴 오버레이·탭바 그라데이션이 쓰는 그 앵커색이다. 팝업은 `fixed inset-0`으로 띄웠는데, AppShell이든 ScrollArea든 `transform`을 안 걸어서 뷰포트 기준으로 제대로 앵커됐다(transform 조상이 있으면 fixed가 거기 갇힌다).

확인 버튼 색에서 한 번 걸렸다. 처음엔 danger를 꽉 채운 버튼(`bg-danger` + 흰 글자)으로 했는데, `--plk-danger`가 밝은 빨강(#f87171)이라 흰 글자를 얹으면 대비가 AA에 못 미친다. 채운 파괴 버튼용 전경색 토큰(`on-danger` 같은)이 없고, 배경색(`text-bg`)을 얹는 건 라이트/다크에서 서로 반대로 깨진다. 그래서 앱이 원래 쓰던 파괴 버튼 언어 — 테두리 + `text-danger` — 를 그대로 따랐다. 취소는 중립 테두리, 로그아웃은 빨강 글자. 마이페이지에 원래 있던 그 로그아웃 버튼과 같은 스타일이라 오히려 일관됐다.

## 로그아웃 상태 화면

로그인이 풀리면 프로필 카드 자리에 로그인 유도 카드(`LoginPromptCard`)가 들어간다. `ProfileCard`와 같은 섀시·간격을 써서, 로그인하면 그 자리가 자연스레 프로필로 바뀌어 보이게 했다. 이 카드는 그냥 `/login`으로 가는 `<a>`라 상호작용이 없어 서버 컴포넌트로 뒀다. 응원팀 줄과 로그아웃 버튼은 로그인 상태에서만 나오고, 환경설정(알림·다크 모드)과 FAQ·버전은 기기 설정이라 양쪽 공통으로 남겼다.

## 공용화는 이번에도 안 했다

`logout`·`isLoggedIn`·`LogoutButton`·`LoginPromptCard` 전부 mobile에만 뒀다. 웹은 아직 로그인 자체가 안 붙어서(로그인이 모바일 전용) 비교 대상이 없다. ADR 0019에서 열어 둔 후보 그대로 — 웹에 auth가 붙어 `apiFetch`·서버 액션이 같은 봉투·같은 쿠키 규약을 두 번째로 쓰게 될 때, 그때 `@plick/core` 승격을 판단한다. 지금 미리 빼면 웹이 안 쓰는 걸 떠안는다.

이 티켓은 mobile 스코프라 웹 마이페이지의 로그아웃 버튼은 손대지 않았다. 웹 auth 티켓에서 같이 붙인다.

## 검증

로컬 BE에 붙여 흐름을 다 밟았다. 로그인된 상태의 마이페이지에서 로그아웃 버튼 → 팝업 → 확인 → `/login`으로 넘어가고, 다시 `/me`로 가면 로그인 유도 카드가 뜬다(쿠키가 지워졌다는 뜻). 네트워크 탭엔 로그인 때와 똑같이 `POST /me → 303 See Other`만 보이고 8080 호출은 안 보인다 — 서버 액션이라 BE 호출은 서버끼리 오간다(ADR 0019에서 이미 겪은 그것). BE가 준 게 `data:null`이라 `apiFetch`가 그대로 null을 벗겨 주는데, 반환값을 안 쓰니 문제없었다.

### `redirect()`는 새로고침이 아니다 — 소프트 내비게이션

네트워크 로그의 `303`을 보고 "그럼 페이지를 통째로 새로고침하나?" 싶을 수 있는데, 아니다. 내비게이션엔 두 종류가 있다. **소프트 내비게이션**(클라 사이드)은 React 앱이 살아 있는 채로 바뀌는 라우트 조각의 RSC 데이터만 받아와 갈아끼운다 — JS/CSS 재다운로드 없음, 공용 레이아웃·컴포넌트 state 보존. **하드 내비게이션**(`window.location` 재로드나 그냥 `<a href>`)은 문서를 처음부터 다시 받아 React 트리·state가 다 날아간다. 앱 내부 이동에 `<a>` 대신 `next/link`의 `<Link>`를 쓰라는 이유가 이거다.

서버 액션의 `redirect()`는 **하드 리로드가 아니라 소프트 내비게이션**이다. 서버 액션은 form 제출이 아니라 Next 클라 런타임이 `fetch`로 부르는 거라, 응답의 `303`을 브라우저가 직접 따라가 새로고침하는 게 아니라 **Next 런타임이 가로채 소프트 내비게이션**으로 `/login`에 넘긴다. 그래서 로그 이름은 `POST /me`지만 화면은 통째로 리로드되지 않는다.

`<Link>`가 성능적으로 낫다는 말과의 관계도 정리해 두면: `<Link>`도 소프트지만 진짜 강점은 **prefetch**다 — hover/뷰포트 진입만으로 목적지를 미리 받아둬 클릭 시 즉시 넘어간다. `redirect()`는 목적지가 서버에서 런타임에 정해져(로그인 성공 → 홈 vs 온보딩, 로그아웃 → `/login`) 미리 받아둘 수가 없다. 그래서 목적지 RSC를 받아오는 왕복 지연은 있지만, **그건 prefetch 유무의 차이지 리로드 여부의 차이가 아니다.** 둘 다 소프트다. (`useRouter().push()`도 소프트지만 기본 prefetch가 없어 `redirect()`와 같은 결이다.)

## 후속 — 로그인 화면에 "둘러보기" 링크

리뷰에서 하나 걸렸다. 로그아웃하면 `/login`으로 보내는데, 그러면 "로그아웃한 채로 그냥 둘러보고 싶은" 사람이 로그인 화면에 갇힌다. 홈·피드는 비로그인으로도 볼 수 있으니(MY만 로그인 분기), 로그인을 강제할 이유가 없다. 그래서 로그인 화면 상단 우측에 작은 "둘러보기" 링크를 달아 홈(`/`)으로 빠져나갈 수 있게 했다.

`AuthScreen`은 로그인·회원가입이 공용하는데, 이 링크는 로그인에만 필요하다. 그래서 `homeHref` 옵셔널 prop으로 열고 로그인 페이지만 `"/"`를 넘긴다 — 회원가입은 그대로다. 마침 회원가입은 상단 좌측에 뒤로가기(`backHref`)를 쓰고 있어서, 상단바를 `justify-between`으로 두고 좌(뒤로가기)·우(둘러보기)를 각자 옵셔널로 채우게 했다. 둘 중 하나만 있어도 자리를 잡는다.
