# 0079. 개인정보처리방침 페이지 — 작성지침을 읽고 초안을 만들었다 (KAN-369)

## 왜 이 페이지가 필요했나

앱 스토어 제출을 준비하면서 KAN-369가 나왔다. App Store Connect와 Play Console 둘 다
제출 양식에 개인정보처리방침 URL을 넣는 칸이 있고, 없으면 제출 자체가 안 된다. PLick은
카카오/구글 로그인으로 이메일을 받는 서비스라 개인정보 보호법상으로도 어차피 의무다.

시작 전에 "내용을 백엔드에서 내려줘야 하나"를 먼저 정리했다. 결론은 프론트 정적 페이지다.
이 문서의 소비자는 스토어 심사원과 일반 방문자라 로그인도 데이터도 필요 없는데, BE에
의존시키면 BE 장애 때 방침 페이지가 빈 화면이 되는 실패 모드만 생긴다. 심사원이 열었을 때
안 뜨면 그게 곧 리젝 사유다. 내용이 바뀌는 주기도 코드 배포 주기보다 길고, 수집 항목이
바뀌는 건 어차피 프론트·백 코드가 같이 바뀌는 일이라 방침 개정도 같은 PR 흐름에 태우면
된다. 개정 이력은 git이 남겨 준다. BE가 관여할 지점은 문서 내용이 아니라 나중에 생길 수
있는 "방침 vN에 언제 동의했나" 같은 동의 기록 쪽이다.

## 작성지침 PDF를 읽었다

개인정보보호위원회 「개인정보 처리방침 작성지침」(2026.4., 185쪽)을 받아서 필요한 부분을
다 읽었다. 처음엔 인터넷에 굴러다니는 템플릿을 긁을까 했는데, 지침을 읽어 보니 그러면 안
되는 이유가 명확했다. 지침이 반복해서 강조하는 게 "실제 처리 현황과 일치"다. 템플릿에 흔한
"전화번호, 생년월일을 수집합니다" 같은 문구를 그대로 두면 실제 수집 항목과 불일치가 되고,
그 자체가 법 위반 리스크이자 심사 리스크다. 잘못 작성된 사례로 '~등' 같은 축약 표현,
제공받는 자를 "OO업체 등 5개사"로 뭉뚱그리는 것, 보유기간을 "목적 달성 시까지"로 추상적으로
쓰는 것들이 실려 있어서 그런 표현은 다 피했다.

지침의 기재사항은 24개인데 상당수가 '해당 시'다. 그래서 코드베이스를 먼저 뒤져서 PLick이
실제로 뭘 수집하는지부터 확정했다.

- 소셜 로그인으로 받는 것: 이메일, 소셜 계정 식별자 (구글은 scope가 `openid email`)
- 직접 입력: 닉네임, 응원팀
- 자동 수집: 인증 토큰 쿠키 2종(accessToken·refreshToken, HttpOnly), 좋아요·댓글 기록
- 없는 것: 분석 도구(GA류 grep으로 확인), 광고, 민감정보, 가명정보, 영상기기

이 기준으로 해당 없는 절(민감정보 공개, 가명정보, 행태정보, 자동화된 결정, 국내대리인,
영상정보처리기기)은 빼거나 "처리하지 않는다"로만 남겼다. 지침 15쪽에 해당 없으면 그렇게
써도 된다고 명시돼 있다. 쿠키 절은 지침이 요구하는 대로 쿠키가 뭔지 한 줄 설명 + 거부
방법 + 거부 시 제약(로그인 기능 이용 불가)을 넣었다. 권익침해 구제기관 연락처는 지침
최신판 기준(분쟁조정위 1833-6972, 신고센터 118, 경찰청 182)으로 적었다. 잘못된 사례에
연락처 누락·오기재가 있어서 그대로 옮겨 적었다.

혼자 확정할 수 없는 값들은 본문에 `[채움 필요: …]`로 남기고 `text-danger`로 빨갛게
칠했다. 운영 주체 명칭, 보호책임자 성명·직위·이메일, 탈퇴 후 보존 정책, AWS 리전(서울이
아니면 국외 이전 절을 다시 써야 한다), 14세 미만 차단 절차 유무, 회원 탈퇴 방법, 시행일자.
페이지를 열면 빨간 글씨가 바로 보여서 채우기 전에 배포하는 사고를 막는다.

## 구현

`apps/mobile/app/privacy/page.tsx` 서버 컴포넌트 하나로 만들었다. 상호작용이 없으니
`"use client"`도 필요 없다. 뼈대는 AppShell + ScrollArea, 상단바는 프로필 수정 화면의
EditTopBar 패턴을 그대로 따서 뒤로가기 + 중앙 타이틀로 했다. 뒤로가기 목적지는 홈으로
뒀는데, 심사원처럼 URL로 직접 들어오는 진입이 많은 페이지라 히스토리 back보다 명시적
목적지가 낫다고 봤다(BackButton 자체가 그렇게 설계돼 있기도 하다).

지침이 목차 + 하이퍼링크를 권장해서 절마다 `id`를 주고 상단에 앵커 목차를 달았다. 여기서
하나 걸린 게 스크롤 컨테이너다. 이 앱은 body가 아니라 ScrollArea(내부 overflow 컨테이너)가
스크롤 주체인데, 앵커 클릭 시 브라우저는 대상 요소의 가장 가까운 스크롤 가능한 조상을
스크롤해 주므로 그냥 동작한다. 대신 상단바가 sticky처럼 위에 있으니 절 제목이 바에 가리지
않게 각 섹션에 `scroll-mt-14`를 줬다. 프로덕션 빌드로 눌러 보니 제목이 바 바로 아래에
정확히 걸린다.

회원가입 화면의 "개인정보처리방침" 텍스트는 그동안 밑줄만 있는 장식이었는데 이번에 진짜
`<Link href="/privacy">`로 연결했다. "이용약관"은 아직 페이지가 없어서 그대로 뒀다
(별도 티켓감이다).

공개 접근은 별도 작업이 필요 없었다. proxy.ts가 비로그인 방문자를 강제 리다이렉트하지
않는 구조라(둘러보기 허용) /privacy도 로그인 없이 열린다.

## 검증에서 막힌 것

dev 서버로 확인하려는데 다른 세션의 `next dev`가 같은 폴더에 이미 떠 있어서 Next 16이
새 dev 인스턴스를 거부했다(같은 프로젝트 디렉터리에 락을 건다. autoPort로 포트를 바꿔도
소용없다). 마침 클린 빌드를 먼저 돌려 둔 상태라 `next start`(mobile-prod, :3101)로 띄워서
확인했다. 375px 모바일 뷰포트에서 상단·중단·하단 스크린샷, 목차 앵커 클릭 이동, 회원가입
링크 연결까지 봤다. lint·check-types·build 전부 통과.

## 남은 것

- [채움 필요] 7곳을 실제 값으로 치환 (치환 후 Todo 헬퍼 컴포넌트 제거)
- 배포 후 실제 URL을 App Store Connect / Play Console 제출 양식에 입력
- 이용약관 페이지는 별도 티켓으로
- App Privacy 설문(애플)과 데이터 보안 양식(구글)을 이 문서 기준으로 작성

## 웹에도 만들었다 (후속)

같은 세션 후속으로 데스크톱 웹(apps/web)에도 /privacy를 만들었다. 처음엔 웹 페이지에
문안을 복사할까 잠깐 생각했지만 바로 접었다. 이건 법률 문서라 두 앱의 문안이 한 글자라도
어긋나면 그 자체가 문제다. 나중에 방침을 개정할 때 한쪽만 고치는 사고가 눈에 선했다.

web-publishing 스킬의 승격 기준(같은 역할 + 앱 중립)에 정확히 들어맞았다. 본문은 토큰
유틸만 쓰고 모바일 레이아웃(AppShell·ScrollArea)에 결합돼 있지 않았으니까. 그래서 본문
전체(서문 + 앵커 목차 + 14개 절 + Todo·Section 헬퍼)를 `@plick/ui`의 `PrivacyPolicyBody`로
이동했다(복사 금지 규칙대로 이동이다). 좌우 패딩과 페이지 제목은 앱 쪽 래퍼 책임으로
분리했다 — 모바일은 상단바에 제목이 있고(px-edge 패딩), 웹은 본문 위 h1이라(text-hero +
max-w-narrow) 제목 위치 자체가 다르기 때문이다. 마이페이지(KAN-319)가 이미 잡아 둔
"GNB + max-w-narrow 중앙 컬럼" 패턴을 그대로 썼다.

웹 회원가입의 AuthCard에도 모바일과 똑같이 밑줄만 있던 "개인정보처리방침" 텍스트가 있어서
/privacy 링크로 연결했다(데스크톱이니 hover 상태도 추가).

검증은 양쪽 클린 빌드 + web-prod(:3100) 데스크톱 뷰포트와 330px 최소 기준선(가로 오버플로
scrollWidth == innerWidth 확인), mobile-prod(:3101) 재확인까지. 승격 후에도 모바일 렌더링이
승격 전과 동일한 걸 스크린샷으로 확인했다.
