# 0087. 핫이슈 캐러셀에 좌우 핸들을 달고 무한 루프로 바꾸기 (KAN-382)

## 무엇을 하려고 했나

홈 최상단 핫이슈 캐러셀에 두 가지를 요청받았다.

1. 웹과 모바일 양쪽에 좌우 이동 핸들(화살표 버튼)을 넣을 것
2. 마지막 카드에서 처음으로 돌아갈 때 카드가 왼쪽으로 좌라락 되감기는 걸 없애고,
   오른쪽으로도 왼쪽으로도 끝없이 이어지는 무한 캐러셀로 만들 것

캐러셀은 이미 `packages/ui/src/HotCarousel.tsx` 한 파일에 있고 모바일 홈과 웹 홈이 함께 쓴다
(KAN-338 때 `@plick/ui`로 승격했다). 그래서 이 파일 하나만 고치면 웹과 모바일이 동시에 바뀐다.
앱마다 다른 건 카드 렌더뿐이라 `children`으로 주입받는 구조도 그대로 쓸 수 있었다.

## 기존 구조부터 다시 읽기

건드리기 전에 지금 캐러셀이 어떻게 서 있는지부터 확인했다.

트랙은 `overflow-x-auto` + `scroll-snap-type: x mandatory`인 가로 스크롤 박스다.
카드 폭은 트랙 폭의 86%, 카드 사이 간격은 10px, 그리고 트랙 맨 앞뒤에 `7% − 10px`짜리
빈 스페이서가 하나씩 서 있다. 스페이서를 두는 이유는 ADR 0002 §6-2에 적어 뒀는데,
좌우 패딩으로 처리하면 카드의 86%가 '패딩을 뺀 영역' 기준이 돼서 첫 카드와 마지막 카드가
화면 정중앙까지 못 온다. 스페이서는 그 문제가 없다.

이 기하 덕분에 스크롤 좌표가 아주 단순해진다. 한 칸의 폭을

```
step = 트랙폭 × 0.86 + 10
```

이라고 두면, i번째 카드가 화면 정중앙에 오는 순간의 `scrollLeft`가 정확히 `i × step`이다.
0번 카드는 `scrollLeft = 0`이고, 마지막 카드는 스크롤 최대치와 딱 맞아떨어진다.
직접 계산해 보면 콘텐츠 전체 폭에서 트랙 폭을 뺀 값이 `(카드수 − 1) × step`으로 나온다.
이 성질을 계속 쓰게 되니 기억해 둘 만하다.

자동 넘김은 고정 `setInterval`이 아니라 리셋되는 `setTimeout`이다. 손가락이 닿으면 멈추고,
스크롤이 이는 동안에는 계속 뒤로 밀린다. 그래서 유저가 직접 넘기는 동안 타이머가 스와이프를
뺏지 않는다. 이 부분은 잘 돌고 있어서 손대지 않았다.

그리고 원래의 되감기 코드는 이랬다.

```js
const next = (activeRef.current + 1) % cards.length;
el.scrollTo({ left: next * step, behavior: "smooth" });
```

마지막 카드에서 `next`가 0이 되니까 `scrollLeft`가 0으로 돌아간다. 스크롤 위치가 실제로 왼쪽
끝까지 이동하는 거라, 카드 다섯 장이 화면을 좌라락 스쳐 지나간다. 이게 없애야 할 그 현상이었다.

## 무한 루프를 어떻게 만들 것인가

가로 스크롤 컨테이너에서 무한 루프를 만드는 정석은 복제다. 카드 목록을 여러 벌 이어 붙이고
가운데 벌만 '진짜'로 취급한다. 스크롤이 복제본 구간으로 넘어가면, 같은 카드의 가운데 벌 좌표로
순간이동시킨다. 복제본은 원본과 픽셀이 똑같으니 화면은 한 톨도 안 변하고 양옆 여유만 되살아난다.

여기서 핵심은 "얼마나 옮기느냐"다. 반올림해서 카드 번호로 옮기면 안 된다. 한 벌의 폭

```
span = 카드수 × step
```

만큼만 통째로 더하거나 빼야 한다. `span`은 한 벌의 주기라서, `scrollLeft`에 `span`을 더해도
화면에 보이는 카드와 그 카드의 위치가 완전히 같다. 소수점 위치, 즉 애니메이션이 카드와 카드
사이 어딘가를 지나는 중이어도 그대로 보존된다. 반올림을 섞으면 그 순간 카드가 살짝 튄다.

벌수는 3벌로 잡았다. 가운데가 진짜, 앞뒤로 한 벌씩 여유. 카드가 5장이면 슬라이드는 15장이 되고
가운데 벌은 인덱스 5~9다. 첫 페인트 전에 `useLayoutEffect`로 `scrollLeft = 5 × step`을 심어
가운데 벌에서 시작하게 했다. `useEffect`로 하면 0번 슬라이드가 한 프레임 보였다가 튀어 들어간다.

`useLayoutEffect`가 왜 다르냐면, 이건 React가 DOM을 바꾼 직후 브라우저가 화면을 그리기 전에
동기로 실행된다. `useEffect`는 그리고 난 뒤에 돈다. 스크롤 위치처럼 "처음부터 이 자리여야 하는"
값은 반드시 `useLayoutEffect`에서 심어야 한다.

복제본에는 `aria-hidden`을 달았다. 스크린 리더에 같은 기사가 세 번 읽히면 안 된다.

## 첫 버전: 스크롤이 멎으면 되돌린다

처음 만든 버전은 되돌리는 시점을 하나로 잡았다. 스크롤 이벤트가 150ms 동안 안 오면 멎은 걸로
보고, 그때 위치가 가운데 벌 밖이면 접는다.

멎은 뒤에만 접은 이유가 있다. 관성 스크롤이 굴러가는 중이나 `behavior: "smooth"` 애니메이션이
도는 중에 `scrollLeft`를 대입하면 그 움직임이 취소되면서 뚝 끊긴다. 그래서 다 끝나고 나서
조용히 옮기는 게 안전하다고 봤다. 스냅이 아직 자리를 잡는 중일 수도 있어서, 위치가 스냅점에서
1px 넘게 떨어져 있으면 접지 않고 타이머를 다시 걸게 했다.

여기까지 만들고 확인했을 때는 잘 도는 것처럼 보였다.

## 막힌 데 1: 브라우저 패널이 얼어 있어서 아무것도 검증이 안 됐다

확인하려고 브라우저 패널을 열었는데 이상했다. 초기 앵커링이 안 먹어서 `scrollLeft`가 0이었고,
핸들을 눌러도 꿈쩍을 안 했다. 코드가 틀린 줄 알고 한참 뒤졌다.

원인은 코드가 아니라 검증 표면이었다. 패널의 탭이 `document.visibilityState === "hidden"`
상태였다. 이 상태에서는 브라우저가 rAF(requestAnimationFrame, 다음 화면 그리기 직전에 콜백을
불러 주는 API)를 아예 안 돌린다. `scrollTo({ behavior: "smooth" })`는 컴포지터가 프레임마다
조금씩 위치를 옮기는 애니메이션이라 rAF가 멈추면 한 픽셀도 안 움직인다. `scrollLeft = x` 같은
즉시 대입은 프레임이 필요 없어서 잘 먹었다. 이 대비가 진단의 결정적 단서였다.

실제 크롬 탭으로 옮겨도 같았다. 창이 뒤에 있으면 렌더러가 얼어서 rAF가 안 돈다.
`await new Promise(r => requestAnimationFrame(r))`를 걸었더니 45초 타임아웃까지 안 돌아왔다.

그래서 검증을 두 갈래로 쪼갰다.

- 눈으로 볼 것(애니메이션, 핸들 모양, 빈자리 여부)은 iOS 시뮬레이터 Safari로 본다.
  홈 화면은 시뮬레이터에서 `localhost:3001`로 그대로 열린다.
- 논리(어느 인덱스로 가려 하는가)는 얼어 있는 탭에서도 결정적으로 잴 수 있게 만든다.
  트랙의 `scrollTo`를 가로채 요청된 좌표를 기록하고 즉시 반영시켰다.

```js
const req = [];
tr.scrollTo = function (o) {
  req.push(+(o.left / step).toFixed(2));
  tr.scrollLeft = o.left; // 애니메이션 대신 즉시 도착시킨다
};
```

이렇게 하면 얼어 있는 탭이 "애니메이션이 매번 끝까지 갔다"는 이상적인 조건으로 바뀐다.
핸들을 20번 연타했을 때 실제로 어느 인덱스를 요청하는지가 숫자로 남는다.
이 도구를 만들고 나서야 다음 문제를 제대로 짚을 수 있었다.

## 막힌 데 2: 연타하면 오른쪽 카드가 잠깐 사라진다

시뮬레이터로 넘어와 천천히 눌러 보니 멀쩡했다. 그런데 사용자가 "네가 하는 것처럼 천천히 하면
안 보이고, 나처럼 엄청 빠르게 버튼을 연타해서 마지막 페이지에 갔을 때 보인다"고 알려 줬다.
증상은 마지막 장에서 오른쪽 카드 자리가 잠깐 비었다가 조금 있다 카드가 나타나는 것.

처음엔 이미지 지연 로딩을 의심했다. 카드의 `<img>`가 `loading="lazy"`라, 화면 밖에 있는
복제본은 뷰포트에 들어오는 순간에야 받기 시작한다. 옆 칸으로 들어오는 카드가 잠깐 빈 상자로
보일 수 있는 조건이 맞았다. 그래서 핫이슈 카드 이미지를 `loading="eager"`로 바꿨다.
핫이슈는 홈 최상단이라 어차피 첫 화면 이미지고, `lazy`를 걸어 둔 게 오히려 LCP에 손해였다.
복제본이 세 벌이어도 URL이 같아 실제 요청은 카드 수만큼만 나간다.

이건 그 자체로 맞는 수정이었지만 증상은 그대로였다. 가설이 그럴듯하다고 원인인 건 아니었다.

진짜 원인은 위에서 만든 `scrollTo` 가로채기로 잡혔다. 연타할 때 요청되는 인덱스가 이랬다.

```
6, 7, 8, 9, 10, 11, 12, 13, 14, 14, 14, ...
```

14는 슬라이드 15장짜리 트랙의 마지막 칸, 즉 스크롤 물리적 끝이다. 그 오른쪽에는 카드가 없고
빈 스페이서만 있다. 그러니 화면 오른쪽이 비어 보인다. 그리고 150ms 뒤 되돌리기가 돌면서
가운데 벌로 순간이동하니, 조금 있다 카드가 나타나는 것처럼 보인다. 사용자가 말한 그대로였다.

왜 14까지 갔냐면, 되돌리는 시점이 "스크롤이 멎었을 때" 하나뿐이었기 때문이다. 연타하는 동안은
스크롤이 계속 이니까 멎을 틈이 없고, 목표는 눌린 만큼 계속 오른쪽으로 쌓인다. 3벌치 여유는
연타 앞에서 순식간에 소모된다.

## 고친 방법: 접는 시점을 셋으로 늘리고 목표에 상한을 둔다

되돌리기를 "가끔 뒤에서 정리하는 일"이 아니라 "움직이기 직전에 항상 하는 일"로 바꿨다.

한 벌 단위로 접는 동작을 `fold`로 따로 뺐다.

```js
function fold(el) {
  const span = count * stepOf(el);
  let pos = el.scrollLeft;
  let shift = 0;
  while (pos < span) {
    pos += span;
    shift += count;
  }
  while (pos >= span * 2) {
    pos -= span;
    shift -= count;
  }
  if (shift === 0) return;
  el.scrollLeft = pos;
  targetRef.current += shift;
}
```

위치와 목표를 같은 벌수만큼 함께 옮기는 게 중요하다. 둘 중 하나만 옮기면 어긋난다.
반올림이 한 군데도 없다는 점도 그대로다. 그래서 애니메이션 도중에 불러도 화면이 안 튄다.

접는 시점은 셋이다.

- 스크롤이 멎었을 때 (기존 되돌리기)
- 손가락이 트랙에 막 닿았을 때 (`touchstart`). 아직 안 움직인 시점이라 순간이동이 절대
  안 보이고, 그 드래그는 양쪽으로 한 벌씩 여유를 갖고 시작한다.
- 핸들을 누를 때마다. 자동 넘김도 같은 경로를 탄다.

여기에 목표 상한을 걸었다. 가운데 벌이 `[count, 2×count)`니까, 목표는 거기서 한 칸만 더
벗어난 `[count − 1, 2×count]`까지만 허용한다. 이 범위 안에서는 양옆에 반드시 복제본이 남아
있어서 빈자리가 생길 수 없다. (이 클램프는 나중에 웹에서 다른 문제를 일으켜 걷어내게 된다.
아래 "막힌 데 4"에 적었다.)

같이 고친 게 하나 더 있다. 원래는 스크롤 이벤트마다 현재 위치를 반올림해 인덱스 ref에 써 넣고,
핸들은 그 ref에 ±1을 했다. 그래서 애니메이션이 도착하기 전에 또 누르면 "지금 지나가고 있는
위치 + 1"이 돼서 연타가 제대로 안 쌓였다. 이걸 위치가 아니라 목표를 들고 있는
`targetRef`로 바꿨다. 스크롤 이벤트는 이제 점 인디케이터만 갱신하고 목표는 안 건드린다.
스와이프로 멈춘 자리는 되돌리기가 돌 때 목표에 다시 동기화한다.

가로채기로 다시 재 보니 연타 20번의 요청 인덱스가 이렇게 바뀌었다.

```
다음: 6, 7, 8, 9, 10, 6, 7, 8, 9, 10, 6, ...   (끝 인덱스 14에 절대 안 닿음)
이전: 4, 8, 7, 6, 5, 4, 8, 7, 6, 5, 4, ...     (0에도 절대 안 닿음)
```

`10 → 6`과 `4 → 8`로 보이는 자리가 접히는 순간이다. 10번 슬라이드와 5번 슬라이드는 같은
카드라서, 화면상으로는 그냥 6번으로 한 칸 더 간 것으로만 보인다. `atEnd`, `atStart` 모두
false였다. 시뮬레이터에서 15번 연타해도 양옆 카드가 항상 붙어 있었다.

## 핸들 디자인

처음엔 사진 위 칩과 같은 토큰(`bg-media-chip` + 테두리 + 블러)으로 만들었다. 사용자가
인스타그램 캐러셀 스타일을 원해서, 테두리와 블러를 빼고 반투명 흰 원판에 짙은 셰브론을 얹는
꼴로 바꿨다.

색은 테마를 타지 않는 미디어 토큰을 썼다. 원판은 `media-on`(사진 위에서는 라이트 테마에서도
항상 흰색인 값), 셰브론은 `media`(사진 자리 짙은 배경색). 사진 위에 얹히는 컨트롤이라
다크/라이트에 따라 뒤집히면 안 된다.

밝기는 한 번 왕복했다. `/85`는 너무 밝다고 해서 `/65`로 낮췄다.

셰브론 위치도 한 번 틀렸다. `ChevronMiniIcon`은 기하학적으로 정중앙이다. 실제로
`getBoundingClientRect`로 재 보니 버튼 중심과 획 중심의 x가 소수점까지 같았다. 그런데 눈으로는
안 가운데다. 셰브론은 획이 열린 쪽 여백이 더 넓어 보여서 그렇다. 처음엔 진행 방향 반대로 1px
밀었는데 더 나빠졌고, 반대로 진행 방향 쪽(바깥쪽)으로 1px 미니까 맞았다. 오른쪽 핸들은
오른쪽으로, 왼쪽 핸들은 왼쪽으로 1px.

핸들 위치는 `left-[7%]` / `right-[7%]`에 `translate-x-1/2`를 걸어 가운데 카드의 좌우 모서리에
물리게 했다. 7%는 스페이서 폭과 같은 값이라, 트랙이 넓어져도 카드 모서리를 계속 따라간다.
세로 중앙은 트랙에서 `pb-2`를 뺀 영역(`absolute inset-x-0 top-0 bottom-2`)을 기준으로 잡았다.
트랙 전체를 기준으로 하면 아래 여백만큼 핸들이 4px 처진다.

## 막힌 데 3: 스타일이 안 먹는 줄 알았는데 Safari 캐시였다

`/65`로 바꾸고 시뮬레이터를 다시 열었더니 원판이 통째로 사라지고 흰 화살표만 남았다.
`bg-media-on/65`와 `text-media`가 둘 다 안 먹은 모양새라, Safari가 `color-mix`를 못 읽나
싶었다.

크롬에서 `getComputedStyle`로 재 보니 배경도 글자색도 정상이었다. 그러면 코드 문제가 아니다.
Safari가 이전 CSS를 캐시에서 쓰고 있었던 거다. `text-media`는 이번에 처음 쓰는 클래스라
옛 CSS에는 아예 없었고, 없는 클래스는 조용히 무시되니 배경은 투명해지고 셰브론은 상속받은
흰색이 됐다. 쿼리스트링을 붙여 다시 여니 바로 정상이었다.

Tailwind는 소스에 나타난 클래스 문자열만 CSS로 만든다. 그래서 새 유틸을 처음 쓰는 순간은
빌드와 캐시 타이밍을 한 번 의심해 볼 만하다. "스타일이 안 먹는다"와 "옛 CSS를 보고 있다"는
화면상 구분이 안 된다.

## 막힌 데 4: 웹에서만 연타가 턱턱 걸리다가 좌라락 몰아서 간다

모바일은 다 됐는데 웹에서 새 증상이 나왔다. 새로고침 직후 오른쪽 핸들을 연타하면 턱턱
걸리면서 안 넘어가다가, 클릭을 멈추면 그제야 쌓인 거리를 한 번에 좌라락 이동한다. 왼쪽은
멀쩡하고 오른쪽만 그랬다. 화면 녹화를 프레임 단위로 뜯어 보니 클릭이 이어지는 동안 카드가
스냅 지점 사이 어중간한 위치에 계속 걸려 있었다.

원인은 세 겹이었다.

첫째, 위에서 건 목표 상한이 비대칭이었다. 시작점이 가운데 벌의 첫 칸(인덱스 `count`)이라
하한(`count − 1`)까지는 한 칸인데 상한(`2×count`)까지는 한 벌 거리다. 왼쪽 연타는 두 번째
클릭에 하한을 치고 바로 접혀서 계속 돌았지만, 오른쪽 연타는 목표가 상한에 눌린 채 같은
좌표로 `scrollTo`만 반복 호출됐다.

둘째, 크롬은 smooth 스크롤 도중 새 `scrollTo`가 오면 같은 목표여도 애니메이션을 처음부터
다시 시작한다. 이징이 느리게 출발하니 연타하는 동안 화면이 거의 안 움직이고, 클릭이 멎은
뒤에야 마지막 애니메이션이 남은 거리를 통째로 달린다. 좌라락의 정체가 이거다. 모바일
Safari는 재시작 거동이 달라서 같은 코드가 멀쩡해 보였다. 한 칸 폭도 달랐다 — 모바일은
332px, 웹은 890px라 같은 재시작이라도 웹이 훨씬 크게 보인다.

셋째, 리사이즈 재앵커링이 높이 변화에도 돌고 있었다. 웹 핫이슈 카드는 트윗 임베드라 로드
과정에서 트랙 높이가 연달아 변하는데, ResizeObserver 콜백이 그때마다 `scrollLeft`를 목표로
즉시 대입해 진행 중인 애니메이션을 점프로 끊었다. 새로고침 직후에만 유독 걸리던 이유다.

고친 방향은 이렇다.

- 상한 클램프를 걷어내고, 다음 목표가 가운데 벌을 벗어나면 위치와 목표를 한 벌 폭만큼 함께
  옮기고 나서 애니메이션을 건다. `fold`와 같은 원리라 애니메이션 도중이어도 화면 픽셀이
  같고, 목표는 항상 가운데 벌 안에 머문다. 클램프에 눌려 같은 좌표를 반복 요청할 일 자체가
  없어졌다.
- 연타 대응으로, 클릭이 왔을 때 직전 클릭의 애니메이션이 아직 가는 중이면 그 목표로 즉시
  완주시키고 나서 다음 칸으로 애니메이션하게 했다.
- ResizeObserver는 폭이 실제로 바뀌었을 때만 재앵커링한다. 높이 변화는 좌표에 영향이 없다.

검증은 가로채기를 한 단계 더 꼬았다. `scrollTo`를 "목표의 5%만 따라가는" 함수로 바꿔서,
애니메이션이 거의 못 따라간 상태에서 다음 클릭이 오는 최악 조건을 만들었다. 이 상태로 연타
10번의 로그가 `5→6, 6→7, 7→8, 8→9, 4→5(접힘), 5→6, ...`으로, 매 클릭이 정확히 한 칸씩
갔다. 왼쪽도 대칭으로 같았고, 위치를 7.4로 던져 두고(스와이프 흉내) 클릭하면 `7→8`로
재동기화됐다.

교훈은 두 가지다. 같은 코드라도 브라우저의 smooth 스크롤 재시작 거동이 달라 한쪽에서만
증상이 난다는 것, 그리고 ResizeObserver로 스크롤 좌표를 만질 때는 어느 축의 변화인지부터
걸러야 한다는 것.

## 막힌 데 5: "즉시 완주"는 뚝딱거린다 — 자체 rAF 애니메이터로

위 수정으로 연타가 한 칸씩 가긴 갔는데, 사용자가 "뚝딱거린다, 갑자기 빡 사라지는 느낌"이라고
했다. 왓챠처럼 막 갈겨도 부드러운 게 목표였다. 맞는 지적이다 — 즉시 완주는 클릭마다
순간이동이 한 번씩 끼는 방식이라, 애니메이션 중간 어딘가에서 카드가 툭 사라지고 다음
애니메이션이 시작된다.

왓챠류 캐러셀이 부드러운 이유는 네이티브 `scrollTo(smooth)`를 안 쓰기 때문이다. 자체
애니메이션을 돌리면 연타가 왔을 때 '지금 지나가는 위치'에서 새 목표로 그대로 이어 갈 수
있다. 네이티브는 이 리타겟이 안 된다 — 크롬은 무조건 처음부터 다시 시작한다.

그래서 `scrollTo(smooth)`를 걷어내고 rAF 기반 자체 애니메이터를 넣었다. 350ms ease-out
큐빅으로 프레임마다 `scrollLeft`를 대입한다. 연타가 오면 진행 중인 rAF를 취소하고 현재
위치에서 새 목표로 새 애니메이션을 시작하는데, ease-out은 출발이 빨라서 이 이음새가 눈에
안 보인다. 결과적으로 연타하는 동안 카드가 끊김 없이 미끄러지듯 흘러간다.

같이 챙긴 것들:

- 애니메이션이 도는 동안 `scroll-snap-type`을 잠시 끈다. mandatory 스냅이 프레임마다
  대입되는 중간 위치를 스냅점으로 되돌리려 해 애니메이션과 싸운다. 도착점이 정확히
  스냅점이라 복원 순간 움직임은 없다.
- 손가락이 닿거나(touchstart) 휠이 돌면(wheel) 애니메이션을 즉시 취소하고 유저에게 주도권을
  넘긴다. 프레임마다 대입하는 애니메이션과 드래그가 `scrollLeft`를 놓고 싸우면 안 된다.
- `prefers-reduced-motion`이면 애니메이션 없이 바로 도착시킨다.
- 스와이프로 목표와 위치가 어긋난 경우의 재동기화는 "애니메이션이 돌고 있지 않을 때만"
  현 위치 기준으로 목표를 다시 잡는 것으로 단순해졌다. 애니메이션 중엔 목표가 진실이다.

직전 절의 "즉시 완주" 로직은 이걸로 대체돼 걷어냈다.

## 남은 것과 비용

복제가 3벌이라 DOM 카드 수가 3배다. 핫이슈는 5장 안팎이라 15장 정도고, 이미지는 URL이 같아
브라우저가 한 번만 받는다. 사진이 없는 카드가 쓰는 트윗 임베드도 react-tweet의 SWR 캐시가
같은 키를 공유해서 요청은 한 번이다. 실질 비용은 DOM 노드 수뿐이라 감당할 만하다고 봤다.
핫이슈가 수십 장으로 늘어나면 복제 벌수 대신 앞뒤 한 장씩만 복제하는 방식을 다시 검토해야 한다.

손으로 스와이프해서 한 번에 여러 장을 날려 보내는 경우는 여전히 3벌 여유에 기대고 있다.
`touchstart`에서 접어 두기 때문에 한 번의 드래그는 양쪽 한 벌씩(카드 수만큼) 여유를 갖고
시작하고, 그 안에서 끝나지 않을 만큼 세게 던지는 건 실제로는 잘 안 나온다.
