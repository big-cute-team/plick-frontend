# 0093. 홈 무한스크롤 분리 — 기사 페이지 신설과 스크롤 튐 제거 (KAN-386)

## 문제: 팀 탭을 누르면 화면이 튄다

홈에서 팀 탭을 누를 때마다 화면이 점프하는 문제로 시작했다. 증상이 두 방향이라 까다로웠다.
스크롤을 한참 내린 상태에서 다른 팀을 누르면 뽝 하고 맨 위로 올라가 버리고, 그렇다고 팀을
누를 때 팀 탭을 화면 상단에 맞추는 식으로 바꾸면 이번엔 화면에 막 들어온 사람이 탭을 눌렀을 때
아래로 확 내려가 버린다. 어느 한쪽 규칙으로 고정하면 반대 상황이 깨지는 구조였다.

코드를 파 보니 스크롤을 강제로 옮기는 이유가 무한스크롤이었다. 팀을 바꾸면 이전 팀 리스트가
빠지고 새 팀 로딩(스켈레톤)으로 문서가 짧아졌다 다시 자라는데, 그동안 브라우저 스크롤 앵커링이
리스트 끝을 화면에 붙잡아 둔다. 그러면 무한스크롤 감시 요소(sentinel)가 계속 화면에 보이는
상태가 되고, IntersectionObserver가 다음 페이지 요청을 연쇄로 쏘아 댄다. 그래서 옛 코드는 팀
전환 때 무조건 스크롤을 맨 위로(또는 그 팀에서 보던 자리로) 옮겼다. 즉 튐은 버그가 아니라
무한스크롤을 지키기 위한 방어였고, 무한스크롤이 있는 한 "안 움직이는" 선택지가 없었다.

## 해결: 무한스크롤을 홈에서 떼어 기사 페이지로 옮긴다

그래서 문제를 화면 분리로 풀었다. 홈(웹·모바일 모두)은 첫 페이지 10건 고정으로 줄이고,
끝까지 내려보는 무한스크롤은 별도 기사 페이지가 맡는다. 웹에는 이미 `/articles`가 있었으니
모바일에 같은 라우트를 신설하고, 홈에는 섹션 제목 옆 "더보기"와 리스트 끝 "○○ 소식 더보기"
링크를 달아 기사 페이지로 잇는다.

이러면 홈에서 팀을 바꿔도 sentinel이 없으니 연쇄 요청 걱정이 없고, 스크롤을 아예 안 건드려도
된다. 위로도 아래로도 안 튀는 제3의 선택지가 생긴 거다. 팀 전환 때 스켈레톤 개수만 노출
건수(10)와 맞춰서 문서가 잠깐 짧아지며 브라우저가 scrollTop을 깎는 잔여 수축도 막았다.

기사 페이지에서는 맨 위가 곧 리스트 시작이라 스크롤 보정이 어색하지 않다. 홈이 어색했던 건
맨 위가 리스트가 아니라 핫이슈 캐러셀이라는 무관한 콘텐츠였기 때문이다. 같은 무한스크롤이라도
어느 화면에 두느냐로 UX가 갈렸다.

## 캐시 공유와 slice

홈과 기사 페이지는 같은 API(`GET /api/v1/articles`)를 소비하고 TanStack Query 쿼리키도
`articleKeys.feed(filter)`로 같다. 그대로 두면 기사 페이지에서 무한스크롤로 5페이지를 쌓고
홈에 돌아왔을 때 홈도 50건짜리 리스트가 되는 문제가 있었다. 쿼리키를 분리할까 하다가, 캐시
하나를 공유하고 홈에서 `slice(0, 10)`으로 잘라 그리는 쪽을 골랐다. 분리하면 같은 데이터를
두 번 받는 이중 페치가 생기고, 홈에서 본 팀을 기사 페이지에서 다시 열 때 캐시를 못 잇는다.
자르는 건 flatMap 뒤 한 줄이다.

## 팀별 스크롤 기억도 기사 페이지로

홈에 있던 팀별 스크롤 기억(`homeTabScrollTops`)은 지웠다. 홈 리스트가 한 페이지 고정이면
팀마다 기억할 위치라는 게 사실상 없다. 대신 기사 페이지에 같은 층(`articlesTabScrollTops`,
웹은 `articleTabScrollTops`)을 만들었다. 떠나는 팀의 위치를 적어 두고, 이미 봤던 팀으로
돌아오면 그 자리로 복원하고, 처음 여는 팀은 맨 위에서 시작한다. 화면 단위 복원
(`scrollTops.home` 등, 기사 상세 갔다 돌아올 때)은 다른 층이라 양쪽 다 그대로 뒀다.

검증하면서 이 두 층이 실제로 따로 노는 걸 확인했다. 기사 페이지 전체 탭에서 400px 내리고
맨유 탭 → 0에서 시작, 전체로 복귀 → 400 복원. 의도대로다.

## 모바일 기사 페이지의 구성

라우트는 웹과 똑같이 `/articles`(전체)와 `/articles/teams/[slug]`(팀별)다. 기존
`/articles/[postId]`(기사 세부)와 겹치지 않는 게 처음엔 걱정이었는데, Next는 정적 세그먼트
(`teams`)를 동적(`[postId]`)보다 먼저 매칭해서 충돌이 없다.

화면 본체(`ArticlesScreen` + `ArticlesFeed`)는 웹 `PostFeed`의 article variant를 이식한
것이다. 팀 탭 선택은 `history.replaceState`로 URL만 바꾼다 — 서버 왕복도 리마운트도 없이
`usePathname`이 갱신돼 필터가 따라오고, 탭 선택이 히스토리에 안 쌓여 뒤로가기 감각도
유지된다. 이 규약(KAN-350)을 그대로 물려받아서, 새로고침하면 그 팀 URL을 서버가 렌더한다.

기사 surface의 URL 헬퍼(`articlesTeamPath` 등)는 웹 전용으로 `apps/web/_utils/feed-paths.ts`에
있던 걸 `@plick/domain/format`으로 승격했다. 두 앱이 같은 규약을 쓰게 됐으니 ADR 0018의
단일 출처 원칙대로다. 모바일 `NewsItem`·`NewsItemSkeleton`·`TeamFilterTabs`도 홈 전용에서
두 화면 공용이 돼 `app/_components/`로 옮겼다.

## 하단 탭 4개와 재탭의 경계

하단 탭에 기사가 들어가 홈/기사/릴스/MY 네 개가 됐다. 아이콘은 피그마 시안이 없어 기존
세트(24 그리드, 1.8 스트로크)에 맞춰 신문 모양을 직접 그렸다. 햄버거 메뉴(TopBarMenu)는
같은 `TABS` 상수를 읽어서 자동으로 따라왔다.

기사 탭의 href는 홈 탭처럼 마지막으로 보던 팀 URL이다(`articlesFilter`를 스토어에 동기화).
활성 판정은 `/articles` 전체라 기사 세부에서도 기사 탭이 빛나는데, 여기서 함정이 하나 있었다.
기존 재탭 로직은 "활성 탭 클릭 = preventDefault + 맨 위로 + 새로고침"이라, 세부 페이지에서
기사 탭을 누르면 아무 일도 안 일어나는 죽은 버튼이 된다. 그래서 `Tab` 타입에 `surface`
판정을 따로 뒀다 — 활성이어도 리스트 화면 밖(세부)이면 재탭이 아니라 목록으로 돌아가는 평범한
이동이다. 웹 GNB의 NavItem이 이미 같은 구분을 하고 있어서 그 판단을 가져왔다.

같은 팀 태그 재탭은 기존대로 맨 위 + 첫 페이지 재수신을 유지하기로 했다. 단순히 스크롤만
올리는 안도 검토했지만 사용자가 지금 동작을 골랐다.

## 기사 세부의 뒤로가기

모바일 기사 세부의 뒤로가기가 `href="/"` 하드코딩이었다. 홈에서 들어왔으면 맞지만 이제 기사
목록에서도 들어오니 목적지를 고정할 수 없다. `BackButton`에 `behavior="back"` 모드를 추가해
히스토리 back을 먼저 시도하고, 딥링크 진입처럼 되돌아갈 히스토리가 없으면 `/articles`로
폴백한다. `window.history.length > 1` 판정이 완벽하진 않지만(새 탭에서도 1보다 클 수 있다)
실용적으로 충분했다. href 자체는 앵커로 남아 크롤러가 따라갈 내부 링크 몫도 겸한다.

## 제목 블록까지 통째로 고정

작업 중간에 요구가 하나 더 들어왔다. 기사 페이지에서는 제목("지금 올라온 소식")과 부제, 팀
탭까지 전부 스크롤에 고정돼 있으면 좋겠다는 것. 팀 탭만 sticky던 걸 제목 블록과 한 덩어리로
묶었다.

구조가 살짝 꼬였는데, 제목은 서버 컴포넌트(ArticlesScreen)에 있고 팀 탭은 클라 컴포넌트
(ArticlesFeed) 안에 있어서 그냥은 한 래퍼로 못 묶는다. ArticlesFeed에 `header` 슬롯(prop)을
뚫고 서버가 JSX를 내려보내 sticky 래퍼 안에서 탭과 함께 그리게 했다. 서버 컴포넌트가 클라
컴포넌트에 JSX를 prop으로 넘기는 건 되는 일이다(직렬화 가능한 RSC 페이로드).

여기서 React 경고를 하나 만났다. "Each child in a list should have a unique key prop" —
리스트를 만든 적이 없는데도 떴다. 서버가 prop으로 넘긴 엘리먼트는 직렬화 과정에서 정적
자식이라는 표시를 잃어서, 클라에서 형제와 나란히 놓이면 React가 동적 배열로 취급해 key를
요구한다. 넘기는 쪽에서 `key`를 명시해서 정리했다.

웹도 같은 요구가 적용돼 `PostFeed`에 같은 `header` 슬롯을 만들고 GNB(h-16) 아래에 고정했다.
위 여백(pt-7)을 sticky 래퍼 안으로 옮기는 걸 잊으면 고정 중에 그 틈으로 리스트가 비쳐 보인다.

## SEO 정리

- 웹 `/articles`는 그동안 "모바일 대응 페이지 없음"이라 canonical만 달았는데(KAN-346),
  모바일에 대응 페이지가 생겼으니 상호 alternate를 붙였다. 웹이 `media` 조건으로 모바일
  URL을 선언하고, 모바일은 웹을 canonical로 가리킨다.
- 모바일 `/articles/teams/[slug]`는 웹과 같은 정책으로 canonical을 데스크톱 팀 허브
  (`/teams/[slug]`)에 몰았다. 같은 팀 기사 목록이라 시그널을 한 곳에 모은다.
- 모바일 사이트맵에 `/articles`를 추가했다. 팀별 기사 페이지는 canonical이 딴 데를 가리키니
  싣지 않는다.
- 홈이 첫 페이지만 렌더해도 SEO 손해는 없다. 크롤러는 원래 무한스크롤 다음 페이지를 못 본다.
  오히려 더보기 앵커로 기사 페이지 내부 링크가 늘었다.

## 검증에서 배운 것: 숨은 브라우저 패널은 IntersectionObserver도 얼린다

브라우저 패널로 기사 페이지 무한스크롤을 검증하는데 스크롤을 끝까지 내려도 다음 페이지 요청이
안 나갔다. sentinel은 뷰포트 안에 있고 커서도 살아 있는데 요청만 없다. 한참 의심하다가 직접
IntersectionObserver를 만들어 붙여 봤더니 내 프로브의 콜백조차 안 불렸다. 숨은(hidden)
브라우저 패널은 렌더링 프레임이 돌지 않아 rAF만이 아니라 IntersectionObserver 알림도 얼어
있는 거였다. 전에 rAF 애니메이션 검증에서 같은 함정을 겪었는데 관찰자 API까지 같은 계열인 줄은
이번에 알았다. iOS 시뮬레이터로 다시 확인하니 스와이프 몇 번에 다음 페이지들이 정상으로 이어
붙었다. 스크롤 위치 검증(scrollTop 읽고 쓰기)은 레이아웃 값이라 패널에서도 정확하다 — 얼어
있는 건 프레임에 묶인 콜백이지 레이아웃 자체가 아니다.

하나 더: 패널을 desktop 프리셋(native size)으로 리사이즈하면 뷰포트 높이가 0이 되는 경우가
있다. `innerHeight`가 0이면 스크롤 자체가 안 되니 명시 크기(1280x800)로 잡아야 했다.

## 후속: 스크롤 때마다 sticky 위에 틈이 번쩍이는 문제

붙이고 나니 스크롤할 때마다 고정된 헤더 블록 위로 얇은 틈이 생겼다 사라진다는 피드백이 왔다.
원인은 당겨서 새로고침이었다. 모바일 `ScrollArea`가 콘텐츠를 `translateY(distance)` 껍데기로
감싸는데, 이 transform이 평상시(`translateY(0)`)에도 늘 걸려 있었다. 조상에 transform이
있다는 사실만으로 브라우저는 안쪽 sticky를 컴포지터(스크롤 스레드)에서 고정하지 못하고 메인
스레드에서 좌표를 따라가게 되는데, 빠른 스크롤에서는 이 갱신이 프레임을 한 박자씩 놓쳐서 그
늦은 만큼이 틈으로 보인 거다.

재밌는 건 웹 `FeedPullRefresh`는 이미 같은 문제를 알고 있었다는 점이다. 거기는
"translateY(0)이 lg 사이드바 sticky를 깬다"는 이유로 제스처가 도는 동안(`active`)과 복귀
애니메이션 구간(`settling`)에만 transform을 달았다. 같은 패턴을 모바일 `ScrollArea`에
이식했다 — 평상시엔 transform이 아예 없어 sticky가 컴포지터 고정을 되찾고, 당기는 동안만
transform이 붙는다(그때는 스크롤 관성이 없어 늦어도 안 보인다). 스피너의 절대배치 기준이
transform에 기대고 있었어서 껍데기에 `relative`를 상시로 깔아 기준을 유지했다.

## 후속: 그래도 남는 실금 — 소수점 픽셀

transform을 걷어낸 뒤에도 축소된 반응형 화면에서 sticky 블록 위로 가는 실금이 비친다는
피드백이 왔다. 이번엔 레이아웃부터 재 봤다. scrollTop을 200.5, 333.33 같은 소수점 값으로
놓고 sticky 래퍼와 스크롤러의 top 차이를 재니 정확히 0이었다. 레이아웃은 붙어 있는데 보이는
건 틈이라면 페인트 문제다. 스크롤 위치가 소수점이면 sticky 레이어와 그 밑을 지나가는 콘텐츠
레이어가 디바이스 픽셀 반올림을 서로 다르게 해서, 경계에 콘텐츠가 비치는 실금이 생긴다. 축소
스케일에서는 CSS 픽셀 경계가 디바이스 픽셀 사이에 떨어지는 일이 더 잦아 더 자주 보인다.

수학으로 없앨 수 있는 게 아니라서 덮는 쪽으로 갔다. sticky를 1px 위로 겹친다 — 모바일은
`-top-px`(넘친 1px는 스크롤 영역이 잘라낸다), 웹은 `top-[63px]`(GNB 64px보다 1px 위,
겹친 부분은 z가 높은 GNB가 덮는다). 실금이 생길 자리에 sticky 배경이 1px 먼저 와 있으니
반올림이 어느 쪽으로 튀어도 비칠 틈이 없다.

## 후속: 잘린 팀 탭 자동 정렬

팀 탭이 가로 스크롤이라 좁은 화면에서는 끝쪽 탭이 반쯤 잘리는데, 잘린 탭을 클릭해도 그대로 잘려
있어 뭘 골랐는지 안 보인다는 피드백이 왔다. `TeamFilterTabs`(웹·모바일 둘 다)에 선택 탭을
`scrollIntoView({inline: "nearest"})`로 끌어오는 이펙트를 달았다. 클릭 핸들러가 아니라
`value` 변화에 반응하게 한 게 포인트다 — 클릭이든 팀별 URL 직접 진입이든 선택은 결국 value로
오니까 한 자리에서 다 잡힌다. `nearest`라 이미 다 보이는 탭에는 아무 일도 안 하고, 첫 렌더만
애니메이션 없이 즉시 맞춘다.

검증하다가 또 패널 함정을 밟았다. smooth 스크롤도 프레임 기반이라 hidden 패널에서는 얼어서,
클릭해도 scrollLeft가 0 그대로였다. behavior를 auto로 강제 호출하니 정확히 움직이는 걸로
로직을 확인했다(60.5px 이동, 완전 노출). IntersectionObserver와 같은 계열의 한계다.

## 남은 것

- 탭 전환 시 클라가 맞추는 `document.title`("… | PLick")과 서버 title 템플릿
  ("%s | 플릭 PLick")이 미묘하게 다른 기존 문제를 발견했다. 이번 범위가 아니라 별도 작업으로
  분리했다.
- 기사 탭 아이콘은 시안 없이 그린 것이라 디자인이 나오면 교체될 수 있다.
