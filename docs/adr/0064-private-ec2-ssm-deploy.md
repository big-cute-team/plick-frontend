# 0064. 프라이빗 EC2 전환과 SSM 배포 (KAN-334)

## 배경

지금까지 프론트 EC2는 퍼블릭 서브넷에 있었다. 퍼블릭 IP가 있으니 GitHub Actions 러너가
scp로 산출물을 올리고 ssh로 릴리스 스크립트를 흘려보내는, 제일 단순한 배포가 가능했다
([ADR 0059](0059-mobile-ec2-deploy.md)). 그런데 인프라를 정리하면서 구성이 바뀌었다.
Next EC2는 프라이빗 서브넷으로 들어가고, 사용자 트래픽은 퍼블릭 ALB로만 받고, BE 통신은
프라이빗 ALB로만 나가는 구조다. 퍼블릭에 세워 뒀던 기존 리소스는 다 지우고 다시 만들기로 했다.

EC2가 프라이빗으로 들어가는 순간 기존 배포는 그냥 죽는다. 퍼블릭 IP가 없으니 러너가 ssh로
닿을 방법이 없다. 이번 세션은 그 배포 경로를 새로 뚫는 작업이었다. 조건이 하나 더 있었는데,
EC2 한 대에 똑같은 세팅을 또 해야 하니 과정을 문서에 상세하게 남겨야 했다.

## 배포 경로를 어떻게 다시 뚫을까

프라이빗 인스턴스에 밖에서 명령을 넣는 방법을 몇 가지 놓고 골랐다.

먼저 배스천(bastion) 호스트. 퍼블릭 서브넷에 점프용 EC2를 하나 두고 거길 거쳐 ssh하는
전통적인 방법인데, 지키고 패치해야 할 서버가 한 대 늘고, 애초에 "SSH를 없애는" 방향과
어긋난다. 바로 버렸다.

다음은 SSH over SSM. SSM 세션 위로 SSH 터널을 뚫으면 기존 scp·ssh 흐름을 거의 그대로 쓸 수
있다. 처음엔 워크플로 변경이 제일 적어 보여서 끌렸는데, 뜯어보니 러너에 session-manager-plugin을
깔아야 하고, 어차피 OIDC로 AWS 자격을 만들어야 하고, SSH 키도 여전히 관리해야 했다. 기존
흐름을 지키려고 부품만 늘리는 꼴이었다.

결론은 S3 + SSM Run Command였다. 러너가 빌드 산출물을 S3에 올리고, SSM `send-command`로
EC2에게 "S3에서 내려받아 릴리스해라"라고 시키는 방식이다. SSH 키가 완전히 사라지고, 러너와
EC2가 직접 연결될 필요가 없어진다. SSM은 에이전트가 EC2 안에서 밖으로 나가 붙는 구조라
인바운드 포트를 하나도 안 열어도 된다. 보안그룹에서 22번이 아예 없어졌다.

인증은 GitHub OIDC로 했다. IAM에 GitHub의 OIDC 공급자(`token.actions.githubusercontent.com`)를
등록하고, `big-cute-team/plick-frontend`의 main 브랜치에서만 assume할 수 있는 배포 롤을 만들었다.
로컬 git remote가 옛 이름(`frontend`)을 물고 있어서 신뢰 정책에 옛 이름을 넣을 뻔했다.
리포 이름이 바뀌면 OIDC 토큰의 sub 클레임은 새 이름으로 나오므로 신뢰 정책도 새 이름이어야 한다.
장수 액세스 키를 시크릿에 넣는 방식은 유출되면 끝이라 처음부터 배제했다. OIDC는 워크플로가
돌 때마다 GitHub이 서명한 단기 토큰을 STS에 내밀고 몇 분짜리 자격을 받아 오는 구조다.
워크플로에 `permissions: id-token: write`를 줘야 이 토큰이 발급된다는 걸 잊기 쉽다.

배포 롤 권한은 좁게 잘랐다. S3는 아티팩트 버킷에 `PutObject`만, SSM은 우리 인스턴스 하나와
`AWS-RunShellScript` 문서에만 `SendCommand`를 걸었다. SSM이 대상 인스턴스와 실행 문서 양쪽
ARN에 권한을 요구한다는 건 이번에 처음 알았다.

## 네트워크에서 챙긴 것

프라이빗 서브넷이라 당연하던 것들이 당연하지 않았다. SSM이 붙는다고 인터넷이 되는 게
아니다. SSM은 VPC 엔드포인트로도 붙을 수 있어서, Node 설치 같은 아웃바운드는 NAT가 따로
있어야 한다. 그래서 세팅 첫 단계를 "아웃바운드 확인 curl"로 잡았다.

S3는 게이트웨이 엔드포인트를 프라이빗 라우트 테이블에 붙였다. 이게 없으면 배포 때마다
tarball이 NAT를 통과하면서 처리 요금이 나간다. 게이트웨이 엔드포인트는 무료고 라우트
테이블에 경로 한 줄 추가되는 게 전부라 안 쓸 이유가 없다. 콘솔에서 "엔드포인트 서비스"라는
비슷한 이름의 메뉴(PrivateLink 판매자용)에 잘못 들어가기 쉬운데, 우리가 쓰는 건 그냥
"엔드포인트"다.

## 워크플로와 릴리스 스크립트 수정

`deploy.yml`에서 SSH 관련 세 스텝(Prepare SSH, scp 업로드, ssh 릴리스)을 들어내고
OIDC 자격 → S3 업로드 → SSM 실행으로 바꿨다. 빌드와 standalone 조립은 그대로다.

release.sh는 원래 ssh 표준입력으로 흘러들어가 EC2에 존재할 필요가 없는 파일이었다. 그 성질을
유지하고 싶어서, 매 배포마다 tarball과 함께 release.sh도 S3에 올리고 SSM 명령이 그걸 내려받아
실행하게 했다. 항상 그 커밋의 스크립트가 실행되니 코드와 스크립트 버전이 어긋날 일도 없다.
스크립트 쪽 변경은 tarball을 `/tmp`에서 기다리는 대신 S3에서 직접 내려받는 부분뿐이다.
그래서 EC2에 aws CLI가 필요해졌다. 우분투에 기본으로 없어서 세팅 단계에 snap 설치를 추가했다.

여기서 함정 두 개를 미리 밟았다.

하나는 실행 유저다. SSM Run Command는 root로 실행된다. 그런데 pm2 데몬과 `/srv`는 전부
ubuntu 소유다. root로 pm2를 부르면 root 홈에 새 pm2 데몬이 하나 떠 버려서, 기존 ubuntu
데몬의 프로세스는 안 보이고 프로세스가 이중으로 뜨는 사고가 난다. 그래서 SSM 명령에서
`sudo -u ubuntu -H env APP=... bash release.sh`로 내려서 실행한다. `-H`가 HOME을
`/home/ubuntu`로 잡아 주는데, pm2가 데몬 소켓을 `$HOME/.pm2`에서 찾기 때문에 이게 빠지면
유저를 바꿔도 같은 사고가 난다.

다른 하나는 `AWS-RunShellScript`의 에러 처리다. 이 문서는 commands 배열을 셸 스크립트
하나로 이어 붙여 실행하고, 종료 코드는 마지막 명령 것만 본다. `set -e`를 첫 줄에 넣지
않으면 중간에 S3 다운로드가 실패해도 다음 명령이 성공하면서 전체가 Success로 찍힌다.
배포가 터졌는데 초록불이 뜨는 최악의 조합이라, commands 첫 줄을 `set -e`로 고정했다.

`send-command`는 비동기라는 점도 처리해야 했다. 명령을 던지면 CommandId만 돌아오고 끝이다.
그대로 두면 서버에서 헬스체크가 실패해 롤백이 돌아도 Actions는 초록불이다. 그래서
`get-command-invocation`을 5초 간격으로 폴링해서 상태가 끝날 때까지 기다리고, 서버 stdout을
스텝 로그에 그대로 찍고, Success가 아니면 stderr까지 찍고 exit 1 한다. 릴리스 스크립트의
헬스체크 실패 → 자동 롤백 → exit 1이 SSM 상태 Failed로, 다시 Actions 빨간불로 이어지는
줄이 이걸로 복원됐다.

## 다시 세우면서 재사용한 것들

퍼블릭 쪽 리소스를 지웠어도 살아남은 게 꽤 있었다. ACM 인증서는 `plick.co.kr`과
`*.plick.co.kr`이 한 장에 담긴 채로 발급 상태 그대로였다. 와일드카드가 `m.plick.co.kr`을
커버하고 apex가 따로 들어 있으니 새 퍼블릭 ALB 리스너에 이 한 장만 다시 붙이면 된다.
Route 53 호스팅 영역도 살아 있었다. `m.plick.co.kr` 레코드는 없어졌지만 어차피 새 ALB를
가리켜야 해서 나중에 만들면 그만이고, ACM 검증용 CNAME이 남아 있는 게 오히려 중요했다.
그게 인증서 자동 갱신의 근거라 지우면 안 된다.

EC2 쪽 세팅(Node 22, pm2, 디렉터리, `.env`, pm2 startup)은 ADR 0059 때와 같은 내용을 새
인스턴스에 반복했다. 접속만 ssh에서 SSM 세션으로 바뀌었는데, 세션이 ssm-user로 열리기
때문에 `sudo su - ubuntu`를 먼저 하는 습관이 필요하다. 이것도 pm2 데몬이 안 보이는 사고와
같은 뿌리다.

## 문서

[docs/deploy.md](../deploy.md)를 새 구성 기준으로 다시 썼다. 티켓 요구사항이 "EC2 한 대에
같은 설정을 또 해야 하니 상세하게"였어서, 0단계 네트워크 전제부터 IAM 정책 JSON, 시크릿
표, SSM 세션에서의 확인 방법, 새로 생긴 실패 유형(AssumeRole 실패, aws CLI 없음, root pm2
사고)까지 순서대로 담았다. 옛 문서의 SSH·퍼블릭 IP 전제는 전부 걷어냈다.

작업이 다 끝난 뒤에는 이 문서를 한 번 더 갈아엎었다. 나중에 포트폴리오 글로도 쓸 수
있게, "프라이빗 EC2를 띄운 직후"부터 도메인 연결과 마지막 반쪽 장애 트러블슈팅까지를
콘솔 메뉴 경로(어느 탭에서 뭘 누르는지) 수준으로 풀고, 이번에 밟은 함정 전부를 해당
단계 자리에 ⚠️로 박아 넣었다. 스크린샷 들어갈 자리는 📷로 표시해 뒀다.

## 첫 배포에서 만난 pm2 데몬 경합

첫 배포에서 web은 17초 만에 끝났는데 mobile은 SSM 명령이 9분 넘게 InProgress에 매달리다
폴링 한도에 걸려 빨간불이 났다. 서버 로그도 비어 있었다. 명령이 실패한 게 아니라 안 끝난
것이었다.

두 잡이 같은 초에 같은 인스턴스로 send-command를 보냈고, 두 release.sh가 동시에 pm2를
불렀다. pm2 클라이언트는 데몬이 안 떠 있으면 자기가 스폰하는데, 두 클라이언트가 동시에
이 구간에 들어가면 한쪽이 데몬 소켓을 기다리며 영원히 매달릴 수 있다. web이 데몬을 띄우며
이겼고 mobile이 물렸다. SSH 시절에는 두 배포가 러너 두 대에서 각자 ssh로 들어와도 결국
같은 경합이 가능했는데 운 좋게 안 밟았던 것 같다.

수정은 두 겹으로 했다. release.sh 첫머리에서 `/tmp/plick-release.lock`에 flock을 걸어
릴리스 전체를 인스턴스 단위로 직렬화했다. 릴리스가 십몇 초라 기다리는 쪽 손해가 없다.
그리고 SSM 파라미터에 `executionTimeout` 420초를 넣어, 무슨 이유로든 서버에서 명령이
매달리면 에이전트가 끊고 실패로 확정하게 했다. 폴링 한도(450초)보다 짧게 잡아야 hang이
"폴링 시간 초과"가 아니라 "명령 실패"로 잡힌다. AWS-RunShellScript의 기본 executionTimeout이
3600초라는 것도 이때 알았다. 기본값이면 hang이 한 시간 동안 InProgress로 남는다.

매달려 있던 mobile 릴리스 프로세스는 SSM 세션에서 pkill로 정리하고 재배포로 복구했다.

## 배포는 됐는데 화면 일부만 비었다

트래픽까지 다 연결하고 나니 이상한 패턴이 남았다. 피드와 릴스는 멀쩡한데 홈 핫이슈
캐러셀과 기사 상세만 비었다. 네트워크 탭은 200이었다. 문서 응답 자체는 성공인데 내용만
없는, 서버 쪽 fetch가 의심되는 모양새였다.

원인은 `API_BASE_URL`이 "빌드 시점에 굳는다"는 이해가 반쪽짜리였던 것 하나였다.
이 값을 읽는 자리가 두 군데고 시점이 다르다. 브라우저 fetch가 타는 `/be`
프록시(rewrites)의 목적지는 정말로 빌드 때 `routes-manifest.json`에 문자열로 굳는다.
그런데 서버 컴포넌트 fetch의 base(`apiFetch`의 `baseUrl()`)는 실행 시점에
`process.env.API_BASE_URL`을 읽는다. Next가 빌드 때 인라인하는 env는 `NEXT_PUBLIC_`
뿐이고 서버 번들의 `process.env`는 그냥 런타임 참조다. 우리는 "빌드에 굳으니 EC2
`.env`에 넣어도 안 먹는다"고 문서에 박아 두고 `.env`에서 뺐는데, 그 탓에 EC2에서 서버
fetch가 전부 `localhost:8080` 폴백으로 돌고 있었다. 프록시는 시크릿 값으로 제대로
구워졌으니 클라 fetch 화면(피드·릴스)만 멀쩡했던 것이다. 서버에서 그리는 화면(홈
핫이슈, 기사 상세)이 비고 클라 fetch 화면은 뜨는 반쪽 장애의 정체가 이거였다.

여기서 진단을 한 번 틀렸다. 처음엔 홈이 동적 API(cookies 등)를 안 쓰니 빌드 때 정적으로
프리렌더되고, 러너에서 실패한 fetch 상태가 HTML에 박제된 것도 원인 중 하나라고 봤다.
그래서 홈과 웹 기사 목록에 `force-dynamic`을 붙이는 수정까지 만들었다. 그런데 `.env`만
고쳤는데 병합 전인데도 캐러셀이 살아났다. 박제 가설이 맞다면 정적 HTML이 그대로 나와야
했다. develop을 그대로 빌드해 라우트 표를 보니 홈이 이미 ƒ(Dynamic)였다. Next 15부터
fetch 기본이 no-store고, 캐시 안 된 fetch를 쓰는 라우트는 자동으로 동적 렌더로 빠진다.
홈은 애초에 매 요청 서버에서 그려지고 있었고, 박제는 없었다. `force-dynamic` 수정은
걷어냈다. 없는 문제를 고치는 코드였다.

교훈이 하나 더 있었다. `.env`에 값을 넣고 `pm2 restart --update-env`를 했는데도 처음엔
안 먹었다. `--update-env`는 `.env` 파일을 읽는 게 아니라 명령을 실행한 셸의 현재 환경을
프로세스에 넣는 옵션이다. release.sh가 재기동 전에 `set -a`로 `.env`를 소싱하는 게 그래서
있는 단계였다. 손 재기동도 같은 순서(`set -a; . shared/.env; set +a; pm2 restart ...
--update-env`)여야 하고, 적용 여부는 `pm2 env <id>`로 프로세스에 실제 들어간 값을 봐야
확실하다. deploy.md의 틀린 서술(".env에 넣어도 안 먹는다")은 두 시점 이야기로 고치고,
이 재기동 함정도 운영 절에 적었다.

덧붙여 화면은 에러인데 네트워크 탭이 200인 게 처음엔 헷갈렸는데, Next가 응답을
스트리밍으로 먼저 열고(이때 상태 코드가 확정된다) 렌더 중 터진 에러를 본문에 실어
에러 바운더리로 그리기 때문이다. 서버 렌더 실패를 status로 거를 수 없다는 뜻이다.

로그인이 안 되는 건 별개 문제로, 카카오·구글 콘솔에 새 도메인의 리다이렉트 URI를
등록하는 운영 작업이라 콘솔에서 처리했다.

## 남은 것

이 브랜치가 main까지 가야 새 워크플로로 첫 배포가 돈다. 그 전에 GitHub 시크릿을
`AWS_DEPLOY_ROLE_ARN`·`EC2_INSTANCE_ID`로 갈아끼우고 옛 `EC2_HOST`·`EC2_SSH_KEY`를 지워야
한다. 첫 배포가 성공하면 퍼블릭 ALB에 대상 그룹을 붙이고 Route 53 레코드를 새 ALB로
돌리는 것까지가 이 티켓의 나머지다. `API_BASE_URL`은 내부 ALB DNS 이름으로 넣되, 빌드
시점에 굳는 값이라 시크릿 갱신 후 재배포가 필요하다는 성질은 그대로다.
