# 0242. 예측 탭에 AI 경기 브리핑 카드를 붙인다 (KAN-724)

## 티켓

에픽 KAN-717은 기사와 경기 기록으로 짧은 AI 경기 브리핑을 만들어 예정 경기 화면에 보여 주는 신규 기능이다.
여섯 장으로 쪼개져 세 사람이 같은 날 병렬로 간다. 이민욱이 DB(KAN-718)와 읽기 API(KAN-719), 통합 검증
(KAN-721), 이준서가 AI 요약 API(KAN-722)와 admin 생성 배치(KAN-723), 내가 이 티켓(KAN-724)이다. 내 몫은
웹과 모바일 예측/프리뷰 탭에 카드 하나를 세우는 것이고, 의존은 KAN-719 하나인데 그게 아직 없으니 티켓에
박힌 계약과 fixture로 먼저 만들어 dev에 올려 두기로 했다. 다른 사람들 PR이 들어왔을 때 FE가 이미 dev에 있어야
KAN-721에서 바로 붙여 볼 수 있다.

계약은 티켓에 다 있었다. `GET /api/v1/matches/{matchId}/briefing`이 `{ status: READY | UNAVAILABLE, briefing }`를
주고, 브리핑은 경기 id 문자열, 생성 시각, 자료 기준 시각(`dataAsOf`), 만료 시각(`expiresAt`), 핵심 문장
1~3개와 각 문장의 근거 id, 주의사항, 출처 목록(기사 또는 경기)이다. 시각은 전부 UTC ISO, id는 전부 문자열이다.
절약안 v2라는 규칙이 붙어 있다. 생성은 서버가 경기당 KST 하루 한 번, 하루 최대 세 경기만 하고 화면은 저장된
결과를 읽기만 한다. 그래서 FE에 "다시 요약" 같은 버튼은 없고, 60초 재조회는 생성 trigger가 아니라 서버가
UNAVAILABLE로 돌린 걸 알아채는 용도다. 만료는 `min(dataAsOf + 24h, 생성 당시 킥오프)`로 서버가 정하고
FE는 그 값을 그대로 쓰되 킥오프 도달과 경기 상태를 한 번 더 본다.

시안은 없었다. 물어보니 토큰으로 판단해 만들라 했고, 위치는 "팀 비교 근처"라는 티켓 문구를 투표 아래,
팀 비교 위로 확정했다.

## 어디에 무엇을 두었나

승부예측 때 정한 네 층을 그대로 따랐다(ADR 0224).

- `@plick/domain/match-briefing`: 화면이 보는 타입과 순수 헬퍼. payload 검증(`parseMatchBriefing`), 숨김 판정
  (`isMatchBriefingVisible`), 감출 시각(`matchBriefingDeadline`), 자료 기준 문구(`matchBriefingAsOfLabel`),
  출처 링크(`matchBriefingSourceHref`), 근거 모으기(`matchBriefingEvidence`), 문구 상수와 표시 상한.
- `@plick/core/match-briefings`: fetcher 하나. `@plick/core/matchBriefingKeys`: 쿼리 키.
  `@plick/core/match-briefing-queries`: 훅 `useMatchBriefing`.
- `@plick/ui/MatchBriefingCard`: 카드. 두 앱이 같은 자리에 같은 모양을 그려 처음부터 공용이다(ADR 0011 게이트 C).
- 앱은 `PredictionTab`(모바일)과 `PredictionPanel`(웹)에 훅 한 줄과 카드 한 블록을 넣은 게 전부다.

훅이 core에 있는 건 승부예측 읽기 훅을 올린 판단(ADR 0232)과 같다. 쓰기가 없고 앱별 안전망(`meta.errorHandled`)에
묶이지 않아 올릴 수 있다. 단 모바일 `QueryProvider`는 데이터 없는 쿼리 실패를 에러 경계로 던지는 기본값이 있어
`throwOnError: false`를 훅에 못박았다. 쿼리는 뮤테이션의 `errorHandled` 안전망을 타지 않으니 이 한 줄이 그 역할이다.

## 검증을 fetcher가 아니라 도메인이 한다

BE 응답을 그대로 믿지 않기로 했다. 티켓의 테스트 목록이 "malformed, 없는 evidence ID, 문자열 ID, matchId 불일치"를
들고 있어서다. 다른 fetcher들은 BE 타입을 선언하고 필드를 옮겨 담는 정도인데, 이번엔 `briefing`을 `unknown`으로
받아 `parseMatchBriefing`이 하나하나 본다. 객체가 아니면, `matchId`가 화면 경기와 다르면(숫자든 문자열이든
문자열로 맞춰 비교), 시각 셋 중 하나라도 `Date`가 못 읽으면, 핵심 문장이 하나도 없으면 null이다. 출처는 종류에
맞는 id(기사면 `articleId`, 경기면 `matchId`)가 문자열이고 반대쪽이 null이어야 하며 어긋난 출처는 그것만 버린다.
문장의 근거 id는 출처 목록에 있는 것만 남기고 중복을 지운 뒤 2개로 자른다. 문장 3개, 80자, 주의사항 1개 60자도
여기서 자른다. 서버가 같은 한도로 만들지만 모바일에서 긴 글이 투표 진입을 밀어내지 않게 하는 마지막 가드다.

fetcher는 4xx를 null로 접는다. 없는 경기 404만이 아니라 401도 그렇다. dev BE에 아직 이 경로가 없어서
보안 matcher가 401 `AUTH_REQUIRED`를 주는데, 이걸 에러로 두면 쿼리가 에러 상태로 남을 뿐 화면에 달라질 게
없고 다시 보내도 같은 답이다. 5xx와 네트워크 실패는 던지고 훅이 `throwOnError: false`로 받는다. 어느 쪽이든
카드가 없는 것 말고는 화면이 달라지지 않는다.

## 만료와 킥오프는 화면이 보고 있는 동안에도 닫는다

서버가 만료를 판정해 UNAVAILABLE로 돌려주더라도 다음 60초 재조회까지는 옛 카드가 남는다. 티켓이 "만료/킥오프
시각에 화면도 바뀌도록 타이머 또는 기존 시간 갱신 경로"를 요구해서 훅 안에 작은 시계를 두었다. 서버 만료와
경기 헤더의 킥오프 중 이른 쪽을 기한으로 `setTimeout`을 걸고, 깨어나면 현재 시각을 상태로 올려 다시 그린다.
`isMatchBriefingVisible`이 `now < deadline`을 다시 계산해 false가 되면 카드가 그 자리에서 사라진다. 32비트
타이머 상한(약 24.8일)보다 먼 기한은 상한에서 한 번 깨어나 다시 재는데, 그때는 아직 기한 전이라 그대로 보인다.
토론 마감의 `useDebateClock`과 같은 구조다. 그걸 그대로 쓸까 했는데 이름이 토론이고 배열을 받는 모양이라
훅 안에 15줄로 다시 썼다.

경기 상태가 SCHEDULED가 아니면 요청 자체를 보내지 않는다(`enabled`). 라이브로 넘어간 경기의 상세는 20초
폴링이 `header.status`를 LIVE로 바꾸고, 그 순간 `enabled`가 꺼지며 판정도 false라 카드가 내려간다. 킥오프
시각에 타이머가 먼저 닫고 상세 폴링이 뒤따르는 식이다.

KST 자정은 조건이 아니다. 전날 12:00 기준 브리핑이 자정을 넘겨도 만료(다음날 12:00)나 킥오프 전이면 그대로
보인다. 당일 재생성이 실패해도 서버가 이전 유효 결과를 READY로 주면 원래 `dataAsOf`와 만료로 표시한다.
테스트에 자정 통과 케이스를 넣어 두었다.

## 카드

면은 `bg-elevate`에 `rounded-card`라 웹에서 각지고 테두리는 없다(홈 예측 카드와 같은 판단). 위부터 제목
"AI 경기 브리핑"과 오른쪽 "11월 4일 12:00 기준", 핵심 문장 목록(accent 점), 주의사항 한 줄(`text-4`), "근거 보기"
토글이다. 토글은 `button`에 `aria-expanded`와 `aria-controls`(React `useId`)를 달아 Tab과 Enter, Space로 열고
닫는다. 펼치면 문장들이 가리키는 출처가 순서대로 중복 없이 서고 각 줄이 "기사"나 "경기" 라벨과 제목으로
기사 상세(`/articles/{id}`)나 경기 상세(`/live/matches/{id}`)로 간다. id는 서버 문자열을 `encodeURIComponent`로
넣는다. 근거가 하나도 없으면(출처 목록에 없는 id만 있던 경우) 토글을 두지 않는다.

모델이 만든 문자열은 전부 JSX 텍스트 노드다. `dangerouslySetInnerHTML`은 쓰지 않는다. 문구에 "실시간"이나
"최신 선발 반영"은 없고 `dataAsOf`를 KST로 적은 기준 시각만 있다. 생성 시각(`generatedAt`)은 화면에 없다.
기준 시각과 혼동되기 때문이다.

링크 컴포넌트는 `@plick/ui`가 `next`를 모르므로 앱이 `next/link`를 넘긴다(`TrendingRow`와 같은 규약). 웹은
`size="lg"`로 패딩과 hover, focus-visible 상태가 붙는다.

## 검증 환경

BE에 브리핑이 없으니 두 겹으로 봤다. 단위 테스트는 도메인(fixture 통과, 문자열 id 비교, 없는 근거 id, 어긋난
출처, 상한, 만료 경계 1ms, 킥오프 우선, 자정 통과, 상태별 숨김, 문구, 링크 인코딩) 12개와 fetcher(READY에
`no-store`, UNAVAILABLE, 404와 401, 5xx 던짐, id 불일치) 5개다.

화면은 스크래치에 20줄짜리 node 프록시(8084)를 두었다. 모든 요청을 mock BE(8081)로 넘기되 `GET
/api/v1/matches/{id}/briefing`만 `state.json`을 읽어 응답한다. 파일을 바꾸면 재시작 없이 다음 요청부터 다른
상태다. `API_BASE_URL=http://localhost:8084`로 두 앱을 빌드하고 `next start`(3081, 3080)로 띄웠다. 다른
세션의 `next dev`가 이 폴더에 떠 있어 두 번째 dev는 Next 16 잠금에 막히기 때문이다(ADR 0199와 같은 우회).
mock의 예정 경기는 900003(아스톤 빌라 대 아스널, 오늘 23:30) 하나라 fixture의 만료를 그 킥오프에 맞췄다.

Playwright로 열한 가지 상태를 돌렸다. READY만 카드가 서고 UNAVAILABLE, 404, 401, 500, 깨진 JSON, 모양
오류, 경기 id 불일치, 깨진 시각, 이미 만료는 전부 카드 없이 투표하기 버튼과 팀 비교 표가 그대로였다. 토스트도
에러 지면도 페이지 에러도 없었다. 근거 id가 전부 없는 READY는 카드는 서되 토글이 없었다. 시계를 만료 10초
전으로 심고 11초 돌리면 카드가 사라졌고, 킥오프 2초 전에서도 같았다. 종료 경기(900001)로 옮기면 요청이
나가지 않았다. 키보드로 토글에 가서 Enter로 펼치고 Space로 접었고 링크 href 셋이 기대한 경로였다. 웹도 같은
결과다. 60초 재조회는 보이는 헤드리스 페이지에서 130초 동안 요청 수를 세어 확인했다.

브라우저 패널에서는 실제 `/be` 경로로 카드가 뜨는 것과 투표 등록(작성 시트, 픽, 의견, 등록)이 전처럼 되는 걸
봤다. mock은 저장하지 않아 취소 시트까지는 못 갔다(ADR 0225와 같은 한계).

dev에 올라가면 BE가 401을 주므로 카드는 없고 다른 화면은 그대로다. KAN-719가 들어오면 그때부터 보인다.

## 헤드리스 리뷰가 잡은 것

push 전 `pr-review.sh`가 CRITICAL 하나와 WARN 셋을 냈다. CRITICAL은 시계 훅이었다. effect 의존성에
`now`까지 넣어 두어서, 기한이 이미 지난 브리핑(서버가 만료된 READY를 계속 주거나, 킥오프는 지났는데 상세
폴링이 아직 LIVE로 바꾸기 전)이면 0ms 타이머가 `setNow`를 부르고 `now`가 바뀌어 effect가 다시 돌고 또 0ms
타이머가 걸리는 루프였다. 카드는 숨겨진 채 탭 전체가 몇 ms마다 다시 그려진다. Playwright 매트릭스의
"이미 만료" 케이스가 바로 그 상태였는데 화면만 보고 통과시켰다. 의존성을 `deadline` 하나로 줄이고, 기한이
지났으면 타이머 없이 현재 시각만 한 번 올리게 했다. 상한에서 일찍 깬 경우는 상태를 건드리지 않고
타이머만 다시 건다. 고친 뒤 같은 케이스에서 `setTimeout` 호출 수를 세어 루프가 사라진 걸 확인했다.

WARN 하나는 출처 검증이었다. 반대쪽 id가 "정확히 null"이어야 통과시켰는데 BE 직렬화가 null 필드를
생략하면 undefined라 기사 출처가 전부 탈락하고 근거 토글이 조용히 사라진다. `?? null`로 정규화하고 생략
케이스 테스트를 넣었다. 다른 하나는 fetcher 테스트가 `http://localhost:8080`을 통째로 단언해 `API_BASE_URL`이
있는 환경에서 깨질 수 있다는 것이라 경로 끝만 보게 바꿨다. 훅과 카드에 단위 테스트가 없다는 WARN은
맞다. 이 저장소에 React 테스트 러너가 없어 Playwright 확인으로 두고, 시계 로직은 위처럼 effect 하나에
가둬 읽기 쉽게 했다.

INFO는 세 개다. 4xx 전부를 null로 접어 429나 408도 숨긴다는 지적은 retry 0에 60초 재조회가 있어 그대로
둔다. `matchBriefingKeys.ts`의 camelCase는 `predictionKeys.ts`, `liveKeys.ts` 선례를 따른 것이고, 아이콘
`size={14}`는 같은 탭의 `ChevronRightIcon` 호출과 같은 관례다.

## 같은 push에 얹은 둘 (KAN-701 후속, 게스트 안내 문구)

push 직전에 두 가지가 더 들어왔다. 둘 다 작아서 브랜치를 따로 내지 않고 이 PR에 실었다.

이민욱이 KAN-701에 BE 변경을 알려 왔다. 랭킹 노출 기준이 정산 5경기에서 1경기로 내려갔고(plick-backend PR
206, dev 배포됨) 동점 정렬이 보정 적중률, 정산 수, 닉네임 코드포인트, user_id 순으로 바뀌었다. 응답 모양은
그대로다. FE에 "5경기" 전제가 네 군데 박혀 있었다. `PREDICTION_RANKING_MIN_SETTLED = 5`, 내 순위 칸의
`3/5` 진행 표시, "n경기 더 예측하면 랭킹에 올라요" 안내, 그리고 `formatPredictionRecord`가 퍼센트를 붙이기
시작하는 선을 이 상수에 묶어 둔 주석이다.

상수를 1로 바꾸면 진행 표시는 `0/1`밖에 없어 뺐다. 내 순위 칸은 자격 미달과 집계 중 둘 다 `-`고 안내가
"첫 경기 결과가 나오면 랭킹에 올라요"다(요청대로). BE가 기준을 다시 올려 `remaining`이 2 이상으로 오면 남은
수를 적는 분기는 남겼다. 퍼센트 표본 하한은 자격과 갈라 `PREDICTION_RATE_MIN_SETTLED = 5`로 따로 두었다.
1전 1적중이 100%인 건 자격과 무관하게 표본 문제라서다.

같은 이유로 랭킹 표의 적중률 칸도 손봤다. dev 실데이터를 보니 1위가 1전 1적중 100%, 2위부터 1전 0적중 0%가
줄줄이다. 순위는 보정 점수라 표본이 큰 8/12 67%가 1/1 100%보다 위에 서는데, 그 옆에 100%를 그대로 적으면
순위가 틀린 것처럼 읽힌다(BE 쪽도 이 어색함을 확인해 달라고 했다). 정산 5경기 전이면 적중률 칸을 `-`로
비우고 적중 칸(`1/1`)은 그대로 둔다(`predictionRankingRateCell`). 시즌 초에는 칸이 대부분 `-`인데, 틀린 숫자보다
빈 칸이 낫다고 봤다. 되돌리기 쉽게 헬퍼 하나로 모아 두었다. 목록이 길어지는 건 한 페이지 50행 무한
스크롤이라 그대로고, 10분 캐시는 `staleTime`이 이미 같은 값이다.

검증은 다른 세션이 띄워 둔 dev 서버(3031, 3030)에 Playwright로 들어가 랭킹 요청만 dev BE 실데이터에 가짜
`me`(자격 미달, 집계 중, 7위)와 표본 12경기 행 하나를 섞어 fulfill했다. 세 상태 모두 칸과 안내가 기대대로였고
표본 행만 `67%`가 섰다.

두 번째는 게스트가 예측을 등록한 직후 뜨는 연동 안내다. "예측이 등록됐어요"에 기록을 쌓으라는 한 줄이었는데,
랭킹에서 적중률 높은 사람들의 기록을 보면 예측이 쉬워진다는 쪽으로 로그인을 끌자는 요청이었다. 제목은
"고수들은 어떻게 예측할까요?", 본문은 계정을 연동하면 시즌 랭킹에서 적중률 높은 사람들의 기록을 보고 승부를
더 쉽게 가늠할 수 있다는 것과 방금 등록한 예측은 그대로 남는다는 사실이다. 두 앱 상수(`PREDICTION_SUBMITTED_*`)로
빼 시트와 팝업이 같은 글자를 쓴다. 게스트 분기는 mock으로 못 보는 줄 알았는데(ADR 0225) 시트를 여는 조건이
`sessionKind` 쿠키 하나라 Playwright로 그 쿠키만 심고 등록하니 떴다.

## 또 얹은 셋 (웹 랭킹 분리, 게스트 블러, 홈 카드 회전 순서)

push 뒤에 세 가지가 더 들어와 같은 브랜치에 실었다.

웹은 랭킹을 VS의 셋째 탭에서 꺼내 GNB 탭 `/rankings`로 세웠다. 모바일은 그대로 `/debates?tab=rank`다.
웹 `DebateTab` 타입에서 `rank`를 빼고 `DEBATE_TABS`도 둘만 남겼다. 홈 제목 줄, MY 기록 띠, 예측 탭의 랭킹
링크는 `RANKINGS_PATH`로 간다. 옛 주소 `/debates?tab=rank`는 모바일 링크와 북마크가 아직 쓰니
`useDebateTab`이 마운트 뒤 `router.replace`로 보낸다. 페이지는 서버가 셸만 그리는 정적 라우트다. 표는
사람마다 다른 `me`가 실려 브라우저에서 받는다. 사이트맵에 넣고 모바일 탭을 alternate로 달았다.
`PredictionRanking` 컴포넌트는 `debates/_components`에서 `rankings/_components`로 옮겼다.

소셜 계정이 아니면(비로그인, 게스트) 두 앱 모두 랭킹 표를 블러로 가리고 "고수들의 적중 기록은 로그인하면
볼 수 있어요"와 로그인(게스트는 연동하기) 버튼을 덮는다. 의견 잠금 지면(`PredictionLockedList`)과 같은
`blur-[0.375rem]`, `aria-hidden`, 포인터 이벤트 꺼짐이다. 내 순위 줄과 다음 페이지는 그리지 않는다. 판정은
`useAuth`의 `isLoggedIn`과 `isGuest`인데 세션 판정이 끝나기 전(`isSessionPending`)에는 가리지 않아 소셜
계정이 첫 그림에서 블러를 보지 않는다. 표 데이터는 공개 값이라 그대로 받아 가린다. 검증은 mock BE가
`/users/me`를 누구에게나 `isGuest: false`로 줘서 Playwright가 그 응답을 `isGuest: true`로 바꾸고, 비로그인은
게스트 발급(`/api/session/guest`)을 503으로 막아 만들었다. 게스트는 연동하기, 비로그인은 로그인하기,
소셜은 표와 내 줄이 그대로였다.

홈 승부예측 카드의 대표 의견 줄은 카드마다 순서와 박자가 달라졌다. BE가 주는 `topOpinions`가 최근 순이라
나란한 카드 셋이 같은 순서로 같은 순간에 넘어가 한 몸처럼 보였다. `shuffledTeaserOrder`가 첫 줄을 고정하고
나머지를 섞으며, 첫 전환까지의 시간을 간격의 0.5배에서 1.5배 사이로 뽑는다(`teaserFirstDelayMs`). 첫 줄을
고정하는 이유는 하이드레이션이다. 서버 HTML은 원래 순서의 첫 의견을 그리므로 브라우저 첫 그림도 같아야
한다. 섞는 건 마운트 뒤 effect에서 한다. 두 앱 홈에 같은 의견 넷을 심고 12초 동안 0.5초마다 닉네임을 읽어
카드 둘이 서로 다른 순서로 돌고 전환 시점이 어긋나는 걸 확인했다.

## 배포 뒤 E2E가 깨졌다 (후속 브랜치)

develop에 머지되고 dev 배포 뒤 E2E 워크플로우가 웹 VS 스펙에서 떨어졌다. "세 탭을 표시하고"가 랭킹 탭을
기다렸는데 웹 랭킹은 `/rankings`로 나갔으니 당연하다. E2E는 PR 게이트가 아니라 배포 뒤에 도는 QA라 머지를
막지 않았고(ADR 0169), 내가 스펙을 같이 안 고친 게 원인이다. 웹 VS 스펙은 두 탭과 랭킹 탭 없음으로, 홈 스펙의
주 메뉴 목록에 랭킹을 더하고, `rankings.spec.ts`를 새로 두어 주 메뉴에서 들어가면 비로그인 로그인 안내가
덮이는 것과 옛 `/debates?tab=rank`가 넘어오는 것을 본다. 모바일 스펙은 랭킹이 셋째 탭 그대로라 손대지
않았다. dev를 상대로 웹 7건 통과.

같은 날 dev 실연동도 확인했다. BE, admin, AI가 모두 들어와 챔피언스리그 3경기가 READY였고 두 앱 모두 카드와
근거 링크(전부 MATCH, 경기 상세 200)가 떴다. 종료 경기는 UNAVAILABLE로 숨겨졌다. 기사 근거는 기사가 연결된
경기가 없어 실데이터로는 못 봤다.

## 남긴 것

- 생성 flag나 조회 flag는 FE에 없다. 서버가 UNAVAILABLE이나 4xx를 주면 그게 OFF다.
- 팬 의견 요약(KAN-726)은 이 카드 아래 자리가 비어 있다. 같은 훅과 카드 구조를 따르면 된다.
- 브라우저 패널의 콘솔에 보인 404와 WebSocket 실패는 mock BE에 없는 아바타와 채팅 경로라 이번 변경과 무관하다.
