# 0249. 서비스 버전을 2.10.0으로 통일하고 표시 위치를 정비했다 (KAN-741)

해축이모에는 버전 번호가 사실상 없었다. 모바일 MY 화면 맨 아래에 `해축이모 v0.1.0`이라는 글자가 있었지만 프로젝트를 만들 때 넣어 둔 값이 그대로 남아 있었을 뿐이고, 그동안 프로덕션 배포는 77번 나갔다. git 태그도 0개였다. 어느 버전이 떠 있는지 물어볼 곳이 없는 상태였다.

## 배포 이력에서 번호를 만들었다

번호를 정하려면 먼저 몇 번 배포했는지 알아야 했다. 배포는 GitHub Actions의 `Deploy` 워크플로가 main 푸시를 받아 나가므로, 그 워크플로의 main 실행 기록 82건을 전부 받아 세었다. 성공 80건, 실패 1건, 취소 1건이었다. 성공 80건 중 3건은 같은 커밋을 수동으로 다시 돌린 것이라 코드가 다른 업데이트는 77개다. 첫 시도는 2026-07-29 17:45였고 실패했으며, 첫 성공은 2026-07-30 09:26이었다. 마지막은 2026-11-06이다.

처음에는 지금의 prod 스택이 시작된 8월 7일을 1.0.0으로 잡았다. 그러다 진짜 첫 배포부터 세기로 바꿔서 7월 30일이 1.0.0이 됐고, 8월 7일은 배포 설정만 바뀐 배포라 Patch인 1.5.2로 내려갔다. 그래도 끝 번호는 2.10.0으로 같았다. Major가 10월 3일 리브랜딩 한 번뿐이라 앞부분이 늘어나도 2.x 구간은 영향을 받지 않기 때문이다.

분류는 커밋 제목의 접두어를 기계적으로 따르지 않았다. `feat`라고 붙어 있어도 네이버 소유확인 태그처럼 사용자에게 달라지는 게 없으면 Patch로 봤다. 기준은 세 가지다. Major는 제품이 통째로 바뀐 경우, Minor는 사용자가 새로 쓸 수 있는 기능이 생긴 경우, Patch는 버그 수정과 성능 개선, 소소한 조정, 인프라 작업이다. 승부예측은 규모가 커도 기존 기능을 깨지 않으므로 Minor다. 소급 분류라 Minor와 Patch의 경계에는 판단이 들어가 있다. 결과는 시작 1번, Major 1번, Minor 33번, Patch 42번이고 전체 목록을 루트 `CHANGELOG.md`로 남겼다.

여기서 작은 일이 하나 있었다. 8월 7일 이전 배포가 어떤 커밋을 포함하는지 보려고 `git merge-base --is-ancestor`를 썼더니 가드 훅이 막았다. 이 명령은 조상 관계만 읽는 읽기 전용인데, 훅의 정규식은 develop 브랜치에서 `git merge`로 시작하는 문자열을 병합 시도로 본다. 오탐이지만 훅을 고칠 일은 아니어서 `git log --first-parent`로 같은 정보를 얻었다.

## 왜 단일 출처를 코드 상수로 뒀나

버전을 화면 한 곳에만 쓴다면 문자열 하나를 고치면 끝이다. 그런데 이번에는 모바일 화면, 웹 푸터, 헬스체크, 프로메테우스 지표까지 읽는 곳이 여러 군데로 늘어난다. 각자 값을 들고 있으면 바로 어긋나므로 한 곳에 모았다.

처음 떠오른 방법은 `package.json`의 `version`을 import하는 것이었다. npm 세계의 정석이지만 여기서는 맞지 않았다. 웹 푸터는 브라우저로도 가는 코드라 `package.json`을 import하면 파일 전체가 번들에 실릴 수 있고, 두 앱의 파일이 따로 있어서 어느 쪽이 기준인지도 애매하다. 그래서 두 앱이 이미 브랜드 문구를 가져다 쓰는 `@plick/domain/brand`에 `APP_VERSION`을 두고, 화면 라벨은 `appVersionLabel()`로 만들었다. 모바일의 `_constants/me.ts`는 이 라벨 하나만 들고 있던 파일이라 지웠다.

상수로 두면 `package.json`이나 CHANGELOG와 어긋날 수 있다는 약점이 남는다. 이걸 문서 규칙으로만 막지 않고 `tests/unit/app-version.test.mjs`를 붙였다. 루트와 두 앱의 `package.json`, CHANGELOG 맨 위 항목이 `APP_VERSION`과 다르면 CI의 `test:unit`이 실패한다. 번호를 올리는 절차는 CLAUDE.md의 Git 절에 두 줄로 적었다.

## 어디에 넣었고 어디에 안 넣었나

넣은 곳은 다음과 같다.

- 모바일 MY 화면 푸터: 원래 있던 자리다. `v0.1.0`이 `v2.10.0`으로 바뀌었다.
- 웹 `SiteFooter`: 카피라이트 줄 옆이다. 웹은 시안에 없어 MY의 버전 라벨을 지웠던 이력이 있어서, 모든 페이지 하단에 있는 푸터에 작은 글씨로 넣었다. 좁은 폭에서는 `flex-wrap`으로 줄이 바뀐다.
- `/api/health` 응답: `{ "status": "ok", "version": "2.10.0" }`이 됐다. ALB 대상 그룹과 CodeDeploy의 `validate_service.sh`, E2E 워크플로는 모두 HTTP 상태 코드만 본다는 걸 확인하고 필드를 더했다. Blue/Green 교체 중에 `curl`로 어느 릴리스가 응답하는지 바로 볼 수 있다.
- 프로메테우스 `plick_build_info{version="2.10.0"}`: 값은 항상 1이고 정보는 라벨에 담는 게 프로메테우스의 관례다. `/metrics`는 별도 포트라 바깥에 노출되지 않는다. 라벨 값은 버전 수만큼만 늘어나므로 카디널리티 걱정은 없다. 카디널리티는 라벨 값의 가짓수이고, 이게 무한히 늘면 프로메테우스 메모리가 그만큼 는다.
- 루트와 두 앱의 `package.json`, `CHANGELOG.md`.

일부러 넣지 않은 곳도 있다.

- `packages/*`의 `0.0.0`: 배포하지 않는 내부 패키지라 Turborepo 기본값 그대로가 맞다.
- 웹 앱 manifest: 표준에 버전 필드가 없다.
- JSON-LD `softwareVersion`: `SoftwareApplication` 타입의 속성인데 이 사이트는 `WebSite`와 `Organization`, `NewsArticle`을 쓴다. 버전을 넣으려고 타입을 새로 선언하는 건 검색 노출에 얻는 게 없다.
- 앱 셸 저장소의 `VERSION = '1.2.0'`: 스토어에 올라가는 네이티브 앱 버전이다. 웹 배포와 주기가 다르고, 바꾸면 앱을 새로 빌드해야 한다. User-Agent의 `PlickApp/1.2.0`도 이 값이다.
- git 태그 `v2.10.0`: 태그는 그 버전이 담긴 커밋에 달아야 한다. 지금 main 최신 커밋의 `package.json`은 아직 `0.1.0`이므로, 이 변경이 main에 병합된 뒤 그 커밋에 건다. main 병합은 사용자가 하는 일이라 태그도 그 뒤 순서다.

## 검증하다 만난 에러 화면

`pnpm build`로 만든 산출물을 `next start`로 띄워 확인했다. 헬스체크는 두 앱 모두 `{"status":"ok","version":"2.10.0"}`을 돌려줬고, 지표는 9464번과 9465번 포트에서 `plick_build_info{version="2.10.0",app="mobile"}`과 `app="web"`으로 나왔다. 웹 `/faq` 푸터에는 카피라이트 옆에 `해축이모 v2.10.0`이 보였고 가로 넘침도 없었다.

모바일 MY는 잠깐 놀랐다. 라벨이 있는 걸 DOM에서 읽은 직후 찍은 스크린샷이 "This page couldn't load"였다. 내 변경은 문자열 출처를 바꾼 것뿐이라 다른 원인이 있을 거라 보고 서버 로그를 봤더니 `Failed to proxy http://localhost:8082/api/v1/users/me`가 줄지어 있었다.

원인은 Next의 rewrites가 빌드 시점에 굳는다는 데 있다. `next.config.js`의 `/be/:path*` 규칙은 `API_BASE_URL`을 읽어 목적지를 만드는데, 이 값은 `next build`를 돌릴 때 `routes-manifest`에 박힌다. 그래서 띄울 때 `API_BASE_URL=https://plick.co.kr/be`를 줘도 서버 컴포넌트의 fetch만 그 값을 쓰고, 브라우저가 부르는 `/be/...`는 빌드 때 잡힌 `localhost:8082`로 간다. 그 포트에 백엔드가 없으니 프록시가 500을 냈고, `/users/me` 조회의 `ApiError`가 에러 경계까지 올라가 화면 전체가 에러로 바뀐 것이다. 서버가 만든 `/me` HTML을 `curl`로 받아 보면 200이고 `해축이모 v2.10.0`이 들어 있었다. 즉 라벨은 정상이고, 에러 화면은 로컬 백엔드가 없어서 생긴 현상이었다.

CI 명령 중 `format:check`는 exit 1이었다. 경고가 난 16개 파일을 전부 확인했더니 커밋 대상이 아닌 `output/pdf/` 아래 작업 산출물이었다. CI는 깨끗한 체크아웃에서 돌기 때문에 이 파일들을 보지 않는다. 내가 고친 파일만 따로 돌린 Prettier는 통과했다. `test:hooks` 40개, `test:unit` 353개, `lint`, `check-types`, `build`는 전부 통과했다.

## 남은 것

이 변경이 나가는 배포는 원래 규칙대로면 Patch일 텐데, 번호를 맞추는 작업 자체라 2.10.0을 그대로 쓴다. 다음 배포부터는 사람이 `APP_VERSION`을 올려야 한다. 자동으로 올리지 않은 건 Minor인지 Patch인지가 판단의 문제라서다. 올리지 않아도 CI는 통과하므로 표시 번호가 다시 낡을 위험은 남아 있다. 테스트가 잡는 건 여러 위치 사이의 불일치뿐이다.

관련 문서는 배포 구조가 [deploy-v2](../deploy-v2.md), 메트릭 서버가 [ADR 0130](0130-prometheus-grafana-monitoring.md), 리브랜딩이 [ADR 0171](0171-haechukimo-redesign.md)이다.

## 같은 PR에 얹은 KAN-742: 제목, 기사 배치, 좋아요와 NEW 표시

버전 작업을 push한 뒤 같은 브랜치에 KAN-742를 얹었다. 티켓은 사이트 제목 변경, AI 브리핑 아이콘, 기사 상세 재배치 세 가지였고, 로컬호스트를 보면서 요청이 계속 늘었다. 팀 풀네임, 섹션 제목 이모지, 채팅방 이름, 급상승 1등 강조, NEW 기준 12시간, 댓글 수와 좋아요 색까지 한 PR에 들어갔다.

### 탭 이름과 제목은 한 태그다

요청은 "제목은 `해외축구 이슈 모음 : 국내에서 가장 빠른 AI기반 실시간 뉴스 플랫폼`, 브라우저 탭에는 `국내에서…`만"이었다. 그런데 HTML에서 탭 이름과 검색 결과의 파란 제목은 같은 `<title>` 하나다. 둘을 가를 수 있는 건 공유 카드용 `og:title`뿐이라, `<title>`은 짧은 문구로, 홈의 `og:title`과 `twitter:title`은 긴 문구로 나눴다. 기사나 FAQ 같은 하위 페이지의 `"%s | 해축이모"` 템플릿은 건드리지 않았다. 전부 같은 문구로 바꾸면 기사 제목이 검색 결과에서 사라지기 때문이다.

여기서 내가 회귀를 하나 만들 뻔했다. 홈 `metadata`에 `openGraph`를 넣었더니 `og:image`가 사라졌다. Next의 메타데이터 병합은 얕아서, 하위 세그먼트가 `openGraph`를 선언하면 부모 것을 필드별로 합치지 않고 통째로 교체한다. 루트의 `opengraph-image.png` 파일에서 온 이미지도 그때 같이 날아간다. 그래서 siteName, type, locale, images를 홈에 다시 적었다. 그렇다고 루트에 제목을 두면 자기 `openGraph`가 없는 모든 페이지가 그 제목을 물려받으므로 홈에만 둔다. 실서비스 홈의 태그와 로컬 응답을 `curl`로 비교해서 찾았다.

### 기사 상세의 임베드를 되살렸다

KAN-301에서 본문과 겹치고 무겁다는 이유로 뺐던 트윗 임베드가 이번엔 본문 아래 구분선 밑으로 돌아왔다. 순서는 제목, by 기자와 오른쪽 끝 시각·조회, 구분선, 실시간 AI 기사, 본문, 투표, 태그, 좋아요와 공유, 진한 구분선, 원문 기사 바로가기, 임베드다. 임베드는 첫 화면 아래에서 브라우저가 받으므로 `next/dynamic`으로 react-tweet을 초기 번들에서 뺐다. `ssr: false`는 주지 않았다. 서버 컴포넌트에서는 금지이기도 하고, 씨앗이 없으면 서버에서 어차피 아무것도 그리지 않는다.

"실시간 AI 기사"는 애니메이션을 두 번 거쳐 고정 그라데이션으로 끝났다. 먼저 보라색 띠가 한 번 훑는 효과를 넣었는데 글자에 쓰는 `background-clip: text`가 SVG 아이콘에 듣지 않아, `mix-blend-mode: lighten` 띠를 위에 얹었다. 흰 바탕은 그대로이고 어두운 글자와 아이콘에만 색이 든다. 반복으로 바꿨다가 결국 움직임을 빼고 보라에서 핑크로 넘어가는 고정 색이 됐다. 지금은 글자는 `background-clip: text`, 아이콘은 SVG `linearGradient`다. 그라데이션 id를 고정 문자열로 두면 위험하다. 이 화면에는 크기가 0인 숨은 사본이 함께 있어서, 같은 id의 정의가 `display:none` 쪽에 먼저 있으면 참조가 깨지고 아이콘이 칠해지지 않는다. 그래서 `useId`를 썼다.

위아래 공백은 CSS 값이 아니라 눈에 보이는 글자 기준으로 맞췄다. 본문은 줄 간격이 1.75라 첫 줄 글자 위에 약 6px이 숨어 있어서, `pt`와 `pb`를 같게 두면 아래가 훨씬 넓어 보인다. 캔버스 `measureText`로 글자 상하단을 계산해 모바일은 위 16.5, 아래 16.3, 웹은 위 18.7, 아래 18.2로 맞췄다. 처음 어림으로 넣은 모바일 값은 4.6px 모자라서 측정 후 다시 고쳤다.

### 풀네임이 만든 부작용

`TEAMS[].name`을 맨체스터 유나이티드, 맨체스터 시티로 바꾸자 웹 승부예측 카드에서 두 팀이 똑같이 `맨체…`로 잘렸다. 두 줄 허용으로는 부족했다. 3열 카드의 이름 칸이 58px 남짓이라 `유나이티드` 다섯 글자가 안 들어가 `유나이티`에서 잘렸다. 웹 카드만 엠블럼을 이름 위로 올려 칸을 넓혔다. 모바일은 칸이 넓어 가로 배치를 유지했다. 기사 제목에 나오는 `맨시티`, `맨유`는 백엔드가 준 문장이라 프론트에서 바꾸지 않는다.

### 좋아요, 댓글 수, NEW

좋아요 하트와 수는 `--plk-like`로 모았다. 기사와 릴스는 누르기 전 빈 하트에 얇은 수, 누르면 찬 하트에 볼드 수다. 기사 제목 옆 `[N]`은 `--plk-comment-count`(#ff3b30)다. 둘 다 흰 배경 대비가 4.5:1에 못 미친다. KAN-627에서 일부러 어둡게 맞춘 빨강을 다시 밝힌 셈이라 Lighthouse 접근성 점수가 내려갈 수 있다는 걸 알고 택한 결정이다.

NEW 배지는 N 한 글자에 번쩍임을 넣었다가, 대문자 `NEW`에 라운드 사각형, 움직임 없음으로 정리됐다. 웹은 `globals.css`가 `rounded-badge`를 0으로 덮어서 `rounded-sm`을 썼다. 기준은 2시간으로 기억하고 있었는데 실제 코드는 30분이었고 12시간으로 바꿨다. 모바일은 부모가 baseline 정렬이라 `self-center`를 줬고, Noto Sans 대문자가 줄 상자 가운데보다 아래에 그려져 아래 여백을 위보다 넉넉히 뒀다.

### 로컬에서 확인하며 막힌 곳

모바일 `next dev`에서 기사 상세가 전부 전역 404로 떨어졌다. 웹은 멀쩡했고 같은 코드의 프로덕션 빌드도 정상이라 코드 문제는 아니었다. dev 서버를 고치는 대신 `API_BASE_URL`을 dev BE로 주고 빌드해 `next start`로 확인했다. rewrites가 빌드 시점에 굳기 때문에 시작할 때가 아니라 빌드할 때 줘야 한다.

NEW 배지는 dev 데이터가 전부 오래돼 볼 수가 없어서, 저장소 밖 스크립트로 8084번 포트에 프록시를 띄웠다. dev BE 응답을 그대로 넘기되 기사 목록 첫 세 건의 `publishedAt`만 방금으로 바꾼다. 코드에 목데이터가 남지 않는다.

좋아요를 누른 뒤의 상태는 끝내 눈으로 못 봤다. 로컬 세션이 dev BE에서 401, 403을 받아 토글이 되지 않는다. dev 배포 뒤 로그인해서 봐야 한다.

버전은 사용자 지시대로 2.10.0을 유지했다. 이 PR에는 새 기능이 들어가므로 규칙대로라면 2.11.0이고, 올릴지는 병합 전에 정한다.
