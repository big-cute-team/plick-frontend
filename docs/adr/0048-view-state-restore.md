# 0048. 화면 상태 복원과 당겨서 새로고침 (KAN-314)

## 무엇이 문제였나

홈에서 토트넘 탭을 누르고 목록을 한참 내려서 기사 하나를 읽고 뒤로 나오면, 토트넘 목록이
아니라 전체 탭 맨 위가 나왔다. 릴스도 마찬가지였다. 다섯 번째 릴을 보다가 홈에 다녀오면
첫 릴부터 다시 시작이었다. 티켓(KAN-314)은 이걸 "상태 저장이 안 되는 문제"라고 불렀는데,
정확히는 상태를 저장하는 주체가 아무도 없는 문제였다.

원인을 파 보니 하나가 아니라 셋이 겹쳐 있었다.

첫째, 클라이언트 상태가 언마운트와 함께 사라진다. 팀 필터는 `NewsFeed` 안의
`useState`였다. Next에서 라우트를 이동하면 떠나는 페이지의 React 트리는 통째로
언마운트되고, `useState`에 있던 값은 그 트리와 함께 죽는다. 돌아올 때는 새 컴포넌트가
초기값 `"ALL"`로 다시 마운트된다. Next의 Router Cache가 있지 않냐고 생각할 수 있는데,
그건 서버 컴포넌트가 렌더한 RSC 페이로드(직렬화된 렌더 결과)를 캐시하는 것이지 클라이언트
컴포넌트의 상태를 보존하는 게 아니다. `staleTimes` 같은 설정을 아무리 만져도 이건 안
고쳐진다.

둘째, 스크롤 복원이 애초에 안 걸린다. 브라우저의 히스토리 스크롤 복원도, Next의 스크롤
처리도 전부 window(문서 전체) 스크롤러 기준이다. 이 앱은 `AppShell`이
`h-[100dvh] overflow-hidden`으로 화면을 고정하고 실제 스크롤은 그 안의
`ScrollArea`(`<main>`)가 한다. 이런 중첩 스크롤러의 `scrollTop`은 브라우저도 Next도
기억해 주지 않는다.

셋째, 뒤로가기가 사실 뒤로가기가 아니었다. 기사 상단의 `BackButton`은 `history.back()`이
아니라 `<Link href="/">`다. 딥링크로 바로 들어온 사람한테도 동선을 보장하려는 의도적
설계인데(0036), 대신 히스토리 복원이라는 공짜 점심도 같이 포기한 거였다.

그나마 데이터는 살아 있었다. 목록 페이지들은 TanStack Query 캐시에 남으니, 문제는 그
데이터를 "어디서 어떻게 보고 있었는지"만 잃어버리는 거였다.

## 뷰 상태를 트리 밖으로

해법의 뼈대는 단순하다. 언마운트에 죽는 게 문제니, 죽지 않는 곳에 두면 된다. zustand
스토어(`_stores/view-state.ts`)를 만들어 홈 필터, 화면별 스크롤 위치, 릴스 인덱스를
담았다. zustand는 `package.json`에 들어온 지 한참인데 이 작업이 첫 사용이다. CLAUDE.md에
예약만 돼 있던 `_stores/` 폴더도 이걸로 개시했다.

persist 미들웨어는 일부러 안 붙였다. 새로고침해서 앱을 다시 여는 건 처음부터 보겠다는
뜻인데, 그때 스크롤이 지난 세션의 500px 지점에 가 있으면 오히려 기괴하다. 모듈 스코프
수명이면 딱 맞는다.

스토어를 구독하는 방식에서 하나 조심한 게 있다. 스크롤 위치는 스크롤할 때마다 바뀌는
값이라 컴포넌트가 셀렉터로 구독하면 프레임마다 리렌더가 돈다. 그래서 스크롤 값은 구독
없이 필요한 순간 `getState()`로만 읽고, 반대로 "맨 위로 가라"는 신호(`topTicks`)는
구독해야 반응할 수 있으니 구독한다. 같은 스토어 안에서도 값의 성격에 따라 읽는 방식을
갈랐다.

## 스크롤 복원 — useLayoutEffect와 두 번의 시도

`ScrollArea`는 서버 컴포넌트였는데 스크롤러 DOM을 잡아야 해서 클라이언트 컴포넌트로
바꿨다. 여기서 오해하기 쉬운 게, 이렇게 바꿔도 `children`으로 들어오는 내용까지
클라이언트로 끌려 내려오는 건 아니다. 서버 컴포넌트가 만든 children은 이미 렌더된 결과로
경계를 통과할 뿐이다. `restoreKey`를 안 주면 아무것도 안 하게 만들어서 `/me`나 온보딩
같은 화면은 손대지 않고 그대로 뒀다.

복원 자체는 `useScrollRestore` 훅이 한다. 마운트 때 저장된 위치로 `scrollTop`을 되돌리는
단순한 일인데, 두 가지 함정이 있었다.

하나는 타이밍이다. `useEffect`에서 하면 브라우저가 맨 위 상태를 한 번 페인트한 다음에
점프해서 화면이 번쩍한다. `useLayoutEffect`는 DOM 변경 후 페인트 전에 동기로 돌기 때문에
사용자 눈에는 처음부터 그 자리였던 것처럼 보인다.

다른 하나는 콘텐츠가 늦게 자라는 경우다. 홈 상단 캐러셀의 트윗 임베드는 마운트 후에야
높이를 잡는다. 복원 시점에 문서가 아직 짧으면 브라우저가 `scrollTop`을 지금 가능한
최대치로 깎아 버린다. 그래서 복원을 한 번 하고, 다음 프레임에 한 번 더 밀어 넣는다.
반대 방향(목록이 짧아진 경우)은 브라우저 클램프가 알아서 끝까지만 내려 주니 그냥 맡겼다.

저장은 scroll 이벤트마다 하지 않고 rAF로 프레임당 한 번으로 눌렀고, 언마운트 클린업에서
마지막 위치를 한 번 더 확정한다.

## 릴스 — startIndex가 안 되는 이유

릴스는 스크롤러가 아니라 Embla 캐러셀이라 접근이 다르다. 처음엔 Embla 옵션의
`startIndex`로 풀 생각이었다. `REELS_CAROUSEL_OPTIONS` 주석에 "딥링크용 startIndex만
호출부에서 덧붙인다"고 예고까지 돼 있던 자리다. 그런데 막상 해 보니 안 됐다. 릴스
데이터는 클라이언트 캐시에서 오는데, Embla가 초기화되는 첫 렌더 시점에는 슬라이드가 아직
0장이다. 0장짜리 캐러셀에 startIndex 3을 줘 봐야 갈 곳이 없다.

그래서 슬라이드가 실제로 붙은 뒤 한 번만 `scrollTo(index, true)`로 점프하는 이펙트를
뒀다. 두 번째 인자 true는 애니메이션 없이 그 자리에서 시작한다는 뜻이라, 사용자에게는
복원이 아니라 원래 거기 있던 것처럼 보인다. 캐시가 정리돼 릴이 첫 페이지로 줄었을 때를
대비해 인덱스는 슬라이드 수로 클램프한다.

저장 쪽에도 함정이 하나 있었다. 현재 인덱스를 스토어에 쓰는 sync가 마운트 직후 0을 한 번
쓴다. 복원할 값을 이펙트에서 읽으면 이미 0으로 덮인 뒤라, 첫 렌더에 `useRef`로 미리 떠
둬야 했다.

## 캐시 1분 → 30분

상태를 되돌려도 그 상태가 가리키는 데이터가 없으면 소용이 없다. 피드 캐시
정책(`FEED_FRESH_MS`)은 `staleTime`과 `gcTime`을 같은 값으로 묶는 설계인데(0030), 원래
1분이었다. 기사 하나를 1분 넘게 읽고 나오면 캐시 엔트리가 정리돼서, 20페이지짜리 목록이
첫 페이지로 줄고 복원할 스크롤 위치도 의미를 잃는다.

처음엔 gcTime만 늘릴까 했는데, 그 둘을 묶어 둔 이유(무한 쿼리 재검증이 커서 체인을
순차로 전부 다시 받는 문제)를 읽고 접었다. 벌어진 구간에서 30페이지 요청 폭탄이
되살아난다. 대신 둘을 같이 30분으로 올렸다. 한 세션에서 화면을 오가는 시간을 넉넉히 덮는
값이다.

이러면 새로고침 시점이 문제가 된다. 30분 동안은 화면에 다시 들어와도 재검증이 안 걸리니,
갱신을 사용자 손에 쥐여 줬다. 그게 아래 두 기능이다.

## 당겨서 새로고침

유튜브처럼 목록 맨 위에서 아래로 당기면 고무줄처럼 딸려 내려오다가 놓으면 새로고침되는
그 제스처다. 브라우저 네이티브 pull-to-refresh는 페이지 전체 리로드라 쓸 수 없고(SPA
상태가 다 날아간다), 직접 만들었다.

핵심은 터치 이벤트를 React JSX가 아니라 엘리먼트에 직접 다는 거였다. React 19는
`onTouchMove`류를 루트에 passive 리스너로 등록한다. passive 리스너에서는
`preventDefault()`가 무시되므로, 손가락을 따라 콘텐츠를 내리는 동안 브라우저 기본
스크롤을 막을 방법이 없다. `addEventListener(..., { passive: false })`로 직접 달아야
한다.

제스처 판정은 세 겹이다. 시작할 때 `scrollTop`이 0이어야 하고(목록 중간에서 아래로 미는
건 평범한 스크롤이다), 첫 8px 동안은 판정을 보류했다가 세로 성분이 가로보다 클 때만
당기기로 확정한다. 마지막 조건이 없으면 홈 맨 위의 핫이슈 가로 캐러셀을 넘길 때 손가락이
1px만 흘러내려도 새로고침이 걸린다. 판정에 쓴 8px은 거리 계산에서 빼는데, 안 빼면 당기기
시작하는 순간 콘텐츠가 8px 툭 튄다.

당기는 거리는 지수 감쇠(`120 * (1 - e^(-x/120))`)로 눌렀다. 처음엔 손가락을 거의
그대로 따라오다가 당길수록 뻑뻑해지고 120px에 수렴한다. 놓는 문턱은 감쇠 후 64px,
갱신 중에는 56px에 고정해 스피너가 늘 같은 자리에서 돈다. 응답이 50ms 만에 오면
스피너가 번쩍하고 사라져 갱신이 된 건지 알 수 없어서, 최소 400ms은 보여 준다.

갱신 동작은 `resetQueries`다. `invalidateQueries`로 하면 무한 쿼리가 쌓인 페이지를 커서
체인으로 전부 다시 받는다. 20페이지를 넘긴 채 당기면 요청 20개가 줄지어 나가고 그게 다
끝나야 스피너가 멈춘다. 어차피 새로고침은 맨 위에서 새로 보는 동작이니 첫 페이지 하나만
받는 리셋이 의미도 비용도 맞다. 서버 컴포넌트가 그리는 핫이슈 캐러셀은
`router.refresh()`로 같이 갱신한다. 이건 리로드가 아니라 서버에서 RSC 페이로드를 다시
받아 화면을 갈아 끼우는 소프트 갱신이라, 방금 복원한 클라 상태를 건드리지 않는다.

릴스에는 안 붙였다. 세로 드래그는 이미 Embla가 릴 넘김에 쓰고 있어서, 같은 제스처를 두
동작에 줄 수 없다. 릴스의 새로고침은 아래 탭 재탭이 맡는다.

한 가지 알고 만든 구멍: `onRefresh`를 함수로 넘겨야 하는데 서버 컴포넌트는 클라이언트
컴포넌트에 함수를 못 넘긴다(직렬화 불가). 그래서 홈 페이지는 `ScrollArea`를 직접 쓰지
않고, 갱신 훅을 아는 얇은 클라 껍데기 `HomeScrollArea`를 하나 거친다.

## 하단바 상시화와 탭 재탭

기사 세부에 하단바가 없어서, 기사를 읽다가 릴스로 가려면 홈까지 나갔다 눌러야 했다.
`TabBar`를 기사 세부(와 그 loading.tsx — 안 넣으면 로딩이 끝나는 순간 본문이 탭바
높이만큼 튄다)에 추가했다. 기사 경로에서는 `TABS`의 `match`가 전부 false라 어느 탭도
활성으로 칠해지지 않는데, 이게 오히려 정직한 표시다.

탭 동작은 티켓 요구대로 둘로 갈랐다. 다른 탭을 누르면 평범한 이동이고 그쪽 화면은 두고
온 그대로다. 지금 있는 탭을 한 번 더 누르면 새로고침이다. 같은 경로로 가는 `Link`는 원래
아무 일도 안 하므로, 활성 탭 클릭만 `preventDefault`로 가로채 스토어의 `topTicks`
카운터를 올리고 피드를 리셋한다. 값에 의미가 없는 카운터를 신호로 쓴 건, 탭바가
스크롤러(홈)나 캐러셀(릴스)을 직접 잡을 방법이 없어서다. 각 화면이 자기 방식대로(홈은
`scrollTo(0)`, 릴스는 `scrollTo(0, true)`) 반응한다.

여기서 하나 막혔었다. 처음엔 맨 위로 올릴 때 `behavior: "smooth"`를 줬는데,
시뮬레이터에서 테스트하니 200px쯤 남기고 멈췄다. 재탭은 스크롤을 올리는 동시에 목록을 첫
페이지로 리셋하는데, 부드러운 스크롤이 달리는 도중에 콘텐츠 높이가 줄면 WebKit이 진행
중인 프로그래매틱 스크롤을 중간에 놓아 버린다. 목적지가 늘 맨 위인 동작에 애니메이션과
리셋의 경합을 붙일 이유가 없어서 즉시 이동으로 바꿨다.

## 기각한 대안

병렬 라우트(`@home`/`@reels` 슬롯)로 두 화면을 동시에 마운트해 두고 탭 전환을 슬롯
전환으로 만들면, 복원 로직 없이 상태가 진짜로 보존된다. 제일 정석적인 해법이긴 한데
라우팅 구조와 화면별 서버 fetch, loading 경계를 통째로 갈아야 해서 티켓 범위를 한참
넘는다. 지금 방식(상태만 트리 밖에 두고 마운트 때 되돌리기)은 화면 코드를 거의 안
건드리고 같은 체감을 만든다. 화면이 더 늘어나 복원 로직이 지저분해지면 그때 다시
꺼내 볼 카드로 남겨 둔다.

검증 중에 콘솔에서 "useEffect changed size between renders" 에러를 보고 잠깐 긴장했는데,
작업 도중 deps 배열 크기를 바꾼 걸 HMR이 그대로 hot swap하면서 낸 소리였다. deps를
리터럴로 쓰는 한 런타임에 크기가 바뀔 수는 없다. 전체 리로드로 재현되지 않는 걸 확인하고
넘어갔다.

## 검증

iOS 시뮬레이터(iPhone 17)와 브라우저에서 확인한 시나리오:

- 홈 토트넘 탭 + 스크롤 → 기사 → 하단바 홈 → 토트넘 탭과 스크롤 위치 그대로
