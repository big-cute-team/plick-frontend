# 0092. 인증 계약 실측으로 확정하고 FE의 낡은 전제를 걷어냈다

## 발단

중간보고서를 쓰다가 인증 절이 전부 "(확인필요)" 딱지를 달고 있는 걸 봤다. 액세스 토큰이 JWT 1시간이라는
서술, 리프레시 토큰이 Valkey에 TTL로 산다는 서술, 가입 시 임시 닉네임을 자동 부여한다는 서술.
보고서에 쓴 문장이 실제 구현과 다르면 발표에서 그대로 틀린 말을 하게 되니, 프론트 코드부터 대조해 봤다.

## 프론트 코드만 보고 내렸던 잠정 결론 (그리고 그게 왜 틀렸나)

프론트 코드를 훑고 나서 처음 내린 결론은 "보고서가 틀린 것 같다"였다. 근거는 이랬다.

- `ACCESS_TOKEN_MAX_AGE`가 15분인데 보고서는 1시간이라 한다.
- `proxy.ts` 주석이 "BE 토큰은 만료 정보가 없는 불투명 문자열이라 exp를 디코드할 수 없다"고
  못 박고 있는데 보고서는 JWT라 한다.
- `profile.ts`와 온보딩 닉네임 페이지 주석이 "온보딩 전엔 닉네임이 null로 온다(현 BE)"라고
  적혀 있는데 보고서는 가입 시 plick+숫자를 자동 부여한다고 한다.

그런데 이 주석들은 전부 "그 시점의 관측"이었다. 통합 당시 BE가 목 토큰을 주던 시절의 전제,
자동 닉네임이 들어오기 전의 유저를 보고 쓴 전제가 코드에 화석처럼 남아 있었던 거다.
주석은 코드처럼 컴파일러가 검증해 주지 않으니, BE가 바뀌면 조용히 거짓말이 된다.

전 세션에서 배운 대로(가설보다 재현 먼저) 프론트 추정으로 결론 내리지 않고 be-verify
서브에이전트에게 BE 소스 + 실측 검증을 맡겼다.

## BE 실측으로 확정된 사실

be-verify가 BE 소스(`~/Documents/plick-backend`)와 공유 DB, 떠 있는 로컬 서버로 확인한 결과,
보고서 서술이 전부 맞고 프론트가 낡은 쪽이었다.

- 액세스 토큰은 HS256 서명 JWT고 `sub`/`iat`/`exp` 클레임이 있다. TTL은 `application.yml`의
  `access-ttl: 1h`. 우리 민팅 스크립트(HS256)로 만든 토큰을 BE가 200으로 받아서 알고리즘과
  시크릿 일치도 실측됐다.
- 리프레시 토큰은 서명 없는 랜덤 값 14일. Redis에 TTL로 저장하고 `getAndDelete`로 꺼내는
  순간 지운다. 한 번 쓰면 사라지는 1회용 회전이고, 재사용하면 "키가 없다"는 사실 하나로
  만료·위조와 같은 401로 수렴한다. 별도 재사용 탐지 로직이나 토큰 패밀리 무효화는 없다.
- 프로바이더 OAuth 토큰은 유저정보 조회에만 메서드 로컬로 쓰고 버린다. 저장 필드 자체가 없다.
- 사용자 식별은 DB 제약으로 `UNIQUE (provider, provider_id)`. email은 nullable에 유니크 없음.
- 가입 시 닉네임은 항상 plick+6자리를 자동 부여한다. 프론트가 봤던 null은 자동 닉네임
  커밋(7/20) 이전에 만들어진 레거시 유저 한 명이었다. 관측 자체는 사실이었는데 표본이
  레거시였던 것.
- `needsOnboarding`은 `nicknameChangedAt == null`로 판정한다. 별도 온보딩 플래그가 있는 게
  아니라, 닉네임을 직접 설정한 시각의 존재가 곧 온보딩 완료다. 온보딩 API 재호출 409도
  같은 필드를 본다. 자동 부여 닉네임이 있어도 이 시각은 null이라 "닉네임이 비어있는지로
  판단하면 안 된다"던 보고서의 논리가 그대로 구현돼 있었다.

실측 못 한 것도 적어 둔다. BE가 직접 발급한 토큰의 exp 실측은 실제 OAuth 인가 코드가
필요해서, 리프레시 회전 실측은 로컬 Redis가 안 떠 있어서 못 했다. 이 둘은 소스로만 확정했다.

검증 중 사고도 하나 있었다. 서브에이전트가 온보딩 완료 유저인 줄 알고 기존 유저에 온보딩
API를 쐈는데 실제로는 미온보딩이라 200이 떨어져 `nickname_changed_at`이 찍혔다. 즉시 NULL로
되돌렸고, 닉네임은 동일 값 제출이라 7일 잠금은 안 걸렸다. 공유 DB에서 기존 유저를 건드리면
안 된다는 규칙을 다시 확인한 셈이다.

## 프론트에 반영한 것

코드 동작 변경은 하나, 주석 정합화가 아홉이다. web과 mobile이 인증 배관을 복제로 갖고 있어
같은 수정이 두 벌씩 들어갔다.

1. `ACCESS_TOKEN_MAX_AGE` 15분 → 55분 (web·mobile `_constants/api.ts`).
   프론트는 쿠키의 소멸을 토큰 만료 신호로 쓴다. exp를 디코드하는 대신 access 쿠키의
   maxAge를 토큰 TTL에 맞춰 두고, 쿠키가 사라지면 "재발급해야 함"으로 읽는 구조다.
   그래서 쿠키 수명은 토큰 TTL보다 약간 짧아야 안전하다. 정확히 1시간으로 두면 서버와
   브라우저의 시계 오차만큼 "쿠키는 살아 있는데 토큰은 죽은" 경계 구간이 생겨, 만료 임박
   토큰을 Bearer로 실었다가 401을 맞을 수 있다. 5분을 빼서 55분으로 뒀다.
   15분이던 동안에도 동작은 안전했다(일찍 재발급할 뿐). 대신 세션당 재발급 회전이 4배로
   돌고, 회전마다 리프레시 토큰이 폐기·재발급되는 낭비가 있었다.
2. `proxy.ts`(web·mobile) 만료 판정 주석 — "불투명 문자열이라 디코드 불가"를 "exp 담긴
   JWT지만 디코드하지 않는다"로. 방식은 그대로 두고 이유를 사실에 맞게 고쳤다. 쿠키 신호가
   디코드보다 단순하고 시계 오차 문제도 함께 흡수한다.
3. `session.ts`(web·mobile) — "쿠키 수명 = 토큰 수명"이라던 서술을 "쿠키가 토큰보다 먼저
   만료된다"로.
4. `profile.ts`·온보딩 닉네임 페이지(web·mobile) — "온보딩 전엔 닉네임 null"을 "가입 시
   자동 부여, 레거시 유저만 null"로. `nickname: string | null` 타입 자체는 유지했다.
   레거시 행이 실제로 존재하니 null 방어는 여전히 필요하다.

## 후속: 프로덕션이 몇십 분마다 로그아웃되던 진짜 이유

PR을 올리고 나서 "프로덕션에서 자꾸 몇십 분 지나면 로그아웃된다"는 증상이 들어왔다.
리프레시 토큰이 14일인데 왜 세션이 이어지지 않는가.

처음엔 로컬 Redis부터 의심했다. 실제로 이 머신의 docker Redis는 꺼져 있었고 로컬 BE의
refresh는 500을 뱉었다(존재하지 않는 토큰이면 401이어야 하는데 500이라는 건 Redis 연결
자체가 실패한다는 뜻이다). 그런데 증상은 프로덕션이었다. 프로덕션은 ElastiCache Valkey가
멀쩡하니 다른 원인이다.

배포 문서를 다시 보니 그림이 맞춰졌다. 프로덕션 FE는 ASG Desired 2로 인스턴스가 2대고,
ALB가 요청을 나눠 보내며, 스티키 세션은 없다. 그리고 KAN-379에서 고쳤던 동시 재발급
묶음(`refreshTokensShared`)은 모듈 스코프 메모리라 한 인스턴스 안에서만 유효하다. 주석에
"문제의 버스트는 같은 인스턴스로 보내는 동시 요청이라 이걸로 덮인다"고 적혀 있었는데,
그건 인스턴스가 1대이던 시절의 전제였다.

시나리오는 이렇다. access 쿠키가 만료된 직후 페이지를 열면 문서 요청과 prefetch,
`/be` fetch가 버스트로 나가고 ALB가 이걸 두 인스턴스에 나눈다. 둘 다 같은 refresh
토큰으로 BE 재발급을 부른다. BE는 `getAndDelete` 1회용 회전이라 먼저 닿은 쪽만 성공하고
나중 쪽은 401을 받는다. 그러면 진 쪽 proxy의 catch가 종류 구분 없이 쿠키를 지우고
로그인으로 보냈다. 조용한 `/be` fetch가 져도 응답에 쿠키 삭제가 실려 세션이 죽었고,
심지어 이긴 쪽의 새 토큰 Set-Cookie보다 진 쪽의 쿠키 삭제가 늦게 도착하면 회전이
성공했는데도 로그아웃됐다. 매 회전이 동전 던지기였고, access 쿠키가 15분이던 프로덕션
빌드에서는 그 동전을 시간당 네 번 던졌다.

proxy의 실패 처리를 세 갈래로 갈랐다.

1. 401이 아니면(BE 5xx, 네트워크) 토큰이 무효라는 증거가 없다. 쿠키를 건드리지 않고
   익명으로 통과시킨다. BE가 잠깐 죽었다고 로그인 상태를 버리던 과잉 반응을 없앴다.
2. `/be` fetch의 401은 쿠키를 지우지 않고 익명 통과만 한다. 공개 조회는 그대로 뜨고
   보호 API는 BE가 401을 주면 된다. 백그라운드 fetch 하나가 세션 전체를 지우던 구멍이
   이거 하나로 막힌다.
3. 페이지 요청의 401은 즉시 로그아웃이 아니라 같은 URL로 1회 재시도 리다이렉트한다.
   경쟁에서 진 요청이 재시도로 돌아올 때쯤이면 이긴 형제의 Set-Cookie가 브라우저에
   저장돼 있어서, 재시도는 새 access를 달고 그냥 통과한다. 사용자는 아무것도 못 느낀다.
   가드 쿠키(15초)가 "1회"를 세므로, 진짜 만료라면 재시도도 401을 받고 그때 쿠키를
   지우고 로그인으로 보낸다. 루프는 없다.

이걸로 로그아웃이 100% 사라지느냐면 아니다. 진 요청의 재시도가 이긴 응답보다 먼저
브라우저를 떠나는 수십 ms 창에서, 재시도가 하필 grace 메모리 없는 인스턴스에 떨어지면
여전히 끊긴다. 이 마지막 구멍은 FE에서 못 막는다. 재발급 상태가 인스턴스별 메모리에
갇혀 있는 게 근본 원인이라, BE가 회전 직후의 옛 토큰을 30초쯤 Redis에 old→new로
기억해주는 게(지금 FE가 인스턴스 안에서 하는 grace를 Redis로 옮기는 것) 완전한 해법이다.
백엔드에 전달할 몫으로 남긴다. 인프라 쪽 대안으로는 FE 대상 그룹에 ALB 스티키 세션을
켜는 방법도 있다.

## 남긴 생각

"확인필요" 딱지가 붙은 문서를 검증할 때 프론트 코드의 주석을 근거로 쓰면 안 된다는 걸 몸으로
배웠다. 주석도 그 시점의 관측일 뿐이고, 이번엔 넷 다 낡아 있었다. 계약의 진실은 BE 소스와
실측에만 있다. 그리고 이번처럼 인증 배관이 web/mobile 두 벌인 코드는 주석 부패도 두 벌로
일어난다. refresh fetcher처럼 이미 `@plick/core`로 공용화된 조각 옆에서, 상수와 주석은 아직
복제로 남아 있는 경계가 보였다.
