# ADR 0056 — web 홈 핫이슈 API 이식과 임베드 크기 맞춤 삼전 (KAN-324)

- 날짜: 2026-07-28
- 브랜치: `feature/KAN-324-web-hot-articles-api`
- 관련: [ADR 0034 모바일 핫이슈 API](0034-mobile-home-hot-articles-api.md) ·
  [ADR 0053 web 피드 API](0053-web-articles-feed-api.md) ·
  [ADR 0055 web 릴스 API](0055-web-reels-feed-api.md) ·
  [ADR 0011 공용 경계](0011-shared-code-boundary.md) · `api-integration` 스킬 `web-wiring.md`

## 무엇을 했나

데스크톱 웹 홈의 핫이슈 그리드를 목데이터에서 `GET /api/v1/articles/hot`으로 갈아탔다.
모바일이 KAN-282에서 이미 붙인 엔드포인트라 web이 두 번째 사용처가 되는 티켓이고, 그래서
`HotArticle` 타입과 `getHotArticles` fetcher를 `@plick/domain`·`@plick/core`로 승격하는 게
이번 작업의 본편이라고 생각하며 시작했다. 그런데 실제로 제일 오래 걸린 건 그게 아니라
사진 없는 기사(지금은 전건이 그렇다)의 트윗 임베드를 데스크톱 카드에 맞추는 일이었다.
세 번을 갈아엎었다. 그 과정을 이 문서에 다 적는다.

## 승격 — 예고된 대로라 순탄했다

web-wiring.md §2의 승격 후보 목록에 "HotArticle은 모바일 단독이라 남았고 articles/hot을
web에 붙일 때 따라 올라간다"라고 예고까지 돼 있던 건이다. ADR 0011 게이트로 재확인해도
셋 다 통과였다. 앱 역참조 없음(팀 매핑은 이미 `@plick/domain` 상수), 계약 타입이라 두 앱에서
동일해야 함, BE로 shape가 굳어 있고 web이라는 두 번째 실사용처가 지금 생김.

- `HotArticle`: 모바일 `_types/articles.ts` → `@plick/domain/types`. 모바일에 이 파일은
  핫이슈 타입 하나만 남아 있었어서 파일째 지워졌다.
- `getHotArticles` + `HotCardResponse` + `toHotArticle`: 모바일 `_services/articles.ts` →
  `@plick/core/articles`. 역시 파일째 삭제. 피드(KAN-321)·상세(KAN-322)가 먼저 가 있던
  모듈 끝에 붙였다.
- 모바일 소비처 세 곳(`(home)/page.tsx`, `HotCarousel`, `HotHeroCard`)의 import 교체.

이로써 모바일 `_services/articles.ts`와 `_types/articles.ts`는 소멸했고, 기사 관련 fetcher와
계약 타입은 전부 패키지에 산다.

## 계약이 그 사이 바뀌어 있었다 — be-verify를 부른 이유

web 이식은 원래 be-verify를 안 부른다. 모바일 코드가 검증된 계약이니까. 그런데 화면을
띄우기 전에 로컬 BE를 curl로 한 번 찔러봤다가 모바일 코드의 주석과 실응답이 어긋나는 걸
발견했다. 모바일 fetcher 주석엔 "sourceUrl은 스웨거·실응답 모두 없다", "집계는 Noop이라
항상 0"이라고 적혀 있는데, 실응답엔 `sourceUrl`이 전건 채워져 있고 viewCount가 2~3,
likeCount도 0이 아닌 값이 섞여 있었다. 이건 web-wiring.md §1의 "모바일 연결 이후 BE가
바뀐 정황"에 정확히 해당해서 be-verify를 불렀다.

리포트 요지는 이렇다.

- `sourceUrl`은 정식 계약 필드가 됐다. BE 커밋(2026-07-24)에서 `HotArticleResponse`
  최상위에 추가됐고, 대표 원문 선정 규칙(기자 tier 오름차순 → 최신순)은 피드와 같다.
  대표 원문이 없으면 null인데 로컬 시드 기준으로는 전건 채워진다. 재미있는 함정 하나:
  스웨거 `Reporter` 스키마에 `sourceUrl`이 보이는 건 springdoc이 상세와 핫이슈의 이름이
  같은 `Reporter` record 두 개를 스키마 하나로 합쳐버린 탓이고, 핫이슈 `reporter` 객체에는
  그 키가 안 온다. 원문 링크는 최상위 `sourceUrl`을 쓰는 게 맞다.
- 집계가 실집계로 교체됐다. `NoopArticleEngagementProvider`는 소스에서 사라졌고
  `CountingArticleEngagementProvider`가 매 요청 likes·comments·article_views를 센다.
  be-verify가 일회용 유저로 like 행을 넣고 재조회해서 likeCount 증가와 `likedByMe` 유저별
  계산까지 실측으로 확인했다(정리도 완료). "항상 0이라 어차피 안 보인다"는 전제는 폐기다.
- 익명 200, 만료 토큰 401 `AUTH_EXPIRED_TOKEN`, size 1..10 기본 5, `imageUrl` 전건 null은
  그대로였다.

그래서 승격하면서 계약 코드를 셋 고쳤다. `HotCardResponse.sourceUrl`을 optional(`?`)에서
정식 `string | null`로, 변환의 `?? null` 방어를 직통으로, 그리고 낡은 주석들(도메인 타입의
"당분간 항상 null이다", 상세 타입의 "Noop이라 항상 0·false다")을 현행화했다. 주석이 계약
문서 역할을 하는 구조라, 코드보다 주석 수정이 더 중요한 변경이었다.

## 화면 교체 — 페이지 구조는 모바일 홈을 그대로 옮겼다

web 홈은 이미 피드가 실 API(KAN-321)라 `getArticles` 하나를 await하고 있었다. 핫이슈가
추가되면서 모바일 홈(KAN-282)과 똑같은 구조가 됐다. `Promise.allSettled`로 병렬로 받고,
한쪽이 죽어도 그 섹션 자리에만 "핫이슈를 불러오지 못했어요"를 그린다. `all`이 아니라
`allSettled`인 이유(하나가 reject되면 멀쩡한 섹션까지 길동무)는 모바일 때 정리한 그대로다.
빈 배열 분기도 뒀다. BE에 최신순 폴백이 있어 사실상 볼 일 없지만 계약상 가능한 상태는
다 그린다.

페칭은 서버 컴포넌트 fetch다. 단발 읽기라 스킬 §0 표에서 고민할 게 없었고, 모바일과 같은
이유로 토큰도 안 싣는다(익명 허용 API인데 만료 토큰을 실으면 401로 오히려 죽는다).

`HotIssueGrid`·`HotCard`의 props는 `FeedPost`에서 `HotArticle`로 갈아탔다. 이 화면이
web의 마지막에서 두 번째 `FeedPost` 소비처였어서 목데이터도 크게 줄었다. `_mocks/posts.ts`는
이제 사이드바(실시간 인기·마이팀 카드) 전용이고, 파일 머리에 "계약 공백이 해소되면 파일째
사라진다"는 사망 예고를 적어 뒀다. 핫이슈용 `HOT_POSTS` slice와 댓글 목데이터, 안 읽는
필드들(body, tags, comments)은 이번 PR에서 지웠다.

## 임베드 크기 맞춤 — 세 번 갈아엎었다

여기가 이번 작업의 늪이었다. 핫이슈도 `imageUrl`이 전건 null이라 미디어 자리는 원문 트윗
임베드가 채우는데(모바일 KAN-284→KAN-297 전략), 데스크톱 카드는 모바일 카드와 기하가
달라서 모바일 코드를 그대로 옮기면 안 맞았다.

문제의 뿌리는 트윗 임베드의 크기 특성이다. react-tweet 카드는 폭을 주면 높이가 따라
나오는(본문이 접히는 줄 수가 폭에 달린) 콘텐츠라, 폭이 넓어질수록 오히려 낮아진다.
모바일 캐러셀 카드는 폭 ~335px에 비율 181:131이라 트윗 자연 높이와 카드 높이가 얼추
비슷해 "가로 꽉 + 세로 가운데(넘치면 위 정렬)"만으로 딱 맞았다. 데스크톱 히어로는 폭
~750px에 높이 ~430px라 같은 트윗이 250px로 낮아져 위아래가 비고, 서브 카드는 폭 374px에
높이 208px라 반대로 트윗(~310px)이 카드보다 커서 잘린다. 같은 코드가 카드 기하에 따라
정반대 증상을 낸다.

1차 시도는 모바일 그대로 이식이었다. 카드 전체를 임베드 영역으로 잡고
`justify-content: safe center`. 히어로는 위아래가 텅 비고 서브는 텍스트와 충돌해 보였다.
이때 사용자 피드백이 "박스에 크기가 맞지 않고, 모바일처럼 아래 음영이 있어야 한다"였다.

2차 시도는 web 릴(KAN-323)의 측정 방식 + 모바일 fill 레이아웃 이식이었다. 텍스트 블록
윗선을 ResizeObserver로 재서 임베드 영역을 잡고, `useTweetFit`(미디어 숨김 + 잔여 축소)으로
박스 안에 가뒀다. 기술적으로는 안 잘리게 됐지만 서브 카드에서 트윗이 0.3배로 쪼그라들어
글자가 안 읽혔다. 사용자가 모바일 캐러셀 스크린샷을 보여주며 "이 형식 그대로"라고 했다.

여기서 방향을 묻는 게 맞다고 판단해 선택지를 정리해 물었다. 모바일 비율 카드 3장 나란히 /
피그마 배치 유지 + 모바일 폭으로 렌더해 확대(zoom) / 모바일 코드 그대로(결과는 다름).
답은 확대였고, 3차로 `useTweetZoom`(335px로 렌더 후 transform scale로 카드 폭까지 확대,
카드 비율도 181:131로 통일)을 구현했다. 픽셀 단위로 모바일 카드를 확대한 모습이 나왔는데,
이번엔 카드가 화면을 압도할 만큼 커졌고(1136px 컨테이너에서 비율 카드는 높이 541px),
확대된 글자도 과했다.

최종 피드백이 결론을 냈다. "카드 크기는 원래대로 줄이고, 가로를 꽉 채워 렌더하고, 세로는
모바일 로직처럼 — 크면 위 정렬에 밑부분 가림, 아니면 가운데." 돌아보면 이건 1차 시도와
같은 구조인데 딱 하나가 다르다. react-tweet의 기본 `max-width: 550px`를 푸는 것. 1차 때
히어로가 "안 맞아" 보인 진짜 원인은 세로 여백이 아니라 750px 카드에서 트윗이 550px에
걸려 좌우가 비던 것이었고, 나는 그걸 세로 문제로 읽고 두 번을 돌아갔다. zoom 부속을 다
걷어내고(`useTweetZoom`, `useTweetFit`, 기준 폭 상수, 확대용 CSS), `.hot-embed`에
`max-width: none`과 카드 라운드 맞춤(`--radius-hero`)만 남겼다. 카드 배치는 피그마 원안
(히어로 stretch + 서브 aspect-[9/5])으로 복귀.

가운데 정렬의 기준 영역은 두 번 오갔다. 카드 전체(`inset-0`) 기준으로 시작했다가,
텍스트 블록 뒤로 내려앉는다는 피드백에 web 릴(KAN-323)처럼 텍스트 블록 윗선을
ResizeObserver로 재는 방식으로 바꿨는데, 눈으로 비교해 본 사용자가 전체 높이 가운데가
낫다고 되돌렸다. 최종은 카드 전체 기준 `safe center`다. 덕분에 측정 훅이 필요 없어져
`HotCard`가 서버 컴포넌트로 남았다. 히어로는 카드 가운데에 서고, 서브는 트윗이 카드보다
높아 위 정렬에 밑부분이 스크림 뒤로 잠기는, 모바일과 같은 문법이다.

교훈. "안 맞는다"는 피드백을 받으면 어느 축이 안 맞는 건지부터 재야 했다. 폭 문제를 세로
문제로 오진해서 측정 훅과 확대 훅을 하나씩 만들었다 버렸다. 그리고 임베드처럼 크기가
콘텐츠에 달린 요소는 박스에 맞추는 전략(자연 크기·축소·확대)이 서너 개씩 나오는데, 어느
게 맞는지는 기하가 아니라 사용자가 정한다. 두 번째 갈아엎기 전에 물었어야 했다.

## 앵커 중첩 — 카드를 Link로 감싸면 안 됐다

퍼블리싱 시절 `HotCard`는 카드 전체를 `<Link>`로 감쌌다. 임베드가 들어오자 브라우저
콘솔에 하이드레이션 에러가 떴다. `<a>` 안에 `<a>`가 못 들어간다는 HTML 제약인데, 임베드
내부에 프로필·원문 앵커가 있어서 카드 래퍼 `<a>`와 중첩된 것이다. 모바일 `HotHeroCard`가
카드를 감싸는 대신 `absolute inset-0` 링크를 형제로 까는 이유가 바로 이거였다. 같은 구조로
바꿔 해결했다. 임베드 내부 상호작용은 전역 CSS에서 이미 꺼둔 상태라(KAN-297) 오버레이
링크가 모든 클릭을 받는다.

부끄러운 디버깅 하나. 그리드 stretch 때문에 `aspect-ratio`가 무시돼 카드 높이가 0으로
접힌 줄 알고 `self-start`를 넣었는데도 0이길래 한참 헤맸다. 컴퓨티드 스타일을 까보니
`aspectRatio: "auto"` — 방금 넣은 arbitrary variant 클래스가 컴퓨티드에 없었다. 새로고침
한 번에 풀렸다. Turbopack dev 서버가 CSS를 미처 다시 안 뱉은 stale 빌드였고, 레이아웃
디버깅 전에 새로고침부터 하는 게 맞았다.

## 검증

계약은 be-verify 재검증(위 절)으로 갈음하고, 화면은 dev :3000에서 직접 밟았다.

- 성공: 히어로 + 서브 2장, 실데이터(제목·팀·상대시각·조회수) 렌더 확인. 임베드가 카드
  가로를 꽉 채우고, 히어로는 세로 가운데, 서브는 위 정렬 + 밑부분 스크림 잠김.
- 앵커 중첩 하이드레이션 에러 소멸(`document.querySelectorAll('a a')` 0건)과 카드 클릭
  시 기사 세부 이동.
- 반응형: 1280 기준, 330px(모바일 뷰, 히어로 한 장)까지.
- 에러·빈 상태는 코드 분기로 확인(모바일과 동일 문구).
- 공용 패키지를 건드렸으므로 web·mobile 양쪽 `build`와 `check-types`, `lint`,
  `format:check` 전부 통과. 모바일은 import 교체 말고 동작 변화가 없어야 하는 쪽이라
  빌드 통과가 곧 회귀 확인이다.

## 남긴 것

- 사이드바(실시간 인기·마이팀 카드)는 여전히 계약 공백이라 목데이터다. `FeedPost`·`User`
  타입과 `_mocks/posts.ts`의 마지막 소비처로 남았다.
- 모바일 핫이슈 화면은 `sourceUrl`이 정식 필드가 되면서 트윗 임베드 폴백이 실제로 살아났다
  (코드는 KAN-284부터 준비돼 있었고 이번에 데이터가 흐르기 시작). 모바일 화면 확인은
  이번 티켓 범위 밖이라 안 밟았다.
