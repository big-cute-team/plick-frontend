# 0054. web 기사 세부 API 이식과 상세 계약·배지 줄의 공용 승격 (KAN-322)

날짜: 2026-07-28
브랜치: `feature/KAN-322-web-article-detail-api`

## 무엇을 했나

모바일에서 이미 붙여 둔 `GET /api/v1/articles/{articleId}`(기사 상세)를 데스크톱 웹에 이식했다.
웹 `/articles/[postId]`는 지금까지 `_mocks/posts.ts`의 `POSTS` 배열에서 id로 하나 찾아 그리던
화면이었다. 목록이 이미 실계약으로 넘어간 뒤였으니(KAN-321) 목록에서 기사를 누르면 실제 id
(`8032` 같은 BE `articleSummaryId`)로 이동하는데 목 배열엔 `h1`, `n2` 같은 문자열 id밖에 없어서
전부 404로 떨어지고 있었다. 지난 세션 ADR에 "상세는 아직 목 기반이라 실제 id가 없다 — 다음 티켓 몫"
이라고 적어 둔 그 구멍을 이번에 메웠다.

작업 자체는 엔드포인트 하나짜리로 작지만, 딸려 온 판단이 셋 있었다. 승격을 어디까지 할 것인가,
계약에 없는 것(관련 기사·실시간 인기·댓글)을 화면에서 어떻게 처리할 것인가, 그리고 세션 중반에
받은 "모바일과 똑같이 만들라"는 피드백을 어디까지 따라갈 것인가다.

## 계약은 이번에도 모바일 코드에서 왔다

`be-verify`를 부르지 않았다. 상세 계약은 모바일 KAN-283에서 서브에이전트가 실제로 때려 확인해
`_services/articles.ts`에 굳혀 둔 그대로고, 그 뒤로 BE가 바뀐 정황이 없었다(`web-wiring.md` §1의
재검증 조건에 걸리는 게 없다). 대신 모바일 fetcher와 ADR 0036을 정독하는 걸로 갈음했다. 거기 적힌
함정이 그대로 다 살아 있었다.

상세 응답은 목록·핫이슈와 또 다른 세 번째 shape다. 기자가 단일 객체가 아니라 `reporters` 배열로
오고(대표 순서 정렬이라 `[0]`이 대표), 원문 트윗 링크가 목록처럼 최상위 `sourceUrl`이 아니라 기자마다
달려 온다. `teams` id 배열은 아예 없어서 팀은 `hashtags`의 팀 한글명에서 역산해야 한다. 본문 문단
필드도 없어 본문은 긴 요약(`summary`, DB `summary_detail`) 하나가 전부다. 좋아요·댓글·조회는 BE가
아직 Noop 구현이라 항상 0과 false로 온다.

에러 계약도 그대로다. 없는 id와 미발행 기사는 404 `ARTICLE_NOT_FOUND`, 정수가 아닌 id는 400
`COMMON_INVALID_PARAM`. 이 라우트는 삭제된 딥링크가 정상 유입 경로라서 이 두 code만 잡아
`notFound()`로 보내고 나머지는 루트 `error.tsx`가 받게 했다. 웹에도 `not-found.tsx`를 새로 깔았다.

## 승격: 상세 계약이 통째로 올라갔다

웹이 두 번째 실사용처가 되면서 ADR 0011 게이트 C(성숙도)가 이 엔드포인트가 쓰는 조각들에 대해
처음 섰다. 지난 세션(KAN-321)에서 "다음 이식 티켓이 나머지를 들고 올라가면 된다"고 적어 둔 그
나머지다. 게이트 A(앱 역참조)와 B(동일성)도 걸리는 게 없어서 넷 다 올렸다.

- `@plick/domain/types`: `ArticleDetail`
- `@plick/domain/constants`: `TEAM_BY_KO_NAME`(해시태그 한글명 → 팀 코드 역산 테이블)
- `@plick/core/articles`: `getArticle` fetcher와 BE 응답 타입(`ArticleDetailResponse`), 경계 변환
  (`toArticleDetail`)
- `@plick/ui/PostBadges`: 구단 로고 + 단계 글자 배지 줄 (아래 "모바일과 똑같이" 절 참고)

모바일에 남은 건 핫이슈(`HotArticle`, `getHotArticles`)뿐이다. `_services/articles.ts`와
`_types/articles.ts`가 이제 핫이슈 전용 파일이 됐고, 파일 머리 주석을 그에 맞게 고쳤다. 핫이슈는
웹 홈 그리드를 붙이는 티켓에서 따라 올라갈 것이다.

`TEAM_BY_KO_NAME`을 domain으로 올린 게 살짝 걸렸다. 이건 참조 상수라기보다 BE DB 값(`teams.name_ko`)을
박아둔 계약 공백이고, 재시드로 표기가 바뀌면 팀 칩이 조용히 빠지는 종류의 물건이다. 그래도 이미
같은 성격의 `TEAM_IDS`가 domain에 살고 있고(KAN-319에서 승격), 상세 fetcher가 core로 올라가는 이상
core가 이 테이블을 봐야 해서 앱에 남길 수가 없었다. core → domain 의존은 이미 있으니 자리는 여기가
맞다. ⚠️ 주석은 그대로 옮겨 왔다.

`getAccessToken`은 승격하지 않고 웹 `_services/session.ts`에 복제했다. `cookies()`를 읽는 서버 전용
헬퍼이고 쿠키 이름 상수가 앱에 있어서 순수 모듈 경계 밖이다. 웹 인증 PR(KAN-318) 때 "web에 인증 읽기
소비처가 생길 때 같이 가져온다"고 주석에 적어 둔 그 시점이 지금이었다. 상세를 토큰 없이 부르면
응답의 `likedByMe`가 항상 false로 와서, 좋아요를 누르고 새로고침하면 하트가 빈 채로 카운트만 올라가
있는 상태가 된다. 지금은 BE Noop이라 어차피 false지만 계약상 토큰을 싣는 게 맞아서 그대로 가져왔다.
만료 토큰으로 401을 맞을 걱정은 없다 — access 쿠키의 수명이 곧 토큰 수명이라 만료되면 쿠키째 사라져
`getAccessToken`이 undefined를 주고 익명으로 부른다.

## 계약에 없는 것들: 목으로 채우지 않는다

이 화면에서 실계약이 못 채우는 자리가 셋이었다. 우측 사이드바의 "관련 기사"와 "실시간 인기", 그리고
본문 밑 "함께 보면 좋은 기사", 거기에 댓글 목록까지 넷이다. 사용자에게 물어 방향을 정했다.

사이드바는 자리를 남기고 준비 중 문구를 넣기로 했다. 카드 두 개의 2열 레이아웃 균형은 지키되 안쪽만
"아직 준비 중이에요!"로 비운다. 관련·인기 API가 생기면 여기서 받아 목록을 되살리면 된다. 목데이터
`TRENDING_POSTS`를 계속 흘리거나 피드 최신 4건을 관련 기사인 척 채우는 선택지도 있었지만 둘 다
버렸다. 모바일 KAN-283에서 "추천 API가 생기기 전까지 목이든 슬라이싱이든 채우지 말자"고 정한 원칙이
있고, 지금 웹만 다르게 갈 이유가 없었다.

댓글도 같은 결이다. 상세 응답에 댓글이 없으니(별도 엔드포인트다) 카운트(0)와 "아직 댓글이 없어요"
빈 상태만 뒀다. 목 댓글 5건과 답글 토글(`CommentThread`)을 흘리던 걸 걷어냈다. 댓글 읽기 API를
이식하는 티켓에서 채운다. `CommentThread` 컴포넌트 자체는 릴스 세부 패널이 아직 쓰고 있어 남는다.

액션 줄에서는 저장 버튼을 뺐다. BE 계약에 저장이 없다(모바일도 KAN-283에서 같은 이유로 뺐다).
좋아요는 상세 응답의 `liked`·`likeCount`를 그리기만 하고 누르는 동작은 붙이지 않았다 — 뮤테이션은
이식 순서상 마지막이고 이 티켓은 읽기 하나가 스코프다. 다만 퍼블리싱 때 정적으로 박혀 있던
강조색(초록)은 고쳤다. 안 눌렀는데 눌린 것처럼 보이던 상태라, `liked`일 때만 강조색이고 기본은
이웃 공유 버튼과 같은 중립 톤이 되게 했다. 이것도 모바일이 먼저 밟은 피드백이다.

## 화면: FeedPost에서 ArticleDetail로

웹 `ArticleMain`이 소비하던 `FeedPost`는 퍼블리싱 때 BE 목표 shape를 추정해 만든 타입이라 실계약과
여러 군데 어긋난다. 갈아타면서 마크업이 전제하던 게 깨진 자리가 이번에도 넷이었다.

- 단일 `team` → `teams` 배열(비어 있을 수 있음). 첫 팀만 대표로 쓰고 없으면 배지를 안 그린다.
- `reporter` 필수 → nullable. 없으면 기자 라인 대신 시각·조회만 한 줄로 남긴다.
- `timeLabel`(가공 문자열) → `publishedAt`(ISO). `formatRelativeTime`으로 바꿔 그린다.
- `body?: string[]`(문단 배열) → 없음. 긴 요약 하나가 본문이라 줄바꿈으로 갈라 문단을 만든다.

사진도 목록과 같은 판단을 따랐다. 목 시절엔 팀 컬러 사각형을 무조건 그렸는데 실데이터는 이미지가
전부 null이라 그 자리를 아예 접고 텍스트만 흐르게 했다.

## "모바일과 똑같이 만들라"

여기까지 만들어 검증하던 중 피드백을 받았다. "함께 보면 좋은 기사" 위치를 모바일처럼 올리고,
팀 태그와 OFFICIAL 태그를 모바일처럼 로고와 새 태그로 바꾸라는 것이었다.

위치부터. 웹은 추천 행이 페이지 맨 밑, 그것도 본문+사이드바 그리드 바깥의 전폭 3열 행이었다.
모바일은 본문 글(해시태그) 바로 밑이자 액션·댓글 위다. 모바일 자리가 맞다 — 기사를 다 읽은 직후에
다음 읽을거리를 권하고, 좋아요·공유·댓글은 그 뒤에 오는 흐름이다. `SuggestedArticles`를
`ArticleMain` 안 해시태그와 액션 사이로 옮기고, 페이지에서는 렌더를 걷어냈다. 본문 컬럼 안으로
들어오면서 섹션 제목 스케일도 페이지 레벨 `text-section`에서 본문 흐름에 맞는 `text-title`로
낮췄다.

배지 줄이 더 큰 변경이었다. 웹은 `PostChips`(텍스트 팀 칩 + 알약 단계 칩)를 쓰고 있었는데, 모바일은
KAN-299/301에서 이미 `PostBadges`(실제 구단 로고 + 알약 배경 없는 단계 글자)로 갈아탄 상태였다.
모바일 컴포넌트를 웹에 복제할까 하다가, 이게 정확히 ADR 0011이 말하는 "순수 원자, 두 번째로 쓰이면
공용"에 해당해서 `@plick/ui`로 승격했다.

승격하면서 손볼 게 하나 있었다. `@plick/ui`는 의도적으로 `@plick/domain`에 의존하지 않는다
(`PostChips`가 도메인 `RumorStage`를 import하는 대신 같은 리터럴을 `PostStage`로 따로 선언해 둔 게
그 흔적이다). 모바일 `PostBadges`는 `Team` 타입과 `STAGE_META`를 도메인에서 가져다 썼으므로 그대로
올릴 수 없었다. `PostChips` 전례대로 props를 `{ code, name }` 구조 타입으로 좁히고, 단계 라벨은
`PostChips`에서 `STAGE_LABEL`로 export해 둘이 나눠 쓰게 했다. 라벨이 두 컴포넌트에 중복돼 있던 걸
이참에 한 곳으로 모은 셈이다. 로고 크기는 표면마다 달라서(모바일 릴 30, 웹 기사 세부 34)
`crestSize` prop으로 뺐다. 모바일 앱 로컬 `_components/PostBadges.tsx`는 지웠고 릴·기사 세부 두
소비처가 패키지에서 import하게 바꿨다.

단계 글자색(RUMOUR=accent, IN_PROGRESS=warn, OFFICIAL=info)은 칩과 같은 매핑을 유지했다. 실제로
`OFFICIAL` 기사를 열어 보니 파란색(`rgb(96,165,250)`)으로 나왔다.

## 검증

빌드·타입·린트는 web과 mobile 둘 다 통과. 화면은 dev(:3000)에 로컬 BE를 물려 직접 밟았다.

- 실기사(`/articles/8032`): 크레스트(`/teams/mun.webp`, 200/21KB) + OFFICIAL 글자 → 제목 → 기자
  라인(Ben Jacobs · 21시간 전 · 조회 1) → 원문 링크 → 본문 → 해시태그 → 함께 보면 좋은 기사(준비 중)
  → 좋아요·공유 → 댓글 0 + 빈 상태. DOM 순서가 모바일 `ArticleBody`와 같다.
- 없는 id(`/articles/99999999`, 404)와 정수가 아닌 id(`/articles/abc`, 400): 둘 다 not-found 화면.
- 반응형: 330px에서 가로 오버플로 0, 사이드바는 `lg` 미만에서 숨김. 데스크톱에서 2열.
- 콘솔 에러 없음.
- 회귀: 모바일 기사 세부(:3001)와 릴스가 승격된 `PostBadges`로 여전히 크레스트를 그리고, 웹 릴스도
  `PostChips` 리팩터 뒤 팀 칩·단계 칩이 그대로 나온다.

로딩 스켈레톤은 실제 본문과 같은 구성(배지 줄 → 제목 → 기자 라인 → 문단 → 해시태그 → 추천 → 액션
→ 댓글 입력)으로 새로 깔았다. 대표 이미지 자리는 넣지 않았다 — 발행 기사 사진이 전부 null이라 실제
화면도 텍스트만 흐르는데 스켈레톤에만 미디어 박스가 있으면 로딩이 끝나는 순간 레이아웃이 튄다.

브라우저 패널의 측정값 문제는 이번에도 만났다. `getBoundingClientRect()`가 전부 0으로 나와서
크레스트가 안 그려지는 줄 알았는데, 패널이 `visibilityState === "hidden"`이라 레이아웃 수치가
0으로 떨어지는 것이었다(ADR 0053에 스크린샷이 새까맣게 나오는 걸로 적어 둔 것과 같은 원인).
`src`와 `alt`, 네트워크 응답 코드로 확인하는 쪽으로 바꿨다.

## 남은 것

- 관련 기사·실시간 인기·추천 기사 API가 생기면 사이드바와 추천 행의 준비 중 문구를 목록으로 되살린다.
- 댓글 읽기 API 이식 티켓에서 댓글 목록을 채운다. 좋아요·조회수 기록은 뮤테이션 티켓 몫이다.
- 웹 홈 핫이슈 그리드가 아직 목데이터다(`HOT_POSTS`). `articles/hot` 이식 티켓에서
  `HotArticle`·`getHotArticles`가 따라 올라간다.
- `FeedPost` 소비처가 웹에 아직 남아 있다(핫이슈, 릴스, 홈 사이드바). 마지막 소비자가 사라지는 PR에서
  `@plick/domain`의 `FeedPost`와 부속(`Comment`, `Debate`)을 지운다. 이번에 기사 세부가 빠져 남은
  소비처가 줄었다.
- `_mocks/posts.ts`는 홈 핫이슈·사이드바·릴스가 아직 써서 남는다.
