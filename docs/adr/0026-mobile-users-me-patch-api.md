# ADR 0026 — 모바일 프로필 수정(응원팀) PATCH 연결 (KAN-268)

- **날짜:** 2026-07-21
- **범위:** `apps/mobile` — `PATCH /api/v1/users/me`를 프로필 수정 화면(`/me/edit`)의 응원팀 저장에 연결. 지금까지 로컬 상태로만 놀던 팀 선택을 실제로 DB에 쓴다.
- **관련:** [ADR 0025 내 프로필 조회](0025-mobile-users-me-api.md) · [ADR 0024 온보딩 저장](0024-mobile-onboarding-api.md) · `api-integration` 스킬

## 무엇을 했나

조회(KAN-267)까지 붙여둔 프로필 수정 화면의 마지막 반쪽을 채웠다. 화면은 이미 `GET /users/me`로 현재 응원팀을 받아 칩을 그려놓고 있었지만, "변경사항 저장" 버튼은 아직 아무 데도 연결돼 있지 않은 껍데기였다. 이번에 그 버튼을 `PATCH /api/v1/users/me`에 이어, 고른 팀이 실제로 `favorite_teams`에 반영되게 했다.

세 번째 보호 API고, 온보딩 저장(KAN-264)에 이은 두 번째 쓰기다. 그래서 새로 세운 게 거의 없다 — `submitOnboarding`을 만들 때 깔아둔 서버 액션 + Bearer 쿠키 + 에러 봉투 패턴을 그대로 재탕했다.

## 스웨거보다 실제 응답 — 이번엔 맞았다

ADR 0025에서 스웨거 설명이 틀렸던 적이 있어서 이번에도 곧이곧대로 안 믿고 실제로 때려봤다. 스웨거의 요청 body는 `{ nickname?, teamIds? }`, "보낸 항목만 변경, 팀은 전체 교체"라고 적혀 있었다. 테스트 유저를 하나 만들어(초기 팀 리버풀) JWT를 민팅하고 curl로 직접 확인해보니 이번엔 문서대로였다: `{"teamIds":[4,6]}`를 보내면 응답과 DB가 딱 아스날·토트넘으로 갈리고, `{"teamIds":[]}`면 팀이 0개로 비워진다. **PATCH지만 팀은 부분 병합이 아니라 통째로 교체**라는 게 핵심이라, 화면 선택 전체를 매번 그대로 보내면 된다.

닉네임은 이번 화면에 수정 UI가 없다(정보 카드는 읽기 전용 표시). 그래서 요청 body에 `nickname`을 아예 안 싣고 `teamIds`만 보낸다 — BE가 "보낸 항목만" 건드리니 닉네임은 안전하게 그대로 남는다. 스웨거에 닉네임 7일 제한(409)이 적혀 있던데, 우리가 안 보내니 이 세션에선 마주칠 일이 없다.

## 팀 코드 → teamId, 다시 그 상수

요청은 `teamId` 숫자 배열을 원한다. FE는 팀을 `TeamCode`("LIV" 등) 문자열로 다루니 경계에서 `TEAM_IDS["LIV"] → 3`으로 바꿔 보낸다 — 온보딩 저장 때 이미 쓰던 `_lib/api/constants.ts`의 그 상수 그대로다. 이 상수는 BE에 팀 목록 조회 API가 없어서 DB 값을 손으로 박아둔 계약 공백이라, 재시드로 teamId가 바뀌면 400으로 조용히 어긋난다(KAN-264 때 실제로 겪었다). 이번에도 붙이기 전에 DB `teams`를 확인해 1~6 매핑이 그대로인 걸 보고 갔다. `GET /teams` 류가 생기면 이 상수를 걷어내는 게 맞다.

읽기(GET) 쪽은 반대로 응답의 `shortName`을 역방향으로 `TeamCode`에 맞춰서 재시드에 안 흔들린다(ADR 0025). 쓰기만 이 숫자 매핑에 묶여 있는 셈이다.

## fetcher는 서버 액션으로 — 조회와 갈린 이유

`getMyProfile`(조회)은 렌더 중 읽기만 해서 서버 액션이 아니라 그냥 서버 전용 모듈이었다. 반면 이번 `updateMyTeams`는 **버튼 클릭으로 클라이언트가 트리거하는 쓰기**라 서버 액션(`"use server"`)이 맞다. 서버 액션은 "클라에서 부를 수 있는 서버 함수"를 만들어주는 장치라, 브라우저는 폼 데이터를 Next 서버로 POST하고, 실제 BE PATCH·access 쿠키 읽기·Bearer 실어보내기는 전부 서버에서 돈다. 그래서 브라우저 네트워크 탭엔 `localhost:8080`으로 가는 PATCH가 안 보인다 — 검증할 때 이걸 착각하면 안 된다. 서버 액션이라 `submitOnboarding`이 사는 `_lib/api/users.ts`에 나란히 뒀다.

성공하면 액션이 `redirect("/me")`로 마이페이지에 되돌린다. 이건 리로드가 아니라 소프트 내비게이션이고, 서버 컴포넌트인 `/me`가 다시 렌더되며 `getMyProfile`을 새로 부른다. 그 fetcher가 `cache: "no-store"`라 방금 바꾼 팀이 곧바로 반영돼 나온다 — 낙관적 업데이트나 캐시 무효화를 손으로 안 해도 화면이 최신이다. 이게 서버 fetch만 쓰는 지금 구조의 공짜 이득이라, 이 화면엔 TanStack Query가 필요 없다(단발 쓰기 + 리다이렉트로 끝, 클라에서 이어지는 게 없다 — 스킬 §0 표의 "서버 fetch가 기본").

401(토큰 무효)이면 로그인으로 보낸다. 프로필 수정은 세션 없이 성립하지 않는 화면이라 조회 때와 같은 판단이다. 그 밖의 실패는 인라인 에러 문구로 돌린다("저장에 실패했어요") — 온보딩 2단계가 쓰던 `role="alert"` 문구 자리를 그대로 가져왔다.

## 화면 쪽 — 단일에서 다중으로, 상태를 부모로

수정 화면의 `TeamPicker`는 원래 `useTeamSelection` 훅으로 **팀 하나만** 고르는 단일 선택이었다(ADR 0025에서 "다중 편집은 PATCH 티켓으로 미룬다"고 남겨둔 자리). 응원팀은 애초에 다중이니 이번에 다중 토글로 바꿨다. 그러면서 선택 상태를 어디에 둘지가 걸렸는데, 저장 버튼이 그 값을 읽어 서버 액션에 넘겨야 해서 **상태를 부모로 끌어올렸다**. 새로 만든 `ProfileEditForm`(클라 컴포넌트)이 `teams` 배열과 저장 로직을 들고, `TeamPicker`는 `selected`/`onToggle`만 받는 제어형이 됐다. 온보딩 2단계 `TeamStep`이 `TeamSelectGrid`를 제어하는 것과 똑같은 모양이다.

`page.tsx`(서버 컴포넌트)는 `getMyProfile`로 받은 `myTeams` 배열을 `ProfileEditForm`에 초깃값으로 넘기고 빠진다. 서버가 데이터 받아 클라 폼에 심고, 폼이 편집·제출을 담당하는 경계가 깔끔하게 나뉜다.

훅으로 쓰던 `useTeamSelection`은 이제 아무도 안 쓴다(마지막 소비자였던 단일 `TeamPicker`가 사라졌다). 남겨두면 죽은 코드라 파일째 지웠다.

## 공용화는 안 했다

web에도 프로필 수정 화면이 있지만(ADR 0013) 아직 PATCH를 안 붙였고, 애초에 `FavoriteTeamPicker`를 웹 로컬로 따로 둔 화면이다. 이 PATCH fetcher·제어형 피커는 **모바일 첫 구현**이니 스킬 §3-3대로 앱별로 둔다. 웹이 같은 엔드포인트를 붙일 때 `updateMyTeams`가 같은 shape면 그때 `@plick/core` 승격을 게이트로 판단하면 된다. 첫 앱에서 미리 빼지 않는다.

## 검증

로컬 BE + 공유 DB에 일회용 테스트 유저(초기 팀 리버풀)를 만들어 JWT를 민팅해 실제 플로우를 밟았다. curl로 계약부터 확인(팀 교체·빈 배열 비우기 둘 다 응답·DB 일치)한 뒤, 브라우저로 `/me/edit`에 쿠키를 심고 UI로 다시 밟았다: 리버풀 하나가 accent로 선택돼 뜨는 초깃값 → 리버풀 해제하고 맨유·첼시 다중 선택 → 저장 → `/me`로 리다이렉트되며 응원팀 카드에 두 팀이 바로 반영(DB도 MUN·CHE 2행) → 다시 들어가 전부 해제하고 저장 → "아직 응원팀이 없어요" + DB 0행. 에러 상태(BE 다운)는 공유 BE를 죽이는 게 부담스러워 라이브로는 안 밟았고, 온보딩 저장에서 이미 검증된 try/catch + 인라인 alert 패턴을 그대로 복사한 거라 코드 리뷰로 갈음했다. 테스트 유저는 삭제했다. check-types·lint·format:check·mobile 클린 빌드 통과.

## 후속 — 이메일 숨김 + 닉네임 변경 인풋 (같은 세션)

연동을 보고 피드백 둘을 이어 반영했다. 첫째, 이메일이 없는 유저(카카오 가입이면 실제로 null이다)는 정보 카드에 "미등록" 같은 자리표시를 두지 말고 **행 자체를 숨기자**는 것. `InfoCard`에서 이메일 행과 그 위 구분선을 `email &&`로 묶어, 없으면 카드가 닉네임 한 줄로 깔끔하게 접히게 했다. 실제로 이메일을 null로 바꾼 테스트 유저로 카드가 한 줄로 줄어드는 것까지 확인했다.

둘째, 닉네임을 바꿀 수 있는 인풋을 따로 달자는 것. 닉네임 자체는 정보 카드에 그대로 보이니, 변경 인풋은 그 아래 별도 섹션(`NicknameEditField`)으로 뒀다 — "새 닉네임" 플레이스홀더로 **빈 값에서 시작**하고(현재 값은 이미 위에 보이므로 프리필하면 카운터가 중복돼 어색하다), 오른쪽에 중복확인 버튼을 붙였다. 다만 **아직 껍데기다.** 입력값은 로컬 `useState`로만 들고, 중복확인·저장은 BE 연동 티켓에서 채운다. BE 닉네임 변경은 7일 제한(409)이 있어(스웨거) 그 에러 처리를 그때 같이 봐야 하고, 지금 PATCH 요청 body에도 `nickname`은 안 싣는다. 라벨 옆에 "7일마다 한 번 바꿀 수 있어요"를 미리 적어 그 제약을 노출만 해뒀다. 다크·라이트 둘 다 토큰 자동 전환으로 확인.
