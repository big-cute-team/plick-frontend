# 첫 투표의 의견 작성과 게스트 예측

2026-11-02, KAN-705. 웹과 모바일에서 첫 투표 뒤 댓글 작성을 유도하고, 게스트도 예측과 의견을 작성한 다음 계정 연동 안내를 받도록 바꿨다. 작업 브랜치는 `codex/KAN-705-vote-opinion-guest-prediction`이다.

## 투표 성공과 댓글 작성을 나눴다

투표와 댓글은 서버에서 서로 다른 요청이다. 첫 투표가 끝나기 전에 댓글을 보내면 KAN-704의 참여 확인에서 거절된다. 기존 투표 훅의 성공 처리에서 요청 전 투표가 없었는지를 확인하고, 처음 성공한 경우에만 의견 작성 창을 열었다. 낙관적으로 선택지를 표시하는 순간에는 창을 열지 않는다. 이미 참여한 사람이 선택을 바꿀 때도 다시 열지 않는다.

의견 창은 본문과 같은 투표 훅과 캐시를 사용한다. 창 안에서 선택을 바꾸면 본문의 선택도 바뀌고, 실패하면 둘 다 이전 선택으로 돌아간다. 변경 요청 중에는 댓글 제출을 막아 투표 확정 후 댓글을 저장하도록 했다. 의견은 기존 기사 댓글 API로 저장하므로 별도의 의견 데이터 모델을 만들지 않았다. 창을 닫으면 투표는 유지된다. 사용자는 의견이 선택 사항이며 건너뛰어도 투표를 유지하는 정책을 확인했다.

댓글 작성 성공 때는 진행 중인 옛 목록 요청을 취소한 다음 새 댓글을 캐시에 넣는다. 먼저 시작된 목록 요청이 늦게 도착해 새 댓글을 지우는 일을 막기 위해서다. 홈과 VS 대표 의견도 새 댓글을 반영하도록 투표 목록을 무효화한다.

## 게스트 안내는 저장 성공 뒤로 옮겼다

기존에는 작성 버튼을 누르면 게스트를 계정 연동 화면으로 보냈다. 이제 작성 화면은 바로 열고, 제출할 때 세션이 없으면 기존 게스트 발급 절차를 기다린다. 저장 성공 후에만 계정 연동 안내를 띄운다. 안내를 닫아도 저장한 예측은 그대로 남고, 다른 경기의 예측을 제출하면 안내가 다시 나온다. 수정 제출도 게스트인 동안은 같은 안내를 받는다.

제출할 때 처음 게스트를 발급받는 경우도 있다. 클릭 당시 React 상태는 비로그인이어도 응답이 올 때는 게스트이므로, 성공 콜백에서 현재 세션 표식을 읽어 안내 여부를 정한다. 표식은 화면 안내에만 쓰고 실제 권한 판단은 서버가 한다. 저장 전 시작된 요약 조회도 취소해 옛 응답이 저장 결과를 덮지 않게 했다.

연동 안내는 기록과 적중률, 시즌 랭킹을 소개하되 이번 기록의 이전을 무조건 보장하지 않는다. 백엔드는 신규 소셜 연결에서는 게스트 사용자 ID를 유지하지만, 이미 가입한 소셜 계정으로 로그인하면 기존 계정으로 전환하고 게스트 이력을 합치지 않기 때문이다.

## 백엔드 계약 확인

API 연동 스킬에 따라 별도 검증 에이전트가 `/Users/dowankim/Documents/plick-backend`의 최신 코드 `089b538`을 확인했다. KAN-704는 반영돼 있지만 `SecurityConfig.java`에서 예측 PUT/DELETE는 여전히 `hasRole("USER")`였다. 이 버전은 게스트 예측에 `403 AUTH_GUEST_FORBIDDEN`을 돌려준다. 예측 입력 계약 자체는 기존과 같은 `{ pick, opinion }`이며 의견은 5~300자다. 투표 댓글은 1~500자다.

localhost:8080 백엔드는 실행 중이지 않아 실제 요청과 DB 검증은 하지 못했다. 프론트 구현과 실제 게스트 예측 연동 완료를 구분한다. 권한 변경 여부와 대상 백엔드에 대해 사용자에게 확인을 요청했다.

## 화면 검증에서 발견한 댓글 수

처음에는 새 댓글 본문이 바로 보이는데 헤더는 계속 0이었다. 기존 헤더는 기사와 릴 각각의 로컬 증가분만 세고 있었고, 투표 의견 창에서 저장한 댓글은 그 콜백에 닿지 않았다. 기사 ID별 댓글 수를 쿼리 캐시에 두고 작성·삭제 훅이 성공 때 한 번씩 갱신하게 바꿨다. 기사·릴 헤더의 로컬 증가분은 제거해 일반 댓글과 답글이 두 번 세어지지 않게 했다. 수를 아직 모르면 임의로 0에서 시작하지 않고 기존 스냅샷을 받는 헤더가 초기값을 만든다.

댓글 목록의 첫 조회가 끝나기 전에 새 의견을 저장하는 경우도 고려했다. 취소할 옛 조회는 있어도 캐시 페이지가 아직 없을 수 있다. 이때 댓글 한 개만 있는 가짜 마지막 페이지를 만들면 기존 댓글이 보이지 않으므로, 데이터가 없을 때는 조회를 다시 시작한다. 이미 새 댓글을 포함한 응답을 받은 경우에는 같은 ID를 제거한 뒤 앞에 넣어 중복 표시를 막았다.

## 검증 범위와 한계

타입 검사와 린트, 전체 포맷 검사, 단위 테스트 286개와 훅 테스트 40개가 통과했다. 웹과 모바일의 production build도 성공했다. 다만 빌드 당시 로컬 환경변수가 가리키는 8082 백엔드는 실행 중이 아니어서 정적 데이터 조회는 ECONNREFUSED와 기존 대체 경로를 탔다. 빌드 성공을 실제 API 연동 성공으로 보지 않는다.

기존 3030·3031 개발 서버를 유지하기 위해 임시 디렉터리에 앱 복사본과 테스트용 화면을 만들었다. 첫 시도는 Turbopack이 복사본 밖의 node_modules 심링크를 거절했고, Webpack 모드로 바꿔 확인했다. 격리 복사본에서는 메트릭 수집 instrumentation을 비우고 루프백 주소의 개발 리소스 접근을 허용했다. 원본 앱의 서버·보안 설정은 바꾸지 않았다. 테스트 화면은 실제 컴포넌트와 서버 액션을 사용하되, 데이터는 임시 Node 모의 서버가 확인한 API 모양으로 응답했다. 검증용 경로는 원본 저장소에서 제거했다.

390px 모바일과 1280px 웹에서 첫 투표 성공 후 팝업, 팝업 안 선택 변경과 본문 동기화, 의견 저장 뒤 댓글 표시를 확인했다. 모바일에서는 서버가 의견 저장을 거절했을 때 입력이 남는지와 이후 성공하는지도 확인했다. 저장 뒤 본문에서 다시 투표를 바꾸면 팝업이 다시 뜨지 않았다. 댓글 수 수정 후 웹에서 새 의견 한 개를 등록하자 헤더도 0에서 1로 바뀌었다.

게스트의 예측 작성 진입과 저장 성공 후 연동 안내를 양쪽에서 확인했다. 모바일에서는 두 번째 경기에도 예측을 제출해 안내가 다시 나오는 것을 확인했다. 웹에서는 모의 서버가 마감 오류를 돌려줄 때 성공 안내 없이 오류 문구가 나오는 것을 확인했다. 실제 백엔드의 게스트 권한 변경과 저장·계정 연동까지의 검증은 아직 남아 있다.

댓글 수 구독에는 실제 조회 API가 없어 `skipToken`을 넣었다. 이를 넣지 않았을 때의 queryFn 누락 경고를 없앴고, 타입이 `number | undefined`로 좁혀지는 과정에서 발견한 오류는 초기 스냅샷을 대체값으로 쓰게 고쳤다. 수정 후 타입 검사와 양쪽 빌드를 다시 통과했다. 검증용 서버는 종료했고 기존 개발 서버는 유지했다.

## 참여하기도 같은 팝업으로 연결했다

사용자가 데브 화면의 참여하기 버튼과 의견 팝업을 확인했다. 당시 KAN-705는 아직 로컬 변경이라 데브에는 이전의 스크롤 이동 동작이 남아 있었다. 실제 데브 기사 8784에서 버튼을 눌러 투표 선택지로 포커스가 이동하는 것을 확인했다. 사용자는 스크롤 이동 대신 팝업 안에서 투표하고 의견까지 작성하기를 원했다.

댓글 잠금 영역과 투표 카드는 서로 다른 컴포넌트에 있으므로, 앱별 Zustand 스토어에 현재 작성할 기사 ID를 두었다. 참여하기가 이 ID를 설정하면 기존 투표 카드가 같은 의견 창을 연다. 투표 저장 성공 뒤에도 같은 스토어를 사용한다. 카드가 사라질 때 자신의 창만 정리하며, 요청 도중 다른 화면으로 이동했으면 뒤늦은 성공 응답으로 팝업을 다시 열지 않는다.

참여 전에는 먼저 선택하라는 제목을 보여주고, 의견을 미리 적어도 투표가 성공하기 전에는 의견 등록 버튼을 잠근다. 팝업에서 선택하면 기존 투표 요청을 보내 본문과 같은 선택·집계를 반영한다. 첫 투표 성공 뒤에는 창을 다시 만들지 않고 제목과 안내만 의견 작성 상태로 바꿔 이미 적은 글을 유지한다. 나중에를 누르면 의견 없이 투표만 남는다.

모바일에서는 참여하기로 팝업 진입, 미투표 의견 제출 차단, 팝업 내부 투표, 나중에로 닫은 뒤 투표 유지를 확인했다. 웹에서는 참여하기에서 시작해 투표와 의견 등록을 완료했고 본문 선택과 댓글 수 1이 함께 반영됐다.

사용자가 함께 보낸 503은 게스트 예측 403과 다른 오류였다. `503 /api/v1/debates/68/vote`는 정상 오류 JSON의 메시지를 얻지 못했을 때 프론트 fetcher가 만든 대체 문구다. 같은 시점에 데브 모바일 헬스체크와 양쪽 투표 목록 GET은 200이었다. 투표 요청 당시 서버·로드밸런서 로그까지 확인한 것은 아니므로, 일시적 업스트림 장애 가능성만 남기고 원인을 확정하지 않았다. 실제 데브 투표를 대신 실행해 사용자의 선택을 바꾸지는 않았다.

## 푸시 전 리뷰

헤드리스 리뷰에서 치명적 지적은 없었다. 웹 댓글 훅에만 첫 목록 재조회 처리가 빠진 점을 발견해 모바일과 동일하게 보완했다. 댓글 수 캐시는 서버 스냅샷보다 로컬 작성·삭제 결과를 우선하므로 캐시가 살아 있는 동안 다른 사용자의 변경이 늦게 보일 수 있다. 서버 스냅샷의 갱신 시점을 구분하는 후속 처리가 필요하다.

현재 투표 카드 호출부는 기사 상세와 열린 릴 상세에 하나씩 있다. 같은 기사의 카드를 한 화면에 여러 개 배치하게 되면 기사 ID만으로 팝업을 여는 구조를 소유 카드 ID 또는 공용 팝업 호스트로 바꿔야 한다. 게스트 예측의 백엔드 권한 변경과 실제 연동 검증도 머지 전에 확인해야 한다.
