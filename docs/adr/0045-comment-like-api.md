# 0045 — 댓글 좋아요 API 연결 (KAN-309)

- 상태: Accepted
- 날짜: 2026-07-27
- 범위: `apps/mobile`. 댓글·대댓글 좋아요 등록·취소(`POST`·`DELETE /api/v1/comments/{commentId}/like`)를
  기사 세부와 릴 세부 시트의 댓글 목록에 붙인다. 댓글 조회에 토큰을 실어 `likedByMe`를 살리는 일,
  기사 좋아요 훅에서 공통 뼈대를 떼어내는 리팩터, 로그아웃 후 남의 좋아요 상태가 보이던 버그 수정까지.
- 관련: [ADR 0044 기사 좋아요 API](0044-article-like-api.md) · [ADR 0042 댓글 API](0042-comments-api.md) ·
  [ADR 0011 공용 경계](0011-shared-code-boundary.md) · `api-integration` 스킬

---

## 이번엔 티켓이 맞았다

바로 전 티켓(KAN-308)은 제목의 메서드가 틀려서 한참 헤맸다. 이번에도 `be-verify` 서브에이전트에
계약 확인을 먼저 맡겼는데, 다행히 `POST`와 `DELETE`가 실제와 맞았다.

응답은 봉투를 벗기면 `{ "likeCount": 2 }` 하나다. 기사 좋아요와 완전히 같은 모양이고, 멱등인 것도
같다. 이미 누른 댓글에 POST를 또 보내도, 안 누른 댓글에 DELETE를 보내도 409가 아니라 200에 현재
카운트가 온다. 그래서 중복 상태 분기를 만들 필요가 없다.

에러는 이렇게 온다.

- 토큰 없음 → 401 `AUTH_REQUIRED`
- 없는 댓글 → 404 `COMMENT_NOT_FOUND`
- 숫자가 아닌 id → 400 `COMMON_INVALID_PARAM`

스웨거에는 200 응답만 적혀 있고 401·404·400 정의가 아예 없다. 에러 body 스키마도 components에 없다.
이번에도 문서보다 실제로 때려 본 결과가 계약이었다.

하나 눈에 걸린 건 소프트 삭제된 댓글이다. BE는 삭제된 댓글에 좋아요를 눌러도 404가 아니라 200으로
받아 준다. 막아 주지 않는다는 뜻이라 화면이 알아서 좋아요 버튼을 안 그려야 한다. 마침 `CommentThread`가
tombstone(삭제 흔적만 남은 댓글)이면 본문 자리에 안내 문구만 남기고 액션 줄을 통째로 감추고 있어서
따로 손댈 게 없었다. 원래 그렇게 짜여 있던 게 여기서 값을 했다.

대댓글도 완전히 같다. 조회 응답에서 대댓글이 부모의 `replies`에 인라인으로 딸려 올 뿐, 좋아요는 같은
엔드포인트에 같은 필드다. 그래서 원 댓글과 대댓글이 같은 컴포넌트, 같은 뮤테이션을 그대로 쓴다.

## 훅을 하나 더 만들지 않고 뼈대를 떼어냈다

기사 좋아요(`useArticleLike`)를 짤 때 낙관적 갱신과 롤백, 로그인 유도까지 45줄 남짓을 꽤 조심스럽게
짰다. 댓글도 눌렀을 때 할 일이 똑같은데, 그걸 복붙하고 서버 액션만 바꾸는 건 내키지 않았다. 롤백
컨텍스트를 쓰는 부분처럼 한 번 틀렸던 대목이 두 벌로 갈라지면 다음에 고칠 때 한쪽만 고치게 된다.

그래서 공통 부분을 `useLikeToggle`로 떼어냈다. 서버 액션 호출을 함수로 받는다.

```ts
useLikeToggle({
  toggle: (liked) => (liked ? likeComment(id) : unlikeComment(id)),
  state,
  onChange,
});
```

`useArticleLike`는 기사 액션을 물리는 얇은 껍데기가 됐고, `useCommentLike`가 댓글 액션을 물린다.
호출부 둘(릴스 액션 레일, 기사 세부 버튼)은 시그니처가 그대로라 손대지 않았다.

같이 옮긴 게 하나 더 있다. `LikeState`는 `useArticleLike.ts` 안에 있었고 `ToggleLikeResult`는
`_types/articles.ts`에 있었는데, 댓글이 두 번째 사용처가 되면서 둘 다 `_types/likes.ts`로 모았다.
기사와 댓글은 엔드포인트만 다르고 계약이 같아서 도메인별로 쪼갤 이유가 없다. 타입을 훅 파일에서
export하고 있던 것도 원래 컨벤션에 어긋났으니 겸사겸사 정리했다.

## 원본이 캐시 하나뿐이라 오히려 단순했다

기사 좋아요에서는 상태의 원본이 화면마다 달라서 고생했다. 릴스는 무한 쿼리 캐시가 원본이고 기사
세부는 서버가 준 props가 원본이라, 훅이 자기 state를 들면 둘 중 하나가 어긋났다. 그래서 `onChange`로
호출부에 되돌려주는 모양이 됐다.

댓글은 그 점이 편했다. 기사 세부든 릴 시트든 댓글 목록은 결국 같은 쿼리키(`comments/list/{articleId}`)
하나를 본다. 기사 세부는 서버가 첫 페이지를 씨앗으로 심어 주고 릴 시트는 클라에서 처음 받는 차이만
있을 뿐, 화면에 그려지는 원본은 무한 쿼리 캐시다. 그래서 `useCommentLike`는 캐시만 고치면 된다.

한 가지 신경 쓴 건 대댓글의 자리다. 대댓글은 최상위 배열에 없고 부모의 `replies` 안에 있어서, 캐시를
훑을 때 항목마다 자기 자신과 답글을 함께 봐야 한다.

```ts
function applyLike(item, commentId, next) {
  if (item.id === commentId) return { ...item, ...next };

  const replies = item.replies.map((reply) =>
    reply.id === commentId ? { ...reply, ...next } : reply,
  );
  return replies.some((reply, i) => reply !== item.replies[i])
    ? { ...item, replies }
    : item;
}
```

재귀로 내려가지 않고 2단에서 멈춘다. 계약상 대댓글의 `replies`는 항상 빈 배열이라(be-verify 확인)
더 내려갈 곳이 없다. 바뀐 게 없으면 원래 객체를 그대로 돌려주는 것도 일부러다. 매번 새 객체를 만들면
아무 관계 없는 댓글까지 리렌더 대상이 된다.

## 조회에 토큰을 실었다 — KAN-303에서 미뤄 둔 숙제

댓글 조회는 익명 허용 API다. 토큰을 실으면 `likedByMe`가 요청한 사람 기준으로 채워지고, 안 실으면
무조건 false로 온다. 카운트는 전역이라 토큰과 무관하게 실제 값이 온다.

KAN-303에서 댓글 목록을 붙일 때는 좋아요가 범위 밖이라 `likedByMe`를 쓸 데가 없었고, 그래서 일부러
토큰을 안 실었다. 그때 fetcher 주석에 "좋아요를 붙일 때 재검토한다"고 적어 뒀는데, 그 재검토 시점이
이번이다. 안 실으면 내가 누른 하트가 새로고침 한 번에 비어 버린다.

배관은 기사에서 한 것과 똑같다(ADR 0044). 같은 fetcher를 서버와 브라우저가 함께 부르는데 BE에 닿는
길이 달라서 토큰을 싣는 자리도 다르다.

- 서버 컴포넌트(기사 세부의 첫 페이지 씨앗)는 `getAccessToken()`으로 꺼내 `getComments(id, { accessToken })`로 넘긴다.
- 브라우저(릴 시트, 다음 페이지)는 HttpOnly 쿠키를 JS가 못 읽으므로 `proxy.ts`가 `/be` 요청에 Bearer를 심는다.

그래서 fetcher에는 `accessToken` 옵션만 하나 늘었다. 브라우저에서 부를 땐 아무것도 안 넘긴다.

## 로그아웃했는데 내가 누른 것처럼 보였다

여기가 이번에 제일 많이 배운 대목이다.

붙이고 나서 사용자가 이상한 걸 잡아 줬다. 로그인해서 댓글 좋아요를 누르고, 로그아웃한 다음, 그 기사에
다시 들어가니 하트가 초록색으로 채워진 채였다. 누르면 "로그인이 필요해요" 팝업이 뜨는데도 표시만은
내가 누른 상태였다.

### 재현이 안 됐다

원인을 찾으려면 먼저 재현부터 해야 하는데, 이게 몇 번을 밟아도 안 났다. 로그인 → 좋아요 → 로그아웃
→ 기사 진입까지 그대로 따라가도 하트가 얌전히 비어 있었다.

한참 뒤에야 알았다. 브라우저를 도구로 조작하다 보니 클릭 한 번에 몇 초씩 걸렸고, 그 사이에 증상이
저절로 사라지고 있었다. 댓글 목록 쿼리는 `gcTime`이 60초다(`FEED_FRESH_MS`). 화면을 떠나면 그 쿼리는
비활성이 되고 60초 뒤 캐시에서 수거된다. 내 재현은 매번 그 60초를 넘기고 있었던 것이다. 사용자는
사람 속도로 눌렀으니 60초 안에 들어갔고, 나는 도구 속도라 못 들어갔다. 버그가 시간 창을 갖고 있으면
"재현 안 됨"은 "버그 없음"이 아니라는 걸 새삼 배웠다.

### 캐시와 서버를 일부러 싸움 붙였다

로그아웃 흐름을 정확한 타이밍으로 밟는 걸 포기하고, 의심하던 메커니즘만 따로 떼어 확인하기로 했다.
가설은 이거였다. 화면이 서버가 새로 내려준 값이 아니라 브라우저 메모리에 남은 옛 값을 그리고 있다.

그러면 둘을 일부러 어긋나게 만들어서 어느 쪽이 이기는지 보면 된다.

1. 로그인 상태로 기사에 들어간다. 화면과 캐시 모두 `좋아요 함, 3`.
2. 화면은 그대로 둔 채 BE를 직접 때려서 좋아요를 취소한다. 이제 서버 진실은 `안 함, 2`.
3. 소프트 내비게이션으로 목록에 나갔다가 곧바로 다시 들어온다.

돌아온 화면은 여전히 초록 하트에 3이었다. 서버는 2라고 말하는데 화면은 3을 그린다. 캐시가 이겼다.
이걸로 메커니즘이 확정됐다.

### 왜 그런가

두 가지가 겹쳐 있었다.

하나, 로그아웃의 `redirect("/")`는 리로드가 아니다. 서버 액션 안에서 부르는 `redirect()`는 브라우저를
새로 띄우는 게 아니라 클라이언트 라우터가 화면만 갈아 끼우는 소프트 내비게이션이다. 문서가 다시
로드되지 않으니 자바스크립트 메모리에 있는 것은 전부 살아남는다. TanStack Query의 캐시가 딱 그 메모리다.
쿠키는 지워졌고 서버는 나를 비로그인으로 보는데, 브라우저 메모리에는 방금까지 로그인 상태로 받은
`likedByMe: true`가 그대로 앉아 있다.

둘, RQ는 캐시에 데이터가 있으면 `initialData`를 쓰지 않는다. 기사 세부는 서버가 첫 페이지를 미리 받아
씨앗으로 넘겨주는데, 그 씨앗은 "캐시가 비어 있을 때 채울 초기값"이지 "캐시를 덮어쓰는 최신값"이 아니다.
그래서 서버가 아무리 올바른 값을 내려보내도 캐시가 살아 있는 동안은 화면에 닿지 않는다.

그리고 60초가 지나 캐시가 수거되면 씨앗이 쓰이면서 저절로 정상으로 돌아온다. 증상이 시간이 지나면
사라지니 더 헷갈렸던 것이다.

### 고친 방법

로그아웃 버튼이 서버 액션을 부르기 직전에 쿼리 캐시를 통째로 비운다.

```ts
const confirm = () => {
  queryClient.clear();
  startTransition(() => logout());
};
```

키를 골라 지우지 않고 전부 비운 이유는, 이게 댓글만의 문제가 아니어서다. 릴스 피드에도 홈 피드에도
`liked`가 들어 있고 전부 같은 함정을 갖고 있다. 로그인 경계를 넘는 마당에 이전 사용자의 데이터를
메모리에 남겨 둘 이유가 하나도 없다.

고치고 나서 아까 그 방법으로 다시 확인했다. 서버 진실을 `안 함, 2`로 만들어 두고 로그아웃한 뒤 기사에
들어가니 하트가 비고 카운트도 2로 나왔다. 캐시가 아니라 서버 값이 그려진 것이다.

### 남겨 둔 구멍

로그인은 걱정이 없다. OAuth 콜백을 거치면서 문서가 새로 로드되니 캐시가 빈 채로 시작한다.

다만 세션이 만료돼 프록시가 `/login`으로 보내는 경로는 로그아웃 버튼을 안 거친다. 그 직후 60초 안에
둘러보면 같은 증상이 날 수 있다. 거기서 로그인을 하면 어차피 전체 로드가 일어나 정리되고, 로그인하지
않고 나가는 경우만 잠깐 어긋난다. 지금은 그대로 두고, 실제로 걸리면 그때 프록시가 쿠키를 지우는
자리에서 같이 처리한다.

더 근본적인 해법으로 쿼리키에 보는 사람(로그인 여부나 유저 id)을 넣는 방법도 생각했다. 그러면 익명
화면이 로그인 캐시를 아예 못 읽으니 로그아웃이든 만료든 한 번에 막힌다. 다만 댓글·릴스·피드의 키를
전부 손대야 하고 지금 문제는 로그아웃 한 곳에서 나므로, 후보로만 적어 둔다.

## 공용화는 하지 않았다

`@plick/domain`이나 `@plick/ui`로 올린 건 없다. web은 아직 댓글 API를 쓰지 않아 ADR 0011의 게이트
C(성숙도)가 서지 않는다. 앱 안에서 `useLikeToggle`을 뽑은 건 패키지 승격이 아니라 같은 앱 안의 중복
제거라 그 게이트와 무관하다.

## 검증

계약과 DB는 `be-verify`가 밟았다. 등록, 중복 등록, 취소, 중복 취소, 미인증, 없는 댓글, 잘못된 id,
대댓글, 소프트 삭제된 댓글까지 확인하고 `comment_likes` 테이블을 매 단계 대조했다. 만든 테스트 유저와
행은 전부 지웠다.

화면은 직접 밟았다.

- 비로그인으로 댓글 하트 → 요청 없이 로그인 팝업이 화면 전체를 덮는다.
- 로그인 후 원 댓글 좋아요 → 즉시 채워지고 2에서 3. BE 조회로 대조.
- 대댓글 좋아요 → 그 답글만 0에서 1로 바뀌고 형제 답글과 부모는 그대로. BE 대조.
- 다시 눌러 취소 → 1에서 0으로 복귀. BE 대조.
- 릴 세부 시트(클라에서 목록을 받는 경로)에서도 등록·취소가 같게 동작. BE 대조.
- 로그아웃 후 재진입 → 위의 캐시 버그가 재발하지 않음.

밟는 동안 만든 좋아요는 전부 되돌려 원래 카운트로 맞춰 놓았다. 공유 DB라 남기면 안 된다.
