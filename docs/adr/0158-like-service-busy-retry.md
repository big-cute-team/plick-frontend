# 0158. 백엔드 요청사항 반영: 좋아요 503 재시도와 게스트 댓글 좋아요

KAN-527. 2026-09-19.

## 무슨 일이었나

백엔드가 9월 15일과 16일에 끝낸 작업을 한 문서로 정리해서 넘겨줬다. 핫이슈 응답이 배열에서
`{ withImage, withoutImage }` 객체로 바뀐 것(KAN-487), 카드에 `summaryShort`가 붙은 것(KAN-503),
게스트 로그인(KAN-506), 그리고 18일에 갱신된 두 가지 — 게스트도 댓글 좋아요를 누를 수 있게 된
것과, 좋아요 쓰기에 상한이 생겨 503이 날 수 있게 된 것(KAN-526)이다. 티켓은 "이 문서 기반으로
프론트가 바꿔야 할 걸 다 반영하라"였다.

먼저 코드를 뒤져 봤다. 앞의 셋은 이미 들어가 있었다. 핫이슈 두 그룹은 KAN-514·KAN-525에서
`HomeScreen`이 `withImage`·`withoutImage`를 따로 받아 캐러셀과 텍스트 카드로 나눠 그리고 있고,
`summaryShort`는 `@plick/core`의 `articles.ts`가 매핑해서 `HotTextCard`·`NewsItem`·`PostListItem`이
있을 때만 깐다. 게스트 로그인은 ADR 0154에서 프록시 발급, `/auth/link` 연동, 403 분기, 마감
재발급까지 다 했다. 그러니 이번 세션에서 실제로 손댈 건 18일 갱신분 둘이었다.

## 게스트 댓글 좋아요는 고칠 게 없었다

문서는 "게스트 상태에서 댓글 좋아요 버튼을 막거나 연동 안내로 보낼 필요가 없다"고 했다. 혹시
프론트가 막고 있나 봤는데, 안 막고 있었다. `useLikeToggle`은 `isLoggedIn`(세션 유무)만 보고
요청을 보내고, 게스트도 세션이 있으니 그냥 통과한다. ADR 0154에서 "좋아요·투표·조회 기록은
아무것도 안 고쳐도 게스트에게 열렸다"고 적었던 그 구조 덕이다. 예전엔 BE가 403
`AUTH_GUEST_FORBIDDEN`으로 거절했고 그때는 프론트 `onError`가 `AUTH_REQUIRED`만 보고 있어서
팝업도 안 뜨고 하트만 도로 비었을 텐데, 이제 BE가 200을 주니 그 경로 자체가 사라졌다.

남은 건 주석 하나였다. `@plick/core`의 `needsSocialAccount()` 설명에 "댓글·댓글 좋아요·신고·채팅은
소셜 사용자 전용"이라고 적혀 있어서 댓글 좋아요를 뺐다. 코드는 그대로다 — 이 함수는 어떤 기능이
막히는지가 아니라 어떤 에러 코드가 연동 유도 팝업감인지를 판정하는 함수라, 댓글 좋아요가 열려도
바뀔 게 없다. 팝업 문구(`LoginPromptDialog`)는 처음부터 "댓글과 신고, 채팅"이라 맞았다.

## 좋아요 503: 어디서 어떻게 받을까

BE 쪽 사정은 이렇다. DB가 느려진 순간 같은 기사에 좋아요가 몰리면 쓰기가 커넥션 풀을 다 차지해
피드 읽기까지 멈추는 걸 로컬에서 재현했다고 한다(피드 4ms가 9초). 그래서 참여 쓰기(좋아요, 댓글
좋아요, 조회 기록)에 세마포어로 동시 실행 상한을 두고, 자리를 500ms 안에 못 얻으면 좋아요는 503
`COMMON_SERVICE_BUSY`로 빨리 실패시킨다. 조회 기록은 그냥 버리고 200을 준다. 카운트 증감은
레디스에 모았다가 1초마다 DB에 내린다.

프론트에 요구한 건 "낙관적으로 올려 둔 +1을 되돌리고 안내 뒤 다시 누르게 하거나, 1초쯤 뒤 한 번
자동 재시도한다. 로그인 화면으로 보내지 않는다"였다.

지금 좋아요 흐름을 다시 짚으면 이렇다. 하트를 누르면 `useLikeToggle`이 `onMutate`에서 즉시 하트를
채우고 카운트를 ±1 한다(낙관적 갱신). 그리고 서버 액션(`likeArticle`·`likeComment`)을 부른다.
서버 액션은 HttpOnly 쿠키의 access 토큰을 꺼내 BE에 `POST …/like`를 보내고, 실패면 `ApiError`의
status·code·message를 `{ ok: false, … }`로 돌려준다. 훅의 `mutationFn`은 그걸 다시 `ApiError`로
던지고, `onError`가 `onMutate` 때 찍어 둔 직전 값으로 되돌린다. 모바일은 그 뒤 `QueryProvider`의
`MutationCache.onError` 전역 안전망이 BE 메시지를 토스트로 띄운다(KAN-447). 웹은 토스트 없이
되돌리기만 한다.

그러니 503을 아무 처리 없이 두면 어떻게 되나 — 하트가 채워졌다가 곧 비고, 모바일이면 BE 문구
"지금은 처리할 수 없습니다. 잠시 후 다시 시도해 주세요."가 토스트로 뜬다. 로그인 화면으로 갈
일도 없다(`AUTH_REQUIRED`만 팝업으로 간다). 사실 "되돌리고 안내한다" 쪽 요구는 이미 맞춰져
있었다.

그래도 자동 재시도를 한 번 넣기로 했다. 이유는 이 503이 사용자 잘못이 아니라 서버가 잠깐
바쁜 것이고, BE 말로는 1초쯤 뒤면 대개 붙기 때문이다. 사용자가 토스트를 읽고 다시 누르는 것보다
그냥 1초 기다렸다 한 번 더 보내는 게 낫다. 되돌아가는 하트를 보여 줄 필요가 없다.

### 어디에 재시도를 둘까

세 자리를 놓고 봤다.

첫째, 서버 액션 안에서 `apiFetch`를 두 번 부르기. 클라 코드를 안 건드려서 간단해 보이지만, 서버
액션은 요청 하나가 Next 서버 프로세스에서 1초를 잡고 기다리는 꼴이 된다. 좋아요가 몰리는 순간에
Next 쪽 워커까지 같이 잡아 두는 건 BE가 풀려고 한 문제를 프론트 서버로 옮기는 셈이라 버렸다.

둘째, 훅의 `onError`에서 `mutate`를 다시 부르기. 이건 `onError`가 이미 롤백을 한 뒤라, 롤백 →
1초 → 다시 낙관적 갱신 → 성공, 이렇게 하트가 한 번 깜빡인다. 그리고 `onMutate`가 두 번 돌면서
"직전 값" 컨텍스트가 롤백된 값으로 새로 찍히는데, 두 번째마저 실패했을 때의 되돌릴 값이 헷갈린다.
버렸다.

셋째, TanStack Query 뮤테이션의 `retry`·`retryDelay` 옵션. 뮤테이션의 `retry`는 기본 0이라 지금까지
안 쓰고 있었는데, 함수형으로 주면 에러를 보고 재시도할지 정할 수 있다. 재시도는 `mutationFn`만
다시 부르고 `onMutate`·`onError`는 건드리지 않는다. 즉 낙관적 값이 그대로 남아 있고, `isPending`도
true라 그 사이 다시 누를 수 없고, 두 번째도 실패했을 때만 `onError`가 한 번 불려 처음에 찍어 둔
값으로 되돌린다. 원하던 동작 그대로라 이걸 골랐다.

```ts
retry: (failureCount, error) => failureCount < 1 && isServiceBusy(error),
retryDelay: SERVICE_BUSY_RETRY_DELAY_MS,
```

`failureCount`는 TanStack 내부(`retryer`)에서 실패 직후 증가시키기 전에 넘어온다. 첫 실패 때 0이고
그때만 true를 주니 딱 한 번 더 간다. 소스에서 `shouldRetry` 판정 순서를 직접 확인했다 — 판정 뒤에
`failureCount++`다.

### 무엇을 공용으로 뺐나

`isServiceBusy(error)`와 `SERVICE_BUSY_RETRY_DELAY_MS`는 `@plick/core`의 `client.ts`에 뒀다.
`needsSocialAccount()` 바로 옆이다. 모바일과 웹의 `useLikeToggle`이 둘 다 같은 판정을 하고
(ADR 0011 게이트 C, 두 번째 사용처가 처음부터 있다), 판정 근거가 BE 에러 코드라 fetch 래퍼
옆이 자리로 맞다. 재시도 간격 1초는 BE가 카운트를 1초 단위로 모아 내리는 주기이기도 하다.

`useLikeToggle`은 두 앱에 복제돼 있어(훅은 승격 후보 목록에 없다) 두 파일에 같은 두 줄을 넣었다.
`useArticleLike`·`useReelLike`·`useCommentLike`가 전부 이 훅을 물려 쓰니 좋아요 세 갈래가 한 번에
덮인다. `useDebateVote`도 같은 훅을 쓰는데, 투표 API는 상한 대상이 아니라 503이 올 일이 없고
와도 한 번 더 보내는 게 해가 아니라 예외를 두지 않았다.

두 번째도 실패하면 모바일은 전역 토스트가 BE 문구를 그대로 띄운다. 따로 문구를 만들지 않았다 —
BE가 이미 사용자용 문장을 보내 주고, 그걸 덮어쓰면 나중에 BE가 문구를 다듬어도 프론트가 옛 말을
한다. 웹은 전역 토스트가 없어 되돌리기만 한다(기존 정책 그대로). 웹에 토스트 인프라를 이번에
들이는 건 티켓 범위를 넘는다고 봤다.

## 검증하려고 BE부터 띄웠다

방금 pull한 BE에 KAN-526이 머지돼 있어 로컬에서 실물로 확인하기로 했다. 8080에는 아무것도 안
떠 있어서 8082에 새로 띄웠다. 503을 쉽게 재현하려고 `STATS_WRITE_PERMITS=1`, `STATS_WRITE_WAIT_MS=1`로
줬다. 자리가 하나뿐이고 1ms만 기다리니 동시 요청 두 건이면 하나는 바로 503이다.

그런데 부팅에서 죽었다. `Schema-validation: missing table [bot_comment_queue]`. BE는 `ddl-auto: validate`인데
마이그레이션 도구가 없어서, 스키마를 바꾸는 PR이 머지되면 공유 Supabase에 누군가 DDL을 손으로
넣어야 한다. 이번엔 봇 댓글 큐(KAN-513)와 이슈 묶음(KAN-519)의 테이블 셋이 빠져 있었다.
검증은 첫 번째 빠진 테이블에서 멈추므로 한 번에 다 찾으려고 `src/test/resources/schema.sql`의
`CREATE TABLE` 목록과 `pg_tables`를 `comm`으로 대조했다. 테이블은 `bot_comment_queue`, `stories`,
`story_articles` 셋, 컬럼은 차이가 없었다. 세 테이블의 DDL을 schema.sql에서 인덱스·코멘트까지
그대로 잘라 사용자 승인 아래 공유 DB에 넣었고(순서는 FK 때문에 stories → story_articles →
bot_comment_queue), 그 뒤 BE가 떴다.

## 검증

계약 확인은 `be-verify` 서브에이전트에 맡겼다. 8082에 게스트를 발급받아 댓글 좋아요를 눌러
보니 200에 `{ likeCount: 1 }`, 취소도 200이었다. 같은 게스트로 댓글 작성은 여전히 403
`AUTH_GUEST_FORBIDDEN`. 09-18 변경이 로컬 BE에 그대로 들어와 있었다.

503은 같은 게스트 토큰으로 기사 좋아요 `POST`를 동시에 20건 쏘니 19건이 503, 1건이 200이었다.
503 본문은 문서와 글자 단위로 같았다 — `{"code":"COMMON_SERVICE_BUSY","message":"지금은 처리할 수
없습니다. 잠시 후 다시 시도해 주세요.","data":null}`. 댓글 좋아요도 19대 1로 같았다. 반대로
1초 간격으로 한 건씩 보내면 10건 전부 200이라, "동시에 겹칠 때만 나고 한 박자 뒤 단건은 붙는다"는
BE 설명이 맞았다. 20건이 겹쳐도 `likes`엔 유저당 1행만 생겼다(멱등). 테스트 게스트와 좋아요는
전부 지웠다.

화면 쪽은 재시도가 실제로 한 번만, 1초 뒤에, 낙관적 값을 유지한 채로 도는지를 봐야 했다. 그런데
브라우저에서 하트 하나 누르는 건 단건이라 진짜 BE로는 503이 안 난다. 그래서 스크래치에 20줄짜리
프록시를 띄웠다. 8083으로 들어온 요청을 8082로 넘기되 좋아요 경로(`POST`·`DELETE …/like`)만
모드에 따라 503 봉투로 바꿔 준다. `once`는 경로별 첫 요청만 503, `always`는 전부 503이다.
모바일은 `API_BASE_URL=http://localhost:8083`으로 prod 빌드해서 `next start`로 띄웠다
(3031에 다른 세션의 `next dev`가 살아 있어 dev 잠금에 걸렸다. Next 16은 같은 디렉터리에 dev
서버를 하나만 허용한다).

`once` 모드에서 기사 좋아요를 누르니 프록시 로그에 `POST …/like -> 503` 다음 정확히 1.016초
뒤 `-> pass`가 찍혔고, 그 사이 하트는 채워진 채였다. 네트워크 탭에는 서버 액션 POST가 두 번
보인다 — 재시도가 서버 액션을 다시 부르는 것이라 그렇다. 끝나면 버튼이 `aria-pressed=true`,
카운트는 BE가 준 3이었다.

`always` 모드에서 취소를 누르니 0.3초 시점엔 낙관적으로 `좋아요 / 2`였다가, 503 두 번(1.014초
간격) 뒤 `좋아요 취소 / 3`으로 돌아오고 `role=status` 토스트에 BE 문구가 그대로 떠 있었다.
로그인 팝업(`role=dialog`)은 뜨지 않았다.

프록시를 끄고 게스트로 댓글 좋아요를 누르니 팝업 없이 `좋아요 취소 / 1`이 됐다. 게스트 댓글
좋아요가 화면에서도 그냥 된다.

검증 중 하나 눈에 띈 것. 브라우저에서 직접 나가는 조회 기록 `POST /be/api/v1/articles/8032/view`가
403이었다. 서버 액션이 아니라 클라 fetch라 `Origin: http://localhost:3013`이 실리는데, BE
`.env`의 `CORS_ALLOWED_ORIGINS`에 3013이 없어 CorsFilter가 거절한 것이다(ADR 0101과 같은 원인).
검증용 임시 포트라 BE 설정을 건드리지 않았고, 이번 티켓과는 무관하다.

## 남은 것

- 웹은 두 번째 503까지 실패하면 되돌리기만 하고 문구가 없다. 웹에 전역 에러 토스트를 들이는
  건 별도 작업이다.
- BE가 카운트를 1초 단위로 모아 내리므로, 취소 직후 1초 안에 다시 누르면 응답 `likeCount`가
  한 박자 전 값일 수 있다(be-verify에서 실제로 한 번 봤다). 응답값으로 덮는 지금 방식에선
  잠깐 숫자가 안 맞을 수 있는데, BE 문서가 "본인이 방금 누른 건 응답에 들어 있다"고 해서 일단
  그대로 둔다. 재현되면 따로 본다.
- 핫이슈 응답 모양 변경은 BE prod 릴리스와 프론트 배포를 같은 시점에 맞춰야 한다(문서 5절).
  프론트는 이미 새 모양만 읽으므로 BE보다 먼저 나가면 홈 핫이슈가 빈다.
- 검증 서버에 처음 들어갔을 때 공유 DB에 게스트가 셋 생겼다(같은 초에 만들어진 96·97·98).
  첫 진입에 RSC prefetch 여러 개가 쿠키 없이 동시에 나가고, 프록시가 요청마다 발급을 부르니
  응답 쿠키는 하나만 살아남고 나머지 둘은 고아가 된다. KAN-514 구조의 빈틈이라 별도 티켓감이다.
