# 0105. 릴스 딥링크 URL과 공유 링크 분기 (KAN-349)

## 시작하며

릴스에 공유 기능(KAN-312)을 붙일 때 한 가지 찜찜한 결정을 했었다. 릴스에서 공유 버튼을
눌러도 릴 주소가 아니라 기사 세부 주소(`/articles/{id}`)를 복사해 주는 것. 그때는 어쩔 수
없었다. 릴스는 커서 피드라 "특정 릴을 가리키는 주소"라는 게 아예 없었으니까. 피드 순서는
서버 커서가 정하고, 클라이언트는 그 순서대로 슬라이드를 넘길 뿐이라 15번째 릴에 도착한
상태를 URL로 표현할 방법이 없었다.

KAN-349가 그 전제를 없애는 티켓이다. BE가 릴스 딥링크 조회 API(KAN-407,
`GET /api/v1/reels/{articleSummaryId}`)를 만들어 줬고, 이걸로 `/reels/[postId]` 라우트를
신설해 공유 링크로 특정 릴에 바로 진입하게 한다. 여기에 사용자와 이야기하다 범위가 하나 더
얹혔다. 유튜브 쇼츠처럼 릴을 넘길 때마다 주소창도 따라 바뀌게 하자는 것. 릴마다 URL이
생기면 SEO 표면도 생긴다.

## URL과 화면 상태의 관계를 먼저 정리했다

작업 전에 사용자가 정확한 질문을 했다. "릴스를 넘기면서 URL이 변하지 않는데 어떻게 특정
아이디로 들어가는 게 가능하냐"는 것. 이 질문에 답하면서 구조가 명확해졌다.

URL은 입구에서 한 번만 쓰인다. `/reels/123`으로 들어오면 서버가 `GET /reels/123`을 불러
첫 페이지를 받고, 그걸 TanStack Query 캐시에 씨앗으로 심는다. 그 순간부터 URL의 역할은
끝이고, 스와이프는 Embla 캐러셀의 인덱스가 바뀌는 클라이언트 상태 변화일 뿐이다. 공유
버튼도 URL을 읽지 않는다. 각 `ReelItem`이 자기 릴의 데이터를 통째로 들고 있어서 `reel.id`로
주소를 조립하면 된다.

그러니까 "넘길 때마다 URL이 바뀌는" 쇼츠 동작은 이 위에 얹는 장식이다. 상태(지금 보는 릴)를
URL에 되비추는 것이고, 기능적으로는 없어도 공유가 된다. 대신 새로고침하면 보던 릴에서 다시
시작되고, 주소창을 복사해도 지금 릴이 공유된다는 UX가 생긴다. SEO는 이 동기화가 아니라
라우트 신설 쪽에서 나온다. 크롤러는 스와이프를 안 하니까, 서버 렌더로 릴의 제목·요약·OG가
HTML에 박혀 나오는 `/reels/{id}` 페이지의 존재와 그 URL들이 사이트맵에 실리는 게 전부다.

## canonical을 어디로 걸지 — 독립 랜딩으로

릴 하나의 콘텐츠 실체는 같은 `articleSummaryId`의 기사다. 릴은 그 기사의 요약을 풀스크린으로
보여주는 포맷이고, 기사 상세는 이미 KAN-346·351에서 SEO 작업이 다 돼 있다. 그래서
`/reels/{id}`의 canonical을 기사 상세로 몰아주는 안(중복 콘텐츠 회피, 신호 집중)과 릴 URL
자체를 독립 랜딩으로 키우는 안(쇼츠 모델)이 갈렸다.

사용자가 독립 랜딩을 골랐다. 그래서 데스크톱 web에도 `/reels/[postId]`를 같이 만들어
canonical 정본으로 삼고(모바일 릴 페이지는 기사 세부와 같은 규약으로 web 릴 URL을
canonical로 가리킨다), 사이트맵에도 릴 URL을 실었다. 기사 페이지와 내용이 겹쳐 신호가 나뉠
수 있다는 리스크는 알고 받아들인 결정이다.

## BE 계약 검증

구현 전에 be-verify 서브에이전트로 로컬 mock 프로필의 실계약을 확인했다. 티켓 댓글대로였고,
문서에 없던 디테일 두 개를 얻었다.

- 딥링크 엔드포인트도 `size`(1~30, 기본 10)를 받는다. 메타데이터 생성에는 앵커 한 장만
  필요해서 `size=1`로 가볍게 부를 수 있게 됐다.
- 커서에 모드가 있다. 디코드하면 피드 기본은 `v2|UNSEEN|…`, 딥링크가 주는 건
  `v2|CHRONO|…`다. 딥링크에서 이어보기하면 개인화 없이 순수 시간 내림차순이라 이미 본 릴도
  다시 나올 수 있다. FE는 불투명 문자열로 그대로 넘기면 되고 파싱할 일은 없지만, "딥링크
  이어보기와 탭 피드는 순서 규칙 자체가 다르다"는 건 캐시를 왜 분리해야 하는지의 근거가 됐다.

없는 id는 404 `ARTICLE_NOT_FOUND`, 정수가 아닌 id는 400 `COMMON_INVALID_PARAM`, 가장
오래된 릴로 들어가면 `items` 한 장에 `nextCursor: null`. 전부 실측으로 확인했다.

## 구현

### 앵커 모드 피드 — 쿼리키 분리가 핵심

`@plick/core`에 `getReelsFrom(postId)`를 추가하고(`reels.ts`, 기존 `getReels`와 같은 자리),
양 앱의 `useReelsFeed`에 `anchorId` 파라미터를 얹었다. 무한 쿼리에서 "커서가 없는 요청 =
첫 페이지"라는 성질을 그대로 써서, `pageParam`이 null이고 앵커가 있으면 `getReelsFrom`,
아니면 `getReels`를 부른다. 첫 페이지만 딥링크 엔드포인트로 받고 이후는 응답 커서로 기존
피드를 이어 가는 티켓 요구가 queryFn 분기 하나로 끝난다.

쿼리키는 `reelKeys.anchor(postId)`로 분리했다. `feed()`와 섞으면 탭 피드의 첫 페이지(최신순
머리)가 앵커 페이지로 바뀌어, 딥링크로 들어갔다가 탭으로 돌아오면 엉뚱한 릴부터 보인다.
KAN-404의 커서 400 리셋(`restartFeedQuery`)도 이 키를 따라가야 해서, 양 앱 컴포넌트의
복구 함수가 앵커 여부로 키를 고른다. 리셋 후 "첫 페이지 다시 받기"는 자연히
`GET /reels/{id}` 재호출이 된다 — queryFn 분기가 키가 아니라 pageParam을 보기 때문에 따로
처리할 게 없다.

### 라우트 — 기사 세부의 틀을 그대로

`/reels/[postId]/page.tsx`는 양 앱 모두 기사 세부(`/articles/[postId]`)의 검증된 틀을
따랐다. `generateMetadata`는 익명 `size=1` 호출로 앵커를 받아 제목·요약(160자 절단)·OG를
구성하고, OG 이미지는 릴과 기사가 같은 id 체계인 덕에 기존 동적 OG(`/articles/{id}/og`,
KAN-351)를 그대로 쓴다. 이미지 라우트를 새로 만들 필요가 없었다.

페이지 본문은 토큰을 실어 씨앗을 받고(`likedByMe`가 유저 기준으로 오는 KAN-308 규약),
`ARTICLE_NOT_FOUND`·`COMMON_INVALID_PARAM`이면 `notFound()`로 보낸다. 세그먼트별
`not-found.tsx`는 티켓 안내대로 "릴스 보러 가기" 버튼을 달았다. 그 외 실패(네트워크 순단)는
씨앗 없이 내려보내 클라가 다시 받는다 — 릴스 탭 페이지와 같은 태도다.

### URL 동기화 — router.replace가 아니라 history.replaceState

`useReelUrlSync(reelId)` 훅을 양 앱에 만들었다. 지금 보는 릴의 id가 바뀔 때마다
`window.history.replaceState(window.history.state, "", "/reels/{id}")`를 부른다. 짧지만
결정이 세 개 들어 있다.

첫째, `router.replace`를 쓰면 안 된다. 그건 소프트 내비게이션이라 딥링크 라우트를 실제로
마운트한다 — 릴 하나 넘길 때마다 피드 컴포넌트가 통째로 갈리고 서버 왕복이 생긴다. 네이티브
`history.replaceState`는 Next App Router가 가로채 `usePathname`만 동기화하고 라우트 트리는
건드리지 않는다(같은 전제를 ADR 0094의 뒤로가기 훅에서 실측했었다). 주소만 바뀌고 화면은
그대로다.

둘째, state를 null로 밀지 않고 `window.history.state`를 그대로 되넘긴다. 릴 세부 시트가
열려 있으면 히스토리 최상단이 `useBackToClose`가 쌓은 항목이고, 그 안의 표식
키(`plkBackToClose`)가 지워지면 시트 닫기 정리 단계의 `back()` 판정이 어긋난다. Next 내부
state(`__NA` 등)도 같은 이유로 보존해야 한다.

셋째, replace지 push가 아니다. 릴을 100장 넘겼다고 뒤로가기를 100번 눌러 되감게 하는 건
고문이다. 뒤로가기는 릴스에 들어오기 전 화면으로 나간다.

이 훅을 탭 피드에도 걸었다. 그래서 `/reels`로 들어가도 주소는 곧장 `/reels/{첫 릴}`이 되고,
새로고침하면 딥링크 라우트로 떨어져 보던 릴에서 다시 시작한다. 쇼츠가 정확히 이렇게 동작한다.

### 탭 피드와 딥링크의 뷰 상태 격리

모바일 캐러셀 훅(`useReelsCarousel`)은 보던 릴 순번을 zustand 뷰 상태 스토어에 남겨 탭으로
돌아올 때 복원한다(KAN-314). 딥링크 페이지가 이걸 같이 쓰면 두 가지가 깨진다. 진입 릴이
0번이어야 하는데 탭에서 보던 7번으로 시작해 버리고, 반대로 딥링크에서 넘긴 순번이 스토어에
쓰이면 탭 피드의 복원 자리가 오염된다 — 두 피드는 목록 자체가 다르다. 그래서 훅에 `remember`
플래그를 달아 딥링크에서는 읽지도 쓰지도 않게 했다.

`topTick`(탭 재탭 신호) 구독은 남겨 뒀다. 부작용으로, 딥링크 페이지에서 릴스 탭을 다시
누르면 최신 피드로 가는 게 아니라 앵커 릴(0번)로 되돌아간다. 주소가 같은 `/reels/{id}`
모양이라 탭바가 탭 피드와 딥링크 페이지를 pathname으로 구분할 수 없어서 생기는 한계인데,
"이 세션의 맨 위 = 진입 릴"이라는 해석도 성립해서 그대로 뒀다. 어긋난 동작이라기보다 결이
다른 동작이라고 판단했다.

### 공유 경로 전환, 그리고 web에 공유가 아예 없었다는 발견

모바일 `share.ts`의 `articleShareUrl`(릴에서도 기사 주소를 만들던 함수)을 경로 조립
(`articleSharePath`/`reelSharePath`)과 절대 주소 변환(`shareUrl`)으로 쪼갰다. `ShareDialog`는
`articleId` 대신 `path`를 받는 범용 팝업이 됐고, 기사 세부는 여전히 기사 경로를, 릴은 릴
경로를 넘긴다. KAN-312 때 "릴을 가리키는 주소가 없다"던 주석은 이 결정이 뒤집혔다는 기록으로
바꿔 달았다.

web을 검증하다가 사용자가 물었다. 왜 모바일은 공유가 눌리는데 웹은 안 눌리냐고. 답은
단순했다 — web 릴의 공유 버튼은 KAN-312 범위 밖이라 onClick 핸들러 없는 장식이었다. 티켓
완료 조건이 "공유 버튼이 `/reels/[postId]`를 생성"이니 이번에 같이 배선했다. 모바일의
`ShareDialog`·`useCopyLink`·share 유틸·상수·타입을 web에 이식하고(데스크톱이라
hover·focus-visible을 얹고, 안내 문구는 "길게 눌러"에서 "드래그해"로), `ReelActionRail`에
`onShare`를 뚫어 `ReelItem`이 팝업 상태를 소유하게 했다 — 레일이 데스크톱·모바일 뷰로 두 벌
붙는 구조라 좋아요 팝업과 같은 층이다. 같은 컴포넌트가 두 앱에 생겼으니 `@plick/ui` 승격
후보인데, 훅·상수와 얽혀 있고 앱별 스타일 차이가 있어 이번엔 ADR 0011 게이트를 넘기지 않고
후보로만 적어 둔다.

### 사이트맵

web 사이트맵의 기사 걷기 루프에서 `/reels/{id}`를 같은 걸음에 싣는다. 릴과 기사가 같은 id
체계라 목록을 따로 걸을 필요가 없다. 기사가 콘텐츠 정본이라 우선순위는 0.5로 기사(0.8)보다
낮췄고, 기사당 URL이 두 개가 됐으니 상한 판정 카운트도 URL 수 기준으로 바꿨다. 로컬 mock
기준으로 릴 URL 1,648건이 실렸다.

## 막힌 데와 삽질

JSX 주석을 표현식 괄호 안에 넣는 초보적인 파스 에러를 냈다. `{cond && (<Comp />)}`의 괄호
안은 JSX children이 아니라 표현식 자리라 `{/* */}`가 못 들어간다. 사용자가 dev 서버를 띄워
두고 있어서 빌드 에러로 바로 잡혔다 — 조건 블록 바깥으로 주석을 뺐다.

기사 세부 페이지의 공유·좋아요 버튼이 인앱 브라우저에서 안 눌리는 걸 발견하고 한참 팠다.
버튼 DOM에 React fiber 키가 아예 없었다(React가 그 노드를 소유하지 않는 상태). 내 변경이
의심돼 작업 전체를 stash하고 베이스라인에서 재현했는데 — 이 과정에서 stash가 tracked만
되돌리고 untracked 신규 라우트 파일은 남겨서, 새 파일이 사라진 export를 import하는 반쪽
상태가 되어 dev 서버가 잠깐 깨지는 소동도 있었다(`-u`로 다시 stash해서 해결) — 베이스라인에서도
완전히 동일했다. 즉 KAN-349와 무관한 기존 문제다. 콘솔의 "Encountered a script tag while
rendering React component" 에러로 보아 트윗 임베드의 script 태그가 히드레이션을 깨는 것으로
추정되고, 별도 태스크로 빼 뒀다.

검증 도구의 한계도 하나 다시 확인했다. 인앱 브라우저 패널이 접혀 있으면 `document.hidden`이
true고 레이아웃이 0으로 죽어서(clientHeight 0) 스크롤도 IntersectionObserver도 안 돈다.
스와이프에 따른 URL 변화는 결국 iOS 시뮬레이터에서 실제 제스처로 확인했다 —
`/reels/7806`으로 진입해 위로 스와이프하니 주소창이 `/reels/7844`(시간순 다음 릴)로 바뀌었다.
제스처·관찰자류 검증은 시뮬레이터라는 원칙을 재확인했다.

## 검증한 것

- 모바일 `/reels` 진입 → 주소가 즉시 `/reels/8032`(첫 릴)로 동기화
- 모바일 `/reels/7806` 딥링크 → 7806이 첫 화면, title·canonical(web 릴 URL)·og:image·
  og:description 모두 그 릴 기준으로 SSR
- 시뮬레이터 실스와이프 → 주소 `/reels/7806` → `/reels/7844` 변화
- 공유 팝업이 모바일·web 모두 `{origin}/reels/{id}` 생성
