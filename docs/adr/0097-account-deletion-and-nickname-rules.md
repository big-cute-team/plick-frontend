# 0097. 회원탈퇴 기능과 닉네임 규칙 강화 (KAN-391)

BE에서 계약 변경 안내가 두 건 왔다. 회원탈퇴 API(`DELETE /api/v1/users/me`)가 새로 생겼고(KAN-389),
닉네임 검증이 길이만 보던 것에서 허용 문자 화이트리스트 + 강화된 욕설 필터로 바뀌었다(KAN-390).
이번 세션에서 이 두 변경을 웹과 모바일 양쪽에 반영했다. FE 티켓은 KAN-391이다.

## 계약부터 다시 밟았다

안내 문서가 꽤 자세했지만 스킬 규칙대로 be-verify에게 로컬 BE를 실제로 때려 보게 했다.
결과는 문서와 정확히 일치했고, 문서에 없던 디테일도 몇 개 건졌다.

- 탈퇴는 행 삭제가 아니라 익명화다. DB 실측으로 `provider_id`가 `withdrawn:<userId>`로,
  `nickname`이 `탈퇴한사용자`로 바뀌고 `email`은 NULL, `favorite_teams` 자식 행은 전부 삭제된다.
  좋아요·댓글 기록은 남는다.
- 같은 토큰으로 두 번 DELETE해도 200이다(멱등). 토큰 없이 부르면 401 `AUTH_REQUIRED`.
- 탈퇴한 유저의 access 토큰으로 `GET /users/me`를 부르면 200이 나온다. 무상태 JWT라 서버가
  이미 발급된 토큰을 무효화할 수 없어서다. 응답은 익명화된 프로필이다. 그래서 "성공 응답 = 정상
  계정"이 아니고, FE가 탈퇴 직후 토큰을 지우는 게 계약의 일부다. 리프레시 재발급은 Redis에 토큰이
  살아 있어도 탈퇴자 판정으로 401 `AUTH_REFRESH_INVALID`를 준다. 즉 남은 access 토큰의 수명(최대
  1시간)이 노출의 상한이고, 그 이상 연장되지는 않는다.
- 닉네임 에러는 세 층이다. 형식(길이·허용문자) 위반은 400 `COMMON_INVALID_PARAM`, 금지어는
  400 `USER_NICKNAME_FORBIDDEN`, 형식은 통과했지만 중복·예약어·욕설 변형이면 200에
  `available: false`. 중복확인 API에서 형식 위반이 200이 아니라 400으로 온다는 게 중요했다 —
  클라 선검증 없이 입력을 그대로 보내면 에러 처리가 지저분해진다.
- 규칙 원천은 BE `NicknamePolicy`다. trim 후 1~12자, `[가-힣a-zA-Z0-9]+` 화이트리스트. 예약어는
  플릭·plick·admin·운영자·탈퇴한사용자 등 부분 일치.

여담으로 검증 도중 로컬 Redis(Docker)가 꺼져 있어 refresh가 500으로 죽는 상태였다. be-verify가
Docker와 `plick-redis` 컨테이너를 띄우고 진행했다.

## 닉네임 규칙: 상수를 domain으로 승격했다

기존 클라 검증은 사실상 `maxLength={10}` 하나였다. 문제가 둘이었는데, 10이라는 값 자체가 BE의
12와 어긋나 있었고(BE가 이번에 12자로 확정), 같은 값이 두 앱 `_constants/onboarding.ts`에 "수동
동기화" 주석과 함께 복제돼 있었다.

BE 검증값을 복사한 계약 상수이고 두 앱이 같은 모양으로 쓰므로 ADR 0011 게이트를 다 통과한다고
봤다. `NICKNAME_MAX_LENGTH = 12`와 `NICKNAME_PATTERN`(허용 문자 정규식, max에서 파생)을
`@plick/domain/constants`로 승격하고 앱 로컬 상수는 지웠다. `ONBOARDING_TOTAL_STEPS`는 앱
전용이라 남겼다.

### 선제 검사를 어디서 하나 — IME 조합 문제

BE 안내는 "입력 단계에서 정규식으로 선제 필터"를 권했다. 처음엔 입력 onChange에서 허용 문자 밖을
바로 지우거나 경고를 띄우는 걸 생각했는데, 한글 IME 조합을 생각하면 안 된다. "시"를 치는 중간엔
"ㅅ"이라는 자모 상태를 반드시 지나가는데, 자모는 허용 문자 밖이라 키 입력마다 검사하면 경고가
조합 중에 계속 깜빡이고, 문자를 지워버리는 방식이면 조합 자체가 깨진다.

그래서 판정 시점을 "중복확인 버튼을 누른 순간"으로 정했다. `useNicknameCheck.check()`가 서버
액션을 부르기 전에 `NICKNAME_PATTERN`으로 먼저 거르고, 걸리면 서버를 부르지 않고
`{ error: "닉네임은 한글·영문·숫자만 1~12자로 쓸 수 있어요" }`를 결과로 세팅한다. 기존 결과 표시
컴포넌트(`NicknameCheckNotice`)의 error 분기를 그대로 타므로 화면 코드는 안 바뀌었다. 훅이 두 앱에
복제돼 있어(앱 서버 액션에 묶여 승격 불가) 두 파일을 같은 모양으로 고쳤다.

정적 안내는 인풋 placeholder를 "한글·영문·숫자 1~12자"로 바꿔 해결했다(온보딩 양앱), 프로필
수정은 라벨 옆 캡션을 "한글·영문·숫자 1~12자 · 7일마다 한 번"으로 갱신했다. 이후 사용자 피드백으로
"공백 없이 써야 하고, ㅋㅋ처럼 자음·모음만으로는 지을 수 없어요" 한 줄을 프로필 수정 인풋 밑에
추가했다 — 허용 문자라는 표현만으론 공백·초성이 안 된다는 게 바로 안 와닿는다는 지적이었다.

버튼 문구도 후속 피드백으로 "중복확인"에서 "닉네임 검사"로 바꿨다. 버튼이 형식 검사까지 하게 되면서
중복확인이라는 이름이 실제 동작보다 좁아졌기 때문인데, 결과적으로 이름이 기능을 따라온 셈이다.

### 서버 우회 대비

클라 검사는 UX용이고 최종 판정은 서버라서, 우회 경로의 에러 처리도 같이 깔았다. `checkNickname`
서버 액션이 400 `COMMON_INVALID_PARAM`을 잡아 BE 메시지를 그대로 돌려주게 했고(기존엔 모든
에러가 "확인에 실패했어요"로 뭉개졌다), 온보딩 제출과 프로필 수정의 에러 코드 passthrough 목록에도
`COMMON_INVALID_PARAM`을 추가했다. BE 메시지가 이미 사용자용 한국어라 그대로 노출한다.

온보딩 라우트는 지금 `_onboarding`으로 잠들어 있지만(ADR 0094·0095) 코드는 살아 있어서 함께
고쳤다. 되살릴 때 이 부분을 다시 만질 필요가 없다.

## 회원탈퇴: 로그아웃의 쌍둥이인데 결정적으로 다른 데가 있다

탈퇴 흐름은 로그아웃(ADR 0020, KAN-300)과 거의 같은 모양이다. 클라 버튼 → 확인 팝업 → 서버
액션 → 쿠키 삭제 → 홈 redirect. 그래서 구현도 `LogoutButton`을 본떴다. 하지만 실패 처리가
정반대다.

로그아웃 액션은 BE 호출을 try/catch로 삼키고 무조건 쿠키를 지운다. 로그아웃을 못 하는 상태에
갇히는 게 최악이라서다. 탈퇴는 반대다. BE 호출이 실패했는데 쿠키만 지우면, 사용자는 탈퇴가 된 줄
알지만 계정은 멀쩡히 남는다. 그래서 `deleteAccount` 서버 액션은 성공했을 때만 쿠키를 지우고,
실패하면 `{ error }`를 값으로 돌려줘 팝업이 열린 채 에러 문구를 보여주고 다시 시도하게 했다.
(서버 액션이 throw한 에러는 프로덕션에서 메시지가 가려지므로 값으로 돌려주는 게 이 저장소의
뮤테이션 관용이다.)

액션 위치는 `auth.ts`가 아니라 `users.ts`로 정했다. 세션을 끝내는 동작이라 auth 같아 보이지만,
호출하는 리소스가 `/users/me`이고 온보딩·프로필 수정과 같은 파일에 있는 게 맞다고 봤다.

토큰 폐기가 계약의 일부라는 점은 위 검증 절에 쓴 대로다. `redirect()`가 try 밖에 있는 것도
의도다 — `redirect`는 내부적으로 throw라서 try 안에 두면 catch가 삼킨다.

### 화면 쪽 결정

버튼 배치는 요구대로 로그아웃 밑인데, 톤을 한 단계 낮췄다. 로그아웃과 같은 아웃라인 danger 버튼을
하나 더 쌓으면 화면에 위험 버튼이 두 개 나란히 서서 무게가 같아 보인다. 탈퇴는 가장 파괴적인
동작이라 오히려 눈에 덜 띄는 언더라인 텍스트 버튼(`text-caption text-text-4`)으로 두고, danger
톤은 확인 팝업의 확인 버튼에만 줬다.

팝업은 새로 만들지 않고 댓글 삭제 때 만든 `ConfirmDialog`(KAN-333)를 그대로 썼다. pending 잠금과
에러 문구를 팝업 안에 유지하는 props가 이미 있어서 정확히 필요한 API였다. 본문 문구는 BE 권장을
다듬어 "탈퇴하면 복구할 수 없어요. 작성한 댓글은 '탈퇴한사용자'로 남아요."로 했다 — 무엇이
지워지고 무엇이 남는지가 확인 팝업이 답해야 할 질문이라서다.

확인 직전에 `queryClient.clear()`를 부르는 것도 로그아웃과 같다(KAN-309). 서버 액션의
`redirect`는 리로드가 아니라 소프트 내비게이션이라 브라우저 메모리의 RQ 캐시가 살아남고, 거기엔
로그인 상태로 받은 유저별 값(`likedByMe`)이 들어 있다. 지우지 않으면 탈퇴 직후 익명 상태로 같은
글에 들어갔을 때 누르지도 않은 하트가 채워져 보인다.

웹은 같은 흐름에 hover·focus-visible만 얹었다. 헤더 드롭다운(`ProfileMenu`)에는 넣지 않았다 —
드롭다운에서 원클릭 거리로 둘 동작이 아니다.

## 규정 문서 세 벌을 같이 고쳤다

약관·개인정보처리방침·FAQ 본문은 `@plick/ui`(TermsBody·PrivacyPolicyBody·FaqBody)에 단일
출처로 있는데, 셋 다 "탈퇴는 운영자 이메일로 요청"이라고 안내하고 있었다. ADR 0080에 "앱 내 탈퇴
기능이 생기면 약관 9조와 방침 11절, FAQ 탈퇴 항목을 한 번에 고쳐야 한다"는 예고까지 있었다.
실제로 고쳐 보니 그 목록만으론 부족했고, 익명화 모델 때문에 방침 4절(보유기간)·5절(파기 절차)도
같이 손대야 했다.

- 약관 9조: 이메일 절차를 "MY 화면의 탈퇴하기 기능, 즉시 처리, 복구 불가"로 교체하고, 재가입이
  신규 가입이라는 항을 추가했다.
- 약관 7조(댓글): 탈퇴해도 댓글이 탈퇴한사용자 표시로 유지되고 탈퇴 후에는 수정·삭제할 수 없다는
  항을 넣었다. 남기기 싫은 댓글은 탈퇴 전에 지우라는 안내까지. 기존 문안은 "언제든지 수정·삭제할
  수 있다"고만 해서 탈퇴 후와 모순이 생길 뻔했다.
- 방침 4절·5절: "탈퇴 시 지체 없이 파기"가 이제 절반만 참이다. 식별자(소셜 계정 식별자·이메일·
  닉네임·응원팀)는 파기, 댓글은 작성자 연결을 끊는 익명처리로 유지라는 걸 구분해 적었다.
- 방침 11절: 탈퇴 행사 방법을 이메일에서 앱 내 기능으로 바꿨다.
- 부칙·14절: 시행일을 2026. 8. 13.로 올리고 직전 시행일과 변경 요지를 남겼다(기존 관례).
- FAQ 탈퇴 항목: 전면 재작성. 탈퇴 방법, 무엇이 지워지고 남는지, 재로그인이 신규 가입이라는 것까지.

## 검증

계약과 DB는 be-verify가 위에 쓴 대로 밟았고, 화면은 직접 밟았다. 로컬 OAuth 없이 검증하려고
be-verify가 만들어 준 일회용 유저의 토큰 쌍을 브라우저 쿠키로 심어 로그인 상태를 만들었다
(api-integration 스킬 §6 방식).

브라우저 패널에서 좌표 클릭이 30초 타임아웃으로 계속 죽는 문제를 또 만났다. KAN-330 때 기록된
함정(패널이 hidden이라 상호작용이 안 먹는다)인데, 이번엔 `javascript_tool`로 DOM에서 버튼을 찾아
`click()`을 직접 부르는 우회가 통했다. 하이드레이션 자체는 끝나 있어서 React 핸들러가 정상으로
돌았다. 그 방식으로 모바일 MY에서 탈퇴하기 → 팝업 문구 확인 → 확인 → 홈 리다이렉트 →
`document.cookie`에서 두 토큰 소멸까지 확인했고, DB 익명화는 be-verify가 재확인한 뒤 테스트
행을 정리했다. 웹도 같은 방식으로 밟았다.

사용자도 로컬에서 직접 탈퇴와 닉네임 검사를 확인해 줬다.

### 로컬 로그인이 안 되던 이유

검증 중에 사용자가 "로컬에서 로그인이 안 된다"고 했는데, 원인은 `apps/mobile`에 `.env.local`이
없던 것이었다. OAuth 클라이언트 ID가 env로 들어가는데 웹에만 파일이 있었다. 모바일 `.env.example`에
로컬 개발용 실제 값(client_id는 인가 URL에 노출되는 공개 식별자라 example에 커밋돼 있다)이 다
있어서 복사로 해결했다. 이미 떠 있던 dev 서버는 env 파일 이전에 시작된 프로세스라 재시작했다.

## 남긴 것

- 중복확인의 `available: false`는 중복인지 금지어인지 구분해 주지 않는다(BE 정책). 화면 문구도
  "이미 사용 중이거나 쓸 수 없는 닉네임이에요" 하나로 묶여 있는 기존 결정(ADR 0027)을 유지했다.
- `ConfirmDialog`가 이제 두 앱에서 각각 두 소비자(댓글 삭제, 회원탈퇴)를 가진다. 앱 간 승격
  (@plick/ui) 후보로 볼 수 있지만 이번 PR에서는 올리지 않았다 — ADR 0011 §7 열린 후보 목록감이다.
- 탈퇴한사용자가 작성자인 댓글의 표시가 FE에서 자연스러운지(아바타·작성자 스타일)는 이번 범위에서
  확인하지 않았다. 실제 탈퇴 데이터가 쌓이면 댓글 화면에서 한 번 볼 것.
