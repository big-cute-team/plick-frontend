# 0139. 카카오 로그인에 연령대·성별 추가 동의 붙이기 (KAN-476)

## 왜 이걸 했나

사용자 행동 분석을 하려면 최소한 "누가 보고 있나"를 알아야 하는데, 지금 PLick이 카카오에서 받아오는 건
이메일 하나뿐이었다. 연령대(`age_range`)와 성별(`gender`)을 받아두면 나중에 타겟 관심사 같은 걸
설계할 재료가 생긴다. BE 쪽 티켓(KAN-475)에서 카카오가 주는 두 값을 가입·로그인 때 저장하기로 했고,
프론트가 할 일은 카카오한테 그 두 항목을 달라고 요청하는 것 하나다.

작업 자체는 상수 한 줄짜리다. 그런데 "왜 한 줄인데 티켓이 따로 있나"가 이 ADR의 내용이다.
카카오 동의 항목은 개발자 콘솔 설정과 인가 요청 파라미터가 맞물려서 돌아가는데, 이게 직관과 다르게
움직이는 구석이 있다.

## 카카오 동의 항목이 움직이는 방식

카카오 개발자 콘솔에는 앱이 가져갈 수 있는 개인정보 항목 목록이 있다. 이메일, 프로필 닉네임,
연령대, 성별 같은 것들이고, 각각을 켜고 끌 수 있다. 켜면 "필수 동의"와 "선택 동의" 중에 고른다.

여기서 헷갈리는 게, 콘솔에서 항목을 켜는 것과 사용자가 실제로 동의한 것은 다른 상태라는 점이다.
동의는 사용자별로 카카오 서버에 기록돼 있다. 처음 로그인할 때 동의 화면을 보고 체크한 항목이
그 사람의 동의 기록이 된다. 그리고 그 기록은 한번 만들어지면 다시 묻지 않는다.

그래서 이런 일이 생긴다. 이미 PLick에 카카오로 가입한 사람은 "이메일만 동의"로 기록이 끝나 있다.
콘솔에서 연령대와 성별을 새로 켜도, 그 사람은 다음 로그인 때 동의 화면을 보지 않는다.
이미 동의 절차를 마쳤다고 카카오가 판단하기 때문이다. 결과적으로 기존 유저의 연령대·성별은
영원히 비어 있게 된다. 새로 가입하는 사람만 새 동의 화면을 보고, 기존 유저는 안 본다.

이걸 뚫는 게 인가 요청의 `scope` 파라미터다. 카카오 문서에서는 "추가 항목 동의 받기"라고 부른다.
인가 URL에 `scope=age_range,gender`를 붙이면 카카오는 "이 앱이 지금 이 항목들을 요구한다"로 읽고,
아직 동의 기록이 없는 항목에 대해 동의 화면을 다시 띄운다. 이미 동의한 항목이면 그냥 넘어간다.
즉 `scope`는 "이번 요청에서 동의를 확인할 항목 목록"이다.

용어를 하나 정리하고 가면, OAuth에서 `scope`는 원래 "이 토큰으로 무엇까지 할 수 있는가"를 적는
권한 범위다. 구글은 이걸 `openid email`처럼 URL 형태 권한 문자열로 쓴다. 카카오도 같은 파라미터
이름을 쓰지만 실제로는 동의 항목 ID 목록이고, 구분자가 공백이 아니라 쉼표다. 같은 이름인데 값의
문법이 다르니 구글 것을 보고 공백으로 이어 쓰면 안 된다.

## 이메일을 같이 적어야 했던 이유

티켓에는 `age_range,gender`를 추가한다고 적혀 있었는데, 그대로 넣으면 안 되겠다 싶은 지점이 있었다.
`scope`를 지정하면 카카오는 거기 적힌 항목만 동의 화면에 올린다. 아무것도 안 적었을 때는 콘솔에서
켜둔 항목 전부가 올라가는데, 적는 순간 그 목록이 내가 적은 것으로 대체된다. 빼는 게 아니라
덮어쓰는 쪽이다.

그러면 신규 가입자 입장에서 무슨 일이 생기냐면, 이메일 동의 화면을 아예 못 본다. 동의를 안 했으니
카카오 사용자 정보 API가 이메일을 안 준다. BE를 확인해 보니 `KakaoOAuthClient`가
`kakao_account.email`을 읽어서 `OAuthUserProfile`에 담고, 그게 `findOrSignUp`으로 들어간다.
email은 null 허용이라 가입이 터지지는 않지만, 이메일 없는 유저가 조용히 쌓인다. 지금 멀쩡히
받고 있는 걸 이번 변경의 부수 효과로 잃는 셈이라 그냥 넘길 수 없었다.

그래서 `account_email`을 같이 적었다. 최종 값은 이렇다.

```ts
KAKAO: {
  endpoint: "https://kauth.kakao.com/oauth/authorize",
  clientIdEnv: "KAKAO_CLIENT_ID",
  extraParams: {
    scope: "account_email,age_range,gender",
    prompt: "login",
  },
},
```

`account_email`은 카카오가 정한 항목 ID다. 이메일인데 `email`이 아니라 `account_email`인 건
카카오계정에 딸린 정보라는 뜻으로 접두어가 붙은 것이고, 사용자 정보 응답에서도
`kakao_account.email`처럼 한 겹 안에 들어 있다.

옆에 있는 `prompt: "login"`은 KAN-395에서 넣은 것으로, 카카오톡 세션이 살아 있어도 로그인 창을
다시 띄우는 값이다. 역할이 겹치지 않아 그대로 뒀다.

## 어디를 고쳤나

`apps/mobile/app/_constants/api.ts`와 `apps/web/app/_constants/api.ts` 두 군데다. 인증 상수는
ADR 0050에서 앱별 복제로 두기로 했고(수동 계약), 웹 파일 상단 주석에도 "두 앱을 같은 모양으로
동기화한다"고 적혀 있다. 그래서 같은 패치를 두 번 넣었다. 파일을 손으로 두 번 고치면 한쪽만
반영하는 실수가 나기 쉬워서, 두 파일에 같은 치환을 적용하고 치환 횟수가 정확히 1인지 단언하는
일회용 스크립트로 처리했다.

인가 URL을 조립하는 쪽은 건드릴 게 없었다. `_services/oauth.ts`의 `buildAuthorizeUrl`이
`...extraParams`로 통째로 펼쳐 넣기 때문에 키를 하나 늘리면 그대로 쿼리에 붙는다. 프로바이더별
차이를 전부 `extraParams`에 몰아둔 구조라(ADR 0022) 이번 같은 변경은 상수만 만지면 끝난다.

## 쉼표가 인코딩되는 문제를 한 번 의심했다

`URLSearchParams`는 쉼표를 `%2C`로 인코딩한다. 그러면 카카오가 받는 값이
`account_email%2Cage_range%2Cgender`가 되는 건데, 이게 쉼표 세 개짜리 목록으로 제대로 해석될지
확신이 안 섰다. 어떤 서버는 인코딩된 구분자를 안 풀고 통째로 하나의 값으로 보기도 한다.

그냥 조립 로직만 떼어서 노드로 찍어 봤다.

```
scope=account_email%2Cage_range%2Cgender
decoded scope: account_email,age_range,gender
```

퍼센트 디코딩은 표준 동작이라 받는 쪽에서 원래 쉼표로 돌아온다. 실제 카카오 인가 요청도
정상 처리되는 걸 뒤에서 확인했으니 기우였다. 그래도 구분자가 인코딩 대상인 문자일 때는
한 번 찍어 보고 가는 게 맞다고 본다.

## 검증

로컬에서 두 앱을 띄우고 카카오 로그인 버튼까지 실제로 눌러 봤다. 모바일은 3001이 이미 물려 있어서
64029로 붙었고, 웹은 3000이다. 버튼을 누르면 서버 액션 `startSocialLogin`이 인가 URL을 만들어
`redirect()`하고, 브라우저가 카카오로 넘어간다.

넘어간 뒤 네트워크 기록을 읽으니 두 앱 모두 인가 URL에 scope가 실려 있었다.

```
https://accounts.kakao.com/login?...&continue=https%3A%2F%2Fkauth.kakao.com%2Foauth%2Fauthorize
  %3Fclient_id%3D...%26redirect_uri%3Dhttp%253A%252F%252Flocalhost%253A3001%252Foauth%252Fcallback
  %26response_type%3Dcode%26state%3D...%26scope%3Daccount_email%252Cage_range%252Cgender...
```

여기서 하나 배운 게, 카카오는 `prompt=login`을 받으면 인가 엔드포인트에서 바로 동의 화면을 주는 게
아니라 `accounts.kakao.com/login`으로 한 번 튕기면서 원래 인가 URL을 `continue` 파라미터에
통째로 집어넣는다. 그래서 URL 안에 인코딩이 두 겹으로 쌓여 `%253A` 같은 게 보인다. 로그인이 끝나면
`continue`를 풀어서 원래 인가 요청을 이어간다.

중요한 건 이 응답이 200이고 평범한 카카오계정 로그인 화면이라는 점이다. 콘솔에서 안 켠 항목을
scope에 적으면 카카오는 로그인 화면을 주지 않고 KOE205 오류 페이지로 막는다. 그게 안 떴으니
`account_email`·`age_range`·`gender` 세 항목이 콘솔에서 이미 유효한 상태라는 뜻이다.

여기서 멈췄다. 그다음 단계인 "추가 동의 화면이 실제로 뜨는가", "거부해도 로그인이 이어지는가"는
카카오 계정 비밀번호를 넣어야 확인되는데, 남의 계정 자격증명을 내가 대신 넣을 일은 아니다.
그 두 줄은 사용자가 직접 확인하는 걸로 남겼다.

## 배포 순서 주의

콘솔에서 연령대·성별 동의 항목을 켜는 게 먼저고, 이 코드 배포가 나중이다. 순서가 뒤집히면
아직 안 켠 항목을 scope에 적은 꼴이라 카카오 로그인 자체가 KOE205로 막힌다. 로그인이 통째로
죽는 거라 영향이 작지 않다.

로컬 검증에서 로그인 화면이 정상으로 나온 걸 보면 이미 켜져 있는 것으로 보이는데, 콘솔 화면을
직접 본 게 아니라 오류가 안 났다는 간접 증거다. dev에 먼저 올려 한 번 더 보는 게 안전하다.

또 하나, 두 항목을 선택 동의로 켜야 거부해도 로그인이 이어진다. 필수 동의로 켜면 거부한 사용자가
로그인을 못 하게 되는데, 분석용 부가 정보 때문에 로그인을 막는 건 과하다.

## 남은 것

FE가 값을 따로 보낼 일은 없다. 카카오가 준 `age_range`·`gender`를 BE가 사용자 정보 응답에서
직접 읽어 저장하고, 로그인할 때마다 새 값으로 덮는다(KAN-475). 프론트는 동의를 요청하는 데까지가
역할이고 값은 스치지도 않는다.

- [ADR 0022](0022-mobile-oauth-login.md): 모바일 OAuth 로그인 뼈대, `OAUTH_AUTHORIZE` 구조
- [ADR 0050](0050-web-auth-api.md): 인증 상수를 앱별 복제로 둔 판단
- [ADR 0103](0103-apple-login-and-account-picker.md): `prompt` 계열 파라미터와 애플이 scope를
  안 받는 이유
