# 0200. 누구에게나 같은 페이지에 내 상태 얹기: 기사·릴스·투표를 익명 ISR로 (KAN-664)

## 어디서 이어지나

[ADR 0199](0199-no-store-bfcache-problem.md)(KAN-632)에서 루트 레이아웃의 `cookies()`·`headers()`를 브라우저로 옮겨 홈·FAQ·팀 프로필을 정적·ISR로 돌렸다. 남은 동적 화면은 페이지 자체가 Bearer 토큰을 실어 데이터를 받는 기사 상세, 릴 상세, 릴스 피드, 투표 목록이다. 응답 하나에 "누구에게나 같은 것"(본문, 좋아요 수, 투표 집계)과 "이 사용자만의 것"(내가 눌렀나, 어느 쪽에 투표했나)이 섞여 있어서 캐시할 수 없다.

BE가 KAN-663으로 `GET /api/v1/users/me/article-states?ids=…`(기사 여러 건의 내 좋아요·투표를 한 번에, 최대 60개)를 열었다. 이번 작업은 네 화면을 익명으로 받아 ISR로 캐시하고, 내 상태는 페이지가 뜬 뒤 이 API로 받아 클라이언트가 얹는 것이다.

개선 전 수치는 KAN-632의 개선 후 증거(`docs/perf/2026-10-15-kan-632/`)가 그대로 출발점이다. 빌드 표에서 `/articles/[postId]`·`/reels`·`/reels/[postId]`·`/debates`가 ƒ, 응답은 `private, no-cache, no-store, max-age=0, must-revalidate`, 기사 Lighthouse `bf-cache` 실패.

## 착수 전에 새로 안 것

티켓에는 "기사·릴스·투표의 `likedByMe`·`myVote`를 빼고 오버레이로 얹는다"만 적혀 있었다. 코드를 따라가 보니 사람마다 달라지는 값이 둘 더 있었다.

하나는 기사 상세의 댓글이다. 페이지가 댓글 첫 페이지를 토큰을 실어 같은 렌더에서 받아 씨앗으로 심고 있었다. 댓글 응답에는 댓글마다 `likedByMe`가 있고, 내가 차단한 사용자의 댓글은 본문이 "차단한 사용자의 댓글입니다"로 바뀌어 온다(BE `CommentResponse`의 `isBlocked`). KAN-663은 기사 단위 상태만 다루니 댓글은 오버레이로 풀 수 없다. 댓글을 서버에서 받지 않고 브라우저에서만 받기로 했다.

다른 하나는 릴스 피드의 순서다. 로그인 세션(게스트 포함)이면 BE가 안 본 릴을 먼저 주고 본 릴을 뒤로 미룬다(UNSEEN → SEEN 두 단계 커서). 첫 페이지를 익명으로 캐시하면 이 개인화가 첫 페이지에서 빠진다. 선택지는 둘이었다. 익명 첫 페이지를 그대로 캐시하거나(첫 30개는 누구에게나 최신순), 빈 껍데기만 캐시하고 첫 페이지를 브라우저에서 토큰을 실어 받거나. 후자는 개인화를 지키지만 첫 릴이 JS 실행과 API 왕복을 기다려 LCP가 밀린다. 딥링크(`/reels/{id}`)는 BE가 원래 개인화하지 않는 시간순(CHRONO)이고, 손해는 첫 페이지뿐이라 전자로 정했다. 두 번째 페이지부터는 브라우저가 프록시를 거쳐 토큰을 실어 받으니 개인화가 다시 붙는다. 첫 페이지의 커서는 익명 응답의 것이지만 BE 커서 형식은 로그인 여부와 무관하게 같아서(`ReelsCursor`) 이어 받는 데 문제가 없다.

BE 코드는 `origin/feat/KAN-663-article-states` 브랜치에만 있었고 로컬 `develop`에는 없었다.

## 내 상태를 어떻게 들고 다닐까

화면마다 좋아요와 투표의 원본이 달랐다. 기사 상세는 서버 props를 복사한 컴포넌트 state(`ArticleLikeButton`, `DebateVoteCard`), 릴스는 무한 쿼리 캐시 안 카드의 `liked`, 투표 목록은 `debateKeys.list()` 캐시였다. 이번에 "눌렀는가"만 떼어 한 곳에 모았다. 수(좋아요 수, 표 수)는 누구에게나 같은 값이라 전처럼 각 화면 원본에 둔다.

### 쿼리 키를 기사 하나에 하나로

처음엔 티켓 문구대로 `useArticleStates(ids)`처럼 묶음을 키로 두는 걸 생각했다. 그러면 릴스 피드가 두 번째 페이지를 받을 때 키가 바뀌어 첫 페이지 id까지 다시 묻거나, 페이지마다 키를 따로 두고 "이 기사는 몇 번째 페이지 키에 있나"를 찾아야 한다. 같은 기사가 피드와 상세에 함께 뜨면 두 키가 서로 다른 값을 들 수도 있다.

그래서 키를 기사 하나에 하나(`["article-states", id]`)로 두고, 카드마다 `useMyArticleState(id)`를 부르게 했다. 대신 카드 30장이 뜨면 요청이 30번 나가면 안 되니 로더가 묶는다(`createArticleStateLoader`). 카드의 쿼리 함수는 `loader.load(id)`를 부르고, 로더는 `setTimeout(0)`으로 다음 매크로태스크까지 들어온 id를 모아 `GET /users/me/article-states?ids=…` 한 번으로 보낸 뒤 결과를 id별 Promise로 나눠 돌려준다. 한 렌더에서 마운트된 카드들의 쿼리는 같은 커밋의 이펙트에서 시작되니 이 창 안에 모두 들어온다. DataLoader라는 라이브러리가 쓰는 방식과 같다. 60개 상한을 넘으면 나눠서 동시에 보낸다.

검증 로그에서 릴스 첫 화면 10장이 `n=10` 요청 한 번으로, 투표 목록 2장이 `n=2` 한 번으로 나갔다.

다시 묻는 시점은 두 번뿐이다. `staleTime`을 무한으로 두고, bfcache에서 복원됐을 때와 세션이 바뀌었을 때만 무효화한다. 누른 직후에는 BE 안내대로 다시 묻지 않고 캐시에 바로 적는다(`setMyArticleState`). 좋아요는 등록·취소가 성공하면 그 상태가 맞고 투표는 응답에 `myVote`가 온다. 캐시에 아직 없는 기사는 이때 만들지 않는다. 마이페이지에서 좋아요만 눌렀다면 그 기사의 투표는 모르니까, 모르는 필드를 "안 함"으로 채운 캐시를 만들면 나중에 그 기사 화면이 틀린 값을 믿게 된다.

### 하트가 비어 보이는 순간과 브라우저 기억

서버 HTML에는 하트가 늘 비어 있다. 익명으로 그린 페이지라서다. 그 위에 브라우저가 내 상태를 받아 채우니, 전에는 HTML에 이미 차 있던 하트가 이제는 API 왕복 한 번 뒤에 찬다. 이 틈을 줄이려고 내가 누른 기사만 `localStorage`에 적어 두고(`article-state-memo.ts`), 응답이 오기 전에는 그 기억으로 먼저 채운다(TanStack Query의 `placeholderData`). 응답이 오면 응답이 이기고 기억도 맞춘다. 다른 기기에서 취소했으면 기억에서 지워진다.

여기서 하이드레이션을 조심해야 했다. 서버 HTML은 빈 하트인데 브라우저가 하이드레이션 첫 패스에서 기억을 읽어 찬 하트를 그리면 서버 결과와 달라 하이드레이션 불일치가 난다. 다행히 KAN-632에서 만든 구조가 이걸 풀어 줬다. `AuthProvider`는 서버와 하이드레이션 첫 패스에서 세션을 "모름"으로 두고, `useLayoutEffect`에서 표식 쿠키를 읽어 올린다. 레이아웃 이펙트 안의 setState는 브라우저가 첫 프레임을 그리기 전에 동기로 다시 렌더한다. 훅이 `isLoggedIn`이 false인 동안은 무조건 "안 누름"을 돌려주게 하면, 하이드레이션 첫 패스는 서버와 같고 바로 다음 동기 렌더에서 기억이 들어간다. 사용자는 빈 하트를 한 프레임도 보지 않는다.

상태 API를 3초 늦춘 프록시로 확인했다. 기억이 있으면 새로고침 0.8초 시점에 이미 "좋아요 취소"(찬 하트)였고, 기억을 지우고 같은 걸 하면 1.2초 시점엔 빈 하트였다가 응답 뒤에 찼다.

기억에는 주인이 있어야 한다. 게스트로 누른 기록이 소셜 로그인한 뒤에 보이면 안 된다. 브라우저는 토큰을 못 읽어 "누구의 세션인가"를 모르지만 표식 쿠키(`sessionKind`)가 게스트/소셜 사이를 오가는 순간은 안다. 기억 옆에 그 종류를 적어 두고(`plick:myArticleStates:owner`), 읽은 종류가 다르면 기억과 쿼리 캐시를 함께 지운다. 소셜 로그인은 OAuth 왕복으로 문서를 새로 받아서 메모리에 "직전 값"이 없기 때문에 저장소에 적어 둬야 비교가 된다. 로그아웃은 게스트로 돌아가므로 소셜 계정끼리 바로 바뀌는 경우에도 중간에 한 번 걸린다.

### bfcache 복원

bfcache는 떠나기 직전의 페이지를 JS 힙까지 통째로 얼려 두었다가 뒤로가기 때 그대로 녹이는 브라우저 캐시다. 녹은 화면의 쿼리 캐시는 떠나기 전 값이다. 그 사이 다른 기기에서 하트를 눌렀을 수 있으니, `pageshow` 이벤트의 `persisted`가 true면 내 상태 쿼리만 무효화한다. 활성 쿼리만 다시 받고 이것도 로더가 한 번으로 묶는다. 본문이나 좋아요 수는 누구에게나 같은 캐시 값이라 건드리지 않았다. 피드 자체를 다시 받으면 ADR 0048의 씨앗 재주입 함정(`resetQueries`가 서버 씨앗을 다시 심어 옛 목록이 스치는 것)이 있어서 그건 하지 않는다. 이 처리는 세션 표식을 다시 읽던 `AuthProvider`의 `pageshow` 처리 옆에 붙였다. 둘 다 "세션에 묶인 값"이라서다.

## 화면 전환

좋아요는 `useLikeToggle`이 `{ liked, likeCount }`를 받아 낙관적 갱신을 하고 `onChange`로 돌려주는 구조라 손댈 게 적었다. 넘기는 `liked`만 내 상태 캐시에서 읽게 바꿨고, 확정된 값을 피드 캐시에 옮겨 적던 `syncLikeIntoFeeds`가 내 상태 캐시도 함께 고치게 했다. 기사 상세 버튼은 이제 좋아요 수만 state로 든다. 릴스 레일은 `reel.liked` 대신 `useReelLike`가 돌려주는 `liked`를 받는다. 마이페이지의 좋아요 목록은 MY라 여전히 토큰으로 받는 동적 화면이어서 카드의 `liked`를 그대로 쓴다.

투표 카드(`DebateVoteCard`)는 표 수를 state로, 내 표를 내 상태 캐시에서 읽어 합친 `Debate`를 표시 전용 `VoteCard`에 넘긴다. 내 표를 찾으려면 기사 id가 필요해서 `articleId` prop이 생겼다(기사 상세, 릴 시트, 투표 목록 세 곳). 투표 목록의 마감 탭은 투표 없이 결과만 보여 주는 `VoteCard`를 직접 쓰던 자리라, 내 표 표시만 얹는 `ClosedVoteCard`를 같은 파일에 두었다.

결과 공개(비율 막대)가 내 표에 걸려 있다. 그래서 응답 전에는 투표 전 모양이었다가 내 표가 오면 결과로 바뀐다. 표 수 쪽 절충도 하나 있다. 투표하고 60초 안에 새로고침하면 체크 표시는 내 표를 가리키는데 표 수는 캐시된 익명 응답이라 내 표가 빠진 숫자다(로컬에서 27표 → 새로고침 26표). BE도 같은 절충을 안내했다. ISR 주기만큼 늦을 뿐이고 다음 재생성에서 맞는다.

## 서버 fetch를 익명으로

네 화면에서 `getAccessToken()`을 걷어냈다. 이게 쿠키를 읽는 마지막 자리였다. `apiFetch`는 토큰 없는 GET을 `next: { revalidate: 60 }`으로 서버 데이터 캐시에 넣으니(KAN-380) 페이지도 60초 ISR이 된다. 페이지의 revalidate는 그 라우트 fetch들의 revalidate 중 가장 짧은 값을 따른다.

티켓은 기사 상세를 "불변에 가까우니 길게"라고 했는데 60초로 뒀다. 본문은 안 바뀌지만 좋아요 수, 댓글 수, 표 수가 같은 페이지에 보인다. 길게 잡으려면 `getArticle`에 별도 revalidate를 넘겨야 하고, 그 대가로 수가 몇 분씩 늦는다. 60초면 인기 기사 하나가 분당 한 번 재생성되는 정도라 서버 부담으로는 충분히 작다.

`[postId]` 두 라우트에는 빈 `generateStaticParams`를 선언했다. ADR 0199에서 본 대로 이 함수가 아예 없는 동적 세그먼트는 요청마다 렌더(ƒ)이고, 빈 배열이라도 있으면 첫 요청에 그려 캐시(●)한다. 릴 딥링크 페이지의 catch에는 `unstable_rethrow`를 넣었다. 정적 생성 중 Next가 제어 흐름으로 던지는 예외를 삼키지 않게 하는 것이다.

### 댓글은 브라우저에서만

댓글 서버 씨앗을 빼는 것만으로는 부족했다. 목록 훅(`useComments`)은 suspense 쿼리다. 씨앗이 없으면 서버 렌더 중에도 데이터를 받으려고 suspend하고, 그러면 ISR 생성 중 서버가 토큰 없이 댓글을 받아 HTML에 굳힌다. 브라우저의 쿼리 캐시에는 그 데이터가 없으니 하이드레이션에서 다시 받으며 서버 결과와 어긋난다. 무엇보다 사람마다 다른 응답의 익명판이 캐시된 HTML에 들어간다. 그래서 기사 상세의 댓글 목록을 `next/dynamic`의 `ssr: false`로 감쌌다. 서버와 하이드레이션은 댓글 뼈대를 그리고, 마운트 뒤 목록이 프록시를 거쳐 토큰을 실어 받는다. 씨앗이 사라져 `CommentList`·`useComments`의 `initial` 인자도 쓰는 곳이 없어져 지웠다. 릴 시트는 원래 씨앗 없이 열리던 곳이라 그대로다.

## 시행착오

단위 테스트에서 한 번 막혔다. 로더와 id 나누기를 `article-states.ts`에 두고 `tests/unit`에서 불렀더니 `ERR_UNSUPPORTED_TYPESCRIPT_SYNTAX`로 파일째 실패했다. 이 저장소의 단위 테스트는 Node 22의 타입 지우기(`--experimental-strip-types`)로 `.ts`를 바로 돌리는데, 지우기만 하는 모드는 TS 고유 문법(생성자 매개변수 프로퍼티 `constructor(public status: number)`)을 못 다룬다. `article-states.ts`가 import한 `client.ts`의 `ApiError`가 바로 그 문법이었다. 네트워크와 무관한 로더와 나누기를 `article-state-batch.ts`로 떼어 테스트가 그것만 부르게 했다.

릴 좋아요 훅은 문자열 치환으로 고치다가 주석 한 줄이 원본과 달라 치환이 통째로 빠졌다. 레일은 `like.liked`를 읽는데 훅은 그걸 안 돌려줘서 타입 검사가 잡았다.

검증 환경도 손이 갔다. 다른 세션의 dev 서버가 이 체크아웃의 3000·3001을 쓰고 있어서 빌드는 워크트리에서 했다. 상태 API는 아직 prod에 없고, 공유 Supabase는 끊겨 로컬 BE에는 데이터가 없다. 그래서 읽기는 prod BE로 넘기고 상태 조회와 좋아요·투표 쓰기만 메모리에서 흉내 내는 node 프록시를 스크래치에 두고 `API_BASE_URL`을 그쪽으로 돌렸다. 쓰기까지 흉내 낸 건 prod 데이터를 건드리지 않기 위해서다. BE 실계약은 `be-verify` 서브에이전트가 KAN-663 브랜치를 로컬 8082와 docker postgres에 띄워 따로 확인했다. 섞인 id의 값과 순서, 중복 제거, 없는 id, 401, 400(61개, 0, 숫자 아님), `no-store, private`, 게스트 토큰까지 문서와 차이가 없었다.

## 확인하다 본 것 두 가지

없는 기사(`/articles/99999999`)가 200으로 나간다. 처음엔 ISR 때문인가 했는데 지금 prod(동적)도 200이다. 레이아웃이 먼저 스트리밍된 뒤 페이지가 `notFound()`를 부르면 상태 코드는 이미 나간 200이고 not-found 화면만 그려진다. 이번 변경과 무관해서 범위에서 뺐다.

BE는 기사 상세 API(`GET /articles/{id}`)가 불릴 때마다 `article_opened`(출처 `DETAIL_API`)를 낸다. 전에는 토큰이 실린 요청이 캐시를 못 타서 사실상 열람마다 한 번씩 나갔는데, ISR이 되면 재생성 때만 나간다. 열람 기록은 브라우저가 마운트 뒤 보내는 조회 API(출처 `VIEW_API`)가 따로 내니 지표가 사라지지는 않지만, `DETAIL_API` 출처 건수는 크게 줄어든다. BE에 알려 둘 몫이다.
