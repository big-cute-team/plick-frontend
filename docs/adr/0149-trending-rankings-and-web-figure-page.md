# 0149. 실시간 급상승 랭킹으로 사이드바를 갈아엎고, 웹에 인물 페이지를 새로 깔았다

KAN-501. 데스크톱 웹 사이드바의 "실시간 인기" 카드를 걷어내고 그 자리에 팀·선수
급상승 랭킹을 넣었다. 하다 보니 웹에 인물 프로필 화면이 없다는 게 걸려서 그것까지
같이 만들었다.

## 갈아엎기로 한 이유

웹 사이드바에는 "실시간 인기"라는 카드가 한 장 있었다. 기사 제목을 1번부터
5번까지 세로로 세운 목록이다. KAN-338에서 채운 건데, 그때는 전용 API가 없어서
핫이슈와 같은 `GET /api/v1/articles/hot`을 그대로 썼다. 최근 48시간 조회수 상위
기사다.

이게 두 가지가 마음에 걸렸다. 하나는 이름이 거짓말이라는 것. "실시간"이라고 써
놓고 실제로는 48시간 누적이니 하루 종일 같은 목록이 걸려 있다. 다른 하나는 바로
왼쪽 "지금 올라온 소식" 리스트와 보이는 게 겹친다는 것. 같은 화면 안에서 기사
제목을 두 번 세우고 있으니 사이드바가 있으나 마나 했다.

이번에 BE가 `GET /api/v1/trends`를 붙였다(KAN-496, KAN-499). 10분마다 배치가 최근
3시간 구간의 신규 기사·댓글·좋아요·조회를 비율로 환산해 지수를 내고, 팀과 선수를
줄 세워 회차로 저장한다. 조회는 최신 회차를 그대로 읽는다. 그러니까 화면에서
계산할 게 하나도 없다.

기사 단위로만 나열되던 화면에 팀과 인물이라는 진입점이 하나 생기는 게 이 기능의
요점이다. 그래서 기존 카드를 옆에 두고 하나 더 쌓는 게 아니라 통째로 바꿨다.

## 계약부터 확인했다

로컬 BE(:8082)를 먼저 찔러 봤다.

```
GET /api/v1/trends?type=TEAM&limit=6
{"code":"OK","data":{"type":"TEAM","collectedAt":null,"items":[]}}
```

빈 배열에 `collectedAt`이 null이다. 에러가 아니라 정상 응답이다 — 배치가 아직
회차를 한 번도 안 만들면 이렇게 온다. 티켓에도 "items가 빈 배열이어도 화면이
깨지지 않는다"가 완료 조건으로 적혀 있는데, `collectedAt`이 null일 수 있다는
말은 없었다. 실제로 찔러 보지 않았으면 집계 시각 줄에서 터졌을 자리다.

dev는 회차가 있었다. 그런데 팀도 선수도 각각 한 건씩만 온다.

```
{"type":"TEAM","collectedAt":"2026-09-15T09:00:00Z","items":[
  {"entityId":6,"name":"토트넘 핫스퍼","imageUrl":null,"score":0.5,
   "rank":1,"previousRank":1,"rankDelta":0,"direction":"SAME","scoreChangeRate":0.0}]}
```

`limit=6`을 줘도 여섯 개가 오는 게 아니다. 목록이 요청한 길이보다 짧을 수 있다는
뜻이라 화면에서 6칸을 고정으로 깔면 안 된다. 그리고 티켓이 미리 경고한 대로
`direction`이 전부 `SAME`이었다. 실사용 트래픽이 붙기 전에는 참여가 거의 없어서
순위가 안 움직인다.

dev API 주소는 GitHub Environments 시크릿이라 내 손에 없는데, 웹 앱이
`/be/*`를 BE로 넘겨주는 프록시를 갖고 있어서 `https://dev.plick.co.kr/be/api/v1/trends`로
그냥 읽혔다. 로그인 없이 되는 공개 API라 토큰도 필요 없었다.

`score`는 도메인 타입에서 뺐다. 0.612345 같은 내부 수치라 화면에 그릴 자리가
없다. 경계 변환에서 버리면 화면 쪽에서 "이건 뭐지" 하고 다시 들여다볼 일이
없어진다.

## 이미지가 전부 비어 있다는 전제

티켓이 맨 앞에 못 박아 둔 게 있다. `imageUrl`이 dev와 prod 모두 전 행 null이라는
것. 팀 6개도, 인물 200명 넘게도 전부다. 마스터 데이터가 아직 안 채워진 것이고
채우는 건 별도 작업이다. 그러니까 이미지가 하나도 없는 상태를 기본으로 잡고
만들어야 한다.

팀과 선수를 다르게 풀었다.

팀은 6개 고정이고 앱 안에 이미 실제 구단 로고가 있다(`public/teams/*.webp`,
`@plick/ui`의 `TeamCrest`). BE가 로고를 주든 말든 이쪽이 정답이다. KAN-500에서
팀 프로필을 만들 때도 같은 판단을 했다 — 도메인 타입 `TeamProfile` 주석에 "BE
`logoUrl`은 현재 6팀 모두 null이라 로고는 레지스트리의 실제 구단 로고를 그린다"고
적혀 있다. 그 전례를 그대로 따랐다. 그래서 팀 줄은 `imageUrl`을 아예 안 본다.
BE `entityId`(=`teams.team_id`)를 레지스트리 `TEAM_CODES`로 팀 코드로 바꾸고
크레스트를 그린다.

선수는 200명이 넘어서 그렇게 박아둘 수가 없다. `imageUrl`이 오면 쓰고, 없으면
**자리 자체를 그리지 않는다.** 이름이 순위 바로 옆에 붙는다.

여기서 한 번 갈아엎었다. 처음에는 이름 첫 글자를 넣은 원으로 떨어뜨렸다.
"히샬리송"이면 "히"다. 빈 원보다는 글자가 있는 게 목록으로 읽힌다고 봤는데,
화면을 본 사용자 판단은 반대였다 — 전 행이 폴백인 상태에서 회색 원에 한 글자씩
박힌 줄이 여섯 개 서 있으면 그게 더 이상해 보인다. 사진이 없으면 그냥 안 보이게
하는 쪽으로 바꿨다. 값이 채워지기 시작하면 그 줄부터 사진이 붙고, 섞여 있어도
어색하지 않다. 웹 인물 프로필 머리의 큰 원도 같은 이유로 없앴다.

여기서 기존 코드를 한 번 뒤집게 됐다. 인물 사진 원을 그리는 `PlayerPhoto`가
모바일 `app/_components/`와 웹 `app/live/_components/`에 **같은 구현으로 두 벌**
있었다. 주석 문구만 다르고 코드는 한 글자도 안 달랐다. 라이브 스코어 선수단에서
시작해 양쪽이 각자 복사한 것이다. `web-publishing` 스킬 §4가 이런 경우를
`@plick/ui`로 승격하라고 정해 두고 있어서(사본이 두 개면 감사 대상) 이번에
`packages/ui/src/PlayerPhoto.tsx` 한 벌로 합치고 양쪽 import를 전부 바꿨다.

이니셜을 넣었다 뺀 덕에 승격된 컴포넌트는 옛 구현 그대로 남았다. 라이브 스코어
선수단은 API-Football CDN 사진이 대부분 채워지는 자리라 폴백 원이 오히려 정답이고,
거기 동작은 이번에 한 글자도 안 바뀌었다. 결과적으로 이 승격은 순수하게 사본
두 벌을 한 벌로 합친 것만 남았다.

## 화살표 규칙을 순수 함수로 뺐다

무엇을 그릴지가 세 필드에 흩어져 있다.

- `direction`이 `UP`이면 위, `DOWN`이면 아래, `NEW`면 이번 회차에 처음 들어온 항목
- `rankDelta`는 오른 칸 수. `NEW`면 `previousRank`와 함께 없다
- `direction`이 `SAME`이면 순위가 그대로다. 이때 `scoreChangeRate`로 화살표를
  그려도 된다고 티켓이 허용했다. 이 값도 없을 수 있다

이걸 JSX 안에서 분기하면 삼항 연산자가 세 겹으로 쌓인다. `_utils/trends.ts`에
`toTrendDelta(item)` 하나를 두고 `{kind:"up"|"down", label, muted}`,
`{kind:"new"}`, `{kind:"same"}` 중 하나를 돌려주게 했다. 화면은 결과만 그린다.
CLAUDE.md가 순수 함수를 컴포넌트 파일에 인라인으로 두지 말라고 한 것도 있지만,
이 경우엔 규칙 때문이 아니라 안 그러면 읽을 수가 없어서다.

`SAME`일 때 점수 변화율로 화살표를 그리는 건 넣었다. dev 확인에서 두 회차 모두
전부 `SAME`이었으니 안 넣으면 여섯 줄이 전부 가로줄만 달고 있는 화면이 된다.
다만 변화율이 0.5% 미만이면 가로줄로 남긴다 — 소수점 한 자리로 반올림하면
"0.0%"가 되는데, 화살표는 달려 있고 숫자는 0인 줄은 거짓말에 가깝다. 이 화살표는
순위에서 온 게 아니라는 표시로 색을 흐리게(`text-text-3`) 뒀다.

방향을 색으로만 알리지 않게도 챙겼다. 삼각형이 위아래로 뒤집혀 형태로 한 번,
`sr-only`로 "상승"/"하락"이 스크린리더에 한 번 더 간다. 상승이 accent(초록),
하락이 danger(빨강)인데 이 둘만으로 구분하게 두면 색각 이상에서 정보가 통째로
사라진다.

## 선수를 누르면 갈 곳이 없었다

여기서 한 번 막혔다.

티켓 완료 조건에 "항목을 누르면 관련 기사 전체 보기로 넘어간다"가 있다. 팀은
간단했다 — 웹에 팀 허브(`/teams/[slug]`)가 이미 있고 그게 그 팀 기사를 모아
보여주는 자리다. 그런데 선수는 갈 데가 없었다. 인물 프로필 `/figures/[figureId]`는
KAN-500에서 **모바일에만** 만들었다. ADR 0146에도 "웹은 아직 이 화면이 없다"고
적혀 있다.

선택지가 둘이었다. 선수 줄을 링크 없이 표시만 하고 웹 인물 페이지를 별도 티켓으로
넘기거나, 이번에 같이 만들거나. 링크 없는 줄로 두면 완료 조건이 반만 찬다. 그래서
만들기로 했다.

이식은 생각보다 작았다. 데이터 레이어는 이미 공용이다 — `@plick/core/figures`의
`getFigureProfile`도, `@plick/core/articles`의 `getArticles({figureId})`도
모바일이 쓰던 그대로다. 쿼리키도 `articleKeys.figureFeed`가 이미 있다. 새로 쓴 건
웹 레이아웃에 맞춘 화면 조각뿐이다.

- `app/figures/[figureId]/page.tsx` — 프로필과 기사 첫 페이지를 `allSettled`로
  병렬로 받는다. 프로필이 404(`FIGURE_NOT_FOUND`)나 400(`COMMON_INVALID_PARAM`)이면
  `notFound()`고, 기사 첫 페이지만 실패하면 페이지를 죽이지 않고 씨앗 없이
  내려보낸다. 그러면 목록이 클라에서 다시 받으면서 그 자리에만 에러와 재시도를
  그린다
- `_components/FigureHeader.tsx` — 사진, 이름·구분·영문명, 소속 팀, 한 줄 소개
- `_components/FigureArticlesFeed.tsx` — 무한스크롤 목록. 줄은 기사 페이지와 같은
  `PostListItem`(article 변형)을 쓴다. 응답이 기사 목록과 같은 카드라 전용 줄을
  만들면 같은 카드가 둘로 갈린다
- `_hooks/useFigureArticles.ts` — 모바일과 동일 구현. 훅은 승격 후보가 아니라서
  (`useArticleFeed`와 같은 판단) 앱별로 둔다
- `not-found.tsx` — 모바일과 같은 문구, 데스크톱이라 GNB를 남긴다

모바일과 딱 하나 다른 게 소속 팀 링크다. 모바일 `FigureHeader`는
`teamProfilePath()`로 `/teams/[slug]/profile`에 건다. 웹에는 그 라우트가 없어서
팀 허브(`teamHubPath()`)로 걸었다.

만들고 나니 딸려 오는 게 하나 더 있었다. `@plick/domain/cross-site.ts`의
`isSharedPath` — 웹↔모바일 전환 배너가 "지금 보던 화면"으로 건너뛸지 홈으로
보낼지를 정하는 함수다. 인물 프로필이 이제 양쪽에 다 있으니 짝으로 등록했다.
안 했으면 웹 인물 페이지에서 "모바일로 보기"를 눌렀을 때 모바일 홈으로 튕겼을
것이다.

## prop으로 내리지 않고 스스로 받게 했다

기존 `TrendingSection`은 데이터를 prop으로 받았다. 홈 페이지가 핫이슈를
`getHotArticles()`로 받아 두고 있었으니 그걸 그대로 넘기면 추가 fetch가 없었다.
기사 상세도 같은 이유로 핫이슈를 한 번 더 부르고 있었다.

급상승은 전용 호출이 필요하니 그 구조가 안 맞는다. 두 가지가 가능했다.

1. 각 페이지의 `Promise.allSettled` 배열에 `getTrends` 둘을 더 넣고 prop으로 내린다
2. 카드가 자기 데이터를 스스로 받고, 부모가 `Suspense`로 감싼다

2번으로 갔다. 이유가 두 개다.

첫째는 이 카드를 쓰는 곳이 둘(홈/팀 허브 `HomeScreen`, 기사 상세)인데 1번이면
같은 배관을 두 군데에 복사해야 한다. `HomeSidebar`와 `ArticleSidebar`가 쓰지도
않는 값을 받아 그대로 아래로 넘기는 통로가 된다.

둘째가 더 중요하다. 서버 컴포넌트는 부모가 `await`을 끝내야 자식이 렌더된다.
페이지에서 `await`하면 급상승 두 호출이 끝날 때까지 HTML이 한 글자도 안 나간다.
사이드바는 본문보다 늦게 와도 되는 자리인데 본문을 붙잡는 셈이다. 자식 서버
컴포넌트를 `Suspense`로 감싸면 React가 거기서 트리를 자른다 — 껍데기와 fallback을
먼저 흘려보내고(스트리밍), 그 안의 `await`이 끝나면 나머지 HTML 조각을 이어
보내서 브라우저가 fallback 자리를 바꿔 끼운다. 클라이언트 왕복이 아니라 같은
응답 스트림 안에서 벌어지는 일이라 JS가 꺼져 있어도 결국 내용은 도착한다.

그래서 `TrendingSection`을 async 서버 컴포넌트로 만들고 안에서 두 랭킹을
`allSettled`로 병렬로 받게 했다. 한쪽이 실패해도 다른 탭은 보여야 하니 실패한
탭만 null로 내려보내고, 탭 안에 실패 문구를 그린다. fallback으로는 실제 카드와
같은 테두리·패딩·줄 수를 가진 `TrendingSectionSkeleton`을 뒀다. 사이드바가
`sticky`라 높이가 도착 전후로 달라지면 본문 옆에서 카드가 튄다.

부수 효과로 기사 상세에서 `getHotArticles()` 호출이 통째로 빠졌다. 사이드바
랭킹 하나 때문에 부르던 거라 이제 쓸 데가 없다. `@plick/core/articles`의
`toTrendingArticles`와 `TRENDING_COUNT`도 같이 지웠다 — 두 핫이슈 그룹을 조회수로
다시 세우던 함수인데 마지막 사용처가 사라졌다.

탭 전환은 요청을 만들지 않는다. 서버가 두 랭킹을 한 번에 내려주고 클라는 자리만
바꾼다. 10분마다 갱신되는 배치 결과라 탭을 누를 때마다 부를 이유가 없고,
사이드바에서 클릭마다 스피너가 도는 것보다 조용하다.

## 검증하다 세 번 막혔다

화면을 띄워 보는 데서 시간을 꽤 썼다.

**하나. dev 서버가 이미 떠 있었다.** 포트 3000에 `next dev`가 돌고 있어서 다른
포트로 하나 더 띄우려니 "Another next dev server is already running"으로 죽는다.
Next는 같은 디렉터리에서 dev 서버 두 개를 허용하지 않는다. 남의 서버를 죽일 수는
없으니 `next build` 산출물을 `next start`로 띄우는 쪽으로 돌렸다.

**둘. 실데이터가 없었다.** 로컬 BE는 회차가 없어 빈 배열이고, dev는 한 건씩에
전부 `SAME`이다. 둘 다 화살표 네 종류를 볼 수가 없다. 그래서 스크래치에 작은
Node 스텁을 하나 띄웠다 — `/api/v1/trends`만 `UP`/`DOWN`/`NEW`/`SAME`이 섞인 여섯
줄로 답하고, 나머지 요청은 전부 dev BE로 넘기는 프록시다. `API_BASE_URL`을 거기로
돌려서 홈과 기사 상세를 통째로 띄웠다. 스텁은 검증이 끝나고 지웠다.

**셋. 스텁을 바꿔도 화면이 안 바뀌었다.** 여기서 제일 오래 붙잡혔다. 스텁의 상류를
로컬 BE에서 dev로 바꾸고 새로고침했는데 인물 페이지가 계속 "아직 이 인물의 소식이
없어요"였다. 스텁을 직접 curl하면 기사가 멀쩡히 나오는데 화면만 비어 있었다.

원인은 Next의 데이터 캐시였다. `packages/core/src/client.ts`의 `apiFetch`는
토큰을 안 실은 GET을 `next: { revalidate: 60 }`으로 캐시한다(KAN-380 — 크롤러는
항상 익명이라 같은 목록을 연달아 훑을 때 BE 왕복을 줄이려고 넣은 것이다). 상류를
바꾸기 전에 한 번 읽은 빈 응답이 60초짜리 캐시에 그대로 앉아 있었다. 60초를
넘기고 다시 부르니 정상으로 나왔다.

같은 파일을 읽다가 하나 더 알았다. `apps/web/next.config.js`의 `rewrites()`에
달린 주석이다 — `/be/*` 프록시의 목적지는 서버가 뜰 때가 아니라 **`next build`
때 한 번 평가돼 `routes-manifest.json`에 문자열로 굳는다.** 그래서 `next start`에
`API_BASE_URL`을 새로 줘도 서버 렌더는 새 주소를 보는데 브라우저의 `/be` 호출은
빌드 때 박힌 주소로 간다. 실제로 그 둘이 갈려서 한동안 "서버는 스텁, 클라는 로컬
BE"라는 이상한 상태를 봤다. 배포에서 `API_BASE_URL`을 CI 빌드 스텝에 넘기는
이유가 이것이다.

검증 결과는 이렇다.

- 홈 1280px: 구단 탭 여섯 줄에 화살표 네 종류가 다 나온다. 링크는
  `/teams/tottenham` 식으로 팀 허브, 선수 탭은 `/figures/193` 식으로 인물 프로필
- 빈 회차(로컬 BE): "아직 집계된 순위가 없어요." 카드가 짧게 줄어들 뿐 안 깨진다
- 기사 상세 1280px: 관련 기사 카드 아래 급상승 카드가 붙는다
- 웹 인물 페이지: dev 기준 히샬리송 관련 기사 3건이 목록으로 뜨고 마지막에 "관련
  기사를 전부 봤어요"
- 330px: 가로 오버플로 0(`scrollWidth === innerWidth`). 사이드바는 `lg` 미만에서
  숨는 기존 규칙 그대로고, 인물 페이지는 1열로 접힌다

## 남은 것

- **팀 로고·선수 사진.** `imageUrl`은 여전히 전 행 null이다. 마스터 데이터를
  어디서 가져와 채울지가 아직 안 정해졌다. 값이 들어오기 시작하면 선수 줄은
  코드를 안 고쳐도 사진으로 바뀐다. 팀 줄은 레지스트리 크레스트를 계속 쓴다
- **화살표가 안 움직인다.** 실사용 트래픽이 붙기 전에는 순위가 거의 그대로다.
  연동이 잘못된 게 아니다
- **웹 인물 페이지를 sitemap에 안 넣었다.** 모바일 쪽도 안 들어가 있어서 맞춰
  두고 넘겼다. 인물 id 목록을 받아올 엔드포인트가 없는 것도 이유다
- **감독 랭킹은 없다.** 인물 사전에 감독이 팀당 1명씩 6명뿐이라 순위가 의미를
  갖지 못해 BE 집계에서 아예 빠졌다(KAN-496)
- **`isSharedPath`의 `/articles`.** 주석은 "기사 목록은 데스크톱 전용"이라고 하는데
  모바일에도 KAN-386에서 생겼다. 이번 범위가 아니라 손대지 않았지만 어긋나 있다
