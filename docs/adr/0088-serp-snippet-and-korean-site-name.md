# 0088. 검색 스니펫 정비와 한글 사이트명 "플릭" (KAN-384)

2026-08-10. 구글에 "플릭"을 검색해 보니 결과가 참담했다. 홈은 제목이 "PLick" 한 단어에,
설명 자리에는 "홈릴스기사MY. 핫이슈. 아직 핫이슈가 없어요. 전체리버풀토트넘아스날맨유첼시맨시티"
같은 문자열이 붙어 있었다. 탭바와 팀 필터 칩, 빈 상태 문구가 공백도 없이 이어 붙은 거다.
심지어 로그인해야 의미 있는 마이페이지(`/me`)가 "MY - PLick"이라는 제목으로 색인돼 있었다.
반면 기사 상세는 제목·요약·날짜까지 깔끔하게 나왔다. KAN-346·380에서 기사 쪽 메타데이터는
공들여 만들었는데 정작 서비스의 얼굴인 홈이 방치돼 있었던 셈이다.

쿠팡 검색 결과를 레퍼런스로 받았다. 상단에 로고와 함께 한글 "쿠팡"이 사이트명으로 뜨고,
제목은 "쿠팡: 로켓배송으로 빠르게…"처럼 서비스 설명형이고, 설명은 검색어가 볼드로 강조된
제대로 된 문장이고, 아래로 사이트링크가 붙는 형태. 이 중 코드로 만들 수 있는 건 다 만드는
게 이번 세션의 목표였다.

## 1. 왜 구글이 우리 description을 버렸나

원인부터 짚었다. 루트 레이아웃의 description이 "프리미어리그 소식을 릴스로" 열네 글자였고,
홈을 포함한 대부분 페이지가 이걸 그대로 상속받고 있었다. 구글은 meta description을 그대로
쓰지 않는다. 너무 짧거나, 검색어와의 관련성이 약하거나, 페이지 본문에서 그 문장을 뒷받침할
텍스트를 못 찾으면 버리고 본문에서 직접 발췌한다. 우리 홈이 정확히 그 케이스였다.

더 나쁜 건 발췌될 본문도 없었다는 점이다. 홈 화면은 기사 카드와 UI 텍스트뿐이라, 서비스가
뭔지 설명하는 문장이 한 줄도 없다. 실제로 검색 결과에 "누락된 검색어: 프리미어 리그"가 떴다.
프리미어리그 서비스인데 홈 페이지 어디에도(구글이 채택한 텍스트 기준) 그 단어가 없다는 뜻이다.
크롤 시점에 피드가 비어 있어서 "아직 핫이슈가 없어요" 같은 빈 상태 문구까지 스니펫에 들어갔다.

## 2. 브랜드 문구를 `@plick/domain/brand`로 모았다

고칠 문구가 루트 title·description, og:site_name, JSON-LD의 사이트명, 홈 소개 문구까지
web·mobile 두 앱에 걸쳐 있었다. 같은 문구를 두 앱에 복붙하면 언젠가 어긋난다. 구글 별도
모바일 URL 가이드도 두 도메인이 같은 시그널을 내야 한다고 요구하니, ADR 0018의 원칙대로
`packages/domain/src/brand.ts`를 새로 만들어 단일 출처로 삼았다.

- `BRAND_NAME_KO`("플릭") / `BRAND_NAME_EN`("PLick")
- `BRAND_TITLE`("플릭 PLick / 프리미어리그 소식을 릴스로") — 구분자와 태그라인은 사용자가
  중간에 정확히 지정해 줬다
- `BRAND_TITLE_TEMPLATE`("%s | 플릭 PLick")
- `BRAND_DESCRIPTION` — 서비스 정의와 팀명(리버풀, 토트넘, …), "프리미어리그", "EPL",
  "이적"을 자연스럽게 담은 130자짜리 문장
- `PAGE_DESCRIPTIONS` — 릴스·기사·로그인·회원가입·FAQ·약관·개인정보처리방침의 페이지별 문구
- `homeIntroCopy(teamFullName?)` — 홈·팀 허브 하단에 보일 소개 문구

기존 `jsonld.ts`에 있던 `BRAND_NAME`·`BRAND_TAGLINE` 로컬 상수는 지우고 여기서 가져다 쓰게
바꿨다.

## 3. 사이트명을 한글 "플릭"으로

쿠팡 결과 상단의 "쿠팡"은 title이 아니라 구글의 사이트명(site name) 기능이다. 구글 문서
기준으로 사이트명 소스 1순위가 홈에 실린 WebSite 구조화 데이터의 `name`이고, og:site_name과
title이 보조 시그널이다. 그래서 세 곳을 전부 "플릭"으로 맞췄다.

- `webSiteJsonLd`: `name: "플릭"`, `alternateName: "PLick"` — 영문 검색도 받아야 하니
  대표명과 별칭으로 나눴다
- `organizationJsonLd`: 같은 구성. description도 새 `BRAND_DESCRIPTION`으로
- 두 앱 루트 레이아웃의 `openGraph.siteName`: "플릭"

NewsArticle의 publisher·author 폴백 이름도 "플릭"으로 통일했다. 사이트명은 도메인 단위
판정이라 구글이 홈을 다시 크롤하고 재처리해야 반영된다. 코드가 배포된다고 바로 바뀌는 게
아니라는 걸 미리 적어 둔다.

## 4. 홈에 크롤러가 읽을 소개 문장을 실었다

description을 구글이 채택하게 하려면 본문에 그걸 뒷받침하는 텍스트가 있어야 한다. 홈과
팀 허브를 그리는 양쪽 `HomeScreen` 하단에 `homeIntroCopy()` 문단을 넣었다. 팀 허브에서는
팀 이름이 들어간 변형("토트넘 핫스퍼의 이적 루머와 오피셜 소식을 모은 페이지예요…")을 낸다.

숨긴 텍스트(sr-only)로 넣을까 잠깐 생각했지만 접었다. 구글은 사용자에게 보이지 않는 텍스트를
평가절하하거나 무시한다. 대신 `text-caption text-text-4`로 화면 맨 아래에 작고 옅게, 실제로
보이는 텍스트로 실었다. 서비스 소개니까 UX적으로도 거짓말이 아니다. sr-only h1의 브랜드
표기도 "플릭 PLick …"으로 바꿔 한글 브랜드명이 본문에 존재하게 했다.

## 5. `/me`가 색인된 진짜 이유 — robots.txt의 트레일링 슬래시

마이페이지가 색인된 경위가 재밌다. robots.ts에 `disallow: "/me/"`가 분명히 있었다. 그런데
robots 규격에서 `Disallow: /me/`는 `/me/edit`은 막아도 트레일링 슬래시 없는 `/me` 자체는
안 막는다. prefix 매칭이 문자 그대로라서다. 크롤러는 당당하게 `/me`를 긁어 갔고, 페이지에
noindex도 없으니 그대로 색인됐다.

고치는 방법이 두 갈래였다. `/me`로 고쳐 크롤 자체를 막느냐, 크롤은 열어 두고 noindex를
다느냐. ADR 0086에서 dev 도메인을 처리할 때와 똑같은 논리로 후자를 골랐다. 이미 색인된
URL은 크롤러가 다시 와서 noindex를 읽어야 빠지는데, robots로 크롤을 막으면 그 noindex를
영영 못 읽는다. "색인은 됐는데 robots에 막힘" 상태로 박제되는 거다. 그래서

- robots disallow에서 `/me/`·`/onboarding/`을 아예 뺐다 (`/api/`·`/oauth/`만 남김 — 이 둘은
  HTML이 아니라 noindex를 실을 수 없다)
- `/me`, `/me/edit`, `/onboarding/nickname`, `/onboarding/team` 페이지(양 앱 8개 파일)에
  `robots: { index: false, follow: false }` 메타데이터를 달았다

배포 후 Search Console에서 `plick.co.kr/me` URL 제거 요청까지 하면 더 빨리 빠진다. 이건
코드 밖 운영 작업이라 TODO로 남긴다.

## 6. 페이지별 description 채우기

title만 있고 description이 없던 페이지들(릴스, 로그인, 회원가입, FAQ, 약관, 개인정보처리방침)에
`PAGE_DESCRIPTIONS`를 달았다. 사이트링크는 구글이 자동 생성이라 강제할 수 없지만, 생겼을 때
각 링크 아래 붙는 설명이 이 문구다. 지금처럼 비워 두면 사이트링크가 생겨도 본문 발췌가 붙어서
또 "홈릴스기사MY" 꼴이 난다. 기사 목록(web 전용)은 한 줄짜리 기존 문구를 팀명이 들어간 긴
문장으로 교체했다.

기사 상세와 팀 허브는 이미 페이지별 메타데이터가 잘 돼 있어서(KAN-346·350·351) 손대지 않았다.
사용자도 중간에 "기사들은 기존처럼 잘 나오면 된다"고 확인해 줬다.

## 7. 검증에서 걸린 것

빌드·타입·린트·포맷은 다 통과했고, 브라우저로 두 앱을 열어 meta·JSON-LD·소개 문구 렌더를
확인했다. 다른 세션이 이미 dev 서버(:3000, :3001)를 물고 있어서 이 세션의 서버를 못 띄우고
떠 있는 서버에 접속해 확인했다 — 같은 소스 디렉터리를 보는 서버라 HMR로 내 수정이 반영돼
있었다.

한 번 식겁한 건 모바일 소개 문구의 너비가 0으로 측정된 거였다. 글자가 한 줄에 한 자씩
세로로 1,353px 쌓인 것처럼 보였는데, 부모를 타고 올라가 보니 body부터 전부 width 0이었다.
`window.innerWidth`가 0 — 브라우저 패널이 접혀 있으면 뷰포트가 0×0이 되는 도구 쪽 아티팩트다
(스크린샷도 검게 나온다). `resize_window`로 375px를 강제하니 335px 폭에 3줄, 정상이었다.
레이아웃 버그가 아니라 측정 환경 문제였다.

## 8. 이번에 안 되는 것, 남는 것

- 사이트링크(쿠팡 아래 붙는 하위 링크 목록)는 마크업으로 신청하는 게 아니다. 섹션 구조,
  페이지별 고유 title·description, 내부 링크, 사이트맵까지 조건은 다 갖췄으니 나머지는
  브랜드 검색량과 시간의 몫이다.
- 사이트명 "플릭" 반영은 구글이 홈을 재크롤·재처리해야 한다. 수 일에서 수 주.
- 운영 TODO: 배포 후 Search Console에서 홈·`/me` 색인 갱신 요청, `/me` URL 제거 요청,
  리치 결과 테스트로 WebSite JSON-LD 확인.
- 크롤 시점에 피드가 비어 "아직 핫이슈가 없어요"가 긁힌 문제는 이제 소개 문구가 있어서
  스니펫이 그리로 갈 공산이 크지만, 비로그인 요청에서 피드 fetch가 실패하는 경우가 있는지는
  별도로 지켜볼 일이다.
