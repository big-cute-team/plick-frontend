# 0175. 전체 110% 확대, 선수단 포지션 네 줄, 릴스 흰 면에 검은 글자 (KAN-574)

KAN-567 리디자인([ADR 0171](0171-haechukimo-redesign.md))과 후속 수정([ADR 0172](0172-kan-569-ui-fixes.md))을
dev에서 써 보고 나온 티켓이다. 적힌 대로 옮기면 넷이다.

1. 전체를 110%로. 글자도 레이아웃도 너무 작다.
2. 팀 정보 페이지 선수단이 한 줄씩 좌라락 내려간다. 모바일과 웹 둘 다 포지션별로 나눠 한 줄씩, 네 줄이
   한 번에 보이게. 지금은 높이가 너무 크다.
3. 모바일은 선수단, 기사 속 인물, 기타를 탭으로 가른다.
4. 릴스. 웹은 카드가 높이를 늘 꽉 채우고 헤더 밑까지 닿게, 배경도 임베드가 꽉 채우게. 웹과 모바일 둘 다
   제목과 내용 뒤 그라데이션을 없애고 글자를 검게. 그러면 배경 그라데이션이 필요 없다.

## 1. 110%를 한 값으로: px 토큰을 rem으로 바꿨다

처음 떠올린 건 제일 싼 방법 둘이었다.

하나는 CSS `zoom: 1.1`을 `html`에 거는 것이다. 한 줄이고 px까지 전부 커진다. 그런데 Chrome 128부터
`zoom`이 표준화되면서 확대된 요소 안의 길이 계산이 바뀌었다. `100dvh` 같은 뷰포트 단위도 zoom 배율을 받아
실제 화면의 110%가 된다. 앱 셸은 `h-[100dvh]`로 화면 높이를 못박고 그 안에서 스크롤하는 구조라, 셸이 화면보다
10% 길어져 하단 탭바가 화면 밖으로 밀린다. `getBoundingClientRect`로 재는 릴 임베드 영역 계산도 zoom 좌표계와
얽힌다. 버렸다.

다른 하나는 모바일 뷰포트 메타의 `initial-scale=1.1`이다. 레이아웃 뷰포트를 1/1.1로 줄여 브라우저가 통째로
확대해 주므로 dvh도 맞는다. 그런데 데스크톱 웹은 뷰포트 메타를 무시하고, `width=device-width`와 같이 쓰면
브라우저마다 레이아웃 폭을 정하는 규칙이 달라 가로 스크롤이 생길 수 있다. 두 앱에 같은 답을 주지 못해 버렸다.

남은 게 rem이다. rem은 루트 요소(`html`)의 font-size를 1로 치는 단위다. 브라우저 기본값이 16px이니
`1rem = 16px`이고, `html { font-size: 110% }`를 걸면 `1rem = 17.6px`가 된다. 모든 크기가 rem이면 이 한 값으로
전부 10% 커진다. 다행히 Tailwind v4의 숫자 간격 유틸(`p-4`, `h-9`, `gap-1.5`)은 `--spacing: 0.25rem`을 곱해 만들어서
이미 rem이다. 문제는 `packages/tokens/theme.css`의 `@theme` 토큰이었다. 글자 크기(`--text-body: 13.5px`),
컨테이너 폭, 간격(`--spacing-edge: 16px`), 라운드가 전부 시안 px 그대로였다. 이것들을 16으로 나눠 rem으로 바꿨다
(`13.5px → 0.84375rem`). 주석의 px는 시안 값으로 남겨 두고 블록 머리에 "16px = 1rem 기준, 실제 크기는 110%를
곱한 값"이라고 적었다. `--radius-pill: 999px`는 "끝까지 둥글게"라는 뜻이라 그대로 뒀다.

`html { font-size: 110% }`는 `theme.css`에 넣되 `@layer base` 안에 뒀다. 레이어 밖 CSS는 레이어 안 CSS를 항상
이긴다. 리디자인 때 레이어 밖 `a { color }`가 `text-accent` 유틸을 눌러 활성 탭 색이 안 먹었던 적이 있다
([ADR 0171](0171-haechukimo-redesign.md)). 지금은 html에 글자 크기 유틸을 달 일이 없지만 같은 함정을 다시 파지 않으려고
base 레이어로 넣었다.

미디어 쿼리는 영향을 받지 않는다. 미디어 쿼리 안의 rem은 루트 font-size가 아니라 브라우저 초기값(보통 16px)을
기준으로 계산하도록 스펙에 정해져 있다. 그래서 Tailwind의 `lg:`(64rem)는 여전히 1024px에서 갈린다. 확대 때문에
태블릿 폭에서 레이아웃이 데스크톱으로 넘어가는 일은 없다.

토큰만 바꾸면 끝이 아니었다. rem을 안 거치는 크기가 세 부류 남아 있었다.

첫째, 숫자 prop으로 크기를 받아 인라인에 px로 박는 공용 컴포넌트다. 아이콘(`size={16}`이 SVG
`width={16}`이 된다), `TeamCrest`, `LiveCrest`, `PlayerPhoto`, `Logo`가 그랬다. 이걸 그대로 두면 글자는 커지는데
아이콘과 엠블럼만 옛 크기로 남아 비율이 어긋난다. `@plick/domain/format`에 `rem(px)` 헬퍼를 두고 전부 거치게 했다.
아이콘은 SVG의 `width`, `height` 속성에 `"1.25rem"` 같은 문자열을 넣는다. 속성(presentation attribute)은 CSS 우선순위가
가장 낮아서, 쓰는 쪽이 `className`으로 `size-5`를 주면 그게 이긴다. 인라인 `style`로 넣었다면 클래스를 눌러 버렸을 것이다.
크레스트류는 원래부터 인라인 style이었는데, Tailwind preflight의 `img { height: auto }`가 height 속성을 무시해서라고
주석에 있다. 거기는 style 안의 값만 rem으로 바꿨다.

둘째, 임의값(arbitrary value) 클래스의 px다. `grid-cols-[36px_minmax(0,1fr)_64px]` 같은 표 열 폭이 스무 군데 남짓
있었다. 글자가 커지는데 열 폭이 그대로면 숫자가 잘린다. 스크립트로 `grid-cols-[…]` 안의 px만 골라 rem으로 바꿨다.
웹 헤더 높이 변수 `--site-header-h: 98px`도 sticky 요소의 top 오프셋이라 `calc(6rem + 2px)`로 바꿨다. 바 두 줄
58 + 38은 rem으로 커지고 선 두 줄 2px는 선이라 그대로다. `SideRail`의 `+22px`, 라인업의 `text-[9.5px]`,
릴 트윗 아바타 크기도 같은 이유로 rem이 됐다.

셋째, 일부러 px로 둔 것들이다. 1px, 2px 선 두께는 커지면 오히려 굵어 보여 뒀다. 모바일 앱 셸의 `max-w-[480px]`는
"폰 폭 이상으로 넓어지지 않게"라는 기기 기준이라 뒀다. 폰은 어차피 480보다 좁아 영향이 없다. OG 이미지(`OgCard`)는
satori가 1200x630 캔버스에 그리는 별도 렌더라 손대지 않았다.

이 규칙은 `apps/CLAUDE.md` 스타일 절에 적었다. 임의값이 필요하면 rem으로, 숫자 크기 prop은 `rem()`으로.

확대 뒤 루트 font-size가 두 앱 다 `17.6px`로 잡히는 걸 헤드리스 Chromium에서 확인했다. 웹 홈(1440x900)과 모바일 홈
(390x844)을 찍어 보니 글자, 간격, 엠블럼, 아이콘이 같이 커지고 넘치는 데는 없었다. 웹 페이지 최대폭이 1280에서
1408px가 됐는데 1440 창에서 좌우 거터 안에 들어간다.

## 2, 3. 선수단: 한 명씩 행에서 포지션 네 줄로, 모바일은 탭으로

전에는 두 앱 다 선수단을 포지션 순(GK, DF, MF, FW)으로 한 명씩 행을 이어 깔았다. 모바일은 `SquadList`(등번호, 이름,
포지션 줄), 웹은 `SquadTable`(번호, 이름, 포지션 열 표)이었다. 한 팀 등록 명단이 서른 명 가까우니 행 높이 40px만
잡아도 1200px, 화면 두세 장이다. 모바일은 그 밑에 기사 속 인물, 관련 이슈, 기본 정보가 섹션으로 이어져 있어서 인물까지
가려면 한참 내려가야 했다. KAN-484에서 탭으로 갈랐던 걸 KAN-567이 시안대로 섹션으로 되돌린 결과였다.

바꾼 모양은 이렇다. 포지션 하나가 한 줄이고, 줄 머리에 포지션 이름, 그 옆은 선수 칩(등번호 + 이름)이 가로로 흐르는
트랙이다. 네 줄이면 명단 전체가 한 화면에 든다. 포지션 열은 줄 머리가 대신하니 칩에는 안 넣었다. 칩을 누르면 전처럼
시즌 스탯 시트(모바일)나 다이얼로그(웹)가 열린다. 선수가 없는 포지션 줄은 그리지 않는다.

모바일 트랙은 손가락으로 민다. 트랙에 `-mr-edge pr-edge`를 줘서 오른쪽 화면 끝까지 칩이 흘러 나가게 했다.
잘린 칩이 화면 끝에 걸쳐 보이는 게 "더 있다"는 신호다.

웹은 그렇게 두면 안 됐다. 마우스 휠은 세로로만 굴러서 가로 트랙을 넘길 방법이 없다. 트랙패드가 없는 사람은 수비수
열 명 중 여덟 명만 보고 끝난다. 그래서 줄마다 오른쪽에 좌우 버튼을 달았다(`SquadTrack`). 홈 핫이슈 캐러셀
(`HotCarousel`, KAN-569)과 같은 규칙이다. 버튼은 트랙 폭만큼 `scrollBy`하고, `scroll` 이벤트와 `ResizeObserver`로
양 끝 도달을 재서 끝이면 꺼진다. 한 줄에 다 들면 둘 다 꺼진 채 남는다. 끝 판정에 1px 여유를 둔 건 트랙 폭이 소수점이면
`scrollLeft + clientWidth`가 `scrollWidth`에 1px 못 미쳐 영원히 "끝 아님"이 되기 때문이다. 줄마다 상태가 따로라
한 컴포넌트가 줄 하나를 맡는다.

모바일은 탭도 붙였다. 선수단, 기사 속 인물, 팀 정보 셋이다. 팀 정보에는 관련 이슈 링크와 기본 정보를 넣었다.
탭 줄 생김새는 경기 상세 탭 줄(`MatchTabBar`)과 같게 했다. 13.5px, 활성은 굵은 글자에 2px 강조 밑줄이다. 탭 줄은
스크롤 영역 안에서 `sticky top-0`이라 선수단을 보다가 내려가도 위에 붙어 있다. 웹 `TeamProfileTabs`와 같이 탭은 URL로
올리지 않고 컴포넌트 상태로 뒀다. 색인할 대상은 팀이지 탭이 아니다.

팀 정보 탭 내용은 서버 컴포넌트 페이지가 JSX로 만들어 `info` prop으로 넘긴다. 탭 컴포넌트는 상태가 있어 클라
컴포넌트(`"use client"`)인데, 서버 컴포넌트가 만든 JSX를 prop으로 받는 건 된다. 서버에서 이미 렌더된 결과(RSC
페이로드)가 넘어오는 것이라 그 안의 `Link`나 `ProfileFacts`가 클라 번들로 끌려 들어가지 않는다. 클라 컴포넌트가
서버 컴포넌트를 직접 import하는 것과는 다르다.

탭 키와 라벨은 `_types/team-profile.ts`, `_constants/team-profile.ts`에 뒀다. 웹에도 같은 이름 파일이 있지만 모바일에만
`info` 탭이 있어 앱별로 둔다([ADR 0011](0011-shared-code-boundary.md)).

E2E 한 곳이 걸렸다. `tests/e2e/specs/mobile/articles.spec.ts`가 팀 프로필에 들어가서 h2 "선수단"을 찾고 있었다.
이제 "선수단"은 탭이라 `getByRole("tab", { name: "선수단", selected: true })`로 바꿨다.

## 4. 릴스: 흰 면에 검은 글자

### 모바일

전에는 [ADR 0172](0172-kan-569-ui-fixes.md)에서 되돌린 풀스크린 구조였다. 밝은 회색 배경(`bg-reel-bg`) 위에 트윗 임베드가
제목 윗선까지를 채우고, 아래 42%에 어두운 스크림(가독성용 반투명 그라데이션)을 깔아 흰 글자로 팀, 제목, 기자를 얹었다.
레일 아이콘도 흰색에 `drop-shadow`, 탭바는 스크림을 깐 `overlay` 변형이었다.

써 보니 어색했던 이유가 티켓에 그대로 있다. 배경도 흰 톤이고 트윗 카드도 흰색인데 그 아래에만 검은 안개가 깔려
화면이 탁했다. 흰 글자를 읽히게 하려고 스크림이 있는 것이니, 글자를 검게 바꾸면 스크림 자체가 필요 없다.

그래서 스크림 레이어를 통째로 지웠다. 이 레이어는 시트가 열릴 때 제목과 같이 `translateY`로 올라가 도킹된 제목 뒤를
받치던 것이라 드래그 변수(`--reel-sheet-drag-y`) 수신자로도 등록돼 있었는데, 그 등록도 같이 사라졌다. 제목 블록 쪽
등록은 그대로라 시트 드래그 동안 제목은 전처럼 손가락을 따라간다. 시트 딤은 `rgba(15,18,20,.32)`로 옅어서 도킹된
검은 제목이 그 위에서도 읽힌다.

팀 이름, 제목, 기자명은 `text-text-strong`, 시각은 `text-text-3`로 바꿨다. 레일은 `text-text-strong`에 그림자를 뺐다.
눌린 좋아요 빨강은 그대로다. 레일 주석에는 비로그인 시트를 왜 부모가 그리는지(필터나 transform이 걸린 조상이
`position: fixed`의 기준 상자가 되는 문제)가 적혀 있었는데, 그림자가 빠져도 이유는 유효해서 일반화해 남겼다.

사진 릴은 따로 생각해야 했다. 지금 발행 릴은 전부 트윗 임베드지만 `imageUrl`이 오면 사진이 릴 전체를 덮는 구조였다.
검은 글자가 사진 위에 올라가면 어두운 사진에서 안 읽힌다. 사진도 임베드와 같은 영역(safe-area부터 제목 윗선까지)만
덮게 바꿨다. `<img>`에 `top`과 `bottom`만 주면 늘어나지 않는다. img는 대체 요소(replaced element)라 높이가 auto면
절대 위치의 top/bottom 사이를 채우지 않고 원본 비율의 높이를 쓴다. 그래서 영역 div를 하나 두고 그 안에서
`size-full object-cover`로 채웠다.

탭바 `overlay` 변형도 스크림 위 흰 글자용이었다. 밝은 배경 위에서 흰 dim 아이콘은 안 보인다. 변형을 없애면 탭바가
흐름 안(`shrink-0`)으로 들어와 릴 높이가 54px 줄고, 레일과 정보 블록의 하단 여백(탭바 높이만큼 띄워 둔 값)과 시트
높이 비율까지 다시 맞춰야 한다. 그래서 변형은 남기되 생김새를 solid와 같게 했다. 흰 바탕, 위 선, 강조색 활성 탭이고
차이는 `absolute`로 떠 있다는 것뿐이다. 오버레이 때문에 갈라 놓았던 `accent-bright` 분기도 빠졌다.

### 웹

전에는 시안의 396x704 어두운 카드(`bg-reel-dark`)였다. 뷰어 섹션에 위아래 30px 여백이 있고 카드는 `max-h-176`
(704px)에서 멈췄다. 큰 창에서는 회색 바탕 가운데에 카드가 작게 떴고, 카드 안에는 흰 트윗 상자가 어두운 면 위에
여백을 두고 따로 떠 있었다. 하단은 그라데이션 위 흰 글자, 좁은 폭 오버레이 레일 뒤에는 오른쪽 스크림이 또 있었다.

바꾼 건 이렇다. 섹션의 `py-7.5`와 카드의 `max-h-176`을 지웠다. 카드는 `h-full`에 `aspect-[9/16]`이라 뷰어 높이
(창 높이에서 헤더를 뺀 값)를 그대로 받고 폭은 비율이 정한다. 헤더 바로 밑부터 창 바닥까지 찬다. 카드 바탕을 흰
`bg-bg`로 바꾸고 트윗을 감싸던 흰 상자와 여백을 걷어, 임베드가 카드 면을 채운 모양이 됐다. 하단 그라데이션과 오른쪽
스크림을 지우고 글자를 본문색으로 바꿨다. 사진은 모바일과 같은 이유로 제목 윗선까지만 덮는다.

레일은 두 톤(`media` 흰색, `surface` 회색 원)을 갈라 쓰고 있었다. 카드가 흰 면이 되니 카드 안 오버레이 레일도
`surface`와 같은 톤이어야 해서, `tone` prop과 `TONE` 표를 지우고 회색 원(`bg-avatar`)에 본문색 아이콘 하나로 합쳤다.
로딩 자리(`ReelSkeleton`)도 같은 흰 카드, 같은 높이로 맞췄다. 안 맞추면 데이터가 도착하는 순간 카드 크기가 튄다.

1440x900 창에서 찍어 보니 카드가 헤더 밑 108px부터 900px 바닥까지 792px 높이로 서고, 트윗이 흰 면 가운데, 제목과
기자가 그 밑에 검게 선다.
