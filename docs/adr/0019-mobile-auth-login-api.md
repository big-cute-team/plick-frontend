# ADR 0019 — 모바일 로그인 API 연결 (KAN-253)

- **상태:** Accepted
- **날짜:** 2026-07-20
- **관련:** [ADR 0017 API 연결 전략](0017-api-integration-strategy.md) · [ADR 0011 공용 경계](0011-shared-code-boundary.md) · `api-integration` 스킬

퍼블리싱만 돼 있던 모바일 로그인 화면에 처음으로 진짜 BE를 붙였다. 엔드포인트는 `/api/v1/auth/login` 하나. 첫 API 연결이라 스킬이 시키는 대로 앱별로만 붙이고, 공용화는 손대지 않았다.

## 스웨거부터 열어봤다

티켓엔 경로만 있어서 스웨거(`localhost:8080/v3/api-docs`)를 먼저 읽었다. 로그인은 `provider`·`code`를 body로 받고, 응답은 `{ code, message, data }` 봉투 안에 `accessToken`·`refreshToken`·`needsOnboarding`을 담아 준다. 태그가 `mock-auth`라 아직 진짜 OAuth는 아니고, `code`가 `"existing"`이면 기존 유저, 아니면 신규 자동가입으로 `needsOnboarding=true`를 준다.

실제로 curl로 때려보니 응답 봉투가 모든 엔드포인트 공통이었다. 그래서 `apiFetch`를 만들 때 아예 봉투를 벗겨 `data`만 돌려주도록 했다. 에러도 봉투에 `code`(예: `COMMON_INVALID_PARAM`)로 오길래 `ApiError`에 그 코드를 실어 두었다. 나중 엔드포인트들도 같은 봉투라 이 래퍼를 그대로 재활용할 수 있을 것이다.

## 토큰을 어디 두느냐가 유일한 고민이었다

로그인은 단발 읽기가 아니라 "토큰을 받아서 저장하는" 쓰기라, 스킬의 서버 fetch/RQ 분기표엔 딱 안 맞았다. 뮤테이션이지만 낙관적 업데이트(응답을 기다리지 않고 UI부터 바꿔 두는 것)가 필요한 것도 아니어서 클라 캐시 라이브러리인 TanStack Query(RQ)를 깔 이유가 없었다. 그래서 **서버 액션** 하나로 처리했다.

서버 액션은 클라이언트 버튼이 부르지만 코드 자체는 서버에서 도는 함수다(파일 맨 위 `"use server"`). 버튼이 이걸 부르면 브라우저는 함수 인자만 서버로 보내고, 실제 BE 로그인·토큰 저장은 전부 서버에서 벌어진다. 그래서 이 방식이 토큰을 다루기에 깔끔했다 — 토큰이 브라우저 JS를 거칠 일이 아예 없다.

토큰은 **HttpOnly 쿠키**에 심었다. HttpOnly는 자바스크립트로 못 읽는 쿠키라, XSS(스크립트 주입 공격)로 스크립트가 끼어들어도 토큰을 훔칠 수 없다. 대신 브라우저가 요청마다 자동으로 실어 보내니 서버는 언제든 읽을 수 있다. 검증할 때 임시 라우트를 만들어 확인해 보니, 서버는 쿠키를 읽는데 `document.cookie`엔 안 잡혔다 — 노린 대로였다. 나중에 인증이 필요한 보호 API가 생기면 서버 컴포넌트가 이 쿠키에서 accessToken을 읽어 `Authorization: Bearer …` 헤더로 실으면 된다. 그 주입 자리는 `apiFetch` 헤더에 주석으로만 열어 뒀다.

성공 후 라우팅은 `needsOnboarding`으로 갈랐다. BE는 신규 자동가입 유저면 이 값을 `true`로 주는데, true면 온보딩 첫 단계(`/onboarding/nickname`)로, 기존 유저면 홈(`/`)으로 redirect한다. 온보딩은 이미 퍼블리싱돼 있어서 닉네임(1/2)의 "다음"이 마이팀(2/2)으로, 마이팀의 "시작하기"가 홈으로 링크가 이어져 있다 — 그래서 로그인은 진입점 하나만 열어 주면 나머지 두 단계는 각 페이지가 알아서 넘긴다. 진입 경로는 `ONBOARDING_ENTRY` 상수로 뒀다. 지금 mock-auth는 `code`가 `"existing"`이 아니면 전부 신규로 쳐서 `needsOnboarding=true`를 주기 때문에, 실제로 로그인하면 늘 온보딩으로 들어간다(기존 유저 분기는 진짜 OAuth가 붙어 `"existing"` 코드가 올 때 살아난다).

온보딩 단계에서 고른 닉네임·팀을 BE에 저장하는 건 아직 안 붙였다(스웨거의 `/users/me/onboarding`). 이 티켓은 로그인까지라, 저장은 온보딩 티켓에서 잇는다.

## 화면은 거의 안 건드렸다 — 상호작용 조각만 클라로 떼어냈다

`AuthScreen`은 그대로 서버 컴포넌트로 뒀다. Next의 App Router는 아무 표시가 없으면 컴포넌트를 서버에서만 렌더하고 브라우저로는 JS를 안 내려보낸다. 로고·태그라인처럼 가만히 있는 화면엔 이게 맞다 — JS가 안 실리니 그만큼 가볍다. 문제는 버튼이다. `onClick`·`useState` 같은 상호작용은 브라우저에서 도는 코드라야 하고, 그러려면 파일 맨 위에 `"use client"`를 붙여 "여기서부턴 클라이언트"라고 선을 그어야 한다. 그 선이 **클라이언트 경계**다.

그래서 화면 전체를 클라로 만들지 않고, 카카오/구글 버튼 묶음만 `SocialLoginActions`라는 작은 `"use client"` 컴포넌트로 떼어냈다. 상호작용이 필요한 조각만 경계 안으로 넣은 것 — 나머지 화면은 여전히 서버 렌더다.

이 클라 컴포넌트가 하는 일은 둘이다. 첫째는 **버튼 잠금**. 사용자가 카카오 버튼을 연타하면 로그인 요청이 두 번 날아갈 수 있는데, 이걸 막으려 `useTransition`을 썼다. 리액트 훅인데, 넘겨준 비동기 작업이 도는 동안 `isPending`이 `true`가 된다. 그 값을 두 버튼의 `disabled`에 물려, 로그인 액션이 끝날 때까지(성공해 홈으로 넘어가거나 실패 메시지가 뜰 때까지) 버튼을 못 누르게 잠근다. 그냥 `useState`로 로딩 불리언을 직접 켜고 꺼도 되지만, 서버 액션의 진행 상태를 다루는 데는 `useTransition`이 리액트 19가 미는 정석이라 그걸 따랐다. 둘째는 **에러 표시**. 로그인 액션이 실패하면 `{ error }` 객체를 돌려주는데, 그걸 받아 버튼 아래 `text-danger`로 띄운다. 성공하면 서버 액션이 알아서 홈으로 redirect하니 클라에서 따로 할 게 없다.

버튼 원자 자체인 `SocialLoginButton`(공용 `@plick/ui`)엔 `onClick`·`disabled` 두 prop만 옵셔널로 열어 줬다. 원래 표현 전용이라 핸들러가 없었는데, 옵셔널로 더한 거라 이 prop을 안 넘기는 웹 쪽 사용처는 그대로 컴파일된다. 공용 패키지를 건드린 셈이라 웹까지 클린 빌드로 회귀를 확인했다.

로그인·회원가입이 같은 `AuthScreen`을 쓰니 이 버튼 묶음도 한 번에 양쪽에 붙었다. 회원가입 버튼도 같은 `login`을 부른다 — mock-auth라 provider만 맞으면 신규 유저를 만들어 주기 때문에, 지금 단계에선 로그인/가입이 같은 호출이다.

## 공용화는 안 했다

`apiFetch`도 로그인 fetcher도 mobile `_lib`에만 뒀다. 스킬 게이트대로 첫 앱은 앱별. 웹에도 같은 로그인 화면이 있어서 두 번째로 붙일 때 `apiFetch`가 같은 봉투·같은 쿠키 규약을 쓰게 되면, 그때 `@plick/core` 같은 데로 올릴지 판단하면 된다. 지금 미리 빼면 웹에서 안 쓰는 추상화를 떠안는 꼴이라 참았다.

## 네트워크 탭에 BE 호출이 안 보여서 잠깐 헷갈렸다

다 만들고 네트워크 탭을 보다 잠깐 멈칫했다. 로그인 버튼을 눌러도 `/api/v1/auth/login`(8080) 호출이 안 보였기 때문이다. 곰곰이 보니 당연했다 — 서버 액션이라 브라우저가 BE를 직접 때리는 게 아니라, 브라우저는 Next 서버 액션(`POST /login`)만 부르고 진짜 8080 호출은 서버 안에서 서버끼리 오간다. 브라우저 네트워크 탭엔 그 서버-서버 구간이 안 잡힌다. HttpOnly로 토큰을 숨긴 것의 대가이자 목적이기도 하다. BE 호출을 눈으로 보고 싶으면 프런트가 아니라 BE 로그를 봐야 한다.

그 `POST /login`마저 성공하면 곧장 홈으로 넘어가며 네트워크 로그가 갈아엎어져 순식간에 사라진 것처럼 보인다. DevTools의 Preserve log를 켜야 리다이렉트 뒤에도 남는다. 그리고 이 요청은 `303 See Other`로 뜨는데, 서버 액션이 POST 맥락에서 `redirect()`를 하기 때문이다 — POST는 처리했으니 홈은 GET으로 가져오라는 표준 PRG(Post-Redirect-Get) 신호다(같은 `redirect()`도 GET 렌더 중이면 307로 뜬다). 버그가 아니라 정상 동작이다.

## 막힌 데

lint가 `API_BASE_URL`·`NODE_ENV`를 turbo가 모르는 env라고 경고를 띄웠다. `turbo.json`에 `globalEnv`로 선언해 풀었다. 이걸 안 하면 turbo 캐시가 env 변화를 못 읽어 잘못된 캐시를 줄 수 있으니 경고가 맞다.

검증은 실제 BE에 붙여 네 상태를 다 밟았다. 성공(쿠키 심김·홈 이동), 신규 유저(구글, 역시 홈), 에러(BE 포트를 죽은 걸로 바꿔 실패 메시지 확인), 회원가입 경로까지. mock의 "항상 성공·즉시"에 속지 말라는 스킬 경고가 실제로 유효했다 — 에러 상태는 BE를 꺼봐야 재현됐다.
