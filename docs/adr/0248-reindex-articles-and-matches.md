# 0248. 기사를 다시 색인 대상으로 돌리고 사이트맵이 기사와 경기를 스스로 싣게 한다

2026-11-06. 티켓은 KAN-738([FE] seo, geo 에 다시 모든 기사들이 색인이 되도록 수정)이다. 브랜치는
`feature/KAN-738-reindex-articles`.

## 티켓이 말한 것과 실제로 빠져 있던 것

티켓 본문은 한 줄이었다. "모든 기사들과 홈, 경기, 예측, 투표 정도(의미없는 페이지들 제외, faq, mypage 같은
것들 제외) 다시 seo에 자동으로 잡히도록 수정". 그래서 먼저 지금 무엇이 색인에서 빠져 있는지부터 전수로 봤다.
두 앱의 `robots.ts`, `sitemap.ts`, 그리고 `robots:` 메타데이터를 주는 페이지를 grep으로 다 뽑았다.

결과는 생각보다 좁았다. 홈과 팀 허브, 라이브 목록, 순위표, 투표 허브(`/debates`), 웹의 예측 랭킹
(`/rankings`)은 이미 사이트맵에 있고 noindex도 아니었다. 경기 상세(`/live/matches/{id}`)도 noindex가
아니었고 canonical까지 제대로 걸려 있었다. 다만 사이트맵에는 없어서 팀 프로필의 경기 탭 링크를 타고
와야만 발견되는 상태였다. 실제로 색인이 막혀 있던 건 두 가지뿐이었다. 기사 상세(`/articles/{id}`)와 릴
딥링크(`/reels/{id}`)다. 둘 다 2026-10-30에 KAN-652([ADR 0220](0220-adsense-low-value-content-response.md))
에서 내가 직접 막은 것이다.

그때 사정을 다시 적어 둔다. 애드센스가 사이트를 "가치가 별로 없는 콘텐츠"로 거절했고, 원인을 재구성해 보니
기사 본문이 트윗 두 문장 요약(100자 남짓)인데 그런 페이지가 사이트맵 5,215개 URL의 거의 전부였다. BE 요약
파이프라인은 건드릴 수 없었으니 "구글이 보는 페이지 집합"을 줄이는 쪽으로 갔다. 기사와 릴에
`robots: { index: false, follow: true }`를 걸고, 사이트맵에서 기사를 걷어 오던 루프를 통째로 지워 22개짜리
정적 목록으로 만들었다. ADR 0220의 "남은 것"에는 이렇게 적어 뒀다. "Search Console에서 기사 URL 검색 유입
비중 확인. 컸다면 noindex를 되돌릴지 판단한다."

이번 티켓이 그 판단이다. 이 서비스에서 검색어에 걸릴 수 있는 고유한 문서는 기사다. 선수 이름과 구단
이름이 제목에 들어간 수천 개의 롱테일 랜딩이고, AI 검색(티켓의 "geo", Generative Engine Optimization의
줄임말로 AI 답변에 인용되게 하는 최적화를 말한다)이 인용할 문서도 기사다. 그걸 통째로 색인에서 뺀 채로
두면 광고 승인 하나를 위해 유입 전체를 내주는 셈이라 되돌리기로 했다. 애드센스 재심사와는 맞부딪히는
결정이라는 점은 끝의 "남은 것"에 따로 적었다.

## 기사 noindex를 푸는 방법

기사 페이지 `generateMetadata`에서 `robots` 줄을 지웠다. 두 앱 두 파일이다. `index: true`로 바꾸지 않고
지운 데는 이유가 있다.

Next의 메타데이터는 루트 레이아웃부터 페이지까지 내려오면서 필드 단위로 덮어쓴다. 페이지가 `robots`를
주면 레이아웃의 `robots`를 통째로 대체하고, 안 주면 레이아웃 값이 그대로 내려온다. 루트 레이아웃은
`robots: IS_PRODUCTION_SITE ? undefined : { index: false, follow: false }`다(KAN-380). dev 환경
(`dev.plick.co.kr`)은 prod와 같은 콘텐츠라 색인되면 중복 콘텐츠가 되니 빌드 시점에 굳는 사이트 URL로
갈라 dev 빌드 전체에 noindex를 건 것이다. 여기서 기사 페이지가 `robots: { index: true }`를 주면 dev
빌드에서도 레이아웃의 noindex를 덮어써 dev 기사가 색인 대상이 된다. 아무것도 안 주면 prod에서는 robots
메타 자체가 안 나가고(검색 엔진의 기본값은 색인 허용이다) dev에서는 레이아웃의 noindex가 붙는다. 그래서
지우는 게 맞다. KAN-652 이전 코드도 그 모양이었다.

## 릴 딥링크는 풀지 않았다

KAN-652 이전에는 릴 딥링크도 색인 대상이었고 웹 사이트맵에 기사와 나란히 실렸다. 이번에 같이 되돌릴지
고민했는데 안 풀었다. 릴은 기사와 같은 `articleSummaryId`의 같은 요약을 세로 화면으로 보여 줄 뿐이라
본문이 같은 URL이 두 벌 생긴다. canonical도 각자 자기 자신을 가리키고 있어서 검색 엔진 눈에는 중복 문서다.
애드센스가 문제 삼은 "얇은 페이지 대량 생산"에서 페이지 수를 정확히 두 배로 불리던 게 이 릴 URL이었다.
티켓이 나열한 목록(기사, 홈, 경기, 예측, 투표)에도 릴은 없다. 그래서 색인 정본은 기사 하나로 두고 릴은
`noindex, follow`를 유지했다. 주석만 "KAN-652와 같은 이유"에서 "기사가 정본이라서"로 고쳤다. 릴스 피드
(`/reels`)는 전처럼 사이트맵에 진입점으로 남는다.

## 사이트맵이 다시 BE를 걷는다

"자동으로 잡히도록"의 몫이 여기다. 페이지가 색인 가능해도 검색 엔진이 URL을 알아야 오는데, 기사는 하루에
수십 건씩 늘고 홈 목록에서는 금방 밀려난다. 사이트맵이 BE의 기사 전건을 실어야 새 기사가 사람 손 없이
크롤러에게 알려진다.

KAN-652에서 지운 루프를 되살렸는데 그대로 복붙하지는 않았다. 예전에는 두 앱 `sitemap.ts`가 같은 커서
페이징 루프와 상한 상수, 로그 문구를 각자 들고 있었다. 이번에 `@plick/core/sitemap`을 만들어
`collectSitemapArticles()`와 `collectSitemapMatchIds()`로 모았다. 앱은 id를 받아 자기 도메인 URL만
조립한다. 공용화 기준(ADR 0011 게이트 C, 두 번째 사용처가 생기면 승격)에 맞고, 무엇보다 `packages`에
있어야 `tests/unit`에서 `fetch`를 stub해 테스트를 붙일 수 있다. 사이트맵은 깨져도 화면에 안 보이는
라우트라 조용히 잘못되기 쉽다.

기사 수집은 이렇게 돈다. BE 목록 API(`GET /api/v1/articles`)는 커서 페이징이고 한 번에 최대 30건이다.
총 건수도 페이지 번호도 없어서 첫 페이지부터 `nextCursor`를 따라 끝까지 순서대로 걸어야 한다. 병렬로 못
돌린다. 걸으면서 id와 발행 시각만 모으고, 발행 시각이 사이트맵의 `lastmod`가 된다.

던지지 않는 게 이 함수들의 계약이다. 사이트맵이 500이면 크롤러는 사이트 전체를 의심한다. 그래서 BE가
중간에 죽으면 그때까지 모은 기사만 돌려주고 `console.error`를 남긴다. 첫 페이지부터 실패하면 빈 배열이고
사이트맵에는 정적 라우트만 나간다. 상한(45,000건)에 닿아 잘리는 경우도 로그를 남긴다. 조용히 잘리는 게
제일 위험해서다.

### force-dynamic인데 왜 캐시가 사는가

사이트맵 라우트에는 다시 `export const dynamic = "force-dynamic"`이 붙었다. 이게 없으면 Next는 사이트맵을
빌드 때 한 번 만들어 정적 파일로 굳힌다. 그러면 두 가지가 틀어진다. CI 러너는 BE에 닿지 못하니 빌드 중
fetch가 실패하고, 닿는다 해도 기사 목록이 빌드 시점에 멈춰 다음 배포까지 새 기사가 안 실린다.

그러면 크롤러가 올 때마다 BE를 99번 부르느냐 하면 그렇지 않다. `force-dynamic`이 바꾸는 건 "라우트 함수를
요청마다 실행한다"와 "캐시 옵션을 명시하지 않은 fetch를 no-store로 낮춘다" 두 가지다. `apiFetch`는 익명
GET에 `next: { revalidate: 60 }`을 명시하고 팀 경기 fetcher도 60초를 명시한다. 명시한 fetch는 Next의
데이터 캐시(fetch 응답을 서버에 저장해 두는 층)를 그대로 탄다. 그래서 함수는 매번 돌지만 안의 fetch는
60초 동안 저장분을 돌려준다. 실측으로 첫 요청이 5.2초, 바로 다음 요청이 0.035초였다.

ISR(`export const revalidate = 3600`)로 바꾸는 것도 생각했다. 그러면 응답에 `s-maxage`가 붙어
CloudFront가 한 시간 들고 있을 수 있다. 버린 이유는 배포 직후의 구멍이다. ISR 라우트는 빌드 때 첫 판을
만드는데 CI에서는 BE에 못 닿으니 기사 없는 사이트맵이 첫 판이 된다. 그 판이 배포 뒤 한 시간 동안 나간다.
배포가 잦은 저장소라 그 구멍이 자주 열린다. 검증된 예전 방식으로 돌아가는 쪽을 택했다.

## 경기 상세를 어디서 가져올 것인가

티켓이 경기와 예측을 따로 짚었다. 예측은 독립 URL이 없다. 경기 상세의 예측 탭과 투표 허브 안에 있고
모바일의 예측 의견 상세(`/live/predictions/{id}`)는 사람마다 잠금이 다른 화면이라 noindex가 맞다. 그러니
경기 상세가 사이트맵에 실리면 경기와 예측이 같이 풀린다.

문제는 경기 id 목록을 어디서 얻느냐였다. 처음 본 건 경기 목록 API(`GET /api/v1/matches?date=`)다. 날짜
하나씩만 받는다. 오늘 앞뒤 7일을 훑으면 15번인데, 그러면 시즌 초 경기가 빠지고, BE가 이 호출을 외부
축구 데이터 API로 넘기는데 과거 날짜의 캐시 수명을 내가 모른다. 사이트맵 요청마다 외부 API 할당량을 쓸
수 있는 구조를 확인 없이 넣고 싶지 않았다. BE 저장소에서 TTL을 찾아봤지만 상세 쪽 값만 보이고 날짜 목록
쪽은 바로 안 나와서 이 길은 접었다.

팀 시즌 경기(`GET /api/v1/teams/{teamId}/fixtures`)가 답이었다. 팀 프로필의 경기 탭이 쓰는 호출이고 한
팀의 시즌 전체(예정과 종료)를 한 번에 준다. BE가 상세를 내주는 경기는 빅6가 낀 경기뿐이라 여섯 팀을
부르면 그게 곧 전부다. 여섯 번을 `Promise.allSettled`로 병렬로 부르고 `Set`으로 중복을 접는다(빅6끼리
붙는 경기는 양쪽 목록에 다 있다). 한 팀이 502로 실패하면 그 팀 몫만 빠지고 로그가 남는다. 팀 프로필
페이지가 이미 사이트맵에 있어 크롤러가 올 때마다 도는 호출이니 BE 부하 면에서 새로 여는 길도 아니다.

경기 URL에는 `lastmod`를 안 넣었다. 스코어와 예측 집계가 계속 바뀌는 화면이라 킥오프 시각을 넣으면
거짓말이 되고, 현재 시각을 넣으면 매 요청마다 전부 바뀌었다고 말하는 셈이라 검색 엔진이 `lastmod`를
안 믿게 된다. 기존 주석 "경기 상세는 시즌 단위로 바뀌는 임시 URL이라 목록만 싣는다"는 지웠다. 시즌이
바뀌면 fixtures 응답이 바뀌고 사이트맵도 따라 바뀐다.

## llms.txt

`llms.txt`는 AI 어시스턴트가 사이트를 요약할 때 읽으라고 두는 마크다운 안내문이다. KAN-652 때 "기사는
색인 대상이 아니고(noindex) 사이트맵에도 없다"고 적어 놨으니 그대로 두면 AI 크롤러에게 기사를 보지
말라고 하는 꼴이다. 기사 상세에 무엇이 실리는지 한 줄, 전체 기사와 경기 목록은 사이트맵에 있다는 한 줄,
릴 딥링크는 같은 내용이라 noindex라는 한 줄로 바꿨다. `seo-text` 테스트는 KAN-652 때 "sitemap.xml이
없어야 한다"로 뒤집어 놨던 걸 다시 뒤집고, noindex라는 말이 릴 줄 하나에만 남는지 검사하게 했다.

## FAQ는 건드리지 않았다

티켓의 괄호 안 "faq, mypage 같은 것들 제외"를 두 가지로 읽을 수 있었다. 이번에 되살리는 범위에서 빼라는
뜻이거나, FAQ를 색인에서 내리라는 뜻이다. 앞쪽으로 읽었다. 마이페이지는 KAN-384부터 noindex고 사이트맵에도
없다. FAQ는 지금 사이트맵에 0.3 우선순위로 있고 FAQPage 구조화 데이터(KAN-623)가 붙어 있다. 색인에서
내리는 건 "다시 잡히게 한다"와 방향이 반대인 변경이라 묻지 않고 하지 않았다. 내리길 원하면 `STATIC_PAGES`
에서 한 줄 빼고 페이지에 noindex를 주면 된다.

## 검증

`pnpm format:check`, `test:hooks`(40), `test:unit`(342, 새 테스트 6개 포함), `lint`, `check-types`, `build`가
통과했다. 빌드 라우트 표에서 `/sitemap.xml`이 두 앱 모두 ○(정적)에서 ƒ(요청마다)로 바뀌었다.

새 단위 테스트(`tests/unit/sitemap-collect.test.mjs`)는 `fetch`를 stub해 여섯 가지를 본다. 커서가 끝날
때까지 걷는지, 상한에서 자르고 로그를 남기는지, 둘째 페이지에서 500이 나면 첫 페이지 분량만 돌려주는지,
첫 페이지부터 실패하면 빈 배열인지, 팀 여섯의 경기를 중복 없이 합치는지, 한 팀이 실패해도 나머지가
남는지다.

실제 응답은 prod 설정으로 빌드해서 봤다. 로컬 빌드는 사이트 URL이 localhost라 루트 레이아웃의 noindex가
전부 붙어 버려서 기사 noindex가 풀렸는지 구분이 안 된다. 그래서 `NEXT_PUBLIC_SITE_URL=https://plick.co.kr`
과 `API_BASE_URL=https://plick.co.kr/be`를 주고 빌드한 뒤 `next start`로 띄웠다(dev BE는 로컬에서
CloudFront 403이라 prod BE 읽기로 검증하는 건 ADR 0171 때부터 쓰는 방법이다). 읽기 전용 공개 GET만 부른다.

| 확인한 것                     | 웹(3064)         | 모바일(3061)     |
| ----------------------------- | ---------------- | ---------------- |
| `/sitemap.xml` 전체 URL       | 3,242            | 3,241            |
| 그중 기사                     | 2,948            | 2,948            |
| 그중 경기 상세                | 270              | 270              |
| 그중 릴 딥링크                | 0                | 0                |
| 첫 요청 시간                  | 5.2초            | 6.0초            |
| 둘째 요청 시간                | 0.035초          | 재지 않음        |
| `/articles/12101` robots 메타 | 없음             | 없음             |
| `/reels/12101` robots 메타    | noindex, follow  | noindex, follow  |
| `/live/matches/1557459`       | 200, robots 없음 | 200, robots 없음 |

전에는 웹 24개, 모바일 23개 URL이었다. 웹이 하나 많은 건 `/rankings` 때문이다. 기사 `lastmod`가 발행
시각으로 찍히는 것(`/articles/12101`이 `2026-11-06T02:17:36.000Z`)과 llms.txt의 새 세 줄, robots.txt의
사이트맵 줄도 봤다. 모바일 `/me`는 여전히 `noindex, nofollow`다.

첫 요청 5초는 걸리는 숫자다. 기사 2,948건이면 99번을 순서대로 왕복한다. 내 노트북에서 인터넷을 건너 prod
BE를 부른 값이라 배포 환경(같은 VPC 안 내부 ALB)에서는 훨씬 짧을 것이다. KAN-380 실측이 1,700건에 1.8초였으니
3초 안팎으로 본다. 다만 기사가 계속 늘면 이 시간도 비례해 늘고, 5,000건을 넘으면 경고 로그가 나오게 해
뒀다. 그때는 BE에 id와 발행 시각만 주는 사이트맵 전용 엔드포인트를 요청하는 게 맞다.

검증이 끝난 뒤 `pnpm build`를 기본 환경으로 다시 돌려 로컬 `.next`를 되돌렸다. prod URL로 구운 산출물을
남겨 두면 다음에 `next start` 계열 설정을 띄운 사람이 브라우저 프록시가 prod BE를 보는 빌드를 쓰게 된다.

## 남은 것

- Search Console의 임시 삭제 요청을 취소해야 한다. 2026-10-30에 `/articles/`와 `/reels/` 접두어로 임시
  삭제를 걸어 뒀다. 임시 삭제는 약 6개월 동안 검색 결과에서 그 접두어를 숨기므로 코드에서 noindex를
  풀어도 `/articles/` 요청이 살아 있는 한 기사가 결과에 안 나온다. 삭제 도구에서 `/articles/` 건을
  취소한다. `/reels/` 건은 릴이 여전히 noindex라 둬도 된다.
- 배포 뒤 Search Console과 네이버 서치어드바이저에 사이트맵을 다시 제출한다. 발견 URL이 23개에서
  3,200개대로 늘어야 한다.
- 애드센스 재심사와 부딪힌다. KAN-652의 전략은 얇은 기사 페이지를 색인 집합에서 빼는 것이었고 이번에 그걸
  되돌렸다. 운영자 글(소개, 가이드, 팀 소개)과 문구 수정은 남아 있지만 색인 집합의 대부분이 다시 100자
  요약 페이지다. 같은 사유로 다시 거절될 수 있다는 걸 알고 한 결정이다. 근본 해법은 기사 본문 분량이고
  BE 요약 파이프라인 몫이다.
- 인물과 선수 프로필(`/figures/{id}`, `/players/{id}`)은 여전히 사이트맵에 없다. 기사 본문의 인물 칩
  링크로 발견된다. 이번 티켓 범위가 아니라 두었다.
