# 0114. 임베드 LCP 챕터 이어서 — 계획을 실측으로 다시 세우고, 크레스트부터 잡다 (2026-08-31)

[0113](0113-embed-lcp-chain-plan.md)에서 세운 챕터의 "이후 2번째 작업"을 하러 들어온
세션이다. 계획대로면 PR 2(무거운 조건부 UI dynamic 전환)를 시작할 차례였는데, 착수 전에
PR 1의 after 측정 데이터를 다시 뜯어보다가 순서가 뒤집혔다. 이 문서는 그 뒤집힌 경위와
실행 기록이다.

## PR 2를 짜려고 폭포수를 열었더니 주인공이 달랐다

PR 1이 끝나며 남긴 진단은 "출발선을 앞당겨도 트랙이 막혀 있으면 완주가 늦는다"였다.
LCP 이미지의 load delay는 533→19ms로 없앴는데 load duration이 633ms로 그 자리를
채웠고, 원인은 simulated slow 4G에서의 대역폭 경합이라고 적어 뒀다. 그 경합의 몫이
PR 2(JS 줄이기)와 PR 3(화면 밖 트윗 이미지 줄이기)라고 생각하고 세션을 닫았었다.

이번에 PR 2의 before를 준비하면서 after 런(reels-run4)의 network-requests를 리소스
종류별로 합산해 봤다. LCP 이미지와 대역폭을 나누는 초기 로드의 바이트 구성이 이랬다.

| 리소스                     | transfer | 출발 시점          | 우선순위     |
| -------------------------- | -------- | ------------------ | ------------ |
| 트윗 이미지(pbs.twimg.com) | 472.1 KB | 34ms(첫 릴)~1051ms | 첫 릴만 High |
| Pretendard woff2           | 285.1 KB | 34 ms              | High         |
| JS 14개                    | 226.6 KB | 43~53 ms           | Low          |
| 팀 크레스트 webp 5장       | 136.8 KB | 43 ms              | Low          |

그리고 JS 226.6 KB의 내역을 청크별로 열어 문자열로 소유자를 특정해 보니, react-dom
69.0 KB + Next 라우터 46.6 KB = 115.6 KB가 dynamic 전환으로는 건드릴 수 없는 프레임워크
바닥이었다. 시트·다이얼로그·댓글 몫으로 실제로 뺄 수 있는 건 15~20 KB. 계획서에서
PR 2의 소유 지표로 적었던 TBT도 이미 3.5ms라 바닥이었다(모바일 웹인데 hydration이
가벼운 앱이라 원래 낮다).

그러니까 "다음 병목은 대역폭 경합"이라는 진단은 맞았는데, 그 경합의 주인공을 잘못
짚고 있던 거다. JS 20 KB를 빼는 PR 2보다, 폰트 285 KB와 크레스트 137 KB가 훨씬 큰
덩어리로 LCP 이미지와 같은 시점에 파이프를 나눠 쓰고 있었다. 크레스트는 렌더가 최대
51px인데 원본이 237~468px로 내려오고 있었고(감사 #20에서 이미 지적된 항목이다), 폰트는
KAN-421에서 셀프호스팅하며 285 KB 통짜 한 파일이라 첫 글자 하나를 그리는 데도 전량이
High로 내려온다.

계획 문서(0113)가 세운 "레버별 귀속" 원칙은 그대로 두고, 레버 목록과 순서를 실측에
맞춰 갈았다. 사용자와 상의해서 확정한 순서는 이렇다.

| 순서 | PR                                         | 소유 지표                           | 예상 폭       |
| ---- | ------------------------------------------ | ----------------------------------- | ------------- |
| A    | 팀 크레스트 리사이즈 (KAN-426)             | /reels 초기 이미지 전송량           | −80 KB        |
| B    | Pretendard 동적 서브셋                     | 폰트 전송량, LCP                    | 285 → 수십 KB |
| C    | 조건부 UI dynamic 전환 (0113의 PR 2)       | 초기 JS 전송량                      | −15~20 KB     |
| D    | 화면 밖 릴 트윗 fetch 게이팅 (0113의 PR 3) | /api/tweet 건수, 트윗 이미지 바이트 | −400 KB급     |

계획서의 PR 2가 C로 밀리면서 지표도 TBT에서 "초기 JS 전송량"으로 갈아 끼웠다.
그리고 감사 #13(TweetEmbed dynamic)은 릴스에서 폐기했다 — PR 1이 첫 릴을 SSR로
만들어서, react-tweet을 `ssr: false`로 빼면 초기 HTML의 임베드가 사라져 PR 1의 LCP
개선을 그대로 되물린다. 감사 시점엔 맞았던 항목이 사이 작업으로 무효화된 경우라,
감사 리포트를 그대로 소진하지 말고 착수 시점에 다시 검증해야 한다는 교훈으로 남긴다.

측정 얘기 하나. 이 챕터의 각 PR은 before를 따로 뜨지 않는다. PR 1의 after 런이 지금
develop과 코드 동일이라(사이 커밋이 문서와 머지 커밋뿐), run4가 그대로 A의 before가
된다. A의 after가 B의 before가 되는 식으로 체인을 잇는다.

## PR A — 크레스트 리사이즈 (KAN-426)

렌더 크기를 전수 조사했다. 모바일 최대 51px(온보딩 그리드), 웹 최대 40px, 릴스는
34px. 3x 디스플레이 기준 최대 153px이라 긴 변 160px로 잡으면 손실이 없다.

리사이즈는 `dwebp`로 PNG 디코드 → `cwebp -resize`로 재인코딩했다. 품질은 세 벌을
떠서 비교했다: q90 67.3 KB, q80 54.8 KB, lossless 162.9 KB(원본보다 커져서 탈락 —
로고처럼 평면 색이 많아도 160px 축소본은 디테일 밀도가 높아 무손실이 손해다).
q80을 160px로 봐도 깨끗했고 실제 렌더는 그 1/3 크기라 q80 채택. 6장 합계
136.6 → 54.8 KB(−60%). mobile·web 양쪽 `public/teams/`에 같은 파일을 넣었다
(TeamCrest가 소비 앱의 public을 읽는 구조라 두 벌 유지가 컨벤션이다).

코드 변경은 없다. zsh에서 `cwebp $rz`로 옵션을 변수에 담아 넘겼다가 word splitting이
안 돼 "-resize 0 160"이 한 인자로 들어가 전부 실패한 헛발질이 하나 있었다 — 옵션은
변수로 조립하지 말고 분기에서 직접 나열하는 게 낫다.

### 결과 — 소유 지표는 다 잡혔고, LCP도 한 칸 내려왔다

after 측정(`docs/perf/2026-08-31-kan-422-embed-lcp/after-crest-resize/`, 같은 조건 5회):

| 지표                     | before   | after        |
| ------------------------ | -------- | ------------ |
| LCP                      | 5.03 s   | 4.81 s (−4%) |
| 크레스트 전송량 (5장)    | 136.8 KB | 49.3 KB      |
| 이미지 전체 전송량       | 630.9 KB | 542.6 KB     |
| 페이지 총 전송량         | 1,204 KB | 1,116 KB     |
| load duration (observed) | 633 ms   | 606 ms       |

88 KB를 뺐는데 LCP는 0.22초 내려왔다. slow 4G 산술로는 0.4초어치 파이프인데,
브라우저가 빈 대역폭을 폰트·JS·다른 릴 이미지에 재배분하니 LCP 몫은 일부만 온다.
"바이트 절감량 ≠ LCP 절감량"이라는 걸 눈으로 확인한 셈이고, 그래서 다음 PR(폰트)이
같은 34ms에 High로 출발하는 285 KB를 건드리는 게 더 기대되는 이유이기도 하다.

## PR B — 폰트 동적 서브셋 (KAN-427): 두 변형 모두 실측 반증, 폐기

크레스트 다음은 폰트였다. 285 KB가 LCP 이미지와 같은 34ms에 High로 출발하니 이게
남은 경합의 최대 지분이라고 봤고, 0111에서 "next/font가 unicode-range를 못 받아
접었다"고 기록한 dynamic subset 전환을 실측 근거로 재개했다. 결론부터: 두 변형을
다 만들어 쟀는데 둘 다 LCP를 못 움직였고 다른 지표를 깎았다. 폐기했다.

변형 1은 npm `pretendard` 패키지의 공식 dynamic subset CSS를 layout에서 import하는
방식이다. Turbopack이 92조각 woff2를 해시 붙여 `/_next/static/media/`로 가져가니
immutable 캐시는 유지되고, 화면에 쓰인 글리프의 조각만 받는 그림을 기대했다.
빌드도 렌더도 문제없었는데 수치가 배신했다.

| 지표        | before (Std 통짜) | 변형 1 (dynamic subset) |
| ----------- | ----------------- | ----------------------- |
| LCP         | 4.81 s            | 4.85 s (동일)           |
| FCP         | 1.06 s            | 3.01 s                  |
| 폰트 전송량 | 285 KB (1건)      | 332 KB (13건)           |

폰트가 오히려 47 KB 커졌다. variable 폰트의 dynamic subset은 조각마다 무게 축
(45~920) 전체를 지고 있어 조각당 20~37 KB다. `/reels`는 릴 10장의 제목이 전부
DOM에 있어 글리프 다양성이 높고, 13조각이 걸려 통짜를 넘었다. 블로그 첫 화면처럼
글자가 적은 페이지에서 이득인 방식이지 이 화면에선 손해다. FCP 3.01은 simulated
lantern 모델이 CSS로 발견된 High 폰트 13건을 크리티컬 패스에 얹은 값이다.

변형 2는 Std 통짜를 유지하되 `preload: false`로 폰트를 첫 대역폭 창에서 빼는
방식이다. 한 줄 변경이라 기대가 컸는데:

| 지표      | before | 변형 2 (preload: false) |
| --------- | ------ | ----------------------- |
| LCP       | 4.81 s | 4.81 s (동일)           |
| FCP       | 1.06 s | 2.56 s                  |
| CLS       | ~0     | 0.052                   |
| 폰트 출발 | 34 ms  | ~76 ms                  |

LCP가 그대로다. 폰트 285 KB를 LCP 이미지의 다운로드 창에서 빼도 완주 시각이 안
변한다는 건, 폰트가 애초에 LCP의 병목이 아니었다는 뜻이다. LCP 이미지(52.8 KB)의
발목을 잡는 건 같은 오리진(pbs.twimg.com)으로 쏟아지는 나머지 릴 9장의 트윗 이미지
~420 KB 쪽이고, 그건 PR D(fetch 게이팅)의 정의 그 자체다. 대신 FCP가 1.5초 늘고
(lantern이 CSS 발견 폰트를 크리티컬 패스에 넣는다), preload와 함께 자동이던
사이즈 조정 fallback의 이점이 흔들려 CLS 0.052가 생겼다.

"폰트 285 KB가 다음 병목"이라는 가설은 그럴듯한 표(크기순 정렬)에서 나왔고, 실측
두 번이 그걸 반증했다. 크기가 큰 리소스가 곧 병목은 아니다 — 병목은 LCP 리소스와
같은 자원(여기선 같은 오리진의 이미지들)을 두고 다투는 쪽에 있었다. 코드는 전부
되돌렸고 KAN-427은 이 기록으로 닫는다. 티켓 하나가 "안 하는 게 맞다"로 끝나는 것도
결론이다.

## PR C — 조건부 UI dynamic 전환 (KAN-428)

레포에 `next/dynamic`이 0건이었다(감사 #12). 탭해야 뜨는 UI — 릴 세부 시트,
공유·로그인·신고·삭제 확인 다이얼로그 — 가 전부 초기 번들에 있었고, 특히 시트는
댓글 스레드와 투표 카드, 뮤테이션 훅까지 통째로 끌고 온다.

전환 자체보다 전환 범위 판단이 일이었다. 시트를 `dynamic(ssr: false)`으로 빼면
시트만 import하는 것들(CommentList→CommentThread 체인, DebateVoteCard)이 릴스
초기 그래프에서 자동으로 따라 나간다. 그래서 릴스만 보면 세 곳(시트, ReelItem의
공유·로그인)이면 끝인데, 같은 다이얼로그를 기사 상세·토론·차단 목록도 조건부로
쓰고 있어 소비처 9개 파일을 같은 패턴으로 쓸었다. TweetEmbed(#13)는 건드리지
않았다 — 위에 적었듯 KAN-422가 무효화했다.

시트에는 함정이 하나 있었다. 시트는 마운트 → rAF 2회 → transition으로 올라오는
구조(useReelDetailMotion)라, 첫 탭 때 청크 다운로드가 끼면 개폐 애니메이션이
그만큼 늦게 시작한다. requestIdleCallback(사파리는 타이머 폴백)으로 하이드레이션
뒤 한가할 때 미리 받아 뒀다 — 초기 LCP 창과 경합하지 않으면서 첫 탭엔 준비돼
있는 절충이다.

TABS 분리(#14)도 같이 했다. 숫자 상수만 쓰는 모듈(useScrollRestore 등)이
`_constants/app.ts`를 거쳐 하단 탭 아이콘 5개를 그래프로 끌고 오던 걸
`_constants/tabs.ts`로 갈랐다. 탭바가 어차피 전 라우트에 있어 바이트 절감은
사실상 0이지만, 그래프 위생 항목이라 비용이 안 드는 김에 정리했다.

결과는 소유 지표만 움직였다. 초기 버스트 JS 226.6 → 218.7 KB(−7.9), 시트 청크
10.2 KB는 idle 시점(768ms)으로 밀렸다. LCP는 4.81초 그대로 — JS는 Low 우선순위라
LCP 이미지의 파이프를 애초에 크게 안 뺏는다는, KAN-427과 같은 결론의 재확인이다.
예상(−15~20 KB)보다 초기 절감이 작은 건 다이얼로그 몫 일부가 공용 청크에 남아서다.
기능 회귀는 브라우저로 시트 개폐·공유·로그인 프롬프트를 직접 밟아 확인했다.

## PR D — 화면 밖 릴 트윗 fetch 게이팅 (KAN-429)

마지막 레버. 사진 없는 릴은 임베드가 미디어라 마운트 즉시 `/api/tweet`을 부르고,
첫 페이지 10장이 동시에 부르니 화면 밖 릴의 트윗 이미지 ~420 KB가 LCP인 첫 릴
이미지와 같은 오리진(pbs.twimg.com)을 나눠 썼다. KAN-427 반증에서 "실병목은
이쪽"이라고 지목했던 그 대상이다.

구현은 세 겹이다. `TweetEmbed`에 `defer` prop을 넣어 켜져 있으면 swr 키를 null로
둔다(useTweet은 키가 없으면 요청 자체가 안 나간다 — KAN-422 시딩과 같은 메커니즘).
`ReelsFeed`가 `Math.abs(i - activeIndex) <= 2`로 창을 계산해 내려보내고,
`ReelItem`이 게이트를 한 방향으로 잠근다 — 한 번 창에 들어온 릴은 나가도 계속
그린다. 받아 둔 임베드를 비웠다 다시 그리면 뒤로 넘길 때 깜빡여서다. 렌더 중
setState로 래치를 걸었는데, React 문서가 지원하는 상태 보정 패턴이라 이펙트 없이
렌더 한 번에 정리된다.

수치는 소유 지표가 다 잡혔다: 초기 `/api/tweet` 9→2건, pbs 14→7건, 페이지 총
전송량 1,116→828 KB(−26%). 브라우저로 넘김도 확인했다 — 넘기면 창이 따라가며
다음 릴을 받고, 지나온 릴은 그대로 남는다.

### 시뮬 LCP가 배치 간 비교를 거부했다

LCP 중앙값은 4.81 → 5.11로 오히려 오른 것처럼 나왔다. 여기서 breakdown을 다시
깠고, 이 챕터 내내 깔려 있던 함정 하나를 확정했다. Lighthouse의 simulated LCP는
그 런에서 관측된 리소스 duration을 스로틀 배율로 증폭해 쓴다. LCP 이미지의 관측
duration이 pbs.twimg.com의 그때그때 컨디션에 따라 54ms(웜)~789ms를 오가니, 같은
빌드 안에서도 simLCP가 4.5~5.2초로 갈린다. before 배치는 트위터 CDN이 빠를 때,
after 배치는 느릴 때 돌았을 뿐이다. 관측 LCP는 두 빌드가 같은 범위(670~790ms)다.

더 중요한 발견은 duration 54ms짜리 런조차 simLCP가 4.5초라는 거다. simulated
slow 4G에서 LCP의 바닥은 로컬 경합이 아니라 모델의 크리티컬 체인 그 자체에 깔려
있다. 이 챕터의 대역폭 레버들(크레스트 −88 KB, JS −8 KB, 트윗 −288 KB)이 요청과
바이트를 크게 줄이고도 시뮬 LCP를 못 움직인 건 그래서다. 반대로 PR 1(서버 렌더)이
0.4초를 움직인 건 체인의 단계 수 자체를 줄였기 때문이고 — 시뮬 지표는 바이트가
아니라 체인에 반응한다는 게 이 챕터의 측정론적 결론이다. 실사용 개선은 필드
데이터(CrUX)로나 보일 것이라, 챕터 서사도 "시뮬 수치"와 "구조 지표"를 나눠 들고
간다.
