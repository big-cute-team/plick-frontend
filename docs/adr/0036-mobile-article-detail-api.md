# 0036. 기사 세부 페이지 API 연결 — 상세 계약의 세 번째 shape와 해시태그 팀 역산 (KAN-283)

## 무엇을 했나

홈에서 기사를 탭했을 때 도착하는 기사 세부 페이지(`/articles/[postId]`)를 mock에서 실제
API(`GET /api/v1/articles/{articleId}`)로 갈아탔다. 이 화면은 `_mocks/posts.ts`의 마지막
소비자였어서, 이번 작업으로 목데이터 파일을 파일째 지웠다. 퍼블리싱 시절부터 이어져 온
`FeedPost` 기반 렌더가 모바일에서 완전히 사라진 세션이기도 하다.

같이 굴러온 변경이 몇 개 있다. 홈 핫이슈 캐러셀의 카드 탭 목적지를 릴스에서 기사 세부로
바꿨고(상세 API가 없어 임시로 릴스에 보내던 것), 사진이 null인 기사는 릴스(KAN-284)처럼
원문 트윗 임베드로 대체하되 세부 페이지에서는 프레임 없이 문서 흐름에 자연 높이로 세웠다.
로딩 스켈레톤과 not-found 화면도 이 라우트에 새로 깔았다.

## 계약 검증에서 나온 것들

be-verify 서브에이전트에 계약 검증을 맡겼는데, 이번에도 스웨거만 봐서는 몰랐을 게 여럿
나왔다.

먼저 상세 응답은 목록(`ArticleCard`)·핫이슈(`HotArticle`)와 또 다른 세 번째 shape다. 기자가
단일 객체가 아니라 `reporters` 배열로 오고(대표 순서 정렬이라 `[0]`이 대표), 원문 트윗 링크가
목록처럼 최상위 `sourceUrl`이 아니라 기자마다 달려 온다. 그리고 `teams` id 배열이 아예 없다.
본문 문단·댓글 필드도 없어서 본문은 긴 요약(`summary`, DB `summary_detail`) 하나가 전부다.

에러 계약도 실제로 때려서 확정했다. 없는 id와 미발행(REVIEW·DISCARDED) 기사는 404
`ARTICLE_NOT_FOUND`, 정수가 아닌 id는 400 `COMMON_INVALID_PARAM`. 이 라우트는 삭제된
딥링크가 정상 유입 경로라서 페이지가 이 두 code를 잡아 `notFound()`로 보내고, 라우트에
`not-found.tsx`를 새로 만들었다. 나머지 에러는 루트 `error.tsx`가 마지막 그물로 받는다.

공개 API지만 유효하지 않은 Bearer 토큰을 실으면 무시가 아니라 401로 끊긴다는 것도
재확인됐다. 피드·핫이슈와 같은 이유로 fetcher는 일부러 토큰을 싣지 않는다.

좋아요·댓글·조회수·`likedByMe`는 BE가 Noop 구현(`NoopArticleEngagementProvider`)이라 항상
0과 false다. 화면은 값을 그대로 그리고, BE가 실집계를 붙이면 수정 없이 살아나게 뒀다.

## 해시태그로 팀을 역산하다

`teams`가 없으니 팀 정보는 `hashtags`(팀 한글명 문자열)에서 꺼내는 수밖에 없었다. 처음엔
도메인 레지스트리 `TEAMS[].name`과 문자열 비교로 될 줄 알았는데, be-verify에 DB 대조를
추가로 부탁해 보니 6팀 중 4팀이 표기가 달랐다. BE `teams.name_ko`는 "아스널·토트넘 핫스퍼·
맨체스터 유나이티드·맨체스터 시티"인데 프론트 레지스트리는 "아스날·토트넘·맨유·맨시티"다.
리버풀과 첼시만 우연히 같다. 단순 비교였으면 4팀이 조용히 팀 없음으로 떨어졌을 것이다.

그래서 `TEAM_BY_KO_NAME` 룩업 테이블을 `_constants/api.ts`에 박았다. `TEAM_IDS`처럼 실제
DB 값을 상수로 든 계약 공백이라, 재시드로 표기가 바뀌면 팀 칩이 빠지는 걸로 드러난다.
해시태그에 팀이 아닌 값이 섞일 걱정은 안 해도 된다 — BE `team_tags`가 teams FK 전용이라
구조적으로 6개 한글명의 부분집합만 온다는 걸 소스에서 확인했다.

다만 사용자 피드백으로 화면의 팀 칩 텍스트는 역산한 레지스트리 표기가 아니라 BE 태그
원문을 그대로 쓰기로 했다(영어로 오면 영어로). 역산한 `teams`는 이미지가 있을 때 MediaThumb
그라데이션 색을 고르는 데만 쓴다.

덤으로 BE 루머 단계가 4단계(`RUMOR·IN_PROGRESS·CONFIRMED·OFFICIAL`)라는 것도 나왔다.
도메인은 3단계라 `CONFIRMED`는 기존 `STAGE_BY_BE_VALUE` 원칙(모르는 값은 null, 배지
미표시)대로 떨어진다. 배지를 새로 만들지는 사용자와 논의할 열린 항목으로 남긴다.

## flow 임베드 — 프레임을 벗기고 릴스의 미디어 숨김만 가져오다

처음엔 KAN-284의 패턴 그대로 16:10 MediaThumb 프레임 안에 임베드를 absolute로 채웠다.
사용자가 보더니 프레임 고정과 배경 음영 없이 임베드만 꽉 차게 해 달라고 해서, `TweetEmbed`에
`layout="flow"` variant를 추가했다. 박스를 채우는 대신 문서 흐름에 자연 높이로 서는 모드다.

이어서 릴스처럼 너무 길면 사진을 숨기는 로직도 요청받았다. fill 모드의 `useTweetFit`은
"박스 대비" 오버플로 판정이라 박스가 없는 flow에는 그대로 못 쓴다. 대신 화면 높이 대비
상한(`TWEET_FLOW_MAX_HEIGHT_RATIO`, 60%)을 기준으로 삼았다. ResizeObserver로 임베드
로딩·이미지 로드로 카드가 자라는 흐름을 따라가다 상한을 넘는 순간 미디어를 뺀다. 릴스와
달리 축소(scale)와 복원은 없다 — 박스에 가둘 이유가 없어 사진만 빼면 충분하고, 박스가
다시 커지는 개념도 없어서다. X Display Requirements상 본문은 자를 수 없다는 제약은 릴스와
동일하게 지켰다.

## 화면 피드백 반영

브라우저 검증 중에 사용자 피드백이 몇 번 들어와 같이 반영했다.

- 좋아요 버튼이 안 눌렀는데도 강조색(초록)이었다. 퍼블리싱 때 정적으로 박은 스타일이었는데,
  `liked`일 때만 강조색이고 기본은 이웃 버튼과 같은 중립 톤으로 바꿨다.
- 상단바의 저장·공유 아이콘과 본문 하단의 저장 버튼을 뺐다. 저장은 BE 계약에 아직 없고,
  액션은 좋아요·공유 둘만 남겼다. `ArticleTopBar`는 뒤로가기만 있는 크롬이 됐다.
- "함께 보면 좋은 기사"는 처음에 최신 피드에서 현재 기사를 뺀 3건으로 채웠는데, 추천 API가
  생기기 전까지 목이든 슬라이싱이든 채우지 말자는 피드백으로 "지금은 준비 중이에요" 자리만
  남겼다. 이 과정에서 `SuggestedArticleItem`은 지웠다.

댓글도 같은 원칙이다. 계약에 댓글이 없으니 목으로 때우지 않고 카운트(0)와 "아직 댓글이
없어요" 빈 상태만 뒀다. 댓글 API 티켓에서 채운다.

## dev 서버 워처가 두 번 죽었다

검증 중에 이상한 일이 있었다. 코드는 분명 고쳤는데 브라우저가 계속 이전 마크업을 그렸다.
파일을 `touch`해도 재컴파일 로그가 안 찍히는 걸 보고 Next dev(Turbopack) 파일 워처가 변경
감지를 멈춘 상태라고 판단했다. 서버를 재시작하니 반영됐는데, 새로 띄운 서버도 편집 몇 개를
받다가 또 같은 증상이 왔다. 편집이 짧은 간격으로 몰릴 때 워처가 이벤트를 놓치는 것으로
보인다. 같은 증상이 또 오면 원인 추적할 가치가 있다 — 사용자 입장에서는 분명 고쳤다는데
화면이 안 바뀌는, 신뢰를 깎는 종류의 버그다.

## 남긴 것

- `CONFIRMED` 단계 배지 표기 여부 (현재는 배지 미표시로 폴백)
- 상세 `reporters`가 2명 이상일 때의 "+N" 표기 (현재 발행 기사는 전건 1명이라 대표만 표시)
- 추천 기사 API가 생기면 "함께 보면 좋은 기사" 리스트 복원
- 좋아요·저장·댓글 실동작은 커뮤니티 API 티켓에서
- 웹(`apps/web`) 기사 세부는 여전히 mock이다. 같은 상세 shape를 쓰게 되는 시점에
  ADR 0011 게이트로 타입·fetcher 공용화를 판단한다 (이번엔 첫 앱이라 앱 로컬)
