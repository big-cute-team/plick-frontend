# ADR 0042 — 댓글 API 연결 (KAN-303): 릴스·기사 공용 GET/POST, 로그인 게이트, 유튜브식 인라인 답글

- 날짜: 2026-07-24
- 브랜치: `feature/KAN-303-article-comments`
- 관련: [ADR 0030 기사 피드 연결](0030-article-feed-api.md) · [ADR 0011 공용 경계](0011-shared-code-boundary.md) · `api-integration` 스킬

## 무엇을 했나

퍼블리싱만 되어 있던 댓글 UI에 처음으로 실제 데이터를 붙였다. `GET /api/v1/articles/{articleId}/comments`로 목록을 받고, `POST` 같은 경로로 작성한다. 기사 세부 페이지와 릴 세부 바텀시트가 이 하나의 API를 같이 쓴다. 비로그인 사용자가 댓글 입력에 손대면 로그인 유도 팝업을 띄우고, 답글은 유튜브처럼 원 댓글 밑에 인라인 입력바가 열리게 했다.

## 계약 확인부터

이번에도 티켓과 스웨거를 그대로 믿지 않고 be-verify 서브에이전트한테 먼저 검증을 맡겼다. 스웨거 shape 확인, JWT 민팅, 일회용 테스트 유저로 실제 curl, DB 대조까지 돌려받은 리포트에서 문서에 없던 사실이 몇 개 나왔다.

- 최상위 댓글은 최신순, 각 댓글의 `replies`는 오래된순으로 온다. 커서 페이지네이션은 최상위에만 걸리고 대댓글은 부모에 통째로 인라인이라 페이지 계산에서 빠진다.
- 삭제된 댓글은 목록에서 사라지지 않는다. `content: null`, `isDeleted: true`인 tombstone으로 남는다. 답글 딸린 원 댓글을 지워도 답글이 계속 보여야 하기 때문이다. 대신 `commentCount` 집계에서는 빠져서, 헤더의 숫자와 목록 행 수가 달라질 수 있다.
- 대댓글에 다시 답글을 다는 것(3단)도 BE가 막지는 않는데, 조회할 때는 최상위 조상 아래로 평탄화된다. 그래서 화면은 1단까지만 열기로 했다. 답글 버튼은 원 댓글에만 있다.
- GET은 공개(토큰 없이 200, 토큰 실으면 `likedByMe`만 채워짐), POST는 보호(토큰 없으면 401 `AUTH_REQUIRED`)다.
- POST 201은 void가 아니라 생성된 댓글 객체를 그대로 돌려준다. 이게 캐시 갱신 전략을 결정했다(아래).
- 댓글 테이블 FK가 `article_summary_id`라 릴 카드 id로도 같은 댓글 목록이 온다. "릴스와 기사가 같은 API"라는 티켓 전제가 DB 레벨에서 확인됐다.

## 데이터 레이어를 왜 이렇게 갈랐나

파일이 둘로 갈렸다. `_services/comments.ts`(평범한 모듈)와 `_services/comment-actions.ts`(`"use server"`).

GET은 공개 API고, 릴 시트(클라)와 기사 페이지(서버)가 둘 다 부른다. 그래서 릴스 fetcher처럼 평범한 모듈로 두고 `apiFetch`가 실행 위치를 보고 base를 고른다(서버는 절대 URL, 브라우저는 `/be` 프록시).

POST는 사정이 다르다. access 토큰이 HttpOnly 쿠키에 있어서 브라우저 JS는 그걸 읽을 수 없다. 서버에서 `cookies()`로 꺼내 `Authorization: Bearer`로 실어야 하니 서버 액션을 경유한다. 그런데 `"use server"` 파일은 async 함수만 export할 수 있다. GET fetcher와 BE 응답 타입, 경계 변환 함수를 같은 파일에 둘 수 없어서 액션만 따로 나갔고, 타입과 변환기는 comments.ts에서 export해 공유한다.

서버 액션에서 하나 더 걸린 게 에러 전달이다. 서버 액션이 던진 에러는 프로덕션에서 Next가 메시지를 가려 버린다. `ApiError` 인스턴스를 던져도 클라에는 뭉개진 채 도착해서 BE 에러 code로 분기할 수 없다. 그래서 액션은 실패를 `{ ok: false, status, code, message }` 값으로 돌려주고, 클라 훅(`useCreateComment`)이 그걸 다시 `ApiError`로 되살려 던진다. 화면은 평소처럼 `e.code === "AUTH_REQUIRED"` 같은 분기를 쓸 수 있다.

## RQ 도입과 캐시 전략

이 티켓이 뮤테이션 첫 등판이라 TanStack Query 도입 트리거가 섰다(스킬의 표 기준). 목록은 `useInfiniteQuery`(커서, `nextCursor ?? undefined` 패턴), 작성은 `useMutation`이다.

작성 성공 시 전체 무효화를 일부러 안 한다. 무한 쿼리를 invalidate하면 쌓인 페이지를 전부 순차로 다시 받는다(커서 체인이라 병렬도 안 된다). POST 201이 생성된 댓글 객체를 그대로 주니까, 그걸 `setQueryData`로 캐시에 직접 끼워 넣는다. 원 댓글이면 첫 페이지 맨 앞(최상위가 최신순이라 새 글 자리가 맨 앞), 답글이면 부모의 `replies` 끝(답글은 오래된순)이다.

헤더의 "댓글 N" 숫자는 따로 처리해야 했다. 원본이 기사 상세·릴 카드 응답의 `commentCount` 스냅샷이라 방금 단 댓글을 모른다. 목록 캐시에서 세는 것도 안 된다 — 아직 안 받은 페이지의 댓글 수를 모른다. 그래서 클라 경계 컴포넌트(기사 `ArticleComments`, 릴 시트)가 `초기값 + 이 화면에서 단 수`를 로컬 state로 든다.

기사 세부는 서버 컴포넌트가 상세와 댓글 첫 페이지를 `Promise.allSettled`로 병렬로 받아 씨앗(`initialData` + `fetchedAt`)으로 심는다. 안 심으면 목록 훅이 마운트되자마자 같은 페이지를 또 받는다. 댓글 fetch만 실패하면 페이지를 죽이지 않고 씨앗 없이 내려보내서 클라가 다시 받게 했다. 릴 시트는 클라에서 열리니 씨앗 없이 열릴 때 받는다.

## 로그인 게이트

티켓 요구가 구체적이었다: 비로그인 사용자가 댓글 input에 접근하거나 제출하려 하면 팝업. 로그인 여부는 이미 있던 `AuthProvider`(서버 레이아웃이 쿠키 존재를 읽어 컨텍스트로 심어 준 것)를 그대로 썼다. 인풋 `onFocus`에서 비로그인이면 즉시 blur하고 팝업을 연다. 제출 경로도 같은 게이트를 탄다. 쿠키는 있는데 토큰이 만료된 경우는 클라가 미리 알 수 없으니 제출 때 401 `AUTH_REQUIRED`를 받아 같은 팝업으로 흘린다. 팝업 자체는 기존 `ErrorDialog`의 스크림+카드 관용에 티켓이 요구한 상단 X와 "로그인 하러 가기"(`/login` 링크)를 얹었다.

## 답글 UX를 두 번 갈아엎은 이야기

처음에는 하단 입력바를 답글 모드로 전환하는 방식으로 만들었다. "답글"을 누르면 하단 입력바 위에 "○○님에게 답글" 배너가 붙는 식. 만들고 나니 사용자 피드백이 왔다 — 유튜브처럼 그 댓글 자리에 입력바가 새로 생겨야 한다는 것. 갈아엎었다.

바뀐 구조에서는 각 `CommentThread`가 `replying` state를 자기가 들고, "답글"을 누르면 원 댓글 바로 밑(기존 답글들 위)에 `CommentComposer`가 인라인으로 마운트된다. 취소 버튼이 붙고, 마운트되자마자 포커스를 받고, 등록 성공이나 취소로 접힌다. 입력바 컴포넌트는 하나를 그대로 쓰되 `parentCommentId` 유무로 답글 모드(작은 사이즈, 취소 버튼, 다른 placeholder)를 가른다. 열림 상태가 스레드 로컬이라 여러 스레드를 동시에 열어도 서로 간섭하지 않는다 — 유튜브와 같은 동작이다.

배너 방식에서 쓰던 `ReplyTarget` 타입과 상태 끌어올리기가 다 필요 없어져서 오히려 코드가 줄었다. 상태가 쓰이는 곳(스레드)에 그대로 두는 쪽이 맞았다.

## 하이드레이션 불일치 한 건

검증 중에 Next dev 오버레이에 recoverable error가 떴다. 댓글의 상대 시각 때문이다. 서버가 SSR로 "11분 전"을 그렸는데 클라가 하이드레이션하는 사이 분 경계를 넘어 "12분 전"이 되면 React가 불일치로 판정한다. 기사 본문의 시각 표시는 서버 컴포넌트 산출물이라(클라가 다시 그리지 않아서) 이 문제가 없는데, 댓글 목록은 클라 컴포넌트를 씨앗으로 SSR한 거라 클라가 같은 걸 다시 계산한다. 시간처럼 정당하게 달라지는 텍스트의 표준 해법대로 그 span에만 `suppressHydrationWarning`을 달았다.

## 검증

계약과 DB는 be-verify가 다 밟았다(성공·401·400·404, 페이지네이션, DB 반영, commentCount 증감, 릴스 id 호환, 테스트 데이터 정리까지). 화면은 브라우저로 직접 밟았다. 비로그인 포커스 → 팝업(X 닫기, 로그인 버튼), 민팅 토큰 쿠키로 로그인 → 댓글 작성 → 목록 맨 앞 반영 + 카운트 증가 + 인풋 클리어, 답글 → 인라인 입력바 → 부모 밑 들여쓰기 반영, 빈 상태("아직 댓글이 없어요"), 릴 시트에서 같은 id의 같은 댓글 목록. 사용자도 본인 계정으로 실사용 확인을 해 줬다. 테스트 유저와 댓글은 DB에서 지웠다.

검증 환경에서 하나 애먹은 것: 브라우저 팬이 백그라운드 탭 취급이라 `requestAnimationFrame`이 발화하지 않아 릴 시트 열림 애니메이션(더블 rAF 후 shown)이 재생되지 않았다. 코드 문제가 아니라 환경 제약이다. DOM 검사와 transform 강제로 우회해서 시트 내용을 확인했다.

## 공용화 판단

전부 앱 로컬에 뒀다. 댓글 타입(`ArticleComment`)은 `@plick/domain`의 퍼블리싱 시절 `Comment`와 어긋나는 실계약이라 기사 타입(ADR 0030)과 같은 판단으로 `_types/comments.ts`에 새로 뒀고, web이 댓글을 붙이는 두 번째 실사용처가 생기면 게이트 C로 승격을 재검토한다. ADR 0011 §7의 기존 후보(`ArticleCard`·`getArticles`·`apiFetch`)와 같은 줄에 선다.
