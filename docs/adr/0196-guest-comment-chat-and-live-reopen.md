# 0196. 게스트에게 댓글과 채팅을 열고, 라이브 경기 화면을 다시 열었다 (KAN-657)

## 어떻게 시작됐나

BE가 KAN-656으로 게스트(소셜 연동 전 임시 계정, KAN-514)에게 댓글 작성·수정·삭제와 실시간 채팅을 열었다. 신고만 소셜 연동 사용자 전용으로 남겼다. 이유는 BE 결정 기록에 있다. 콜드스타트에 참여를 늘리려는 것이고, 게스트는 users 행이라 댓글과 채팅 코드는 그대로 두고 권한 경계만 열면 된다. 신고는 게스트를 대량 발급해 남용하기 쉬워 막아 뒀다.

FE 쪽 티켓이 KAN-657이다. 할 일은 셋이었다. 게스트에게 댓글 입력창을 노출하고, 채팅 입력창을 노출하고, 게스트가 신고하면 BE가 주는 403 `AUTH_GUEST_FORBIDDEN`을 받아 계정 연동 안내를 띄운다. 신고 버튼은 숨기지 않고 노출해 연동을 유도하는 쪽을 권장한다고 적혀 있었다.

같은 세션에서 사용자가 한 가지를 더 얹었다. KAN-644에서 축구 데이터 상류가 죽어 준비중으로 닫아 둔 라이브 경기 화면들(LIVE 목록, 경기 상세, 순위, 팀·선수 프로필)을 다시 열자는 것이었다. 처음에 "라이브 채팅도 다시 열어"라고 해서 `/live/chat`이 닫혀 있나 찾았는데, 그 경로는 KAN-644에서도 열어 뒀다. 되물으니 라이브 경기 페이지들을 뜻한다고 했다.

## FE가 게스트를 어디서 막고 있었나

KAN-514에서 게스트 로그인을 깔 때 "비로그인"이 사실상 사라졌다. 첫 진입에 프록시가 게스트를 발급해 세션이 생기기 때문이다. 그래서 `AuthProvider`가 "세션이 있는가"(`isLoggedIn`)와 "소셜 계정인가"(`!isGuest`)를 따로 들고 다니고, 소셜 전용 기능은 `isGuest`로 한 번 더 막았다. 그 자리를 전부 뽑았다.

- 댓글 입력줄 `CommentComposer`(모바일·웹). 포커스가 오거나 제출할 때 `!isLoggedIn || isGuest`면 입력을 막고 로그인 유도 시트를 띄웠다.
- 신고·차단 버튼 `CommentReportBlockActions`(모바일)와 `CommentMoreActions`(웹). `canAct = isLoggedIn && !isGuest`로 둘 다 막았다.
- 채팅 패널 `LiveChatPanel`(모바일·웹). 비로그인, 게스트, 닉네임 없음 세 게이트가 순서대로 있고 게스트는 "계정 연동이 필요해요" 안내 지면으로 끝났다.
- 로그인 유도 시트 `LoginPromptDialog`(모바일·웹). 게스트면 호출부가 넘긴 `description`을 무시하고 "댓글과 신고, 채팅은 소셜 계정을 연동해야 쓸 수 있어요"를 보여줬다.

반대로 뽑지 않아도 되는 것도 있었다. 댓글 수정 폼, 삭제, 좋아요, 차단 확인은 사전 게이트가 없고 요청이 실패했을 때만 `needsSocialAccount(err)`로 받는다. 이 함수는 `@plick/core/client`에 있고 401 `AUTH_REQUIRED`와 403 `AUTH_GUEST_FORBIDDEN`을 묶어 "소셜 계정이 있어야 되는 일을 막힌 것인가"로 답한다. 호출부가 code 두 개를 늘어놓지 않게 한 자리라, 티켓이 "다른 게스트 제한 화면에서 이미 공통 처리하고 있는지 확인"하라고 한 그 공통 처리가 이것이다. 그래서 손대지 않았다. 게스트가 이제 댓글을 쓸 수 있어도, 아직 KAN-656이 안 올라간 BE에 붙으면 403이 오고 그때는 이 경로가 연동 안내로 돌린다. 배포 순서가 BE보다 FE가 먼저여도 화면이 깨지지 않는다는 뜻이다.

## 신고는 어떻게 두나

티켓 문면대로라면 게스트가 신고 버튼을 눌러 사유를 고르고 보낸 뒤 403을 받고 나서 안내를 띄우는 것도 된다. 하지만 기존 코드는 이미 그보다 앞서 있었다. 게스트가 "신고"를 누르면 요청 없이 바로 연동 안내 시트를 띄우고, 혹시 요청이 나가 403이 와도 `ReportCommentDialog`의 `onAuthRequired`가 같은 안내로 돌린다. 버튼을 숨기지 않고 연동을 유도한다는 권장과도 맞는다. 사유를 다 고르고 나서야 막히는 것보다 누르자마자 안내가 뜨는 쪽이 낫다고 봐서 사전 게이트를 그대로 뒀다. 그래서 신고 쪽 코드 변경은 변수 이름(`canAct` → `canReport`)과 주석뿐이다.

차단은 갈랐다. BE `SecurityConfig`를 보니 KAN-656 전에도 `/api/v1/users/me/blocks`는 `authenticated()`였다. 게스트를 막은 건 FE뿐이었다. 게스트가 댓글판에 제대로 들어오는 이상 괴롭히는 사람을 가릴 수단은 있어야 해서 세션만 있으면 열었다. 모바일은 차단 버튼의 `!canAct`를 `!isLoggedIn`으로, 웹은 `open(next)`에서 `next === "report" && isGuest`일 때만 안내로 빠지게 했다. dev BE에 게스트 토큰으로 차단을 쳐 보니 `USER_BLOCK_TARGET_NOT_FOUND` 404가 왔다. 권한에서 막힌 게 아니라 핸들러까지 들어갔다는 뜻이다.

로그인 유도 시트의 게스트 문구는 "신고는 소셜 계정을 연동해야 쓸 수 있어요. 지금까지 기록은 그대로 이어져요"로 바꿨다. 게스트가 이 시트를 보는 경우가 신고를 누를 때뿐이라서다. 토큰이 만료된 채 다른 일을 하다 401을 받는 경우도 있지만, 프록시가 페이지 요청마다 refresh로 갈아 끼우므로 드물다.

## 채팅의 닉네임 게이트는 왜 그대로 두나

채팅 패널의 세 번째 게이트는 닉네임이 없으면 온보딩으로 보내는 것이다. 게스트가 여기 걸리면 열어도 소용이 없다. BE 커밋 메시지에 "게스트 행은 생성 때 닉네임이 있어 온보딩 검사도 통과한다"고 적혀 있었고, dev BE에 게스트로 `/users/me`를 쳐 보니 `nickname: "plick670360"`이 왔다. 발급 응답의 `needsOnboarding: true`는 응원팀 같은 온보딩이 남았다는 뜻이지 닉네임이 없다는 뜻이 아니었다. 그래서 게이트는 두고 게스트 분기만 지웠다.

## 라이브 화면 다시 열기

KAN-644의 설계(ADR 0191)대로 `packages/domain/src/live-pause.ts`의 `LIVE_SCORE_PAUSED`를 false로 돌렸다. 프록시의 `/live-paused` rewrite 분기와 웹 `LiveStrip`, 모바일 홈 LIVE 띠의 조회 건너뛰기가 한꺼번에 원래대로 돌아간다. 깃발과 준비중 라우트, 테스트는 지우지 않았다. 상류가 또 죽으면 한 줄로 닫을 수 있어야 해서다.

열기 전에 상류 상태를 봤다. prod와 dev BE 모두 `/api/v1/matches`와 `/standings`가 아직 `MATCH_UPSTREAM_ERROR` 502였다. 그래도 사용자 결정이라 열었다. 열면 어떻게 보이는지 확인했는데, LIVE 목록은 날짜 띠와 채팅방 배너가 뜨고 경기 칸은 스켈레톤으로 남으며 아래에 "순위표를 불러오지 못했어요"가 뜬다. 팀 프로필은 머리가 `TEAMS` 이름으로 폴백한다. 준비중보다는 못하지만 깨지지는 않는다. 상류가 살아나면 그대로 채워진다.

E2E의 팀 프로필 시나리오는 `LIVE_SCORE_PAUSED`를 직접 import해 갈래를 고르므로(ADR 0191) spec은 손대지 않았다.

## 검증

사용자가 BE 저장소를 pull하기 전에 시작해서 처음엔 BE 브랜치 `claude/allow-guest-comment-chat`의 커밋 하나를 읽고 맞췄다. pull 뒤 다시 보니 develop에 머지돼 있었고 diff는 같았다. dev BE는 develop에서 자동 배포되므로 바로 dev에 붙여 봤다.

먼저 curl로 계약을 쳤다. 일회용 게스트를 발급받아 기사 8757에 댓글을 쓰니 201, 수정 200, 좋아요 200, 신고는 403 `AUTH_GUEST_FORBIDDEN`에 "소셜 계정을 연동해야 쓸 수 있는 기능입니다", 삭제 200이었다. 웹소켓은 curl로 가짜 핸드셰이크를 치면 400이 와서 판단이 안 됐고, `scripts/chat-mock`에 깔린 `ws` 클라이언트로 `wss://dev.plick.co.kr/be/ws/chat?token=`에 붙이니 게스트 토큰으로 열리고 보낸 메시지가 닉네임과 함께 돌아왔다.

브라우저는 dev BE를 바라보는 prod 빌드를 띄웠다(`mobile-devbe-alt` 3062, `web-devbe-alt` 3063). 3001에 다른 세션의 `next dev`가 살아 있어 Next 16 dev 잠금 때문에 빌드+start로 갔다. 여기서 두 번 헛걸음을 했다.

- `localhost:3062`로 열자 기사 화면이 "문제가 생겼어요"였다. 서버 로그는 401 `AUTH_INVALID_TOKEN`. 브라우저의 localhost 쿠키 저장소에 prod BE가 발급한 토큰이 남아 있었고, 포트가 달라도 같은 저장소라 dev BE에 그걸 보낸 것이다. `127.0.0.1`로 여니 새 게스트가 발급됐다.
- `/live/chat`이 "닉네임을 정해 주세요"에서 멈췄다. RSC 페이로드에는 `{"isGuest":true,"userId":1499,"nickname":"plick833521"}` 시드가 분명히 실려 있는데 화면이 안 바뀌었다. 프로필 시드는 `AuthProvider` 안의 `ProfileSeedReader`가 `use(profile)`로 풀어 `useEffect`로 올리는 구조(KAN-602)인데, 브라우저 패널의 탭이 백그라운드에 있는 동안은 이 갱신이 안 돌았다. 탭을 앞으로 올리자 바로 채팅방으로 바뀌었다. 코드 문제가 아니라 패널 상태 문제였다. 백그라운드 탭에서 Suspense 뒤 상태 갱신을 기다리면 안 된다는 걸 알았다.

웹소켓은 브라우저에서 붙이면 실패했다. dev BE가 `127.0.0.1:3063` origin을 허용하지 않아서다(같은 이유로 브라우저의 `/be` 직접 호출도 403 `Invalid CORS request`). 게스트 여부와 무관한 환경 문제라 채팅 주소만 `CHAT_WS_URL=ws://localhost:8090/ws/chat`로 목 서버에 돌렸다. 목 서버는 토큰이 있기만 하면 통과시키니 FE 쪽 흐름(게이트 통과, 접속, 전송, 목록 반영)만 본 것이고, 게스트 토큰을 dev BE가 받는지는 위 `ws` 클라이언트 결과로 본다.

모바일에서 게스트로 댓글 입력창을 누르니 시트가 안 뜨고, 등록하니 `plick833521`로 바로 붙었다(수정·삭제 버튼 포함). 남의 댓글의 신고를 누르니 "계정 연동이 필요해요 / 신고는 소셜 계정을 연동해야 쓸 수 있어요" 시트가 떴다. 검증 댓글은 삭제했다. 채팅방은 입력창이 열리고 보낸 글이 목록에 붙었다. LIVE 탭은 준비중 대신 목록 화면이 떴다. 웹도 같은 순서로 확인했다. curl로 `/live`, `/live/standings`, `/teams/arsenal/profile`을 치면 두 앱 다 200에 "경기 정보를 준비 중이에요"가 없다.

`check-types`, `lint`, `format:check`, `test:unit`(95), `test:hooks`(40)는 통과했다.
