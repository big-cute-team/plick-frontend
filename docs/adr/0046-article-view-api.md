## 화면이 없는 API를 붙인다

지금까지 붙인 API는 전부 화면에 흔적이 남았다. 피드는 목록이 되고, 좋아요는 하트가 채워지고,
댓글은 줄이 하나 늘었다. 조회수 기록은 그런 게 없다. 사용자가 누르는 것도 아니고, 성공해도
화면이 아무 반응을 하지 않는다. 그래서 이번 작업은 "무엇을 그릴까"가 아니라 "언제 보냈다고
칠까"를 정하는 게 전부였다.

늘 하던 대로 `be-verify` 서브에이전트에 계약 확인부터 맡겼다. 티켓 설명에는 `[보호] 하루 1회만
카운트. 성공 시 본문 없이 200. 릴스 조회, 게시물 조회 공용`이라고만 적혀 있었는데, 이번엔
티켓이 대체로 맞았다. 대신 티켓에 없던 게 여럿 나왔다.

응답 봉투를 벗기면 `data`가 `null`이다. 갱신된 조회수를 안 준다. 좋아요가 `{ likeCount: 2 }`를
돌려주던 것과 다르다. 이게 뒤에서 "카운트를 즉시 올릴 것인가" 판단을 갈랐다.

에러 코드는 스웨거에 아예 선언돼 있지 않았다. 스웨거는 이 엔드포인트에 200 하나만 적어 뒀고,
401·404·400은 전부 실호출로 확인한 것이다. 토큰 없음은 401 `AUTH_REQUIRED`, 없거나 미발행인
기사는 404 `ARTICLE_NOT_FOUND`, 정수가 아닌 id는 400 `COMMON_INVALID_PARAM`.

### 릴스 전용 엔드포인트는 없다

티켓의 "릴스 조회, 게시물 조회 공용"이 무슨 뜻인지 애매해서 `/api/v1/reels/{id}/view` 같은 게
따로 있는지도 같이 확인해 달라고 했는데, 없었다. 스웨거 path 목록에도 없고 실제로 때리면
404다. 릴스도 결국 같은 `articleSummaryId`를 쓰기 때문에 기사용 엔드포인트 하나로 두 화면을
다 처리하는 게 맞다. 릴스 피드 아이템의 id로 POST를 보내 릴스 피드의 `viewCount`가 0에서 1로
오르는 것까지 확인받았다.

이건 이미 KAN-308(좋아요)에서 겪은 구조와 같다. PLick에서 릴과 기사는 표현만 다르고 같은
`article_summaries` 한 행이다. 그래서 좋아요도, 조회도 엔드포인트가 하나다.

### 하루 1회는 서버가 막는다

가장 알고 싶었던 건 중복 방지가 어디에 있느냐였다. 프런트가 막아야 하면 "하루"의 기준 시각을
프런트가 정해야 하고, 그건 기기 시계에 기대는 일이라 하고 싶지 않았다.

DB에 `article_views` 테이블이 있고 `(user_id, article_summary_id, view_date)`에 유니크 제약이
걸려 있다. BE가 `ON CONFLICT DO NOTHING`으로 넣는다. `view_date` 기본값이
`(now() AT TIME ZONE 'Asia/Seoul')::date`라 KST 날짜 기준이다. 즉 서버가 전부 막는다. 같은
기사에 세 번 보내도 전부 200이고 카운트는 1에 머문다. 409 같은 게 오지 않으니 프런트에
"이미 봤음" 분기를 둘 이유가 없다.

여기서 하나 알게 된 게 있다. `article_summaries`에는 `view_count` 컬럼이 아예 없다.
`viewCount`는 조회할 때마다 `article_views` 행을 세서 만든다. 그래서 POST 직후 GET에 즉시
반영된다. 배치나 동기화 지연을 걱정할 필요가 없다는 뜻이라 반가웠다. 대신 `viewCount`는
"본 사람 수"가 아니라 "(유저×기사×날짜) 행의 누적"이다. 같은 사람이 날짜를 넘겨 다시 보면
1 더 오른다.

## 서버 액션이 아니라 브라우저 fetch로

좋아요(`article-likes.ts`)는 `"use server"` 서버 액션이다. 이유는 명확했다. access 토큰이
HttpOnly 쿠키라 브라우저 JS가 읽을 수 없으니, 쿠키를 읽을 수 있는 서버를 한 번 경유해야
`Authorization: Bearer …`를 만들 수 있다.

조회 기록도 보호 API니까 같은 모양으로 가면 되겠다고 생각하고 시작했는데, 쓰다 보니 이미
다른 길이 나 있었다. KAN-308에서 `proxy.ts`에 넣어 둔 배관이다. 브라우저가 `/be/*`로 보내는
요청은 프록시를 거치는데, 거기서 요청 헤더에 Bearer를 심어 준다. access가 만료됐고 refresh가
남아 있으면 갱신까지 하고 심는다. 릴스 다음 페이지 fetch가 이 길로 다닌다.

그러면 서버 액션과 브라우저 fetch 중 뭐가 나은가. 결과는 같지만 비용이 다르다.

서버 액션은 이름과 달리 "서버에서 도는 함수"가 아니라 **클라이언트가 Next 서버로 보내는
POST 요청**이다. 버튼을 눌러 호출하면 브라우저가 액션 id를 담아 현재 라우트로 POST를 치고,
Next가 그 함수를 서버에서 실행한 뒤 응답에 **갱신된 RSC 페이로드**를 함께 실어 보낸다.
서버 액션이 끝나면 라우터가 그 페이로드로 현재 화면을 조용히 다시 그리기 때문이다. 좋아요처럼
"눌렀으니 화면이 바뀌어야 하는" 일에는 그 왕복이 값을 하지만, 조회 기록은 화면이 바뀔 일이
없다. 릴을 넘길 때마다 나가는 fire-and-forget 한 방에 Next 서버 왕복과 라우터 갱신
페이로드를 딸려 보내는 건 과하다.

그래서 `_services/article-views.ts`는 `"use server"` 없는 평범한 모듈로 뒀다. `apiFetch`가
브라우저에서 실행되면 base를 `/be`로 잡고, 프록시가 토큰을 심는다. 기사·릴스 피드 fetcher와
같은 모양이다.

```ts
export async function recordArticleView(articleId: string): Promise<void> {
  await apiFetch<void>(
    `/api/v1/articles/${encodeURIComponent(articleId)}/view`,
    { method: "POST" },
  );
}
```

이게 전부다. 봉투 안이 `null`이라 변환할 것도, 돌려줄 것도 없다.

## 언제가 조회인가

BE는 "조회"를 정의하지 않는다. POST가 들어오면 셀 뿐이다. 그래서 시점은 프런트 정책이고,
표면마다 다르다.

기사 세부는 쉽다. 그 화면에 들어온 것 자체가 조회다.

릴스는 애매하다. 릴은 한 장이 화면을 꽉 채우고 세로로 넘긴다. 손가락 한 번에 여러 장을
지나칠 수 있는데, 스쳐 간 릴도 봤다고 쳐야 하나. 세 가지를 놓고 사용자에게 물었다. 활성되는
즉시, 1초쯤 머물면, 세부 시트를 열 때만. 답은 **활성되는 즉시**였다. 하루 1회 제약이 있어서
한 번 잘못 세면 그날은 못 되돌린다는 점 때문에 나는 머무름 문턱을 권했는데, 조회수는 노출에
가깝게 세는 게 맞다는 판단이었다. 결정이 났으니 그대로 갔고, 덕분에 구현에서 타이머와
정리(cleanup)가 통째로 빠졌다.

### 서버 렌더에서 부르지 않은 이유

기사 세부 페이지는 서버 컴포넌트다. 여기서 그냥 `await recordArticleView(id)` 하면 클라
컴포넌트를 하나도 안 만들고 끝난다. 그런데 그러면 안 되는 이유가 둘 있다.

첫째, 서버 컴포넌트 렌더는 사용자가 실제로 그 화면을 본 순간과 정확히 겹치지 않는다. Next는
뷰포트에 들어온 `<Link>`를 미리 당겨 둔다(prefetch). 라우트가 동적이면 기본값이 전체가 아니라
부분 프리페치라 매번 본문까지 그리진 않지만, 그래도 "목록에서 스쳐 지나간 기사"가 조회로
잡힐 여지가 남는다. 하루 1회라 한 번 잘못 세면 그날은 끝이다.

둘째, 렌더 중에 부수효과를 일으키는 건 React가 보장하지 않는 영역이다. 렌더는 여러 번 돌 수
있고 중간에 버려질 수도 있다. POST를 그 안에 두면 몇 번 나갈지 알 수 없다.

그래서 브라우저에 실제로 마운트된 뒤에 도는 이펙트로 보낸다. 세부 화면 전체를 클라로 내릴
이유는 없으니, 아무것도 그리지 않는 얇은 클라 경계를 하나 세웠다.

```tsx
"use client";

export function ArticleViewTracker({ articleId }: { articleId: string }) {
  useArticleView(articleId);
  return null;
}
```

`return null`인 컴포넌트가 처음엔 좀 이상해 보였는데, 서버 컴포넌트 트리 안에서 부수효과만
필요할 때 쓰는 관용 패턴이다. 릴스는 `ReelItem`이 이미 클라 컴포넌트라 훅을 그냥 부른다.

### 중복 호출을 세션 안에서 걸러낸다

서버가 하루 1회를 막으니 프런트 중복 방지는 정합성 목적으로는 필요 없다. 그런데 릴스는
앞뒤로 넘기면 같은 슬라이드가 계속 다시 활성이 된다. 그때마다 POST가 나가면 서버는 조용히
버리겠지만 네트워크만 낭비다.

그래서 이번 세션에 이미 보낸 id를 `Set`에 담아 둔다. 훅 안 `useState`나 `useRef`가 아니라
**모듈 수준**에 둔 게 요점이다. 컴포넌트 안에 두면 릴을 넘겼다 돌아올 때, 기사 세부에서 뒤로
갔다 다시 들어올 때 초기화돼서 같은 요청이 또 나간다. 모듈 변수는 하드 리로드 전까지 살아
있고, 그게 곧 "이번 세션"이다.

```ts
const recorded = new Set<string>();

export function useArticleView(articleId: string, active = true) {
  const { isLoggedIn } = useAuth();

  useEffect(() => {
    if (!isLoggedIn || !active || recorded.has(articleId)) return;
    recorded.add(articleId);
    recordArticleView(articleId).catch((e) => {
      console.error("[views] 조회 기록 실패:", e);
    });
  }, [articleId, active, isLoggedIn]);
}
```

응답을 기다리지 않고 `add`를 먼저 하는 것도 의도다. `await` 뒤에 찍으면 개발 모드
StrictMode의 이펙트 두 번 실행이나 빠른 재활성이 그 틈에 같은 요청을 두 번 내보낸다.

실패한 id도 보낸 것으로 친다. 지웠다가 다시 시도하게 만들면 404(미발행 기사)처럼 계속 실패할
요청을 릴을 넘길 때마다 반복하게 된다. 조회 한 건을 잃는 편이 낫다.

### 비로그인이면 아예 안 부른다

보호 API라 토큰 없이 부르면 401만 돌아오고 익명 조회수 같은 것도 없다. 화면에 들어올 때마다
401을 쌓을 이유가 없어서 `AuthProvider`로 로그인 여부를 먼저 본다. 쿠키가 HttpOnly라 클라가
직접 못 읽으니 서버가 심어 준 이 값을 쓴다(KAN-308에서 좋아요가 같은 이유로 쓴다).

### 카운트를 즉시 올리지 않는 이유

좋아요는 누르는 즉시 하트를 채우고 카운트를 ±1 한다. 조회수도 그렇게 할까 잠깐 생각했는데
안 하기로 했다.

응답이 갱신된 카운트를 안 준다는 게 첫째 이유다. 좋아요는 BE가 계산한 값으로 덮어써서 그
사이 다른 사람이 누른 것까지 반영되는데, 여기는 덮어쓸 값이 없다.

둘째가 더 결정적이다. 하루 1회 제약 때문에 **이번 호출이 실제로 세어졌는지를 프런트가 알
수 없다**. 오늘 두 번째로 들어온 사람에게 +1을 보여주면 새로고침에서 도로 내려간다. 틀린 값을
잠깐 보여주느니 다음 조회 때 맞는 값을 보여주는 게 낫다. `viewCount`가 실시간 집계라 다음
로드에는 바로 맞다.

## 브라우저 검증에서 만난 것들

계약과 DB는 `be-verify`가 봤으니 화면은 직접 밟았다. 일회용 테스트 유저를 하나 만들고 토큰을
민팅해 쿠키로 심고 들어갔다.

릴스를 처음 열었을 때 POST가 **두 번** 나가서 놀랐다. 120ms 간격으로 서로 다른 기사 id 둘.
활성 슬라이드는 하나뿐인데 왜 둘인가 싶어 Embla 캐러셀의 `activeIndex` 동작부터 다시 읽고,
RQ 씨앗의 `staleTime`을 뒤지고, StrictMode 이중 실행까지 의심했다.

원인은 코드가 아니라 브라우저 상태였다. 다른 세션이 남긴 만료된 `accessToken` 쿠키가 프로필에
남아 있었고, 그 상태로 첫 로드가 401을 맞은 뒤 내가 새 쿠키를 심으면서 두 로드의 요청이
한 로그에 섞여 보인 것이다. 쿠키를 정리하고 다시 재니 로드당 정확히 한 번이었다. 남의 dev
서버와 브라우저 프로필을 물려받아 검증할 때는 이런 잔여 상태를 먼저 씻어야 한다는 걸 다시
배웠다.

기사 세부에서도 한참 헤맸다. POST가 아예 안 나가길래 컴포넌트 배치나 import를 계속 들여다
봤는데, RSC 페이로드에는 `ArticleViewTracker`가 멀쩡히 들어 있었다. 결국 DOM에서 버튼의
React fiber 키를 세 봤더니 0이었다. **그 탭이 하이드레이션되지 않은 상태**였던 것이다.
이펙트가 안 도는 게 당연했다. 새 탭을 열어 같은 주소로 들어가니 곧바로 한 번 나갔다. 앞의
401 난장판이 남긴 여파였다.

"요청이 안 나간다"를 만나면 코드를 의심하기 전에 하이드레이션 여부부터 재 보는 게 빠르다.
`Object.keys(el).filter(k => k.startsWith('__react')).length`가 0이면 그 페이지의 클라 코드는
한 줄도 돌지 않는다.

정리하면 이렇게 확인했다.

- 기사 세부 진입 → POST 한 번, 200. 새로고침하니 `조회 1`로 표시가 올라왔다.
- 릴 활성 → POST 한 번. 다음 릴로 넘기면 그 릴로 한 번 더.
- 넘겼다가 되돌아오면 → 요청 없음(`Set`이 걸러낸다).
- 쿠키를 지우고 기사 세부 진입 → 요청 없음.
- DB `article_views`에 (유저, 기사, 오늘 날짜) 행이 정확히 하나씩.

끝나고 테스트 유저와 그가 만든 `article_views` 5행을 전부 지웠다. 공유 DB라 남기면 남의
기사 조회수가 이유 없이 올라가 있다. 대상 기사 `viewCount`가 0으로 돌아온 것까지 확인했다.

## 공용화는 하지 않았다

`apps/web`은 아직 목데이터로 돌고 인증 배관도 없다. 조회 기록을 붙일 화면 자체가 없으니
ADR 0011 게이트 C(성숙도)에서 걸린다. 두 번째 실사용처가 없다. 전부 `apps/mobile` 안에 뒀다.

`useArticleView`는 기사 세부와 릴스 둘이 함께 쓰는데, 이건 앱 안에서의 재사용이라 승격과는
다른 얘기다. 좋아요가 `useLikeToggle`을 두 화면이 나눠 쓰는 것과 같은 모양이다.

## 남은 것

BE에 넘길 게 둘 있다. 둘 다 프런트가 밟을 일은 없지만 `be-verify`가 찾아냈다.

같은 경로에 GET이나 DELETE를 보내면 405가 아니라 500 `COMMON_INTERNAL_ERROR`가 온다. 전역
예외 핸들러가 `HttpRequestMethodNotSupportedException`을 안 잡는 것 같다.

`sub`가 존재하지 않는 userId인 토큰으로 부르면 401이 아니라 500이 난다(users FK 위반).
서명은 유효한데 유저가 지워진 경우다.

만료 토큰(401 `AUTH_EXPIRED_TOKEN`)을 만나면 지금은 그냥 삼킨다. `proxy.ts`가 페이지
내비게이션에서 refresh로 이어 주므로 다음 이동에서 자연히 회복되고, 조회 한 건을 잃을 뿐이라
따로 처리하지 않았다. 다른 API와 묶어 공통 흐름을 만들 일이 생기면 그때 같이 본다.
