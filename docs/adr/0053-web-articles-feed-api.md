# 0053. web 기사 피드 API 이식과 피드 계약의 공용 승격 (KAN-321)

날짜: 2026-07-28
브랜치: `feature/KAN-321-web-articles-api`

## 무엇을 했나

모바일에서 이미 검증해 둔 `GET /api/v1/articles`(기사 피드)를 데스크톱 웹에 이식했다. 웹은 이 리스트를
두 화면이 쓴다. 홈의 "지금 올라온 소식" 섹션과 `/articles` 페이지다. 둘 다 목데이터(`NEWS_POSTS`,
`POSTS`)를 클라이언트에서 팀별로 걸러 보여주던 걸, 서버가 첫 페이지를 미리 받아 TanStack Query에
씨앗으로 심고 팀 탭 전환과 무한스크롤은 클라이언트가 이어받는 구조로 바꿨다. 모바일 홈(KAN-271)과
같은 구조다.

그리고 이번 작업의 본편은 사실 화면 교체가 아니라 승격 판단이었다. 웹이 이 계약의 두 번째 실사용처가
되면서, 모바일에 앱 로컬로 살던 조각들이 ADR 0011 게이트 C(성숙도: 두 번째 사용처가 실제로 생겼는가)를
처음 통과했다. 어디까지 올리고 어디부터 남길지가 이 세션에서 제일 오래 고민한 지점이다.

## 계약은 be-verify가 아니라 모바일 코드에서 왔다

모바일을 붙일 때는 스웨거를 못 믿어서 `be-verify` 서브에이전트로 실제 응답을 때려 확인했다. 그 결과가
지금 모바일 fetcher에 굳어 있다. BE 응답 타입(`FeedCardResponse`), 경계 변환(`toArticleCard`),
팀 id 역매핑(`TEAM_CODES`), 루머 단계 철자 교정(`STAGE_BY_BE_VALUE`, BE는 `RUMOR`고 도메인 타입은
`RUMOUR`다), 커서 페이지네이션(`nextCursor`가 null이면 끝) 전부다. 웹 이식 단계에서는 이 코드가 곧
검증된 계약이라 `be-verify`를 다시 부르지 않았다(web-wiring.md §1의 재검증 조건에 해당하는 게 없었다).

## 승격: 무엇을 올렸고 무엇을 남겼나

옮긴 것.

- `@plick/domain/types`: `ArticleCard`, `ArticleReporter`, `ArticleFeedPage`, `InitialArticleFeed`
- `@plick/domain/constants`: `TEAM_CODES`, `STAGE_BY_BE_VALUE`
- `@plick/domain/format`: `formatRelativeTime` (모바일 `_utils/time.ts`는 이걸로 비어서 삭제)
- `@plick/core/articles`: `getArticles` fetcher와 BE 응답 타입, 경계 변환, 페이지 크기 상수
- `@plick/core/articleKeys`, `@plick/core/query-client`: 쿼리키와 QueryClient 팩토리

남긴 것과 그 이유.

- `getHotArticles`·`getArticle`과 `HotArticle`·`ArticleDetail` 타입, `TEAM_BY_KO_NAME`. 같은 파일에
  살던 조각이라 통째로 올릴까 한참 망설였다. 어차피 다음 티켓(핫이슈, 상세)에서 웹이 쓸 게 뻔하니까.
  그래도 남겼다. 게이트 C가 "두 번째 사용처가 이미 있다"이지 "곧 생길 예정이다"가 아니고, 스킬도
  엔드포인트 하나가 쓰는 조각만 그때그때 대조하라고 되어 있다. 미리 올리는 건 ADR 0011이 경계하는
  "언젠가 공유하겠지"와 같은 습관이다. 대신 모바일 `_services/articles.ts`와 `_types/articles.ts`가
  반쪽이 된 상태를 파일 머리 주석에 적어 뒀다. 다음 이식 티켓이 나머지를 들고 올라가면 된다.
- `useArticleFeed`·`useInfiniteScroll` 훅. 웹에 같은 구현으로 복제했다. React 훅이라 순수 모듈만 받는
  `@plick/core`의 경계 밖이고, 타입·fetcher·쿼리키를 다 걷어 올린 뒤라 훅 자체는 RQ 옵션 껍데기에
  가깝다. 복제 비용이 승격 비용보다 싸다고 봤다.
- 피드 캐시 정책 상수(`FEED_FRESH_MS` 30분, `FEED_MAX_RETRIES`). 값은 모바일과 같게 뒀지만 이건 계약이
  아니라 앱 정책이다. 모바일의 30분은 뷰 상태 복원(KAN-314)과 당겨서 새로고침이라는 그 앱의 사정에서
  나온 값이라, 표면 사정이 다른 웹과 언제든 갈라질 수 있어 앱별로 뒀다.

`query-client` 승격은 좀 결이 달랐다. 이건 이번 엔드포인트가 새로 만든 중복이 아니라 웹 인증
PR(KAN-318) 때 이미 동일 복제본이 깔려 있던 파일이다. diff를 떠 보니 바이트 단위로 같아서 core로 올리고
양쪽 복제본을 지웠다. 이 승격으로 `@plick/core`의 package.json에 `@tanstack/react-query`와
`@plick/domain` 의존이 처음 생겼다. pnpm은 패키지가 선언 안 한 모듈을 못 끌어오게 막으니(유령 의존 방지)
core 소스가 RQ와 도메인 타입을 import하는 순간 선언이 필수다. `QueryProvider`는 같은 내용의 복제본이
양쪽에 있지만 `"use client"` 컴포넌트라 core에 못 들어가고, 앱에 남아 core의 팩토리만 가져다 쓰게 했다.

## 화면: FeedPost에서 ArticleCard로

웹 리스트 컴포넌트들은 아직 퍼블리싱 때 추정으로 만든 `FeedPost` 타입을 소비하고 있었다. 실계약으로
갈아타면서 마크업이 전제하던 게 셋 깨졌다.

- `timeLabel`(가공된 문자열) → `publishedAt`(ISO). 화면에서 `formatRelativeTime`으로 바꿔 그린다.
  서버 렌더 시각과 클라 하이드레이션 시각이 달라 "19시간 전"이 서로 어긋날 수 있어서 모바일과 같이
  `suppressHydrationWarning`을 달았다. 상대 시각은 몇 초 차이가 나도 틀린 게 아니라 억제가 맞다.
- 단일 `team` → `teams` 배열, 비어 있을 수 있음. 첫 팀만 대표로 쓰고 없으면 팀 이름 자리를 비운다.
- `reporter` 필수 → nullable. 없으면 기자 이름과 구분점을 안 그린다.

썸네일도 모바일(KAN-284)을 따라갔다. 목데이터 시절엔 줄마다 팀 컬러 사각형을 무조건 그렸는데, 실데이터는
이미지가 전부 null이라 그 자리를 아예 접고 텍스트가 전체 폭을 쓴다. 스켈레톤도 같은 이유로 텍스트 3줄만
그린다(모바일 KAN-297과 같은 판단). 모바일 리스트에 있는 하트(좋아요 수, KAN-308)는 웹 행에 안 넣었다.
데스크톱 피그마 시안에 없던 요소고, 이번 티켓은 "지금 UI 그대로 데이터만 실계약으로"가 스코프다.

`PostFeed`는 클라 필터 컴포넌트에서 RQ 컨테이너로 다시 썼다. 팀 탭을 누르면 쿼리키가 바뀌어 BE에
`teamId`를 붙인 요청이 새로 나가고(받은 페이지 안에서 거르던 기존 방식과 달리 팀별 전체 목록이 온다),
리스트 끝 감시 요소(IntersectionObserver)가 보이면 커서로 다음 페이지를 잇는다. 로딩(스켈레톤 4줄),
에러(재시도 버튼), 빈 상태("아직 이 팀 소식이 없어요"), 다음 페이지 실패(400이면 커서를 버리고 리셋)
분기는 모바일 NewsFeed의 검증된 구조를 그대로 가져오되 hover 등 데스크톱 인터랙션 토큰으로 바꿨다.

한 가지는 모바일과 다르게 남겼다. 선택한 팀 탭을 모바일은 zustand 뷰 상태 스토어에 두는데(KAN-314,
기사에 들어갔다 나오면 트리가 언마운트돼 탭이 초기화되는 문제) 웹은 기존 `useState`를 유지했다. 웹도
같은 증상이 있을 수 있지만 스토어 도입은 이 티켓 스코프를 넘어서, 모바일이 그랬듯 별도 티켓 몫으로
미뤘다.

두 페이지 서버 컴포넌트는 각자 첫 페이지를 `await`해 `InitialArticleFeed`(페이지 + 받은 시각)로
내려준다. 받은 시각을 같이 넘기는 이유는 모바일 때와 같다. RQ가 씨앗의 신선도를 캐시 엔트리 생성
시각으로 찍는 걸 서버가 실제로 받은 시각으로 못박아야 묵은 씨앗이 방금 받은 것으로 취급되는 걸 막는다.
쿼리키가 홈과 기사 페이지에서 같아서(`["articles","feed","ALL"]`) 홈을 먼저 본 사용자가 기사 페이지로
넘어가면 캐시를 그대로 이어 쓰고, 서버가 받아 온 두 번째 씨앗은 조용히 버려진다. 이중 페치는 없다.

서버 fetch가 실패해도 페이지를 통째로 에러로 떨어뜨리지 않는다. `initial` 없이 렌더하면 클라가 직접
받으면서 로딩과 에러를 그 자리에만 보여준다. 홈에서 피드 하나 죽었다고 핫이슈까지 안 보이면 손해다.

## 검증에서 헤맨 것

빌드·타입·린트는 web과 mobile 둘 다 통과. 화면은 dev(:3000)에 로컬 BE를 물려 직접 밟았다. 실데이터
렌더, 팀 탭 클릭 시 `/be/api/v1/articles?size=10&teamId=3` 재요청, 스크롤 끝에서 커서 붙은 다음 페이지
요청, 330px까지 가로 오버플로 없음, 콘솔 에러 없음을 확인했다. 모바일 홈(:3001)도 승격된 코드로 여전히
정상 렌더되는 걸 확인했다.

여기서 한 번 놀랐다. 무한스크롤을 확인하려고 스크롤을 내렸는데 네트워크 목록에 다음 페이지 요청이 안
보였고, 스크린샷은 새까맣게 나왔다. 코드 버그인가 싶었는데 DOM을 직접 찍어 보니 리스트가 이미 20행으로
늘어 있었다. 요청이 안 나간 게 아니라 네트워크 조회를 IntersectionObserver 콜백보다 먼저 한 거였고,
스크린샷이 검은 건 검증용 브라우저 패널이 `document.visibilityState === "hidden"` 상태로 돌기 때문이다.
숨은 패널은 그리기가 멈추니 화면 확인은 스크린샷이 아니라 접근성 트리(read_page)와 DOM 조회로 해야
한다. 다음 세션을 위해 적어 둔다.

에러·빈 상태는 실데이터로 못 밟았다. 여섯 팀 모두 기사가 있고 BE를 일부러 죽이는 건 공유 환경이라
피했다. 이 분기들은 모바일 NewsFeed에서 이미 검증된 코드와 같은 구조라 코드 리뷰로 갈음했다.

## 후속 피드백: 리스트 행의 하트

PR을 올린 직후 피드백을 받았다. 모바일 리스트 행에는 하트(좋아요 수, KAN-308)가 있는데 웹 행에서
뺐다는 것. 위에서 "데스크톱 피그마 시안에 없던 요소"라고 스스로 정리하고 넘어갔는데, 이 프로젝트의
규칙은 화면 동작을 모바일과 최대한 같게 맞추고 다르게 갈 거면 사용자에게 물어보는 거였다. 시안에
없다는 건 시안이 하트 도입(KAN-308) 이전에 그려졌기 때문이지 빼기로 한 결정이 아니다. 물어봤어야 했다.

모바일 NewsItem과 같은 형태로 넣었다. 기자 이름 뒤에 `HeartMiniIcon` + `formatCount(likeCount)`,
글자 없이 하트로만, `liked` 칠하기 없음(목록 응답은 익명이라 늘 false다). 이제 행이 담는 정보는
모바일과 완전히 같고 밀도와 hover만 데스크톱이다.

같은 결로 남아 있던 차이가 하나 더 있었다. 팀 탭 선택 유지다. 위에서 `useState`로 두고 후속으로
미뤘다고 썼는데, 사용자에게 물었더니 이번 PR에서 맞추자고 했다. 모바일 KAN-314와 같은 이유로
(라우트를 떠나면 트리가 언마운트돼 컴포넌트 상태가 사라지고, Next Router Cache는 RSC 페이로드만
보존하지 상태는 안 들고 있다) 웹에도 zustand 뷰 상태 스토어를 만들었다. 모바일과 다른 점은 피드가
두 화면(홈 소식, 기사 페이지)에 있다는 것이라, 탭 선택을 surface(`variant`)별로 따로 기억하게 했다.
홈에서 리버풀을 보다 기사 페이지에 가면 거긴 제 탭(전체)이 그대로다. 브라우저로 홈 리버풀 탭 →
기사 상세(404, 상세는 아직 목 기반이라 실제 id가 없다 — 다음 티켓 몫) → 뒤로에서 리버풀 탭 유지와
두 surface의 독립을 확인했다.

이어서 모바일의 탭 재탭 새로고침도 그대로 가져오라는 지시를 받았다. 캐시가 30분이라 화면에 다시
들어와도 자동 갱신이 안 걸리는 건 웹도 같은데, 모바일은 당겨서 새로고침과 하단 탭 재탭이 갱신 통로고
웹엔 아무 통로가 없었다. GNB가 하단 탭의 데스크톱 대응물이므로 `NavItem`에 같은 동작을 달았다. 지금
있는 페이지의 링크를 한 번 더 누르면 이동 대신 맨 위로 올리고 그 화면의 현재 팀 탭 피드를
`resetQueries`로 첫 페이지부터 다시 받는다(`useFeedRefresh`, 모바일 `useHomeRefresh`와 같은 구조 —
invalidate가 아니라 reset인 이유도 같다. 무한 쿼리 invalidate는 쌓인 페이지를 커서 체인 순서대로 전부
다시 받는다). 서버 컴포넌트 몫은 `router.refresh()`로 함께 간다. 한 가지 웹 고유 판단: 재클릭 판정은
활성 pill(`startsWith`)이 아니라 경로 완전 일치로 했다. 기사 세부(`/articles/123`)에서도 "기사" pill은
활성인데, 거기서 누르는 건 목록으로 돌아가는 평범한 이동이어야 하기 때문이다.

검증 중 콘솔에서 `useState is not defined` 에러를 보고 잠깐 긴장했는데, 스택에 전부
`performReactRefresh`가 있었다. `useState`를 스토어로 바꾸는 편집 도중 HMR이 반쯤 갈아끼운 순간의
잔재이고, 콘솔 조회가 탭 수명 전체의 누적 로그를 돌려줘서 리로드 뒤에도 계속 보였던 것이다. 최종
코드에는 해당 식별자가 없고 리로드 후 동작도 정상이다.

## 후속 피드백 2: 스크롤이 정확히 반대로 움직였다

탭 유지를 넣고 나니 스크롤이 두 방향 다 틀렸다는 지적을 받았다. 기사 목록을 한참 내려보다 MY에
갔다 돌아오면 팀 탭은 살아 있는데 위치는 맨 위였고, 반대로 새로고침하면 맨 위가 아니라 저 밑으로
떨어졌다. 원인이 둘 다 달라서 따로 봐야 했다.

돌아왔을 때 맨 위인 쪽. GNB 링크로 돌아오는 건 뒤로가기(popstate)가 아니라 새 push 내비게이션이다.
브라우저의 스크롤 복원은 히스토리 엔트리를 되짚는 popstate에만 걸리고, Next도 push에는 오히려
맨 위로 올리는 게 정상 동작이다. 데이터는 쿼리 캐시가 들고 있어 목록이 그대로 살아나는데 위치만
아무도 안 챙기니 어긋나 보인 것이다. 모바일이 `useScrollRestore`(KAN-314)로 푼 문제와 같은데,
모바일은 스크롤러가 `AppShell` 안의 `<main>`이고 웹은 문서 자체라 대상만 다르다. 문서 `scrollY`를
surface별로 스토어에 적어 두고 되돌리게 했다.

새로고침에 저 밑으로 가는 쪽. 이건 브라우저 기본값(`history.scrollRestoration = "auto"`)이 제
일을 한 결과다. 새로고침 시 브라우저는 이전 스크롤 위치를 되살리려 하는데, 무한스크롤로 5페이지를
쌓아 둔 뒤 새로고침하면 문서는 첫 페이지 높이로 돌아오고 위치만 예전 값이라 목록 끝에 처박힌다.
마운트 동안 `manual`로 눌러 브라우저의 복원을 끄고, 떠날 때 원래 값으로 돌려놨다. 새로고침은
처음부터 보겠다는 뜻이므로 맨 위에서 시작하는 게 맞고, 스토어가 메모리라 저장값도 함께 사라져
의미론이 맞아떨어진다.

복원 타이밍에서 한 번 헛돌았다. `useLayoutEffect`에서 즉시 되돌리는 것만으로는 안 된다. Next는
push 내비게이션 커밋에서 새 페이지를 맨 위로 올리는데 그 이펙트가 부모 쪽이라, 자식인 이 훅이
먼저 돌아 복원해 봐야 곧바로 덮인다. 커밋이 끝난 직후이자 페인트 전인 마이크로태스크에서 한 번 더
되돌리게 하니 잡혔다(그래서 화면에는 처음부터 그 자리였던 것처럼 보인다). 다음 프레임에 한 번 더
시도하는 건 늦게 자리 잡는 콘텐츠로 문서가 자라는 경우용이다.

저장 쪽에서도 하나 버렸다. 처음엔 모바일처럼 언마운트에서 마지막 위치를 확정했는데, 계측을 붙여
보니 그 시점의 `scrollY`가 이미 400이 아니라 335였다. 떠나는 중에 문서가 짧아지면서 브라우저가
위치를 깎은 값이다. 그걸 저장하면 돌아왔을 때 엉뚱한 자리가 되므로 언마운트 저장을 빼고 스크롤
중 저장만 남겼다. 마지막 위치는 어차피 스크롤하는 동안 이미 들어가 있다.

검증에서 또 표면 문제에 걸렸다. 브라우저 패널 탭은 `visibilityState === "hidden"`이라 rAF는
물론 scroll 이벤트도 안 뜬다. 스크롤 이벤트는 렌더링 단계에서 발행되는데 숨은 페이지는 그 단계를
건너뛰기 때문이다. 실제 Chrome 탭을 열어 봐도 백그라운드라 마찬가지였다. 결국 `window.scrollTo`로
위치를 옮긴 뒤 `dispatchEvent(new Event("scroll"))`로 저장을 직접 트리거해서, 그 다음의 복원 경합만
실제 코드로 밟는 방식으로 확인했다. `scrollTo` 자체는 숨은 탭에서도 동작하므로 경합 검증에는 문제가
없다. 계측 로그로 저장 400 → 복원 400, 새로고침 후 0을 확인했고 사용자도 실제 브라우저에서 확인했다.

HMR 함정도 하나 있었다. 훅을 고친 직후 브라우저에서 확인했더니 여전히 옛 동작이라 코드가 틀린 줄
알았는데, 계측을 넣어 보니 그 계측조차 로드돼 있지 않았다. 하드 리로드하니 그제서야 새 코드가 돌았다.
훅 파일을 고친 뒤 바로 검증할 때는 리로드부터 하고 시작해야 한다.

## 남은 것

- 홈 핫이슈 그리드와 사이드바 "실시간 인기"는 아직 목데이터다. 핫이슈는 `articles/hot` 이식 티켓 몫이고,
  실시간 인기와 알림 수는 대응 BE 엔드포인트가 없는 계약 공백이라 숨길지 대체할지 사용자 확인이 필요하다.
- `FeedPost` 소비처가 웹에 아직 남아 있다(핫이슈, 상세, 릴스, 사이드바). 마지막 소비자가 사라지는 PR에서
  `@plick/domain`의 `FeedPost`와 부속을 지운다.
- 웹 팀 탭 선택 상태의 내비게이션 유실(위 `useState` 결정) 여부를 확인하고 필요하면 모바일처럼 뷰 상태로
  뺀다.
