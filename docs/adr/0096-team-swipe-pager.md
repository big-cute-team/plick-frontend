# 0096. 팀 리스트 좌우 스와이프 페이저 (KAN-388)

## 뭘 만들었나

홈 "지금 올라온 소식"과 기사 페이지의 기사 리스트를 좌우로 끌면 이웃 팀 탭으로
넘어가는 스와이프 페이저를 만들었다. 트위터나 인스타그램의 탭 스와이프처럼
리스트가 손가락에 붙어 따라오고, 옆에서 다음 팀 리스트가 실제로 끌려 들어오고,
놓으면 관성으로 마저 넘어가거나 제자리로 돌아온다.

만들기 전에 방식을 세 개 놓고 고민했다. 팀 7개를 전부 가로 페인으로 깔고 CSS
scroll-snap으로 넘기는 게 네이티브 감각으로는 제일 확실한데, 이 앱은 세로
스크롤러가 화면 전체(`main`) 하나고 거기에 당겨서 새로고침, 스크롤 복원, sticky
헤더가 전부 물려 있다. 페인마다 세로 스크롤러를 따로 가지는 구조로 바꾸면 이걸
전부 이식해야 한다. 반대로 제스처만 감지하고 커밋 때 페이드 애니메이션을 트는
방식은 손가락을 안 따라와서 원하는 감각이 아니었다. 그래서 중간을 택했다:
평소에는 지금 구조 그대로 두고, 드래그하는 동안만 현재 리스트 옆에 이웃 팀
미리보기 페인을 절대배치로 붙여 트랙째 `translateX`로 민다. 손을 떼면 커밋
또는 원위치. 이러면 사용자 눈에는 페인 7개짜리 페이저와 구분이 안 되는데
스크롤 배관은 하나도 안 건드린다.

드래그 물리를 embla로 할지도 고민했다. 릴스 캐러셀이 이미 embla를 쓰고 있어서
공짜로 얻을 게 많아 보였는데, embla는 고정된 슬라이드 집합을 자기가 측정하고
소유하는 모델이라 "내용이 갈아끼워지는 창 2개" 구조와는 맞지 않았다. 릴스도
슬라이드가 늘어날 때마다 reInit과 싸운 전적이 있다(ADR의 KAN-276 기록). 터치
판정은 당겨서 새로고침(`usePullToRefresh`)이 이미 같은 슬롭-축판정 패턴을 갖고
있어서 직접 구현이 오히려 범위가 작았다.

## 구조

- `_hooks/useTeamSwipePager.ts`: 제스처 전부. non-passive 터치 리스너, 8px
  슬롭 안에서 축 판정(가로 우세일 때만 가로챔), 드래그 중 트랙에 직접
  `translateX` 대입(프레임마다 리렌더하지 않으려고 React 상태는 이웃 페인
  마운트가 바뀔 때만 쓴다), 릴리즈 때 폭 35% 또는 플릭 속도로 커밋 판정,
  260ms CSS 전환으로 스냅.
- `_components/TeamSwipePager.tsx`: DOM 골격. 바깥 `overflow-x-clip` 뷰포트,
  안쪽 트랙, 드래그 중에만 붙는 미리보기 페인.
- `_components/TeamFeedPreview.tsx`: 미리보기 내용. 진짜 피드와 같은
  `useArticleFeed(team)`를 구독해서 캐시가 있으면 실물, 없으면 스켈레톤을
  그리는데, 마운트 자체가 프리페치가 된다. 커밋 후 갈아 끼워질 진짜 페인도
  같은 캐시를 그리므로 교체 순간 픽셀이 이어진다.
- `_constants/team-filter.ts`: `FILTER_ORDER` (전체 + 빅6). 탭바
  (`TeamFilterTabs`)의 나열 순서와 스와이프의 이웃 판정이 같은 배열을 쓰게
  묶었다.

커밋 경로가 이 설계의 핵심인데, 스와이프가 확정되면 기존 탭 클릭 핸들러
(`handleChange`)를 그대로 호출한다. 탭 전환의 원본이 URL이라(KAN-350,
`history.replaceState`) 필터 교체, 문서 제목, 스토어 동기화, 기사 페이지의
팀별 스크롤 저장·복원이 전부 기존 경로를 그대로 탄다. 스와이프용 상태 배관을
하나도 새로 만들지 않았다.

## 커밋 순간의 픽셀 잇기

제일 공들인 부분이다. 커밋 스냅이 끝난 순간 트랙 transform을 바로 걷으면
안 된다. `onCommit`은 URL만 바꾸고 새 팀 리스트는 React가 다음 렌더에서 갈아
끼우기 때문에, 그 전에 걷으면 옛 팀 리스트가 한 프레임 비친다. 그래서 transform을
±폭에 둔 채 `filter` prop이 확정한 팀으로 바뀌기를 기다렸다가,
`useLayoutEffect`(페인트 전)에서 transform 제거와 미리보기 페인 제거를 한
프레임에 처리한다. 미리보기와 새 리스트가 같은 캐시를 그리므로 이 교체는 눈에
보이지 않는다. transition 스타일을 transform보다 먼저 비워야 복귀가
애니메이션으로 새지 않는 것도 여기서 배웠다.

세로 정렬 문제도 있었다. 리스트를 내린 채 스와이프하면 미리보기 페인을 그냥
컨테이너 상단에 붙여서는 안 된다. 기사 페이지는 팀별 스크롤 저장이 있어서
(KAN-386) "이 팀으로 가면 복원될 자리"의 내용이 끌려 들어와야 커밋 후 복원과
픽셀이 이어진다. 그래서 축이 확정되는 순간 스크롤 기하를 재고(sticky 블록
바닥, 컨테이너의 뷰포트 위치, scrollTop), 이웃 팀의 저장 위치를 리스트 내부
깊이로 환산해 미리보기 페인의 `top`을 보정한다. 처음 보는 팀은 맨 위(sticky
바로 아래)에서 시작하는 걸로 잡으면 기존 `requestTop` 경로와 정확히 맞아떨어진다.

## 후속 피드백 1: 홈은 스크롤을 건드리면 안 됐다

처음에는 홈도 기사 페이지처럼 커밋 때 "리스트 맨 위가 sticky 아래 오는
위치"로 스크롤을 보정했다. 시뮬레이터에서는 그럴듯해 보였는데, 사용자가 바로
잡아냈다: 홈은 팀별 스크롤 저장이 없는 화면이고 탭 클릭은 스크롤을 절대 안
건드리는데(KAN-386에서 일부러 그렇게 만들었다), 스와이프만 맨 위로 점프하니
어색하다는 거다. 맞는 말이었다. 홈의 전환 모델은 "보던 자리 그대로, 내용만
교체"다.

그래서 세로 보정을 `targetScrollTop` prop의 유무로 갈랐다. 팀별 스크롤을
넘기는 화면(기사)만 미리보기를 보정하고 커밋 때 스크롤을 맞춘다. 안 넘기는
화면(홈)은 미리보기 `top`이 항상 0이고 커밋 후에도 스크롤을 손대지 않는다 —
지금 보던 깊이의 이웃 리스트 내용이 그대로 옆에서 끌려 들어오고, 커밋돼도
그 자리다. 클릭과 완전히 같은 감각이 되면서 오히려 픽셀 연속성은 더 좋아졌다.
화면별 전환 모델이 다르면 제스처도 그걸 따라야지, 제스처가 자기 모델을
강요하면 안 된다는 걸 배웠다.

## 후속 피드백 2: 크롬 [Intervention] 스팸

사용자 콘솔에 "Ignored attempt to cancel a touchmove event with
cancelable=false"가 스와이프마다 쌓였다. 크로미움은 스크롤이 이미 시작된
터치의 touchmove를 `cancelable=false`로 보내는데, 거기에 `preventDefault()`를
부르면 무시하면서 경고를 쌓는다. 문제는 경고만이 아니다. `touch-action`이
기본값이면 크롬은 손가락이 살짝만 비껴도(자체 슬롭 ~4px가 우리 판정 슬롭
8px보다 먼저 찬다) 세로 스크롤을 먼저 시작해 버리고, 그 뒤에 우리가 가로
제스처를 가로채면 세로 스크롤과 가로 트랙이 동시에 움직이는 이상한 상태가
된다. 홈 맨 아래 증상에도 이게 섞여 있었을 거다.

세 겹으로 막았다. 페이저 컨테이너에 `touch-action: pan-y`를 줘서 크롬이 이
영역에서 세로 팬만 시작할 수 있게 하고(가로 우세 드래그면 팬을 아예 안
시작해서 이벤트가 계속 cancelable로 남는다), 축 판정 시점에 이벤트가
`cancelable=false`면 이미 스크롤이 주도권을 가진 것으로 보고 제스처를
포기하고, 그래도 남는 경우를 위해 `preventDefault`는 `e.cancelable`일 때만
부른다. iOS 사파리는 원래 문제가 없었어서 시뮬레이터만 봤으면 못 잡았을
문제다.

## 그 외 결정들

- 화면 좌우 24px 안에서 시작한 터치는 무시한다. iOS 엣지 스와이프 백과
  겹치면 페이지가 뒤로 가면서 리스트도 넘어가는 이중 동작이 된다.
- 끝 탭(전체·맨시티)에서 더 끌면 감쇠 저항만 준다. 순환은 안 한다. 감쇠
  곡선은 당겨서 새로고침 것을 `_utils/damp.ts`로 일반화해서 같이 쓴다.
- 스와이프 영역은 리스트뿐이다. 홈의 핫이슈 캐러셀과 팀 탭은 자체 가로
  스크롤이 있어서 페이저 밖에 둔다. 홈 맨 아래 푸터에서 스와이프해도 아무
  일 없는 건 의도한 동작이다.
- `prefers-reduced-motion`이면 스냅 애니메이션 없이 즉시 확정한다.
- 미리보기 페인은 `aria-hidden` + `pointer-events-none`. 제스처 도중에만
  존재하는 장식이고 링크가 들어 있어서 탭이 새면 안 된다.

## 후속 피드백 3: 빠른 플릭의 최소 거리가 너무 길었다

실기기에서 써 본 사용자가 빠르게 넘길 때 문턱이 너무 길다고 했다. 플릭
커밋에 속도(0.4px/ms) 말고도 최소 거리 30px 조건을 걸어 뒀는데, 폰에서
짧고 빠른 스와이프는 슬롭 8px을 빼면 30px에 못 미치는 경우가 많았다.
속도와 방향 일치 조건이 이미 떨림을 걸러 주므로 거리를 16px로 내려 총
이동 32px짜리 플릭(예전 기준이면 바운스)이 커밋되는 걸 시뮬레이터로
확인했고, 실기기로 다시 써 본 사용자 요청으로 10px까지 내렸다. 천천히
끄는 거리 커밋 기준도 폭의 35%가 무겁다고 해서 25%로 낮췄다. 문턱값은
결국 손맛이라 머리로 정한 초깃값을 실기기 피드백으로 두 번 깎았다 —
이런 값은 상수 파일에 모아 두길 잘했다.

## 검증

제스처와 rAF는 브라우저 패널에서 얼어 있어서(개인 메모의 검증 표면 규칙)
iOS 시뮬레이터에 `touch_path`로 실제 터치를 주입해 봤다. 양방향 커밋, 끝 탭
저항, 세로 스크롤·당겨서 새로고침과의 축 분리, 스크롤 내린 상태의 커밋(기사:
저장 위치 복원, 홈: 자리 유지), 무한스크롤로 쌓인 페이지의 유지까지 확인했다.
HMR로 고친 코드가 시뮬레이터에 안 붙어서 옛 동작을 새 동작으로 착각할 뻔한
적이 있다 — 제스처 수정 검증은 페이지를 새로 열고 하는 게 안전하다.
