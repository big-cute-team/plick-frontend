# 0069. SEO 전략 계획 수립 (KAN-345)

2026-08-03. 소마 특강에서 SEO 강의를 들었고, 자료 PDF를 받아서 이걸 PLick에 어떻게 적용할지
계획을 세우는 세션이었다. 결과물은 [docs/seo-strategy.md](../seo-strategy.md)이고, 이 ADR에는
그 문서를 만들면서 뭘 조사했고 뭘 알게 됐는지를 남긴다.

## 왜 지금 하나

컷오버(KAN-344)가 끝나서 `plick.co.kr`, `m.plick.co.kr`이 실제로 떠 있는 상태가 됐다.
그런데 구글에서 우리 서비스를 검색하면 아무것도 안 나온다. 강의에서 들은 표현이 정확히
우리 상태였다. "만들었는데 아무도 안 써요"의 80%는 서비스가 나빠서가 아니라 아무도 모르기
때문이라는 것. 그리고 SEO는 복리라서 시작이 빠를수록 쌓이는 게 많다고 했다. 색인에서 안정적
유입까지 3~6개월이 걸린다니, 지금 기반을 깔아야 연말에 검색 유입이 생긴다는 계산이 나온다.

## 강의 자료에서 가져온 프레임

PDF 38쪽을 다 읽고 PLick에 적용할 수 있는 걸 추렸다.

- 기술적 SEO 최소 요건: sitemap.xml + robots.txt + Search Console 등록. 이것만 하면 구글에
  최소한 "존재"는 한다.
- 크롤링 → 인덱싱 → 랭킹 3단계. 각 단계마다 잡는 수단이 다르다(사이트맵/시맨틱 HTML·메타
  태그/콘텐츠 품질·Core Web Vitals·백링크).
- 모든 페이지에 고유한 title(60자)과 description(160자). 한국어 서비스면 한국어로.
- 렌더링 전략: 랜딩·소개는 SSG, 목록·검색은 SSR, 로그인 후 화면은 CSR. Next는 페이지별로
  섞어 쓸 수 있다.
- 키워드는 롱테일(경쟁 없음, 전환 높음) → 연관(중간) → 핵심(대기업 점령) 순서로 점령한다.
  SEO는 한 방이 아니라 쌓기 게임.
- 운영 사이클: Search Console에서 측정 → "노출은 되는데 클릭이 안 되네" 발견 → title·콘텐츠
  개선 → 대기. 월 1회만 돌려도 6개월 후 완전히 달라진다.

## 코드베이스 조사에서 나온 것

Explore 에이전트한테 메타데이터·라우트·렌더링·배포·도메인 레지스트리를 전수 조사시켰다.
결과가 예상보다 극단적이었다. 요약하면 "렌더링 기반은 좋은데 그 위가 전부 비어 있다".

없는 것: robots, sitemap, 페이지별 metadata(기사 상세 포함 전 라우트), OG 태그·이미지,
JSON-LD, canonical, metadataBase, 사이트 URL 환경변수, 팀·선수 페이지, 릴 개별 URL,
SEO를 다룬 ADR. 전부 0건이었다. 루트 레이아웃의 `title: "PLick"` 하나가 메타데이터의 전부다.

반면 좋은 것도 분명했다. 기사 상세(`ArticleBody`)가 완전한 서버 컴포넌트라 `<h1>`과 본문
문단이 초기 HTML에 그대로 들어간다. proxy.ts가 비로그인을 리다이렉트하지 않아 크롤러 경로도
열려 있다. 릴스·홈도 서버에서 첫 페이지를 seed해 줘서 SSR HTML에 콘텐츠가 있다. 즉 SPA들이
겪는 "구글 봇이 빈 화면을 본다" 문제는 우리한테 없다. 메타데이터만 얹으면 되는 상태다.

조사하면서 알게 된 함정 몇 개가 계획의 뼈대가 됐다.

1. `plick.co.kr`과 `m.plick.co.kr`에 같은 기사가 중복으로 존재한다. canonical 상호 선언이
   없으면 랭킹 시그널이 갈라진다. 구글의 별도 모바일 URL(m-dot) 패턴 대응이 필요하다.
   이건 코드보다 먼저 "어느 쪽이 대표냐"를 정해야 하는 문제라 Step 0 결정 사항으로 뺐다.
2. ADR 0047이 `NEXT_PUBLIC_SITE_URL` 도입을 명시적으로 거부했었다. 공유 링크는
   `window.location.origin`으로 충분하다는 이유였고 그 맥락에선 맞는 결정이었는데,
   metadataBase·sitemap·canonical은 서버가 절대 origin을 알아야 해서 이 결정과 충돌한다.
   기존 결정을 뒤집는 게 아니라 용도를 분리해서(공유는 origin, 메타는 env) 공존시키기로 했다.
3. 기사 대표 이미지(`imageUrl`)가 발행 기사 전건 null이다. OG 이미지를 기사 이미지로 채우는
   흔한 전략이 우리 데이터로는 성립하지 않는다. 대신 `next/og`로 팀 컬러 + 제목을 그리는
   동적 OG 생성으로 방향을 잡았다. handoff.md의 미해결 질문에 "OG 썸네일 생성 방식"이
   처음부터 있었는데 이제야 답이 생긴 셈이다.
4. 팀 필터가 URL에 반영되지 않는다. zustand view-state(ADR 0048)에만 담겨서 "토트넘 이적
   루머"라는 검색어를 받아줄 URL이 사이트에 존재하지 않는다. 그래서 `/teams/[slug]` 팀 허브
   페이지 신설이 G1(팀 검색어)의 핵심 작업이 됐다. slug 필드가 `Team` 타입에 없어서 도메인
   패키지 확장도 같이 가야 한다. 팀 정식 명칭("토트넘 핫스퍼")은 `TEAM_BY_KO_NAME`에만 있고
   `TEAMS[].name`은 축약형이라는 것도 이번에 처음 의식했다. h1·title에는 풀네임을 써야 한다.
5. `/reels/[postId]`는 handoff 원설계에 있었는데 구현이 안 됐고, ADR 0047도 "이 티켓 범위
   밖"으로 미뤘다. 릴과 기사가 같은 `article_summaries` 행이라는 걸 활용하면 데이터는 이미
   있으니 라우트만 만들면 된다. 다만 릴 상세와 기사 상세가 같은 콘텐츠의 두 URL이 되므로
   canonical을 기사로 모으기로 했다.
6. 선수 검색어는 프론트 단독으로 못 한다. 도메인에 `Player` 타입이 없고 BE `team_tags`가
   팀 전용이다. handoff의 목표 타입에는 `players[]`가 있었으니 원래 로드맵엔 있던 것.
   BE에 선수 태그를 요청하는 게 선행 과제라고 계획서에 못 박았다.

## 계획서의 구조를 이렇게 잡은 이유

처음엔 강의 체크리스트(Step1·2·3)를 그대로 옮길까 했는데, 우리 상황엔 "검색어마다 받아줄
페이지가 있는가"라는 축이 더 중요했다. "프리미어리그" 최상단이라는 목표는 솔직히 단기엔
불가능하고(공식 리그, 네이버 스포츠, 위키가 점령), 브랜드 검색어는 반대로 색인만 되면 먹는다.
그래서 계획서를 검색어 유형 → 랜딩 페이지 매핑으로 먼저 정리하고, 실행은 Step 0(결정) →
1(기술 기본) → 2(구조 확장) → 3(콘텐츠·운영)으로 쌓았다. 난이도 표를 1절에 박아둔 건
"프리미어리그 1위"라는 기대치를 문서로 정렬해 두기 위해서다.

## 막힌 것, 미룬 것

- PDF가 시스템에 193쪽으로 표기돼 있었는데 실제로는 38쪽이었다. 뒤에 부록이 있는 줄 알고
  범위를 더 읽으려다 에러로 확인했다.
- PDF 렌더링에 poppler가 없어서 `brew install poppler`부터 하고 시작했다.
- 대표 도메인을 뭘로 할지(A안: apex canonical + m-dot alternate)는 권장안만 적고 결정은
  팀 합의로 미뤘다. 잘못 정하면 나중에 301 대이동이라 혼자 정할 사안이 아니다.
- 이 세션은 계획 수립까지다. 코드 변경은 없고, 실행은 7절의 티켓 분할대로 후속 세션에서 한다.
