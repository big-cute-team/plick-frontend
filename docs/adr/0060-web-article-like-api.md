# 0060 — 웹 좋아요 API 이식과 dev가 느려진 범인 찾기 (KAN-330)

- 상태: Accepted
- 날짜: 2026-07-29
- 범위: `apps/web`. 기사·릴 좋아요 등록·취소(`POST`·`DELETE /api/v1/articles/{articleId}/like`)를
  기사 세부 버튼과 릴 액션 레일에 붙인다. 계약 타입 `LikeState`·`ToggleLikeResult`를
  `@plick/domain`으로 승격하고, 작업 중에 드러난 로컬 dev 느려짐(KAN-334 배포 설정에서 온 것)도 같이 고친다.
- 관련: [ADR 0044 모바일 좋아요 API](0044-article-like-api.md) · [ADR 0058 웹 댓글 API](0058-web-comments-api.md) ·
  [ADR 0059 EC2 배포](0059-mobile-ec2-deploy.md) · [ADR 0011 공용 경계](0011-shared-code-boundary.md)

---

## 이번 건은 계약을 다시 확인할 필요가 없었다

모바일에서 같은 엔드포인트를 이미 붙였다(KAN-308, ADR 0044). 그때 `be-verify`가 스웨거와 실제 응답을
대조하고, 티켓 제목의 `GET`이 사실은 `POST`라는 것까지 잡아냈다. 그 결과가 모바일 코드에 그대로 굳어
있으니 이번엔 그 코드가 계약이다. 스킬의 `web-wiring.md` §1이 정확히 이 상황을 다룬다 — 모바일이 붙인
엔드포인트면 `be-verify`를 부르지 않고 모바일 코드를 읽는다.

다시 적어 두면 계약은 이렇다.

- `POST`·`DELETE /api/v1/articles/{articleId}/like`, 둘 다 봉투를 벗기면 `{ likeCount }` 하나.
- 둘 다 멱등이다. 이미 누른 기사에 POST를 또 보내도 409가 아니라 200에 현재 카운트가 온다.
- 에러는 401 `AUTH_REQUIRED`와 404 `ARTICLE_NOT_FOUND`.
- 초기 상태를 조회하는 API는 없다. 기사 목록·상세·릴스 응답이 저마다 `likeCount`와 `likedByMe`를 들고 온다.

멱등이라는 게 이번에도 편했다. 검증 중에 이미 좋아요가 눌린 기사에 POST를 한 번 더 보냈는데
카운트가 2로 튀지 않고 1 그대로 왔다. "좋아요를 1 증가시켜라"가 아니라 "켜진 상태로 만들어라"에
가까운 API라 재시도나 중복 클릭이 데이터를 어긋나게 만들지 않는다.

## 무엇을 올리고 무엇을 복제했나

web이 ADR 0011 게이트 C(성숙도)의 두 번째 실사용처다. 그래서 이 티켓의 본편은 사실 승격 판단이었다.
조각별로 이렇게 갈랐다.

| 조각                                           | 결정                         | 근거                                  |
| ---------------------------------------------- | ---------------------------- | ------------------------------------- |
| `LikeState`·`ToggleLikeResult`                 | `@plick/domain/types`로 승격 | 굳은 계약이고 앱 역참조가 없다        |
| `_services/article-likes.ts` (`"use server"`)  | web에 복제                   | 쿠키 이름이 앱에 박혀 있다            |
| `useLikeToggle`·`useArticleLike`·`useReelLike` | web에 복제                   | React 훅이라 core의 순수 모듈 경계 밖 |
| `LIKE_LOGIN_PROMPT`                            | web에 복제                   | 계약 상수가 아니라 화면 문구다        |

타입 승격으로 모바일 `_types/likes.ts`는 파일째 사라졌다. `web-wiring.md` §2가 "남은 건 `likes.ts`뿐이고
좋아요 뮤테이션을 web에 붙일 때 따라 올라간다"고 예고해 둔 그대로다. 이걸로 모바일 `_types/`에서 web과
공유하는 계약 타입은 다 올라갔고, 남은 `reels.ts`의 `ReelDetailMotion`·`TitleMotion`은 모바일 제스처
상태라 애초에 올릴 물건이 아니다.

서버 액션을 안 올리는 규칙은 이번에도 그대로 적용했다. `"use server"` 파일은 `cookies()`로 앱의 쿠키
이름을 읽고, 그 이름은 각 앱 `_constants/api.ts`에 있다. 패키지가 앱 상수를 역참조하면 게이트 A에서
바로 실격이다. 파일이 80줄짜리라 복제 비용도 싸다.

훅도 안 올렸다. 여기엔 조금 더 설명이 필요한데, `@plick/core`는 순수 모듈 패키지로 출발했고
(ADR 0050) 지금은 `@tanstack/react-query` 의존까지 들어와 있다. 그래도 훅은 안 올린다는 게
KAN-321·323·329에서 세 번 반복해 내린 판단이다. 승격분(fetcher·쿼리키·타입)을 다 걷어내고 나면 훅에
남는 건 얇은 껍데기라, 앱마다 조금씩 다른 표면 정책을 억지로 한 파일에 합치는 것보다 복제가 싸다.

## 릴스 레일이 두 벌이라는 걸 늦게 알았다

모바일에선 릴 하나에 액션 레일이 하나다. 그래서 `ReelItem`이 `useReelLike`를 부르고 레일에
`onLike`만 내려 주면 끝이었다.

web은 달랐다. 데스크톱은 카드 밖 오른쪽에 레일이 서고, 좁은 뷰포트에선 사진이 눌리지 않도록 카드 안
우측에 오버레이한다. 구현은 레일 컴포넌트를 두 번 렌더하고 `lg:hidden`과 `max-lg:hidden`으로 하나씩
숨기는 방식이다. 즉 DOM에는 항상 두 벌이 있다.

처음엔 모바일처럼 레일 안에서 훅을 부르려다 이게 걸렸다. 레일마다 훅을 부르면 훅 인스턴스가 두 개가
되고, 각자 `needsLogin` 로컬 state를 든다. 좋아요 카운트 자체는 쿼리 캐시가 원본이라 두 레일이 같은
값을 그리지만, 비로그인 팝업은 클릭한 쪽에서만 뜬다. 지금은 한쪽이 항상 `display: none`이라 눈에 띄는
사고는 안 나겠지만, "어느 레일이 눌렸느냐"가 뷰포트에 좌우되는 상태를 두 벌 만드는 건 그냥 잘못된 구조다.

그래서 훅을 `ReelItem` 한 층 위로 올리고 레일은 `onLike`와 표시만 받게 했다. 로그인 팝업도 그 층에서
한 번만 그린다. 결과적으로 모바일 `ReelActionRail`과 같은 모양이 됐다 — 거기서 팝업을 부모에 둔 이유는
레일의 `drop-shadow` 때문이었고(필터가 걸린 조상은 `position: fixed`의 기준 상자가 된다) web은 레일에
필터가 없어 이유가 다른데, 도착한 구조는 같다.

브라우저에서 확인해 보니 릴 하나의 레일 두 벌이 같이 0 → 1로 오르고 같이 강조색이 됐다. 원본이 캐시
하나라 훅 하나가 둘을 동시에 갱신한다.

## 기사 세부는 버튼만 클라로 떼어 냈다

`ArticleMain`은 서버 컴포넌트다. 문단·해시태그·추천 카드까지 다 들고 있어서 여기에 `"use client"`를
붙이면 그게 전부 클라 번들로 내려간다. 좋아요 알약 하나만 `ArticleLikeButton`으로 떼어 클라 경계를
그 버튼에 좁혔다. 모바일 `ArticleBody`에서 한 것과 같다.

상태를 어디에 두느냐가 릴스와 갈린다. 릴스는 무한 쿼리 캐시가 원본이라 캐시를 직접 고쳐야 스크롤로
벗어났다 돌아와도 유지되고, 기사 세부는 클라 캐시가 없고 서버가 준 props가 원본이라 컴포넌트 state가
곧 화면이다. 훅이 상태를 안 들고 `onChange`로 되돌려주는 설계(ADR 0044에서 릴스가 깨지며 얻은 결론)가
그대로 값을 했다 — 호출부만 다르게 물리면 두 화면이 같은 훅을 쓴다.

## 그런데 로컬이 갑자기 기어 다녔다

작업 중반에 dev 서버가 이상해졌다. web을 띄우면 "Ready"를 찍고 몇 초 만에 죽고, 다시 띄우면 또 죽었다.
`ps`로 보니 `next-server` 하나가 168% CPU를 물고 있었고, 터미널에는 macOS의 malloc 로그가 끝없이 흘렀다.
사용자도 "웹 모바일 전부 로컬호스트 로딩이 심하다"고 했다. 직전에 EC2 배포 설정(KAN-334)을 건드린 게
관련 있느냐는 질문이 왔다.

관련이 있었다. KAN-334에서 두 앱 `next.config.js`에 이걸 넣었다.

```js
output: "standalone",
outputFileTracingRoot: path.join(appDir, "../../"),
```

`outputFileTracingRoot`는 이름만 보면 빌드 산출물 추적용이다. 실제로 standalone에 `packages/*`를
담으려면 꼭 필요한 값이고 그 목적 자체는 옳다. 문제는 이 값을 빌드만 읽는 게 아니라는 것이다.
설치된 Next 16 코드를 직접 열어 보니 dev 번들러가 Turbopack 프로젝트 루트를 이렇게 정한다.

```js
// next/dist/esm/server/lib/router-utils/setup-dev-bundler.js:511
const rootPath =
  nextConfig.turbopack?.root || nextConfig.outputFileTracingRoot || opts.dir;
```

`hot-reloader-turbopack.js:208`도 같은 식이다. 즉 배포용으로 넣은 한 줄 때문에 **dev의 감시 범위가
`apps/web`에서 리포 루트로 올라갔다**. 그 안에는 이런 게 들어 있었다.

| 대상                | 크기 |
| ------------------- | ---- |
| `node_modules`      | 457M |
| `apps/web/.next`    | 1.2G |
| `apps/mobile/.next` | 829M |

`.next`가 감시 범위에 들어가는 게 특히 나쁘다. dev 캐시를 쓰면 그 쓰기가 다시 watch 이벤트로 돌아오는
되먹임이 생긴다. CPU가 계속 물려 있고 서버가 스스로 주저앉던 그림과 맞는다.

고치는 방향을 둘 놓고 골랐다. 하나는 `turbopack.root`를 앱 폴더로 좁히는 것인데, Next 타입 주석이
"이 디렉터리 아래만 turbopack이 resolve할 수 있다"고 못박고 있어 모노레포에서 `packages/*` 해석을
끊을 위험이 있다. 다른 하나는 애초에 dev에서 이 옵션들을 평가하지 않는 것이다. standalone 산출물은
빌드에만 필요하니 후자가 맞다.

```js
const isBuild = process.env.NODE_ENV === "production";

...(isBuild && {
  output: "standalone",
  outputFileTracingRoot: path.join(appDir, "../../"),
}),
```

`next build`가 NODE_ENV를 production으로 두고 config를 읽으므로 CI 워크플로는 손댈 게 없다. 배포 설정을
되돌린 게 아니라 적용 시점만 좁힌 것이다.

효과는 바로 나왔다. 쌓여 있던 `.next` 2GB를 지우고 다시 띄우니 홈 200ms, 기사 세부 590ms에 응답했고
컴파일이 끝난 뒤 idle CPU가 0.1%로 내려갔다. 서버가 죽는 현상도 사라졌다. 확인차 두 앱을 다시 빌드해
`.next/standalone/apps/<app>/{server.js,.next/}` 구조와 rewrite가 굳는 것까지 그대로인지 봤다.

교훈은 하나다. 배포용 옵션을 config에 넣을 때 그게 dev에서도 읽히는 값인지 확인해야 한다. 이름에
"output"이 붙어 있다고 빌드 전용이라는 보장이 없다. 확신이 안 서면 설치된 패키지 소스를 grep하는 게
문서를 뒤지는 것보다 빨랐다.

## 화면이 하이드레이션 안 되는 줄 알았던 삽질

검증을 브라우저 패널에서 시작했는데 좋아요 버튼을 클릭해도 아무 반응이 없었다. 콘솔에 에러도 없고
페이지 텍스트는 멀쩡히 읽혔다. 버튼 DOM 노드에 React fiber 키(`__react…`)가 아예 안 붙어 있길래
하이드레이션이 통째로 실패한 줄 알고 코드를 한참 의심했다.

원인은 코드가 아니라 검증 표면이었다.

```js
{ vis: "hidden", hidden: true, w: 0, h: 0, ready: "complete" }
```

패널이 숨김 상태에 뷰포트 0x0이라 React 스케줄러가 굶어 하이드레이션이 진행되지 않았던 것이다.
문서가 로드는 다 되니 텍스트는 읽히고, 그래서 더 헷갈렸다. 실제 Chrome으로 옮겨 같은 페이지를 여니
한 번에 정상 동작했다. 애니메이션이 얼어 있다는 건 알고 있었는데, 하이드레이션까지 멈춘다는 건 이번에
처음 봤다. 앞으로 web 상호작용 검증은 처음부터 실제 브라우저로 간다.

## 검증

계약은 모바일과 같은 코드를 쓰는 것으로 갈음했다(`web-wiring.md` §1). 화면은 dev(:3000)와 로컬 BE로
직접 밟았다.

- 기사 세부에서 좋아요 → 즉시 강조색으로 차고 `aria-label`이 "좋아요 취소"로 바뀐다. 새로고침해도 유지된다
  (읽기에 토큰을 실어 `likedByMe`가 이 유저 기준으로 오는 배관은 KAN-322에서 이미 깔려 있었다).
- 이미 눌린 기사에 POST가 한 번 더 나갔을 때 카운트가 1 그대로였다 — 멱등 계약대로다.
- 릴스에서 좋아요 → 0에서 1로 오르고 같은 릴의 레일 두 벌이 함께 강조된다. 다시 눌러 취소하면 0으로 복귀.
- DB `likes` 테이블에서 토글이 행 생성·삭제로 반영되는 걸 대조했다. 검증으로 만든 행은 지웠다.
- 두 앱 빌드, `check-types`, `lint`, `format:check` 통과.

## 남은 것

- 댓글 좋아요(모바일 KAN-309)는 아직 web에 없다. `useLikeToggle` 뼈대를 이번에 그대로 가져왔으니
  그 티켓은 `useCommentLike`와 `comment-likes.ts`만 복제하면 된다.
- 홈·기사 목록은 여전히 익명으로 읽어 `liked`가 늘 false다. 목록에서 내가 누른 걸 칠하게 되면 그때
  토큰을 실어야 한다(모바일과 같은 상태).
- 토글 실패 중 401이 아닌 것은 문구 없이 되돌리기만 한다. 모바일과 같은 판단이고, 실사용에서 실패가
  잦다면 그때 표시 방식을 다시 본다.
- dev 캐시가 9일 만에 1.6GB까지 자란 건 별개 관찰이다. 위 수정으로 감시 범위는 좁아졌지만 캐시 상한을
  둘지는 안 정했다.
