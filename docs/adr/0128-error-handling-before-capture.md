# 0128. 에러 처리 구조 개선 — before 조사와 캡처

에러바운더리 + throwOnError + Suspense로 에러 처리를 선언형으로 바꾸는 작업을 시작했다.
구현에 들어가기 전에, 개선 전 상태를 증거로 남기는 세션이었다. 포트폴리오 장표를 먼저
만들고, 거기 들어갈 before 스크린샷과 수치를 실측으로 확보했다.

## 왜 이 작업인가

스터디에서 받아온 숙제가 출발점이다. 에러바운더리와 axios interceptor로 에러를 처리하되,
에러바운더리가 못 잡는 비동기 에러를 잡는 방법을 훅으로 만들어 오라는 것. 힌트는 TanStack
Query의 throwOnError였고 Suspense 적용도 포함이다.

에러바운더리는 React가 렌더링하는 도중 던져진 에러만 잡는다. fetch 콜백이나 이벤트 핸들러
안에서 터지는 에러는 렌더링 바깥 콜스택이라 경계가 개입할 자리가 없다. 그런데 비동기에서
받은 에러를 상태에 저장해 뒀다가 다음 렌더에서 다시 throw하면 렌더 중 에러로 바꿔치기할 수
있다. throwOnError는 이 트릭의 TanStack Query 내장판이다. 쿼리가 실패하면 에러를 isError
상태에 담고 끝내는 대신 다음 렌더에서 throw해서 가장 가까운 에러바운더리로 올려보낸다.
Suspense는 같은 발상의 로딩 버전이고, PLick에서 axios interceptor 자리는 이미
`@plick/core/client`의 apiFetch 래퍼가 차지하고 있다(모든 호출이 지나가며 ApiError로 정규화).

## 장표를 먼저 만들었다

포트폴리오 피그마 새 파일에 `포트폴리오 8-1 에러 처리` 장표를 포플8(LCP 폰트 장표) 복제로
만들어 8과 9 사이에 끼웠다. 문제/해결/결과 3절에 before 사진 칸 2개와 after 사진 칸 1개,
4열 결과 표를 자리만 잡아 두고, 캡처를 채우는 순서로 갔다. 개선하고 나면 before를 다시 찍을
수 없으니 순서가 중요했다.

## 예상이 틀렸다 — before는 "빈 화면"이 아니라 "반복"이었다

처음 가설은 "에러 처리를 빼먹은 화면이 조용히 빈 화면으로 죽는다"였다. 그래서 prod 빌드를
띄우고 커서 페이지네이션 요청만 500을 주는 프록시로 /articles를 바닥까지 내려봤는데, "다음
소식을 불러오지 못했어요"와 다시 시도 버튼이 떴다. 릴스도 마찬가지로 다음 페이지 실패 시
재시도 슬라이드가 붙고, 커서가 상한 400은 첫 페이지부터 다시 받는 복구 로직까지 있었다.
홈도 핫이슈와 소식 섹션이 각자 에러 문구를 그렸다. 읽기 경로는 거의 다 처리돼 있었다.

그런데 그 "잘 처리됨"이 곧 문제였다. grep으로 세어 보니 컴포넌트 15곳에 isError·isPending
수동 분기가 54곳이고, 데이터 훅 19개 중 훅 수준 에러 처리는 2개뿐이라 뮤테이션은 콜사이트마다
onError를 다시 짜고 있었다. 새 화면마다 같은 코드를 또 쓰는 구조고, 빼먹으면 무방비가 된다.

실제로 빼먹은 곳이 나왔다. 좋아요 토글(useLikeToggle)은 실패하면 낙관적 갱신을 롤백하고
console.error만 남긴다. 사용자 입장에선 하트가 켜졌다가 소리 없이 원복될 뿐 아무 안내가
없다. 또 기사 상세는 본문 fetch가 500이면 그대로 throw해서 라우트 error.tsx가 페이지 전체를
교체한다. 댓글처럼 멀쩡히 뜰 수 있는 영역까지 함께 사라진다. 부분 실패를 표현할 수단이 없는
것이다. 장표의 서사를 "빈 화면" 대신 이 두 축(수동 반복 54곳 + 빼먹은 틈 실존)으로 바꿨다.

## 캡처 절차에서 배운 것

before 스크린샷은 세 가지 함정을 넘고 나왔다.

- dev 서버로 찍으면 Next 개발용 에러 오버레이가 떠서 실사용자 경험이 아니다. prod
  standalone 빌드로 찍었다(정적 자산 복사 요령은 ADR 0111 측정 절차와 같다).
- `/be` 리라이트의 목적지는 빌드 시점에 굳는다. 특정 엔드포인트만 실패시키려고
  `API_BASE_URL=http://localhost:8081`로 다시 빌드하고, :8081에 BLOCK 정규식에 걸리는
  경로만 500 봉투를 주고 나머지는 :8080 BE로 넘기는 30줄짜리 프록시를 뒀다. 프록시 재시작만
  으로 실패 지점을 갈아끼울 수 있어서 리빌드 없이 장면을 바꿨다.
- 익명 GET은 서버 데이터 캐시(60초 revalidate, KAN-380)에 남아서, BE를 다 막아도 홈이
  캐시로 멀쩡하게 떴다. 서버를 내리고 `.next/standalone/**/.next/cache`를 지운 뒤에야
  실패가 SSR까지 전파됐다.

여기에 하나 더, standalone 서버는 dev 서버와 달리 `.env.local`을 자동으로 읽지 않는다.
로그인 검증 중에 카카오 인가 URL 조립이 KAKAO_CLIENT_ID 부재로 즉사해서 "로그인에
실패했어요"만 떴는데, 네트워크 탭의 login 서버 액션 4건이 전부 0.5kB 즉답 200인 걸 보고
BE까지 가지도 못했음을 알았다. `set -a; source .env.local`로 env를 실어 재기동해 해결했다.

확보한 증거는 세 가지다. ① 좋아요 실패 콘솔 병기 컷(화면은 하트가 멀쩡한데 콘솔엔
"[likes] 좋아요 반영 실패: ApiError" — DevTools 창은 브라우저 패널로 못 찍어서 사용자가
직접 캡처했다), ② 기사 상세 error.tsx 전체 교체 컷(1125x2436 @3x, playwright-core 재활용),
③ 위 grep 수치. 셋 다 장표에 반영했고 원본은 세션 스크래치패드에 있다.

## 다음

구현 단계. 공통 관문(apiFetch)은 이미 있으니 가운데 연결부를 채운다 — throwOnError 정책
(재시도 무의미한 에러만 던지기), 컴포넌트 단위 ErrorBoundary + QueryErrorResetBoundary,
RQ 밖 비동기용 useAsyncError 훅, Suspense 전환. 끝나면 같은 조건으로 after를 찍어 표를
채운다.

## 구현 (같은 세션 후반)

KAN-447로 티켓을 만들고 구현에 들어갔다. 만든 것은 다섯 덩어리다.

### 경계 세 조각

ErrorBoundary는 클래스 컴포넌트로 만들었다. getDerivedStateFromError가 훅 대응물이 없어서
렌더 에러를 잡는 유일한 통로가 클래스 생명주기다. 그 위에 QueryBoundary를 얹었다 —
TanStack의 QueryErrorResetBoundary에서 reset을 받아 ErrorBoundary의 onReset에 물리고,
suspense 훅을 쓰는 자식이면 Suspense까지 씌운다. 이 reset 연결이 핵심이다. 없으면 "다시
시도"가 경계 상태만 지우고 쿼리는 여전히 에러라, 리마운트된 suspense 훅이 캐시의 에러를
그대로 다시 던져 무한 에러 화면이 된다. reset이 쿼리의 에러 상태를 지워야 리마운트가
refetch로 이어진다.

### throwOnError 기본값과 옵트아웃

QueryClient 팩토리(@plick/core)가 config를 받게 바꾸고, 모바일 QueryProvider가
`throwOnError: (error, query) => query.state.data === undefined`를 기본으로 넣었다.
보여줄 데이터가 하나도 없는 실패만 경계로 던진다는 정책이다. 캐시가 있는 실패(다음 페이지,
백그라운드 refetch)는 던지면 오히려 손해다 — 스크롤하던 목록이 통째로 에러 화면이 된다.
그래서 그런 실패는 쿼리 상태로 남기고 화면의 다음 페이지 재시도 UI가 받는다.

기본값을 켜면서 기존 화면이 라우트 error.tsx로 후퇴하는 회귀를 막으려고 세 훅은 명시적으로
껐다. 릴스(커서 400 첫 페이지 복구·재시도 슬라이드), 기사 피드(팀 스와이프 미리보기가 에러를
안 그리는 게 의도), 기자 목록(실패 시 대표 기자 폴백이 설계). 에러를 화면이 직접 소유하는
게 더 나은 자리는 소유권을 존중했다 — 전부 경계로 밀어넣는 게 목표가 아니다.

### suspense 전환

useComments를 useSuspenseInfiniteQuery로, useDebates를 useSuspenseQuery로 바꿨다. 걱정했던
initialData 씨앗은 suspense 훅에서도 그대로 받아 줘서(씨앗이 있으면 suspend 없이 즉시 그림)
SSR 씨앗 패턴과 충돌하지 않았다. 댓글 목록과 VS 리스트에서 isPending 스켈레톤 분기와
isError 분기가 사라졌고, 그 자리는 감싼 QueryBoundary의 fallback·에러 UI 선언이 대신한다.

한 가지 몰랐던 동작: suspense 훅은 씨앗이 없으면 SSR 중에 서버에서도 fetch를 돈다. 댓글만
500인 상태로 기사에 들어가면 서버가 재시도(백오프 포함)를 다 돌고 React #419(SSR 경계
중단)를 스트리밍한 뒤, 클라가 그 경계를 다시 그리며 자기 재시도를 또 돈다. 직렬로 두 번
재시도하는 셈이라 에러 UI까지 14초쯤 걸렸다. 지금은 수용했지만 재시도 정책을 서버/클라
분리하는 개선 여지가 있다.

### 뮤테이션 전역 안전망

MutationCache의 onError는 콜사이트 onError와 무관하게 항상 불린다. 여기에 토스트를 걸어
"onError를 안 단 뮤테이션이 실패하면 기본으로 알린다"를 만들었다. 좋아요와 차단 해제가
그 즉시 수혜자다. 이중 안내를 막는 규칙 둘: 콜사이트가 완결 처리하는 훅(댓글 CRUD·신고·
차단)은 meta.errorHandled로 빠지고, 화면 상태로 처리되는 코드(AUTH_REQUIRED 로그인 유도,
DEBATE_CLOSED 마감 전환)는 코드로 걸러 뺀다. meta 타입은 Register 인터페이스 보강으로
붙여서 오타가 컴파일에 걸린다.

좋아요의 "실패 시 조용히 롤백"은 원래 문서화된 판단이었다(모달은 과하다). 모달이 과하다는
판단은 유지하되 토스트라는 더 가벼운 층이 생겨서, 무반응 대신 지나가는 한 줄로 알리는
쪽으로 바꿨다.

### useAsyncError

숙제의 핵심 훅. 에러를 setState 갱신 함수에 실어 두고 React가 다음 렌더에서 그 함수를
실행할 때 던지게 한다 — 비동기 콜스택의 에러가 렌더 중 throw로 바뀌어 경계 관할이 된다.
실사용처는 릴스의 커서 복구 절차다. restartFeedQuery가 실패하면 예전엔 void로 삼켰는데,
복구의 실패는 더 물러설 데가 없어 경계로 보내는 게 맞다.

### 검증에서 밟은 것

- 검증은 API_BASE_URL을 실패 프록시(:8081)로 굳힌 prod 빌드로 했다. 댓글만 500 →
  기사 본문·투표·추천은 살고 댓글 섹션만 에러+다시 시도(after 캡처), 프록시 정상화 후
  다시 시도 클릭 → 댓글 로드(playwright로 3단계 자동 검증). VS만 500 → 제목 살고 리스트
  자리만 에러. 좋아요만 500 → 하트 롤백 + 토스트(mint-jwt로 세션을 만들어 캡처).
- 앱 브라우저 패널로 실패 화면을 확인하려다 스켈레톤에서 멈춘 것처럼 보여 한참 팠는데,
  document.hidden이 true라 React가 경계 복구 렌더를 미루고 있던 것뿐이었다. 숨은 패널은
  얼어 있다 — 이런 검증은 playwright(visible 취급)로 해야 한다.
- `kill $(lsof -tnP -iTCP:8081)`이 프록시만 죽일 줄 알았는데 그 포트에 연결을 들고 있던
  앱 서버까지 죽였다. lsof는 리스너와 클라이언트를 구분하지 않는다. pkill -f로 바꿨다.

### 수치

수동 분기 총량은 54→50으로 소폭이다. isPending의 대부분이 버튼 비활성 같은 정당한 사용이고
이번에 전환한 화면이 둘이라 그렇다. 실질 변화는 개수보다 기본값이다 — 첫 로드 실패 처리가
"화면마다 손으로"에서 "안 쓰면 경계가 기본"으로 바뀌었고, 무반응 실패 2곳(좋아요·차단 해제)이
0이 됐고, 부분 실패 표현(섹션 단위 에러)이 불가에서 가능이 됐다.
