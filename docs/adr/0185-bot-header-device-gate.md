# 0185. 봇은 봇이라고 적어 보내고, 모르는 봇은 쿠키를 돌려주는지로 가른다

KAN-607. 2026-10-07.

## 무슨 일이었나

AX 지표의 방문자 수가 실제보다 크게 나왔다. 방문자는 기기 식별자(`plick_did` 쿠키, `X-Plick-Device`
헤더) 단위로 세는데, 그 식별자가 사람 아닌 것들에게 너무 많이 발급되고 있었다. dev와 prod의 원인이
달랐다.

dev는 E2E였다. 9월 30일부터 10월 7일까지 기기 187대 중 180대가 E2E에서 나왔고 실제 사람 기기는 7대였다.
E2E 실행 10번(매일 아침 정기 실행과 dev 배포 직후)과 기기가 한꺼번에 생긴 시각 10번이 1분 안쪽으로 다
맞았다. Playwright는 테스트마다 새 브라우저 컨텍스트를 열어 쿠키가 비어 있으니, 프록시가 매번 새 기기
식별자와 새 게스트를 발급한다. E2E는 갤럭시와 데스크톱 크롬 UA를 쓰므로 `CRAWLER_UA_PATTERN`에도 안
걸린다.

prod는 UA를 위장한 크롤러였다. 10월 2일부터 7일까지 기기 5,172대 중 2,589대가 `app_entered`도
`screen_viewed`도 없이 사라졌다. 첫 이벤트에서 마지막 이벤트까지 중앙값이 0.08초였다. 새벽 3시에서
6시에도 시간당 100대 넘게 고르게 들어왔는데 사람 기기는 같은 시간대에 25~36대다. 거의 다 기사 상세
서버 렌더링 한 번(`detail_api`)으로 끝나고 기사 533개를 고르게 훑었다. 10월 4일 23시 8분 ALB 로그에서
IP 하나가 `Mozilla/5.0 (Linux; Android 10; K) ... Chrome/131.0.0.0 Mobile Safari/537.36`으로 1분 동안
페이지 162개를 긁었고 그때 기기 146대가 생겼다. 평범한 안드로이드 크롬 UA라 패턴으로는 못 거른다.

여기에 BE(이준서님)가 댓글로 하나를 더 짚었다. 이름표로 잡히는 크롤러도 문제가 남아 있었다. 10월 6일
6시간 표본에서 페이지 요청 4,725건 중 3,084건(65%)이 패턴에 걸리는 크롤러였는데, 이들은 게스트는 안 받지만
서버 렌더링이 피드를 부르니 `feed_served`가 기기 없이 사람으로 남는다. 노출 321,205건 중 278,301건(87%)이
이 몫이라 "조회 / 노출"이 실제보다 10배 넘게 낮게 나왔다. 그리고 `GoogleOther`가 이름에 bot이 없어
패턴을 지나치고 있었다(6시간 144건).

BE는 KAN-606에서 `X-Plick-Bot: 1`을 받으면 그 요청의 이벤트를 `is_bot = true`로 남기게 바꿔 두었다. 프런트
몫은 그 헤더를 제대로 된 경우에 싣는 것, 그리고 패턴으로 못 잡는 크롤러를 다른 방법으로 거르는 것이다.

## 봇 표시는 헤더 목록에 이름 하나를 더하는 일이었다

[ADR 0161](0161-analytics-headers-proxy.md)에서 분석 헤더를 설계할 때 값을 정하는 자리를 프록시 하나로
못박아 두었다. `resolveAnalytics`가 요청마다 값을 정하고 `forward`가 `ANALYTICS_HEADERS` 전체를 돌며
요청 헤더에 찍는다. 브라우저 `/be` fetch면 그 헤더가 rewrites를 타고 BE까지 그대로 가고, 페이지 요청이면
서버 컴포넌트가 `headers()`로 읽어 서버 측 `apiFetch`에 옮겨 싣는다. 옮겨 싣는 쪽
(`_services/analytics-headers.ts`)도 `ANALYTICS_HEADER_NAMES` 목록을 돈다. 게스트 발급과 재발급 호출은
프록시가 `analytics.headers`를 통째로 넘긴다.

그래서 `ANALYTICS_HEADERS`에 `bot: "X-Plick-Bot"` 하나를 더하고 `resolveAnalytics`가 봇일 때 값을 `1`로
채우면 네 경로(브라우저 fetch, 서버 렌더링 fetch, 게스트 발급, 재발급)가 전부 따라온다. 공용 fetcher
서른 곳은 안 건드렸다. 설계할 때 "앞으로 헤더가 늘면 목록만 고치면 되게" 했던 게 이번에 그대로 먹혔다.

`forward`의 동작 하나를 다시 확인했다. 목록을 돌면서 값이 있으면 `set`, 없으면 `delete`한다. 그래서
브라우저가 `/be` 요청에 `X-Plick-Bot`을 직접 실어 보내도 프록시가 봇으로 안 봤으면 지워진다. 예외는
`X-Plick-Entry`뿐이다(조회 기록처럼 브라우저가 직접 싣는 값을 살린다). 봇 표시는 프록시가 주인이다.

봇 판정은 둘이다. 크롤러(`CRAWLER_UA_PATTERN`)이거나 E2E 쿠키 `plick_e2e`가 있을 때다. E2E 쿠키는
[ADR 0174](0174-e2e-dev-waf-bypass.md)에서 dev WAF를 지나려고 만든 것이라 이미 모든 E2E 요청에 실려
있다. 새 신호를 만들 필요가 없었다. 값은 안 본다. 위조해 봐야 보낸 사람 자기 이벤트가 판단 수치에서 빠질
뿐이고, 그걸 막으려면 WAF 토큰을 프록시가 들고 대조해야 하는데 얻는 게 없다. BE도 같은 판단으로 서명을
안 붙였다(BE DECISIONS 2026-10-07).

판정 자체는 `@plick/core/analytics`의 `isBotRequest`로 뺐다. 두 줄짜리지만 두 앱 프록시가 같은 함수를
부르고 단위 테스트가 걸리는 자리가 생긴다. 쿠키 이름 `E2E_COOKIE`도 같이 두었다. 지금까지 이 이름은
Playwright 설정과 워크플로우 yml에만 문자열로 있었고 앱 코드에는 출처가 없었다.

크롤러의 분석 쓰기를 204로 끊는 분기(KAN-584, [ADR 0181](0181-ax-event-gaps-prefetch-entry.md))는 그대로
두었다. 봇 헤더가 있으니 BE까지 보내도 봇으로 남겠지만, 안 보내는 쪽이 BE 부하도 적고 바꿀 이유가 없다.
E2E는 크롤러가 아니라 이 분기를 안 타고, 쓰기가 BE까지 가서 `is_bot = true`로 남는다. E2E 시나리오가
보는 좋아요 수 같은 화면 동작은 그대로다.

## 쿠키를 돌려주기 전까지는 기기 번호를 안 믿는다

위장 크롤러는 UA로 못 거른다. ADR 0181 회고에 "UA로 거르는 크롤러는 끝이 없다"고 적어 두었는데 그 말이
그대로 현실이 됐다. 이름표 대신 행동으로 가른다. 핵심은 쿠키를 받아서 다시 들고 오는가다.

전에는 쿠키 없는 첫 요청에서 식별자를 만들고, 응답 쿠키에 심고, 그 요청의 헤더에도 바로 실었다. 사람이면
첫 서버 렌더링 이벤트부터 기기가 붙으니 좋지만, 쿠키를 버리는 크롤러도 요청마다 번호 하나씩 BE에 남긴다.
바꾼 뒤에는 첫 요청에서 식별자를 만들어 쿠키에만 심고 헤더에는 안 싣는다. 브라우저가 그 쿠키를 들고 다시
올 때부터 헤더에 싣는다.

사람은 첫 화면이 뜨자마자 `AnalyticsTracker`가 `app_entered`를 `/be`로 보내는데, 그때는 이미 응답 쿠키가
저장돼 있으니 거기서부터 정상적으로 기기가 붙는다. 잃는 건 첫 페이지의 서버 렌더링 이벤트(`feed_served`,
`detail_api`)와 게스트 발급 이벤트(`guest_issued`) 하나씩이다. 티켓이 "첫 서버 렌더링 이벤트 하나만 기기
없이 남는다"고 받아들인 범위다. 쿠키를 버리는 크롤러는 영원히 첫 요청만 반복하므로 기기 번호를 한 번도
못 받고, 방문자로 세어지지 않는다.

이 판정도 순수 함수 `resolveDeviceId`로 뺐다. 입력은 쿠키 값, 전환 배너가 쿼리로 넘긴 값(`?did=`),
`/be` fetch인지, 크롤러인지 넷이고, 출력은 식별자와 "헤더에 실을지"(`send`), "쿠키를 심을지"(`issue`)다.
규칙은 이렇다.

- 쿠키가 형식에 맞으면 그 값을 싣고 안 심는다. `/be` fetch도 같다.
- `/be` fetch인데 쿠키가 없으면 아무것도 안 한다. 배너 쿼리도 안 본다.
- 배너가 넘긴 값이 있으면 소문자로 접어 쿠키에만 심는다.
- 크롤러면 아무것도 안 한다.
- 나머지(쿠키 없는 사람의 페이지 요청)는 새 UUID를 만들어 쿠키에만 심는다.

배너 값을 어떻게 할지 잠깐 고민했다. 배너가 넘긴 값은 다른 앱에서 이미 쿠키를 받은 브라우저가 만든
링크라 "쿠키 없는 첫 방문"과는 다르다. 헤더에 실어도 될 것 같았다. 그래도 티켓 규칙을 문자 그대로 두었다.
첫 페이지 한 번만 비고 다음 요청부터 같은 기기로 이어지니 손실이 작고, 규칙이 "쿠키에서 온 값만 싣는다"
하나로 남는다. 예외를 하나 두면 테스트와 주석이 둘이 된다.

ADR 0181 회고에 "진입 화면 우선순위와 크롤러 차단이 `NextRequest`에 묶여 있어 단위 테스트가 없다"고
적었었다. 기기 식별자 판정도 같은 처지였는데, 이번에 함수로 빼면서 테스트가 생겼다. 새 UUID를 만드는
부분은 두 번째 인자로 주입받아 테스트가 고정값을 끼운다.

## 패턴과 E2E 설정

`googleother`를 두 앱 패턴에 더했다. UA는 `Mozilla/5.0 (Linux; Android 6.0.1; Nexus 5X ...) ...
(compatible; GoogleOther)`로 구글봇과 모양이 같고 이름만 다르다. 단위 테스트의 크롤러 목록에 원문을
넣었다. 반대로 댓글이 의심한 2019년 iOS 13 UA(`iPhone OS 13_2_3 ... Version/13.0.3`)는 사람 목록에 넣어
패턴이 잡지 않는 걸 고정했다. 위장 크롤러가 쓰는 UA지만 진짜 옛 아이폰도 있을 수 있어 UA로 막기는
위험하고, 그쪽은 기기 헤더 게이트가 거른다.

Playwright 설정도 하나 바꿨다. 전에는 `plick_e2e` 쿠키를 dev 대상이면서 `E2E_BYPASS_TOKEN`이 있을 때만
심었다. CI 러너는 늘 토큰이 있지만 팀 IP에서 로컬로 dev를 상대로 돌리면 토큰이 없어 쿠키가 안 실리고,
그 실행은 사람으로 세어진다. 이제 배포 대상(dev, prod)이면 토큰이 없어도 자리 값 `e2e`로 심는다. WAF는
팀 IP를 IP 규칙으로 통과시키니 값이 뭐든 상관없고, 프록시는 이름만 본다. local 대상은 쿠키 도메인이
`.plick.co.kr`이라 안 맞아 뺐다.

## 로컬에서 확인한 것

BE 저장소를 최신으로 받으니 KAN-606이 들어 있어 로컬 BE로 BE 판정까지 볼 수 있었다. 로컬 프로필은
이벤트를 카프카 대신 로그 한 줄(`analytics event type=... device=... bot=...`)로 찍는다. 그 줄을 보면 된다.

BE를 띄우는 데 먼저 막혔다. `.env`의 공유 Supabase가 `tenant/user ... not found`로 거절했다. Docker도 꺼져
있어서 Docker Desktop을 올리고, BE 문서(`docs/ARCHITECTURE.md`)의 절차대로 로컬 Postgres 컨테이너에
테스트 스키마(`src/test/resources/schema.sql`, 테이블 30개)를 넣고 Redis 컨테이너를 띄운 뒤, `DB_URL`
셸 환경변수로 `.env`를 덮어 8082에 올렸다. `spring.config.import`로 읽는 `.env`보다 OS 환경변수가
앞서므로 파일을 안 고쳐도 된다. 데이터는 비었지만 피드 호출은 `feed_served`를 남기고 게스트 발급도
도니 이번 검증에는 충분했다.

모바일 dev(3001)와 웹 dev(3040)를 8082에 붙이고 curl로 여섯 경우를 쳤다. 결과는 전부 기대대로였다.

| 경우                                         | device                               | bot   |
| -------------------------------------------- | ------------------------------------ | ----- |
| 쿠키 없는 첫 페이지, 사람 UA                 | null (응답에 `plick_did` Set-Cookie) | false |
| `plick_did` 쿠키를 들고 온 페이지            | 쿠키 값                              | false |
| `plick_e2e=whatever` 쿠키                    | 쿠키 값                              | true  |
| GoogleOther UA                               | null                                 | true  |
| `/be` fetch, E2E 쿠키 + did                  | 쿠키 값                              | true  |
| `/be` fetch, 쿠키 없이 `X-Plick-Bot: 1` 위조 | null                                 | false |

마지막 줄이 `forward`의 삭제 동작이다. 프록시가 봇으로 안 본 요청의 봇 헤더는 지워진다. `guest_issued`도
같이 봤다. 쿠키 없는 첫 페이지의 게스트 발급은 기기 없이, E2E 쿠키가 있으면 `bot=true`로 남았다.

브라우저 흐름은 모바일 패널로 봤다. 쿠키와 `localStorage`(`plick_last_active`, 30분 세션 기준)를 지우고
다시 들어가니 `guest_issued`는 기기 없이, 바로 뒤의 `app_entered`와 `screen_viewed`는 응답 쿠키로 받은
기기를 달고 왔다. 사람의 첫 방문이 정확히 설계대로 흐른다. 웹은 `127.0.0.1:3040`(localhost와 쿠키 저장소가
갈린다)으로 열어 `guest_issued`가 기기 없이 남는 것까지 봤다. 그 뒤 클라이언트 이벤트는 BE CORS 허용
목록에 `127.0.0.1`이 없어 안 가지만, 그 길은 모바일과 같은 공용 코드다.

한 번 헷갈린 게 있다. 웹 서버를 올린 직후 `guest_issued`에 새 기기가 붙은 줄이 하나 남았다. 새 코드로는
나올 수 없는 조합이라 한참 봤는데, 그 직후의 curl은 전부 새 코드 동작이었다. Next 16 dev의 Turbopack
파일 캐시(`.next/dev/cache/turbopack`, 9월 28일 것)가 옛 `proxy.ts` 컴파일 결과를 되살려 첫 요청 몇 개를
처리하고 몇 초 뒤 재컴파일한 것으로 본다. 옛 코드는 새 기기를 바로 헤더에 실었으니 그 줄과 정확히
맞는다. 브라우저 패널이 서버 준비를 확인하려고 보내는 `HEAD /`도 프록시를 타고 게스트를 발급받는다는 것도
이때 알았다. 검증할 때 dev 서버를 올리고 첫 몇 초의 로그는 믿지 않는 게 낫다.

## 바뀌지 않는 것

이번 변경이 안 건드리는 것도 적어 둔다.

- 위장 크롤러의 게스트 계정은 계속 생긴다. 기기 헤더만 막았지 게스트 발급은 첫 페이지 요청에서 그대로
  일어난다. 방문자 수는 맞아지지만 `users`에 게스트 행은 페이지마다 하나씩 쌓인다. 게스트 발급을 첫
  클라이언트 요청으로 미루면 같이 풀리지만, 게스트 발급 자리가 "GET 네비게이션 중 응답 쿠키를 심을 수
  있는 유일한 자리"(KAN-514)라 구조를 크게 건드려야 한다. 티켓도 범위 밖으로 두었다.
