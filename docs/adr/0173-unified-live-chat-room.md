# 0173. 라이브 채팅을 경기별 방에서 언제나 열린 통합 방 하나로 (KAN-572)

## 무엇을 바꿨나

라이브 채팅은 원래 경기마다 방이 따로 있었다([ADR 0131](0131-live-match-chat.md)). 킥오프 30분 전에 열리고
3시간 뒤에 닫혔고, 모바일은 경기 상세의 채팅 탭, 웹은 경기 상세 우측 aside가 그 경기 방에 붙었다.
그러다 BE가 들어오기 전이라 채팅을 통째로 꺼 뒀다([ADR 0142](0142-live-chat-temporary-close.md), `CHAT_ENABLED=false`).

BE가 KAN-571에서 방 구조를 바꿨다. 경기별 방을 없애고 모두가 들어가는 방 하나를 언제나 열어 둔다.
접속 주소에서 경기 id가 빠지고, 입장 때 주는 최근 메시지가 20개에서 50개로 늘고, 방 전체 전송량 상한에
걸리면 `ROOM_BUSY`라는 거절이 새로 온다. 이번 작업은 화면을 여기에 맞추고, 채팅을 다시 켜는 것이다.

티켓 본문 아래에 기획 결정이 두 줄 붙어 있었다.

1. 웹, 모바일 둘 다 경기 상세의 채팅 탭은 지우지 않고 공용 방으로 바꾼다.
2. 웹 홈의 우측 "실시간 급상승" 상자 밑에 채팅방을 하나 더 둔다. 같은 방이지만 첫 화면에 두어 유입을 늘린다.

그리고 켤지 말지는 사용자에게 물었다. 켜면 develop 푸시와 함께 dev에 바로 노출되고, main 병합 전에는
prod BE(KAN-571)와 prod SSM `CHAT_WS_URL`이 준비돼 있어야 한다. 답은 "켠다"였다. 그래서 `CHAT_ENABLED`를
`true`로 돌렸다.

## 걷어낸 것: 방의 수명

경기별 방 시절 화면에는 "방이 지금 열려 있나"를 판단하는 코드가 곳곳에 있었다.
`@plick/core/chat`의 `chatRoomPhase(kickoffAt)`가 킥오프 시각으로 `before`·`open`·`after`를 돌려주고,
두 앱의 채팅 패널이 이걸로 세 군데를 갈랐다.

- `after`(킥오프 3시간 뒤)면 접속하지 않고 "채팅방이 닫혔어요" 안내만 그렸다.
- 핸드셰이크가 연속으로 거절돼 멈추면, `before`일 때는 "채팅방은 킥오프 30분 전에 열려요", 아니면
  "채팅에 연결하지 못했어요"를 골랐다. 브라우저 웹소켓은 핸드셰이크의 HTTP 상태 코드를 JS에 알려주지 않고
  그냥 1006(비정상 종료)으로 끊기 때문에, 404(방 없음)인지 서버 장애인지를 킥오프 시각으로 짐작한 것이다.
- 웹 패널은 연기·취소 경기면 "채팅방이 열리지 않아요"로 끝냈다.

통합 방은 닫히지 않는다. BE 쪽 거절도 401(토큰)과 403(게스트, 온보딩 미완)만 남고 404와 400이 없어졌다.
그래서 이 판단은 전부 틀린 말이 된다. 종료된 경기를 열어도 채팅은 붙어야 하고, 연기된 경기에서도 마찬가지다.
`chatRoomPhase`, `CHAT_OPEN_BEFORE_MS`·`CHAT_OPEN_AFTER_MS`, 도메인 타입 `ChatRoomPhase`를 지웠다.
연속 거절 문구는 세션 만료(`auth`)가 아니면 "채팅에 연결하지 못했어요" 하나다.

## 접속 주소에서 경기 id 빼기

토큰이 HttpOnly 쿠키라서 브라우저 JS는 토큰을 못 읽는다. 그래서 ADR 0131에서 세션 발급 라우트
`GET /live/chat/session`을 두고, 서버가 쿠키에서 토큰을 꺼내 완성된 `wss://…/ws/chat?matchId=&token=`을
응답 본문으로 내려주게 했다. 이 라우트가 `matchId` 쿼리를 검사하고 없으면 400을 돌려줬다.

이제 `chatSocketUrl(token)`과 `fetchChatSessionUrl()`에서 경기 id 인자를 뺐고, 라우트도 쿼리를 읽지 않는다.
여기서 배포 순서 하나를 따져 봤다. 새 서버가 뜬 뒤에도 옛 JS를 들고 있는 탭이 `?matchId=123`을 붙여 부를 수
있다. 라우트는 이제 쿼리를 아예 안 보니 그냥 같은 주소를 준다. 반대로 FE가 먼저 나가고 BE가 옛날이면
경기 id 없는 접속이 400으로 거절되겠지만, BE KAN-571은 이미 dev에 머지·배포돼 있어서 그 경우는 없다.
BE도 경기 id가 붙어 와도 무시하고 통합 방에 넣게 만들어 두어서 어느 쪽이 먼저 나가도 깨지지 않는다.

## 다시 붙었을 때 목록을 이어 붙이지 않고 갈아 끼우기

예전에는 입장할 때 최근 20개가 오면 그걸 기존 목록 뒤에 `mergeChatMessages`로 이어 붙였다. 서버가 메시지
id를 안 주기 때문에 `userId|sentAt|content`를 키로 삼아 이미 화면에 있는 건 건너뛰었다.

티켓은 다시 붙었을 때 "화면 목록을 이 50개로 바꿔 끼운다"고 했다. 처음엔 기존 병합으로도 중복은 안 보이니
굳이 바꿀 필요가 있나 싶었다. 그런데 통합 방은 사정이 다르다. 여러 경기 이야기와 잡담이 한 방에 몰리니
같은 사람이 같은 초에 "ㅋㅋㅋ"를 두 번 치는 일이 생긴다. 키가 같은 서로 다른 메시지다. 이어 붙이기 방식은
이걸 하나로 뭉갠다. 그리고 끊긴 사이 대화가 50개를 넘으면 화면에 남은 옛 줄과 새 지급분 사이에 구멍이 생기는데,
이어 붙이면 그 구멍이 티 나지 않은 채 한 목록처럼 보인다. 서버가 준 50개가 곧 지금의 정답이니 그걸로
통째로 바꾸는 편이 맞다.

문제는 "어느 프레임이 입장 지급분인가"를 클라가 어떻게 아느냐다. 프레임에는 종류 표시가 없고 언제나
메시지 배열이다. BE 코드(`ChatRoomRegistry.startLive`)를 읽어 보니 순서가 이렇게 보장된다.

1. 핸드셰이크가 끝나면(브라우저에서는 `onopen`) 서버가 레디스에서 최근 50개를 읽는다.
2. 그 사이 방에 들어온 실시간 메시지는 따로 모아 둔다.
3. 락을 잡은 채로 지급분 프레임을 먼저 큐에 넣고, 모아 둔 실시간 분에서 지급분과 겹치는 것을 뺀 나머지를
   그 뒤에 넣는다. 락 안에서 넣으니 실시간 분이 지급분을 앞지르지 못한다.
4. 단, 방이 비어 지급분이 0개면 지급 프레임을 아예 보내지 않는다.

그래서 `ChatSocket`에 `awaitingSnapshot` 플래그를 뒀다. `onopen`에서 켜고, 그 뒤 처음 오는 메시지 프레임을
`snapshot: true`로 넘기고 끈다. 훅은 `snapshot`이면 `replaceChatMessages`로 목록을 갈아 끼우고, 아니면
예전처럼 병합한다. 4번 경우(방이 비었다)에는 첫 실시간 묶음이 지급분 자리에 오게 되는데, 방이 비었다는 건
마지막 메시지 뒤 24시간(BE 보관 기한)이 지났다는 뜻이라 화면에 남은 옛 줄을 지워도 잃을 게 없다.

하나 더 걸렸다. 첫 프레임이 거절 통보(`ERROR`)만 든 배열일 수도 있다. 빈 방에 들어가자마자 뭔가 보냈다가
거절되면 그렇게 된다. 이걸 지급분으로 치면 목록이 빈 배열로 갈린다. 그래서 메시지가 하나라도 든 프레임이
와야 플래그를 소모하게 했다.

## ROOM_BUSY: 입력한 글을 지우지 않기

`ROOM_BUSY`는 방 전체 전송량이 서버 한 대의 초당 상한을 넘었을 때 보낸 사람에게만 오는 거절이다.
메시지는 방에 나가지 않고, 접속은 유지된다. 티켓은 "입력한 글을 지우지 말고 안내를 띄운다"고 했다.

여기서 바로 막혔다. 입력창은 보내는 순간 비운다. `socket.send()`가 true면 `setValue("")`다. 서버의 거절은
그 뒤에 비동기로 온다. 거절을 받는 시점에는 지울 글이 이미 없다. 선택지는 둘이었다.

- 서버 확인이 올 때까지 입력창을 안 비운다. 하지만 서버는 성공 응답(ack)을 따로 안 준다. 내 메시지가
  방 브로드캐스트로 되돌아오는 걸 성공으로 봐야 하는데, 키가 같은 메시지가 겹칠 수 있다는 앞의 문제가
  다시 생기고, 채팅 입력이 느리게 느껴진다.
- 보낼 때 비우되, 튕기면 되돌려 채운다.

뒤쪽으로 갔다. 훅이 마지막으로 보낸 글을 `lastSentRef`에 들고 있다가, `ROOM_BUSY`가 오면
`bounced = { content, at }`을 내보낸다. 입력창(`Composer`)은 이 값이 바뀌면 그 글을 다시 채운다.
사용자가 그 사이 새 글을 치고 있었다면 덮지 않는다. `at`을 둔 이유는 같은 글이 두 번 튕겼을 때도
새 값으로 인식되게 하려는 것이다.

어느 글이 튕겼는지는 "마지막 글"로 짐작한다. A, B를 연달아 보냈는데 A가 튕기고 그 통보가 B 뒤에 오면
B가 채워진다. 서버가 메시지 id를 주지 않는 한 정확히 맞출 방법이 없고, 접속당 한도(5초에 5건)가 먼저
걸리니 연달아 보내는 경우 자체가 드물어 이 정도로 뒀다.

`RATE_LIMITED`에는 이 되돌리기를 붙이지 않았다. 그 통보는 계속 던지는 동안 한 번만 오는 것이라
(ADR 0131, KAN-465) 마지막 한 건만 되돌려 봐야 그 사이 버려진 것들과 앞뒤가 안 맞는다. `ROOM_BUSY`는
BE가 매번 보낸다(접속당 한도가 먼저 걸려서 한 사람이 받는 통보도 5초에 5건을 못 넘는다).

구현에서 하나 짚을 것은 "props가 바뀌면 state를 맞춘다"를 effect로 하지 않은 점이다.
`useEffect(() => setValue(bounced.content), [bounced])`로 쓰면 한 번 그린 뒤 다시 그리게 되고, 요즘 React
린트 규칙은 effect 안의 동기 setState를 경고한다. 대신 렌더 중에 이전 값(`restored`)과 비교해 다르면
바로 state를 고치는 패턴을 썼다. React는 렌더 도중의 setState를 감지하면 자식을 그리기 전에 그 컴포넌트를
즉시 다시 렌더한다. 한 번의 커밋으로 끝난다.

## 진입 자리

"채팅 진입을 경기 상세 안이 아니라 언제든 들어갈 수 있는 자리로 옮긴다(위치는 기획과 정한다)"가 티켓 문장이었고,
기획 결정은 웹 홈 레일이었다. 모바일은 따로 정해진 게 없어서 이미 있던 자리를 살렸다.

모바일 LIVE 목록 맨 위에는 원래 채팅방 배너가 있었다(시안 KAN-567). 경기별 방 시절에는 오늘 진행 중인 경기가
있을 때만 떴고, 누르면 그 경기 상세(첫 탭이 채팅)로 갔다. 진행 중 경기가 없는 날엔 배너가 없었다. 이 판정을 위해
LIVE 페이지는 다른 날짜를 보고 있을 때도 오늘 목록을 한 번 더 받아 왔다(`getMatches(today)`).

통합 방에서는 배너가 늘 떠야 하고, 갈 곳도 특정 경기가 아니다. 그래서 `/live/chat` 라우트를 새로 만들었다.
상단바("채팅방") 아래 남는 높이를 채팅 패널이 다 가져가고 입력바가 화면 하단에 붙는다. 경기 상세 채팅 탭과
같은 배치라 같은 패널을 그대로 쓴다. 하단 탭바는 두지 않았다. 탭바가 있으면 입력바가 그 위로 떠야 하고,
키보드가 올라올 때 두 개의 하단 요소가 겹친다. 배너가 늘 뜨니 LIVE 페이지의 오늘 목록 추가 요청과
`liveChatMatch` 헬퍼도 지웠다. 채팅 지면은 로그인 전용 대화라 `noindex`다.

웹은 `SideRail`에 `chat` 속성을 두고 홈만 켰다. `SideRail`은 홈, 기사 세부, 이슈, 투표 페이지가 같이 쓰는
레일이다. 다 붙이면 페이지를 옮길 때마다 소켓을 새로 열고 닫는다. 페이지 이동 한 번이 접속 한 번이고,
입장마다 50개를 다시 받는다. 티켓도 홈만 말했다.

웹 쪽 구조도 정리했다. 전에는 경기 상세 전용 `live/_components/MatchChatPanel`과, 채팅 API가 없던 시절
레일 자리만 잡아 둔 껍데기 `_components/ChatRail`이 따로 있었다. 이제 홈과 경기 상세 두 화면이 같은 카드를
쓰니 레이어 규칙(두 화면 이상 공용이면 `_components/`)대로 `_components/LiveChatPanel`로 옮기고, 껍데기는 지웠다.
이름도 바꿨다. 경기와 무관해졌으니 `useMatchChat`은 `useLiveChat`, 패널은 `LiveChatPanel`이다.

웹 패널에 게스트 안내도 붙였다. 모바일에는 KAN-514부터 있었는데 웹에는 없어서, 게스트가 들어오면 서버가 403으로
세 번 거절한 뒤 "연결하지 못했어요"가 떴다. 경기 상세 aside만 있던 때는 드문 경로였지만 홈 레일에 올라오면
게스트가 가장 먼저 보는 자리가 된다.

## 홈 레일에서 입력줄이 잘리는 문제

처음엔 홈 레일 목록 높이를 `min-h-82.5 max-h-[50dvh]`로 뒀다. 최소는 시안 높이 330px이고 메시지가 차면
화면 절반까지 자라게 한 것이다. 브라우저에서 1440x900으로 재 보니 채팅 상자만 540px이었다.

우측 레일은 `position: sticky`로 상단바 아래 붙는다. sticky 요소는 뷰포트보다 길면 아래쪽이 잘린 채로 붙어 있고,
그 잘린 부분은 부모(본문 그리드)가 끝날 때까지 스크롤해야 보인다. 홈 본문은 무한 스크롤 피드라 사실상 끝이 없다.
dev 사이트에서 급상승 상자 높이(252px)와 sticky 오프셋(120px)을 재어 더해 보니 900px 화면에서 입력줄이
화면 밖으로 밀렸다. 입력줄이 안 보이는 채팅방은 쓸 수 없다.

그래서 홈 레일은 목록을 `h-82.5`로 고정했다. 채팅 상자가 419px이 되고 120 + 252 + 14 + 419 = 805로 900 안에 든다.
경기 상세 aside는 sticky가 아니라 기존 `min-h-113 max-h-[70dvh]`를 그대로 뒀다.

## 검증

dev로 실제 접속을 먼저 보려 했다. ADR 0131 때는 dev-api 공개 ALB가 보안 그룹으로 막혀 이 맥에서 타임아웃이었는데,
이번엔 `https://dev-api.plick.co.kr/ws/chat`에 업그레이드 헤더를 붙여 토큰 없이 찔러 보니 401이 왔다. 닿기는 한다.
하지만 로컬에서 띄운 FE(오리진 `http://localhost:…`)가 거기에 붙으면 BE의 허용 오리진 검사(`dev.plick.co.kr`,
`dev-m.plick.co.kr`만 허용)에 걸린다. 로그인된 dev 토큰도 필요하다. 결국 "dev 서버로 실제 접속 확인"은
develop에 병합되어 dev에 배포된 뒤에 dev 도메인에서 할 일로 남겼다.

화면 로직은 로컬에서 봤다. 저장소의 채팅 목 서버(`scripts/chat-mock`, node `ws`)를 통합 방 계약으로 고쳤다.
방이 하나고, `matchId`가 와도 무시하고, 입장 때 최근 50개를(빈 방이면 보내지 않고), `POST /busy?on=1`이면
통과할 메시지마다 `ROOM_BUSY`를 돌려준다. 경기 데이터와 `/users/me`는 BE `mock` 프로필(8081)이 주고,
`.claude/launch.json`의 `mobile-chat`·`web-chat`(`next start`, `CHAT_WS_URL=ws://localhost:8090/ws/chat`)으로 붙였다.

- 모바일 LIVE 목록 맨 위에 배너가 경기와 무관하게 떴고, 누르니 `/live/chat`으로 갔다.
- 목 서버에 60건을 심고 들어가니 11~60번 50건이 한 번에 떴다. 목 서버 로그에 `matchId=-`, 경기 id 없이 붙었다.
- `busy` 켜고 "손흥민 골 들어간다"를 보내니 입력창에 글이 그대로 남고 밑에 "채팅이 몰리고 있어요. 잠시 뒤 다시
  보내 주세요"가 떴다. 목록은 50건 그대로. 풀고 다시 보내니 51번째로 붙고 입력창이 비었다.
- `POST /kick?retry=3000`으로 끊고 그 사이 5건을 더 심었다. 다시 붙은 뒤 목록은 50건, 중복 0(고유 50),
  17번부터 65번까지였다. 끊긴 사이의 61~65번과 내 메시지가 다 들어왔다. "다시 연결하는 중" 띠는 사라졌다.
- 목록을 맨 위로 올리고 3건을 심으니 "새 메시지 1개" 버튼이 떴다. 3건인데 1개로 세는 건 기존 동작이다.
  메시지 수가 아니라 목록이 바뀐 횟수(100ms 묶음 단위)를 센다. 이번에 손대지 않았다.
- 킥오프 전 경기(900003) 상세의 채팅 탭이 같은 방을 보여줬다.
- 웹 홈(1440x900) 급상승 밑에 채팅방 상자 419px, 50건. 종료된 경기(900001) 상세 aside도 "방이 닫혔어요"
  대신 같은 방 50건이 떴다.

로컬에서 `pnpm check-types`, `pnpm lint`, `pnpm format:check`, `pnpm build`가 통과했다.

## 남은 것

- dev 배포 뒤 dev.plick.co.kr·dev-m.plick.co.kr에서 로그인 계정 둘로 대화가 오가는지(티켓 완료 조건 마지막 줄).
- main 병합 전에 prod BE에 KAN-571이 올라갔는지, prod SSM(`/plick/frontend/{mobile,web}/prod/env`)에
  `CHAT_WS_URL`이 있는지. 없으면 prod가 채팅을 연 채 붙지 못한다([ADR 0142](0142-live-chat-temporary-close.md) "되살릴 때").
- "새 메시지 N개"를 메시지 수로 세는 것. 통합 방은 흐름이 빨라 차이가 커진다.

## 헤드리스 리뷰

push 전에 `./scripts/review/pr-review.sh`를 돌렸다. 첫 실행은 기본 예산 1달러에서 멈췄다. 파일 이름을 여럿
바꿔서 diff가 2,170줄로 불었고, 모델이 파일을 읽다가 예산이 바닥나 구조화된 결과를 못 내고 끝났다(스크립트는
실행 오류 exit 3). `REVIEW_BUDGET_USD=2.5 REVIEW_MAX_TURNS=24`로 다시 돌리니 15턴, 0.86달러에 CRITICAL 0으로 끝났다.
WARN 하나는 `screen-publishing` 스킬 문서가 옛 이름 `MatchChatPreview`를 가리킨다는 것이라 고쳤다. INFO 하나는
`ROOM_BUSY` 되돌리기가 "마지막 글"로 짐작한다는 한계인데, 위에 적은 그대로라 두었다.
