# 0052. 웹 온보딩 API 이식(KAN-320)과 로그인 재진입 가드

## 이번 세션에서 한 일

모바일에서 검증이 끝난 온보딩 API 두 개를 데스크톱 웹에 이식했다. `POST /api/v1/users/me/onboarding`(닉네임·응원팀 일괄 저장)과 `GET /api/v1/users/nickname-check`(닉네임 중복 확인)다. 그리고 작업 중에 사용자가 짚어준 문제로, 로그인된 유저가 `/login`에 다시 들어가지는 걸 웹·모바일 양쪽에서 막았다.

## 이식은 생각보다 절반이 이미 끝나 있었다

`/web-wire-api` 절차대로 모바일 코드를 먼저 읽었는데, 재밌는 상태였다. 닉네임 중복 확인 쪽(`checkNickname` 서버 액션, `useNicknameCheck` 훅, `NicknameCheckNotice` 표시 컴포넌트)은 KAN-319 프로필 수정 이식 때 이미 웹에 들어와 있었다. 프로필 수정 화면이 닉네임 변경을 하면서 중복 확인이 필요했기 때문이다. 그래서 이번 세션의 순수 신규분은 `submitOnboarding` 서버 액션 하나와, 목데이터로 돌던 온보딩 화면 두 개(W8 닉네임, W9 팀 선택)를 실제 데이터 흐름으로 갈아끼우는 일이었다.

`submitOnboarding`은 모바일 `_services/users.ts`의 것을 그대로 웹 `_services/users.ts`에 복제했다. `"use server"` 서버 액션 파일은 승격하지 않고 앱별 복제로 두는 게 확정 규칙이다(web-wiring.md §2). 쿠키를 읽고 `redirect()`를 부르는 코드라 앱의 라우트 구조에 묶여 있고, 파일이 얇아서 복제 비용이 싸다. 에러 처리 세 갈래(409 `USER_ALREADY_ONBOARDED`는 홈으로 조용히 리다이렉트, 닉네임 중복·금지어는 BE 한국어 문구를 그대로 팝업에, 401은 로그인으로)는 모바일 ADR 0024가 정한 그대로다.

## 승격 판단: 패키지로 올릴 건 없었고, 웹 안에서의 이동만 있었다

web-wiring.md §2의 후보 목록과 대조했는데 이번 엔드포인트가 쓰는 조각은 전부 정리가 끝나 있었다. `apiFetch`·`ApiError`는 KAN-318에서 `@plick/core`로, `TEAM_IDS`는 KAN-319에서 `@plick/domain`으로 이미 올라갔다. 새로 승격할 게 없었다.

대신 웹 안에서의 배치 이동이 하나 있었다. `ErrorDialog`와 `NicknameCheckNotice`는 KAN-319 때 프로필 수정 라우트(`me/edit/_components/`)에 co-locate돼 있었는데, 당시 주석에 "온보딩이 연결되면 `_components/`로"라고 예고를 박아 뒀었다. 이번에 온보딩이 두 번째 소비자가 됐으니 예고대로 `apps/web/app/_components/`로 옮기고 import를 정리했다. 예고 주석을 남겨두는 방식이 실제로 잘 작동했다. 다음 세션의 클로드(나)가 판단을 다시 할 필요 없이 옮기기만 하면 됐다.

## 화면 교체에서 결정한 것들

웹 온보딩 화면은 KAN-247·248 퍼블리싱 때 만든 중앙 카드 레이아웃인데, 동작이 목 기준이라 실계약과 어긋나는 게 두 가지 있었다. 둘 다 사용자에게 물어서 정했다.

첫째, 팀 선택이 단일 선택이었다. 모바일은 KAN-267 피드백으로 다중 선택(빈 배열 허용, 재클릭 해제)이 됐고 BE 계약도 `teamIds` 배열인데, 웹 온보딩만 목 시절의 단일 선택으로 남아 있었다. web-wiring.md §4가 "붙일 때 사용자에게 확인한다"고 예고해 둔 지점이라 물었고, 다중 선택으로 확정했다. 웹 `me/edit`이 이미 다중 토글이라 화면 간 일관성도 이쪽이 맞다.

둘째, 모바일에 있는 "다음에 할게요" 건너뛰기 링크가 웹 카드(피그마 225-2, 224-2)에는 없었다. 가입 시 BE가 자동 닉네임을 부여하므로 건너뛰어도 정상 상태고, 특히 자동 닉네임(plick+숫자)은 금지어 "plick"을 포함해 중복확인을 통과할 수 없어서, 건너뛰기가 없으면 닉네임을 정하기 싫은 신규 유저가 온보딩에 갇힌다. 넣는 걸로 확정하고 웹용 `SkipLink`를 만들었다(데스크톱이라 hover만 얹었다).

닉네임 단계의 동작도 모바일과 맞췄다. 목 시절엔 "비어있지 않으면 통과"였는데, 이제 중복확인 버튼을 눌러 BE 판정을 받아야 "다음"이 열린다. 입력을 바꾸면 직전 확인 결과를 지워서 다음 버튼이 자동으로 다시 잠긴다. 확인 결과는 그 순간의 답이라 제출 때 BE가 다시 검사하고, 그 사이에 누가 같은 닉네임을 선점했으면 팀 선택 화면의 팝업으로 알려준다. 두 단계 사이 닉네임 전달도 모바일과 같은 쿼리 파라미터 방식이다. 온보딩 저장 API가 두 단계 값을 한 번에 받으니 1단계는 전송 없이 값만 나르고, 쿼리 없이 2단계에 직접 들어오면 1단계로 돌려보낸다.

작업 중에 사용자가 제목 굵기를 짚어줘서 두 화면 제목에 `font-extrabold`를 붙였다. 모바일 온보딩 제목이 `text-headline` + `font-extrabold` 조합인데 웹 퍼블리싱 때 굵기가 빠져 있었다.

## 로그인 재진입 가드 — 온보딩 재진입은 일부러 안 막았다

검증 중에 사용자가 두 가지를 물었다. 온보딩을 이미 끝낸 유저가 `/onboarding/*` URL로 들어가지는 것과, 로그인된 유저가 `/login`에 들어가지는 것을 막아야 하지 않느냐는 거였다.

확인해 보니 둘 다 모바일도 같은 상태였다. 즉 이번 이식에서 생긴 문제가 아니라 두 앱 공통의 설계 상태다. 그래서 성격을 나눠서 답했다.

온보딩 재진입은 막지 않는 게 맞다고 봤다. `GET /users/me` 응답에 "온보딩 완료" 플래그가 없어서 FE가 진입 시점에 완료 여부를 알 방법이 없다. `nickname != null`로 추정하는 휴리스틱은 지금 BE(온보딩 전 닉네임 null)에선 통하지만, BE가 예고한 가입 시 자동 닉네임이 들어오는 순간 신규 유저까지 온보딩 완료로 오판해서 온보딩에 못 들어가는 더 나쁜 버그가 된다. 모바일 ADR 0024가 제출 시점 409를 홈 리다이렉트로 삼킨 것도 같은 이유다. 화면 진입은 열어 두되 저장이 거절되면 목적지로 보내는 것. BE에 플래그가 생기면 그때 선제 가드를 붙이면 된다.

`/login` 가드는 반대로 계약 제약이 없고 싸서, 사용자 결정으로 웹·모바일 둘 다 이번에 막았다. 구현에서 한 가지를 조심했는데, 쿠키 존재만 보고 막으면 안 된다. access 쿠키가 있어도 만료·무효일 수 있고, 그 상태의 유저를 홈으로 튕기면 다시 로그인하러 갈 길이 막힌다. 그래서 온보딩 페이지와 같은 패턴으로 `getMyProfile()`을 불러 BE가 세션을 실제로 인정할 때만 홈으로 보낸다. 401이면 null이 돌아와 로그인 화면이 그대로 열린다. 렌더마다 BE 호출이 하나 늘지만 로그인 페이지는 진입 빈도가 낮아 감수할 만하다.

## 검증

계약은 모바일 코드가 이미 검증된 출처라 `be-verify`를 부르지 않았다(web-wiring.md §1 조건에 해당 없음). 화면은 dev(:3000)에서 직접 밟았다. 공유 DB라 일회용 테스트 유저 두 명(`provider_id`에 KAN320 접두어)을 만들어 썼고 끝나고 지웠다.

- 정상 흐름: 닉네임 중복 판정(빨간 X) → 사용 가능 판정(초록 체크, 다음 버튼이 쿼리 실린 링크로 열림) → 팀 다중 선택 토글(선택 2, 해제 1 확인) → 시작하기 → 홈 리다이렉트. DB에서 닉네임과 favorite_teams 두 행(ARS, LIV)을 대조했다.
- 재제출 409: 온보딩 끝난 유저로 팀 화면에 직접 들어가 제출 → 에러 없이 홈으로.
- 제출 시점 중복: 두 번째 유저로 기존 닉네임을 쿼리에 실어 제출 → "이미 사용 중인 닉네임입니다. 이전 단계에서 닉네임을 바꿔주세요." 팝업.
- 가드: 쿼리 없이 팀 화면 직접 진입 → 닉네임 단계로. 비로그인 온보딩 진입 → `/login`으로. 로그인 상태 `/login` 진입 → 홈으로(웹·모바일 각각), 비로그인이면 로그인 화면 정상 렌더.
- 반응형: 330px에서 두 화면 모두 가로 오버플로 0.

지난 세션(KAN-319)에서 배운 zsh `UID` 함정을 피해 변수 없이 갔는데도 한 번 데였다. `TUID=$(db.sh -c "insert ... returning user_id")`로 받으니 psql이 커맨드 태그(`INSERT 0 1`)까지 stdout에 섞어 변수가 여러 줄이 됐고, 그걸 그대로 민팅 스크립트 인자로 넘겨 사용법 에러가 났다. `-tA`여도 커맨드 태그는 나온다. `| head -1`로 첫 줄만 집으면 된다.

빌드는 웹·모바일 둘 다 통과, check-types·lint·format:check도 통과.
