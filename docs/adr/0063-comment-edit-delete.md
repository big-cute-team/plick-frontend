# 0063. 댓글 수정·삭제 API를 웹·모바일에 동시에 붙이다 (KAN-333)

## 무엇을 했나

KAN-333은 지금까지의 웹 이식 티켓들과 결이 달랐다. KAN-329~332는 모바일에서 먼저 검증한 API를
웹으로 옮기는 작업이었는데, 이번엔 댓글 수정(`PATCH /api/v1/comments/{commentId}`)과
삭제(`DELETE /api/v1/comments/{commentId}`)를 두 앱에 처음부터 동시에 붙였다. 티켓 요구는
간단해 보였다. 내가 쓴 댓글에만 수정·삭제 버튼을 보여주고, 누르면 실제로 고쳐지고 지워지면 된다.

늘 하던 대로 계약 확인부터 be-verify 서브에이전트에 맡겼다. 티켓도 스웨거 설명도 믿지 않고
실제로 때려 보는 절차인데, 이번에도 그 값을 했다. 리포트가 돌아오고 나서야 이 티켓의 진짜
문제가 드러났다.

## 막힌 곳: 응답에 "내 댓글" 표시가 없다

댓글 목록 응답(`CommentResponse`)에는 작성자 식별 필드가 전혀 없다. `userId`도 `authorId`도
`isMine`도 없고 `nickname` 문자열 하나뿐이다. "내가 쓴 댓글에만 버튼"을 그리려면 각 댓글이
내 것인지 알아야 하는데, 계약상 그걸 알 방법이 없었다.

닉네임 문자열 대조가 유일한 우회로였는데, be-verify가 DB를 열어 보니 `users.nickname`에는
unique 제약이 없었다. DB만 보면 동명이인이 가능하니 닉네임 대조는 오판할 수 있다는 얘기다.

그런데 코드베이스를 다시 뒤져 보니 실제로는 앱 수준에서 닉네임이 유일했다. 닉네임이 정해지는
경로는 온보딩(`POST /users/me/onboarding`)과 프로필 수정(`PATCH /users/me`) 둘뿐이고, 두 경로
모두 BE가 `USER_NICKNAME_DUPLICATED`로 중복을 거절한다. 별도의 중복 확인 API
(`GET /users/nickname-check`)까지 있다. DB 제약이 없을 뿐 애플리케이션이 유일성을 지키고 있었다.

그래서 이렇게 정리했다. 닉네임 대조로 구현하되, 오판했을 때의 안전망을 확인해 둔다. 설령 버튼이
남의 댓글에 잘못 떠도 실제 수정·삭제 요청은 BE가 소유자 검사를 해서 403 `COMMENT_FORBIDDEN`으로
거절한다(be-verify가 남의 토큰으로 직접 확인했다). 즉 최악의 경우에도 화면 오표시일 뿐 보안
구멍은 아니다. 응답에 `isMine`(또는 작성자 id)을 넣어 달라는 건 BE 요청 사항으로 남겼다.
그게 들어오면 닉네임 대조 로직만 걷어내면 된다.

## 내 닉네임을 클라 컴포넌트까지 어떻게 내리나

닉네임 대조를 하려면 비교 상대인 "내 닉네임"이 댓글 컴포넌트(클라이언트)까지 와 있어야 한다.
그런데 access 토큰은 HttpOnly 쿠키라 브라우저 JS가 못 읽고, 내 프로필을 주는
`GET /users/me`는 인증이 필요해서 서버에서 토큰을 실어 불러야 한다. 클라 아일랜드가 스스로
알아낼 수 없는 값이라 서버가 내려줘야 한다.

마침 똑같은 문제를 이미 한 번 푼 자리가 있었다. 로그인 여부를 나르는 `AuthProvider`다. 루트
레이아웃(서버 컴포넌트)이 쿠키를 보고 판단한 boolean을 컨텍스트로 시드하고, 댓글 입력바 같은
클라 컴포넌트가 `useAuth()`로 꺼내 쓴다. 그 컨텍스트의 주석에 "유저 정보가 붙으면 이 객체를
넓힌다"고 적어 뒀었는데 그 날이 왔다. `{ isLoggedIn: boolean }`을
`{ isLoggedIn, nickname: string | null }`로 넓히고, 루트 레이아웃이 로그인 상태일 때
`getMyProfile()`을 불러 닉네임을 함께 시드하게 했다.

여기서 한 가지 조심한 게 있다. 루트 레이아웃은 모든 화면의 공통 조상이라 여기서 던진 에러는
앱 전체를 죽인다. 닉네임은 어디까지나 버튼 노출용 보조 값이라, 프로필 조회가 실패해도 앱은
떠야 한다. 그래서 `getMyProfile().catch(() => null)`로 삼켰다. null이면 `mine` 판별이 전부
false로 떨어져 수정·삭제 버튼만 안 뜨고 나머지는 멀쩡히 돈다. 부작용으로 로그인 상태의 모든
페이지 렌더에 `/users/me` 호출이 하나 늘었는데, 레이아웃과 페이지는 병렬로 렌더되므로
페이지 자체 fetch와 겹쳐 돌아 체감 지연은 거의 없다고 봤다.

## 삭제를 캐시에 어떻게 반영하나: tombstone의 재발견

삭제 응답은 `data: null`이다. 작성(201로 생성된 댓글이 옴)이나 수정(200으로 수정본이 옴)과
달리 응답으로 캐시를 고칠 재료가 없다. 무효화(invalidate)는 KAN-303 때 정한 대로 피하고
싶었다 — 무한 쿼리를 무효화하면 쌓인 페이지를 전부 순차로 다시 받는다.

그럼 캐시에서 그 댓글을 빼면 되나? 처음엔 그렇게 생각했다가, 대댓글이 딸린 댓글이 걸렸다.
BE는 소프트 삭제고, 대댓글이 있는 댓글을 지우면 목록 조회에 tombstone(`content: null,
isDeleted: true`)으로 계속 나온다는 걸 KAN-303 때 확인해 뒀었다. 그럼 대댓글 없는 댓글은?
이건 아무도 확인한 적이 없어서 be-verify에 추가로 물었다. 답은 "대댓글 유무와 무관하게 전부
tombstone으로 남는다"였다. 대댓글 자체를 지워도 부모의 `replies` 배열에서 안 빠지고
tombstone이 된다.

이게 캐시 정책을 정해 줬다. 캐시에서 항목을 빼 버리면 다음 refetch 때 tombstone으로 되살아나
깜빡인다. 서버가 보여줄 모양 그대로 캐시를 고치는 게 맞다. 그래서 `useDeleteComment`는 대상
댓글을 캐시에서 찾아 `content: null, isDeleted: true`로 덮기만 한다. 화면은 KAN-303 때 이미
만들어 둔 tombstone 분기("삭제된 댓글이에요")가 그대로 받아 준다. 삭제 직후 화면과 refetch
후 화면이 같은 모양이 된다.

수정 쪽 캐시는 더 쉬웠다. PATCH가 수정 반영본을 통째로 돌려주니 그걸로 덮으면 되는데, 통째로
갈아끼우는 대신 `content`와 `isEdited`만 골라 덮었다. 응답의 `replies` 표현이 목록 캐시와
미묘하게 다를 가능성(검증 안 된 영역)을 차단하려는 보수적인 선택이다. 대댓글 수정이면 캐시에서의
자리가 부모의 `replies` 안이라, 댓글 좋아요(`useCommentLike`) 때 만든 2단 순회 패턴을 그대로
따랐다.

## 카운트 배관

댓글 수 헤더는 서버 스냅샷 + 로컬 증감으로 돌고 있었다. 작성 성공마다 `onPosted` 콜백이 올라와
+1 하는 구조라, 대칭으로 `onDeleted`를 뚫어 -1 하게 했다. BE의 `commentCount` 집계가 삭제된
댓글을 빼고 세는 걸 확인해 뒀으므로(대댓글도 센다) 댓글이든 답글이든 삭제 성공은 -1이 맞다.
콜백은 `CommentList` → `CommentThread` → `CommentItem`으로 내려가고, 소비처는 기사 세부
(`ArticleComments`)와 릴 세부(모바일 시트, 웹 패널) 세 곳이다.

## UI: 있는 관용만 조립했다

새로 그린 건 사실상 없다. 수정·삭제 버튼은 액션 줄의 "답글" 버튼과 같은 텍스트 버튼으로 옆에
붙였고, 수정을 누르면 본문 자리가 인라인 폼(`CommentEditForm`)으로 바뀐다. 폼의 입력 스타일과
글자수 제한(500자), 에러 문구 자리는 작성 입력바(`CommentComposer`)에서 가져왔다. 삭제는
로그아웃 확인 팝업과 같은 스크림+카드+두 버튼 확인 팝업(`ConfirmDialog`)을 새로 컴포넌트로
묶어 띄운다. 소프트 삭제라 데이터는 남지만 사용자 입장에선 되돌릴 수 없는 동작이라 확인을
한 번 거치게 했다.

`ConfirmDialog`는 body로 포털을 뚫는다. 이유는 `LoginPromptDialog` 때(KAN-308) 겪은 것과
같다 — 릴 세부 시트는 `translateY`로 오르내리는데, `transform`이 걸린 조상은 `position: fixed`의
기준 상자가 돼서 팝업이 화면이 아니라 시트 조각만 덮는다.

에러 처리는 화면마다 결을 맞췄다. 수정 실패는 폼 밑에 인라인 문구(BE 메시지가 이미 사용자용
한국어다), 삭제 실패는 확인 팝업 안에 문구를 남겨 팝업을 연 채 바로 재시도할 수 있게 했다.
토큰 만료(401 `AUTH_REQUIRED`)만 예외로 로그인 유도 팝업으로 돌린다. 남의 댓글을 건드렸을 때의
403 `COMMENT_FORBIDDEN`은 정상 경로에선 버튼 자체가 안 떠서 도달할 수 없지만, 닉네임 오판이나
다른 기기에서의 선점 삭제 같은 경우에 BE 메시지("본인 댓글만 수정·삭제할 수 있습니다.")가
그대로 보인다.

## 공용화 판단

이번에도 승격은 안 했다. 서버 액션(`updateComment`·`deleteComment`)은 쿠키 이름이 앱에 박혀
있어 작성 액션과 같은 이유로 앱별 복제(KAN-329에서 정한 방침), 뮤테이션 훅도 같은 이유로 앱별.
`ConfirmDialog`와 `CommentEditForm`은 모바일이 active, 웹이 hover·focus로 인터랙션이 갈려서
ADR 0011 게이트 B에 걸린다. 도메인 타입(`UpdateCommentResult`·`DeleteCommentResult`)만
`@plick/domain`에 추가했다 — 이건 원래 단일 출처다.

웹과 모바일을 동시에 구현하다 보니 복제 파일 쌍이 네 개 더 늘었다(훅 둘, 컴포넌트 둘). 지금까지는
"모바일 먼저, 웹은 두 번째 사용처"라는 순서가 승격 판단의 리듬을 만들어 줬는데, 동시 구현은 그
리듬이 없어서 처음부터 공용으로 빼고 싶은 유혹이 컸다. 그래도 게이트 B(인터랙션 동일성)에서
걸리는 건 똑같아서 앱별로 뒀다. 댓글 UI 덩어리 전체의 승격 여부는 ADR 0011 §7 후보 목록 건이다.

## 남은 것

- BE에 `CommentResponse` 작성자 식별 필드(`isMine` 또는 `userId`) 추가 요청. 들어오면
  `AuthProvider`의 닉네임 시드와 닉네임 대조를 걷어내고 응답 필드로 바꾼다.
- 닉네임 변경 직후에는 옛 닉네임으로 캐시된 댓글 목록과 새 닉네임이 어긋나 내 댓글에 버튼이
  잠깐 안 뜰 수 있다. 캐시 수명(60초) 안의 일시 현상이라 그대로 뒀다.
