# 0202. 매일 아침 깨지던 E2E 하나: CDN이 준 묵은 홈 씨앗과 "기사 더 보기" 클릭의 경합 (KAN-666)

## 증상

GitHub에 E2E 워크플로우 실패 알림이 사흘 연속 왔다. 10-17, 10-18, 10-19 새벽 2시대 스케줄 런이 전부
빨간불이었고, 열어 보면 매번 같은 한 건이었다. `specs/mobile/articles.spec.ts`의
"기사 더 보기를 누르면 홈 리스트에 이어 붙는다". 나머지 17건은 통과했다. 재시도 1회도 같은 자리에서 같은 값으로
죽었다.

```
Error: expect(received).toBeGreaterThan(expected)
Expected: > 10
Received:   10
Call Log:
- Timeout 10000ms exceeded while waiting on the predicate
```

홈에 기사 10건이 떠 있고, "기사 더 보기"를 눌렀는데 10초가 지나도 10건 그대로라는 뜻이다.

마지막 배포는 10-16 KAN-665 두 PR이었다. 게스트 토큰 발급을 페이지 응답에서 떼어 브라우저가 따로 받아 가게 한
변경이고([ADR 0201](0201-guest-issue-off-page-response.md)), 그래서 홈 같은 익명 페이지를 CloudFront가
저장할 수 있게 됐다. 배포 직후 10-16 05:51 런은 통과했고, 그 뒤 손댄 코드가 없는데 다음 날부터 깨졌다. 코드가
아니라 환경이 바뀐 신호였다.

## 먼저 버린 가설들

처음 떠오른 건 dev BE가 2페이지를 못 주는 경우였다. dev DB의 기사가 10건뿐이거나 커서가 상했거나. 그런데 홈
HTML의 씨앗에 `nextCursor`가 박혀 있었고, `/be/api/v1/articles?size=10&cursor=...`를 curl로 치니 2페이지도
10건이 정상으로 왔다. BE는 아니었다.

다음은 로컬 재현이었다. 같은 spec을 dev 상대로 로컬에서 돌리니 1.6초에 통과했다. 트레이스를 열면 클릭 뒤에
`cursor=`가 붙은 2페이지 요청이 찍혀 있었다. 그래서 CI 런의 아티팩트를 받아 트레이스를 뜯었다
(`gh run download`). 거기엔 커서 요청이 아예 없었다. 대신 커서 없는 `articles?size=10` 요청이 한 번, 200으로
끝나 있었다. 클릭이 다음 페이지를 부르지 못했고, 대신 누군가 1페이지를 다시 받아 간 것이다.

## 1페이지를 다시 받은 이유

홈의 기사 리스트는 서버 컴포넌트가 첫 페이지를 받아 `initial`로 내려주고, 클라이언트의 `useArticleFeed`가
그걸 TanStack Query의 `initialData`로 심는다. 이때 씨앗의 나이를 `initialDataUpdatedAt`에 서버가 받은 시각
`fetchedAt`으로 달아 둔다. `staleTime`은 30분(`FEED_FRESH_MS`)이다. 씨앗이 30분보다 오래됐으면 마운트하면서
1페이지를 다시 받는다. 화면에 오래 머문 뒤 되돌아온 탭의 묵은 씨앗을 방금 받은 것처럼 취급하지 않으려고 넣은
장치다.

CI가 받은 홈 HTML의 `fetchedAt`을 읽었다. 1792289711628, 즉 2026-10-18 02:15:11 UTC. 테스트는 10-19
02:30에 돌았으니 씨앗이 정확히 24시간 15분 묵었다. 그리고 02:15는 전날 E2E 런이 돈 시각이다.

응답 헤더가 설명해 줬다.

```
x-cache: Hit from cloudfront
x-nextjs-cache: STALE
cache-control: s-maxage=20, stale-while-revalidate=31535980
```

홈은 KAN-632부터 20초 ISR이다([ADR 0199](0199-no-store-bfcache-problem.md)). ISR(Incremental Static
Regeneration)은 Next가 페이지를 한 번 그려 두고, `revalidate` 초가 지난 뒤 들어온 요청에는 묵은 페이지를
바로 내주면서 뒤에서 새로 굽는 방식이다. 그래서 요청이 뜸하면 "다음 요청"이 올 때까지 묵은 채로 남는다.
`stale-while-revalidate`는 CDN에게도 같은 허락을 준다. 20초가 지난 뒤에도 1년 동안은 저장된 걸 내주고 뒤에서
원본에 다시 물어보라는 뜻이다.

dev는 트래픽이 없다. 홈을 다시 굽게 만드는 요청이 하루에 한 번, E2E 런뿐이다. 그러니 어제 런이 구운 페이지를
오늘 런이 받는다. CI 러너가 붙는 CloudFront POP(미국 IAD)도 하루에 그 한 번만 두드려진다. 재시도 런이 받은
응답은 `age: 16`이었는데 씨앗은 똑같이 하루 전 것이었다. 첫 테스트가 받은 묵은 응답을 CloudFront가 20초 동안
들고 있다가 그대로 준 것이다.

로컬에서 통과한 이유도 같은 자리에서 갈린다. 내 요청은 서울 POP으로 가고, 팀원들이 수시로 들어오니 씨앗이 2분
전 것이었다. 30분 안이라 재요청이 없다.

## 클릭이 사라진 메커니즘

재요청이 왜 클릭을 먹었나. `NewsFeed`의 "기사 더 보기" 버튼은 `disabled={isFetching}`이다. KAN-404 때 넣은
보호다. 1페이지를 다시 받는 중에 캐시에 남은 옛 커서로 다음 페이지를 쏘면 복구 refetch가 취소되면서 400 루프에
갇혀서, 1페이지가 돌아오는 동안은 버튼을 잠근다.

Playwright의 `click()`은 요소가 보이고 활성화돼 있는지 확인한 뒤 누른다. 그런데 테스트가 보는 첫 버튼은 서버가
그린 HTML의 버튼이다. 서버 렌더 시점엔 `isFetching`이 false라 활성이다. 테스트는 `goto("/")`가 끝나고 첫
`article`이 보이자마자 누른다. 그 직후 하이드레이션이 끝나면서 묵은 씨앗 판정이 나고 재요청이 나가고 버튼이
잠긴다. 클릭이 이 틈에 떨어지면 비활성 버튼은 클릭 이벤트를 내지 않으니 아무 일도 없다. 재요청이 끝나 버튼이
풀려도 클릭은 다시 오지 않는다. 10건에서 멈추고 10초 뒤 실패한다. CI 러너는 느려서 하이드레이션과 재요청
216ms가 클릭과 겹치기 좋았다.

이걸 로컬에서 재현하는 데 두 번 걸렸다. 먼저 `page.route`로 홈 HTML을 가로채 `fetchedAt`을 하루 전으로 바꿔
봤다. 재요청은 나갔다. 트레이스에 커서 없는 `size=10` 요청이 찍혔다. 그런데 옛 spec도 통과했다. 내 기기가
빨라 재요청이 76ms에 끝나고 클릭이 그 뒤에 도착한 것이다. 그래서 커서 없는 1페이지 요청만 2초 늦추는 라우트를
하나 더 걸어 잠금 구간을 넓혔다. 그러자 옛 spec은 CI와 같은 모양으로 죽었고(10건, 11.5초), 고친 spec은 4.1초에
통과했다.

## 어떻게 고쳤나

앱이 아니라 테스트를 고쳤다. 버튼 잠금은 KAN-404의 보호라 풀 이유가 없고, 묵은 씨앗을 다시 받는 것도 CDN 캐시를
연 이상 맞는 동작이다. 실사용자는 페이지가 뜬 뒤 200ms 안에 맨 아래 버튼을 누르지 못하니 겪지 않는 경합이다.

spec은 클릭과 개수 확인을 `expect(async () => {...}).toPass()`로 한 묶음에 넣었다. 누르고 3초 안에 개수가
안 늘면 다시 누른다. 전체 15초 안에 한 번이라도 늘면 통과다. 클릭이 삼켜진 경우에만 두 번째 클릭이 나가고,
첫 클릭이 먹었으면 2페이지가 300ms 안에 와서 한 번으로 끝난다. 두 번째 클릭이 재요청 중에 떨어지면 Playwright가
비활성 상태를 보고 풀릴 때까지 기다린 뒤 누른다.

```ts
const loadMore = page.getByRole("button", { name: "기사 더 보기" });
await expect(async () => {
  await loadMore.click();
  await expect
    .poll(() => articles.count(), { timeout: 3_000 })
    .toBeGreaterThan(before);
}).toPass({ timeout: 15_000 });
```

하이드레이션을 기다리는 쪽도 생각했다. 브라우저가 발급을 부르는 `POST /api/session/guest` 응답을 기다리면 그
뒤는 하이드레이션이 끝난 상태다. 그런데 쿠키가 이미 있는 컨텍스트에선 발급이 안 나가고, `networkidle`은
트윗 임베드가 계속 폴링해서 끝나지 않는다(home.spec의 주석). 테스트가 앱 내부 신호에 기대는 것보다 사용자처럼
"안 되면 다시 누른다"가 덜 깨진다고 봤다.

## prod는 어떤가

지금 prod 홈은 `private, no-store`에 CloudFront `Miss`다. KAN-632부터 665가 아직 main에 없다. develop이
main으로 가고 ADR 0201의 CloudFront 콘솔 작업까지 하면 그때부터 같은 캐시가 켜진다.

켜진 뒤 생길 수 있는 것과 아닌 것을 가르면 이렇다. 유저별 값이 공용 캐시로 새는 일은 없다. 홈 서버 렌더는 토큰
없이 익명으로 받고(`sharesDataCache`가 인증 없는 GET만 공유 캐시로 보낸다), 좋아요 같은 내 상태는 KAN-664에서
브라우저가 따로 받아 덧씌운다. 쿠키를 심거나 지우는 응답은 프록시 안전핀이 `private, no-store`로 덮는다. 묵은
HTML이 지워진 청크를 가리키는 일도 없다. 정적 자산 S3 sync에 `--delete`를 붙이지 않아 구세대 청크가 남는다.

남는 건 요청이 뜸한 POP의 첫 방문자가 마지막으로 구워진 페이지를 받는다는 점이다. 한국은 트래픽이 있어 몇 초에서
1분이고, 해외 POP은 dev처럼 하루 묵을 수 있다. 씨앗이 30분을 넘으면 300ms 안에 최신으로 갈아끼워지지만 그 순간
목록이 바뀌는 게 보인다. 새 글이 시간당 한두 개라 체감은 작다. 줄이고 싶으면 홈의 `stale-while-revalidate`를
1년에서 몇 분으로 낮추는 선택지가 있는데, 원본 장애 때 묵은 페이지로 버티는 효과와 맞바꾸는 일이라 이번엔 두지
않았다.

## 남은 것

- dev 홈의 하루 묵은 씨앗 자체는 그대로다. E2E 런 외의 트래픽이 생기지 않는 한 매일 같은 조건이고, 이 spec은
  그 조건에서도 통과하게 됐다. 다른 "누르면 요청" 시나리오가 같은 자리에서 깨지면 이 패턴을 쓴다
- prod에 KAN-665를 배포할 때 ADR 0201의 CloudFront 캐시 정책 교체 콘솔 작업이 함께 가야 한다. 안 하면 지금처럼
  `Miss`가 이어지고 이 ADR의 prod 절은 해당 없다
