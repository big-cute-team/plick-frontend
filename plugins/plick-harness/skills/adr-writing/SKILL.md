# 세션 ADR 쓰기

ADR은 사내 규격 문서가 아니라 나중에 블로그나 포트폴리오에 올릴 내 회고 글이다.
한 세션(같은 브랜치, 같은 PR)에 파일 하나다. 세션 중 변경이 생기면 새 파일을 만들지 말고 그 파일에 절을 이어 붙인다.

파일 이름은 `docs/adr/000N-<짧은-설명>.md`이고 N은 기존 최댓값 다음 번호다. 커밋에 포함한다.

## 문체

1인칭 회고 흐름으로 쓴다. 이걸 만들었다, 여기서 이런 문제를 만났다, 이렇게 풀었다를 자연스럽게 이어 쓴다.
담백한 `~했다`체로, 막힌 데는 막혔다고 솔직하게 쓴다.

자세히 쓴다. 시행착오를 다 적는다. 어떤 걸 시도했다가 왜 버렸는지, 어디서 몇 번 막혔는지까지 남긴다.
나중에 읽는 사람이 초보자여도 완전히 이해할 수 있게 쓰는 게 목표다. 분량을 아끼지 않는다.

기술 메커니즘은 끝까지 파고들어 설명한다. 서버 액션, 쿠키, 내비게이션(soft/hard, prefetch), 캐싱,
서버와 클라 경계, 리다이렉트, 훅의 exit code 계약, 권한 규칙과 모드의 우선순위처럼
어떻게 왜 그렇게 되는가가 걸리는 대목은 얼버무리지 않는다. 요청과 응답 흐름, 무엇이 어디서 도는지,
왜 그 방식인지까지 풀어 쓴다. 읽는 사람이 나중에 따로 되물을 필요가 없어야 한다.
`"use server"`는 서버 액션이지 단순 서버 실행이 아니고, `cookies()`는 요청 헤더를 읽고 `Set-Cookie`로
지시하는 것이며, `redirect()`는 리로드가 아니라 소프트 내비게이션이라는 식으로,
오해하기 쉬운 지점은 정의부터 바로잡아 준다.

전문용어는 처음 나올 때 한 줄로 풀어준다.

AI 티 나는 말투는 금지다. 과장 형용사(강력한, 매끄러운, seamless, robust류), "결론적으로"와
"~할 수 있습니다" 남발, 기계적 나열, 문단마다 소제목 다는 습관을 피한다.

## 구성

정해진 목차는 없다. 다만 개선 작업이면 항목마다 "전에는 어땠나, 무엇이 문제였나, 어떻게 바꿨나, 바꾸고 나서
무엇이 달라졌나(측정값이 있으면 숫자로)"가 빠지지 않게 쓴다. 포트폴리오에서 그대로 쓰는 단위가 그것이다.

다른 규칙이나 화면과 얽히면 CLAUDE.md "더 읽을 것"과 관련 스킬, 관련 ADR에 상호 링크한다.

## 생략

오타 수정이나 포맷만 한 세션은 생략할 수 있다. 판단이 서지 않으면 남기는 쪽으로 간다.

기존 0002~0011은 옛 격식 톤이라 그대로 두고, 이 문체는 새로 쓰는 ADR부터 적용한다.
